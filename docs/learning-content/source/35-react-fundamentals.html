React Fundamentals — JSX, Component, State & Rendering

Nền tảng React 18 cho phỏng vấn: JSX, props/state, key, composition, event, controlled input, reconciliation và automatic batching.

JSX, component và dòng dữ liệu một chiều

Q1 JSX là gì, nó biên dịch thành gì và vì sao JSX phải có một phần tử cha?

What

JSX là cú pháp mở rộng của JavaScript cho phép viết cấu trúc UI ngay trong code, được Babel hoặc TypeScript compiler dịch thành lời gọi hàm tạo React element — plain object mô tả UI chứ không phải DOM node thật. Từ React 17, automatic JSX runtime dùng jsx() và jsxs() từ react/jsx-runtime thay cho React.createElement, nên file không còn bắt buộc import React.

Why

JSX chỉ là syntactic sugar nhưng cho phép compiler kiểm tra type và báo lỗi ngay lúc build thay vì ghép chuỗi HTML thủ công, đồng thời gom cả cấu trúc cây vào một expression. Vì một function component phải return đúng một giá trị, khi có nhiều phần tử anh em bắt buộc phải bọc chúng lại — nếu không compiler báo lỗi adjacent JSX elements và bạn phải tự thêm wrapper.

How
Nguồn .tsx (JSX)
↓ Babel / tsc transform lúc build
jsx("h1", { children: "Hi" })
↓ chạy khi render, trả về object
React element: cặp type + props + key
↓ reconciler so sánh và commit
DOM node được mount hoặc cập nhật

React element là mô tả bất biến và rẻ để tạo; DOM thật chỉ sinh ra ở bước commit. Fragment (<>...</>) nhóm nhiều con mà không thêm node nào vào DOM, nên không phá layout flex/grid hay cấu trúc bảng.

When

Dùng JSX cho mặc định của mọi component React. Dùng Fragment khi hai phần tử anh em cùng cấp cần nằm trong cùng một return, ví dụ một component trả về nhiều ô <td> trong khi phần tử <tr> do component cha quản lý cấu trúc.

When NOT

Không lạm dụng wrapper <div> khi chỉ cần Fragment vì DOM thừa làm sai CSS; ngược lại đừng dùng Fragment khi thật sự cần một node bọc, vì Fragment không nhận className, style, và dạng shorthand <>...</> cũng không truyền được key. Không cần JSX nếu muốn gọi jsx() trực tiếp, nhưng cách đó khó đọc.

// 1) Nguồn TSX
const el = <h1 className="title">Hello</h1>;

// 2) Output của compiler (automatic runtime, không cần import React)
import { jsx as _jsx } from "react/jsx-runtime";
const el2 = _jsx("h1", { className: "title", children: "Hello" });

// 3) Fragment: nhiều con, không sinh node DOM thừa
function Cells() {
  return (
    <>
      <td>SKU-01</td>
      <td>12</td>
    </>
  );
}

// Dạng đầy đủ <React.Fragment key={id}>...</React.Fragment> là cách duy nhất
// để vừa nhóm nhiều con vừa truyền key cho chính nhóm đó.
Use case

Bảng tồn kho: component SkuCells trả về ba ô <td> cho một dòng, và nó được gọi bên trong <tr>. Fragment giữ cấu trúc bảng hợp lệ, còn nếu bọc <div> thì browser sẽ đẩy node ra ngoài bảng khi parse.

Pitfall / Interview trap

Nhầm JSX với HTML: JSX dùng className thay class, htmlFor thay for, mọi attribute đều camelCase, và biểu thức phải bọc trong dấu ngoặc nhọn. Nhầm tiếp là tưởng JSX tạo DOM — nó chỉ tạo object; cùng một cây element chạy được cả ở server để render ra string.

Nói trong 60 giây
  • JSX là sugar của JavaScript, compiler dịch thành lời gọi jsx() trả về React element object.
  • Từ React 17 dùng automatic runtime nên không cần import React.
  • Element chỉ là mô tả; DOM thật sinh ra ở commit phase.
  • Component chỉ return một giá trị nên cần Fragment để nhóm nhiều anh em.
  • Fragment không thêm node DOM, không nhận className/style, chỉ nhận key ở dạng đầy đủ.

Q2 Function component khác class component thế nào và vì sao props là read-only?

What

Function component là một function nhận props và trả về JSX; state, side effect và ref đều thể hiện qua hook như useState, useEffect, useRef. Class component kế thừa React.Component, giữ state trong this.state và chạy lifecycle method như componentDidMount. Từ React 18, function component là cách viết mặc định; class chỉ còn cần cho error boundary vì chưa có hook tương đương.

Why

Props là tham số đầu vào và bất biến theo thiết kế, tạo nên mô hình dữ liệu chảy một chiều từ cha xuống con (one-way data flow). Muốn con thay đổi dữ liệu thì cha truyền một callback xuống, con gọi callback đó — nhờ vậy luồng dữ liệu luôn suy luận được từ trên xuống, không có mutation ngầm. Class dễ sinh bug hơn vì this phụ thuộc ngữ cảnh gọi và lifecycle nhóm logic theo thời điểm chạy thay vì theo trách nhiệm.

How
Parent — nơi giữ state
↓ props: value và onChange, con chỉ được đọc
Child A
Child B
↑ con gọi onChange(id) để yêu cầu cha đổi state
Parent render lại → props mới xuống cả hai con

Vòng dữ liệu khép kín: state ở cha, con là hàm thuần theo props. Cùng props và cùng state luôn cho cùng output, nên component dễ test và dễ tái sử dụng ở ngữ cảnh khác.

When

Mặc định dùng function component cho code mới. Dùng class khi cần error boundary (cặp static getDerivedStateFromError và componentDidCatch) hoặc khi bảo trì component class cũ. Chia component theo trách nhiệm: một component một việc (render một dòng tồn kho, chọn kho, gọi API tồn kho), không chia theo từng thẻ HTML vụn.

When NOT

Không mutate props hay gán lại field của object nhận từ props (ví dụ props.item.qty = 5) — đó là bug aliasing rất khó tìm vì cha không hề biết dữ liệu đã đổi. Không tách component chỉ để bọc một <div> không có trách nhiệm riêng; cũng không nâng mọi state lên component cha chỉ để tránh chia file.

// Function component: props read-only, type tường minh
type SkuRowProps = { sku: string; qty: number; onPick: (sku: string) => void };

function SkuRow({ sku, qty, onPick }: SkuRowProps) {
  return (
    <tr>
      <td>{sku}</td>
      <td>{qty}</td>
      <td><button onClick={() => onPick(sku)}>Chọn</button></td>
    </tr>
  );
}

// Class tương đương — this.props cũng read-only
class SkuRowClass extends React.Component<SkuRowProps> {
  render() {
    const { sku, qty, onPick } = this.props;
    return <button onClick={() => onPick(sku)}>{sku} - {qty}</button>;
  }
}
Use case

Bảng tồn kho: StockTable giữ state filter, sort và trang hiện tại; SkuRow chỉ nhận props và gọi onPick. Đổi cách render một dòng không đụng tới logic lọc phía cha, và ngược lại đổi logic lọc không phải sửa dòng.

Pitfall / Interview trap

Tạo object hoặc function mới ngay trong JSX (style={{ color: "red" }}, items={list.filter(...)}, onPick={() => ...}) làm con re-render mỗi lần cha render; nếu con đã bọc React.memo thì reference mới này vô hiệu hóa memo. Câu hỏi phỏng vấn hay gặp: “vì sao con vẫn render dù props không đổi?” — câu trả lời thường nằm ở đây.

Nói trong 60 giây
  • Function component dùng hook, là mặc định từ React 18; class còn cần cho error boundary.
  • Props là tham số read-only, dữ liệu chỉ chảy một chiều từ cha xuống con.
  • Con muốn đổi dữ liệu thì gọi callback do cha truyền xuống, không sửa props.
  • Class gom logic theo lifecycle, function gom theo trách nhiệm nên dễ đọc và tái sử dụng hơn.
  • Chia component theo trách nhiệm, không theo từng thẻ HTML.

Q3 State khác props thế nào, chuyện gì xảy ra khi state đổi và vì sao không được sửa state trực tiếp?

What

Props là dữ liệu cha truyền vào và chỉ đọc. State là dữ liệu nội bộ component tự quản lý, khởi tạo bằng useState và cập nhật qua hàm setter. Khi gọi setter, React lên lịch render lại component đó cùng các component con, tạo cây element mới, so sánh với cây cũ rồi chỉ commit những thay đổi DOM thật sự cần thiết.

Why

React so sánh state cũ và mới bằng Object.is. Nếu bạn mutate object hoặc mảng rồi truyền lại đúng reference cũ, React coi như không có gì thay đổi và bỏ qua re-render — UI đứng yên dù dữ liệu đã khác. Mutation còn phá giả định “mỗi render là một snapshot”: biến trong closure của lần render trước vẫn trỏ vào object đã bị sửa, khiến memo và so sánh props sai. Trong StrictMode ở dev, hàm updater còn bị gọi hai lần nên nó buộc phải thuần.

How
Người dùng click
↓ handler gọi setState(giá trị mới)
React xếp các cập nhật cùng tick vào một batch
↓ render phase: phải pure, không side effect
Element mới được tạo từ props và state mới
↓ diff với element cũ
Commit thay đổi DOM tối thiểu rồi browser paint

Vì các cập nhật trong cùng một tick được batch, nhiều lệnh setState liên tiếp chỉ tạo một lần render. Khi giá trị mới phụ thuộc giá trị cũ, dùng dạng updater setQty(prev => prev + 1) để không phụ thuộc biến closure của lần render cũ.

When

Dùng state cho dữ liệu thay đổi theo tương tác và ảnh hưởng tới render: text trong input, filter đang chọn, danh sách vừa fetch xong, trạng thái mở/đóng panel. Nếu một giá trị tính được từ props hoặc state khác — danh sách đã lọc, tổng số dòng, cờ “đã chọn hết” — thì tính ngay lúc render thay vì lưu vào state.

When NOT

Không mirror props vào state rồi đồng bộ bằng useEffect — dùng trực tiếp props, hoặc đổi key khi muốn reset component. Không dùng state cho dữ liệu không ảnh hưởng giao diện (id của timer, cờ đã chạy) — useRef phù hợp hơn. Cũng đừng lưu state dẫn xuất, vì hai nguồn dữ liệu cho cùng một sự thật sẽ lệch nhau.

// SAI: mutate rồi set lại chính reference đó → React bail out, không re-render
function BadList() {
  const [items, setItems] = useState<Item[]>([]);
  const add = (it: Item) => {
    items.push(it);      // sửa mảng cũ
    setItems(items);      // reference không đổi — UI không cập nhật
  };
}

// ĐÚNG: tạo mảng mới, dùng updater thuần (an toàn cả khi StrictMode gọi 2 lần)
function GoodList() {
  const [items, setItems] = useState<Item[]>([]);
  const add = (it: Item) => setItems(prev => [...prev, it]);
  const bump = (id: string) =>
    setItems(prev => prev.map(x => (x.id === id ? { ...x, qty: x.qty + 1 } : x)));
}
Pitfall / Interview trap

Bug kinh điển: qty tăng sai khi bấm nhanh liên tục, hoặc state cũ bị “kẹt” trong closure của setTimeout — cả hai đều do dùng giá trị cũ thay vì updater. Bẫy khác là tưởng setState là đồng bộ: nó chỉ xếp lịch, nên không đọc được state mới ngay sau đó trong cùng một hàm.

Nói trong 60 giây
  • Props do cha truyền và read-only; state là dữ liệu nội bộ, cập nhật bằng setter.
  • setState gây render lại component và con, rồi mới diff và commit DOM.
  • React so sánh bằng Object.is nên mutate giữ nguyên reference thì không re-render.
  • Luôn tạo object/mảng mới, ưu tiên dạng updater khi giá trị mới phụ thuộc giá trị cũ.
  • Giá trị tính được từ state khác thì tính lúc render, không lưu state.

Render danh sách, điều kiện, event và form input

Q4 Danh sách và key: vì sao không nên dùng index làm key, hậu quả khi key sai là gì?

What

Key là định danh duy nhất cho mỗi phần tử trong danh sách, giúp reconciler nhận ra phần tử của lần render trước tương ứng với phần tử nào ở lần render sau. Index chỉ an toàn khi danh sách tĩnh: không chèn, không xoá, không lọc và không đổi thứ tự. Với danh sách động, key phải là id ổn định đến từ dữ liệu như row.id hay task.code.

Why

Dùng index thì việc chèn một phần tử vào đầu hoặc sort lại danh sách làm toàn bộ index lệch đi một vị trí. React tưởng các phần tử “vẫn thế” nên tái sử dụng component và DOM cũ, khiến state nội bộ bị gán sai dòng: chữ đang gõ trong ô của dòng A nhảy sang dòng B, checkbox đã tick chuyển sang dòng khác, focus nhảy loạn. Về hiệu năng, key đổi hàng loạt hoặc key sinh mới mỗi render khiến React unmount rồi mount lại cả danh sách, tốn kém hơn nhiều so với update tại chỗ.

How
Dữ liệu mới sau khi insert / sort / filter
↓ reconciler đối chiếu con theo key
Key khớp → update tại chỗ, giữ state con
Key mới → mount phần tử mới
Key mất → unmount và dọn state
↓ commit
DOM chỉ đổi ở đúng phần tử cần đổi

Key đúng giúp danh sách giữ được identity qua các lần render, nên state của con — giá trị đang gõ, animation đang chạy, dữ liệu đã fetch — đi theo đúng dòng dữ liệu. Đó cũng là lý do key phải nằm trên phần tử được sinh trong map, không nằm sâu bên trong component con.

When

Dùng key ổn định cho mọi danh sách động: bảng tồn kho, danh sách pick task, kết quả search, log sự kiện. Sau khi filter hay sort vẫn giữ nguyên key gốc là id của bản ghi, tuyệt đối không lấy vị trí trong mảng đã lọc làm key. Khi phần tử có thể xuất hiện ở nhiều danh sách khác nhau thì ghép tiền tố để tránh trùng key: listId + id.

When NOT

Index chấp nhận được khi danh sách tĩnh, không reorder, không chèn hay xoá, và mỗi item không giữ state nội bộ — ví dụ render một bảng hằng số hoặc chia các ô theo số cố định. Không dùng Math.random() hay Date.now() làm key vì mỗi render sinh key mới, làm mất state và giảm hiệu năng; cũng không dùng key trùng nhau giữa các phần tử anh em vì React sẽ cảnh báo và hành vi diff không còn xác định.

// SAI: index làm key — reorder hoặc insert làm lệch identity
{rows.map((r, i) => <Row key={i} item={r} />)}

// ĐÚNG: key ổn định lấy từ dữ liệu
{rows.map(r => <Row key={r.id} item={r} />)}

// key là chuyện của React, KHÔNG được truyền vào component như một prop.
// Con cần id thì truyền riêng:
<Row key={r.id} id={r.id} item={r} />
Pitfall / Interview trap

Triệu chứng dễ nhận ra nhất của key sai: gõ vào ô search của dòng thứ hai nhưng chữ lại hiện ở dòng thứ ba sau khi danh sách đổi thứ tự, hoặc xoá dòng đầu thì dòng cuối mất tick. Cũng rất hay gặp bẫy dùng key={index} bên trong một component đã dùng React.memo — memo không cứu được vì key mới làm remount cả subtree.

Nói trong 60 giây
  • Key là định danh giúp reconciler biết phần tử nào là phần tử nào giữa hai lần render.
  • Index chỉ đúng với danh sách tĩnh, không insert/delete/sort/filter.
  • Dùng index với danh sách động làm state con gán sai dòng và làm remount, giảm hiệu năng.
  • Key phải đến từ dữ liệu, ổn định, duy nhất giữa các anh em.
  • Key không phải prop — con cần id thì truyền prop riêng.

Q5 Render có điều kiện và composition — làm sao tránh lạm dụng các điều kiện lồng nhau?

What

Conditional rendering là dùng if, ternary hoặc && để chọn JSX nào được render, và trả về null khi không muốn hiển thị gì. Composition là tái sử dụng bằng cách truyền nội dung vào component qua props.children hoặc render prop — hàm nhận dữ liệu và trả về JSX — thay vì copy markup hoặc thêm hàng loạt prop boolean kiểu isHeader, showFooter.

Why

Điều kiện lồng nhau trong JSX làm logic khó đọc, khó test và dễ sai nhánh; mỗi cấp ternary là một nhánh ẩn không ai kiểm tra. Guard clause (return sớm) đưa các trạng thái loading, error, empty ra ngoài, phần thân còn lại chỉ nói về happy path. Composition giữ component cha không cần biết chi tiết nội dung con, nên giảm prop drilling và tránh component phình to theo số biến thể hiển thị.

How
Liệt kê các trạng thái: loading, error, empty, có dữ liệu
↓ mỗi trạng thái một guard clause return sớm
Phần thân chỉ còn happy path
↓ nhánh phụ dùng ternary hoặc && ngay tại chỗ
Component đọc được từ trên xuống, mỗi nhánh một lý do

Với composition, component khung (Card, Modal, Section) chỉ lo layout và nhận nội dung qua children; nơi gọi quyết định nội dung là bảng, form hay thông báo. Component khung không phải sửa khi có thêm loại nội dung mới.

When

Guard clause cho trạng thái mạng và dữ liệu rỗng; ternary khi cần chọn giữa hai nhánh A và B; && khi chỉ có hoặc không có một khối; composition khi nhiều nơi dùng chung một layout nhưng nội dung khác nhau, hoặc khi một component cần nhận cả header, body và footer từ bên ngoài.

When NOT

Không dùng && với biến có thể mang giá trị 0 hoặc chuỗi rỗng — React sẽ render số 0 ra màn hình, hãy so sánh tường minh count > 0 && ... hoặc dùng ternary. Không lồng quá hai cấp ternary, hãy tách thành biến hoặc component nhỏ. Không lạm dụng render prop khi children đã đủ, và không dùng composition để giấu logic nghiệp vụ bên trong JSX.

type Props = { order: Order; loaded: boolean };

function OrderPanel({ order, loaded }: Props) {
  if (!loaded) return <Spinner />;                       // guard clause
  if (order.status === "cancelled") return <p>Đơn đã huỷ</p>;

  return (
    <Card title={`Đơn ${order.code}`}>
      {order.lines.length > 0 && <LineTable lines={order.lines} />}
    </Card>
  );
}

// Card không biết nội dung con là gì — composition qua children
function Card({ title, children }: { title: string; children: React.ReactNode }) {
  return (
    <section className="card">
      <h4>{title}</h4>
      {children}
    </section>
  );
}
Pitfall / Interview trap

{items.length && <List />} render số 0 khi danh sách rỗng — bug hay bị hỏi trong phỏng vấn React. Bẫy thứ hai: dùng render prop rồi đặt tên prop là children nhưng lại truyền như prop thường, khiến JSX tự đóng thẻ và nội dung nằm trong attribute, khó đọc. Cuối cùng, đổi cả cây con giữa hai component khác type sẽ unmount subtree và xoá state — nếu muốn giữ state thì giữ cùng type và đổi prop.

Nói trong 60 giây
  • Guard clause cho loading/error/empty, để thân hàm chỉ còn happy path.
  • Ternary cho hai nhánh, && cho một nhánh, cẩn thận bẫy render số 0.
  • Không lồng ternary quá hai cấp, tách thành biến hoặc component.
  • Composition qua children hoặc render prop thay cho hàng loạt prop boolean.
  • Component khung không biết nội dung con, nên thêm loại nội dung mới không phải sửa nó.

Q6 Event handling trong React: synthetic event là gì, truyền tham số cho handler thế nào, và event pooling đã bỏ từ React 17 nghĩa là gì?

What

React bọc native event trong SyntheticEvent — object chuẩn hoá giao diện gồm preventDefault, stopPropagation, target, hoạt động giống nhau trên mọi trình duyệt. Từ React 17, listener được gắn ở root container thay vì ở document, và event pooling đã bị gỡ: object event không còn bị reset sau handler, nên đọc e.target.value trong callback bất đồng bộ vẫn an toàn.

Why

Event delegation ở root giúp giảm số listener phải gắn cho từng node, tự dọn theo subtree khi unmount, và cho phép nhiều cây React độc lập cùng tồn tại trên một trang — điều mà việc gắn ở document không làm được. Trước React 17, pooling tái sử dụng object event để giảm áp lực GC nhưng khiến nhiều người gặp lỗi khi truy cập event trong setTimeout hay trong lời gọi API bất đồng bộ; bỏ pooling loại bỏ hẳn nhóm bug đó, đổi lại chi phí cấp phát object cao hơn một chút và đã được tối ưu ở tầng khác.

How
Người dùng click
↓ native event bubble lên root container
React tra bảng listener và dispatch SyntheticEvent
↓ gọi handler theo đúng tên prop: onClick, onChange
Handler chạy: đọc e.target, cập nhật state hoặc gọi callback
↓ cập nhật state trong cùng tick được batch
Một lần render, UI cập nhật

Vì event đi qua root container theo cơ chế bubble, một listener đặt trên phần tử cha vẫn nhận được event từ con — đây là nền tảng để truyền dữ liệu kèm theo khi cần (dataset) thay vì tạo hàng trăm handler riêng.

When

Truyền tham số cho handler bằng inline arrow khi danh sách nhỏ: onClick={() => remove(id)}. Khi danh sách lớn hoặc component con đã bọc React.memo, dùng dạng curried remove(id) trả về handler ổn định, hoặc đặt id trên element và đọc từ e.currentTarget.dataset.id. Với input thì luôn đi theo cặp value và onChange.

When NOT

Không gọi handler ngay trong JSX — onClick={remove(id)} chạy lúc render và gây vòng lặp cập nhật vô hạn nếu handler có setState. Không gọi e.persist() vì từ React 17 nó không còn cần thiết. Không tối ưu sớm bằng useCallback cho mọi handler — chỉ làm khi component con đã được memo, nếu không bạn chỉ thêm phức tạp.

// Cách 1: inline arrow — gọn, nhưng tạo hàm mới mỗi render
<button onClick={() => remove(id)}>Xoá</button>

// Cách 2: curried — handler ổn định, hợp khi con đã được memo
const handleRemove = (id: string) => (e: React.MouseEvent) => {
  e.stopPropagation();   // không cho click lan lên dòng cha
  remove(id);
};
<button onClick={handleRemove(id)}>Xoá</button>

// Controlled input: value và onChange là một cặp bắt buộc
<input value={sku} onChange={e => setSku(e.target.value) />

// Sai: handler bị gọi ngay trong lúc render
// <button onClick={remove(id)}>Xoá</button>
Use case

Một listener ở phần tử cha xử lý click cho cả bảng: đặt data-row-id trên mỗi dòng, đọc e.target.dataset.rowId trong handler. Cách này hợp khi bảng có hàng nghìn dòng vì không phải tạo hàm mới cho từng dòng.

Nói trong 60 giây
  • SyntheticEvent là wrapper chuẩn hoá của native event, hành vi giống nhau trên mọi browser.
  • Từ React 17 listener gắn ở root container, hỗ trợ nhiều cây React trên một trang.
  • Event pooling đã bị gỡ từ React 17, nên đọc event trong callback async vẫn an toàn.
  • Truyền tham số bằng inline arrow hoặc curried handler; đừng gọi handler lúc render.
  • Chỉ tối ưu reference handler khi con đã memo.

Q7 Controlled và uncontrolled input khác nhau thế nào, khi nào nên dùng defaultValue kèm ref?

What

Controlled input nhận value từ state React và cập nhật lại state qua onChange, nên React là nguồn dữ liệu duy nhất và giá trị đọc ra bất cứ lúc nào cũng đúng. Uncontrolled input giữ giá trị trong DOM; React chỉ đặt giá trị ban đầu bằng defaultValue hoặc defaultChecked và đọc giá trị khi cần qua useRef.

Why

Controlled cho phép validate và định dạng ngay từng keystroke, disable nút lưu theo dữ liệu, đồng bộ nhiều trường với nhau — đổi lại mỗi keystroke gây một lần re-render. Uncontrolled ít code, không re-render theo keystroke, phù hợp form lớn hoặc khi tích hợp plugin DOM tự quản giá trị. Hai điểm đặc biệt: input kiểu file luôn là uncontrolled vì browser chỉ cho đọc danh sách files; và defaultValue chỉ có tác dụng ở lần mount nên đổi prop này sau đó không cập nhật gì.

How
Người dùng gõ phím
↓
Controlled: onChange → setState → re-render với value mới
Uncontrolled: DOM tự cập nhật, React không can thiệp
↓
Controlled: đọc giá trị từ state bất cứ lúc nào
Uncontrolled: chỉ đọc khi submit qua ref
↓
Validate tức thời, UI đồng bộ
Ít re-render, code ngắn

Nguyên tắc chọn: nếu giá trị của trường ảnh hưởng tới phần UI khác — nút lưu, thông báo lỗi, ô tổng tiền — thì cần controlled; nếu giá trị chỉ được dùng một lần lúc gửi thì uncontrolled là đủ.

When

Controlled cho search box, form cần validate theo từng trường, form cần đồng bộ nhiều field, ô nhập cần format số hoặc chữ hoa. Uncontrolled khi nhập dữ liệu một lần rồi gửi, khi upload file, hay khi form quá nhiều trường khiến việc re-render mỗi keystroke trở thành vấn đề hiệu năng.

When NOT

Đặt value mà không có onChange biến input thành read-only — React chỉ cảnh báo ở dev nên rất dễ lọt. Không đặt đồng thời cả value và defaultValue, và không để giá trị chuyển từ undefined sang chuỗi giữa hai lần render vì React sẽ chuyển input từ uncontrolled sang controlled và cảnh báo. Không đọc ref.current.value trong lúc render — chỉ đọc trong event handler hoặc effect.

// Controlled: state là nguồn duy nhất, validate được từng keystroke
function SkuField() {
  const [sku, setSku] = useState("");
  return (
    <>
      <input value={sku} onChange={e => setSku(e.target.value.toUpperCase())} />
      <button disabled={sku.length < 3}>Lưu</button>
    </>
  );
}

// Uncontrolled: DOM giữ value, đọc khi submit qua ref
function ImportBox({ onSend }: { onSend: (q: string) => void }) {
  const ref = useRef<HTMLInputElement>(null);
  return (
    <div>
      <input defaultValue="SKU-" ref={ref} />
      <button onClick={() => onSend(ref.current?.value ?? "")}>Gửi</button>
    </div>
  );
}
Pitfall / Interview trap

Chọn input kiểu file: giá trị files chỉ đọc được, muốn reset thì phải gán lại null qua ref — dùng uncontrolled là bắt buộc. Bẫy khác: lưu số vào state dạng number rồi ép value={qty} làm input không gõ được dấu thập phân hay chuỗi rỗng; giữ dạng chuỗi trong state và convert khi gửi là cách an toàn hơn.

Nói trong 60 giây
  • Controlled: React state là nguồn duy nhất, value đi kèm onChange.
  • Uncontrolled: DOM giữ giá trị, defaultValue đặt lúc mount, đọc qua ref khi cần.
  • Controlled để validate và đồng bộ, đổi lại re-render mỗi keystroke.
  • defaultValue chỉ tác dụng lần mount; input file luôn uncontrolled.
  • value mà thiếu onChange là read-only — bẫy hay bị hỏi.

Đặt state, reconciliation, React 18 và form handling

Q8 Lifting state up và single source of truth — đặt state ở đâu trong cây component?

What

Lifting state up là chuyển state từ component con lên tổ tiên chung gần nhất của mọi component cần dữ liệu đó: cha giữ state rồi truyền giá trị xuống bằng props và truyền hàm cập nhật xuống cho con gọi. Single source of truth nghĩa là mỗi mảnh dữ liệu chỉ tồn tại ở một nơi; mọi nơi khác đọc lại hoặc tính lại từ đó thay vì giữ bản sao.

Why

Nếu mỗi con giữ bản sao riêng thì dữ liệu chắc chắn lệch nhau: hai filter hiển thị hai giá trị khác nhau, số dòng tổng không khớp danh sách đang thấy. Cách chữa thường thấy là thêm useEffect đồng bộ giữa các state — dễ sinh vòng lặp render, race condition và render thừa. Một nguồn dữ liệu duy nhất cộng với cập nhật một chiều làm trạng thái UI luôn suy ra được, không cần đồng bộ thủ công.

How
Hai component anh em cần cùng một dữ liệu
↓ tìm tổ tiên chung gần nhất trên cây
Đặt state ở đó, xoá state trùng ở các con
↓ props đi xuống: value và onChange
Con chỉ đọc props; muốn đổi thì gọi callback lên cha

Bốn bước áp dụng: xác định chính xác component nào cần đọc dữ liệu; tìm tổ tiên chung gần nhất; đặt state tại đó và truyền value cùng onChange xuống; biến các con thành component thuần theo props, không giữ bản sao dữ liệu.

When

Khi hai sibling cần cùng dữ liệu như ô search và bảng kết quả, khi cha cần dữ liệu để quyết định layout hoặc tính tổng, khi một dữ liệu phải reset đồng bộ giữa nhiều nhánh. Nguyên tắc chọn vị trí: state nên nằm gần nơi dùng nhất nhưng vẫn đủ cao để mọi component cần nó là con của nó.

When NOT

Đừng nâng state lên tận gốc ứng dụng: state ở app khiến mỗi keystroke render lại cả cây, kể cả sidebar và header không liên quan. Khi phải xuyên qua bốn, năm tầng trung gian chỉ để truyền props, cân nhắc Context; khi dữ liệu là server state thì thư viện caching giảm việc tự quản. Cũng không lưu lại dữ liệu dẫn xuất sau khi đã nâng state — nó sẽ thành nguồn dữ liệu thứ hai.

function StockScreen() {
  const [query, setQuery] = useState("");            // nguồn dữ liệu duy nhất
  const [rows] = useState<Row[]>([]);

  // Dẫn xuất, KHÔNG lưu vào state
  const visible = rows.filter(r => r.sku.includes(query));

  return (
    <>
      <SearchBox value={query} onChange={setQuery} />
      <ResultCount value={visible.length} />
      <ResultTable rows={visible} />
    </>
  );
}

// Con không giữ state: chỉ đọc props và báo thay đổi lên cha
function SearchBox({ value, onChange }: { value: string; onChange: (v: string) => void }) {
  return <input value={value} onChange={e => onChange(e.target.value)} />;
}
Use case

Màn hình tồn kho: ô filter theo kho, bảng kết quả và số lượng đều đọc từ một state query ở component cha. Muốn reset filter thì chỉ cần setQuery("") một chỗ, thay vì gọi reset ở ba component khác nhau.

Pitfall / Interview trap

Bug hay gặp là hai state cùng mô tả một sự thật (query ở cha và internalQuery ở con), rồi phải vá bằng useEffect — mỗi lần đồng bộ lại gây một lần render và tạo nguy cơ vòng lặp. Câu hỏi phỏng vấn “đặt state ở đâu?” kỳ vọng câu trả lời theo hai trục: tổ tiên chung gần nhất, và giữ state càng gần nơi dùng càng tốt.

Nói trong 60 giây
  • Lift state lên tổ tiên chung gần nhất khi nhiều component cần cùng dữ liệu.
  • Một sự thật chỉ nằm ở một chỗ, mọi nơi khác đọc hoặc tính lại từ đó.
  • Cha giữ state, con nhận value qua props và yêu cầu đổi qua callback.
  • Đặt gần nơi dùng nhất để tránh render lại cả cây lớn.
  • Nhiều tầng trung gian thì cân nhắc Context, nhưng đừng biến mọi state thành global.

Q9 Reconciliation và virtual DOM: diff hoạt động thế nào, React nhanh hơn thao tác DOM thủ công ở đâu, và chi phí thật của một lần re-render là gì?

What

Reconciliation là quá trình React so sánh cây element mới với cây của lần render trước để tính ra tập thay đổi DOM nhỏ nhất. Thay vì thuật toán so cây tổng quát có chi phí rất cao, React dùng heuristic O(n) dựa trên hai giả định: khác type thì coi như một cây hoàn toàn mới, và trong danh sách thì dùng key để nhận diện phần tử.

Why

Virtual DOM không tự động nhanh hơn DOM: thao tác DOM viết tối ưu vẫn nhanh hơn. Lợi ích thật nằm ở chỗ bạn mô tả UI theo trạng thái, React dồn thay đổi vào một lần commit và tránh kiểu cập nhật thô như ghi lại toàn bộ innerHTML — vốn làm mất state và focus của input. Chi phí thật của một lần re-render gồm gọi lại hàm component, tạo các element object mới, diff cây, rồi mới tới commit và browser paint; chỉ bước commit mới chạm DOM.

How
setState → render phase
↓ gọi component, tạo cây element mới, phải pure
Diff: cùng type → update props; khác type → thay cả subtree
↓ trong danh sách, key quyết định mount, update hay unmount
Commit phase: mutate DOM thật, chạy layout effect
↓
Browser paint khung hình mới

Vì render phase có thể bị gọi lại (StrictMode ở dev) hoặc bị bỏ dở khi có cập nhật ưu tiên cao hơn, đừng đặt side effect ở đó. Muốn tối ưu thì giảm số lần render và kích thước cây phải diff: React.memo cho subtree nặng, useMemo cho tính toán tốn kém, key ổn định cho danh sách, tách component để cô lập phạm vi cập nhật.

When

Hiểu cơ chế này để trả lời các câu về hiệu năng: vì sao danh sách dài lại giật, vì sao truyền object mới xuống con đã memo không có tác dụng, vì sao đổi type làm mất state của subtree. Áp dụng khi thật sự có vấn đề đo được: bọc dòng bảng bằng React.memo, giữ handler ổn định bằng useCallback, đẩy việc lọc và sắp xếp nặng vào useMemo.

When NOT

Không memo hoá mọi thứ: so sánh props cũng tốn thời gian và làm code khó đọc, trong khi với subtree nhỏ thì render lại rẻ hơn hẳn phần diff thêm vào. Không tối ưu theo cảm giác — đo bằng Profiler trước. Và đừng trả lời phỏng vấn rằng virtual DOM nhanh hơn DOM thủ công; câu trả lời đúng là nó giúp tránh cập nhật DOM dư thừa và giữ được mô hình khai báo dễ suy luận.

// Khác type → unmount cả subtree và mount lại: state của panel bị mất
{isEdit ? <EditPanel /> : <ViewPanel />}

// Muốn giữ state thì giữ cùng type và đổi prop
<Panel mode={isEdit ? "edit" : "view"} />

// Chặn re-render lan xuống cây nặng — memo chỉ hiệu quả khi props ổn định
const Row = React.memo(function Row({ item, onPick }: RowProps) {
  return <button onClick={() => onPick(item.id)}>{item.code}</button>;
});
// Ở cha: onPick phải là useCallback, item phải là reference mới CHỈ khi dữ liệu đổi
Pitfall / Interview trap

Bẫy hay bị khai thác: đổi điều kiện render từ component A sang component B cùng vị trí trong cây — hai type khác nhau nên React unmount subtree và toàn bộ state bên trong mất sạch (form đang nhập bị xoá trắng). Bẫy khác: đặt side effect hoặc log trong thân render, khiến số lần chạy hiển thị sai lệch so với số lần commit thực tế.

Nói trong 60 giây
  • Reconciliation là diff cây element, dùng heuristic O(n): khác type thay subtree, cùng type update props.
  • Danh sách dùng key để nhận diện phần tử, key sai gây remount và mất state.
  • Virtual DOM không nhanh hơn DOM thủ công; nó tránh cập nhật dư và giữ mô hình khai báo.
  • Chi phí re-render: gọi component, tạo element, diff, commit DOM.
  • Tối ưu bằng memo, useMemo, key ổn định, tách component — và luôn đo bằng Profiler.

Q10 React 18: automatic batching hoạt động thế nào và vì sao StrictMode gọi render/effect hai lần trong dev lại là điều tốt?

What

Từ React 18, automatic batching gộp mọi cập nhật state trong cùng một tick thành một lần render, kể cả khi xảy ra trong promise, setTimeout hay native event handler. StrictMode ở môi trường dev chủ động gọi lại hàm render và chạy effect theo vòng mount, unmount rồi mount lại; production không có hành vi này.

Why

Batch giảm số lần render và commit khi một luồng xử lý cập nhật nhiều mảnh state — bắt đầu fetch, tắt loading, gán dữ liệu, set lỗi — nên ít việc diff và ít layout thrashing hơn. Double-invoke của StrictMode là một bài stress test: nếu component giả định effect chỉ chạy một lần, hoặc render có side effect, bạn sẽ thấy ngay ở dev thay vì gặp bug khó tái hiện ở production; code chịu được remount là code đúng với mô hình của React 18 và sẵn sàng cho các tính năng tương lai.

How
Ba lệnh setState trong cùng một tick, kể cả sau await
↓ đưa vào cùng một batch
React 17 trở về trước: async context → nhiều lần render
React 18: một lần render duy nhất
↓
Commit DOM một lần, UI không nhấp nháy trạng thái trung gian

Muốn thoát khỏi batch — ví dụ cần đọc kích thước DOM ngay sau khi set state — dùng flushSync, nhưng chỉ trong trường hợp thật sự cần vì nó phá lợi ích của batching. Về StrictMode, hãy viết effect luôn có cleanup: trả hàm huỷ, dùng AbortController cho request, gỡ listener trong cleanup.

When

Hiểu batching để giải thích vì sao số lần render thực tế ít hơn số lệnh setState và vì sao không cần tự gộp cập nhật. Hiểu StrictMode khi debug test flaky hoặc khi thấy effect chạy hai lần trong dev. Bọc toàn bộ ứng dụng trong StrictMode ở môi trường phát triển, và dùng flushSync khi thật sự phải đo DOM ngay sau cập nhật.

When NOT

Không tắt StrictMode để “hết lỗi” — lỗi đó chính là dấu hiệu code có side effect chưa được dọn. Không tách setState vào setTimeout để tránh batching vì từ React 18 cách đó vô ích; nếu thấy hai request thật ở production thì đó là bug thiếu cleanup, không phải lỗi của StrictMode. Cũng không đặt fetch, log hay thao tác ghi vào thân render, và nhớ hàm updater truyền cho setState phải thuần vì có thể bị gọi hai lần.

// React 18: ba cập nhật trong một tick, kể cả sau await → chỉ một lần render
async function load() {
  setLoading(true);
  const data = await fetchOrders();
  setLoading(false);      // gộp cùng dòng dưới
  setOrders(data);      // → React 18 render MỘT lần
}

// StrictMode ở dev: mount → unmount → mount lại, nên effect PHẢI có cleanup
useEffect(() => {
  const ctrl = new AbortController();
  fetch("/api/stock", { signal: ctrl.signal })
    .then(r => r.json())
    .then(setStock)
    .catch(() => { /* request bị huỷ thì bỏ qua */ });
  return () => ctrl.abort();   // thiếu dòng này → set state hai lần, race condition
}, []);
Pitfall / Interview trap

Thấy log trong effect in ra hai lần ở dev là bình thường và không phải bug — nhưng nếu thấy hai request mạng thật ở production thì đó là bug thật do thiếu cleanup. Bẫy thứ hai: tin rằng cứ gọi nhiều setState là nhiều lần render rồi tự gộp state thủ công, trong khi React 18 đã làm việc đó và việc gộp tay thường tạo ra một state object cồng kềnh khó cập nhật.

Nói trong 60 giây
  • React 18 batch mọi cập nhật trong cùng tick, kể cả trong promise và setTimeout.
  • Ít render hơn đồng nghĩa ít diff và ít layout thrashing; cần đọc DOM ngay thì dùng flushSync.
  • StrictMode dev gọi render và effect hai lần để lộ side effect không thuần.
  • Effect phải có cleanup — AbortController, gỡ listener, huỷ timer.
  • Đừng tắt StrictMode để che lỗi, và đừng đặt side effect trong thân render.

Q11 Bonus — xử lý form trong React: submit, validate và tổ chức state của form nhiều trường thế nào cho sạch?

What

Xử lý form trong React gồm bốn việc: chặn submit mặc định của browser bằng e.preventDefault(), gom giá trị các trường vào một object state, validate rồi gửi lên server, và quản lý ba trạng thái đang gửi, thành công, thất bại. Form nhiều trường nên gom vào một object state với một handleChange dùng chung.

Why

Để browser tự submit sẽ reload trang và xoá sạch state React, đồng thời bỏ qua validate ở client nên người dùng chỉ thấy lỗi sau khi server trả về. Một object state cho cả form giúp validate tập trung một chỗ, hiển thị lỗi theo từng field, disable nút gửi khi dữ liệu chưa hợp lệ hoặc đang gửi, và reset form chỉ bằng một lệnh. Cách này cũng tránh việc mỗi trường có một state riêng khiến mười trường thành mười useState khó đọc và khó reset đồng bộ.

How
Người dùng điền form và bấm Lưu
↓ onSubmit: preventDefault rồi validate
Có lỗi → set errors theo field, không gọi API
Hợp lệ → setSubmitting(true) và gọi API
↓
Thành công: reset form hoặc điều hướng
Thất bại: giữ nguyên dữ liệu để người dùng sửa
↓ dù kết quả nào cũng tắt cờ submitting
Nút gửi trở lại trạng thái bình thường, không double submit

Điểm quan trọng là cờ submitting phải được tắt trong finally, và dữ liệu người dùng đã nhập không được xoá khi server trả lỗi. Nếu form dùng uncontrolled thì đọc toàn bộ giá trị một lần qua FormData ngay trong onSubmit.

When

Dùng object state kèm validate cho form nghiệp vụ có nhiều trường phụ thuộc nhau — phiếu nhập kho, tạo đơn, cấu hình tài khoản. Dùng useReducer khi form có nhiều hành động khác loại (thêm dòng, xoá dòng, đổi số lượng, tính lại tổng). Dùng uncontrolled kèm FormData khi form dài, chỉ gửi một lần, hoặc khi tích hợp file upload.

When NOT

Không tự viết lại thư viện form nếu dự án đã dùng sẵn một thư viện quản lý form và validate — chỉ cần hiểu cơ chế bên dưới. Không validate chỉ ở client: server luôn phải kiểm tra lại. Không đặt state của một form cục bộ vào Context hay store toàn cục chỉ để tránh truyền props vài tầng, và cũng không giữ giá trị số dạng number trong state nếu input cần cho phép gõ dở — hãy giữ chuỗi rồi convert khi gửi.

type Form = { sku: string; qty: string };
type Errors = Partial<Record<keyof Form, string>>;

function CreateOrderForm({ onSubmit }: { onSubmit: (f: Form) => Promise<void> }) {
  const [form, setForm] = useState<Form>({ sku: "", qty: "" });
  const [errors, setErrors] = useState<Errors>({});
  const [submitting, setSubmitting] = useState(false);

  // Một handler dùng chung cho mọi trường, lấy tên qua e.target.name
  const change = (e: React.ChangeEvent<HTMLInputElement>) =>
    setForm(prev => ({ ...prev, [e.target.name]: e.target.value }));

  const validate = (f: Form): Errors => {
    const next: Errors = {};
    if (!f.sku) next.sku = "Bắt buộc nhập SKU";
    const q = Number(f.qty);
    if (!Number.isInteger(q) || q <= 0) next.qty = "Phải là số nguyên dương";
    return next;
  };

  const submit = async (e: React.FormEvent) => {
    e.preventDefault();                 // chặn reload trang
    const next = validate(form);
    setErrors(next);
    if (Object.keys(next).length > 0) return;   // không gọi API khi dữ liệu sai
    setSubmitting(true);
    try {
      await onSubmit({ ...form, qty: String(Number(form.qty)) });
      setForm({ sku: "", qty: "" });          // reset sau khi thành công
    } finally {
      setSubmitting(false);                    // luôn tắt cờ, kể cả khi lỗi
    }
  };

  return (
    <div>
      <input name="sku" value={form.sku} onChange={change} />
      <span>{errors.sku}</span>
      <input name="qty" value={form.qty} onChange={change} />
      <span>{errors.qty}</span>
      <button onClick={submit} disabled={submitting}>{submitting ? "Đang lưu" : "Lưu"}</button>
    </div>
  );
}
Use case

Form nhập phiếu kho: validate ở client để phản hồi nhanh, server validate lại để bảo vệ dữ liệu, cờ submitting chống double submit, và lỗi từ server được gán vào errors theo field để người dùng thấy ngay cạnh ô nhập.

Pitfall / Interview trap

Quên preventDefault() làm trang reload và mất toàn bộ state — triệu chứng kinh điển khi mới làm React. Bẫy thứ hai: disable nút gửi nhưng không reset form hay không tắt cờ nếu API lỗi, khiến nút kẹt vĩnh viễn. Bẫy thứ ba: giữ qty dạng number trong state rồi ép value thành số, làm người dùng không gõ được chuỗi trung gian — giữ chuỗi trong state và convert lúc gửi là an toàn.

Nói trong 60 giây
  • Luôn chặn submit mặc định rồi tự validate trước khi gọi API.
  • Form nhiều trường nên gom vào một object state với một handler dùng chung.
  • Validate ở client để phản hồi nhanh, server vẫn phải kiểm tra lại.
  • Cờ submitting chống double submit, tắt trong finally, giữ dữ liệu khi lỗi.
  • Form dài hoặc upload file thì uncontrolled và FormData là lựa chọn hợp lý.
