Maven, Gradle & Quy trình Build/Agile

Công cụ build và quy trình làm việc của team: vòng đời Maven, quản lý version, multi-module, Gradle, xung đột dependency, CI tái lập và Agile/Git workflow.

Maven — lifecycle, scope & quản lý version

Q1 Maven build lifecycle gồm những phase nào và plugin gắn vào phase nào?

What

Maven có 3 lifecycle độc lập: clean, default (build) và site. Lifecycle default chạy các phase theo thứ tự validate → compile → test → package → verify → install → deploy. Gọi một phase nghĩa là chạy lần lượt mọi phase trước nó trong cùng lifecycle, kèm mọi plugin goal đã bind vào các phase đó.

Why

Phase là hợp đồng chuẩn hoá giữa các plugin: plugin chỉ cần khai báo goal thuộc phase nào, không cần biết ai gọi nó. Hiểu sai thứ tự tạo ra build "xanh giả": chạy tới integration-test mà dừng trước verify thì failsafe đã chạy test tích hợp nhưng build vẫn có thể báo thành công; còn mvn package không ghi artifact vào local repo nên module khác không resolve được.

How
validate
compile (compiler-plugin)
test (surefire)
↓ đóng gói artifact
package → target/*.jar
verify (failsafe + jacoco)
↓ đưa artifact ra ngoài máy build
install → ~/.m2/repository
deploy → remote repository

Không cấu hình gì thì Maven áp default lifecycle mapping theo packaging. Với packaging=jar: resources → process-resources, compiler → compile, surefire → test, jar → package, install → install, deploy → deploy. Plugin như jacoco không có binding mặc định nên phải tự khai báo <executions><execution><phase>.

When

Developer dùng mvn clean verify làm lệnh build chuẩn (đầy đủ unit + integration test, không ghi repo). CI dùng install khi multi-module cần module khác resolve, và deploy chỉ ở bước release artifact có version chính thức.

When NOT

Không mvn deploy cho version -SNAPSHOT ở môi trường production, và không bỏ phase verify chỉ để build nhanh — làm vậy là tắt luôn integration test. Cũng tránh chạy mvn test đơn lẻ trong pipeline vì nó không sinh artifact.

<!-- pom.xml — chọn phase nào cho goal nào -->
<plugin>
  <artifactId>maven-surefire-plugin</artifactId>
  <!-- packaging=jar: goal test da bind san vao phase test -->
  <configuration>
    <excludes><exclude>**/*IT.java</exclude></excludes>
  </configuration>
</plugin>

<plugin>
  <artifactId>maven-failsafe-plugin</artifactId>
  <!-- default: integration-test -> phase integration-test, verify -> phase verify -->
</plugin>

<plugin>
  <groupId>org.jacoco</groupId>
  <artifactId>jacoco-maven-plugin</artifactId>
  <!-- khong co binding mac dinh -> tu chon phase -->
  <executions>
    <execution>
      <id>report</id>
      <phase>verify</phase>
      <goals><goal>report</goal></goals>
    </execution>
  </executions>
</plugin>
Use case

Pipeline chạy ./mvnw clean verify để có unit test, integration test và coverage trong một lệnh, rồi bước sau mới deploy lên Nexus khi là release tag.

Pitfall / Interview trap

Nhầm mvn package với mvn install: chỉ install mới ghi vào ~/.m2/repository, nên build module con trước mà quên install thì module khác báo "could not resolve dependencies". Ngoài ra clean thuộc lifecycle khác nên mvn clean package là hai lifecycle chạy nối tiếp.

Nói trong 60 giây
  • 3 lifecycle: clean, default, site; default: validate → compile → test → package → verify → install → deploy.
  • Gọi một phase sẽ chạy mọi phase trước nó trong cùng lifecycle.
  • Plugin bind goal vào phase qua <executions>; có default mapping theo packaging.
  • package chỉ tạo jar, install đưa vào local repo, deploy đưa lên remote repo.
  • Failsafe chỉ fail build ở phase verify — đừng dừng ở integration-test.

Q2 Dependency scope khác nhau thế nào và khai sai scope gây hậu quả gì trong Spring Boot?

What

Maven có các scope: compile (mặc định), provided, runtime, test, system (deprecated) và import (chỉ dùng trong dependencyManagement). Scope quyết định artifact có mặt trên classpath lúc compile, lúc runtime hay chỉ khi test, có bị đóng gói vào artifact cuối và có lan truyền (transitive) sang project phụ thuộc hay không.

Why

Scope sai thường không làm compile fail mà làm runtime fail. spring-boot-maven-plugin:repackage chỉ đưa dependency scope compile và runtime vào fat jar; provided và test bị loại. Vì Maven gộp cả classpath test khi chạy test, test có thể xanh 100% trong khi jar production ném NoClassDefFoundError/ClassNotFoundException.

How
Dependency khai trong pom
↓ scope quyết định classpath nào nhìn thấy nó
compile: compile + runtime
runtime: chỉ runtime
provided: chỉ compile
↓ repackage chỉ lấy compile + runtime
Fat jar chạy được
provided/test: KHÔNG vào jar → lỗi runtime
ScopeCompile classpathRuntime classpathVào fat jarTransitive
compileCóCóCóCó
providedCóKhôngKhôngKhông
runtimeKhôngCóCóCó (thành runtime ở consumer)
testKhôngKhôngKhôngKhông

Cách chọn nhanh: cần cả khi chạy → compile; API do container cung cấp lúc chạy (servlet-api, tomcat khi deploy WAR) → provided; chỉ nạp qua JDBC/reflection → runtime; chỉ dùng trong test (JUnit, Mockito, Testcontainers) → test.

When

Dùng provided cho spring-boot-starter-tomcat khi đóng gói WAR để deploy lên Tomcat/WildFly bên ngoài, và cho servlet/JPA API khi container đã cung cấp. Dùng runtime cho driver PostgreSQL và thư viện nạp qua ServiceLoader.

When NOT

Không để spring-boot-starter-web hay spring-boot-starter-data-jpa ở scope provided trong ứng dụng chạy fat jar — build thành công nhưng app chết khi start. Không để Testcontainers/AssertJ ở scope compile vì chúng bị kéo vào image production. Không dùng scope system — hãy đưa artifact lên repository nội bộ.

<!-- pom.xml — scope đúng cho từng loại dependency -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
  <!-- compile (mac dinh) -> nam trong fat jar -->
</dependency>

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-tomcat</artifactId>
  <scope>provided</scope>   <!-- deploy WAR len container ngoai -->
</dependency>

<dependency>
  <groupId>org.postgresql</groupId>
  <artifactId>postgresql</artifactId>
  <scope>runtime</scope>    <!-- nap qua JDBC -->
</dependency>

<dependency>
  <groupId>org.testcontainers</groupId>
  <artifactId>postgresql</artifactId>
  <scope>test</scope>
</dependency>
Use case

Service deploy dạng executable jar lỗi ClassNotFoundException ngay khi start vì starter web bị set provided "cho nhẹ image" — sửa về compile là chạy được, jar nặng thêm vài MB nhưng đúng ngữ nghĩa.

Pitfall / Interview trap

Khi tách library dùng chung: đánh provided cho dependency mà consumer thực sự cần lúc chạy thì service phải tự khai lại — quên là production NoClassDefFoundError. Ngược lại, scope test không bao giờ transitive nên khai trong library không giúp consumer có được nó.

Nói trong 60 giây
  • compile/provided/runtime/test/system/import; scope đổi classpath và transitive.
  • provided: có lúc compile, không lúc runtime, không vào fat jar.
  • runtime: không compile, có runtime, có vào jar — ví dụ JDBC driver.
  • test: chỉ classpath test, không transitive; đừng để lọt vào production.
  • Boot repackage chỉ đóng gói compile + runtime ⇒ sai scope lộ lỗi ở prod.

Q3 dependencyManagement và BOM (spring-boot-dependencies) giải quyết vấn đề gì?

What

dependencyManagement khai báo version, scope và exclusion cho một dependency mà không thêm nó vào classpath: module con chỉ cần ghi groupId:artifactId là đã lấy đúng version đó. BOM (Bill of Materials) là POM chỉ gồm dependencyManagement, được import bằng type=pom + scope=import để chốt version cho cả một hệ sinh thái thư viện.

Why

Khai version lẻ tẻ ở từng module khiến cùng một thư viện có nhiều version trong cùng build → hai bản class trên classpath, lỗi NoSuchMethodError chỉ lộ lúc runtime. BOM tập trung quyết định version vào một chỗ, và với Spring Boot thì BOM đã chọn sẵn bộ version tương thích (Spring Framework, Hibernate, Jackson, JUnit) nên nâng framework là nâng một con số.

How
spring-boot-dependencies (BOM)
parent công ty / aggregator
↓ import vào dependencyManagement, không thêm classpath
module common
module order-service
module payment-service
↓ khai <dependency> KHÔNG version
Một version duy nhất cho toàn build

Có hai cách dùng: kế thừa spring-boot-starter-parent, hoặc đã có parent riêng của công ty thì import spring-boot-dependencies. Muốn lệch khỏi BOM, hãy khai entry tường minh trong dependencyManagement của project — entry của project thắng entry import. Override bằng cách đặt lại property chỉ chắc chắn khi property đó được kế thừa từ parent; với BOM import thì đừng trông vào cách đó.

When

Luôn dùng BOM cho Spring Boot (starter-parent hoặc import). Dùng thêm BOM của bên khác khi có nhiều artifact cùng họ: jackson-bom, testcontainers-bom, spring-cloud-dependencies. Dùng BOM nội bộ để chốt version cho library dùng chung giữa nhiều service.

When NOT

Không đặt <scope>import</scope> trong thẻ <dependencies> — chỉ dependencyManagement hiểu scope này, khai sai chỗ thì dependency không được thêm vào classpath. Không vừa import BOM vừa ghi version ở module: nó vô hiệu hoá BOM. Cũng không tự chọn version lệch BOM chỉ vì IDE gợi ý — lệch một artifact trong cùng bộ Spring có thể gây NoSuchMethodError.

<!-- Cach 1: ke thua parent chuan -->
<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>3.3.4</version>
</parent>

<!-- Cach 2: da co parent rieng -> import BOM -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>${spring-boot.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
    <!-- entry cua project thang entry import -->
    <dependency>
      <groupId>com.fasterxml.jackson.core</groupId>
      <artifactId>jackson-databind</artifactId>
      <version>2.17.2</version>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <!-- KHONG ghi version -> lay tu BOM -->
  <dependency><groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId></dependency>
</dependencies>
Use case

Nâng cả hệ sinh thái bằng một dòng: đổi spring-boot.version 3.2.x → 3.3.x, mọi service trong parent lấy đúng bộ Spring/Hibernate/Jackson tương thích.

Pitfall / Interview trap

dependencyManagement không kéo dependency vào build — chỉ khai ở đó thì classpath trống, nhiều bạn tưởng đã "cài" thư viện. Exclusion khai trong dependencyManagement cũng chỉ áp dụng khi entry đó thực sự được dùng để resolve.

Nói trong 60 giây
  • dependencyManagement = version/scope dùng chung, không thêm vào classpath.
  • BOM = POM chỉ chứa dependencyManagement, import bằng type=pom scope=import.
  • spring-boot-dependencies chốt bộ version tương thích cho cả hệ sinh thái.
  • Module con khai dependency không version; override bằng entry tường minh của project.
  • Lợi ích: nâng version tập trung, hết version drift trong multi-module.

Q4 Multi-module Maven: parent vs aggregator, reactor build order và khi nào tách module?

What

Parent làm việc kế thừa: module con dùng thẻ <parent> để nhận properties, dependencyManagement, pluginManagement và cấu hình chung. Aggregator làm việc tổng hợp: thẻ <modules> liệt kê các module để một lệnh build chạy tất cả. Một POM packaging=pom hoàn toàn có thể vừa là parent vừa là aggregator.

Why

Khi build nhiều module, Maven dựng reactor và sắp thứ tự theo quan hệ phụ thuộc giữa các module trước khi chạy — common luôn build trước order-service dù thứ tự trong <modules> ghi khác. Nhờ đó một lệnh build vẫn đúng thứ tự, và Maven phát hiện phụ thuộc vòng giữa module để báo lỗi sớm.

How
order-platform (parent + aggregator)
↓ reactor sắp theo phụ thuộc, không theo thứ tự khai báo
1. common
2. order-api
↓ module sau chỉ build được khi module trước đã có
3. order-service → jar chạy được

Cờ hay dùng: -pl chọn module (theo path hoặc :artifactId), -am build kèm module nó phụ thuộc, -amd build kèm module phụ thuộc vào nó, -T 1C build song song theo số core. Khi module phụ thuộc không nằm trong reactor và chưa có trong local repo, build sẽ lỗi resolve.

When

Tách module khi: (1) có library dùng chung cho nhiều service (common, dto, client) và muốn publish artifact có version riêng; (2) cần enforce boundary — module A không import được class của B nếu B không là dependency của A, điều package structure không cưỡng chế được; (3) tách API contract (order-api chứa DTO/interface) khỏi implementation; (4) build và test nhanh hơn nhờ chia nhỏ.

When NOT

Không tách khi chỉ có một deployable: over-splitting đổi lấy build chậm hơn, versioning overhead và refactor tốn công hơn. Không tạo module chỉ chứa vài class tiện ích. Không để cyclic dependency giữa module — dấu hiệu ranh giới sai, hãy rút phần dùng chung xuống module thấp hơn. Cũng không dùng parent khác nhau cho các module dùng chung BOM.

<!-- order-platform/pom.xml — vua parent vua aggregator -->
<groupId>com.example</groupId>
<artifactId>order-platform</artifactId>
<version>1.4.0</version>
<packaging>pom</packaging>
<modules>
  <module>common</module>
  <module>order-api</module>
  <module>order-service</module>
</modules>
<dependencyManagement><dependencies>
  <dependency><groupId>com.example</groupId>
    <artifactId>common</artifactId><version>${project.version}</version></dependency>
</dependencies></dependencyManagement>

<!-- order-service/pom.xml — con ke thua parent -->
<parent>
  <groupId>com.example</groupId>
  <artifactId>order-platform</artifactId>
  <version>1.4.0</version>
</parent>
<artifactId>order-service</artifactId>
<dependencies>
  <dependency><groupId>com.example</groupId><artifactId>common</artifactId></dependency>
  <dependency><groupId>com.example</groupId><artifactId>order-api</artifactId></dependency>
</dependencies>
# build toan bo reactor
./mvnw clean verify -T 1C

# chi build order-service + cac module no phu thuoc
./mvnw -pl order-service -am clean verify

# xem thu tu reactor truoc khi build that
./mvnw validate | grep -i reactor
Use case

Ba service dùng chung DTO và client: đưa chúng vào module order-api; service chỉ phụ thuộc artifact contract, và compiler cưỡng chế consumer không với được vào class nội bộ.

Pitfall / Interview trap

Parent không tự động build module con — thiếu <modules> thì mvn install ở POM cha không làm gì cho con. Ngược lại aggregator không truyền cấu hình — thiếu <parent> thì cấu hình chung không áp dụng.

Nói trong 60 giây
  • parent = inheritance; aggregator = <modules>; thường cùng một POM packaging=pom.
  • Reactor tự sắp build order theo phụ thuộc giữa module.
  • -pl / -am / -amd / -T 1C để build một phần và song song.
  • Tách module khi có library dùng chung hoặc cần enforce boundary.
  • Tránh over-splitting và cyclic dependency giữa module.

Gradle — task, plugin & version tập trung

Q5 Gradle: task, plugin, build phase là gì và vì sao Gradle build nhanh hơn Maven?

What

Gradle chạy build theo 3 pha: initialization (đọc settings.gradle.kts, xác định project), configuration (chạy build script để dựng task graph) và execution (thực thi các task thực sự cần). Task là đơn vị công việc có inputs/outputs; plugin (java, application, org.springframework.boot) áp sẵn task và nối chúng thành DAG.

Why

Gradle nhanh hơn không phải vì "viết bằng Kotlin" mà vì 4 cơ chế cộng dồn: (1) incremental build — task chỉ chạy lại khi input đổi, ngược lại báo UP-TO-DATE; (2) daemon giữ JVM nóng nên không tốn thời gian khởi động JVM mỗi lần build; (3) build cache lưu output task và tái dùng giữa các máy/CI run; (4) configuration cache và build song song giữa các project. Maven chạy tuần tự các phase đã bind và không có khái niệm up-to-date cho plugin tùy biến.

How
1. Initialization
2. Configuration → dựng task graph
↓ chỉ task trong graph được gọi là chạy
3. Execution: compileJava
test
jar
↓ input không đổi
UP-TO-DATE / FROM-CACHE — không chạy lại

Task như build là lifecycle task chỉ tổng hợp task khác: nó phụ thuộc assemble và check. Xem chính xác điều gì sẽ chạy bằng ./gradlew tasks, ./gradlew build --dry-run và ./gradlew taskTree.

Tiêu chíbuild.gradle.kts (Kotlin)build.gradle (Groovy)
Kiểm tra kiểuCó, lỗi phát hiện lúc compile scriptDynamic, typo chỉ lộ lúc chạy
IDEAutocomplete + refactor chính xácGợi ý yếu hơn

Khuyến nghịMặc định cho project mớiLegacy, nhiều ví dụ cũ
When

Dùng Gradle cho dự án mới, build nhiều module, cần logic tùy biến (custom task, transform artifact, Android). Dùng Kotlin DSL làm mặc định để script được type-check trong CI; Groovy DSL khi phải bảo trì script cũ.

When NOT

Không chuyển Maven → Gradle chỉ để "hiện đại": chi phí migrate hệ build lớn thường lớn hơn lợi ích nếu pipeline đang ổn. Không viết logic nặng trong pha configuration (đọc file, gọi mạng) — nó chạy ở mọi lần build kể cả khi task không được gọi, làm hỏng configuration cache. Không dựa vào thứ tự task khai báo — phải khai dependency qua dependsOn.

// build.gradle.kts
plugins {
    java
    id("org.springframework.boot") version "3.3.4"
}

java {
    toolchain { languageVersion = JavaLanguageVersion.of(21) }
}

// task co inputs/outputs -> duoc up-to-date check tu dong
tasks.register<Copy>("copyDockerfile") {
    from("src/main/docker")
    into(layout.buildDirectory.dir("docker"))
}

tasks.named<Test>("test") { useJUnitPlatform() }
# xem task nao se chay ma khong chay that
./gradlew build --dry-run

# xem vi sao mot task chay lai (input nao doi)
./gradlew compileJava --info | grep -i "not up-to-date"

# chay lai tu dau khi nghi cache sai
./gradlew build --rerun-tasks
Use case

Vòng lặp dev: sửa một class rồi ./gradlew test chỉ chạy lại compileJava + test với class đã đổi, các task khác báo UP-TO-DATE; trên CI bật build cache remote nên job test tái dùng output của module không thay đổi.

Pitfall / Interview trap

"Gradle nhanh hơn" chỉ đúng khi task khai báo inputs/outputs đúng: custom task không khai input sẽ luôn chạy hoặc luôn bị coi là up-to-date — cả hai đều sai. Trên CI container lạnh, lợi ích daemon biến mất, phần lớn tốc độ đến từ cache và incremental.

Nói trong 60 giây
  • 3 pha: initialization, configuration, execution.
  • Task = đơn vị công việc có inputs/outputs, nối thành DAG; plugin áp task sẵn.
  • build là lifecycle task phụ thuộc assemble + check.
  • Nhanh hơn nhờ incremental, daemon, build cache, configuration cache.
  • Kotlin DSL type-safe; Groovy DSL dynamic — chọn Kotlin cho project mới.

Q6 Version catalog (libs.versions.toml) và dependency locking để làm gì?

What

Version catalog là file gradle/libs.versions.toml khai báo tập trung [versions], [libraries], [bundles], [plugins]; build script tham chiếu qua accessor type-safe và có autocomplete như libs.jacksonDatabind. Dependency locking ghi lại version thực tế đã resolve (kể cả transitive) vào gradle.lockfile, các lần build sau chỉ dùng đúng những version đó.

Why

Catalog giải quyết trùng lặp và trôi version: một chỗ khai version, mọi module dùng chung. Locking giải quyết tính tái lập: khi có dynamic version (1.+, latest.release) hoặc range từ transitive dependency, hai lần build cách nhau vài ngày có thể resolve ra version khác nhau — build "chạy được hôm qua, hỏng hôm nay" dù code không đổi. Lock cũng là điểm kiểm soát bảo mật: version đã pin thì biết chính xác CVE nào đang có.

How
libs.versions.toml
version khai một lần
↓ accessor type-safe
build.gradle.kts dùng libs.*
↓ resolve lần đầu
gradle.lockfile — commit vào git
↓ CI/dev build lại
Đúng version như cũ (reproducible)

Lock chỉ áp dụng cho configuration đã bật trong khối dependencyLocking; dùng lockAllConfigurations() cho gọn. Khi chủ động nâng version, ghi lại lock bằng --write-locks hoặc cập nhật chọn lọc bằng --update-locks group:name. Lock file phải được commit, nếu không nó chỉ là file local và không có giá trị tái lập trên CI.

When

Dùng catalog cho mọi dự án Gradle, kể cả dự án nhỏ vì lợi ích autocomplete. Dùng locking khi có dynamic version/range, khi cần build tái lập nghiêm ngặt, khi CI/CD yêu cầu audit SCA, hoặc khi library nội bộ còn -SNAPSHOT. Maven không có lock file chuẩn nên cách tương đương là cấm version range, ghim version tường minh và thêm maven-enforcer-plugin với rule dependencyConvergence.

When NOT

Không commit lock file rồi nâng dependency bằng tay mà quên --write-locks — build sẽ lỗi vì lock cũ. Không bật lock cho configuration không quan trọng vì mỗi lần thêm plugin phải ghi lại lock. Không dùng dynamic version như cách "luôn mới nhất": đó là nguồn gốc của build không tái lập, version mới nên nâng qua Renovate/Dependabot có PR review.

# gradle/libs.versions.toml
[versions]
springBoot = "3.3.4"
jackson = "2.17.2"

[libraries]
springBootStarterWeb = { module = "org.springframework.boot:spring-boot-starter-web", version.ref = "springBoot" }
jacksonDatabind = { module = "com.fasterxml.jackson.core:jackson-databind", version.ref = "jackson" }

[bundles]
json = ["jacksonDatabind"]

[plugins]
springBoot = { id = "org.springframework.boot", version.ref = "springBoot" }
// build.gradle.kts
plugins { alias(libs.plugins.springBoot) }

dependencies {
    implementation(libs.springBootStarterWeb)
    implementation(libs.bundles.json)
}

// bat lock cho toan bo configuration
dependencyLocking { lockAllConfigurations() }
# sinh va commit lock file
./gradlew dependencies --write-locks
git add gradle.lockfile

# nang co chu dich mot thu vien
./gradlew build --update-locks com.fasterxml.jackson.core:jackson-databind
Use case

Đội nâng Spring Boot 3.2 → 3.3: sửa một dòng springBoot trong libs.versions.toml, chạy ./gradlew build --write-locks, review diff lock file để thấy chính xác transitive nào đổi version trước khi merge.

Pitfall / Interview trap

Catalog và lock giải quyết hai việc khác nhau nên đừng trả lời gộp: catalog quản lý khai báo, lock quản lý kết quả resolve. Lock file bị sửa tay là dấu hiệu xấu; hãy để Gradle ghi lại.

Nói trong 60 giây
  • Catalog: một chỗ khai version, accessor type-safe libs.*.
  • Lock: ghi version resolve thực tế, kể cả transitive, vào gradle.lockfile.
  • Lock cần khi có dynamic version/range hoặc yêu cầu audit.
  • --write-locks sinh lock, --update-locks nâng chọn lọc, commit lock file.
  • Maven không có lock: ghim version + enforcer dependencyConvergence.

Q7 Xung đột dependency transitive: Maven và Gradle chọn version thế nào, khi nào dùng exclude?

What

Transitive dependency là dependency của dependency. Khi hai đường khác nhau kéo về hai version của cùng một artifact, Maven áp nearest-wins (chọn bản ở đường ngắn nhất tính từ project gốc; bằng độ dài thì entry khai báo trước thắng), còn Gradle mặc định áp highest version wins trong các candidate của cùng configuration. Hai công cụ cho kết quả khác nhau trên cùng một graph.

Why

Hiểu sai cơ chế này khiến bạn debug sai chỗ: version chạy thực tế không phải version ghim ở dependency trực tiếp. Triệu chứng kinh điển là NoSuchMethodError, AbstractMethodError, ClassNotFoundException chỉ xuất hiện lúc runtime; hoặc trùng binding slf4j; hoặc lẫn javax.* với jakarta.* khi nâng Spring Boot 2 → 3.

How
order-service
↓ hai đường cùng kéo jackson-databind
A → jackson 2.15 (1 bậc)
B → C → jackson 2.17 (2 bậc)
↓ Maven: nearest-wins · Gradle: highest-wins
Maven chọn 2.15 — gần hơn
Gradle chọn 2.17 — cao hơn
↓ bơm version chủ đích
BOM / dependencyManagement / constraint: chốt một version

Bước chẩn đoán luôn là vẽ graph ra: Maven dùng mvn dependency:tree -Dverbose để thấy cả nhánh bị omitted for conflict, -Dincludes=groupId:artifactId để lọc đúng một artifact; Gradle dùng dependencyInsight --dependency X --configuration runtimeClasspath để biết ai kéo version nào và vì sao thắng. Sau khi biết nguyên nhân mới chọn cách sửa: BOM/constraint (tốt nhất), nâng dependency trực tiếp, rồi mới tới exclude.

When

Dùng exclude khi thư viện kéo vào một artifact bạn chắc chắn không dùng và gây hại thật: loại commons-logging vì đã dùng SLF4J, loại binding log thứ hai, hoặc loại client HTTP cũ đã bị thay. Dùng constraints/dependencyManagement khi chỉ cần ghim version mà vẫn muốn giữ dependency.

When NOT

Đừng dùng exclude như cách sửa đầu tiên: exclusion trong Maven phải khai ở từng dependency trực tiếp, nên một đường transitive mới xuất hiện là artifact quay lại classpath. Exclude quá tay cũng có thể cắt class mà thư viện cần lúc chạy, sinh NoClassDefFoundError — chỉ lộ ở production.

# Maven: ve graph, verbose de thay nhanh bi conflict
mvn dependency:tree -Dverbose -Dincludes=com.fasterxml.jackson.core:jackson-databind
mvn dependency:tree -Dscope=runtime > tree.txt

# Gradle: ai keo version nao va vi sao version do thang
./gradlew dependencyInsight --dependency jackson-databind --configuration runtimeClasspath
./gradlew dependencies --scan
// Gradle: constraint ghim version cho ca graph, khong phu thuoc duong di
dependencies {
    implementation("com.example:legacy-client:2.1.0") {
        // chi loai khi chac chan khong dung
        exclude(group = "commons-logging", module = "commons-logging")
    }
    constraints {
        implementation("com.fasterxml.jackson.core:jackson-databind:2.17.2")
    }
}
<!-- Maven: exclude dat o tung dependency truc tiep -->
<dependency>
  <groupId>com.example</groupId>
  <artifactId>legacy-client</artifactId>
  <exclusions>
    <exclusion>
      <groupId>commons-logging</groupId>
      <artifactId>commons-logging</artifactId>
    </exclusion>
  </exclusions>
</dependency>
Use case

Service ném NoSuchMethodError ở method mới của Jackson sau khi thêm một SDK. dependency:tree -Dverbose cho thấy SDK kéo nhánh Jackson cũ ở gần hơn; ghim version đúng bằng entry dependencyManagement (Maven) hoặc constraint (Gradle) là hết lỗi.

Pitfall / Interview trap

Nearest-wins và highest-wins là câu hỏi phân biệt rất hay gặp — trả lời "cả hai chọn version cao nhất" là sai. Và nếu dùng resolutionStrategy mà không ghi lại lý do, vài tháng sau đồng đội sẽ không hiểu vì sao version bị ghim.

Nói trong 60 giây
  • Transitive dependency gây xung đột version trong cùng classpath.
  • Maven nearest-wins (ngắn nhất, tie → khai trước); Gradle highest-wins.
  • Chẩn đoán: dependency:tree -Dverbose, dependencyInsight, --scan.
  • Ưu tiên BOM/dependencyManagement/constraint hơn exclude.
  • Exclude dễ vỡ khi graph đổi, có thể gây NoClassDefFoundError runtime.

Build tái lập, CI & quy trình Agile/Git

Q8 Build tái lập trên CI: wrapper, lock file, cache và publish artifact nào?

What

Build tái lập nghĩa là cùng source, cùng toolchain, cùng tập version dependency sẽ cho ra artifact giống nhau. Thực hành gồm: wrapper (mvnw/gradlew) để mọi máy và CI dùng đúng version build tool, chốt version bằng BOM + lock file, cache có khoá theo file khai báo dependency, và build một lần rồi promote nguyên bản artifact sang các môi trường.

Why

Môi trường là biến số lớn nhất của build: máy dev có Maven 3.8, CI cài Maven 3.9, máy khác có JDK khác → kết quả khác nhau và không ai tái hiện được lỗi của ai. Rebuild cho từng môi trường còn tệ hơn: base image mới hơn, dependency trôi version, dẫn tới "chạy được ở staging, chết ở prod". Promote cùng một artifact (cùng digest bất biến) loại bỏ nhóm lỗi đó.

How
Commit: ./mvnw hoặc ./gradlew
BOM + lock file
↓ CI: cache repository, build một lần
verify + test
build jar + image, tag bất biến
↓ promote cùng artifact, KHÔNG rebuild
dev
staging
prod
↓ rollback = deploy lại artifact cũ, tức thì

Cache trên CI phải khoá theo file khai báo dependency: Maven cache ~/.m2/repository với key là hash của pom.xml; Gradle cache ~/.gradle/caches với key là hash của gradle.lockfile + libs.versions.toml. Cache cũ là nguồn lỗi khó tìm nên cần đường thoát: --refresh-dependencies hoặc bump cache key khi nghi ngờ.

When

Áp dụng từ đầu cho mọi dự án có CI: commit wrapper, cấm version range, bật lock (Gradle) hoặc ghim version tường minh (Maven), cache theo hash file khai báo, và chỉ build một lần cho mỗi commit rồi promote. Nếu cần artifact byte-for-byte giống nhau thì cố định project.build.outputTimestamp (Maven).

When NOT

Không cache thư mục repository khi khai báo dependency đổi mà không khoá lại cache — CI sẽ dùng bản cũ và sinh lỗi "local đúng, CI sai". Không deploy bằng tag mutable như latest trong production, không publish -SNAPSHOT lên repo dùng cho release.

# CI: wrapper + cache khoá theo file khai báo dependency
name: ci
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven          # key theo pom.xml
      - run: ./mvnw -B -ntp clean verify
      - run: docker build -t registry.example.com/order-service:$GITHUB_SHA .
# version build tool lay tu wrapper, khong phu thuoc may cai san
./mvnw -v
./gradlew --version

# kiem tra build co tai lap voi cache/local repo hien co
./gradlew build --offline

# promote: deploy dung digest da build, khong build lai
docker inspect --format='{{index .RepoDigests 0}}' registry.example.com/order-service:1.4.0
Use case

Hotfix được test ở staging rồi promote nguyên image (cùng digest) sang production; rollback chỉ là deploy lại digest cũ, không phải chạy lại build với rủi ro kéo base image mới hơn.

Pitfall / Interview trap

Cache CI "thành công" nhưng vẫn sai vì key không đổi khi dependency đổi — luôn hash file khai báo vào cache key. Và --offline chỉ chứng minh repo hiện có đủ artifact, không chứng minh artifact hôm nay giống hệt tuần trước nếu còn dùng version động.

Nói trong 60 giây
  • Commit wrapper (mvnw/gradlew) — cố định version build tool.
  • Chốt version bằng BOM + lock file, cấm version range.
  • Cache CI khoá theo pom.xml / gradle.lockfile / libs.versions.toml.
  • Build một lần, promote cùng artifact qua dev → staging → prod.
  • Publish: jar library và container image; không publish fat jar/SNAPSHOT.

Q9 Agile/Scrum thực chiến và Git workflow: sprint, estimation, trunk-based vs GitFlow?

What

Scrum vận hành theo sprint 1–4 tuần (phổ biến là 2 tuần): product backlog do PO ưu tiên, sprint planning chọn sprint goal và độ lớn công việc, daily standup 15 phút đồng bộ tiến độ và blocker, sprint review demo với stakeholder, retrospective cải tiến cách làm việc. Ước lượng bằng story point (độ lớn tương đối theo dãy Fibonacci) và dùng velocity để dự báo, không dùng làm chỉ số năng suất.

Why

Story point không phải đơn vị thời gian nên không quy đổi "1 point = 1 giờ" — quy đổi là mất tính tương đối và biến estimate thành cam kết. Velocity là kết quả đo để biết sprint sau nhận bao nhiêu việc; dùng nó làm KPI sẽ dẫn tới thổi điểm và cắt góc kiểm thử. Về Git, nhánh càng sống lâu càng tích luỹ merge conflict và tích hợp muộn; nhánh ngắn giữ main luôn gần trạng thái deploy được.

↓ sprint 1–4 tuần, standup mỗi ngày

Với team nhiều người, chốt trước: branch naming feat/<ticket>-mô-tả, fix/…, hotfix/…; commit theo Conventional Commits (feat|fix|refactor|perf|test|docs|build|ci|chore kèm scope) để sinh changelog và bump version tự động; PR nhỏ (dưới ~400 dòng diff), 1–2 reviewer, CI phải xanh trước khi merge, và main được bảo vệ.

When

Trunk-based khi team có CI/CD tự động, deploy thường xuyên, sản phẩm là service (web/SaaS) và dùng được feature flag để che phần chưa xong. GitFlow khi phải phát hành phiên bản đóng gói theo lịch, hỗ trợ nhiều bản song song, hoặc vá khẩn cấp trên bản đã phát hành. Kanban phù hợp khi luồng công việc liên tục, không muốn chia sprint.

When NOT

Đừng "trunk-based hình thức" rồi vẫn giữ nhánh feature sống 2 tuần — đó là gánh nặng của cả hai quy trình. Đừng để standup thành báo cáo cho quản lý, đừng estimation theo giờ trong planning poker, và đừng đóng sprint khi chưa đạt Definition of Done. Retro phải có action item có người chịu trách nhiệm.

# trunk-based: nhanh ngan, rebase de giu lich su tuyen tinh
git switch -c feat/JIRA-412-order-export
git commit -m "feat(order): add CSV export endpoint" \
           -m "Stream theo page de gioi han memory khi export don lon."
git fetch origin
git rebase origin/main
git push -u origin HEAD
# PR nho -> review -> CI xanh -> squash merge vao main

# hotfix tren ban da phat hanh (GitFlow)
git switch -c hotfix/1.4.1-payment-timeout main
git commit -m "fix(payment): retry on gateway timeout"
git tag -a v1.4.1 -m "hotfix 1.4.1"
Use case

Sprint 2 tuần, velocity trung bình 34 point: planning nhận khoảng 30 point để còn buffer cho bug production và review; PR nào quá lớn bị yêu cầu tách nhỏ trước khi review.

Pitfall / Interview trap

Hai bẫy hay bị hỏi: (1) dùng velocity làm KPI năng suất → team phình estimate; (2) nhầm story point là thời gian. Về Git: rebase lên nhánh người khác đang dùng sẽ viết lại lịch sử chung — chỉ rebase nhánh riêng của mình.

Nói trong 60 giây
  • Scrum: backlog → planning → sprint → review → retro; DoD rõ ràng.
  • Story point là độ lớn tương đối; velocity để dự báo, không phải KPI.
  • Trunk-based: nhánh ngắn 1–2 ngày, merge liên tục, cần CI mạnh + feature flag.
  • GitFlow: develop/release/hotfix cho bản phát hành theo lịch.
  • PR nhỏ, CI gate, branch naming + Conventional Commits.
