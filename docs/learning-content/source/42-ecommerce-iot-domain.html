Miền nghiệp vụ E-commerce, Enterprise & IoT

Kiến thức miền giúp trả lời phỏng vấn fullstack: mô hình bán hàng, vòng đời đơn hàng, thanh toán idempotent, khuyến mãi, tìm kiếm và hệ thống IoT (MQTT, device twin, telemetry).

E-commerce: catalog, đơn hàng & thanh toán

Q1 Catalog/product variant, tồn kho và giá — tách read model/write model khi nào, và vì sao order phải lưu snapshot giá?

What

Catalog chia product (SPU) thành variant (SKU): tồn kho quản lý theo SKU × location, giá theo price list có hiệu lực theo thời gian. Read model (list, search, detail) được denormalize để đọc nhanh, write model chuẩn hóa để ghi đúng — và mỗi order line bắt buộc lưu snapshot giá tại thời điểm đặt hàng.

Why

Traffic đọc catalog thường lớn hơn ghi hàng chục đến hàng trăm lần, đồng thời cần join nhiều bảng (variant, attribute, price, stock, khuyến mãi). Nếu để chung một mô hình, mỗi lần đọc phải join nặng và mỗi lần ghi giá/tồn kho lại ảnh hưởng path đọc. Tách read model giúp scale độc lập; snapshot giá trong order đảm bảo hoá đơn, thuế và đối soát không đổi khi catalog thay đổi giá về sau.

How
Write model (Product / Variant / PriceList / Stock)
↓ domain event (ProductUpdated, PriceChanged, StockAdjusted)
Projection / Outbox
Search index (denormalized doc)
↓
Read model cho list/detail/search
Order line: snapshot giá + tax + discount

Ghi vào write model trong một transaction, phát event ra ngoài, projection cập nhật read model. Order khi tạo chỉ đọc giá hiện hành rồi sao chép các con số vào chính order line.

@Entity
public class OrderLine {
  private Long skuId;
  private String productName;      // snapshot
  private BigDecimal unitPrice;     // snapshot giá tại thời điểm đặt
  private String currency;         // VND
  private BigDecimal discountAmount; // snapshot khuyến mãi đã áp
  private BigDecimal taxRate;        // snapshot thuế
  private Long priceVersion;        // trỏ tới price list version đã dùng
}
When

Tách read/write khi catalog lớn (hàng trăm nghìn SKU trở lên), traffic đọc cao và có nhiều view khác nhau (mobile, web, feed). Snapshot giá dùng trong mọi hệ thống có hoá đơn: thương mại điện tử, B2B báo giá, dịch vụ thuê theo gói.

When NOT

Không tách CQRS chỉ vì "nghe hay" — dưới vài nghìn SKU và traffic thấp thì một DB với index đúng là đủ, tách chỉ thêm độ trễ đồng bộ và phức tạp vận hành. Không tham chiếu động giá catalog vào order cũ. Không để read model là nguồn sự thật cho tồn kho.

Use case

Nền tảng dịch vụ không gian: catalog sản phẩm/thiết bị có nhiều variant theo công suất và phụ kiện; trang danh mục đọc read model đã denormalize, còn đơn hàng lưu snapshot giá và cấu hình gói tại thời điểm mua để đối soát sau này.

Pitfall / Interview trap

Bẫy kinh điển: lưu sku_id trong order rồi lúc in hoá đơn lại join sang catalog để lấy giá — giá đã đổi thì hoá đơn sai. Cũng đừng nhầm tồn kho "hiển thị" (read model, có thể trễ vài giây) với tồn kho "giữ chỗ" (write model, phải chính xác).

Nói trong 60 giây
  • Catalog = SPU → SKU variant; tồn kho theo SKU × location; giá theo price list.
  • Tách read model (denormalized, scale đọc) khỏi write model (chuẩn hóa, nguồn sự thật).
  • Đồng bộ bằng domain event + outbox, chấp nhận eventual consistency.
  • Order luôn snapshot giá/thuế/discount để hoá đơn bất biến.
  • Không tách CQRS khi quy mô nhỏ.

Q2 State machine cho vòng đời đơn hàng/fulfillment — transition nào hợp lệ, chống double-processing thế nào?

What

Vòng đời đơn hàng là một state machine hữu hạn: mỗi trạng thái chỉ cho phép một tập transition hợp lệ (CREATED → PENDING_PAYMENT → PAID → ALLOCATED → PICKING → PACKED → SHIPPED → DELIVERED, cùng nhánh CANCELLED/RETURNED). Mọi thay đổi trạng thái đi qua một lệnh duy nhất kèm idempotency key, để một event lặp lại không đẩy đơn đi hai bước.

Why

Đơn hàng nhận event từ nhiều nguồn (payment webhook, WMS, carrier, con người) nên gần như chắc chắn có event đến trùng hoặc đến sai thứ tự. Không có state machine thì một webhook retry có thể ship hai lần hoặc chuyển PAID → SHIPPED bỏ qua bước giữ tồn kho. Transition map biến quy tắc nghiệp vụ thành dữ liệu kiểm tra được, và idempotency key biến thao tác thành an toàn khi lặp.

How
Nhận order event + idempotency key
↓
Đã xử lý key này? → bỏ qua (return sớm)
Lock order (SELECT FOR UPDATE)
↓ canTransitionTo(next)?
Cập nhật status + outbox event
Không hợp lệ → reject, ghi log

Đọc order với khoá bi quan hoặc optimistic version, kiểm tra transition, ghi trạng thái mới và phát event trong cùng transaction bằng outbox.

public enum OrderStatus {
  CREATED, PENDING_PAYMENT, PAID, ALLOCATED, PICKING, PACKED, SHIPPED, DELIVERED, CANCELLED, RETURNED;

  private static final Map<OrderStatus, Set<OrderStatus>> TRANSITIONS = Map.of(
      CREATED,        Set.of(PENDING_PAYMENT, CANCELLED),
      PENDING_PAYMENT,Set.of(PAID, CANCELLED),
      PAID,           Set.of(ALLOCATED, CANCELLED),
      ALLOCATED,      Set.of(PICKING, CANCELLED),
      PICKING,        Set.of(PACKED),
      PACKED,         Set.of(SHIPPED),
      SHIPPED,        Set.of(DELIVERED, RETURNED),
      DELIVERED,      Set.of(RETURNED)
  );

  public boolean canTransitionTo(OrderStatus next) {
    return TRANSITIONS.getOrDefault(this, Set.of()).contains(next);
  }
}

@Transactional
public void applyTransition(Long orderId, OrderStatus next, String idemKey) {
  if (!processedRepo.tryInsert(idemKey)) return;   // đã xử lý → bỏ qua
  Order order = orderRepo.findByIdForUpdate(orderId).orElseThrow();
  if (!order.getStatus().canTransitionTo(next))
    throw new InvalidTransitionException(order.getStatus(), next);
  order.setStatus(next);
  outbox.publish(new OrderStatusChangedEvent(orderId, next));
}
When

Mọi hệ thống có đơn hàng hoặc job chạy qua nhiều bước: bán lẻ, đặt lịch dịch vụ, vận hành kho (picking/packing/shipping), quy trình onboarding nhiều bước. Đặc biệt cần khi có webhook từ bên thứ ba.

When NOT

Không dùng state machine cho dữ liệu không có ràng buộc thứ tự (ví dụ gắn thẻ, ghi log). Không cho phép transition "nhảy" tùy tiện như PAID → SHIPPED bỏ ALLOCATED. Đừng giữ idempotency key vô hạn — cần TTL hoặc bảng riêng có dọn dẹp.

Use case

Webhook thanh toán bị retry 3 lần: lần 1 chuyển đơn PENDING_PAYMENT → PAID; lần 2, 3 cùng idempotency key nên bị bỏ qua, đơn không bị đẩy sang bước fulfillment hai lần.

Pitfall / Interview trap

Bẫy hay gặp: kiểm tra trạng thái bằng chuỗi if/else rải rác thay vì một transition map duy nhất, khiến hai nơi code cho ra hai kết quả khác nhau. Ngoài ra, event đến sai thứ tự (PAID đến sau khi đã CANCELLED) phải bị state machine từ chối một cách chủ động, không im lặng nuốt lỗi.

Nói trong 60 giây
  • Order = state machine với transition map tường minh.
  • Chỉ cho phép bước kế tiếp hợp lệ, chặn skip bước.
  • Mỗi lệnh kèm idempotency key để chống double-processing.
  • Lock order + kiểm tra transition + outbox trong cùng TX.
  • Event sai thứ tự/trùng phải bị từ chối, không âm thầm bỏ qua.

Q3 Thiết kế thanh toán: idempotency, webhook retry, reconciliation và xử lý callback đến trễ?

What

Thanh toán gồm luồng đồng bộ (authorize/capture do hệ thống chủ động gọi) và luồng bất đồng bộ (webhook từ gateway báo kết quả). Idempotency key chống thu tiền hai lần, webhook phải chịu được retry và đến trễ, còn reconciliation đối chiếu ledger nội bộ với settlement của gateway theo lô định kỳ. Trạng thái chuẩn: PENDING, PAID, FAILED, REFUNDED.

Why

Mạng chập, client double-click, gateway retry webhook và callback đến trễ đều là chuyện bình thường, không phải ngoại lệ. Không có idempotency thì một cú retry thành hai lần trừ tiền — hậu quả về niềm tin và pháp lý. Không có reconciliation thì các lệch lạc âm thầm (gateway đã thu nhưng ledger nội bộ chưa ghi) sẽ chỉ lộ ra khi khách khiếu nại.

How
POST /payments (Idempotency-Key)
→
Payment PENDING
↓ gọi gateway authorize/capture
Webhook báo PAID/FAILED
Kiểm tra signature + eventId
Cập nhật nếu chưa có kết quả
↓ job hằng ngày
Reconciliation vs settlement

Ghi PENDING trước khi gọi gateway. Webhook đến thì xác thực chữ ký, dedupe theo eventId, chỉ chuyển trạng thái khi đang còn PENDING; callback đến trễ khi đã PAID thì bị coi là trùng và bỏ qua.

Content-Type: application/json

  "paymentId": "pay_771", "orderId": "ord_204",
  "amount": 1250000, "currency": "VND", "status": "PAID",
  "occurredAt": "2026-10-16T03:12:44Z" }
-- Reconciliation: tìm lệch giữa ledger nội bộ và settlement của gateway
SELECT p.order_id,
       p.amount              AS ledger_amount,
       g.amount              AS gateway_amount,
       p.status              AS ledger_status,
       g.status              AS gateway_status
FROM payments p
FULL OUTER JOIN gateway_settlement g
  ON g.txn_ref = p.gateway_ref
WHERE p.amount <> g.amount
   OR p.status <> g.status
   OR g.txn_ref IS NULL;   -- gateway có, nội bộ thiếu
When

Checkout thương mại điện tử, thu phí định kỳ, ví nội bộ, thanh toán COD có đối soát với đơn vị vận chuyển. Cần mỗi khi tiền đi qua một bên thứ ba không kiểm soát được.

When NOT

Không dùng float/double cho tiền — dùng BigDecimal hoặc đơn vị nhỏ nhất (long cents). Không xoá bản ghi payment, chỉ thêm bản ghi reversal. Không trả tiền trong cùng transaction với gọi gateway (không thể 2PC ra ngoài). Không bỏ qua xác thực chữ ký webhook.

Use case

Khách bấm "Thanh toán" hai lần trong 2 giây: cùng Idempotency-Key nên lần hai trả về đúng paymentId cũ, không phát sinh giao dịch thứ hai. Webhook "captured" đến trễ 30 phút khi đơn đã PAID cũng chỉ bị dedupe.

Pitfall / Interview trap

Bẫy: webhook đến trước khi response đồng bộ về, hoặc đến trễ sau khi đơn đã hủy — phải có quy tắc thắng thua rõ ràng (thường trạng thái cuối của gateway thắng, nhưng chỉ một lần). Một bẫy khác: idempotency key lưu theo request nhưng quên scope theo merchant/user, khiến hai khách khác nhau va vào cùng key.

Nói trong 60 giây
  • Idempotency-Key + dedupe eventId chống thu tiền hai lần.
  • Ghi PENDING trước khi gọi gateway, đối chiếu sau.
  • Webhook: xác thực chữ ký, retry được, callback trễ bị bỏ qua.
  • Trạng thái: PENDING / PAID / FAILED / REFUNDED, chỉ thêm reversal.
  • Reconciliation hàng ngày với settlement của gateway.

Q4 Luồng cart → checkout → payment → fulfillment: chỗ nào cần transaction, chỗ nào cần saga và bù trừ?

What

Luồng cart → checkout → payment → fulfillment trải qua nhiều bounded context nên không thể bọc trong một transaction: chỉ giữ transaction ACID cục bộ ở nơi có bất biến dữ liệu (giữ tồn kho, ghi payment, tạo order), phần điều phối cross-service dùng saga với các bước bù trừ khi một bước thất bại.

Why

Checkout chạm tới tính tồn kho, thu tiền, và khởi tạo fulfillment (WMS: picking, packing, shipping) — mỗi phần có DB riêng và bên thứ ba riêng. Cố gắng dùng một transaction phân tán (2PC) vừa không khả thi với gateway bên ngoài vừa làm giảm khả dụng. Saga cho phép tiến triển độc lập và quay lui logic khi cần: nhả tồn kho, hoàn tiền.

How
Cart (Redis)
→
Checkout
→
Payment authorize/capture
↓
Order PAID (TX cục bộ)
Reserve inventory
WMS: picking → packing
↓
Carrier / shipping
Bù trừ khi lỗi: nhả tồn kho / hoàn tiền

Orchestrator điều phối tuần tự; mỗi bước ghi trạng thái saga để có thể retry và bù trừ idempotent khi bước sau thất bại.

@Transactional
public Long reserveStock(Long orderId, List<OrderLine> lines) {
  for (OrderLine line : lines) {
    // optimistic: chỉ trừ khi còn đủ, atomic trong 1 câu UPDATE
    int updated = stockRepo.decrementIfAvailable(line.getSkuId(), line.getQty());
    if (updated == 0)
      throw new InsufficientStockException(line.getSkuId());
  }
  return orderId;   // bước saga: reserve-inventory
}

// Bù trừ (compensation) — phải idempotent
public void releaseStock(Long orderId, List<OrderLine> lines) {
  for (OrderLine line : lines) stockRepo.increment(line.getSkuId(), line.getQty());
}
When

Dùng transaction cục bộ cho: giữ/trừ tồn kho, ghi order và order line, ghi payment. Dùng saga cho: chuỗi reserve tồn kho → thu tiền → tạo shipment → (nếu cần) carrier. Áp dụng khi số bước từ ba trở lên và chấp nhận eventual consistency vài giây.

When NOT

Không dùng saga cho thao tác nằm gọn trong một DB — chỉ tổn thêm độ phức tạp. Không bù trừ bằng cách xoá bản ghi đã ghi (chỉ ghi bản ghi đối ứng). Không gọi chuỗi 5 service đồng bộ không timeout, không circuit breaker. Không giữ tồn kho vô thời hạn — cần timeout nhả chỗ.

Use case

Đơn dịch vụ không gian gồm thiết bị + gói lắp đặt: hệ thống giữ tồn kho thiết bị, thu tiền, rồi tạo lệnh picking cho kho. Nếu bước tạo shipment lỗi, saga nhả tồn kho và hoàn tiền, không để đơn treo nửa vời.

Pitfall / Interview trap

Bẫy: bước bù trừ không idempotent, chạy retry lại nhả tồn kho hai lần gây oversell. Một bẫy khác: thu tiền trước nhưng không có đường hoàn khi tồn kho thất bại giữa chừng — thứ tự bước và ma trận bù trừ phải được thiết kế trước khi code.

Nói trong 60 giây
  • Transaction cục bộ chỉ ở nơi có bất biến: tồn kho, order, payment.
  • Cross-service dùng saga + bù trừ, không dùng 2PC.
  • Mỗi bước idempotent, ghi trạng thái saga để retry được.
  • Tồn kho giữ chỗ có timeout, không treo vô hạn.
  • Compensation luôn là bản ghi đối ứng, không xoá dữ liệu.

Khuyến mãi, pricing & tìm kiếm

Q5 Promo/pricing rule engine: thứ tự áp dụng giảm giá, chống lạm dụng voucher, tính giá theo thời điểm?

What

Pricing/promotion engine tách luật giảm giá khỏi code thành dữ liệu có phiên bản: mỗi rule gồm điều kiện, hành động, độ ưu tiên, khả năng xếp chồng và khoảng thời gian hiệu lực. Engine áp dụng theo một thứ tự xác định để kết quả tính giá luôn tái lập được, và mọi kết quả đều lưu lại rule nào đã thắng.

Why

Khuyến mãi thay đổi liên tục và do bộ phận kinh doanh đặt, nếu hard-code vào service thì mỗi đợt sale là một lần deploy. Thứ tự áp dụng quyết định số tiền giảm (giảm giá trước hay sau khi trừ voucher, có cộng dồn hay không), và tính theo thời điểm quyết định khách có được giá đó hay không khi giá đổi giữa lúc bỏ giỏ và lúc thanh toán.

How
Giỏ hàng (line, qty, subtotal)
→
Lọc rule còn hiệu lực tại thời điểm T
↓ xếp theo priority
1. Item-level (giảm theo line)
2. Order-level (giảm theo tổng)
3. Voucher/free-ship
↓
Tổng tiền cuối + breakdown rule đã áp

Quy tắc vàng: item-level trước, order-level sau, voucher sau cùng, và mọi phép tính dùng một thứ tự cố định. Rule xung đột (exclusiveWith) bị loại; nếu nhiều rule cùng priority, chọn cái cho khách lợi nhất và ghi lại lý do.

-- Chống lạm dụng voucher: ràng buộc ở DB, không chỉ ở app
CREATE TABLE voucher_redemption (
  voucher_id  BIGINT NOT NULL,
  user_id     BIGINT NOT NULL,
  order_id    BIGINT NOT NULL,
  redeemed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT uk_voucher_user UNIQUE (voucher_id, user_id)
);

-- Chỉ trừ lượt khi đơn thực sự PAID, dùng 1 câu UPDATE điều kiện
UPDATE voucher
SET used_count = used_count + 1
WHERE id = :id
  AND used_count < max_uses
  AND status = 'ACTIVE';
When

Dùng khi có nhiều loại ưu đãi cùng tồn tại (giảm giá sản phẩm, mã đơn hàng, freeship, quà tặng), khi có nhiều kênh bán, hoặc khi giá thay đổi theo thời điểm (giá theo giờ cao điểm, giá thuê theo gói). Chống lạm dụng quan trọng khi chi phí mỗi lượt giảm giá đáng kể.

When NOT

Không dựng rule engine nếu chỉ có một chương trình giảm giá cố định — một bảng config là đủ. Không tin dữ liệu giá gửi từ client; luôn tính lại phía server. Không áp rule theo thời gian "now" của từng request mà không chốt thời điểm — cần một mốc thời gian dùng chung cho cả phiên tính giá.

Use case

Chiến dịch bán thiết bị lọc không khí: giảm 10% theo danh mục, cộng mã freeship nếu không đối kháng, trừ thêm cho hạng thành viên. Engine trả về breakdown để hiển thị "tiết kiệm 320.000đ" và lưu lại để đối soát doanh thu khuyến mãi.

Pitfall / Interview trap

Bẫy: kiểm tra lượt dùng voucher bằng đọc rồi ghi (read-then-write) — hai request đồng thời cùng vượt được. Phải ràng buộc bằng UNIQUE và UPDATE điều kiện ở DB. Bẫy thứ hai: áp mã ở giỏ hàng bằng thời điểm bỏ giỏ, nhưng lúc thanh toán rule đã hết hạn — cần chốt giá theo thời điểm checkout và báo rõ nếu đổi.

Nói trong 60 giây
  • Rule = dữ liệu có version: điều kiện, hành động, priority, hiệu lực.
  • Thứ tự cố định: item-level → order-level → voucher/freeship.
  • Chốt thời điểm tính giá, tính lại phía server.
  • Chống lạm dụng bằng UNIQUE + UPDATE điều kiện ở DB.
  • Lưu breakdown để hiển thị và đối soát.

Q6 Tìm kiếm và đề xuất trong e-commerce: full-text, filter facet và ranking theo doanh thu/tồn kho?

What

Tìm kiếm e-commerce chạy trên search engine (inverted index + facet) chứ không phải LIKE trên DB giao dịch. Ranking kết hợp relevance văn bản với tín hiệu kinh doanh như doanh thu và tồn kho; phần đề xuất là bài toán riêng dùng quan hệ cùng xuất hiện và vector tương đồng để gợi ý sản phẩm liên quan.

Why

Người mua bỏ đi rất nhanh nếu tìm sai hoặc kết quả chậm, và LIKE '%...%' trên bảng giao dịch vừa không dùng được index vừa tranh tài nguyên với đơn hàng. Facet cần đếm theo thuộc tính (hãng, khoảng giá, công suất) — đây là việc search engine làm rất tốt. Đẩy sản phẩm còn tồn kho và bán chạy lên trên giúp tăng chuyển đổi và giảm hàng tồn.

How
Write model DB
→
Indexer (event + CDC)
→
Search index
↓
Query: match + filter + facet
Ranking: relevance × business signal
Kết quả + facet counts

Indexer đẩy document denormalized (tên, mô tả, thuộc tính, giá, còn hàng, doanh thu 30 ngày) vào index. Query lọc trước rồi mới tính điểm; tín hiệu kinh doanh nhân vào score sau relevance để không phá vỡ tính liên quan.

{
  "query": {
    "function_score": {
      "query": {
        "bool": {
          "must":   [ { "multi_match": { "query": "may loc khong khi",
                        "fields": ["name^3", "brand", "keywords"] } } ],
          "filter": [ { "term": { "status": "ACTIVE" } },
                      { "term": { "in_stock": true } } ]
        }
      },
      "functions": [
        { "field_value_factor": { "field": "revenue_30d", "modifier": "log1p",
                                  "factor": 0.01, "missing": 0 } },
        { "gauss": { "stock_age_days": { "origin": 0, "scale": 30, "decay": 0.5 } } }
      ],
      "score_mode": "sum",
      "boost_mode": "multiply"
    }
  },
  "aggs": {
    "by_brand": { "terms": { "field": "brand.keyword" } },
    "by_price": { "range": { "field": "price",
        "ranges": [ { "to": 2000000 }, { "from": 2000000, "to": 5000000 },
                    { "from": 5000000 } ] } }
  }
}
When

Dùng search engine khi catalog từ vài nghìn SKU trở lên, cần facet, gợi ý gõ tới đâu ra tới đó, hoặc cần xếp hạng theo nghiệp vụ. Đề xuất liên quan phù hợp ở trang chi tiết sản phẩm và giỏ hàng trống.

When NOT

Không dùng search engine làm nguồn sự thật cho tồn kho hay giá — chỉ là bản sao có thể trễ. Không trả kết quả hết hàng mà không đánh dấu. Không để index lệch quá lâu so với DB. Không ép toàn bộ listing lên RAM cho mọi collection nhỏ.

Use case

Người dùng gõ "máy lọc không khí cho phòng 20m2": filter theo khoảng giá và hãng trả facet counts, sản phẩm còn tồn kho và bán chạy được đẩy lên đầu; trang chi tiết gợi ý filter thay thế dựa trên quan hệ cùng xuất hiện trong đơn hàng.

Pitfall / Interview trap

Bẫy: để in_stock trong index lệch nhiều phút nên khách bấm vào báo hết hàng — cần đồng bộ gần thời gian thực cho các field quan trọng và xác nhận lại khi thêm vào giỏ. Một bẫy nữa: ghi điểm theo doanh thu quá mạnh khiến kết quả không còn liên quan tới truy vấn.

Nói trong 60 giây
  • Search engine cho full-text + facet, không LIKE trên DB giao dịch.
  • Index document denormalized, cập nhật bằng event/CDC.
  • Ranking = relevance × tín hiệu kinh doanh (doanh thu, tồn kho).
  • Đề xuất dùng co-occurrence và vector tương đồng.
  • Index là bản sao, DB vẫn là nguồn sự thật.

IoT: ingestion, device shadow & telemetry

Q7 IoT ingestion: MQTT hay HTTP, QoS 0/1/2, at-least-once vs exactly-once và buffer khi mất mạng?

What

MQTT là giao thức pub/sub nhẹ chạy trên TCP cho thiết bị băng thông thấp, hỗ trợ QoS 0/1/2 và session bền qua broker; HTTP phù hợp thiết bị gửi thưa hoặc cần request/response rõ ràng. Ingestion trên thực tế gần như luôn là at-least-once, nên consumer phải idempotent theo cặp (deviceId, seq) chứ không mơ tới exactly-once đầu-cuối.

Why

Hàng nghìn thiết bị có thể mất mạng bất cứ lúc nào, băng thông rất hẹp và nguồn pin hạn chế. MQTT giữ một kết nối dài và overhead header nhỏ, tiết kiệm hơn nhiều so với mở lại TLS cho từng message HTTP. Hiểu QoS để chọn đúng: gửi số liệu cảm biến định kỳ không cần QoS 2, còn lệnh điều khiển thì không được mất.

How
Thiết bị
→
Gateway (TLS, auth)
→
MQTT broker (QoS 1, session bền)
↓
Ingestion service
Kafka (partition theo deviceId)
TSDB / Rules engine
↓ khi mất uplink
Store-and-forward buffer (disk trên gateway)

Thiết bị gửi QoS 1 kèm số thứ tự tăng dần; gateway đẩy vào topic, ingestion dedupe theo (deviceId, seq) trước khi ghi. Khi mất uplink, gateway ghi message xuống đĩa và replay khi có mạng.

// Gateway: giữ session để nhận lại message QoS 1 chưa được ack
MqttClient client = new MqttClient(
    "ssl://broker.internal:8883", clientId, new MemoryPersistence());

MqttConnectOptions opts = new MqttConnectOptions();
opts.setCleanSession(false);        // giữ session, không mất QoS 1 đang chờ
opts.setAutomaticReconnect(true);
opts.setMaxInflight(100);            // chặn tràn bộ nhớ khi mạng kém
client.connect(opts);
client.subscribe("site/+/device/+/telemetry", 1);

client.setCallback((topic, msg) -> {
  try {
    kafka.send("iot.telemetry", topic, msg.getPayload());
  } catch (Exception e) {
    diskBuffer.append(topic, msg.getPayload());   // replay sau
  }
});
When

MQTT khi thiết bị gửi thường xuyên, cần đẩy lệnh xuống (server push), hoặc kết nối chập chờn. HTTP khi thiết bị gửi thưa (vài lần mỗi giờ), dùng thiết bị đơn giản không giữ kết nối, hoặc cần đi qua proxy/hạ tầng sẵn có. QoS 1 là lựa chọn mặc định cho telemetry; QoS 2 chỉ khi trùng lặp gây hậu quả thật.

When NOT

Không dùng QoS 2 cho mọi telemetry — tốn round-trip, giảm throughput. Không dùng QoS 0 cho lệnh điều khiển hoặc sự kiện cảnh báo. Không dựa vào MQTT để bảo đảm exactly-once đầu-cuối — consumer vẫn phải idempotent. Không để buffer ở gateway phình vô hạn làm đầy đĩa.

Use case

Thiết bị khử trùng gửi số liệu mỗi 30 giây: gateway giữ buffer khi mất mạng trong 2 giờ, khi có mạng gửi lại theo đúng thứ tự; ingestion dedupe nên số liệu không bị đếm trùng dù message có thể được gửi lại nhiều lần.

Pitfall / Interview trap

Bẫy: nhầm QoS cao với exactly-once — QoS 2 chỉ bảo đảm giữa client và broker, không bảo đảm phía sau broker. Bẫy thứ hai: dùng cleanSession=true khiến message QoS 1 đang chờ bị mất khi thiết bị ngắt kết nối. Bẫy thứ ba: không giới hạn maxInflight làm thiết bị hết RAM khi mạng chậm.

Nói trong 60 giây
  • MQTT pub/sub nhẹ cho thiết bị thường xuyên; HTTP cho thiết bị gửi thưa.
  • QoS 0 hao nhất và có thể mất; QoS 1 ít nhất một lần; QoS 2 chỉ với lệnh quan trọng.
  • Thực tế là at-least-once → consumer dedupe theo (deviceId, seq).
  • Session bền + memoryPersistence để không mất message chờ ack.
  • Store-and-forward ở gateway khi mất uplink, có giới hạn đĩa.

Q8 Device twin/shadow và điều khiển thiết bị: desired vs reported, command/ack, đồng bộ offline, versioning firmware?

What

Device shadow (twin) là bản sao trạng thái thiết bị trên cloud gồm hai phần: desired (cloud muốn) và reported (thiết bị báo về). Điều khiển bằng cách ghi desired rồi phát command; thiết bị thực thi và gửi ack. Chênh lệch giữa desired và reported chính là phần việc còn phải làm, gọi là delta.

Why

Thiết bị IoT thường xuyên mất mạng, nên không thể giả định lệnh được thực thi ngay. Shadow tách "ý muốn" khỏi "thực tế" và cho phép gửi lại khi thiết bị online. Versioning trên shadow tránh việc ghi cũ ghi đè ghi mới, còn versioning firmware giúp rollout và rollback có kiểm soát thay vì mỗi máy một phiên bản không rõ.

How
App ghi desired
→
Shadow (desired / reported, version++)
↓ tính delta
Command xuống thiết bị (QoS 1, có TTL)
→
Thiết bị thực thi
↓
Ack → cập nhật reported
Quá TTL vô ack → command hết hạn

Thiết bị online thì nhận delta ngay; thiết bị offline thì desired được giữ và gửi khi nó kết nối lại. Mỗi cập nhật shadow mang version để chống ghi đè ngược.

{
  "deviceId": "unit-8841",
  "state": {
    "desired":  { "mode": "AUTO", "targetLevel": 12, "fanSpeed": 3, "fwVersion": "2.4.1" },
    "reported": { "mode": "AUTO", "targetLevel": 12, "fanSpeed": 2, "rssi": -58,
                  "filterLifePct": 41, "fwVersion": "2.4.0" }
  },
  "metadata": {
    "desired":  { "fwVersion": { "ts": 1760581200, "version": 17 } },
    "reported": { "fwVersion": { "ts": 1760578000, "version": 12 } }
  },
  "version": 42,
  "timestamp": 1760581230
}
public void syncShadow(String deviceId) {
  Shadow shadow = shadowRepo.find(deviceId);
  Map<String, Object> delta = delta(shadow);   // desired != reported
  if (delta.isEmpty()) return;

  Command cmd = Command.builder()
      .deviceId(deviceId)
      .payload(delta)
      .ttl(Duration.ofMinutes(5))          // không treo vĩnh viễn
      .build();
  commandQueue.enqueue(cmd);   // QoS 1; chỉ xoá khỏi hàng đợi khi có ack
}
When

Dùng khi điều khiển thiết bị có trạng thái cần giữ (chế độ, mức cài đặt, lịch chạy) hoặc khi thiết bị có thể offline lâu. Versioning firmware cần khi triển khai OTA cho nhiều máy với nhóm rollout theo đợt.

When NOT

Không giả định desired sẽ thành reported ngay — luôn chờ ack. Không để command không TTL, nằm mãi trong hàng đợi rồi thực thi khi đã vô nghĩa. Không cho thiết bị ghi đè reported bằng dữ liệu cũ hơn version hiện tại. Không nhét toàn bộ telemetry vào shadow — shadow chỉ giữ trạng thái, không phải nơi lưu chuỗi thời gian.

Use case

Người dùng đặt thiết bị chạy chế độ tự động qua app trong lúc máy mất wifi: desired được ghi lại, khi máy kết nối trở lại sẽ nhận delta, thực thi, gửi reported và ack; app hiển thị trạng thái "đang chờ đồng bộ" cho tới lúc đó.

Pitfall / Interview trap

Bẫy: hai nguồn cùng ghi desired gây tranh chấp (app của khách với bản tin tự động) — cần quy tắc ưu tiên và version. Bẫy thứ hai: coi "đã gửi lệnh" là "đã thực thi" khiến UI báo sai trạng thái. Bẫy thứ ba: downgrade firmware ngoài ý muốn nếu không so sánh phiên bản trước khi rollout.

Nói trong 60 giây
  • Shadow = desired (ý muốn) + reported (thực tế) + metadata version.
  • Delta = desired trừ reported; đó là việc cần làm.
  • Command có TTL, chỉ xoá khi có ack từ thiết bị.
  • Thiết bị offline thì desired chờ, gửi khi kết nối lại.
  • Firmware versioning để rollout theo đợt và rollback được.

Q9 Dữ liệu chuỗi thời gian và vận hành IoT: lưu telemetry, retention/downsampling, cảnh báo ngưỡng và OTA an toàn?

What

Telemetry IoT là dữ liệu chuỗi thời gian ghi rất nhiều và đọc theo khoảng: lưu vào time-series store partition theo thời gian, downsample theo cửa sổ và đặt retention rõ ràng. Vận hành cần cảnh báo ngưỡng có khử rung, quản lý certificate cho từng thiết bị, và OTA cập nhật firmware có kiểm tra chữ ký cùng khả năng rollback.

Why

Một đội thiết bị gửi số liệu mỗi 30 giây sinh ra hàng tỷ điểm dữ liệu mỗi năm; giữ toàn bộ ở độ phân giải gốc là tốn kém vô ích vì dashboard chỉ cần trung bình theo phút. Ngược lại, cảnh báo cần dữ liệu gốc gần thời gian thực để bắt sự cố. Bảo mật thiết bị quan trọng vì thiết bị nằm ngoài vành đai mạng, và một bản OTA không kiểm tra chữ ký là lỗ hổng cho toàn bộ đội máy.

How
Thiết bị
→
Broker
→
Stream (Kafka)
↓ song song
TSDB raw (retention ngắn)
Rules engine → cảnh báo
Aggregate 5 phút (retention dài)

Ghi raw ngay để phục vụ cảnh báo; job định kỳ tổng hợp theo cửa sổ rồi xoá dữ liệu gốc quá hạn. Certificate mỗi thiết bị được cấp phát và thu hồi; bản OTA được ký, thiết bị xác minh chữ ký trước khi ghi và giữ phân vùng cũ để rollback.

-- Time-series: partition theo thời gian, nén sau, xoá theo retention
SELECT create_hypertable('telemetry', 'ts',
       chunk_time_interval => INTERVAL '1 day');
SELECT add_retention_policy('telemetry', INTERVAL '90 days');

-- Downsampling: giữ min/max/avg mỗi 5 phút cho dashboard & báo cáo
INSERT INTO telemetry_5m (device_id, bucket, avg_level, max_level, samples)
SELECT device_id,
       time_bucket(INTERVAL '5 minutes', ts) AS bucket,
       avg(level)  AS avg_level,
       max(level)  AS max_level,
       count(*)    AS samples
FROM telemetry
WHERE ts >= now() - INTERVAL '5 minutes'
GROUP BY device_id, bucket;
When

Dùng khi số điểm dữ liệu vượt khả năng của DB quan hệ thông thường, khi dashboard cần đọc theo khoảng thời gian, hoặc khi cảnh báo cần độ trễ khử rung. OTA an toàn bắt buộc với thiết bị đặt ở nơi khó tiếp cận vật lý.

When NOT

Không ghi mỗi điểm thành một dòng trong DB giao dịch dùng chung — sẽ làm chậm cả hệ thống. Không đặt retention vô hạn cho raw data. Không cảnh báo trên từng điểm đơn lẻ mà không khử rung — nhiễu cảm biến gây bão thông báo. Không phát OTA không ký, không chia đợt, không có rollback.

Use case

Nền tảng vận hành thiết bị làm sạch không khí: raw telemetry giữ 90 ngày để điều tra sự cố, bản tổng hợp 5 phút giữ 2 năm cho báo cáo; cảnh báo kích hoạt khi mức bụi mịn vượt ngưỡng trong 3 điểm liên tiếp; firmware cập nhật theo đợt 5% rồi mở rộng khi tỷ lệ lỗi thấp.

Pitfall / Interview trap

Bẫy: ghi raw và aggregate vào cùng một bảng làm truy vấn lẫn lộn. Bẫy thứ hai: cảnh báo theo ngưỡng tức thời khiến một điểm nhiễu đã bắn thông báo — cần trung bình theo cửa sổ hoặc số lần liên tiếp. Bẫy thứ ba: OTA cắt điện giữa lúc ghi làm hỏng máy — cần ghi vào phân vùng dự phòng, xác minh chữ ký và có cơ chế quay về bản cũ.

Nói trong 60 giây
  • Telemetry là time-series: partition theo thời gian, không nhét vào DB giao dịch.
  • Raw retention ngắn cho điều tra; aggregate 5 phút giữ lâu cho báo cáo.
  • Downsampling tự động, không giữ raw vô hạn.
  • Cảnh báo ngưỡng phải khử rung (trung bình/nhiều điểm liên tiếp).
  • Bảo mật: certificate mỗi thiết bị, OTA ký + xác minh + rollback.
