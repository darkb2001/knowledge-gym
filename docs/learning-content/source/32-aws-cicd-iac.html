Vòng đời deploy & CI trên AWS

AWS1 Ứng dụng chạy dev → staging → prod: làm sao build một lần rồi promote mà không rebuild?

What

Một vòng đời deploy chuẩn trên AWS tách rời ba thứ: build (tạo artifact), release (gắn artifact với cấu hình môi trường) và run (chạy ở từng môi trường). Artifact (image/zip) được build một lần ở CI rồi promote nguyên bản qua dev → staging → prod; cấu hình khác nhau giữa các môi trường (endpoint, secret, scale) được inject lúc deploy, không nhúng vào artifact.

How

Mỗi môi trường là một environment riêng với biến env / parameter riêng. Bất biến (immutable) hoá artifact bằng cách deploy theo image digest sha256 thay vì tag mutable như :latest. Cấu hình đọc từ SSM Parameter Store hoặc Secrets Manager theo tiền tố /order-api/<env>/….

CodeCommitmerge vào main
→trigger build
CodeBuildbuild 1 lần → image
→push
Amazon ECRdigest sha256 bất biến
→cùng digest
CodeDeploystaging → prod
When

Hệ thống nhiều môi trường, cần audit/rollback chính xác, nhiều team cùng release, yêu cầu "chạy đúng cái đã test ở staging".

When NOT

Prototype một môi trường duy nhất thì promote ít giá trị. Không nhúng secret của prod vào artifact. Không rebuild lại ở mỗi môi trường — dependency trôi version sẽ tạo lỗi "staging OK, prod chết".

# CI build MOT lan, lay digest bat bien
docker build -t $ECR_URI:$GIT_SHA .
docker push $ECR_URI:$GIT_SHA
DIGEST=$(aws ecr describe-images --repository-name order-api \
  --image-ids imageTag=$GIT_SHA \
  --query 'imageDetails[0].imageDigest' --output text)

# Promote CUNG artifact sang tung moi truong, chi doi config
aws ecs update-service --cluster staging --service order-api \
  --force-new-deployment --task-definition order-api-staging:12
aws ssm put-parameter --name /order-api/prod/IMAGE_DIGEST \
  --value "$DIGEST" --type String --overwrite
Bẫy thi / Pitfall

Dùng tag mutable (:latest, :prod) là mất khả năng truy vết — rollback không biết đang chạy code nào. Promote đúng nghĩa là deploy cùng digest, không phải build lại rồi gắn tag mới.

AWS2 CodeCommit & Git-based workflow + CodeBuild: buildspec.yml, env, cache, artifact

What

CodeCommit là Git repo managed (private, IAM-controlled). CodeBuild là CI managed chạy lệnh trong container theo file buildspec.yml. Kết hợp: push vào branch → CodeBuild kéo source → build/test → sinh artifact và report.

How

buildspec có các phase install → pre_build → build → post_build. Biến env lấy từ env.variables, parameter-store (SSM) hoặc secrets-manager. cache giảm thời gian build (Maven .m2, node_modules). artifacts là thứ chuyển cho bước deploy; reports đẩy JUnit result lên CodeBuild console.

AWS3 CodeDeploy: appspec.yml, deployment group, in-place vs blue/green, lifecycle hooks và rollback

What

CodeDeploy tự động deploy app lên EC2/On-Premises, Lambda hoặc ECS. Đơn vị cấu hình là application → deployment group (nhóm instance/target) → revision (bundle gồm code + appspec.yml). appspec.yml khai báo file cần copy và script chạy tại từng lifecycle hook.

How

Deploy EC2 in-place chạy hook theo thứ tự cố định; hook nào exit non-zero → deploy fail và dừng. Rollback: CodeDeploy tự deploy lại revision trước đó (khi bật auto-rollback) hoặc bạn chạy lại deploy revision cũ.

CodePipeline & CloudFormation

AWS4 CodePipeline: stage, action, luồng source→build→deploy và manual approval

What

CodePipeline là orchestrator: mỗi pipeline gồm nhiều stage, mỗi stage gồm nhiều action (song song hoặc tuần tự theo runOrder). Action có category (Source, Build, Test, Deploy, Approval, Invoke), owner (AWS, ThirdParty, Custom), provider và version. Artifact đi từ action này sang action khác qua S3 artifact bucket.

How

Stage chuyển tiếp qua transition; có thể disable transition hoặc chèn Manual Approval (Approval action của AWS). Approve qua console hoặc aws codepipeline put-approval-result. Stage fail → pipeline dừng, có thể retry stage.

AWS5 CloudFormation template anatomy + intrinsic functions (Ref / GetAtt / Sub / Join / Condition)

What

Template CloudFormation khai báo hạ tầng dạng declarative. Các section theo thứ tự: AWSTemplateFormatVersion, Description, Metadata, Parameters, Rules, Mappings, Conditions, Transform, Resources (bắt buộc), Outputs. Chỉ Resources là bắt buộc.

How

Giá trị động nối các phần bằng intrinsic function: Ref lấy tham số/tên logic, Fn::GetAtt lấy attribute của resource, Fn::Sub nội suy chuỗi, Fn::Join ghép mảng, Fn::If+Fn::Equals chọn theo điều kiện, Fn::FindInMap tra bảng, Fn::ImportValue lấy output từ stack khác.

When NOT

Không dùng Ref để lấy attribute (như ARN) — phải dùng GetAtt. Không hard-code giá trị môi trường; đưa vào Parameters/Mappings để tránh sửa template mỗi lần deploy.

Bẫy thi / Pitfall

Trong YAML có thể dùng short form !Ref, !GetAtt, !Sub; trong JSON phải viết đầy đủ {"Ref": ...}, {"Fn::GetAtt": [...]}. Trộn short form vào JSON sẽ lỗi cú pháp.

AWS6 CloudFormation nâng cao: nested stack, change set, drift, stack policy và lỗi DELETE_FAILED

What

Các tính năng vận hành: nested stack (AWS::CloudFormation::Stack, tái sử dụng template con), change set (xem trước thay đổi), drift detection (phát hiện tài nguyên bị sửa tay ngoài CFN), stack policy (chặn update/replace không mong muốn) và rollback (tự hoàn tác khi stack update fail).

How

Update luôn tạo change set trước để review. Khi update fail, CFN rollback về trạng thái trước (trừ khi bật preserve successfully provisioned resources). Resource bị sửa tay hiện ra ở tab Drift. Stack policy là JSON kiểm soát action Update:* trên resource.

When NOT

Không sửa resource tay sau khi tạo bằng CFN (drift, lần update sau sẽ ghi đè). Không xoá stack còn resource bị block — sẽ ra DELETE_FAILED, phải retain hoặc xoá thủ công resource rồi xoá lại.

Bẫy thi / Pitfall

DELETE_FAILED thường do S3 bucket không rỗng hoặc ENI/SecurityGroup còn phụ thuộc. Stack policy không bảo vệ khỏi xoá stack — chỉ chặn update.

AWS7 AWS SAM: Serverless application model, event source, policy template và sam build/deploy/local

What

AWS SAM là lớp viết tắt (transform AWS::Serverless-2016-10-31) trên CloudFormation để mô tả ứng dụng serverless. Resource chính: AWS::Serverless::Function, ::Api, ::HttpApi, ::SimpleTable, ::StateMachine, ::LayerVersion. Khi deploy, SAM transform thành CloudFormation "chuẩn" (bổ sung Role, Permission, Stage, Event mapping…).

How

Event source khai báo trigger (Api, S3, SQS, SNS, DynamoDB, Kinesis, Schedule, EventBridge) ngay trong Function — SAM tự sinh permission/role cần thiết. Phần Globals đặt default chung (runtime, timeout, memory). Policy có thể là managed policy, inline, hoặc policy template viết sẵn (ví dụ DynamoDBCrudPolicy).

AWS8 AWS CDK: construct / app / stack, synth ra CloudFormation, cdk diff/deploy và khi nào dùng thay SAM

What

AWS CDK định nghĩa hạ tầng bằng ngôn ngữ lập trình (TypeScript, Python, Java, Go, C#…). Ba khái niệm: App (gốc), Stack (đơn vị deploy, tương ứng 1 CloudFormation stack), Construct (khối tài nguyên tái sử dụng, phân tầng L1/L2/L3). CDK synth ra CloudFormation template rồi để CFN triển khai.

How

cdk synth sinh template trong cdk.out/; cdk diff so template với stack đang chạy; cdk deploy tạo change set và apply. L2 construct đã cấu hình sẵn default an toàn (ví dụ tạo role least-privilege, gateway endpoint) nên ít boilerplate hơn CFN/SAM.

import * as cdk from 'aws-cdk-lib';
import { Construct } from 'constructs';
import * as lambda from 'aws-cdk-lib/aws-lambda';

export class OrderApiStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    const fn = new lambda.Function(this, 'CreateOrder', {
      runtime: lambda.Runtime.NODEJS_20_X,
      handler: 'create.handler',
      code: lambda.Code.fromAsset('src'),
      timeout: cdk.Duration.seconds(10),
    });

    fn.addFunctionUrl({ authType: lambda.FunctionUrlAuthType.NONE });
  }
}

AWS9 Ứng dụng không được downtime khi release: chọn chiến lược deploy nào và vì sao?

What

Các chiến lược triển khai phổ biến: All-at-once (deploy hết cùng lúc), Rolling (thay dần từng đợt), Immutable / Blue-Green (môi trường mới hoàn toàn, chuyển traffic), Canary (phần nhỏ traffic ăn bản mới, rồi tăng dần) và Linear (tăng đều theo bậc thang). CodeDeploy/ECS dùng canary/linear/all-at-once để dịch traffic.

How

Blue/Green: dựng môi trường mới → test → chuyển 100% traffic → rollback bằng cách chuyển ngược. Canary/Linear: dịch theo bước (ví dụ 10% trong 5 phút) kèm alarm để tự rollback nếu metric xấu.

When NOT

Không canary khi chưa có observability (không có metric để phát hiện bản lỗi). Không blue/green nếu schema DB không tương thích ngược (cả hai version chạy song song).

Bẫy thi / Pitfall

Canary/Blue-Green dịch traffic theo tỉ lệ, không phải "một nửa instance". Session sticky và migration phá vỡ (rename/drop cột) là nguyên nhân downtime kinh điển dù chiến lược đúng.

  --stage-name DeployProd \
  --action-name ManualApproval \
  --result summary="Approved by on-call",status=Approved

# Kiem tra trang thai deploy / rollback
aws deploy get-deployment --deployment-id d-ABCDE1234 \
  --query 'deploymentInfo.status'   # SUCCEEDED | FAILED | ROLLED_BACK
Use case

Release giờ cao điểm: on-call nhận SNS, kiểm tra staging xanh, approve; canary 10% trong 5 phút — nếu 5XXErrorRate vượt ngưỡng, CodeDeploy tự rollback về bản trước.

When NOT

Không auto-approve mọi release ở prod (mất ý nghĩa gate). Không bỏ alarm — auto rollback vô nghĩa nếu không có tín hiệu lỗi để kích hoạt.

Bẫy thi / Pitfall

Manual approval action hết hạn sau 7 ngày mặc định. Auto-rollback chỉ hoạt động khi alarm ở trạng thái ALARM trong thời gian deployment đang chạy — alarm tạo sai ngưỡng sẽ rollback nhầm.
