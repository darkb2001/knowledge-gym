Module 39

Kiến trúc Module & OSGi

Chia hệ thống thành module có ranh giới rõ: JPMS, OSGi (bundle lifecycle, classloader, service), versioning package và cách ép luật phụ thuộc bằng test.

Module hoá & ranh giới code

Q1 Cohesion/coupling là gì và vì sao monolith vẫn cần module hoá?

What

Module là một đơn vị code có biên rõ ràng: nó lộ ra API tối thiểu và giấu phần còn lại. Cohesion đo mức các thành phần bên trong một module thuộc về nhau (càng cao càng tốt); coupling đo mức phụ thuộc giữa các module (càng thấp càng tốt). Module hoá là thiết kế biên sao cho cohesion cao bên trong và coupling thấp qua biên.

Why

Monolith là một đơn vị deploy nhưng chứa nhiều lý do thay đổi độc lập — đơn hàng, thanh toán, kho vận. Không có biên rõ ràng, mọi thay đổi lan ra toàn codebase, không thể test cục bộ, không ai dám xoá code vì không biết ai dùng, và khi cần tách service thì không biết cắt ở đâu. Module hoá giữ được lợi ích deploy đơn giản của monolith mà vẫn có ranh giới để kiểm soát thay đổi.

How

Xác định biên theo trục thay đổi (một module đổi vì một lý do) chứ không theo tầng kỹ thuật, sau đó bảo vệ biên bằng công cụ thay vì bằng quy ước miệng.

Nhận diện trục thay đổi
↓ nhóm code theo trục
Định nghĩa API công khai của module
Giấu implementation
↓ chuyển phụ thuộc sang API
Gate tự động trong CI (ArchUnit / Spring Modulith)
↓ phát hiện rò rỉ
Rò rỉ: shared entity, import chéo package
When

Áp dụng khi có từ 2 team trở lên cùng sửa một codebase, hoặc khi số package nội bộ bắt đầu lớn đến mức không ai nắm hết. Cũng dùng khi chuẩn bị tách microservice: module hoá trước là bước đệm rẻ hơn nhiều so với việc cắt thẳng service từ một đống code dính chùm.

When NOT

Script vài trăm dòng, prototype một người, hoặc codebase mà mọi thứ thực sự chỉ phục vụ một mục đích — chia module lúc này chỉ tạo ceremony. Đừng module hoá để rồi mỗi module phải import gần hết các module khác: đó là coupling chuyển từ trong package ra ngoài module, không giảm gì.

// RÒ RỈ: module orders import trực tiếp repository nội bộ của module inventory
package com.example.orders;
import com.example.inventory.internal.StockLevelRepository; // xuyên biên, không qua API
import com.example.billing.entity.InvoiceEntity;        // shared entity = leak

// SỬA: chỉ phụ thuộc API công khai; module kia tự đổi implementation
import com.example.inventory.api.StockQuery;
import com.example.billing.api.InvoiceSummary;
Use case

Một hệ đặt hàng-vận chuyển: tách module catalog, orders, shipping. Lúc đầu chỉ là package; sau một sprint, đổi giá chỉ còn sửa catalog vì mọi nơi đã đi qua API của nó.

Pitfall / Interview trap

Dấu hiệu module bị rò rỉ mà interviewer hay hỏi: shared entity (nhiều module cùng import một entity class), import chéo vào package internal, cyclic dependency giữa package, và module "util" chung phình dần vì bất cứ thứ gì không biết đặt đâu đều nhét vào đó. Package không phải module: nếu không có gate compile-time hay test tự động thì ranh giới chỉ là đồ trang trí.

Nói trong 60 giây
  • Cohesion cao bên trong, coupling thấp qua biên.
  • Monolith vẫn cần module hoá để giới hạn phạm vi thay đổi.
  • Biên phải có gate tự động, không chỉ quy ước.
  • Rò rỉ: shared entity, import chéo internal, cyclic.
  • Module hoá trước khi tách microservice.

Q2 Package-by-layer vs package-by-feature, và khi nào tách multi-module Maven/Gradle?

What

Package-by-layer nhóm code theo tầng kỹ thuật: controller, service, repository, entity. Package-by-feature nhóm theo năng lực nghiệp vụ: mỗi feature chứa trọn controller, service, repository, model của nó. Package-by-feature khớp với module hoá vì trục đổi thường là theo feature chứ không theo tầng.

Why

Với package-by-layer, một thay đổi nghiệp vụ phải chạm vào mọi tầng và mọi tầng đều phụ thuộc toàn bộ các tầng còn lại — không có ranh giới nghiệp vụ nào để bảo vệ, và bạn không thể extract một feature ra module riêng vì nó bị rải rác khắp nơi. Package-by-feature tạo biên tự nhiên, giúp việc tách module/service sau này gần như cơ học.

How

Bắt đầu bằng package-by-feature trong một Maven module, chỉ tách thành multi-module khi có nhu cầu thật (reuse, enforce compile-time, build song song).

monolith package-by-layer
↓ nhóm lại theo feature
package-by-feature (1 module)
↓ enforce + nhu cầu reuse/build
multi-module Maven/Gradle
↓ khi thực sự cần
ứng viên tách service

When

Chọn package-by-feature cho hầu hết ứng dụng nghiệp vụ. Tách thành multi-module Maven/Gradle khi: muốn chặn compile-time (module A không thể import module B nếu không khai dependency), cần build/release từng phần, có thư viện dùng chung cho nhiều app, hoặc team cần ranh giới cứng hơn package.

When NOT

Đừng tách multi-module ngay từ ngày đầu cho một app nhỏ — build chậm hơn về mặt cấu hình, version bump nhiều nơi, và refactor qua module đau hơn qua package. Cũng tránh "one class per module" và tránh tạo module common/shared chứa mọi thứ: nó biến thành nút thắt coupling cho toàn hệ.

<!-- pom.xml của module orders: chỉ khai dependency nó thật sự dùng -->
<dependency>
  <groupId>com.example</groupId>
  <artifactId>inventory-api</artifactId> <!-- API, không phải inventory-impl -->
  <version>1.4.0</version>
</dependency>
Use case

Tách module inventory-api (interface + DTO) khỏi inventory-impl. Module orders phụ thuộc inventory-api, nên không thể vô tình chạm vào entity hay repository nội bộ — compiler chặn ngay.

Pitfall / Interview trap

Tách multi-module mà module nào cũng depends on common và common lại depends ngược lên impl → cyclic giữa artifact, Maven build fail hoặc phải gộp lại. Một bẫy khác: coi "có nhiều module" là "đã module hoá tốt" — nếu module A import hết package public của module B thì coupling y như cũ, chỉ tốn thêm công build.

Nói trong 60 giây
  • Package-by-feature khớp trục thay đổi nghiệp vụ.
  • Package-by-layer không tạo biên bảo vệ được.
  • Multi-module để enforce compile-time + build/release riêng.
  • Chỉ tách khi có nhu cầu thật, không từ ngày đầu.
  • Tách API khỏi impl để chặn truy cập nội bộ.

Q3 JPMS: module-info.java, requires/exports/opens, jlink/jdeps và khi nào nên dùng?

What

JPMS (Java Platform Module System, Java 9+) là cơ chế module hoá ở cấp ngôn ngữ và runtime. Mỗi module khai báo trong module-info.java: module requires module nào, exports package nào ra ngoài, opens package nào cho reflection. Khác Maven module (chỉ là ranh giới build), JPMS enforce được ở compile-time và runtime classpath.

Why

Maven/Gradle module chỉ tách artifact — bạn vẫn có thể import bất cứ package public nào của dependency. JPMS chặn thật: package không exports thì bên ngoài không compile được, và ở runtime truy cập sâu vào module khác bị chặn bởi strong encapsulation. Đây cũng là cơ sở để jlink tạo runtime image gọn — chỉ đóng gói đúng những module thật sự cần.

How

Đặt module-info.java ở gốc source tree, khai báo quan hệ, rồi dùng jdeps để dò dependency và jlink để đóng runtime.

module-info.java
↓ jdeps phân tích
Phát hiện package rò / thiếu requires
↓ compile với module-path
Compile-time enforce exports
↓ jlink
Runtime image tối giản
DirectiveÝ nghĩa
requiresPhụ thuộc module khác lúc compile + runtime
requires transitiveAi đọc module này cũng thấy module kia (truyền API ra ngoài)
requires staticChỉ cần lúc compile, không bắt buộc lúc runtime
exportsCho phép bên ngoài truy cập package (compile + runtime)
opensChỉ mở cho reflection, không export type ở compile-time
When

Dùng khi cần application image nhỏ (CLI, tool, desktop, container tối giản), khi cần fail-fast strong encapsulation, hoặc khi viết thư viện muốn định nghĩa API bề mặt chính xác. opens ... to giới hạn đúng framework được reflection, rất hợp với các dependency injection container chạy trên module-path.

When NOT

Ứng dụng Spring Boot thông thường không cần JPMS: classpath mode chạy tốt hơn, và nhiều thư viện dùng reflection/unnamed module gây ma sát (cần opens khắp nơi, "automatic module" chỉ là module suy diễn từ jar name — dễ vỡ). Cũng đừng nhầm JPMS với OSGi: JPMS không có versioning của module, không có multi-version, không có lifecycle/hot-redeploy. Với splitting package, JPMS cấm hoàn toàn còn OSGi cho phép có kiểm soát.

@SuppressWarnings
module com.example.orders {
    requires java.sql;
    requires transitive com.example.common;   // API của mình lộ type của common
    requires static org.jetbrains.annotations; // chỉ lúc compile

    exports com.example.orders.api;            // công khai
    opens com.example.orders.internal to spring.core; // reflection có kiểm soát
}
# Dò dependency giữa các module/package
jdeps --multi-release 21 --module-path mods -s com.example.orders

# Tạo runtime image tối giản chỉ gồm module cần thiết
jlink --module-path "$JAVA_HOME/jmods:mods" --add-modules com.example.orders \
      --strip-debug --no-header-files --no-man-pages --output runtime-image
Use case

Một CLI tool dùng jlink giảm runtime từ hơn 200MB JDK xuống vài chục MB, và nhờ exports hẹp mà không ai vô tình phụ thuộc vào class nội bộ của package khác.

Pitfall / Interview trap

Nhầm exports với opens: exports cho truy cập type lúc compile, opens chỉ cho reflection lúc runtime (framework cần cái này). Bẫy thứ hai: JPMS không có khái niệm version trong requires — không thể yêu cầu "cần common từ 1.4 trở lên". Muốn version range, multi-version bundle hay thay đổi lúc runtime thì đó là địa hạt của OSGi, không phải JPMS.

Nói trong 60 giây
  • JPMS enforce ở compile-time và runtime.
  • requires / exports / opens khác nhau rõ ràng.
  • jdeps dò dependency, jlink đóng runtime gọn.
  • Không có versioning và lifecycle như OSGi.
  • Spring Boot thường chỉ cần classpath.

OSGi — bundle, classloader, service

Q4 OSGi là gì và bundle lifecycle hoạt động thế nào?

What

OSGi là một đặc tả (specification) framework cho phép module hoá động trên JVM: ứng dụng gồm nhiều bundle (một jar có Manifest đặc biệt), mỗi bundle có vòng đời riêng, classloader riêng, và version riêng. Bundle có thể được cài, khởi động, dừng, cập nhật ngay trong runtime mà không cần restart cả JVM.

Why

Với classpath truyền thống, mọi class nằm trên một không gian phẳng: không thể có hai version của cùng thư viện, không thể nạp lại code đã chạy, không thể biết chắc bundle nào đến từ đâu. OSGi giải quyết đúng ba vấn đề đó — versioning, isolation, dynamic lifecycle — nên rất phù hợp với thiết bị, gateway IoT, hệ điều hành nhúng và hệ thống chạy plugin cập nhật từ xa trong nhiều năm.

How

Lifecycle của một bundle đi qua các trạng thái cố định; chuyển trạng thái là do framework điều khiển, không phải code tự đặt cờ.

INSTALLED
↓ resolve (thoả mãn wiring import/export)
RESOLVED
↓ start()
STARTING
↓ BundleActivator.start() xong
ACTIVE
↓ stop()
STOPPING → RESOLVED
UNINSTALLED

Ngoài ra có LAZY_ACTIVATION: bundle ở trạng thái STARTING nhưng chờ class đầu tiên được nạp mới thực sự active — hữu ích để giảm thời gian khởi động trên thiết bị.

When

Dùng OSGi khi cần cập nhật một phần hệ thống lúc đang chạy mà không restart (firmware gateway, edge box ngoài hiện trường), khi nhiều plugin có thể đến từ bên thứ ba và phải cách ly lẫn nhau, hoặc khi nhiều thành phần cần chạy song song nhiều version thư viện khác nhau.

When NOT

Đừng chọn OSGi chỉ vì "nghe module hoá hơn JPMS". Chi phí thật: framework runtime, tooling phức tạp, debug classloader khó, team phải học manifest và service model, và các thư viện dùng classpath quen thuộc dễ vỡ khi vào bundle. Hệ thống 12-factor stateless, deploy bằng container thì restart nhanh, không cần hot-swap — dùng Spring Boot trên classpath hợp lý hơn nhiều.

// BundleActivator: hook duy nhất vào lifecycle kiểu cũ
public class Activator implements BundleActivator {
  public void start(BundleContext ctx) {
    // đăng ký service, mở tài nguyên
    ctx.registerService(SensorReader.class.getName(), new SensorReaderImpl(), null);
  }
  public void stop(BundleContext ctx) { // giải phóng tài nguyên, service tự bị gỡ }
}
Use case

Gateway công nghiệp chạy nhiều driver kết nối thiết bị: mỗi driver là một bundle. Khi cần thêm loại thiết bị mới hoặc vá lỗi driver, cài/update đúng bundle đó, các bundle khác và kết nối đang chạy vẫn tiếp tục.

Pitfall / Interview trap

Nhầm trạng thái RESOLVED — bundle đã resolve nhưng chưa chạy code, chỉ khi start() mới sang STARTING/ACTIVE. Cũng hay hỏi: "sao bundle cài rồi mà không chạy?" — thường do chưa resolve được (thiếu Import-Package) hoặc start-level thấp hơn mức đang active. Đừng quên UNINSTALLED là trạng thái cuối và không quay lại được.

Nói trong 60 giây
  • OSGi = module động trên JVM: version, isolation, lifecycle.
  • Lifecycle: INSTALLED → RESOLVED → STARTING → ACTIVE → STOPPING.
  • LAZY_ACTIVATION giảm thời gian khởi động.
  • Hợp thiết bị, IoT gateway, hệ plugin cập nhật runtime.
  • Chi phí tooling cao, không hợp app container hoá đơn giản.

Q5 Vì sao mỗi bundle có classloader riêng và hệ quả với static/singleton, ClassCastException?

What

Mỗi bundle trong OSGi được nạp bởi một bundle classloader riêng, thay vì classloader phẳng của classpath. Bundle classloader tự nạp class trong chính bundle mình, và chỉ uỷ quyền nạp class của package khác nếu manifest khai Import-Package (hoặc DynamicImport-Package). Không có import thì không thấy — dù class đó có tồn tại ở bundle bên cạnh.

Why

Đây chính là cơ chế tạo isolation và multi-version: hai bundle có thể cùng chứa package com.foo phiên bản khác nhau mà không đụng nhau, vì mỗi cái thấy bản của mình. Nhưng cũng vì thế, static/singleton chỉ có phạm vi trong một bundle: hai bundle nạp cùng một class com.foo.Counter sẽ giữ hai biến static riêng biệt, và đối tượng của chúng thuộc hai Class khác nhau dù tên giống hệt.

How

Wiring diễn ra lúc resolve: framework tìm bundle nào Export-Package khớp với Import-Package của bundle cần, rồi "nối" classloader hai bên.

Bundle A
Bundle B
↓ mỗi bundle có classloader riêng
ClassLoader A
ClassLoader B
↓ Import-Package khớp Export-Package
Wire: A thấy class của B
↓ nếu KHÔNG khai import
Không thấy class → NoClassDefFoundError

Hệ quả thực tế: state toàn cục, cache tĩnh, registry tự viết bằng static field đều bị "nhân bản" theo bundle. Đúng cách là trao đổi state qua service (một instance do một bundle đăng ký) chứ không qua static.

When

Hữu ích khi thật sự cần cô lập: plugin bên thứ ba không tin cậy, hai thư viện cần hai version, hoặc muốn thay nạp một phần code. Khi đó classloader riêng là công cụ đúng.

When NOT

Đừng dựa vào static làm state chia sẻ giữa các bundle — nó không chia sẻ gì cả. Cũng tránh DynamicImport-Package như cách chữa cháy cho mọi lỗi "không thấy class": nó phá tính xác định của wiring và che lỗi thiết kế manifest. Và nếu bạn chỉ muốn module hoá tĩnh thì classloader phẳng (hoặc JPMS) đơn giản hơn nhiều.

// Bundle A và bundle B cùng nạp com.foo.Shared → HAI class object khác nhau
Object o = serviceFromB.getShared();
// ClassCastException dù class name y hệt:
Shared s = (Shared) o; // ✗ "com.foo.Shared cannot be cast to com.foo.Shared"

// CÁCH ĐÚNG: chỉ bundle export package, các bundle khác import nó
// B export com.foo (version 1.0.0); A Import-Package: com.foo;version="[1.0,2)"
// → cả hai dùng CÙNG một Class object, cast thành công
Use case

Lỗi kinh điển: hai bundle cùng gói sẵn một thư viện JSON ở trong jar thay vì import package của nó. Kết quả là mỗi bên có classloader riêng cho thư viện đó, và framework báo ClassCastException cùng tên class — dấu hiệu gần như chắc chắn rằng package đang bị đóng gói trùng thay vì import.

Pitfall / Interview trap

Câu hỏi bẫy kinh điển: "Vì sao ClassCastException khi cả hai class cùng tên?" — vì identity của một class là cặp (tên đầy đủ, classloader), không chỉ tên. Cũng hỏi tiếp: "static trong OSGi ra sao?" — mỗi bundle một bản, singleton không xuyên bundle. Cách chữa đúng là export/import package, không phải reflection hay deserialize qua lại.

Nói trong 60 giây
  • Mỗi bundle một classloader, chỉ thấy class được import.
  • Isolation tạo multi-version nhưng nhân bản static/singleton.
  • Class identity = tên + classloader.
  • ClassCastException cùng tên = đóng gói trùng package.
  • Chữa đúng: export/import package, không dùng static chia sẻ.

Q6 OSGi services & Declarative Services: component, service registry, Config Admin, dependency động?

What

OSGi Services là cách các bundle hợp tác: một bundle đăng ký một object vào service registry theo tên interface, bundle khác lấy ra dùng — không cần biết nhau lúc compile. Declarative Services (DS) là mô hình khai báo cho việc này: bạn annotate một class (hoặc viết một file component XML) để framework tự tạo instance, tự inject service phụ thuộc và tự quản vòng đời của nó.

Why

Service registry giải quyết vấn đề "bundle A cần bundle B" mà không tạo wired cứng: B có thể được thay, được nâng cấp, hoặc biến mất lúc runtime. DS biến dependency động đó thành an toàn — khi service phụ thuộc không còn, component tự deactivate thay vì ném NullPointerException. Đây là thứ khiến OSGi khác hẳn module tĩnh.

How

DS quản lý component theo dependency: đủ service thì active, thiếu thì deactivate rồi chờ.

Service Registry (theo interface + version)

↓ B bị stop/gỡ service

When

Dùng DS cho hầu hết bundle cần trao đổi service (thay vì tự viết ServiceTracker hay BundleActivator — dễ rò service vì quên unregister). Config Admin dùng khi cấu hình phải đổi mà không build lại bundle: endpoint thiết bị, timeout, danh sách broker.

When NOT

Không lạm dụng dynamic reference mọi nơi: nhiều dependency động làm luồng khởi động và debug rối. Với service gần như luôn tồn tại (core nền tảng), khai mandatory rõ ràng rồi để bundle fail-fast nếu thiếu, thay vì cố sống chấp nhận trạng thái nửa vời. Cũng đừng dùng service registry làm message bus hay event bus — đó không phải mục đích của nó.

@Component(service = TelemetryPublisher.class)
public class TelemetryPublisherImpl implements TelemetryPublisher {

  @Reference                                // mandatory: không có thì component không active
  private SensorReader sensorReader;

  @Reference(cardinality = ReferenceCardinality.OPTIONAL)
  private MqttBroker broker;

  @Activate void start(Map<String, Object> config) {
    String topic = (String) config.getOrDefault("topic", "telemetry/default");
  }
  @Deactivate void stop() { // đóng kết nối; SensorReader có thể đã biến mất trước đó }
}
Use case

Driver thiết bị (SensorReader) đăng ký service; tầng publish telemetry tham chiếu nó. Khi driver được cập nhật ở runtime, service tạm rút — component publish tự deactivate rồi activate lại với instance mới, không cần restart gateway.

Pitfall / Interview trap

Hay bị hỏi: "Điều gì xảy ra khi service biến mất?" — với DS, component phụ thuộc tự @Deactivate, rồi @Activate lại khi service trở về; đó là lý do phải viết đúng cặp activate/deactivate và không giữ state giả định service luôn tồn tại. Bẫy thứ hai: tự đăng ký service bằng tay qua BundleContext rồi quên unregister → service leak khi bundle dừng, framework vẫn giữ reference cũ.

Nói trong 60 giây
  • Service registry: hợp tác theo interface, không wired cứng.
  • DS khai báo component, tự inject và quản lifecycle.
  • Service mất → @Deactivate, quay lại → @Activate.
  • Config Admin cho cấu hình đổi lúc runtime.
  • Đừng lạm dụng dynamic; core dependency để mandatory.

Q7 Versioning & Import/Export package: bundle A phụ thuộc B thì nâng cấp thế nào?

What

Trong OSGi, đơn vị version hoá là package, không phải cả jar. Mỗi package export được gắn một version theo semantic versioning major.minor.micro[.qualifier]; bundle import khai một version range. Framework chỉ resolve khi range của bên import giao với version export của bên kia.

Why

Versioning ở mức package cho phép nâng cấp cục bộ đúng nơi thay đổi: sửa implementation mà API không đổi thì bump micro, mọi consumer cũ vẫn resolve bình thường. Nếu version hoá ở mức cả jar, bất kỳ thay đổi nhỏ nào cũng buộc mọi thứ phải nhảy version cùng nhau — đúng cái đau đầu mà OSGi muốn tránh.

How

Quy tắc bump version và cách khai range quyết định việc nâng cấp có "êm" hay không.

Thay đổiBumpHệ quả với consumer
Sửa bug, không đổi signaturemicro (1.4.0 → 1.4.1)Range cũ vẫn khớp
Thêm method/class mới (backward compatible)minor (1.4 → 1.5)Range cũ vẫn khớp
Xoá/đổi signature, breaking changemajor (1.x → 2.0)Consumer phải mở rộng range
Bundle B export com.foo 1.4.0
↓
Bundle A Import-Package: com.foo;version="[1.4,2)"
↓ nâng B lên 1.5.0 (minor)

↓ nâng B lên 2.0.0 (major)
Resolve fail cho tới khi A mở rộng range

Nói cách khác: range do consumer khai, nên consumer là bên quyết định mình sẵn sàng nhận tới mức nào. Nhà cung cấp chỉ cam kết bằng cách bump đúng theo semver.

When

Khai range rõ ràng luôn luôn cho mọi Import-Package: để trống version nghĩa là chấp nhận mọi version, kể cả 2.0 breaking — nguy hiểm. Dùng range hẹp ([1.4,1.5)) khi API còn non và bạn muốn kiểm soát chặt.

When NOT

Đừng khai range quá rộng cho tiện (ví dụ [1,3) cho mọi thứ) — bạn nhận breaking change mà không hay. Cũng đừng bump major vì lý do nội bộ không ảnh hưởng API: bump major vô cớ đẩy hàng loạt consumer vào trạng thái không resolve được. Và khi nhiều provider cùng export một package (split package hoặc trùng), wiring trở nên khó đoán — nên giữ một nguồn export duy nhất cho mỗi package.

# Manifest của bundle B (provider)
Export-Package: com.foo.api;version="1.5.0", com.foo.spi;version="1.5.0"

# Manifest của bundle A (consumer)
Import-Package: com.foo.api;version="[1.4,2)", com.foo.spi;version="[1.4,2)"

# Kiểm tra wiring resolve được không (Bnd / bndtools)
bnd print --verify bundle-A.jar
Use case

Bundle B được vá lỗi và nâng 1.4.0 → 1.4.1. Các bundle A, C, D đang khai [1.4,2) resolve lại ngay, không cần build lại — một lợi ích trực tiếp của việc version hoá theo package thay vì theo jar.

Pitfall / Interview trap

Bẫy hay gặp: bỏ version trong Import-Package — bundle "chạy được" ở dev nhưng có thể resolve nhầm một major version khác trong production. Bẫy thứ hai là split package: hai bundle cùng export một package làm wiring phụ thuộc thứ tự, hành vi không xác định — OSGi cho phép điều này (khác JPMS cấm hẳn) nhưng nên tránh. "Uses constraint" cũng là chủ đề hay bị hỏi: nó lan version của package bị một export dùng gián tiếp, nên một số breakage không nằm ở package bạn import trực tiếp.

Nói trong 60 giây
  • Version hoá theo package, không theo jar.
  • Semver: micro/minor/patch không phá, major phá.
  • Consumer khai version range trong Import-Package.
  • Range khớp thì nâng cấp êm, không build lại.
  • Major bump bắt buộc consumer cập nhật.

Q8 Enforce ranh giới module: Spring Modulith + ArchUnit trong CI thế nào?

What

Spring Modulith là bộ hỗ trợ module hoá ứng dụng Spring: mỗi package cấp dưới gốc là một module, chỉ package gốc của module được coi là API công khai, và các module giao tiếp qua event. ArchUnit là thư viện test kiến trúc: bạn viết luật phụ thuộc bằng code Java và chạy như unit test — phụ thuộc sai làm test đỏ.

Why

Ranh giới module chỉ có giá trị khi bị thi hành tự động. Nếu chỉ là tài liệu hay quy ước, sau vài sprint ai cũng import chéo cho nhanh. Đưa luật vào CI biến "đừng phụ thuộc sai" thành một build gate: PR vi phạm bị chặn ngay, chi phí sửa luôn thấp vì sai mới sinh ra chứ chưa kịp nhân rộng.

How

Kiểm ở hai lớp: Modulith verify cấu trúc/event, ArchUnit kiểm luật phụ thuộc chi tiết hơn.

Viết module theo package
↓

↓ chạy như test
CI gate: build đỏ nếu vi phạm
↓ phát hiện sớm
Dependency cycle → refactor ngay

When

Dùng ngay khi dự án có hơn vài module nghiệp vụ và nhiều người cùng commit. ArchUnit đặc biệt hợp khi muốn giữ luật cụ thể: "controller không được import repository", "domain không được phụ thuộc framework". Spring Modulith hợp khi muốn giao tiếp giữa module theo event và có tài liệu kiến trúc tự sinh.

When NOT

Đừng viết 50 luật ArchUnit từ ngày đầu — đội sẽ tắt test vì "vỡ lung tung". Bắt đầu với vài luật then chốt (không cycle, không chạm internal, không phụ thuộc chéo tầng), rồi tăng dần. Cũng đừng ép event-based giữa module khi một lời gọi đồng bộ đơn giản là đủ: event thêm eventual consistency, tracing và độ phức tạp debug — chỉ dùng khi thật cần decouple.

// Spring Modulith: verify ranh giới module trong test
class ModularityTests {
  @Test void verifyModules() {
    ApplicationModules modules = ApplicationModules.of(ShopApplication.class);
    modules.verify();                      // không cycle, boundary đúng
    modules.document(Documenter.Canvas.C4);   // sinh tài liệu kiến trúc
  }
}

// ArchUnit: domain không được phụ thuộc framework
@Test void domainHasNoFrameworkDependency() {
  noClasses().that().resideInAPackage("..domain..")
    .should().dependOnClassesThat()
    .resideInAnyPackage("org.springframework..")
    .check(new ClassFileImporter().importPackages("com.example"));
}
Use case

Cửa hàng đang refactor hoá đơn: ArchUnit chặn một PR vô tình cho package orders import repository nội bộ của inventory. Build đỏ ngay trong CI, tác giả sửa sang gọi API của inventory — chưa kịp hình thành thói quen xấu.

Pitfall / Interview trap

Nhầm Spring Modulith là framework mới thay Spring Boot: nó là bổ trợ, chạy trên app Spring Boot sẵn có. Bẫy thứ hai: đặt ArchUnit test ở module không được chạy trong pipeline (bị exclude khỏi mvn test/gradle check) → luật tồn tại mà không bao giờ thi hành. Luôn kiểm rằng gate chạy trong CI thật, không chỉ trên máy dev.

Nói trong 60 giây
  • Ranh giới chỉ đáng tin khi có gate tự động.
  • Spring Modulith: verify + tài liệu kiến trúc.
  • ArchUnit: luật phụ thuộc dạng code test.
  • Bắt đầu vài luật then chốt, tăng dần.
  • Đảm bảo test chạy trong CI, không chỉ máy dev.

Q9 Kiến trúc plugin/extension: SPI + ServiceLoader, extension point, khi nào KHÔNG nên chọn OSGi?

What

Kiến trúc plugin cho phép mở rộng hệ thống mà không sửa core: core định nghĩa extension point (interface), plugin hiện thực nó. Cách nhẹ nhất trên JVM là SPI + ServiceLoader: plugin khai implementation trong META-INF/services/<interface>, core nạp chúng lúc chạy. Bản "nặng" hơn là OSGi, thêm isolation và hot-swap nhưng kèm chi phí lớn.

Why

Hai lựa chọn này khác nhau ở mức cô lập và động. ServiceLoader chạy trên classpath phẳng: đơn giản, không cần runtime đặc biệt, nhưng mọi plugin ở cùng một classloader — không có multi-version, không update lúc đang chạy, một plugin lỗi có thể ảnh hưởng cả tiến trình. OSGi cho isolation và hot-swap thật, đổi lại là toàn bộ chi phí vận hành kèm theo.

How

Nguyên tắc chọn: đi từ nhẹ tới nặng, chỉ leo thang khi nhu cầu thực sự bắt buộc phiên bản nhẹ không đáp ứng được.

When

Chọn SPI/ServiceLoader khi plugin tin cậy, ít, và cập nhật cùng nhịp deploy — ví dụ nhiều implementation của một interface, driver nội bộ, hoặc mở rộng build-time. Chọn OSGi khi thật sự cần: plugin bên thứ ba không tin cậy, phải cập nhật từng phần lúc đang chạy trên thiết bị không thể restart, hoặc cần nhiều version thư viện cùng tồn tại.

When NOT

Không chọn OSGi khi: hệ thống deploy theo container và restart nhanh là chuyện bình thường; team chưa có người từng vận hành OSGi; plugin tin cậy, nội bộ; hoặc vấn đề thật chỉ là "muốn decouple code". Những trường hợp đó, Spring Boot trên classpath với interface rõ ràng tiết kiệm hàng tháng công sức. Đường chuyển từ OSGi sang Spring Boot: bỏ Manifest và service registry, thay @Reference bằng injection của DI container, thay activation bằng bean lifecycle, gộp bundle boundary thành module/package boundary, và chấp nhận restart thay vì hot-swap — isolation giảm nhưng độ phức tạp vận hành cũng giảm mạnh.

// Extension point do core định nghĩa
public interface PaymentProvider {
  String id();
  PaymentResult charge(PaymentRequest req);
}

// Plugin khai trong META-INF/services/com.example.PaymentProvider
// com.acme.StripeProvider

// Core nạp plugin, không biết class cụ thể
ServiceLoader<PaymentProvider> loader = ServiceLoader.load(PaymentProvider.class);
for (PaymentProvider p : loader) {
  if (p.id().equals(requestedId)) return p.charge(req);
}
Use case

Nền tảng thanh toán nội bộ có 4 cổng nội bộ, cập nhật cùng lúc deploy app: ServiceLoader đủ dùng, không cần OSGi. Ngược lại, hộp gateway ngoài hiện trường thêm driver thiết bị mới mà không được phép ngắt kết nối — đó mới là ca cần hot-swap.

Pitfall / Interview trap

Bẫy hay gặp: chọn OSGi cho một app web stateless — trả giá toàn bộ phức tạp để đổi lấy khả năng gần như không bao giờ dùng. Bẫy ngược lại: dùng ServiceLoader nhưng kỳ vọng nó cô lập plugin — nó không, mọi plugin chung classloader nên xung đột version vẫn xảy ra. Cần ghi nhớ: OSGi giải quyết isolation/version/hot-swap, không phải "decouple cho đẹp".

Nói trong 60 giây
  • Extension point + plugin qua SPI/ServiceLoader là nhẹ nhất.
  • ServiceLoader không cô lập, không hot-swap.
  • OSGi có isolation, multi-version, update runtime.
  • Đi từ nhẹ tới nặng, chỉ leo khi thật cần.
  • Chuyển sang Spring Boot: bỏ manifest/registry, dùng DI.

OSGi dependency động: static/dynamic reference và classloader không phải sandbox

What

OSGi bundle wiring giải quyết package visibility/version, còn Declarative Services quản service dependency với cardinality và policy cụ thể. Mất service không phải lúc nào cũng deactivate component; classloader isolation cũng không phải security sandbox cho plugin không tin cậy.

How / Trade-offs / Pitfalls
  • Đính chính cách nói tuyệt đối ở card DS: mandatory reference không thỏa mãn khiến component không thể active/tiếp tục satisfied. Nhưng với dynamic policy có replacement phù hợp, SCR có thể bind/unbind mà không deactivate; optional dynamic reference có thể mất service mà component vẫn active. Static policy có vòng reactivation khi wiring cần đổi tùy policy option và replacement.
  • @Reference mặc định mandatory unary và static policy. Cần nêu cardinality (0..1, 1..1, 0..n, 1..n), static/dynamic và reluctant/greedy; không giữ service reference vĩnh viễn khi runtime thay đổi. Dynamic field thường dùng volatile hoặc cơ chế bind/unbind đúng spec, code phải chịu được service rút giữa các thao tác.
  • Bundle state ACTIVE không đồng nghĩa mọi DS component đã active: có thể unsatisfied reference/configuration; delayed component cũng chưa instantiate cho tới khi được yêu cầu. Debug manifest import/export và version range/uses constraint trước, rồi component satisfied/config và service ranking; không chữa mọi lỗi bằng DynamicImport-Package:*.
  • Class identity là tên đầy đủ + defining classloader. Static state chia theo class thực được define, không luôn “mỗi bundle một bản”: nhiều bundle import cùng API class từ exporter sẽ dùng cùng Class. Split copies mới sinh cast lỗi cùng tên. Update bundle có thể cần refresh dependent wiring; không hứa mọi dependent chuyển version tức thì.
  • Isolation classloader không ngăn malicious code truy cập filesystem/network hoặc gọi System.exit theo quyền process. Plugin không tin cậy cần process/container isolation, permission design và supply-chain controls. OSGi không thay sandbox.
