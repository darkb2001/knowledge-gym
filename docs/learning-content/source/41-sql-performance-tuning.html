Module 41

SQL Performance Tuning & Oracle/PostgreSQL

Tối ưu truy vấn thực chiến: đọc execution plan, chọn index, chiến lược join, N+1, thống kê & bảo trì, phân trang keyset và khác biệt khi viết SQL cho Oracle vs PostgreSQL.

Đọc Execution Plan & Index

Q1 Đọc execution plan: PostgreSQL EXPLAIN (ANALYZE, BUFFERS) vs Oracle EXPLAIN PLAN?

What

Đọc execution plan là bước bắt buộc trước khi tối ưu. PostgreSQL dùng EXPLAIN (ANALYZE, BUFFERS) để chạy thật và trả về thời gian + bộ đệm; Oracle dùng EXPLAIN PLAN FOR rồi DBMS_XPLAN.DISPLAY. Bốn con số phải nhìn trước: rows (ước lượng), cost, actual time và loops.

Why

Không đọc plan thì mọi "tối ưu" chỉ là đoán. Plan cho biết optimizer chọn Seq Scan hay Index Scan, Join nào, và — quan trọng nhất — chỗ nào estimate lệch xa actual. Một bảng ước lượng rows=6 nhưng actual rows=650000 nghĩa là statistics sai, planner chọn nested loop cho 650k dòng và query sập.

How
SQL + EXPLAIN (ANALYZE)
↓ parser → rewrite → planner
Planner ước lượng rows/cost từ statistics
↓ executor chạy thật
Đọc từ trong ra ngoài (inner node trước)
So actual vs estimate

Đọc plan từ node lá (inner) ra node gốc: mỗi node có cost=start..total (đơn vị tương đối), rows ước lượng, width byte một row. Với ANALYZE thêm actual time=startup..total, rows thật và loops — tổng rows thật = rows × loops. BUFFERS cho biết shared hit (đọc từ RAM) vs read (đọc từ disk); nhiều read = thiếu cache.

When

Dùng ngay khi có query chậm, trước và sau khi tạo index để so sánh. Trên production dùng EXPLAIN (ANALYZE, BUFFERS) cẩn thận vì nó chạy thật — query ghi (INSERT/UPDATE/DELETE) sẽ thay đổi dữ liệu, luôn bọc trong BEGIN; ... ROLLBACK;. Oracle EXPLAIN PLAN FOR không chạy query, muốn số thật dùng DBMS_XPLAN.DISPLAY_CURSOR sau khi chạy.

When NOT

Đừng tin cost giữa hai database khác nhau — nó là đơn vị nội bộ, không so được giữa PostgreSQL và Oracle. Đừng đọc plan mà bỏ qua loops — nested loop có actual time nhỏ nhưng nhân với 10.000 loops mới là chỗ chậm. Đừng tối ưu trên bảng dev 1.000 dòng rồi áp lên production 50 triệu dòng: planner chọn plan khác hẳn.

-- PostgreSQL: plan thật + thời gian + buffer
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.total
FROM orders o
WHERE o.customer_id = 42 AND o.status = 'PAID';

-- Kết quả rút gọn:
-- Index Scan using idx_orders_customer on orders
--   (cost=0.43..12.55 rows=8 width=24)
--   (actual time=0.031..0.052 rows=6 loops=1)   ← estimate 8 vs actual 6: tốt
--   Buffers: shared hit=11
-- Planning Time: 0.180 ms   Execution Time: 0.091 ms

-- Oracle: plan (không chạy query)
EXPLAIN PLAN FOR
SELECT o.id, o.total FROM orders o
WHERE o.customer_id = 42 AND o.status = 'PAID';
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);

-- | Id | Operation                    | Name                | Rows | Cost |
-- |  0 | SELECT STATEMENT             |                     |    6 |    3 |
-- |  1 |  TABLE ACCESS BY INDEX ROWID | ORDERS              |    6 |    3 |
-- |* 2 |   INDEX RANGE SCAN           | IDX_ORDERS_CUSTOMER |    6 |    1 |
Use case

API danh sách order chậm 2.1 s: chạy EXPLAIN (ANALYZE, BUFFERS) thấy Seq Scan on orders (rows=650000) dù WHERE có customer_id — index bị thiếu, tạo index xong query còn 1.2 ms.

Pitfall / Interview trap

estimate lệch actual là tín hiệu số 1 cần soi, không phải chuyện nhỏ. rows × loops mới là số dòng thật của node con. Và EXPLAIN ANALYZE trên query ghi sẽ ghi thật nếu không rollback.

Nói trong 60 giây
  • PG: EXPLAIN (ANALYZE, BUFFERS); Oracle: EXPLAIN PLAN + DBMS_XPLAN.
  • Bốn số: rows, cost, actual time, loops.
  • Đọc plan từ inner node ra ngoài.
  • Estimate lệch actual = statistics sai / index thiếu.
  • Cost không so được giữa hai engine.

Q2 Index B-tree hoạt động thế nào, selectivity/cardinality là gì, khi nào planner bỏ index?

What

B-tree index là cây cân bằng N-ary: node gốc và node nhánh chứa key dẫn hướng, node lá chứa key đã sort cùng con trỏ tới row (ctid trong PostgreSQL, ROWID trong Oracle). Tìm kiếm O(log n). Cardinality = số giá trị phân biệt của cột; selectivity = tỉ lệ row mà điều kiện lọc ra — index chỉ hữu ích khi selectivity đủ cao.

Why

Index không miễn phí: mỗi INSERT/UPDATE phải cập nhật cây, và index scan còn phải đọc heap để lấy row thật. Khi một điều kiện khớp gần nửa bảng, planner tính ra đọc cả index rồi nhảy heap đắt hơn đọc tuần tự toàn bảng — nên nó bỏ index. Hiểu điều này giải thích tại sao "tạo index rồi mà vẫn Seq Scan".

How
Root
↓ so sánh key
Branch [1..500]
Branch [501..1000]
↓ 1 lần nữa
Leaf: (key, row pointer) đã sort

Một truy vấn 1 tỉ dòng chỉ đi qua ~3–4 node. Ba trường hợp planner bỏ index phổ biến: (1) bảng quá nhỏ — Seq Scan rẻ hơn; (2) điều kiện khớp tỉ lệ lớn (selectivity thấp, ví dụ status chỉ 3 giá trị); (3) biểu thức bọc quanh cột khiến index không dùng được, và kiểu dữ liệu không khớp gây ép kiểu ngầm. Sửa bằng cách viết lại điều kiện cho "sạch" (để cột trần bên trái phép so sánh) hoặc tạo expression index.

When

Tạo B-tree cho cột xuất hiện trong WHERE đẳng thức, ORDER BY, JOIN key, và có cardinality cao (email, order_id, created_at). Với cột low-cardinality kết hợp, dùng composite index hoặc partial index thay vì index đơn. Khi điều kiện là biểu thức cố định, dùng expression index.

When NOT

Đừng index mọi cột — mỗi index làm chậm ghi và phình dung lượng. Đừng kỳ vọng index cho LIKE '%abc%' (leading wildcard) — cần trigram/full-text. Đừng quên kiểu dữ liệu không khớp: so sánh varchar với integer buộc ép kiểu, index trên cột bị vô hiệu.

-- status chỉ 3 giá trị trên 2.000.000 rows → selectivity rất thấp
CREATE INDEX idx_orders_status ON orders (status);

EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'NEW';
-- Seq Scan on orders (rows=650000)  ← planner bỏ index: khớp ~1/3 bảng

-- Hàm bọc quanh cột → index vô dụng
SELECT * FROM orders WHERE EXTRACT(YEAR FROM created_at) = 2026;  -- Seq Scan
SELECT * FROM orders
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';  -- Index Scan

-- Kiểu không khớp → ép kiểu ngầm, mất index
-- WHERE account_no = 12345   (account_no là varchar)  → account_no = '12345'

-- Expression index nếu buộc phải dùng biểu thức
CREATE INDEX idx_orders_yy ON orders ((EXTRACT(YEAR FROM created_at)));
Use case

Truy vấn tìm đơn theo email khách hàng: idx_customers_email cardinality ~1 (gần như unique) → Index Scan đọc đúng 1 row. Ngược lại index trên is_deleted boolean gần như luôn bị planner bỏ.

Pitfall / Interview trap

"Cứ tạo index là nhanh" — SAI: index low-cardinality và bảng nhỏ thường bị bỏ. "Hàm trên cột vẫn dùng index được" — SAI, trừ khi có expression index. Câu hỏi "khi nào planner bỏ index?" gần như luôn được hỏi — trả lời đủ 3 nhóm lý do.

Nói trong 60 giây
  • B-tree: cây cân bằng, leaf chứa (key, row pointer), O(log n).
  • Cardinality = số giá trị phân biệt; selectivity = tỉ lệ row khớp.
  • Planner bỏ index khi: bảng nhỏ, selectivity thấp, hàm/ép kiểu trên cột.
  • Index có chi phí: ghi chậm, tốn dung lượng.
  • Sửa: viết điều kiện sạch, composite/partial/expression index.

Composite, Covering & Join

Q3 Composite index: thứ tự cột, left-most prefix, và index cho ORDER BY/GROUP BY?

What

Composite index là index trên nhiều cột theo một thứ tự xác định, ví dụ (tenant_id, status, created_at). Nó giống như danh bạ in theo họ → tên → năm sinh: chỉ tra được nếu bạn biết phần ngoài cùng bên trái. Đó là nguyên tắc left-most prefix — query phải dùng được tiền tố liên tục từ cột đầu tiên.

Why

Cùng một tập cột, chỉ đổi thứ tự đã tạo ra index dùng được hoặc vô dụng. Đặt sai thứ tự là lỗi cực phổ biến: index (status, created_at) không phục vụ WHERE created_at > ..., và (created_at, status) lại không phục vụ WHERE status = .... Ngoài ra composite index còn có thể cung cấp sẵn thứ tự sort, giúp bỏ hẳn bước Sort trong plan.

How
Index (tenant_id, status, created_at)
↓ WHERE tenant_id = ? ✓ dùng được
tenant_id + status ✓
tenant_id + status + range created_at ✓
↓ nhảy cột
status = ? (thiếu cột trái nhất) ✗
created_at range (nhảy cột) ✗

Quy tắc đặt cột: cột cho đẳng thức (=) đặt trước, cột cho range (>, <, BETWEEN) đặt sau — vì sau một range, các cột tiếp theo không còn dùng để seek được nữa. Với ORDER BY/GROUP BY, thứ tự cột trong index nên khớp thứ tự sort (đổi chiều bằng DESC/NULLS LAST nếu cần) để planner đọc leaf theo thứ tự sẵn có thay vì thêm node Sort.

When

Dùng khi query có bộ lọc cố định nhiều cột (multi-tenant: luôn tenant_id + status), khi cần vừa filter vừa sort, hoặc khi join theo cặp khóa. Ví dụ index (tenant_id, status, created_at DESC) phục vụ "20 đơn PENDING mới nhất của tenant" bằng một lần index scan, không cần sort.

When NOT

Đừng tạo nhiều composite index na ná nhau — chi phí ghi nhân lên. Đừng đặt cột range lên trước cột đẳng thức. Đừng quên index (a, b) đã phục vụ được truy vấn chỉ cần a — không cần tạo thêm index đơn trên a.

CREATE INDEX idx_orders_cust ON orders (customer_id, status, created_at);

-- DÙNG ĐƯỢC (prefix liên tục)
-- WHERE customer_id = 42
-- WHERE customer_id = 42 AND status = 'PAID'
-- WHERE customer_id = 42 AND status = 'PAID' AND created_at > '2026-01-01'
SELECT * FROM orders
WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 20;
-- Index Scan, KHÔNG có node Sort — index đã cho sẵn thứ tự

-- KHÔNG dùng được
-- WHERE status = 'PAID'                 ← thiếu cột trái nhất customer_id
-- WHERE created_at > ...                ← nhảy cột giữa

-- Equality trước, range sau — pattern tối ưu cho event log
CREATE INDEX idx_events ON events (tenant_id, type, occurred_at);
-- WHERE tenant_id=? AND type=? AND occurred_at BETWEEN ? AND ?  ← seek hoàn hảo

-- Phục vụ GROUP BY khi thứ tự cột khớp
EXPLAIN (ANALYZE) SELECT customer_id, status, COUNT(*)
FROM orders GROUP BY customer_id, status;
-- GroupAggregate trên index (không Sort) thay vì HashAggregate + Sort
Use case

Trang "đơn của tôi" sắp theo mới nhất: index (customer_id, created_at DESC) biến truy vấn thành một index scan lấy thẳng 20 row đầu, không đọc bảng rồi sort.

Pitfall / Interview trap

Nhớ kỹ: left-most prefix, và range sau equality. Bẫy kinh điển: tạo index (a, b) rồi hỏi tại sao query trên b vẫn chậm. Cũng đừng quên index (a, b) thay thế được index (a).

Nói trong 60 giây
  • Composite index dùng được theo left-most prefix liên tục.
  • Equality trước, range sau.
  • Thứ tự cột khớp ORDER BY/GROUP BY thì bỏ được Sort.
  • Index (a,b) phục vụ cả truy vấn chỉ cần a.
  • Đặt sai thứ tự = index vô dụng, lỗi hay gặp.

Q4 Covering index / index-only scan, INCLUDE trong PostgreSQL — khi nào nên thêm cột?

What

Covering index là index chứa đủ mọi cột mà query cần, nên engine trả lời được chỉ từ index mà không phải đọc bảng — gọi là index-only scan. PostgreSQL dùng mệnh đề INCLUDE (...) để nhét thêm cột "chở theo" vào leaf mà không tham gia vào việc sắp xếp/seek của index.

Why

Index scan thường tốn kém ở bước nhảy vào heap lấy row thật: mỗi row một lần đọc random, hàng trăm nghìn lần là thảm hoạ. Nếu mọi cột SELECT đã nằm sẵn trong index, PostgreSQL trả luôn từ leaf — bỏ được bước heap đó. Nhưng index-only scan phải chờ VACUUM: chỉ những page đã được đánh dấu all-visible mới đọc thẳng, còn lại vẫn phải Heap Fetches.

How
Query: WHERE customer_id=? AND status=? → total, created_at
↓ index chứa cột filter
Index Scan → từng row nhảy heap lấy total
Chậm nếu nhiều row
↓ thêm INCLUDE (total, created_at)
Index Only Scan, Heap Fetches: 0

Đặt cột dùng để seek/sort/filter ở phần key của index (trước INCLUDE), còn cột chỉ để SELECT đặt trong INCLUDE. Cách này giữ được tiền tố index gọn và vẫn tránh đọc heap. Chạy VACUUM ANALYZE trước để đảm bảo Heap Fetches về 0 — nếu còn heap fetch, covering index chưa phát huy tác dụng.

When

Dùng cho truy vấn hot path, chạy liên tục, chọn rất ít cột (danh sách id + vài trường hiển thị), khi thấy plan có Index Scan với nhiều heap fetch chậm. Ví dụ list "20 order id + total mới nhất" — covering index biến thành index-only scan.

When NOT

Đừng nhét nhiều cột rộng (text, jsonb) vào INCLUDE — index phình ra, ghi chậm, có khi lớn bằng bảng. Đừng làm covering index cho truy vấn SELECT * (không bao giờ cover được hết) hay cho query ít gọi. Và đừng quên VACUUM — nếu bảng vừa update nhiều, index-only scan vẫn phải đọc heap.

-- Index thường: seek được nhưng vẫn phải đọc heap lấy total
CREATE INDEX idx_orders_plain ON orders (customer_id, status);

-- Covering: thêm cột chỉ-để-SELECT vào INCLUDE
CREATE INDEX idx_orders_cover ON orders (customer_id, status)
  INCLUDE (total, created_at);

VACUUM ANALYZE orders;   -- để page được đánh dấu all-visible

EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, status, total
FROM orders
WHERE customer_id = 42 AND status = 'PAID';

-- Kết quả mong đợi:
-- Index Only Scan using idx_orders_cover on orders
--   Heap Fetches: 0      ← 0 nghĩa là covering index đã hoạt động

-- Oracle tương đương: index có cột include (index-organized covering)
-- CREATE INDEX idx_orders_cover ON orders (customer_id, status, total)
-- hoặc Oracle 12c+: CREATE INDEX ... ON orders (customer_id, status) INCLUDE (total)
Use case

Màn hình dashboard poll mỗi 2 giây: SELECT id, total FROM orders WHERE customer_id=? AND status='PAID'. Covering index khiến truy vấn không đụng heap, giảm tải I/O rõ rệt.

Pitfall / Interview trap

Tạo covering index rồi quên VACUUM → plan vẫn Index Scan với Heap Fetches cao, tưởng không hiệu quả. Và SELECT * không bao giờ được cover — chỉ cover khi danh sách cột cố định và hẹp.

Nói trong 60 giây
  • Covering index = index chứa đủ cột query cần → index-only scan.
  • INCLUDE chở cột phụ, không tham gia seek/sort.
  • Lợi: bỏ heap fetch random, giảm I/O.
  • Cần VACUUM để Heap Fetches về 0.
  • Không dùng cho SELECT * hay cột rộng.

Q5 Join strategies: nested loop vs hash join vs merge join — planner chọn thế nào?

What

Có ba chiến lược join chính. Nested Loop — với mỗi row bảng ngoài, tra một lần vào bảng trong (rất tốt nếu bảng trong có index, bảng ngoài nhỏ). Hash Join — build bảng hash từ bảng nhỏ hơn rồi dò bảng lớn (tốt cho hai bảng lớn, join bằng đẳng thức, không cần sort). Merge Join — duyệt hai input đã sort sẵn và gộp (tốt khi hai bên có index theo join key hoặc đều đã sort).

Why

Biết planner chọn gì và tại sao, để khi plan tệ thì chẩn đoán được nguyên nhân — thường vì estimate sai số row dẫn tới chọn nested loop cho tập dữ liệu lớn. Đây cũng là câu phân biệt middle với senior: không chỉ nêu tên mà giải thích điều kiện chọn và cách đọc từng node trong plan.

How
Bảng ngoài nhỏ + index trên bảng trong
→ Nested Loop
↓ hai bảng lớn, join bằng '=', không index
→ Hash Join
Build hash bảng nhỏ → probe bảng lớn
↓ cả hai đã sort sẵn theo join key
→ Merge Join
Duyệt song song hai luồng đã sort

Trong plan PostgreSQL: Nested Loop có một node con ngoài và node trong chạy lặp loops = số row ngoài; Hash Join có node Hash (build) và một nhánh probe, kèm Batches/Memory Usage; Merge Join có Merge Cond và hai input đã sort. Dấu hiệu planner chọn sai: Nested Loop với loops hàng chục nghìn, hoặc Hash Join Batches > 1 (work_mem không đủ, spill ra đĩa).

When

Nested Loop: lookup theo khóa chính/index sau khi đã lọc mạnh (join 1 triệu order với customer theo customer_id có index). Hash Join: join khối lớn không index, đẳng thức, ví dụ join fact với dimension. Merge Join: hai bảng đã sort theo cùng key (tận dụng index) hoặc khi join kèm dải (BETWEEN) không phải đẳng thức.

When NOT

Đừng ép Nested Loop cho hai bảng lớn không index — O(n×m). Đừng dùng hint/ép join kiểu enable_hashjoin=off trên production như giải pháp lâu dài — sửa gốc là statistics/index. Đừng quên work_mem cho hash join lớn.

-- Probe: buộc planner thử Hash Join để so sánh (chỉ để học/đo)
SET local enable_nestloop = off;

EXPLAIN (ANALYZE, BUFFERS)
SELECT c.name, o.total
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE c.country = 'VN';

-- Nested Loop: bảng ngoài nhỏ (10 row) × index lookup trên orders
--   ->  Nested Loop  (actual time=0.044..0.910 rows=1250 loops=1)
--         ->  Seq Scan on customers  (rows=10 loops=1)
--         ->  Index Scan using idx_orders_customer on orders  (loops=10)

-- Hash Join: hai bảng lớn, không index join key
--   ->  Hash Join  (Hash Cond: (o.customer_id = c.id))
--         ->  Seq Scan on orders o  (rows=2000000 loops=1)
--         ->  Hash  (rows=50000 loops=1)  Buckets: 65536  Batches: 1
--               ->  Seq Scan on customers c  (rows=50000 loops=1)

-- Merge Join: cả hai đã sorted theo join key
--   ->  Merge Join  (Merge Cond: (o.customer_id = c.id))
--         ->  Index Scan using idx_orders_customer on orders o
--         ->  Index Scan using customers_pkey on customers c
Use case

Join order với customer: ví dụ điển hình planner chọn Nested Loop khi filter country='VN' chỉ ra 10 customer, tra bảng orders theo index customer_id với 10 loops — nhanh. Nếu statistics sai khiến nó tưởng chỉ 1 customer mà thực tế 50.000, plan sập.

Pitfall / Interview trap

Bẫy hay gặp: Nested Loop với loops khổng lồ (nhân rows × loops mới ra chi phí thật). Hash Join Batches > 1 nghĩa là spill đĩa — tăng work_mem. enable_* chỉ là công cụ chẩn đoán, không phải fix.

Nói trong 60 giây
  • Nested Loop: bảng ngoài nhỏ + index bảng trong.
  • Hash Join: hai bảng lớn, đẳng thức, không index.
  • Merge Join: hai input đã sort sẵn.
  • Đọc plan: loops, Hash/Batches, Merge Cond.
  • Planner chọn sai thường do statistics lệch.

Query Pattern, Bảo trì & Khác biệt Engine

Q6 N+1 query: nhận diện và sửa (JOIN FETCH, batch fetching, @EntityGraph)?

What

N+1 query là anti-pattern ORM: một truy vấn lấy N entity cha, rồi ORM phát thêm N truy vấn để nạp từng liên kết khi truy cập (thường do lazy loading kích hoạt trong vòng lặp). Tổng cộng 1+N round-trip tới DB thay vì 1 — chi phí bùng nổ theo số bản ghi.

Why

Mỗi truy vấn tốn round-trip mạng + parse + plan, nên 101 truy vấn chậm hơn một truy vấn join rất nhiều dù tổng dữ liệu như nhau. Đây là lỗi hiệu năng ORM phổ biến nhất và hay được hỏi trong phỏng vấn backend Java vì nó gắn trực tiếp với JPA/Hibernate.

How
1 query: SELECT * FROM orders (100 rows)
↓ vòng lặp truy cập order.getCustomer()
N=100 query: SELECT * FROM customers WHERE id = ?
×100 round-trip
↓ sửa bằng fetch join / batch
1 query: JOIN FETCH → 1 round-trip

Nhận diện: bật hibernate.generate_statistics=true và log SQL, hoặc xem số statement trong log. Nếu thấy cùng một câu SELECT lặp lại với chỉ tham số id khác nhau, đó là N+1. Sửa: (1) JOIN FETCH trong JPQL để nạp liên kết trong cùng truy vấn; (2) @EntityGraph để khai báo nhánh cần fetch theo tên thuộc tính — gọn hơn, không phải viết join; (3) batch fetching (@BatchSize hoặc hibernate.default_batch_fetch_size) gom nhiều id vào một IN (...) — phù hợp khi quan hệ @Many khiến fetch join nhân dòng.

When

Dùng JOIN FETCH/@EntityGraph khi quan hệ là @ManyToOne/@OneToOne (fetch join không nhân dòng). Dùng batch fetching khi quan hệ @OneToMany/@ManyToMany — fetch join trên nhiều collection sẽ gây tích Descartes và MultipleBagFetchException. Với collection lớn, batch size 20–50 là hợp lý.

When NOT

Đừng bật EAGER toàn cục để "chữa" N+1 — nó gây N+1 ở nơi khác và tải dữ liệu thừa. Đừng fetch join nhiều collection cùng lúc (Cartesian + nổ dòng). Đừng nạp dữ liệu rồi để lazy load kích hoạt trong vòng lặp — đó chính là nguyên nhân.

-- Đúng những gì ORM phát ra: 1 + N truy vấn round-trip
SELECT id, customer_id, total FROM orders WHERE status = 'NEW' LIMIT 100;  -- 1 lần
SELECT id, name FROM customers WHERE id = 101;   -- lặp 100 lần, chỉ khác id
-- ... tổng 101 statement ~2500 ms cho cùng lượng dữ liệu

-- Sửa: một truy vấn join thay cho 1+N
SELECT o.id, o.total, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'NEW' LIMIT 100;   -- 1 statement ~80 ms

-- Batch fetching gom id lại thành IN (...) một round-trip
SELECT id, name FROM customers
WHERE id IN (101, 102, 103, /* ... tối đa batch size ... */ 150);
// Trước khi sửa: 101 statement cho danh sách order
List<Order> orders = orderRepo.findByStatus("NEW");
for (Order o : orders) {
  o.getCustomer().getName();   // lazy → N query phát sinh
}

// Fix 1: JOIN FETCH trong JPQL
@Query("SELECT o FROM Order o JOIN FETCH o.customer WHERE o.status = :status")
List<Order> findWithCustomer(String status);

// Fix 2: @EntityGraph — gọn, không viết join
@EntityGraph(attributePaths = "customer")
List<Order> findByStatus(String status);

// Fix 3: batch fetching — hợp cho @OneToMany collection
// @BatchSize(size = 50) trên collection, hoặc toàn cục:
// spring.jpa.properties.hibernate.default_batch_fetch_size=50
// → gom id thành: SELECT ... WHERE customer_id IN (?, ?, ... 50 giá trị)
Use case

API trả 100 order kèm tên customer: trước là 101 statement ~2500 ms, sau khi thêm @EntityGraph(attributePaths="customer") còn 1 statement ~80 ms.

Pitfall / Interview trap

Nhiều người "sửa" N+1 bằng cách chuyển FetchType sang EAGER — chỉ dời vấn đề, không giải. Và fetch join hai collection @OneToMany cùng lúc sẽ nổ số dòng (tích Descartes) hoặc ném MultipleBagFetchException.

Nói trong 60 giây
  • N+1: 1 query cha + N query lazy cho con.
  • Nhận diện qua hibernate statistics / log SQL lặp.
  • Sửa: JOIN FETCH, @EntityGraph, batch fetching.
  • ManyToOne → fetch join; OneToMany → batch size.
  • EAGER không phải giải pháp.

Q7 Thống kê & bảo trì: ANALYZE/VACUUM (PostgreSQL) vs DBMS_STATS (Oracle)?

What

Planner không đọc dữ liệu thật mà dựa vào statistics để ước lượng số row mỗi bước. PostgreSQL cập nhật qua ANALYZE (thu histogram/ndistinct) và dọn dữ liệu chết bằng VACUUM; Oracle thu qua DBMS_STATS.GATHER_*_STATS. Statistics sai là nguyên nhân số 1 khiến plan "tự nhiên" đổi và chậm.

Why

PostgreSQL dùng MVCC: UPDATE/DELETE để lại dead tuple, không xoá ngay. Dead tuple chiếm chỗ (bloat), làm bảng phình và index scan phải đọc page vô ích. VACUUM thu hồi không gian và đánh dấu page all-visible (điều kiện cho index-only scan); ANALYZE cập nhật thống kê. Thiếu cả hai (autovacuum bị tắt/không theo kịp) → vừa bloat vừa plan sai.

How
UPDATE / DELETE nhiều row
↓ MVCC: row cũ thành dead tuple
Dead tuple tích tụ → bloat + statistics cũ
↓ tự động (autovacuum) hoặc chạy tay
VACUUM thu hồi chỗ + all-visible
ANALYZE cập nhật histogram

Sau bulk load/migrate, luôn chạy VACUUM (ANALYZE) để planner có số liệu mới; nếu không, planner vẫn tưởng bảng nhỏ và chọn nested loop. Với cột lệch phân bố (selectivity không đồng đều), cần histogram chi tiết — PostgreSQL tăng default_statistics_target hoặc ALTER ... SET STATISTICS cho riêng cột; Oracle dùng METHOD_OPT => 'FOR COLUMNS SIZE AUTO'. Kiểm tra sức khoẻ bảng bằng view monitoring.

When

Chạy tay sau bulk insert/update/delete lớn, sau khi migrate dữ liệu, hoặc định kỳ với bảng ghi nhiều. Theo dõi pg_stat_user_tables để biết bloat và dead tuple; đặt autovacuum nhạy hơn cho bảng nóng. Oracle thu stats theo table/schema, cân nhắc cascade => TRUE để thu cả index.

When NOT

Đừng chạy VACUUM FULL giữa giờ cao điểm — nó khoá bảng exclusive; dùng pg_repack/VACUUM (FULL) trong cửa sổ bảo trì. Đừng tắt autovacuum để "đỡ tải" — đổi lại là bloat và plan sai. Đừng thu stats quá dày đặc trên hệ lớn — tốn IO; hãy để autovacuum lo và chỉ chạy tay sau sự kiện lớn.

-- PostgreSQL: cập nhật thống kê + dọn dữ liệu chết
ANALYZE orders;                      -- chỉ statistics (nhanh)
VACUUM (ANALYZE, VERBOSE) orders;    -- dọn + thu stats

-- Cột lệch phân bố: tăng độ chi tiết histogram
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;

-- Xem sức khoẻ bảng: dead tuple, lần autovacuum cuối
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
WHERE relname = 'orders';

-- Oracle: thu thống kê theo bảng, kèm index (cascade)
EXEC DBMS_STATS.GATHER_TABLE_STATS('WMS', 'ORDERS', cascade => TRUE);

-- Histogram cho cột skewed
EXEC DBMS_STATS.GATHER_TABLE_STATS(
  'WMS', 'ORDERS',
  method_opt => 'FOR COLUMNS SIZE AUTO');
Use case

Bảng orders sau khi migrate 5 triệu row: n_dead_tup tăng vọt và plan chuyển sang Seq Scan sai. Chạy VACUUM (ANALYZE) xong, planner lại chọn đúng Index Scan và query về mức cũ.

Pitfall / Interview trap

VACUUM ≠ VACUUM FULL: cái sau khoá exclusive, không dùng giờ cao điểm. Và VACUUM không cập nhật statistics — phải có ANALYZE. Đây là điểm rất hay bị hỏi.

Nói trong 60 giây
  • Planner dựa vào statistics, không đọc dữ liệu thật.
  • PG: ANALYZE (stats) + VACUUM (dead tuple/bloat).
  • Oracle: DBMS_STATS.GATHER_TABLE_STATS.
  • VACUUM FULL khoá bảng — chỉ maintenance window.
  • Stats sai = plan sai, nguyên nhân số 1.

Q8 Partitioning và partial index — khi nào hiệu quả, các loại partition?

What

Partitioning chia một bảng logic thành nhiều bảng vật lý con theo khóa. Ba loại chính: range (theo khoảng — thời gian, id), list (theo tập giá trị rời — region, tenant), hash (chia đều theo hàm băm — phân tán tải). Partial index là index chỉ phủ một tập con row theo điều kiện WHERE, ví dụ chỉ index các đơn status='PENDING'.

Why

Partitioning giúp query chỉ chạm phần dữ liệu liên quan (partition pruning), và giúp bảo trì theo khối (drop cả partition cũ thay vì DELETE hàng loạt gây bloat). Partial index thì index nhỏ hơn nhiều khi phần lớn row không bao giờ bị truy vấn theo điều kiện đó — vừa nhanh vừa nhẹ cho ghi.

How
Bảng orders (logical)
↓ partition by range (created_at)
orders_2026_01
orders_2026_02
orders_2026_03
↓ WHERE created_at trong tháng 02/2026
Partition pruning → chỉ scan orders_2026_02

Điều kiện để partitioning có lợi: query luôn lọc theo khóa partition (nếu không, planner scan mọi partition — còn chậm hơn bảng phẳng), và dữ liệu có tính chu kỳ rõ (theo tháng, theo vùng). Partial index hiệu quả khi truy vấn nhắm một tập nhỏ đặc trưng — ví dụ worker chỉ quét status='PENDING' trong khi 99% row là DONE.

When

Range partition: dữ liệu log/time-series, dọn theo tháng bằng drop partition. List partition: multi-tenant/region cần quản lý theo đơn vị. Hash partition: chia đều tải khi không có khóa range/lưu tự nhiên. Partial index: bảng lớn nhưng hot query chỉ đụng phần nhỏ row.

When NOT

Đừng partition bảng nhỏ (dưới vài triệu row) — overhead quản lý không đáng. Đừng partition theo khóa mà query không lọc theo — pruning không xảy ra. Đừng dùng partial index cho điều kiện "đa số row đều khớp" — index sẽ to gần bằng index đầy đủ, mất ý nghĩa.

-- PostgreSQL: range partition theo tháng
CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY,
  created_at  timestamp NOT NULL,
  total       numeric
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_01 PARTITION OF orders
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

-- Partition pruning: chỉ 1 partition được scan
EXPLAIN ANALYZE SELECT * FROM orders
WHERE created_at >= '2026-01-05' AND created_at < '2026-01-10';
-- Append  ->  Seq Scan on orders_2026_01   ← các partition khác bị loại

-- Partial index: chỉ index row "nóng"
CREATE INDEX idx_orders_pending ON orders (created_at)
WHERE status = 'PENDING';

-- Oracle: interval partitioning tự sinh partition
-- PARTITION BY RANGE (created_at)
--   INTERVAL (NUMTOYMINTERVAL(1, 'MONTH')) (PARTITION p_init VALUES LESS THAN (...));
Use case

Bảng log truy cập theo tháng: range partition giúp query báo cáo tháng 2 chỉ scan 1 partition, và cuối mỗi quý DROP partition cũ tức thời thay vì DELETE hàng chục triệu dòng.

Pitfall / Interview trap

Partitioning không thay thế index — partition nhỏ vẫn cần index đúng. Bẫy lớn: query không lọc theo khóa partition → planner scan toàn bộ partition, chậm hơn bảng phẳng. Và partial index chỉ được dùng khi điều kiện WHERE của query bao hàm điều kiện của index.

Nói trong 60 giây
  • Partition: range / list / hash theo khóa.
  • Lợi: partition pruning + bảo trì theo khối (drop).
  • Phải lọc theo khóa partition mới có pruning.
  • Partial index: index tập con nhỏ, hot query.
  • Partition không thay thế index đúng.

Q9 Phân trang hiệu quả: LIMIT/OFFSET vs keyset; Oracle FETCH FIRST / ROWNUM?

What

Offset pagination (LIMIT n OFFSET m) đọc và bỏ qua m row trước khi trả về. Keyset pagination (seek method) dùng điều kiện WHERE key > last_seen ORDER BY key LIMIT n — bắt đầu ngay từ vị trí đã biết nhờ index. Oracle từ 12c dùng OFFSET ... ROWS FETCH NEXT n ROWS ONLY; trước 12c phải bọc ROWNUM trong subquery.

Why

OFFSET lớn chậm vì engine vẫn phải đọc và vứt bỏ m row (m thường rất lớn ở cuối danh sách), tốn I/O và CPU dù chỉ trả 20 row. Ngoài ra offset pagination không ổn định khi dữ liệu thay đổi giữa hai lần lật trang — có thể trùng hoặc nhảy mục. Keyset giải quyết cả hai: chi phí gần như hằng số nhờ index và vị trí dựa trên giá trị khóa.

How
LIMIT 20 OFFSET 1000000
đọc + bỏ 1.000.000 row
↓ chi phí tăng theo độ sâu trang
WHERE id > last_seen ORDER BY id LIMIT 20
↓ index seek đúng vị trí
Chỉ đọc 20 row — chi phí hằng số

Keyset cần một khóa sắp xếp duy nhất và ổn định (id tăng dần là lý tưởng). Khi sắp theo nhiều cột, dùng so sánh tuple: WHERE (sort_col, id) > (?, ?) để tránh trùng. Với Oracle ROWNUM: nó được gán trước ORDER BY, nên phải bọc lồng subquery mới đúng — bỏ query ra ngoài rồi mới lọc ROWNUM.

When

Keyset cho danh sách cuộn vô hạn, feed, log, API danh sách dài cần hiệu năng. Offset chỉ dùng khi cần nhảy tới trang bất kỳ và dữ liệu nhỏ / trang nông, hoặc khi UI cần "trang 7/99". Oracle 12c+ dùng cú pháp chuẩn FETCH FIRST/NEXT; code cũ có thể dùng ROWNUM lồng.

When NOT

Đừng dùng OFFSET lớn cho danh sách dài. Đừng quên cột ORDER BY phải có index — nếu không, keyset vẫn phải sort toàn bộ rồi mới lấy 20 row. Đừng dựa vào OFFSET khi dữ liệu ghi liên tục nếu cần kết quả nhất quán (bỏ/trùng mục). Và ROWNUM phải bọc subquery, nếu không thứ tự sai.

-- OFFSET lớn: PostgreSQL vẫn đọc + vứt 1.000.000 row
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 1000000;  -- ~2100 ms

-- Keyset: index seek, gần như hằng số
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 20;       -- ~0.8 ms

-- Keyset với sort nhiều cột: so sánh tuple
SELECT * FROM orders
WHERE (created_at, id) < ('2026-01-15 09:00:00', 987654)
ORDER BY created_at DESC, id DESC LIMIT 20;

-- Oracle 12c+ cú pháp chuẩn
SELECT * FROM orders ORDER BY id
OFFSET 1000000 ROWS FETCH NEXT 20 ROWS ONLY;

-- Oracle cũ: ROWNUM gán trước ORDER BY → phải bọc subquery
SELECT * FROM (
  SELECT id, total FROM orders ORDER BY id
) WHERE ROWNUM <= 20;
Use case

API feed đơn hàng cuộn vô hạn dùng keyset: mỗi trang trả kèm next_cursor = id cuối, client gửi lại làm tham số cho trang sau — truy vấn luôn nhanh bất kể cuộn sâu bao nhiêu.

Pitfall / Interview trap

OFFSET lớn chậm vì phải đọc rồi vứt bỏ, không phải vì trả nhiều row. Keyset vẫn cần index trên cột sort. Bẫy Oracle: ROWNUM gán trước ORDER BY — luôn bọc subquery.

Nói trong 60 giây
  • OFFSET lớn: đọc + bỏ m row → chậm dần theo trang.
  • Keyset: WHERE key > last_seen → chi phí hằng số.
  • Keyset ổn định hơn khi dữ liệu ghi liên tục.
  • Cần index trên cột sort.
  • Oracle: FETCH FIRST (12c+) / ROWNUM bọc subquery.

Q10 Khác biệt PostgreSQL ↔ Oracle khi viết SQL và tối ưu?

What

Hai hệ khác nhau ở kiểu dữ liệu, cách sinh khóa (sequence/identity), ngữ nghĩa NULL vs chuỗi rỗng, bộ hàm (NVL/DECODE vs COALESCE/CASE), ngôn ngữ thủ tục (PL/SQL vs PL/pgSQL), transaction/isolation và cách planner chọn plan. Port code giữa hai bên phải rà từng nhóm này, không chỉ đổi cú pháp.

Why

Lỗi port phổ biến nhất không phải cú pháp mà là ngữ nghĩa ngầm: Oracle coi '' là NULL nên col = '' không bao giờ khớp, còn PostgreSQL coi '' là chuỗi rỗng khác NULL — cùng câu SQL cho kết quả khác nhau. Tương tự, phân trang, hàm xử lý NULL, và mặc định isolation cũng khác, khiến hành vi thay đổi khi chuyển hệ.

How
SQL viết cho Oracle
↓ rà NULL semantics, kiểu, hàm, sequence
NVL → COALESCE
DECODE → CASE
SYSDATE → now()
↓ kiểm tra phân trang, isolation, transaction
Chạy test lại toàn bộ trên PostgreSQL

Các điểm cần nhớ: NULL/empty string khác hẳn; identity là chuẩn chung nhưng Oracle cũ dùng SEQUENCE + trigger; hàm NVL/DECODE (Oracle-only) thay bằng COALESCE/CASE (chuẩn SQL); phân trang khác cú pháp; transaction — Oracle không có READ UNCOMMITTED và mặc định READ COMMITTED, PostgreSQL cũng READ COMMITTED nhưng dùng MVCC snapshot per-statement; DDL có auto-commit hay không khác nhau. Về tối ưu: Oracle hay dùng hint và DBMS_XPLAN, PostgreSQL tránh hint và ưu tiên sửa statistics/index; Oracle có bitmap index, PostgreSQL có partial/expression/GIN index.

When

Gặp '' trong dữ liệu Oracle cũ khi migrate — phải quyết định chuẩn hoá về NULL hay giữ chuỗi rỗng, vì logic so sánh thay đổi. Khi port query dùng NVL, DECODE, ROWNUM, SYSDATE. Khi chuyển stored procedure — PL/SQL sang PL/pgSQL phải viết lại, không tự động.

When NOT

Đừng giả định '' = NULL trên PostgreSQL — sai ngữ nghĩa. Đừng copy hint Oracle sang PostgreSQL — hint tối thiểu và khác hẳn. Đừng bê nguyên ROWNUM sang — dùng LIMIT. Và đừng bỏ qua chuyện isolation/transaction khi port — hành vi đồng thời có thể đổi.

-- NULL vs chuỗi rỗng
-- Oracle: '' IS NULL là TRUE (không phân biệt empty string với NULL)
SELECT 1 FROM dual WHERE '' IS NULL;      -- Oracle: trả 1 row
SELECT '' IS NULL;                        -- PostgreSQL: false

-- Hàm xử lý NULL: Oracle-only → chuẩn SQL
-- Oracle:  NVL(col, 'N/A')                -- đúng 2 tham số
-- Chuẩn: COALESCE(col, col2, 'N/A')   -- n tham số, portable

-- DECODE (Oracle) → CASE (chuẩn)
-- Oracle:  DECODE(status, 'A', 1, 'B', 2, 0)
SELECT CASE status
         WHEN 'A' THEN 1
         WHEN 'B' THEN 2
         ELSE 0
       END AS code
FROM orders;

-- Identity (cả hai hỗ trợ chuẩn này)
-- Oracle:     id NUMBER GENERATED ALWAYS AS IDENTITY
-- PostgreSQL: id BIGINT GENERATED ALWAYS AS IDENTITY

-- Ngày giờ & ngôn ngữ thủ tục
-- Oracle:     SYSDATE, TO_DATE('2026-01-01','YYYY-MM-DD'), PL/SQL
-- PostgreSQL: now() / CURRENT_DATE, '2026-01-01'::date, PL/pgSQL

-- Phân trang
-- Oracle:     ... ORDER BY id OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY
-- PostgreSQL: ... ORDER BY id LIMIT 10 OFFSET 20
Use case

Migrate báo cáo từ Oracle sang PostgreSQL: thay NVL→COALESCE, DECODE→CASE, ROWNUM→LIMIT/OFFSET, và rà lại mọi chỗ so sánh '' vì ngữ nghĩa NULL khác — đây là bước hay bị bỏ sót và gây sai số liệu.

Pitfall / Interview trap

Ba bẫy hay hỏi: '' IS NULL khác nhau giữa hai hệ; NVL không portable (dùng COALESCE); ROWNUM gán trước ORDER BY. Thêm nữa: Oracle không có READ UNCOMMITTED, và hint Oracle không mang sang PostgreSQL.

Nói trong 60 giây
  • NULL vs '' khác hệ — bẫy ngữ nghĩa lớn nhất.
  • NVL/DECODE → COALESCE/CASE.
  • Sequence/identity, phân trang, hàm ngày khác cú pháp.
  • PL/SQL ≠ PL/pgSQL — phải viết lại.
  • Transaction/isolation & tối ưu (hint vs stats/index) cũng khác.

SQL DEM/DET: actual plan Oracle, bitmap và kiểm chứng tối ưu

What

Tối ưu query phải dựa trên dữ liệu và execution plan thật: PostgreSQL bitmap scan là cách truy cập tạm từ index, không phải persistent bitmap index của Oracle. DEM/DET nếu là tên bảng nghiệp vụ phải được làm rõ schema, cardinality và query trước khi đề xuất index.

Không bịa schema DEM/DET

DEM/DET không phải cặp keyword SQL chuẩn phổ quát. Nếu interviewer dùng làm tên bảng master/detail, yêu cầu PK/FK, số dòng, phân bố và query thực tế; ví dụ minh họa bên dưới giả định DEM(id,created_at) và DET(dem_id,status,amount), không tuyên bố đây là schema hệ thống người dùng.

Actual và estimated

Oracle EXPLAIN PLAN chỉ estimate. Sau execution thu runtime statistics bằng gather_plan_statistics hoặc statistics_level phù hợp, đọc DBMS_XPLAN.DISPLAY_CURSOR(sql_id, child_number, ALLSTATS LAST); so E-Rows/A-Rows và Starts trên đúng child cursor. Không bật collect toàn app tùy tiện; cần quyền và cân nhắc overhead. PG actual rows là trung bình mỗi loop, đọc cả loops, buffers và spills; shared read không chứng minh physical disk vì OS cache có thể phục vụ.

Bitmap khác nhau

Oracle bitmap index lưu bitmap persistent, hữu ích data warehouse/ít concurrent DML; update có thể khóa phạm vi nhiều row nên không chọn chỉ vì status ít giá trị trong OLTP. PostgreSQL Bitmap Index Scan dựng bitmap TID từ B-tree/khác, BitmapAnd/Or kết hợp và Bitmap Heap Scan đọc heap theo block; lossy bitmap phải recheck. Nó không có nghĩa CREATE BITMAP INDEX tương đương Oracle.

Quy trình với DEM/DET giả định

Lọc khoảng ngày bằng >= và < thay vì bọc function lên cột khi chưa có expression index phù hợp. Xem selectivity trước khi chọn DEM(created_at,id), DET(dem_id,status) hay DET(status,dem_id). Không tạo cả ba mù quáng: thứ tự join, độ chọn lọc, write overhead và partition pruning quyết định. EXPLAIN ANALYZE chạy thật, rollback không hoàn tác mọi side effect như sequence hay external function; dùng read-only replica/staging khi thích hợp.

Nghiệm thu

So latency p95 và rows/buffers/temp I/O cùng dataset và bind params đại diện, warm/cold cache rõ ràng. Estimate lệch có thể do skew/correlation/parameter-sensitive plan, không chỉ thiếu index; cập nhật stats và kiểm dữ liệu trước. Partition chỉ có lợi khi pruning hoặc maintenance khớp use case, không phải luôn nhanh hơn.

FROM dem d JOIN det t ON t.dem_id = d.id
WHERE d.created_at >= :from_time AND d.created_at < :to_time
  AND t.status = :status
GROUP BY d.id;
