CloudFront & tối ưu edge

AWS1 CloudFront cơ bản: distribution, origin, cache behavior, TTL và invalidation

What

Amazon CloudFront là CDN toàn cầu: request của người dùng đi tới edge location gần nhất, phục vụ bản cache tại chỗ; nếu trượt cache (miss) mới gọi về origin (S3 bucket, ALB/EC2, HTTP server, API Gateway). Một distribution gồm nhiều cache behavior — mỗi behavior khớp một path pattern (/api/*, /images/*, Default (*)) và gắn origin + chính sách cache riêng.

How

Tài liệu được cache theo TTL (mặc định 86400 giây = 24 giờ, min 0, max 31536000). TTL có thể do origin gửi bằng header Cache-Control/Expires, hoặc bị ép bởi cache policy. Khi cập nhật nội dung mà không muốn chờ hết TTL, bạn tạo invalidation để xoá cache theo path.

Bẫy thi / Pitfall

Muốn nội dung cập nhật nhanh mà không invalidate: đặt TTL ngắn hoặc dùng versioned filename (app.v2.js). Đừng nhồi tất cả header/cookie vào cache key — hit ratio tụt. CloudFront hỗ trợ cả POST/PUT (không cache) để đẩy request động về origin.

AWS2 Giữ S3 private với OAC và phân phối nội dung có kiểm soát: signed URL vs signed cookie

What

Hai nhu cầu khác nhau: (1) CloudFront đọc S3 mà bucket vẫn private → dùng Origin Access Control (OAC) (thay thế OAI cũ). (2) Chỉ phát nội dung cho người có quyền → dùng signed URL (một file) hoặc signed cookie (nhiều file / cả site).

How

Với OAC, CloudFront ký request (SigV4) tới S3 và bucket policy chỉ cho phép đúng distribution đó — không cần bật public, hỗ trợ cả SSE-KMS. Với signed URL/cookie, bạn dùng key pair (trusted signer) hoặc key group ký thời hạn (Expires) và (tuỳ chọn) giới hạn IP.

AWS3 So sánh: CloudFront Functions vs Lambda@Edge — chạy code ở edge khi nào?

What

CloudFront Functions là hàm JavaScript siêu nhẹ chạy ở viewer request/response (trước/sau khi vào cache), khởi động dưới mili-giây, không truy cập mạng. Lambda@Edge là Lambda đầy đủ chạy ở cả 4 điểm: viewer request/response và origin request/response, có thể gọi service ngoài, thời gian chạy dài hơn.

How

Chọn theo nhu cầu: thao tác URL/header đơn giản, redirect, thêm header bảo mật, chuẩn hoá query → CloudFront Functions (rẻ, scale tốt). Cần gọi API ngoài, đọc secret, A/B test nặng, resize ảnh tại edge, chọn origin động theo dữ liệu → Lambda@Edge.

CloudFront Functionsviewer only · JS · sub-ms · không network
Lambda@Edge4 hook · Node/Python · tới 30s · có network
Originxử lý nghiệp vụ nặng
// CloudFront Function — viewer request, chạy sub-millisecond
function handler(event) {
    var req = event.request;
    if (req.uri.endsWith('/')) { req.uri = req.uri + 'index.html'; }
    req.headers['x-country'] = { value: 'VN' };
    return req;
}

Đề hay hỏi \"cần đọc dữ liệu từ DynamoDB ở edge\" → Lambda@Edge (Functions không có network). \"Cần modify header/redirect với chi phí thấp nhất\" → CloudFront Functions. Lambda@Edge gắn vào distribution ở region us-east-1 và phải nằm cùng region khi publish.

Route 53 & DNS

AWS4 Route 53: record types, alias vs CNAME và cách đặt TTL

What

Route 53 là DNS managed: mỗi hosted zone chứa các record. Loại hay gặp: A (IPv4), AAAA (IPv6), CNAME (bí danh tên miền), MX (mail), TXT (xác thực/SPF), NS/SOA (quản trị zone), CAA, SRV. Alias record là kiểu riêng của AWS: trỏ tới resource AWS (CloudFront, ALB/NLB, S3 website, API Gateway) mà không cần IP.

How

Điểm mấu chốt: CNAME không dùng được ở zone apex (example.com) và tính phí query; alias dùng được ở apex, miễn phí query, và hỗ trợ Evaluate Target Health để failover theo health check. TTL trên record quyết định thời gian resolver cache câu trả lời — TTL ngắn giúp đổi cấu hình nhanh hơn nhưng tăng số query.

AWS5 Tình huống: chọn routing policy nào và dựng failover bằng health check

What

Route 53 có nhiều routing policy: simple (một record), weighted (chia % cho canary/A-B), latency (đưa người dùng tới region có độ trễ thấp nhất), failover (primary/secondary + health check), geolocation (theo quốc gia/châu lục), geoproximity, multivalue answer.

How

Ý tưởng chọn nhanh: cần phát hành dần → weighted; tối ưu tốc độ theo vùng → latency; dự phòng khi site chết → failover; phục vụ nội dung theo luật bản địa → geolocation. Health check theo dõi endpoint (HTTP/HTTPS/TCP + chuỗi khớp); khi unhealthy, failover chuyển sang secondary.

API Gateway — cửa vào API

AWS6 So sánh: API Gateway REST API vs HTTP API vs WebSocket API

What

Ba loại API khác nhau về mục tiêu. REST API (v1) giàu tính năng: API key + usage plan, caching, request validation, mapping template (VTL), integrate non-proxy, WAF, private endpoint. HTTP API (v2) tối ưu chi phí/độ trễ, hỗ trợ JWT authorizer gốc + CORS built-in nhưng ít tính năng hơn. WebSocket API cho giao tiếp hai chiều (chat, realtime).

How

Chọn theo yêu cầu: chỉ cần proxy tới Lambda/HTTP backend, cần rẻ và nhanh → HTTP API (rẻ hơn REST khoảng 70%). Cần API key, usage plan, caching, VTL, WAF, integration tinh chỉnh → REST API. Cần push hai chiều server→client → WebSocket.

AWS7 Lambda proxy integration, mapping template và stage variable

What

Lambda proxy integration (AWS_PROXY) đưa toàn bộ request vào event của Lambda (method, path, query, headers, body, isBase64Encoded) và bắt Lambda trả về đúng cấu trúc statusCode + headers + body. Non-proxy (custom) cho phép bạn dùng mapping template (VTL) để biến đổi request/response.

How

Proxy là cách mặc định, ít cấu hình nhất — Lambda tự kiểm soát response. Khi backend cần định dạng cố định (vd dịch vụ legacy nhận XML), dùng non-proxy + mapping template. Stage variable cho phép cùng một API trỏ tới resource khác nhau theo stage (dev/prod), thường dùng để trỏ tới Lambda alias.

AWS8 So sánh: xác thực API — IAM, Lambda authorizer, Cognito authorizer, API key + usage plan

What

Bốn cơ chế hay bị nhầm:
IAM auth — client ký request bằng SigV4, phù hợp gọi nội bộ giữa AWS service. Lambda authorizer — hàm tự quyết định allow/deny, trả về IAM policy. Cognito user pool authorizer — xác thực JWT do Cognito phát hành cho người dùng app. API key + usage plan — chỉ để đo lường và throttle, KHÔNG phải cơ chế xác thực bảo mật.

How

Người dùng cuối đăng nhập bằng Cognito → API Gateway kiểm JWT, không cần code. Hệ thống khác đăng nhập riêng (vd token OAuth ngoài) → Lambda authorizer. Service nội bộ AWS gọi nhau → IAM. Muốn giới hạn theo khách hàng (mobile client) → API key + usage plan (kèm throttling/quota).

IAM authSigV4 · service-to-service

AWS9 Throttling, quota, timeout 29 giây và caching của API Gateway

What

API Gateway bảo vệ backend bằng throttling (tốc độ) và quota (tổng số request theo tuần/tháng). Giới hạn mặc định toàn tài khoản/mỗi region là 10.000 request/giây và burst 5.000. Thêm vào đó là integration timeout 29 giây — nếu backend chậm hơn, API Gateway trả lỗi 504.

How

Chặn quá tải theo từng client bằng usage plan (rate + burst + quota) và có thể dùng per-method throttle. Với REST API, bật caching theo stage để giảm gọi backend (TTL 0–3600s, mặc định 300s). Request vượt hạn mức bị trả 429 Too Many Requests.

AWS10 Tình huống: thiết kế API cho app mobile — auth, cache, throttle và CORS

What

Một app mobile cần API vừa bảo mật vừa tiết kiệm: người dùng đăng nhập (auth), dữ liệu ít đổi được cache, các client phải bị giới hạn tốc độ, và web front-end gọi cross-domain nên phải có CORS. Đây là bài tổng hợp rất hay gặp trong DVA-C02.

How

Ghép: Cognito user pool phát JWT → gắn Cognito authorizer (REST) hoặc JWT authorizer (HTTP API). Bật cache theo stage cho các GET ít đổi (TTL ví dụ 300s) để giảm tải backend. Gắn usage plan + API key cho từng khách hàng để throttle/quota. Thêm CORS (OPTIONS) cho phép origin của web app. Nếu cần nội dung tĩnh toàn cầu, đặt CloudFront trước API/S3.

Use case
