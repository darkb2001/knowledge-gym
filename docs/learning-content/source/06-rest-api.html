REST API & Security

Thiết kế API, CORS, Idempotency, JWT, OAuth 2.0/OIDC, OWASP Top 10, HTTPS, Rate Limiting — bắt buộc cho Backend & Fullstack.

Thiết kế API & Giao thức

Q1 Phân biệt PUT vs PATCH?

What

PUT thay thế toàn bộ representation của resource tại URI — client gửi full state mong muốn. PATCH áp dụng partial update — chỉ sửa fields được gửi (JSON Merge Patch RFC 7396 hoặc JSON Patch RFC 6902). Cả hai đều idempotent nếu thiết kế đúng: gọi N lần cùng body → cùng kết quả.

Why

Phân biệt semantics tránh bug nghiệp vụ: PUT thiếu field → field bị NULL/default (mất data). PATCH phù hợp form sửa một phần (email, status). WMS: PUT thay thế toàn bộ pick task config; PATCH chỉ đổi status=COMPLETED mà không đụng line items.

How
PUTPATCH
SemanticsReplace entire resourcePartial update
Idempotent✅ Luôn✅ Nếu patch deterministic
Missing fieldsNULL / default / rejectGiữ nguyên giá trị cũ
FormatFull JSON bodyMerge Patch hoặc JSON Patch ops
When

PUT khi client có full snapshot resource (sync form edit-all-fields). PATCH khi mobile/SPA chỉ gửi delta, hoặc API public cho phép sửa vài field (profile email, order status). Spring: @PutMapping + full DTO validation; @PatchMapping + JsonMergePatch.

When NOT

Đừng dùng PUT cho "chỉ sửa 1 field" — client phải GET trước rồi merge, race condition. Đừng PATCH với JSON Patch ops phức tạp nếu client đơn giản — Merge Patch dễ hơn. Không nhầm PATCH idempotent với POST — POST tạo mới không idempotent.

# PUT — replace entire user
PUT /api/users/42
{ "name": "Alice", "email": "a@x.com", "role": "ADMIN" }

# PATCH — chỉ đổi email (Merge Patch)
PATCH /api/users/42
Content-Type: application/merge-patch+json
{ "email": "new@x.com" }
@PatchMapping("/{id}")
public UserDto patch(@PathVariable Long id,
    @RequestBody JsonMergePatch patch) {
  UserDto current = userService.findDto(id);
  JsonNode patched = patch.apply(objectMapper.valueToTree(current));
  return userService.update(id, objectMapper.treeToValue(patched, UserDto.class));
}
Use case
WMS operator đổi task priority qua PATCH {"priority": 1} — không cần gửi lại 20 fields pick line. Admin sync full order qua PUT khi import từ ERP.
Pitfall / Interview trap
"PATCH không idempotent" — SAI theo RFC nếu patch cùng body. Trap: PUT thiếu optional field → Hibernate set null → mất data. Luôn document API contract: PUT require all fields hay merge semantics.
Nói trong 60 giây
  • PUT = replace full resource; PATCH = partial update.
  • Cả hai idempotent nếu design đúng.
  • PUT thiếu field → NULL; PATCH giữ field cũ.
  • Spring: PutMapping full DTO, PatchMapping + JsonMergePatch.
  • WMS: PATCH status; PUT full config sync.

Q2 CORS hoạt động như thế nào?

What

CORS (Cross-Origin Resource Sharing) là cơ chế browser bảo vệ Same-Origin Policy: JS từ origin A không đọc response API origin B trừ khi server B trả headers cho phép. Simple request (GET, POST form) gửi thẳng; Preflight OPTIONS hỏi trước với non-simple method/header.

Why

CORS chỉ áp dụng browser — Postman/curl/server-to-server không bị. SPA WMS dashboard (app.wms.com) gọi API (api.wms.com) cần CORS config đúng. Thiếu CORS → browser block dù API trả 200 (opaque error).

How
Browser origin A
↓ OPTIONS preflight (nếu Authorization, JSON body PUT...)
Server B: Allow-Origin, Allow-Methods, Allow-Headers
↓ Actual request + credentials nếu cần
JS đọc response

Headers chính: Access-Control-Allow-Origin, Allow-Methods, Allow-Headers, Allow-Credentials, Max-Age (cache preflight).

When

Bắt buộc khi SPA/mobile web gọi API khác subdomain/port/protocol. Spring: CorsConfigurationSource hoặc @CrossOrigin trên controller. Gateway có thể centralize CORS thay từng service.

When NOT

Không cần CORS cho same-origin hoặc server-side BFF proxy (browser chỉ gọi cùng origin). Không fix CORS bằng disable security — config đúng origin whitelist. Không Allow-Origin: * khi credentials: true.

@Bean
CorsConfigurationSource corsSource() {
  CorsConfiguration cfg = new CorsConfiguration();
  cfg.setAllowedOrigins(List.of("https://app.example.com"));
  cfg.setAllowedMethods(List.of("GET","POST","PUT","PATCH","DELETE"));
  cfg.setAllowedHeaders(List.of("Authorization", "Content-Type"));
  cfg.setAllowCredentials(true);
  return request -> cfg;
}
Use case
WMS React dashboard gọi Spring Boot API — preflight OPTIONS cho PUT pick confirm kèm JWT Authorization header.
Pitfall / Interview trap
"CORS error = server lỗi 500" — SAI: thường API OK nhưng browser chặn đọc response. Trap: duplicate CORS header Gateway + Service. CORS ≠ authentication — chỉ control browser read access.
Nói trong 60 giây
  • CORS = browser policy, server trả Allow-* headers.
  • Preflight OPTIONS cho non-simple request.
  • Chỉ browser — Postman không cần.
  • Credentials true → origin cụ thể, không *.
  • Spring CorsConfigurationSource whitelist origin.

Q3 Idempotency trong API?

What

Idempotency: gọi cùng request N lần → cùng kết quả, không tạo side effect thêm. HTTP GET/PUT/DELETE idempotent theo spec; POST mặc định không — retry có thể double-charge hoặc tạo duplicate order.

Why

Network timeout, mobile retry, gateway replay — client không biết server đã xử lý chưa. Idempotency Key cho phép client retry an toàn: server nhận diện duplicate và trả cached response thay thực thi lại.

How
Client POST + Idempotency-Key: uuid
↓ server check UNIQUE(key)
Key mới → execute + cache response
↓ retry cùng key
Trả cached response — không charge lại
MethodIdempotent?
GET, PUT, DELETE✅
POST❌ — cần Idempotency Key
PATCH✅ nếu deterministic
When

POST payment, create order, transfer stock — mọi non-idempotent mutation client có thể retry. Stripe/PayPal pattern: header Idempotency-Key TTL 24h. WMS: confirm pick POST với key tránh double-confirm khi scanner lag.

When NOT

Đừng idempotency key random mỗi retry — client phải reuse cùng key. Đừng cache response vô thời hạn — set TTL. GET không cần idempotency key — đã idempotent. Đừng nhầm idempotent với "exactly-once delivery" — cần outbox + consumer idempotency cho async.

@PostMapping("/payments")
public PaymentResponse pay(
    @RequestHeader("Idempotency-Key") String key,
    @RequestBody PaymentRequest req) {
  return idempotencyService.execute(key, () -> paymentService.charge(req));
}
// DB: UNIQUE(idempotency_key) + lưu response cached
Use case

Mobile app POST payment timeout → retry cùng Idempotency-Key → server trả 200 cached, không charge 2 lần.

Pitfall

Key collision giữa users nếu không scope key theo tenant/user. Processing state: request đang xử lý, retry thứ 2 → return 409 Conflict hoặc wait.

Nói trong 60 giây
  • Idempotent = N lần gọi = 1 kết quả.
  • POST cần Idempotency-Key cho retry an toàn.
  • DB UNIQUE key + cache response.
  • Client reuse key khi retry, không random mới.
  • Khác exactly-once async — cần outbox.

Q4 API Versioning strategies?

What

API Versioning cho phép thay đổi contract (breaking change) mà không làm gãy client cũ. Các strategy: URI path (/v1/), header (Accept-Version), query param, content negotiation (Accept: application/vnd.app.v2+json).

Why

Mobile app không update ngay — cần support v1 song song v2. Breaking change: đổi field type, remove endpoint, đổi semantics. Version rõ ràng giúp deprecate có kế hoạch và monitor adoption.

How
StrategyVí dụƯu / Nhược
URI Path/api/v1/usersRõ ràng, dễ cache — URL dài
HeaderAccept-Version: 2URL sạch — cache/CDN phức tạp
Query param?version=2Đơn giản — ít RESTful
Content NegotiationAccept: application/vnd.app.v2+jsonChuẩn HTTP — client phức tạp
When

URI path: Spring Boot phổ biến nhất — @RequestMapping("/api/v1"). Header/Accept: public API lớn (GitHub). Chỉ bump major khi breaking — additive change (thêm optional field) không cần version mới.

When NOT

Đừng version mọi minor fix — version explosion. Đừng breaking change không bump version. Đừng maintain 5 version cùng lúc — sunset policy (Deprecation header, deadline). Không version internal service-to-service nếu deploy cùng pipeline — contract test đủ.

Best practice

URI path + sunset header Sunset: Sat, 01 Jan 2027. Monitor v1 traffic → 0 trước khi remove. OpenAPI document per version.

Pitfall

v1 và v2 share DB schema incompatible — migration phải backward compatible hoặc tách read model.

Nói trong 60 giây
  • Versioning cho breaking change — additive không cần.
  • URI /v1/ phổ biến Spring Boot.
  • Deprecate + sunset header trước khi remove.
  • Monitor traffic version cũ.
  • Internal same-deploy có thể skip version.

Q5 Pagination — cursor vs offset?

What

Offset pagination: ?page=2&size=20 → SQL OFFSET 20 LIMIT 20. Cursor (keyset) pagination: ?cursor=base64(lastId,lastSort) → WHERE (sort_col, id) < cursor ORDER BY ... LIMIT 20 — không scan bỏ qua rows.

Why

Offset lớn (page 5000) = DB scan 100k rows rồi discard — chậm O(offset). Cursor ổn định khi insert/delete giữa pages (offset duplicate/skip items). Infinite scroll mobile cần cursor; admin table jump page cần offset.

How

Offset-based

  • ?page=2&size=20
  • Jump to page N
  • Chậm offset lớn
  • Duplicate/skip khi data đổi

Cursor-based

  • ?cursor=eyJpZCI6MTIzfQ&limit=20
  • Ổn định insert/delete
  • Keyset — index-friendly
  • Không jump page tùy ý
-- Keyset / cursor pagination
SELECT * FROM orders
WHERE (created_at, id) < ('2024-01-15', 12345)
ORDER BY created_at DESC, id DESC
LIMIT 20;
When

Offset: admin UI, total count hiển thị, dataset < 10k rows. Cursor: feed/timeline, WMS task list realtime, API public lớn. Spring Data: Pageable offset; custom keyset với encoded cursor.

When NOT

Offset cho table 10M rows deep page. Cursor khi client cần "page 47 of 200" exact. Cursor không sort stable (non-unique sort key) → duplicate. Đừng expose raw DB id làm cursor nếu enumerable — opaque token.

Use case

WMS mobile pick list scroll: cursor lastTaskId — operator scroll không miss task khi task mới insert. Admin report page 3: offset OK với filter date range nhỏ.

Pitfall

COUNT(*) với offset pagination expensive — cân nhắc estimate hoặc bỏ total. Cursor decode tamper → validate signature trong token.

Nói trong 60 giây
  • Offset đơn giản; cursor scale + stable scroll.
  • OFFSET lớn chậm — keyset dùng index.
  • Cursor không jump arbitrary page.
  • Spring Pageable = offset; keyset custom.
  • WMS mobile feed → cursor.

Q6 WebSocket vs SSE — khi nào dùng?

What

WebSocket: full-duplex persistent connection (ws:// upgrade) — client và server gửi anytime. SSE (Server-Sent Events): HTTP long-lived, server push one-way (text/event-stream). Long polling: REST hack — client poll, server hold đến có data.

Why

REST polling 1s interval = waste bandwidth + latency. Push giảm latency cho dashboard WMS task status, conveyor events. SSE đơn giản hơn WebSocket khi chỉ cần server→client.

How
WebSocketSSEREST Polling
DirectionBidirectionalServer → ClientClient pull
Protocolws:// upgradeHTTP streamHTTP request/response
ReconnectManual + heartbeatBrowser autoNatural
Proxy/LBSticky, timeout configStandard HTTPEasy
 
// SSE — Spring Boot
@GetMapping(value = "/events", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ServerSentEvent<OrderEvent>> stream() {
  return orderEventPublisher.getStream()
    .map(e -> ServerSentEvent.builder(e).id(e.getId()).build());
}

// WebSocket — STOMP
@MessageMapping("/task/update")
@SendTo("/topic/tasks")
public TaskUpdate handle(TaskUpdate msg) { return msg; }
When

SSE: live dashboard order status, notification feed — browser native EventSource. WebSocket: WCS control bidirectional, chat, collaborative edit, sub-second PLC feedback loop. Polling: update 30s+ đủ, hoặc fallback behind strict firewall.

When NOT

WebSocket cho one-way notification — SSE đủ, ops đơn giản hơn. SSE cho binary stream — dùng WebSocket. Push khi client chỉ cần data 1 lần — GET đủ. WebSocket không auth JWT standard — cần handshake auth.

Use case

WMS supervisor dashboard: SSE stream pick-task completed events. WCS operator console gửi stop conveyor: WebSocket bidirectional. ERP sync status 5 phút: REST polling OK.

Pitfall

WebSocket qua LB timeout không heartbeat → silent disconnect. SSE không IE legacy — polyfill. Scale SSE/WebSocket cần Redis pub/sub hoặc message broker broadcast.

Nói trong 60 giây
  • SSE = server push one-way, HTTP đơn giản.
  • WebSocket = bidirectional, realtime control.
  • Polling OK latency > 30s.
  • WMS dashboard SSE; WCS control WebSocket.
  • Scale push cần pub/sub backend.

Q7 JWT trong REST API — overview?

What

Client gửi Authorization: Bearer <jwt>; server verify signature + exp → set SecurityContext. JWT stateless — không lookup session DB.

Why

Phù hợp SPA/mobile API và microservices — scale horizontal không shared session.

When

Public REST API, cross-domain. Không lưu token localStorage — prefer HttpOnly cookie qua BFF.

When NOT

Khi cần revoke instant không blacklist — cân nhắc session. Đừng đặt sensitive data trong payload (Base64 readable).

  • Stateless scale — revoke cần blacklist/TTL.
  • Chi tiết → Module 15.

Q8 Authentication vs Authorization — overview?

What

AuthN = "Bạn là ai?" (401). AuthZ = "Bạn được làm gì?" (403). AuthN trước AuthZ trong Filter Chain.

When NOT

Đừng nhầm có JWT = có quyền — vẫn cần @PreAuthorize và object-level check (BOLA).

→ Module 15

RBAC vs ABAC, resource scopes, privilege escalation — Module 15 Q1–Q2.

Q9 Session vs JWT — chọn gì cho REST?

What

Session + cookie: server state, revoke dễ. JWT: stateless, scale dễ, revoke khó hơn.

When

JWT: SPA/mobile API. Session: SSR same-site app cần logout instant.

When NOT

Session in-memory multi-pod không sticky. JWT 7 ngày không refresh.

What

Zero trust: mTLS, JWT pass-through, Client Credentials, gateway token exchange — không trust internal network.

When NOT

Đừng plain HTTP internal. Đừng tin X-User-Id header không signed.

OWASP Top 10

Q11 SQL Injection?

What

Attacker inject SQL qua input không sanitize — concatenate string vào query. Payload ' OR '1'='1 bypass login; ; DROP TABLE destructive (hiếm với prepared statement).

Why

OWASP #1 lịch sử — một lỗi concat SQL = full DB compromise. JPA native query với string concat vẫn vulnerable.

How
// ❌ Vulnerable
String sql = "SELECT * FROM users WHERE name='" + input + "'";

// ✅ PreparedStatement / JPA @Param
@Query("SELECT u FROM User u WHERE u.name = :name")
Optional<User> findByName(@Param("name") String name);
When

Luôn parameterized query. Dynamic sort column: whitelist enum, không concat user input. Least privilege DB user (no DROP).

When NOT

Đừng "escape" thủ công thay prepared statement. Đừng assume ORM 100% safe — native query + concat vẫn lỗi. WAF không thay fix code.

Use case

Search SKU WMS: WHERE sku = :sku parameterized — attacker không inject UNION SELECT password.

Pitfall

ORDER BY ${column} trong MyBatis — SQL injection vector. Second-order injection: store payload, execute later trong report query.

Nói trong 60 giây
  • Concat SQL + user input = injection.
  • Fix: parameterized query, @Param, JPA bind.
  • Native query vẫn phải bind.
  • Least privilege DB user + WAF defense in depth.

Q12 XSS (Cross-Site Scripting)?

What

Attacker inject script chạy trong browser victim — steal cookie/JWT localStorage, keylog, deface. Ba loại: Stored (DB), Reflected (URL param), DOM-based (client JS unsafe).

Why

XSS + JWT localStorage = account takeover. Stored XSS trong WMS comment field → admin mở → script chạy với admin session.

How
LoạiMô tảPhòng chống
StoredScript lưu DBOutput encoding, sanitize input
ReflectedScript trong URL echoValidate input, encode output
DOM-basedJS xử lý URL unsafeAvoid innerHTML, DOMPurify
 
// Thymeleaf auto-escape; CSP header
http.headers(headers -> headers.contentSecurityPolicy(
  "default-src 'self'; script-src 'self'"));
When

Encode output context-aware (HTML, JS, URL). CSP strict script-src 'self'. HttpOnly cookie — JS không đọc session.

When NOT

Đừng lưu JWT localStorage nếu có XSS surface — xem Module 15 Q11. Đừng trust client sanitize only — server encode output. th:utext Thymeleaf bypass escape.

Pitfall

JSON API không XSS nếu Content-Type application/json — browser không execute. XSS risk ở SPA render user HTML. Link Module 15: JWT localStorage + XSS.

Nói trong 60 giây
  • Stored/Reflected/DOM XSS — inject script.
  • Encode output + CSP + sanitize input.
  • JWT localStorage vulnerable XSS → Module 15.
  • HttpOnly cookie cho session token.

Q13 CSRF (Cross-Site Request Forgery)?

What

Attacker lừa browser victim gửi request authenticated tới site đích — browser tự gửi cookie session. Victim không cần click nếu auto-submit form/image.

Why

Cookie-based auth tự attach mọi request cùng domain — attacker exploit từ evil.com. Khác XSS: CSRF không cần inject script vào victim site.

How
User login bank.com (cookie set)
↓ visit evil.com
Hidden form POST bank.com/transfer
↓ browser gửi kèm session cookie → transfer thành công

Spring CsrfFilter: Synchronizer Token Pattern — form kèm CSRF token server validate. SameSite=Strict/Lax cookie giảm risk.

When

Bật CSRF protection cho cookie-session app (form POST/PUT/DELETE). Double-submit cookie hoặc token trong meta tag cho SPA.

When NOT

JWT Bearer header-only API — browser không auto-send → CSRF ít relevant (disable CSRF stateless API OK). Đừng disable CSRF trên cookie-auth app. CORS không chống CSRF.

Use case

Thymeleaf admin WMS: mọi form có th:action + CSRF token auto. SPA + cookie JWT: cần CSRF token header.

Nói trong 60 giây
  • CSRF = browser gửi cookie khi victim visit evil site.
  • Fix: CSRF token, SameSite cookie.
  • Bearer JWT API — CSRF ít risk.
  • CORS ≠ CSRF protection.

Q14 Broken Authentication?

What

OWASP: login/register/password recovery implement sai — brute force, weak session, credential stuffing, predictable session ID, password reset token leak.

Why

Auth là cửa ngõ — broken auth = full account compromise. API login endpoint hay bị bỏ qua rate limit.

How
  • Rate limit login + CAPTCHA sau N fails
  • Credential stuffing: check breached passwords (HIBP k-anonymity)
  • Cookie: HttpOnly, Secure, SameSite
  • Account lockout + notify user
  • MFA cho admin/sensitive ops
@RateLimiter(name = "login", fallbackMethod = "loginFallback")
public AuthResponse login(LoginRequest req) { ... }
When

Mọi production auth endpoint. Lockout exponential backoff. Password policy + bcrypt/argon2.

When NOT

Đừng reveal "user không tồn tại" vs "sai password" — user enumeration. Đừng password reset link không expire. Đừng JWT forever không refresh.

Use case

WMS admin login: 5 fails → lock 15 phút + email alert. Password reset token 1h TTL single-use.

Nói trong 60 giây
  • Rate limit, lockout, MFA, secure cookies.
  • Credential stuffing — check breached passwords.
  • Không user enumeration qua error message.
  • Password hash bcrypt/argon2.

Q15 Insecure Deserialization?

What

Deserialize object từ untrusted input → RCE qua gadget chains. Java ObjectInputStream, Jackson polymorphic defaultTyping, XMLDecoder — vector phổ biến.

Why

Attacker craft byte stream trigger class chain execute arbitrary code — không cần SQLi. Redis/Java cache deserialize user data = critical.

How
// ❌ Không deserialize untrusted binary
ObjectInputStream ois = new ObjectInputStream(input);

// ✅ JSON explicit DTO — no default typing
ObjectMapper mapper = new ObjectMapper();
// @JsonTypeInfo với whitelist class nếu polymorphic cần thiết
When

JSON DTO explicit types cho API. Validate schema. Disable Jackson default typing globally.

When NOT

Java native serialization cho REST API. Accept application/java-serialized-object. Polymorphic deserialize without whitelist.

Pitfall

Log4Shell adjacent: untrusted data trigger unexpected code paths. Spring HTTP Invoker/RMI deprecated vì deserialization risk.

Nói trong 60 giây
  • Untrusted deserialize → RCE gadget chains.
  • Không ObjectInputStream cho API input.
  • Jackson: no default typing, explicit DTO.
  • Whitelist polymorphic types nếu cần.

Q16 OAuth 2.0 flows — overview?

When NOT

Q20 HTTPS / TLS handshake?

What

TLS encrypt transit — handshake negotiate cipher, verify server certificate (CA chain), exchange symmetric session key. TLS 1.3: 1-RTT, forward secrecy mandatory, loại weak ciphers.

Why

Plain HTTP = sniff password/JWT/API key on network. PCI/HIPAA require TLS. mTLS thêm client cert verify — S2S identity (Module 15).

How
Client Hello
↓ cipher suites, TLS version, SNI
Server Hello + Certificate chain
↓ client verify CA + hostname
Key Exchange (ECDHE)
↓ symmetric session key — encrypted app data
HTTP request/response encrypted
When

Mọi production API public. HSTS header force HTTPS. cert-manager/Let's Encrypt auto-renew. Internal service mesh mTLS (Istio STRICT).

When NOT

TLS 1.0/1.1 — disable. Self-signed cert production without trust chain. trustServerCertificate=true JDBC bypass verify. Terminate TLS at gateway rồi HTTP plain to backend without mTLS — risk east-west sniff.

Pitfall

Certificate expire midnight outage — monitor expiry 30 days ahead. Mixed content: HTTPS page load HTTP API — browser block.

Nói trong 60 giây
  • TLS encrypt transit — handshake + cert verify.
  • TLS 1.3, forward secrecy, disable 1.0/1.1.
  • HSTS + auto-renew cert.
  • mTLS for S2S — Module 15.
  • Không trust-all cert production.

Q22 API Key rotation không downtime?

What

Rotate API key mà không gãy client đang dùng key cũ — overlap period accept cả key_v1 và key_v2.

Why

Key leak, employee offboard, compliance periodic rotation — cần quy trình zero-downtime.

How

When

Use case

ERP webhook integration: issue key_v2, partner migrate trong 30 ngày, dashboard show v1 traffic declining.

Nói trong 60 giây
  • Dual-key overlap grace period.
  • Monitor v1 usage → 0 rồi revoke.
  • Log by key_id track migration.
  • Emergency vs scheduled rotation.

Q24 HTTP caching & conditional requests (ETag, Cache-Control, 304) hoạt động thế nào?

What

HTTP caching cho phép client, proxy và CDN tái sử dụng response thay vì gọi lại server — chuẩn hoá trong RFC 9111. Conditional request: client gửi validator đã lưu (ETag qua If-None-Match, Last-Modified qua If-Modified-Since); server so sánh và trả 304 Not Modified (không kèm body) nếu chưa đổi, hoặc 200 OK + body mới nếu đã đổi. Cache-Control quyết định ai được cache, cache bao lâu và có phải revalidate không.

Why

304 tiết kiệm băng thông và latency vì không truyền lại body, đồng thời giảm tải DB/CPU. Ngoài ra If-Match biến ETag thành cơ chế optimistic concurrency chống lost update khi nhiều client cùng sửa một resource. Chỉ method an toàn (safe: GET/HEAD) và idempotent mới nên cache được.

How

↓ gửi If-None-Match: "v3-abc123"
Server so sánh ETag hiện tại với validator
↓ giống → 304 (dùng cache) · khác → 200 + body mới + ETag mới
Client/CDN phục vụ bản cache — không truyền lại body

When

GET resource ít đổi (catalog, config, product detail) → max-age + ETag. Ghi cần chống đè: PUT/PATCH kèm If-Match để trả 412 khi bản client đã cũ. CDN/proxy cache public asset → public kèm s-maxage.

When NOT

Không cache/share response chứa dữ liệu per-user nếu thiếu private và Vary: Authorization. Dữ liệu nhạy cảm (token, PII) → no-store. Đừng nhầm no-cache với no-store: no-cache vẫn lưu nhưng buộc revalidate, no-store mới là không lưu.

Use case

Danh mục sản phẩm e-commerce: ETag + Cache-Control: public, max-age=300 — CDN phục vụ hầu hết request, server chỉ trả body khi dữ liệu thực sự đổi.

Pitfall / Interview trap

Quên Vary → cache trả response của user A cho user B. ETag yếu (W/"...") không đủ an toàn cho ghi. Cache "cũ" sau deploy do max-age dài — đổi tên asset hoặc dùng stale-while-revalidate đúng cách.

Q25 Problem Details (RFC 9457) — chuẩn error response cho REST API?

What

Problem Details (RFC 9457, thay thế RFC 7807) định nghĩa một JSON object machine-readable cho lỗi HTTP, dùng media type application/problem+json. Member chuẩn: type (URI định danh loại lỗi), title (mô tả ngắn, ổn định), status (mã HTTP), detail (giải thích cho occurrence cụ thể), instance (URI của lần lỗi). Có thể mở rộng thêm extension member tuỳ loại lỗi.

Why

Client và nhiều service cần một error contract thống nhất thay vì mỗi endpoint một shape khác nhau. Problem Details cho phép phân nhánh theo type ổn định (không phụ thuộc chuỗi message), đồng thời giữ detail cho người đọc. Lỗi validation nhiều field gom vào extension errors[], mỗi phần tử dùng JSON Pointer chỉ tới field sai.

Deep Dive — Thuật toán Rate Limiting

Q26 Token bucket, leaky bucket hay sliding window — chọn thuật toán rate limiting nào?

What

Token bucket: bucket chứa tối đa C token, nạp token với tốc độ r/giây; mỗi request tiêu 1 token, hết token thì bị chặn. Leaky bucket: request vào queue (bucket), xả ra với tốc độ cố định r; queue đầy thì drop. Fixed window: đếm theo cửa sổ rời rạc. Sliding window log/counter: cửa sổ trượt chính xác (log) hoặc xấp xỉ (counter).

Why

Traffic thật vốn bursty (người dùng click theo cụm). Token bucket tách bạch burst capacity (C) và sustained rate (r) — khớp với cách nhà cung cấp quảng cáo "100 RPS sustained, burst 200". Leaky bucket làm phẳng output, hợp downstream không chịu được spike (payment gateway, DB legacy, SMS).

// Token bucket — tính token động theo timestamp, không cần job nền
boolean tryAcquire(long nowNanos) {
  double refill = (nowNanos - lastRefillNanos) / 1e9 * ratePerSec;
  tokens = Math.min(capacity, tokens + refill);
  lastRefillNanos = nowNanos;
  if (tokens >= 1.0) { tokens -= 1.0; return true; }
  return false; // → 429 Too Many Requests + Retry-After
}

When

Token bucket làm mặc định cho public API (cho phép burst hợp lệ). Leaky bucket khi downstream phải nhận rate đều. Sliding window counter cho rate limit phân tán chính xác hơn trên gateway. Luôn kèm 429 + Retry-After (RFC 6585) và header X-RateLimit-*.

When NOT

Không self-limit trong bộ nhớ mỗi pod rồi tưởng đã giới hạn toàn cụm — nhiều worker sẽ "burst-collide"; cần store chung (Redis). Không dùng fixed window cho rate limit bảo mật vì kẻ tấn công khai thác biên cửa sổ (tới 2× limit). Đừng đặt limit quá khớp khiến burst hợp lệ bị chặn oan.

Use case

Gateway: token bucket per API key (100 req/s, burst 200). Login endpoint: sliding window strict (10/phút/IP). Job gọi SMS provider giới hạn cứng 5/s → leaky bucket làm phẳng.

Pitfall / Interview trap

429 không kèm Retry-After → client retry ngay (thundering herd). Reset theo đồng hồ server nhưng node lệch giờ → dùng timestamp tập trung. Nhầm key scope (IP vs user vs endpoint) làm NAT chặn nhầm cả một toà nhà.
