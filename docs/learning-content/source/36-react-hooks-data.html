React Hooks, Quản lý State & Data Fetching

Hooks và quản lý dữ liệu ở FE: dependency array, cleanup chống race, memo hoá, custom hook, Context, thư viện state và server-state cache.

Hook cơ bản — state, effect, memo hoá

Q1 useState — khi nào bắt buộc dùng updater function, và bẫy stale closure là gì?

What

useState trả về cặp [value, setValue]; setValue nhận giá trị mới hoặc một updater function dạng (prev) => next. React gom nhiều lần set state trong cùng một lượt xử lý thành một lần re-render (automatic batching), nên update nào phụ thuộc giá trị cũ thì buộc phải dùng updater function.

Why

Mỗi lần render tạo ra một closure mới đóng gói giá trị state tại thời điểm render đó. Nếu bạn cập nhật bằng setCount(count + 1) hai lần liên tiếp, cả hai đều đọc cùng một count cũ nên kết quả chỉ tăng 1 — đây là stale closure. Vấn đề nặng hơn khi closure sống lâu: callback trong setTimeout, setInterval, subscription hay promise resolve sau nhiều giây vẫn giữ giá trị state cũ; ghi state từ đó sẽ ghi đè kết quả của những update mới hơn. Updater function không đọc biến từ closure mà nhận prev do React truyền vào, nên luôn đúng với state mới nhất.

How
Event handler gọi setCount 2 lần
↓ React gom vào cùng một batch
setCount(count + 1) — cả hai đọc count = 0
setCount(c => c + 1) — nhận prev tuần tự
↓
Kết quả: 1 (mất update)
Kết quả: 2, re-render 1 lần

Cùng cơ chế đó áp dụng cho object/array: setUser(u => ({ ...u, name })) để không mất các field khác, vì React thay thế toàn bộ giá trị chứ không merge như this.setState.

When

Bắt buộc dùng updater function khi giá trị mới phụ thuộc giá trị cũ: counter, toggle, thêm/xoá item trong list, accumulate kết quả từ nhiều nguồn. Cũng dùng khi hàm set state được gọi từ useEffect, setInterval hoặc callback async — nơi closure có thể đã lỗi thời.

When NOT

Không cần updater khi set giá trị độc lập (setOpen(true), setName(e.target.value)). Đừng biến mọi state thành một object khổng lồ rồi set từng field bằng spread — đó là dấu hiệu nên dùng useReducer. Và đừng lưu giá trị dẫn xuất (derived) vào state: nếu tính được từ state/props thì tính ngay khi render, lưu vào state sẽ gây lệch dữ liệu.

// LỖI: stale closure — chỉ tăng 1 dù gọi 2 lần
const [count, setCount] = useState(0);
setCount(count + 1);
setCount(count + 1);

// ĐÚNG: updater function + batching
setCount(c => c + 1);
setCount(c => c + 1); // = 2, chỉ 1 lần re-render

// ĐÚNG: object state — spread giữ field cũ
const [form, setForm] = useState({ name: '', city: '' });
setForm(prev => ({ ...prev, name: 'An' }));

// LỖI: closure trong interval giữ count cũ mãi mãi
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, []); // thiếu dep -> count bị "đóng băng" ở 0
Use case

Nút "Thêm vào giỏ": setCart(prev => [...prev, item]) đúng ngay cả khi user bấm nhanh nhiều lần trong 50ms — mọi lần bấm đều được nối tiếp thay vì ghi đè lên nhau.

Pitfall / Interview trap

Hai bẫy hay bị hỏi: (1) mutate trực tiếp — items.push(x); setItems(items) không tạo reference mới nên React bail out và UI không đổi; phải tạo mảng mới. (2) useState(prop) chỉ dùng prop làm giá trị khởi tạo, các lần render sau prop đổi sẽ không cập nhật state — cần reset bằng cách đổi key của component.

Nói trong 60 giây
  • useState trả cặp value/setter; setter nhận giá trị hoặc updater function.
  • Stale closure: closure giữ state của lần render cũ — set dựa giá trị cũ thì mất update.
  • Updater (prev) => next luôn nhận state mới nhất, an toàn trong interval/async.
  • React 18 batch mọi lần set trong cùng lượt xử lý thành 1 re-render.
  • Object/array phải spread tạo reference mới, không mutate tại chỗ.

Q2 useEffect — dependency array đúng cách, cleanup, và chống race condition khi fetch?

What

useEffect chạy sau khi React commit DOM. Dependency array quyết định vòng đời: [] chạy một lần sau mount, [a, b] chạy lại khi a hoặc b đổi (so sánh bằng Object.is), bỏ trống thì chạy sau mọi render. Hàm cleanup được trả về sẽ chạy trước lần effect kế tiếp và khi component unmount.

Why

Effect dùng để đồng bộ với hệ thống ngoài React (network, timer, DOM, subscription). Với fetch, hai lỗi kinh điển: thiếu dependency khiến effect đóng băng giá trị cũ (stale closure), và race condition — user đổi filter nhanh, request cũ về sau request mới rồi ghi đè state, UI hiển thị dữ liệu của filter đã bị bỏ. Cleanup là cơ chế chuẩn để huỷ request cũ hoặc unsubscribe, và đảm bảo không set state sau khi component đã unmount.

How
userId = 1 → effect chạy, gọi fetch A
↓ user đổi userId = 2 (A chưa xong)
cleanup: controller.abort() cho A
effect mới: fetch B
↓
Chỉ B ghi state — không còn ghi đè

Thêm một lớp bảo vệ nữa là cờ active (hoặc bỏ qua kết quả nếu signal.aborted): abort không phải lúc nào cũng chặn kịp callback đã resolve.

When

Dùng effect khi cần đồng bộ với thứ nằm ngoài React: gọi API, subscribe store/websocket, gắn event listener trên window, khởi tạo timer, đo DOM, gửi analytics khi prop đổi. Nguyên tắc: mỗi giá trị dùng trong effect mà đến từ props/state phải có mặt trong dependency array.

When NOT

Không dùng effect để: (1) tính giá trị dẫn xuất — tính ngay trong render; (2) xử lý sự kiện — viết trong event handler; (3) reset state khi prop đổi — dùng key; (4) chain các effect với nhau để truyền dữ liệu — set state ngay trong event handler. Ngoài ra, nếu dữ liệu là server state, useEffect + fetch thủ công là tự làm lại những gì TanStack Query đã làm tốt hơn.

useEffect(() => {
  const controller = new AbortController();
  let active = true;

  fetch(`/api/orders?status=${status}`, { signal: controller.signal })
    .then(r => r.json())
    .then(data => { if (active) setOrders(data); })
    .catch(err => {
      if (err.name !== 'AbortError') setError(err);
    });

  return () => { active = false; controller.abort(); };
}, [status]);
Use case

Ô search đổi theo từng ký tự: gõ "abc" rồi "abcd" trong 200ms — abort khiến request của "abc" bị huỷ, tránh hiển thị kết quả của từ khoá ngắn hơn lên màn hình.

Pitfall / Interview trap

Trong React StrictMode ở môi trường dev, mỗi effect chạy 2 lần (mount → unmount → mount) để phát hiện effect thiếu cleanup. Đây là hành vi cố ý, không phải bug — cách xử lý là viết cleanup đầy đủ, tuyệt đối không "chữa" bằng cách bỏ dependency array hay thêm cờ ref chống chạy hai lần. Cũng lưu ý linter exhaustive-deps cảnh báo khi bạn dùng object/function literal trong deps — chúng đổi reference mỗi render và gây vòng lặp vô hạn.

Nói trong 60 giây
  • Effect chạy sau commit; deps quyết định chạy lại, cleanup chạy trước lần sau và khi unmount.
  • Race condition khi fetch: AbortController + cờ active để request cũ không ghi state.
  • Effect chỉ để đồng bộ với hệ ngoài React — không dùng cho derived state hay event handling.
  • StrictMode dev chạy effect 2 lần để bạn viết cleanup tử tế.
  • Object/function literal trong deps là nguyên nhân loop phổ biến nhất.

Q3 useMemo / useCallback — khi nào thật sự cần và cái giá của việc lạm dụng?

What

useMemo cache kết quả của một phép tính giữa các lần render; useCallback cache chính function reference đó (useCallback(fn, deps) tương đương useMemo(() => fn, deps)). Cả hai chỉ có hiệu lực khi dependency array không đổi — dependency đổi thì giá trị được tính lại.

Why

Mỗi lần render, mọi biến và function literal trong component được tạo mới. Điều đó chỉ gây hại trong ba trường hợp: (1) phép tính thực sự đắt (sort/filter mảng vài nghìn phần tử, xử lý ảnh) bị chạy lại vô ích; (2) function/object truyền xuống component bọc React.memo làm prop đổi reference mỗi render khiến memo vô hiệu; (3) function làm dependency của effect khác gây chạy lại liên tục. Chỉ khi rơi vào các trường hợp này thì memo hoá mới có lợi.

How
Parent re-render
↓
Không memo: prop mới → React.memo child re-render
useCallback/useMemo: reference giữ nguyên → child bail out
↓
Chi phí: cấp phát cache + so sánh deps mỗi render

Chi phí của memo hoá không bằng 0: React phải giữ closure và mảng deps qua các render, đồng thời so sánh từng phần tử deps bằng Object.is. Với phép tính rẻ, chi phí này còn lớn hơn việc tính lại.

When

Dùng useMemo khi phép tính rõ ràng đắt: lọc/sắp xếp danh sách lớn, build cây dữ liệu, parse chuỗi lớn; hoặc khi tạo object/array làm dependency cho effect. Dùng useCallback khi truyền handler xuống component đã bọc React.memo, hoặc khi handler là dep của một effect, hoặc khi handler được truyền vào custom hook cần ổn định reference.

When NOT

Không memo hoá mặc định mọi thứ: useCallback cho một child không bọc React.memo là vô nghĩa vì child vẫn re-render cùng parent. Không dùng useMemo cho phép so sánh vài phần tử, cho chuỗi format ngắn, hay để "tránh tính lại" một biểu thức rẻ — code khó đọc hơn mà không nhanh hơn. Khi đã bật React Compiler, phần lớn memo hoá thủ công trở nên dư thừa.

function OrderTable({ orders, keyword }: Props) {
  // ĐẮT: chạy lại mỗi render nếu không memo -> cần useMemo
  const filtered = useMemo(
    () => orders.filter(o => o.sku.includes(keyword)),
    [orders, keyword],
  );

  // cần useCallback vì RowRow được React.memo và nhận prop này
  const handleSelect = useCallback((id: string) => {
    onSelect(id);
  }, [onSelect]);

  return filtered.map(o => <RowRow key={o.id} row={o} onSelect={handleSelect} />);
}

const RowRow = React.memo(function RowRow({ row, onSelect }: RowProps) { /* ... */ });
Use case

Bảng 5.000 dòng có ô tìm kiếm: useMemo cho bước filter sắp xếp giúp mỗi lần user mở dropdown (state khác đổi) không phải lọc lại toàn bộ mảng.

Pitfall / Interview trap

Câu hỏi bẫy: "useMemo có đảm bảo giá trị được cache không?" — Không. React có quyền "quên" cache trong một số điều kiện (ví dụ unmount, hoặc trong tương lai với các tính năng như offscreen) nên useMemo không phải nơi lưu side effect hay dữ liệu cần đảm bảo tồn tại; đừng phụ thuộc nó để tránh chạy side effect. Một bẫy khác: memo hoá nhưng truyền deps thiếu — giá trị cache vĩnh viễn sai và cực khó debug.

Nói trong 60 giây
  • useMemo cache giá trị, useCallback cache function reference — cùng bản chất.
  • Chỉ cần khi: tính toán đắt, prop cho React.memo, hoặc làm dep cho effect.
  • useCallback vô nghĩa nếu child không memo — parent re-render vẫn kéo child theo.
  • Memo hoá tốn bộ nhớ và so sánh deps — lạm dụng làm code rối mà chậm hơn.
  • Cache của useMemo không được đảm bảo — không dùng để chứa side effect.

Q4 useRef — giữ giá trị qua các render vs truy cập DOM, và vì sao nó không gây re-render?

What

useRef(initial) trả về một object bền vững có đúng một field current. Gán ref vào JSX (ref={myRef}) thì React ghi element DOM vào current sau khi mount. Ref tồn tại xuyên suốt vòng đời component và thay đổi current không kích hoạt re-render.

Why

State là dữ liệu thuộc về output render: đổi state thì phải render lại để UI khớp. Nhưng nhiều dữ liệu không xuất hiện trên UI — id của setInterval, cờ isFirstRender, giá trị previous của prop, thời điểm render cuối, đối tượng WebSocket. Nếu đặt chúng vào state, mỗi thay đổi gây một vòng render thừa. Ngược lại, vì ref là object ổn định, bạn có thể đọc nó trong closure async mà luôn nhận giá trị mới nhất — đây là điểm khác biệt cốt lõi với closure của state.

How
render #1 — useRef tạo { current: 0 }
↓ gán lại cùng object, không cấp phát mới
render #2 — vẫn cùng object ref
ref.current++ → không re-render
↓ khi cần UI khớp thì mới gọi setState
render #N — đọc được mọi thay đổi trước đó

Với DOM: React gán ref.current = node sau commit và đặt về null khi unmount — vì vậy đọc ref.current lúc render lần đầu sẽ là null.

When

Truy cập DOM imperative: input.focus(), scrollIntoView, video.play(), lấy kích thước phần tử. Giữ giá trị mutable không đổi UI: timer id, cờ chống double-submit, counter số lần render, giữ giá trị trước đó (usePrevious), giữ instance của thư viện bên thứ ba (chart, map, editor).

When NOT

Không dùng ref thay state cho dữ liệu hiển thị: đổi ref.current không làm UI cập nhật, component sẽ lệch với dữ liệu. Không đọc/ghi ref trong thân render (ngoại lệ duy nhất là lazy init if (ref.current === null)) vì render phải là pure và có thể bị React gọi nhiều lần hoặc bỏ dở trong concurrent rendering. Với DOM, ưu tiên cách khai báo (state, conditional render) trước khi chuyển sang thao tác imperative.

// 1) DOM ref
const inputRef = useRef<HTMLInputElement>(null);
useEffect(() => { inputRef.current?.focus(); }, []);

// 2) giá trị mutable, không gây re-render
const rendered = useRef(0);
rendered.current += 1;

// 3) giữ giá trị trước đó của prop
function usePrevious<T>(value: T) {
  const ref = useRef<T | undefined>(undefined);
  useEffect(() => { ref.current = value; }, [value]);
  return ref.current;
}

// 4) timer id — sống qua mọi render, không cần state
const timerId = useRef<number | null>(null);
Use case

Cờ chống gửi trùng: if (submitting.current) return; ngay đầu handler. So với state isSubmitting, cờ ref chặn được lần bấm thứ hai ngay lập tức, trước khi React kịp render lại và cập nhật giá trị state.

Pitfall / Interview trap

Đừng nói "ref là biến instance của class" — điểm khác biệt là ref không tham gia vào luồng dữ liệu một chiều: React không theo dõi nó, nên đọc nó trong render phá vỡ tính pure. Bẫy tinh tế: gán ref={(node) => ...} callback chạy lại mỗi lần element đổi, còn object ref thì ổn định. Và useRef() khác createRef() (tạo object mới mỗi render) lẫn useState (đổi thì re-render).

Nói trong 60 giây
  • useRef trả object ổn định với field current, sống qua mọi render.
  • Đổi current không re-render — dùng cho dữ liệu không thuộc UI.
  • Gắn vào JSX để lấy DOM node, gán sau commit, null khi unmount.
  • Dùng cho timer id, cờ chống double-submit, giá trị previous, instance lib.
  • Không dùng thay state cho dữ liệu hiển thị; không đọc/ghi ref trong render.

Q5 useReducer — khi nào tốt hơn useState, và dùng làm state machine cho form/flow?

What

useReducer(reducer, initialArg) trả về [state, dispatch]. Mọi thay đổi state đi qua một hàm thuần reducer(state, action) => newState, được gọi bằng dispatch({ type: 'ADD_ITEM', payload }). Thay vì nhiều setter rải rác, toàn bộ luật chuyển trạng thái nằm trong một chỗ.

Why

useReducer thắng useState khi: state là nhiều field liên quan và một action phải cập nhật nhiều field cùng lúc (set 5 state riêng lẻ dễ rơi vào trạng thái trung gian không hợp lệ); transition tiếp theo phụ thuộc cả state hiện tại lẫn action; cần chặn transition sai (ví dụ không cho submit khi chưa validate); hoặc muốn test logic mà không cần render component. Vì reducer là pure function, bạn test được toàn bộ luật nghiệp vụ bằng unit test thuần tuý.

How
dispatch({ type: 'NEXT_STEP' })
↓
reducer(state, action) — switch theo type
transition không hợp lệ bị bỏ qua / throw
↓
state mới (step 2, touched = true) → re-render

Reducer phải trả về object mới, không mutate state cũ — React so sánh reference để quyết định re-render, và mutating state phá vỡ mọi giả định của concurrent rendering.

When

Form wizard nhiều bước: state gồm step, values, errors, touched, isSubmitting. Flow có state machine: upload (idle → uploading → success → error), checkout, editor undo/redo. Cũng dùng khi cần truyền dispatch xuống component con thay vì nhiều callback setState khác nhau.

When NOT

Với 1–2 giá trị độc lập (isOpen, keyword) thì useReducer chỉ thêm boilerplate. Không dùng reducer nội bộ component để giả làm global store — nếu state cần chia sẻ giữa nhiều nhánh cây, đó là bài toán Context hoặc thư viện state. Cũng đừng gọi API hay đọc localStorage bên trong reducer: reducer phải pure, mọi side effect đặt ở ngoài (event handler hoặc effect).

type State = { step: number; values: Record<string, string>; errors: string[]; submitting: boolean };
type Action =
  | { type: 'SET_FIELD'; name: string; value: string }
  | { type: 'NEXT_STEP' }
  | { type: 'SUBMIT_START' }
  | { type: 'SUBMIT_FAILED'; errors: string[] };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case 'SET_FIELD':
      return { ...state, values: { ...state.values, [action.name]: action.value } };
    case 'NEXT_STEP': {
      const errors = validateStep(state.step, state.values);
      if (errors.length) return { ...state, errors };
      return { ...state, step: state.step + 1, errors: [] };
    }
    case 'SUBMIT_START': return { ...state, submitting: true };
    case 'SUBMIT_FAILED': return { ...state, submitting: false, errors: action.errors };
  }
}

const [state, dispatch] = useReducer(reducer, { step: 0, values: {}, errors: [], submitting: false });
Use case

Form tạo đơn 3 bước: NEXT_STEP chỉ tăng step khi validateStep không có lỗi — nhờ vậy không bao giờ tồn tại trạng thái "đang ở bước 3 nhưng dữ liệu bước 1 chưa hợp lệ", thứ rất dễ xảy ra khi dùng 5 state riêng.

Pitfall / Interview trap

Bẫy hay bị hỏi: hàm reducer chạy hai lần trong StrictMode dev — nếu bạn viết side effect (log, gọi API, mutate biến ngoài) trong reducer thì nó chạy trùng. Một bẫy khác: mutate state.values rồi trả state cũ khiến React bail out, UI đứng im dù logic "chạy đúng". Lưu ý cuối: useReducer không thay thế Redux — nó chỉ gom logic state của một component (hoặc một subtree qua Context).

Nói trong 60 giây
  • useReducer = state + dispatch + pure reducer; transition tập trung một chỗ.
  • Tốt hơn useState khi nhiều field liên quan, một action đổi nhiều field, cần chặn transition sai.
  • Reducer pure và testable — unit test không cần render.
  • Luôn trả object mới; side effect để ngoài reducer.
  • 1–2 giá trị độc lập thì useState vẫn gọn hơn.

Q6 Custom hook — nguyên tắc tách logic, chia sẻ logic khác chia sẻ state thế nào?

What

Custom hook là một function tên bắt đầu bằng use và có thể gọi các hook khác bên trong. Nó đóng gói logic (state + effect + cách phối hợp) thành đơn vị tái sử dụng. Điểm cần nhớ: mỗi lần gọi custom hook tạo ra một instance state riêng biệt — hai component cùng gọi useCounter() sẽ có hai biến đếm độc lập.

Why

Custom hook giải quyết vấn đề tái sử dụng hành vi có trạng thái — thứ mà HOC và render props làm được nhưng rườm rà (wrapper hell, prop name collision). Vì logic tách khỏi UI, bạn test được bằng renderHook mà không cần dựng giao diện, và component trở về đúng vai trò: mô tả giao diện. Cái được chia sẻ là cách xử lý, không phải chính dữ liệu.

How
useDebounce(value, 300ms)
↓ mỗi component gọi hook = instance state riêng
SearchBox: timer + debounced riêng
FilterBar: timer + debounced riêng
↓
Cùng đoạn logic, không chia sẻ state

Muốn chia sẻ state giữa nhiều component thì phải nâng state lên component cha, đưa vào Context, hoặc dùng store — custom hook chỉ là lớp đóng gói logic tái dùng.

When

Khi một cụm logic có state/effect bị lặp ở 2–3 nơi trở lên: debounce ô search, phân trang, fetch dữ liệu có loading/error, form field validation, theo dõi kích thước cửa sổ, đồng bộ state với localStorage. Cũng nên tách khi logic làm component phình quá dài và trộn nhiều mối quan tâm.

When NOT

Không cần custom hook nếu đó chỉ là hàm thuần không dùng hook nào — viết util function bình thường (formatCurrency, groupBy) sẽ dễ test và không bị ràng buộc quy tắc hook. Cũng đừng tạo hook chỉ để bọc một useState đơn lẻ — abstraction không mang lại giá trị, chỉ thêm một tầng gián tiếp phải nhảy file khi đọc code.

function useDebounce<T>(value: T, delay = 300): T {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // cleanup: huỷ timer mỗi lần value đổi
  }, [value, delay]);

  return debounced;
}

function usePagination(total: number, pageSize = 20) {
  const [page, setPage] = useState(1);
  const pageCount = useMemo(() => Math.ceil(total / pageSize), [total, pageSize]);

  const next = useCallback(() => setPage(p => Math.min(p + 1, pageCount)), [pageCount]);

  return { page, pageCount, next, setPage };
}

// dùng trong component — state của hook là riêng cho component này
const debouncedKeyword = useDebounce(keyword, 400);
const { page, pageCount, next } = usePagination(orders.length);
Use case

useDebounce(keyword, 400) cắm thẳng vào query key của TanStack Query: user gõ liên tục nhưng chỉ có một request cho giá trị đã ổn định — kết hợp debounce với cache cho trải nghiệm search mượt.

Pitfall / Interview trap

Ba câu trả lời sai thường gặp: (1) "custom hook chia sẻ state giữa các component" — sai, nó chia sẻ logic; (2) gọi custom hook có điều kiện trong if/loop — vi phạm Rules of Hooks; (3) dùng custom hook để che một useEffect phức tạp nhưng không đặt tên rõ — hook nên có tên mô tả đúng việc nó làm. Thêm nữa: mọi hook bên trong custom hook cũng phải tuân thủ deps đầy đủ, và state trong hook bị reset khi component cha đổi key.

Nói trong 60 giây
  • Custom hook = function tên use..., gọi hook khác; chia sẻ logic, không chia sẻ state.
  • Mỗi lần gọi là một instance state riêng — như useState đặt cạnh nhau.
  • Lợi ích: tái sử dụng hành vi có state, tách UI khỏi logic, test bằng renderHook.
  • Hàm thuần không dùng hook thì viết util, đừng bọc thành hook.
  • Vẫn phải tuân Rules of Hooks và deps đầy đủ bên trong.

Chia sẻ state toàn cục & server state

Q7 Context — khi nào thay thế props drilling, vì sao re-render cả cây và cách giảm?

What

Context cho phép truyền dữ liệu xuống bất kỳ độ sâu nào trong cây mà không phải đẩy prop qua từng tầng trung gian. createContext(defaultValue) tạo context; Provider value={...} cung cấp giá trị; useContext(Ctx) ở component con đọc giá trị mới nhất từ Provider gần nhất phía trên.

Why

Vấn đề của props drilling không phải là gõ nhiều mà là coupling: component tầng giữa buộc phải biết và chuyển tiếp prop mà nó không dùng, nên mọi thay đổi chữ ký prop lan khắp cây. Context cắt bỏ tầng trung gian đó. Nhưng cái giá là: khi value của Provider đổi, mọi component gọi useContext trên context đó đều re-render, kể cả khi chúng chỉ cần một phần nhỏ của value — React không làm so sánh từng phần như selector của store.

How
Provider value đổi (object mới)
↓ không có selector — so sánh bằng reference
Mọi useContext(Ctx) re-render
Provider tách nhỏ: chỉ consumer của context đó re-render
↓
Memo component con + useMemo cho value → giảm tải

Bốn cách giảm: (1) tách context theo tần suất thay đổi — ví dụ ThemeContext (ít đổi) tách khỏi UserContext; (2) tách state và dispatch thành hai context để component chỉ dispatch không bị re-render khi state đổi; (3) memo hoá value bằng useMemo/useCallback để object không đổi reference mỗi render; (4) chia nhỏ component — bọc phần con trong React.memo, hoặc dùng thư viện có selector (ví dụ use-context-selector) hay store ngoài React.

When

Dữ liệu mang tính "môi trường", ít thay đổi và được nhiều nơi đọc: theme (light/dark), locale/i18n, user đang đăng nhập, quyền hạn, feature flag, instance của thư viện (router, query client, toast). Cũng phù hợp khi giá trị đổi rất ít (gần như một lần lúc mount).

When NOT

Không dùng Context làm state manager cho dữ liệu thay đổi nhanh theo từng ký tự gõ phím hoặc cập nhật liên tục: mỗi lần value đổi, toàn bộ consumer re-render, và trong cây lớn điều này đắt hơn props drilling. Khi chỉ có 1–2 tầng trung gian thì truyền prop trực tiếp rõ ràng hơn. Và dữ liệu đến từ server thì thuộc về query cache, không phải Context.

// Tách 2 context: state đổi thường xuyên, dispatch ổn định
const StateCtx = createContext<CartState | null>(null);
const DispatchCtx = createContext<Dispatch<CartAction> | null>(null);

export function CartProvider({ children }: { children: ReactNode }) {
  const [state, dispatch] = useReducer(cartReducer, initialCart);

  return (
    <DispatchCtx.Provider value={dispatch}>
      <StateCtx.Provider value={state}>
        {children}
      </StateCtx.Provider>
    </DispatchCtx.Provider>
  );
}

// Component chỉ gửi action -> không re-render khi cart đổi
export function AddToCartButton({ id }: { id: string }) {
  const dispatch = useContext(DispatchCtx)!;
  return <button onClick={() => dispatch({ type: 'ADD', id })}>Thêm</button>;
}

export function useCartState() {
  const ctx = useContext(StateCtx);
  if (!ctx) throw new Error('useCartState must be used inside CartProvider');
  return ctx;
}
Use case

App có dark mode, i18n và user session: gộp ba thứ vào một Provider chung sẽ khiến đổi theme làm re-render cả những component chỉ đọc user. Tách ba context riêng giới hạn phạm vi re-render đúng bằng số component thật sự quan tâm đến theme.

Pitfall / Interview trap

Bẫy phổ biến nhất: <Ctx.Provider value={{ user, setUser }}> — object literal mới mỗi render khiến mọi consumer re-render kể cả khi user không đổi. Phải memo: const value = useMemo(() => ({ user, setUser }), [user]). Bẫy khác: bọc Provider quá cao trong cây khiến phạm vi re-render rộng không cần thiết; và lưu ý defaultValue của createContext chỉ dùng khi không có Provider — nó không phải giá trị khởi tạo state.

Nói trong 60 giây
  • Context giải bài toán props drilling và coupling ở tầng trung gian.
  • value đổi → mọi consumer re-render, không có selector như store.
  • Giảm tải: tách context theo tần suất đổi, tách state/dispatch, useMemo cho value, memo component con.
  • Hợp cho theme, locale, auth, feature flag, instance thư viện.
  • Dữ liệu đổi nhanh hoặc server state thì không dùng Context.

Q8 State toàn cục — Redux Toolkit hay Zustand hay Context, và khi nào KHÔNG cần thư viện?

What

Ba lựa chọn phổ biến khác nhau về bản chất: Redux Toolkit là store tập trung với action/reducer, middleware, devtools và time-travel; Zustand là store nhỏ gọn dạng hook, component subscribe theo selector nên chỉ re-render khi phần state được chọn thay đổi; Context là cơ chế built-in của React, không có selector nên re-render toàn bộ consumer.

Why

Tiêu chí chọn nên bám vào ba câu hỏi: state có được nhiều vùng xa nhau trong cây dùng chung không? tần suất cập nhật cao hay thấp? nhóm cần gì ở công cụ (devtools, middleware, persist, testability)? Redux Toolkit đáng dùng khi logic state phức tạp, có nhiều luồng async đan xen, đội ngũ đông cần quy ước thống nhất và cần debug lịch sử action. Zustand phù hợp khi cần store gọn, ít boilerplate, cập nhật tần suất cao và muốn tránh re-render thừa. Context chỉ nên dùng cho dữ liệu ít đổi.

How

So sánh nhanh trước khi chọn:

When

Chọn Redux Toolkit khi có nhiều feature chia sẻ state, cần undo/redo hoặc audit chuỗi action, cần middleware cho logging/analytics, hoặc cần truy cập store từ ngoài React. Chọn Zustand khi state toàn cục vừa phải (giỏ hàng, filter toàn app, trạng thái player), ưu tiên ít code và re-render tối thiểu.

When NOT

Không cần thư viện state khi: (1) state chỉ dùng trong một component hoặc một nhánh nhỏ — useState/useReducer là đủ; (2) dữ liệu đến từ API — dùng query library, không nhân bản server state vào store (đây là nguyên nhân số một của bug dữ liệu lệch); (3) chỉ có theme/locale/auth — Context là đủ; (4) state là URL — dùng search params của router thay vì store, để link chia sẻ được và back/forward hoạt động.

// Zustand: store gọn, subscribe theo selector
import { create } from 'zustand';

interface CartStore { items: Item[]; add: (i: Item) => void }

export const useCart = create<CartStore>((set) => ({
  items: [],
  add: (item) => set(s => ({ items: [...s.items, item] })),
}));

// component chỉ re-render khi items đổi
const items = useCart(s => s.items);

// Redux Toolkit: slice + action, devtools có sẵn
const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] as Item[] },
  reducers: {
    added(state, action: PayloadAction<Item>) {
      state.items.push(action.payload); // Immer cho phép "mutate" an toàn
    },
  },
});
Use case

Ứng dụng bán hàng: giỏ hàng + filter toàn cục + trạng thái player dùng Zustand (cập nhật nhanh, ít re-render); danh mục sản phẩm và đơn hàng dùng TanStack Query; chỉ user session dùng Context. Ba loại state, ba công cụ khác nhau, không ép tất cả vào một store.

Pitfall / Interview trap

Câu trả lời bị trừ điểm: "dự án nào cũng phải có Redux". Hãy nói rõ Context không phải state manager — nó là cơ chế truyền dữ liệu, không có selector nên không phù hợp cho state đổi liên tục. Trap về Zustand: chọn cả object từ store (useCart(s => ({ items: s.items, total: s.total }))) trả về object mới mỗi lần nên gây re-render thừa — phải dùng selector trả về primitive hoặc useShallow. Và nhớ: mọi state toàn cục đều là global mutable state — càng ít càng dễ debug.

Nói trong 60 giây
  • Nguyên tắc: server state → query library, UI state → useState/useReducer, ít đổi chia sẻ → Context.
  • Redux Toolkit: store tập trung, devtools, middleware, phù hợp app lớn nhiều luồng.
  • Zustand: gọn, selector theo hook, ít re-render, hợp app vừa và state cập nhật nhanh.
  • Context không có selector — không dùng cho state đổi liên tục.
  • Khi nào không cần thư viện: state cục bộ, dữ liệu API, state trên URL.

Server state, trạng thái UI & xử lý lỗi

Q9 Server state khác client state thế nào? TanStack Query — cache key, staleTime, invalidation, retry, dedupe?

What

Server state là dữ liệu thuộc sở hữu của backend: bất đồng bộ, có thể lỗi thời bất cứ lúc nào, nhiều component cùng cần, và bạn không phải nguồn chân lý. Client state là trạng thái giao diện do app kiểm soát: modal đang mở, bước form hiện tại, filter đã chọn. Hai loại này cần công cụ khác nhau — query library cho loại đầu, useState/store cho loại sau.

Why

Nếu tự fetch bằng useEffect, bạn phải tự làm: loading/error state cho từng chỗ gọi, cache để hai component không gọi trùng, chống race condition, retry, refetch khi cửa sổ được focus lại, invalidate sau khi mutate. Chép thủ công những thứ đó ở hàng chục component là nguồn bug lớn nhất của app React. Điểm cốt lõi cần nhớ khái niệm: stale — dữ liệu trong cache vẫn dùng được ngay (instant) nhưng có thể đã cũ, còn inactive là dữ liệu không còn component nào dùng và sẽ bị thu hồi sau gcTime.

How
useQuery({ queryKey: ['orders', filters] })
↓ key là danh tính của dữ liệu, dạng mảng có thứ tự
Cache hit + còn fresh → trả ngay
Cache hit + stale → trả dữ liệu cũ rồi refetch nền
Miss → fetch
↓ hai component cùng key, cùng lúc
Dedupe thành một request, chia sẻ kết quả

Cơ chế chính: queryKey là danh tính dữ liệu — mọi tham số ảnh hưởng kết quả phải nằm trong key (['orders', { status, page }]). staleTime là khoảng thời gian dữ liệu còn được coi là mới; trong khoảng này không refetch. gcTime (trước đây là cacheTime) là thời gian giữ dữ liệu sau khi không còn ai dùng. invalidateQueries đánh dấu dữ liệu cũ để refetch — gọi sau mutation là cách đồng bộ phổ biến nhất. Mỗi query có một queryFn; nhiều query cùng key đang chạy sẽ được dedupe thành một request. retry mặc định 3 lần với exponential backoff, chỉ tự retry lỗi mạng/5xx (không retry 4xx).

When

Dùng query library cho mọi dữ liệu đến từ API: danh sách có phân trang, chi tiết bản ghi, autocomplete, dữ liệu dashboard. Kèm useMutation cho thao tác ghi, rồi invalidate các key bị ảnh hưởng. Với staleTime: dữ liệu ít đổi (danh mục, cấu hình) đặt cao (5–30 phút); dữ liệu cần tươi (số dư, trạng thái đơn) đặt thấp (0–30 giây).

When NOT

Không dùng query library cho client state: trạng thái modal, bước của wizard, giá trị input đang gõ — đưa chúng vào cache chỉ gây khó hiểu. Không bật refetchOnWindowFocus cho mọi query trong app nội bộ nặng (gây bão request) — nên tinh chỉnh theo query. Và đừng chọn staleTime: 0 mặc định kèm refetch liên tục: mỗi lần mount, focus, reconnect lại có request, dễ trông như lỗi hiệu năng.

function useOrders(filters: Filters) {
  return useQuery({
    // key = danh tính dữ liệu; mọi tham số ảnh hưởng kết quả phải có mặt
    queryKey: ['orders', filters],
    queryFn: ({ signal }) => fetchOrders(filters, signal),
    staleTime: 30_000,
    retry: 2,
    select: (data: Order[]) => data.slice(0, 50),
  });
}

function useCreateOrder() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: createOrder,
    onSuccess: () => qc.invalidateQueries({ queryKey: ['orders'] }),
  });
}

// component — loading/error do lib quản lý, không tự viết useEffect
const { data, isPending, isError, error } = useOrders(filters);
Use case

Trang danh sách đơn và trang chi tiết đơn cùng đọc ['orders', filters]: khi user vào chi tiết rồi quay lại, dữ liệu nằm sẵn trong cache nên hiển thị ngay, đồng thời refetch nền để cập nhật. Sau khi tạo đơn mới, invalidate key ['orders'] làm mọi màn hình liên quan tự làm mới.

Pitfall / Interview trap

Bốn trap hay gặp: (1) queryKey chứa object/array tạo mới mỗi render khiến key "đổi" liên tục và fetch lặp — dùng giá trị primitive hoặc chuẩn hoá key; (2) quên đưa tham số vào key nên hai filter khác nhau dùng chung cache; (3) nhầm staleTime với gcTime — staleTime quyết định khi nào refetch, gcTime quyết định khi nào xoá cache; (4) nói "TanStack Query thay thế Redux" — không hẳn, nó thay thế phần server state; client state toàn cục vẫn cần store riêng. Lưu ý cuối: queryFn nên nhận signal từ context để huỷ request khi component unmount.

Nói trong 60 giây
  • Server state: bất đồng bộ, có thể stale, chia sẻ nhiều nơi, không do mình sở hữu.
  • queryKey là danh tính dữ liệu — mọi tham số ảnh hưởng kết quả phải nằm trong key.
  • staleTime: bao lâu coi là mới; gcTime: bao lâu giữ cache sau khi không ai dùng.
  • Dedupe request trùng key; retry cho lỗi mạng, không retry 4xx.
  • invalidateQueries sau mutation để đồng bộ; client state vẫn để ở useState/store.

Q10 Loading / error / empty state, optimistic update kèm rollback, và error boundary cho lỗi render?

What

Mọi màn hình dữ liệu có bốn trạng thái phải xử lý: loading, error, empty (thành công nhưng không có dữ liệu) và có dữ liệu. Optimistic update là cập nhật UI ngay khi user hành động, trước khi server trả lời, và khôi phục trạng thái cũ nếu request lỗi. Error boundary là component bắt lỗi xảy ra trong lúc render cây con và hiển thị UI thay thế thay vì màn hình trắng.

Why

Ba khái niệm này cùng phục vụ một mục tiêu: app không được rơi vào trạng thái mơ hồ. Nếu thiếu nhánh empty, user thấy màn hình trống và không biết là "không có kết quả" hay "app hỏng"; nếu thiếu error state, lỗi mạng bị nuốt im lặng; nếu không có error boundary, một exception trong render làm trắng cả app. Optimistic update giảm độ trễ cảm nhận với thao tác tần suất cao, đổi lại bạn phải trả giá bằng việc giữ và khôi phục state cũ — nên chỉ dùng khi xác suất thất bại thấp.

How
User bấm "Yêu thích"
↓ onMutate: ghi cache ngay, lưu snapshot cũ
UI đổi tức thì (optimistic)
Server 200 → invalidate để đồng bộ
Server lỗi → onError khôi phục snapshot
↓
onSettled: invalidate lần cuối để chốt dữ liệu thật

Với lỗi render, boundary là class component: static getDerivedStateFromError để cập nhật state, componentDidCatch để log. React không có hook tương đương; trong app thực tế dùng thư viện react-error-boundary cho API gọn và hỗ trợ reset. Đặt boundary ở cấp route/layout, và bọc riêng từng widget quan trọng để một widget hỏng không kéo cả trang.

When

Optimistic update cho thao tác tần suất cao, dễ đoán kết quả và ít khả năng fail: like/timemark, toggle trạng thái, thêm/xoá item khỏi danh sách yêu thích, sắp xếp lại thứ tự. Error boundary cho mọi route và các widget độc lập (chart, bảng dữ liệu). Empty state là bắt buộc với mọi danh sách và mọi ô tìm kiếm.

When NOT

Không dùng optimistic cho thao tác quan trọng, có khả năng bị server từ chối theo luật nghiệp vụ: thanh toán, đặt hàng khi cần kiểm tra tồn kho, gửi form có validate phía server — hãy dùng trạng thái pending rõ ràng, disable nút và hiển thị tiến trình. Error boundary không bắt lỗi trong event handler, lỗi trong code async, lỗi trong setTimeout hay lỗi của chính nó — những chỗ đó phải try/catch hoặc để error state của mutation lo. Cũng không cần boundary cho từng component nhỏ trong cùng một danh sách.

const toggle = useMutation({
  mutationFn: toggleFavorite,
  onMutate: async (id: string) => {
    await qc.cancelQueries({ queryKey: ['favorites'] });
    const prev = qc.getQueryData<string[]>(['favorites']);
    qc.setQueryData<string[]>(['favorites'], old => [...(old ?? []), id]);
    return { prev }; // snapshot để rollback
  },
  onError: (_err, _id, ctx) => qc.setQueryData(['favorites'], ctx?.prev),
  onSettled: () => qc.invalidateQueries({ queryKey: ['favorites'] }),
});

// Error boundary: chỉ class component mới bắt được lỗi render
class ErrorBoundary extends React.Component<{ children: ReactNode }, { error: Error | null }> {
  state = { error: null };
  static getDerivedStateFromError(error: Error) { return { error }; }
  componentDidCatch(error: Error, info: React.ErrorInfo) { reportError(error, info); }
  render() {
    if (this.state.error) return <FallbackUI error={this.state.error} />;
    return this.props.children;
  }
}
Use case

Danh sách đơn hàng: isPending hiển thị skeleton, isError hiển thị thông báo kèm nút "Thử lại" gọi refetch(), data.length === 0 hiển thị hướng dẫn tạo đơn đầu tiên, có dữ liệu thì render bảng. Bốn nhánh rõ ràng, không nhánh nào là màn hình trắng.

Pitfall / Interview trap

Ba điểm bị hỏi nhiều: (1) Error boundary không bắt lỗi trong event handler hay async — phải try/catch, và lỗi của chính boundary thì boundary cha mới bắt được; (2) optimistic update mà không cancelQueries trước khi ghi cache có thể bị một refetch đang bay ghi đè ngược lại, làm UI nhảy về giá trị cũ; (3) rollback cần snapshot chứ không phải "tính lại từ đầu" — với cache phức tạp, khôi phục snapshot do onMutate trả về là cách chắc chắn nhất. Ngoài ra đừng quên trạng thái empty: "loading xong rồi không có gì" khác hoàn toàn với "chưa load xong".

Nói trong 60 giây
  • Bốn trạng thái bắt buộc: loading, error, empty, có dữ liệu — không để màn hình trắng.
  • Optimistic: onMutate ghi cache + snapshot, onError rollback, onSettled invalidate.
  • Chỉ optimistic cho thao tác nhanh, ít fail; thanh toán/đặt hàng dùng pending rõ ràng.
  • Error boundary là class component, bắt lỗi render cây con, đặt ở cấp route/widget.
  • Boundary không bắt lỗi event handler và async code.
