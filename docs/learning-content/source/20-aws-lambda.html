Lambda cơ bản & cách chạy

AWS1 Lambda là gì? Anatomy: handler, runtime và execution role

What

AWS Lambda là dịch vụ compute serverless chạy code theo sự kiện (event-driven), không cần quản lý server. Bạn chỉ nộp một deployment package (file .zip hoặc container image), khai báo handler, runtime và một execution role (IAM role); Lambda lo phần scaling, patching và HA. Mỗi invocation chạy trong một execution environment cách ly.

How

Ba mảnh ghép bắt buộc: handler (điểm vào, ví dụ app.handler), runtime (Node.js, Python, Java, .NET, Go, Ruby hoặc custom runtime/OS-only image) và execution role — Lambda assume role này để gọi dịch vụ AWS khác (ghi CloudWatch Logs, đọc DynamoDB, PutObject S3…). Mọi quyền của function đến từ role, không có credential cứng trong code.

When

When NOT

Không cho workload chạy liên tục nặng (chi phí sẽ vượt EC2/Fargate), không cho tác vụ cần > 15 phút một lần gọi, không cho app cần lưu state lâu dài trên máy, không cho library cần native binary cồng kềnh khó build.

Bẫy thi / Pitfall

Đừng nhầm execution role (role Lambda assume để chạy function) với resource-based policy (ai được phép invoke function). Thiếu Logs permission trong execution role sẽ khiến function chạy nhưng không có log.

AWS2 Invocation model: sync vs async vs event source mapping — chọn cái nào?

What

Lambda có 3 mô hình gọi: synchronous (RequestResponse — caller chờ kết quả), asynchronous (Event — Lambda xếp event vào queue nội bộ rồi trả về ngay) và event source mapping (Lambda poll stream/queue rồi tự gọi function theo batch). Đây là một trong những điểm dễ nhầm và hay thi nhất.

How

Sync: API Gateway, ALB, CLI/SDK dùng Invoke — lỗi trả thẳng cho caller, retry do caller quyết định. Async: S3, SNS, EventBridge, Lambda destinations — Lambda retry 2 lần mặc định (tổng 3 lần thử), khoảng cách ~1 phút rồi ~2 phút; lỗi throttle (429) và system error (5xx) được đưa lại queue tới 6 giờ. ESM: SQS, Kinesis, DynamoDB Streams, MSK, MQ — Lambda poll và gọi theo batch, xử lý ít nhất một lần (at-least-once) nên code phải idempotent.

Synccaller chờ response · 6 MB
Asyncqueue nội bộ · retry 2 lần
Event source mappingpoll + batch · idempotent
# Synchronous: cho ket qua tra ve ngay trong out.json
aws lambda invoke --function-name order-api \
  --payload '{"orderId":"A-1001"}' out.json

# Asynchronous: Lambda xep hang roi tra ve ngay, khong doi ket qua
aws lambda invoke --function-name order-worker \
  --invocation-type Event \
  --payload '{"orderId":"A-1001"}' out.json

When

Sync khi cần trả kết quả ngay cho user (REST API). Async khi tác vụ nền, không cần response (gửi mail, resize ảnh). ESM khi cần consume stream/queue throughput cao theo batch.

When NOT

Không dùng sync cho tác vụ dài dễ timeout ở caller; không dùng async khi bắt buộc thứ tự nghiêm ngặt (không đảm bảo order, có thể trùng); không bật ESM cho SQS FIFO mà code không xử lý partial batch failure.

Bẫy thi / Pitfall

Async có thể giao trùng event dù function không lỗi (queue eventually consistent) — luôn viết idempotent. Với ESM SQS, cấu hình DLQ trên chính queue SQS, không phải trên function; còn với luồng async, dùng on-failure destination hoặc DLQ của Lambda.

Cold start, concurrency & throttling

AWS3 Cold start vs warm start: SnapStart và provisioned concurrency

What

Cold start là độ trễ khi Lambda phải tạo execution environment mới: tải code, khởi động runtime, chạy code khởi tạo (init). Warm start là tái dùng environment đã init nên gần như tức thời. Java, .NET và function nhiều dependency chịu cold start nặng nhất.

How

Vòng đời: Init → Invoke → Freeze (giữ environment nếu còn request) → Thaw hoặc hủy. Giảm cold start bằng 4 cách: (1) tăng memory ⇒ nhiều CPU, init nhanh hơn; (2) Init ngoài handler (static/global, tái dùng connection); (3) provisioned concurrency — giữ sẵn N environment đã init, phản hồi tính bằng ms; (4) SnapStart — chụp snapshot (Firecracker MicroVM) của environment lúc publish version rồi khôi phục từ cache, thường đạt cold start dưới 1 giây, hỗ trợ Java 11+, Python 3.12+, .NET 8+.

When

SnapStart khi API Java/Python cần cold start thấp mà không muốn trả tiền giữ sẵn; provisioned concurrency khi SLA latency khắt khe (double-digit ms) và có traffic dự đoán được.

When NOT

SnapStart không đi cùng provisioned concurrency, EFS/S3 Files hay /tmp > 512 MB. Provisioned concurrency tính phí kể cả khi không dùng — đừng bật cho function traffic thưa.

Bẫy thi / Pitfall

SnapStart chụp lúc publish version, nên state sinh trong init (UUID, timestamp, connection) sẽ bị "đông cứng" và lặp lại sau khi restore — phải seed lại tính duy nhất. Provisioned concurrency gắn với version/alias, không gắn $LATEST.

AWS4 Concurrency & throttling: reserved, burst và lỗi 429 TooManyRequests

What

Ứng dụng đặt hàng dùng một Lambda xử lý SQS bị throttle giờ cao điểm, message trả về queue liên tục. Concurrency = số request Lambda xử lý đồng thời; mỗi request cần một execution environment riêng. Account mặc định có 1.000 concurrent executions mỗi Region, dùng chung cho mọi function.

How

Hai cơ chế kiểm soát: reserved concurrency đặt trần đồng thời cho một function (phần còn lại của pool 1.000 dành cho các function khác, tránh một function "ăn" hết) và provisioned concurrency giữ sẵn environment đã init. Ngoài ra Lambda giới hạn tốc độ scale: 1.000 environment mỗi 10 giây cho mỗi function — vượt là bị throttle với 429 TooManyRequestsException (sync) hoặc event quay lại queue (async).

When NOT

Không đặt reserved = toàn bộ 1.000 cho một function (các function khác không còn gì); không bật provisioned concurrency rồi quên alias — phải gắn version/alias. Không dùng reserved để "chống" cold start (nó không init sẵn).

Bẫy thi / Pitfall

Reserved concurrency là trần, còn provisioned là sàn đã init — đừng nhầm. Đặt reserved = 0 để "tắt" function là cách chặn async: event đi thẳng vào DLQ/on-failure destination không retry. Tăng provisioned đồng nghĩa phải trừ vào pool dự trữ.

Cấu hình, package & mạng VPC

AWS5 Memory, CPU, timeout và /tmp: cấu hình & tối ưu chi phí

What

Một job ETL tải file lớn về /tmp rồi xử lý, nhưng fail vì hết dung lượng. Lambda cho phép cấu hình memory 128–10.240 MB (bước 1 MB), timeout tối đa 900 giây (15 phút) và ephemeral storage /tmp 512–10.240 MB. CPU không đặt trực tiếp — tỉ lệ thuận với memory.

How

Tăng memory vừa tăng CPU vừa giảm thời gian chạy; vì tính phí theo GB-giây, đôi khi nhiều memory hơn lại rẻ hơn (chạy nhanh hơn, ít giây hơn). /tmp dùng cho file tạm, giải nén, model ML — nhưng không bền và gắn với từng execution environment, có thể còn lại giữa các lần invoke warm (đừng giả định sạch). Đo đạc bằng AWS Lambda Power Tuning để tìm cấu hình tối ưu.

When NOT

Không dùng /tmp như database (mất khi environment bị thu hồi); không đặt timeout 900 giây "cho chắc" — timeout dài làm treo caller và tăng chi phí; không dùng EFS nếu chỉ để lưu file tạm (thêm độ trễ + phí).

Bẫy thi / Pitfall

CPU tỉ lệ với memory, không tinh chỉnh riêng. "Max 10.240 MB" ≠ "10GB free tier". Function chạm timeout bị tính là lỗi; với async nó retry 2 lần. /tmp giữa các invoke warm có thể chứa dữ liệu cũ — luôn dọn/kiểm tra.

AWS6 Layers & deployment package: 50 MB / 250 MB / 10 GB container image

What

Hai kiểu deployment package: .zip (code + dependency) và container image (build từ base image của Lambda hoặc OS-only, đẩy lên ECR). Layer là .zip phụ chứa dependency dùng chung, được giải nén vào /opt trong execution environment — giúp package gọn và tái sử dụng.

How

Chọn .zip khi dependency gọn, muốn dùng console editor và deploy nhanh. Chọn container image khi cần native binary lớn, ML framework, hoặc vượt giới hạn dung lượng .zip (tối đa 10 GB uncompressed). Tối đa 5 layer một function; runtime không tự thêm /opt vào path cho image. Build multi-stage để image nhỏ, deploy nhanh hơn.

AWS7 Lambda trong VPC: NAT, Hyperplane ENI và RDS Proxy

What

Ứng dụng cần Lambda đọc một RDS trong private subnet. Mặc định Lambda chạy trong VPC do AWS quản lý nên không truy cập được tài nguyên private của bạn. Gắn function vào VPC thì function có thể tới RDS/ElastiCache, nhưng mất internet trừ khi thêm NAT.

How

Khi attach VPC, Lambda tạo Hyperplane ENI trong subnet và cần các quyền ec2:CreateNetworkInterface, DescribeNetworkInterfaces, DescribeSubnets, DeleteNetworkInterface… (gói sẵn trong AWSLambdaVPCAccessExecutionRole). Để ra internet phải đặt function ở private subnet có route tới NAT Gateway (NAT nằm ở public subnet). Vì mỗi execution environment mở connection riêng tới DB, dùng RDS Proxy để pool connection, giảm áp lực lên DB và tăng tốc failover.

Version, triển khai an toàn & quan sát

AWS8 Version & alias: canary deployment có cân trọng số

What

Version là snapshot bất biến của code + config (mỗi lần publish là một số version mới). Alias là con trỏ có tên (dev/prod/live) trỏ tới một version và có thể cập nhật. Alias hỗ trợ weighted routing để chia một phần traffic sang version mới — nền tảng cho canary deployment.

How

Quy trình: publish version mới → tạo/cập nhật alias trỏ version mới → nếu muốn canary, cấu hình thêm trọng số cho version cũ (ví dụ 10% vẫn về version cũ, 90% sang mới) → theo dõi metric → tăng dần tới 100%. Tích hợp với CodeDeploy để shift traffic tự động theo pre/post hook và tự rollback khi alarm kích hoạt. Event source mapping và API Gateway nên trỏ tới alias ARN, không trỏ version cứng.

When

Mọi function production nên dùng version + alias để rollback tức thì. Canary khi thay đổi rủi ro (logic mới, dependency mới) và có metric/alarm để đánh giá.

When NOT

Không trỏ event source vào $LATEST (không version-hoá, không weighted được). Không canary khi không có observability — không đo được thì đừng shift. Weighted alias giới hạn 2 version — không dùng để A/B nhiều bản.

Bẫy thi / Pitfall

Publish version là bất biến; muốn đổi code phải publish version mới. Provisioned concurrency và SnapStart gắn với version/alias chứ không gắn $LATEST. Trọng số weighted alias là tỉ lệ đến version phụ, phần còn lại đi version chính.

AWS9 Logging & tracing: CloudWatch Logs, X-Ray và Powertools

What

Lambda ghi log ra CloudWatch Logs (mỗi function một log group /aws/lambda/{tên-function}), phát metric vào CloudWatch và có thể trace bằng AWS X-Ray. Đây là kỹ năng thuộc Domain 4 (Troubleshooting & Optimization) — đọc log/metric/trace để tìm root cause.

How

Mọi thứ in ra stdout/stderr đều thành log stream. Bật active tracing để X-Ray theo dõi request qua các service (API Gateway → Lambda → DynamoDB) và xem service map, subsegment. Thư viện AWS Lambda Powertools (Logger, Tracer, Metrics) chuẩn hoá structured log JSON, thêm trace id và phát custom metric qua EMF (Embedded Metric Format) để vẽ alarm.

# Truy van log bang CloudWatch Logs Insights
aws logs start-query \
  --log-group-name /aws/lambda/order-api \
  --query-string 'fields @timestamp, @message | filter @message like /ERROR/ | sort @timestamp desc'
# AWS Lambda Powertools: structured log + custom metric (EMF)
from aws_lambda_powertools import Logger, Tracer, Metrics
logger = Logger(); tracer = Tracer(); metrics = Metrics()

@tracer.capture_lambda_handler
def handler(event, context):
    metrics.add_metric(name="OrdersProcessed", unit="Count", value=1)
    logger.info("order processed", order_id=event["orderId"])
Công cụVai tròMetric hay dùng
CloudWatch LogsLog per-invocation, Insights queryFilter ERROR, request id
CloudWatch MetricsInvocation, Duration, ErrorsErrors, Throttles, ConcurrentExecutions
X-RayTrace phân tán, service mapSubsegment, lỗi downstream
PowertoolsChuẩn hoá log JSON + EMF + tracingCustom business metric
When

Bật X-Ray cho hệ microservices/serverless cần tìm bottleneck giữa các service. Dùng Powertools khi muốn log có cấu trúc, trace id xuyên suốt và custom metric không tốn API call riêng.

When NOT

Không log secret/PII ra CloudWatch. Không bật X-Ray sampling 100% cho function volume lớn (tăng phí) — chỉnh sampling rule. Không dựa mỗi log để đo business metric — dùng EMF.

Bẫy thi / Pitfall

Không có log ≠ function không chạy — thường do execution role thiếu quyền Logs, hoặc log nằm ở log group của version/alias khác. X-Ray cần cả bật tracing và quyền trong execution role. Timeout/cold start để lại dấu rõ trong log stream theo request id.
