CloudWatch Metrics & Logs

AWS1 CloudWatch metrics, alarm và composite alarm: từ số liệu thô tới hành động tự động

What

Một metric là chuỗi data point theo thời gian, định danh bằng namespace (ví dụ AWS/Lambda, OrderApi/App) + tên metric (ví dụ Duration) + dimensions (cặp key/value như FunctionName=order-api). Mỗi data point là một tập statistics (Average, Sum, Min, Max, SampleCount, p50/p90/p99) trên một period.

How

Số liệu chảy từ service (metric có sẵn của AWS) hoặc do bạn tự publish (PUT metric data) về alarm. Alarm có 3 trạng thái OK / ALARM / INSUFFICIENT_DATA và có thể gắn action: gửi SNS, thực thi Auto Scaling action hoặc EC2 action (stop / terminate / reboot / recover).

Metricperiod 60s, Sum
→ngưỡng + M-of-N
AlarmALARM / OK
→alarm action
SNSbáo on-call
EC2 / ASGreboot, recover, scale
When

Dùng alarm cho mọi thứ cần phản ứng tự động: 5xx tăng, queue backlog, CPU, error rate, business metric tự publish (đơn hàng lỗi/phút). Composite alarm dùng khi có quá nhiều alarm cùng kêu trong một sự cố — gom theo logic AND/OR/NOT để giảm alarm noise (ví dụ chỉ kêu khi vừa latency cao vừa error rate cao trên cùng một service).

When NOT

Đừng dùng alarm cho dữ liệu cần audit hay truy vết "ai gọi API gì" — đó là việc của CloudTrail. Đừng lạm dụng composite alarm để che hết alarm con: khi incident xảy ra bạn vẫn cần nhìn thấy alarm con nào kêu.

aws cloudwatch put-metric-alarm \
  --alarm-name order-api-5xx-high \
  --namespace AWS/ApplicationELB \
  --metric-name HTTPCode_Target_5XX_Count \
  --statistic Sum --period 60 --evaluation-periods 3 \
  --datapoints-to-alarm 2 --threshold 10 \
  --comparison-operator GreaterThanThreshold \
  --treat-missing-data notBreaching \
  --alarm-actions arn:aws:sns:ap-southeast-1:123456789012:oncall \
  --ok-actions    arn:aws:sns:ap-southeast-1:123456789012:oncall

Bẫy thi / Pitfall

Alarm độ phân giải cao (period 10 hoặc 30 giây) chỉ hợp lệ khi metric là high-resolution. Đặt evaluation-periods × period = "M trong N phút" là điểm hay bị hỏi: alarm kêu chỉ khi có ÍT NHẤT M data point vượt ngưỡng trong N lần đánh giá gần nhất.

AWS2 CloudWatch Logs: log group, log stream, retention, metric filter và subscription filter

What

Log group là đơn vị quản lý (thường một group = một ứng dụng), log stream là chuỗi sự kiện từ một nguồn cụ thể (một Lambda instance, một EC2, một ECS task). Retention được đặt ở mức log group, không phải từng stream.

How

Log đi vào CloudWatch Logs rồi có thể đi tiếp theo 3 hướng: metric filter biến dòng log thành metric (để alarm), subscription filter đẩy log theo thời gian thực sang đích xử lý, và export (batch) ra S3 để lưu trữ lâu dài.

App / ECSstdout
→PutLogEvents
Log group/order-api/app
→filter pattern
Firehose→ S3 / OpenSearch
Lambdareal-time xử lý
When

Metric filter khi bạn cần đếm thứ gì đó trong log (số lần ERROR, số lần thanh toán thất bại) để alarm. Subscription filter khi cần log đi đâu đó gần như tức thời (Lambda enrich, Kinesis để phân tích, Firehose gom vào S3/OpenSearch).

When NOT

Đừng dùng export ra S3 cho mục đích real-time — export là job batch, có thể mất tới vài giờ mới xong và không phải luồng liên tục. Và đừng để retention mặc định (Never expire) cho môi trường prod lâu dài nếu không kiểm soát chi phí lưu trữ.

# 1) biến dòng log chứa ERROR thành metric ErrorCount
aws logs put-metric-filter \
  --log-group-name /order-api/app \
  --filter-name ErrorCount \
  --filter-pattern "ERROR" \
  --metric-transformations \
      metricName=ErrorCount,metricNamespace=OrderApi,metricValue=1,defaultValue=0

# 2) đặt retention 30 ngày cho log group
aws logs put-retention-policy --log-group-name /order-api/app --retention-in-days 30

# 3) đẩy log real-time sang Kinesis Data Firehose
aws logs put-subscription-filter \
  --log-group-name /order-api/app \
  --filter-name to-firehose \
  --filter-pattern "" \
  --destination-arn arn:aws:firehose:ap-southeast-1:123456789012:deliverystream/logs-to-s3
Cơ chếĐích / kết quảĐặc điểm

Log đã export sang S3 thì không query được bằng Logs Insights nữa. Muốn giữ lâu + vẫn phân tích thì dùng subscription filter đẩy sang Firehose → S3, rồi query bằng Athena.

AWS3 CloudWatch Logs Insights: viết query để tìm đúng dòng log lỗi

What

Logs Insights là công cụ query log có cấu trúc, chạy trên log group trong CloudWatch Logs. Ngôn ngữ query gồm các lệnh xếp theo dòng, ngăn bởi |: fields, filter, parse, stats, sort, limit, pattern. Bạn có thể query tối đa nhiều log group cùng lúc trong một lần chạy.

How

Query chạy trên dữ liệu log còn trong log group (kể cả khi bạn không đặt retention), trả về theo thứ tự thời gian hoặc theo bảng thống kê.

Log groupschọn nhiều group
→query syntax
Logs Insightsfilter + stats
→visualize / export
Dashboardadd to dashboard
When

Khi cần trả lời nhanh câu hỏi "lỗi gì, từ bao giờ, tập trung ở đâu": đếm theo thời gian, gom theo status code, tìm request chậm, lọc theo requestId để dựng lại một transaction.

When NOT

Không thay thế trace phân tán (dùng X-Ray) hay audit (dùng CloudTrail). Query trên tập log cực lớn nên giới hạn khoảng thời gian để tránh tốn thời gian và chi phí scan.

fields @timestamp, @requestId, @message, @duration
| filter @message like /ERROR/ and @duration > 1000
| parse @message /(?<code>\d{3}) /
| stats count(*) as n, avg(@duration) as avg_ms by bin(5m), code
| sort n desc
| limit 20
LệnhViệc nó làm
fieldsChọn cột hiển thị / dùng tiếp
filterLọc dòng theo điều kiện (so sánh, regex, in)
parseTách trường từ chuỗi log bằng regex (glob hoặc named capture)
stats ... by bin(5m)Aggregate theo thời gian: count, avg, pct, sum
sort / limitSắp xếp và giới hạn số dòng trả về
Bẫy thi / Pitfall

@message, @timestamp, @requestId, @duration là các trường hệ thống (bắt đầu bằng @). Nhiều log mặc định không phải JSON nên bạn phải parse để lấy field; nếu app ghi log JSON thì các field đó có sẵn ngay.

X-Ray, CloudTrail & debug Lambda

AWS4 X-Ray: trace, segment, subsegment, sampling rule và cách đọc một trace lỗi

What

X-Ray là dịch vụ trace phân tán. Một trace là hành trình đầy đủ của MỘT request qua nhiều service; trace gồm nhiều segment (một segment = một service xử lý, ví dụ một Lambda invocation); mỗi segment chia thành subsegment cho các lời gọi xuống dưới (SQL, HTTP, AWS SDK, downstream service). Annotations (key/value, được index nên tìm kiếm được) khác metadata (không index).

How

Ứng dụng nhúng X-Ray SDK (Node.js, Python, Java, .NET, Go, Ruby) để tự sinh segment/subsegment, hoặc bật Active Tracing cho Lambda. Dữ liệu segment được gửi tới X-Ray daemon (UDP cổng 2000, chạy trên EC2/ECS/Elastic Beanstalk) hoặc qua API. Backend dựng service map để bạn thấy nút nào lỗi/chậm.

Clientrequest
→trace header
API Gatewaysegment 1
→invoke
Lambdasegment 2
→subsegment
DynamoDBsubsegment lỗi
When

Khi cần tìm nút thắt trong hệ microservice/serverless: service nào chậm, lời gọi nào lỗi, retry ở đâu. Rất hợp câu hỏi "vì sao request này chậm 3 giây" mà log từng service riêng lẻ không kể được.

When NOT

Không dùng X-Ray để trả lời "ai đã đổi security group" (CloudTrail) hay "resource này có đúng cấu hình không" (AWS Config). Cũng không bật trace 100% traffic đắt đỏ — hãy dùng sampling rule.

# Lọc trace lỗi của service order-api
aws xray get-trace-summaries \
  --start-time 2026-10-04T09:00:00Z --end-time 2026-10-04T09:15:00Z \
  --filter-expression 'service("order-api") AND fault = true'

# Lấy chi tiết một trace theo Id
aws xray batch-get-traces --trace-ids 1-5e8f7c3a-0123456789abcdef01234567
Khái niệmÝ nghĩaGhi chú

Bẫy thi / Pitfall

Lambda cần quyền IAM AWSXRayDaemonWriteAccess (qua role của function) mới gửi được trace. Trên EC2/ECS phải chạy X-Ray daemon và mở UDP 2000 — SDK không tự gửi trực tiếp nếu thiếu daemon.

AWS5 CloudWatch vs CloudTrail vs X-Ray vs Config: bốn service dễ nhầm nhất

What

Cả bốn đều là "observability/governance" nhưng trả lời bốn câu hỏi hoàn toàn khác nhau. Nhầm chúng là lỗi phổ biến trong đề DVA-C02.

CloudWatch"hệ thống đang khoẻ không?" — metric, log, alarm
CloudTrail"ai đã gọi API gì?" — audit
X-Ray"request đi đâu, chậm ở đâu?" — trace
AWS Config"cấu hình có đúng chuẩn?" — compliance
How

CloudWatch thu metric/log của resource; CloudTrail ghi lại các lời gọi API (management events mặc định, data events phải bật riêng); X-Ray dựng trace phân tán; Config đánh giá cấu hình resource theo rule và ghi lại lịch sử thay đổi cấu hình.

When

Chẩn đoán hiệu năng/lỗi runtime → CloudWatch + X-Ray. Điều tra "ai làm, từ IP nào, lúc nào" → CloudTrail. Kiểm tra tuân thủ cấu hình (bật encryption, đúng tag, không mở public) → AWS Config.

When NOT

Đừng dùng CloudTrail để xem CPU/latency (nó chỉ có sự kiện API). Đừng dùng Config để chặn thao tác xấu theo thời gian thực — Config ghi nhận và đánh giá, không phải WAF/GuardDuty.

# CloudWatch — lấy metric lỗi của Lambda
aws cloudwatch get-metric-statistics --namespace AWS/Lambda --metric-name Errors \
  --dimensions Name=FunctionName,Value=order-api \
  --start-time 2026-10-04T09:00:00Z --end-time 2026-10-04T10:00:00Z \
  --period 300 --statistics Sum

# CloudTrail — tìm hành động phá huỷ
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=DeleteTable \
  --start-time 2026-10-04T09:00:00Z

# AWS Config — rule nào đang NON_COMPLIANT
aws configservice describe-compliance-by-config-rule --compliance-types NON_COMPLIANT

AWS6 Tình huống: function Lambda vừa báo timeout vừa bị throttling — đọc gì và sửa gì?

What

Bạn có một API Lambda order-api. Dashboard báo Duration sát trần, một số invocation trả về Task timed out after 3.00 seconds, đồng thời xuất hiện TooManyRequestsException (throttling 429). Cần phân biệt rõ 5 loại lỗi Lambda hay gặp để xử lý đúng.

How

Đối chiếu metric với log và cấu hình để tách nguyên nhân. Bộ metric cần nhìn: Invocations, Errors, Throttles, Duration, ConcurrentExecutions, IteratorAge, và log stream của từng instance.

MetricDuration, Throttles, Errors
→log stream
Log LambdaREPORT line
→trace
X-Raysubsegment chậm
→fix
Configtimeout/memory/concurrency
When

Checklist 5 lỗi kinh điển, mỗi lỗi một hướng sửa: (1) Timeout — tăng Timeout (tối đa 15 phút) và tối ưu đoạn chậm; (2) OOM — tăng MemorySize (memory cũng tỷ lệ CPU); (3) Cold start — giảm package, dùng Provisioned Concurrency hoặc SnapStart; (4) Throttling — kiểm tra concurrency (mặc định 1.000/account/region) và reserved concurrency; (5) AccessDenied — kiểm tra execution role/resource policy.

When NOT

Đừng "tăng timeout" như phản xạ cho timeout nếu nguyên nhân thật là downstream chậm — timeout dài chỉ che đi vấn đề và làm bill tăng. Cũng đừng tăng memory nếu log cho thấy function chết vì lỗi code, không phải hết RAM.

# Xem cấu hình đang chạy
aws lambda get-function-configuration --function-name order-api \
  --query '{timeout:Timeout,memory:MemorySize,reserved:ReservedConcurrentExecutions}'

# Xem REPORT cuối mỗi invocation (Duration, Billed Duration, Max Memory Used)
aws logs filter-log-events --log-group-name /aws/lambda/order-api \
  --filter-pattern "REPORT" --limit 20

# Xem 15 phút gần nhất có bị throttling không
aws cloudwatch get-metric-statistics --namespace AWS/Lambda --metric-name Throttles \
  --dimensions Name=FunctionName,Value=order-api \
  --start-time 2026-10-04T09:00:00Z --end-time 2026-10-04T09:15:00Z \
  --period 60 --statistics Sum
Triệu chứngMetric / dấu hiệuCách xử lý

Bẫy thi / Pitfall

Throttling xảy ra khi vượt concurrency. Chú ý: reserved concurrency "giữ chỗ" cho function nhưng lấy đi phần của các function khác; provisioned concurrency mới là thứ giữ instance nóng. Đọc kỹ đề để không chọn nhầm cái nào.

Troubleshooting hệ thống trên AWS

AWS7 502 / 504 / 403 sau ALB và API Gateway: đọc log gì, tìm ở đâu?

What

Các mã lỗi 5xx ở tầng load balancer thường KHÔNG phải lỗi app mà là lỗi kết nối tới target hoặc target trả lời sai. Hiểu ý nghĩa từng mã giúp khoanh vùng nhanh thay vì đọc log app vô ích.

How

Bật access log của ALB (đích là S3), rồi so khớp elb_status_code với target_status_code và target_response_time để biết LB lỗi hay target lỗi.

ClientHTTPS
→idle timeout 60s
ALBaccess log → S3
→health check
TargetECS / Lambda task
When

Dùng access log + target health để phân loại: target bị unhealthy, target đóng kết nối giữa chừng, hay target không phản hồi trong thời gian cho phép.

When NOT

403 không phải lỗi 5xx: nó thường do WAF, security group/NACL, authorizer của API Gateway, hoặc Lambda resource policy chặn — không cần đọc access log 5xx mà kiểm tra lớp bảo vệ.

AWS8 Tình huống: Lambda trong VPC gọi RDS bị timeout — VPC, NAT gateway và connection pool

What

Bạn chuyển Lambda order-api vào VPC để truy cập RDS PostgreSQL private. Sau đó function bắt đầu timeout, và mỗi lần scale lên lại có thêm connection mới tới DB. Có hai vấn đề độc lập cần tách ra: định tuyến ra Internet và quản lý connection.

How

Lambda trong VPC chỉ có IP private. Muốn ra Internet (gọi API ngoài, tải package) phải đi qua NAT gateway ở public subnet; muốn gọi service AWS nội bộ thì thêm VPC endpoint. Về DB, mỗi Lambda instance mở connection riêng nên khi scale đột biến có thể vượt max_connections — dùng RDS Proxy để gom connection pool.

When

Đặt Lambda trong VPC + private subnet khi DB không public. Thêm VPC endpoint cho Secrets Manager/S3/CloudWatch Logs để không phải kéo traffic qua NAT (giảm chi phí + độ trễ). Dùng RDS Proxy khi có nhiều Lambda hoặc traffic tăng giảm thất thường.

When NOT

Nếu function chỉ dùng service AWS và không cần DB private, đừng nhét vào VPC — thêm VPC chỉ làm phức tạp và (trước đây) tăng cold start. Cũng đừng lạm dụng RDS Proxy cho workload connection ổn định, ít function.

# Kiểm tra Lambda đang ở subnet nào + security group
aws lambda get-function-configuration --function-name order-api \
  --query 'VpcConfig.{subnets:SubnetIds,sg:SecurityGroupIds}'

# Kiểm tra RDS còn slot connection không
aws cloudwatch get-metric-statistics --namespace AWS/RDS --metric-name DatabaseConnections \
  --dimensions Name=DBInstanceIdentifier,Value=order-db \
  --start-time 2026-10-04T09:00:00Z --end-time 2026-10-04T09:15:00Z \
  --period 60 --statistics Maximum

# Tạo RDS Proxy (PostgreSQL) để gom connection pool
aws rds create-db-proxy --db-proxy-name order-api-proxy \
  --engine-family POSTGRESQL \
  --role-arn arn:aws:iam::123456789012:role/rds-proxy-role \
  --vpc-subnet-ids subnet-aaa subnet-bbb

AWS9 Dashboard, CloudWatch agent và operational excellence: SLO cơ bản + structured JSON log

What

SLO là mục tiêu chất lượng dịch vụ (ví dụ 99,9% request thành công trong 30 ngày) đo bằng SLI (chỉ số thực tế: latency p99, error rate, availability). Chênh lệch giữa mục tiêu và thực tế là error budget — dùng để quyết định "được phép release rủi ro tới đâu".

How

Gom metric + log vào CloudWatch dashboard, đặt alarm theo SLO. Với tài nguyên EC2/ECS cần thêm số liệu tầng OS (RAM, disk) — metric mặc định của CloudWatch không có memory/disk — phải chạy CloudWatch agent. Log nên ghi dạng structured JSON để Logs Insights query thẳng field, kèm correlationId/requestId.

EC2 / ECSapp + agent
→mem, disk, JSON log
CloudWatchmetrics + logs
→SLO alarm
Dashboardone pane of glass
When

Dashboard cho on-call nhìn nhanh tình trạng; agent cho workload IaaS/PaaS cần metric OS; structured log khi bạn cần phân tích/alert trên field cụ thể thay vì grep chuỗi.

When NOT

Đừng nhồi mọi metric lên một dashboard (nhiễu, khó đọc) — tách dashboard theo service/team. Và đừng đặt SLO 100%: không có error budget nghĩa là không thể release.

AWS10 Tình huống tổng hợp: sự cố prod 9h00 — lần theo metric → log → trace → audit

What

9h00 sáng, alarm order-api-5xx-high kêu. Bạn có 15 phút để khoanh vùng. Quy trình chuẩn là đi từ triệu chứng (metric) tới chi tiết (log), tới luồng request (trace), và cuối cùng là thay đổi cấu hình/API (CloudTrail + Config) nếu nghi do ai đó vừa deploy.

How

Bốn bước, mỗi bước trả lời một câu hỏi và thu hẹp phạm vi trước khi sang bước sau.

1. Metriclỗi từ khi nào?
→khoanh thời gian
2. Logs Insightslỗi gì, ở đâu?
→requestId
3. X-Raynút nào chậm/lỗi?
→ai đổi gì?
4. CloudTrailaudit thay đổi
When

Áp dụng cho mọi incident runtime. Nếu nghi vấn liên quan tới hành động của con người/CI (deploy, xoá resource, đổi SG), bước 4 là bắt buộc — và AWS Config cho biết cấu hình đã lệch chuẩn ở đâu.

When NOT

Đừng bắt đầu bằng cách đọc log thô toàn bộ — sẽ ngập. Luôn bắt đầu từ metric để có mốc thời gian, rồi mới lọc log theo khoảng đó và theo requestId.

# Bước 1 — lỗi bắt đầu từ lúc nào (theo phút)
aws cloudwatch get-metric-statistics --namespace AWS/ApplicationELB \
  --metric-name HTTPCode_Target_5XX_Count \
  --start-time 2026-10-04T08:30:00Z --end-time 2026-10-04T09:20:00Z \
  --period 60 --statistics Sum

# Bước 2 — tìm dòng log lỗi trong đúng khoảng đó
# Logs Insights query:
#   fields @timestamp, @requestId, @message
#   | filter @message like /ERROR/ or @message like /500/
#   | sort @timestamp desc | limit 50

# Bước 3 — trace lỗi của service
aws xray get-trace-summaries \
  --start-time 2026-10-04T08:55:00Z --end-time 2026-10-04T09:15:00Z \
  --filter-expression 'service("order-api") AND error = true'

# Bước 4 — ai đã thay đổi gì quanh thời điểm đó
aws cloudtrail lookup-events \
  --start-time 2026-10-04T08:45:00Z --end-time 2026-10-04T09:05:00Z \
  --lookup-attributes AttributeKey=EventName,AttributeValue=UpdateService

Bẫy thi / Pitfall

Thứ tự này là "vũ khí" khi đề cho một sự cố mơ hồ. Nhớ cặp đôi kinh điển: thay đổi cấu hình / hành động API → CloudTrail; cấu hình sai chuẩn / drift → AWS Config. Còn ai gọi cái gì với dữ liệu S3 thường phải bật thêm CloudTrail data events (mặc định tắt, tính phí riêng).
