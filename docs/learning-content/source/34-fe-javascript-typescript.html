Module 34

JavaScript & TypeScript cho Fullstack

JavaScript hiện đại và TypeScript dùng hằng ngày ở fullstack: event loop, closure, async, module, type system, generic và kiểm tra kiểu ở ranh giới API.

JavaScript runtime — event loop, scope, this, prototype

Q1 Event loop hoạt động thế nào — vì sao setTimeout(fn, 0) chạy sau Promise.then?

What

JavaScript chạy single-threaded trên một call stack; event loop điều phối phần bất đồng bộ qua hai hàng đợi: microtask (Promise.then, queueMicrotask, MutationObserver) và macrotask (setTimeout, setInterval, I/O, UI event). Mỗi vòng: chạy hết call stack → xả sạch microtask queue → lấy một macrotask → render nếu cần → lặp lại.

Why

Microtask luôn được ưu tiên và phải cạn trước khi event loop nhích sang macrotask kế tiếp. Vì thế Promise.then chạy trước setTimeout 0 dù setTimeout được gọi trước — đây là thứ tự bắt buộc của spec, không phải chuyện timing ngẫu nhiên. Nắm sai thứ tự này là nguồn bug "log ra sai chỗ" rất phổ biến.

How
Call stack rỗng
↓
Drain hết microtask (Promise.then)
↓
Lấy 1 macrotask (setTimeout, I/O)
↓
Render / repaint → lặp lại

await trong async function thực chất cũng là microtask (phần sau await được schedule vào microtask queue), nên code sau await vẫn chạy trước setTimeout 0 kế tiếp.

When

Dùng khi cần debug thứ tự log, khi muốn defer việc nặng để UI kịp vẽ (setTimeout 0 hoặc scheduler.yield), hoặc khi cần gộp nhiều cập nhật trong một microtask.

When NOT

Không đổ việc nặng vào microtask: một chuỗi Promise.then tự gọi lại sẽ starvation — event loop không bao giờ tới bước render, UI đứng hình. Việc cần "sau khi browser vẽ" thì dùng requestAnimationFrame, không phải microtask.

console.log("A");
setTimeout(() => console.log("B"), 0);   // macrotask
Promise.resolve().then(() => console.log("C")); // microtask
console.log("D");

// output: A, D, C, B
// A, D = synchronous trên stack; C = microtask; B = macrotask
Use case

Autocomplete: gõ phím schedule một microtask để huỷ/refresh state, còn gọi API để trong setTimeout debounce — UI phản hồi ngay, không chờ network.

Pitfall / Interview trap

Người phỏng vấn hay trộn setTimeout 0, Promise.then và await trong một snippet rồi hỏi output. Nhớ: mỗi lần await nhường quyền cho microtask queue, và setTimeout bên trong then vẫn là macrotask — thứ tự thay đổi theo số lần nhường quyền.

Nói trong 60 giây
  • JS single-threaded: call stack + event loop + task queues.
  • Microtask (Promise.then) xả hết trước mỗi macrotask (setTimeout).
  • Vì vậy setTimeout 0 luôn sau Promise.then.
  • await = nhường quyền ở ranh giới microtask.
  • Microtask quá nhiều → starvation, UI không render.

Q2 Closure là gì — giải thích bẫy vòng lặp var + setTimeout và cách sửa

What

Closure là hàm "nhớ" được các biến thuộc scope nơi nó được tạo, kể cả sau khi scope đó đã kết thúc. Scope chain là chuỗi lexical environment: mỗi hàm giữ reference tới environment cha, lookup biến đi từ trong ra ngoài. Điểm cốt tử: closure bắt giữ binding (ô biến), không phải bản sao giá trị tại thời điểm tạo hàm.

Why

var là function-scoped: cả vòng lặp chỉ có một binding i, nên mọi callback đều trỏ vào cùng ô nhớ đó và đọc giá trị cuối cùng. let tạo binding mới cho từng iteration, nên mỗi callback giữ giá trị riêng — đó là lý do cùng một vòng lặp, đổi var thành let là output khác hẳn.

How
for (var i = 0; i < 3; i++)
↓
1 binding i dùng chung cho cả loop
↓
3 closure cùng trỏ vào i
i = 3 khi callback chạy
↓
Sửa: let (binding per iteration) hoặc IIFE chụp bản sao

Cách sửa phổ biến: (1) dùng let; (2) wrap trong IIFE truyền i vào tham số; (3) dùng arr.forEach((v) => ...) — callback nhận tham số riêng mỗi lần gọi.

When

Closure là nền của debounce/throttle, module private state (biến "riêng tư" mà không cần class), memoization, currying và React hooks (useState trả về hàm giữ state qua closure — cũng là gốc của bug stale closure).

When NOT

Không tự nhiên tạo closure bắt cả object lớn (cache, DOM node) rồi giữ nó sống mãi — GC không thu hồi được, gây memory leak trong SPA. Không "chữa" stale closure bằng cách thêm dependency mù quáng vào useEffect; hiểu binding trước.

// BUG: var dùng chung một binding
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0); // 3 3 3
}

// FIX 1: let tạo binding mới mỗi iteration
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log(j), 0); // 0 1 2
}

// FIX 2: IIFE chụp bản sao giá trị
for (var k = 0; k < 3; k++) {
  (function (n) {
    setTimeout(() => console.log(n), 0); // 0 1 2
  })(k);
}
Pitfall / Interview trap

Câu hỏi kinh điển "output của đoạn for-var-setTimeout là gì". Đáp án chuẩn: 3 3 3, vì cả ba closure chia sẻ một binding i. Cũng hay bị hỏi closure trong event listener tạo trong loop — cùng bản chất, cùng cách sửa.

Nói trong 60 giây
  • Closure = hàm nhớ scope nơi nó sinh ra.
  • Nó capture binding, không capture giá trị tại thời điểm tạo.
  • var: một binding cho cả loop → 3 3 3.
  • let: binding mỗi iteration → 0 1 2; hoặc dùng IIFE/forEach.
  • Closure mạnh cho debounce, module state, hooks.

Q3 this trong JavaScript xác định thế nào — vì sao truyền method làm callback bị mất this?

What

this phụ thuộc cách hàm được gọi (call-site), không phải nơi định nghĩa: gọi như method thì this là object trước dấu chấm; gọi hàm trần thì undefined (strict mode) hoặc globalThis; new thì là instance đang tạo; call/apply/bind thì do caller chỉ định. Arrow function ngoại lệ: nó không có this riêng, kế thừa this từ lexical scope bao quanh.

Why

Khi viết setTimeout(obj.method, 0), JS chỉ truyền function reference, object bị bỏ lại phía sau. Call-site bây giờ là một lời gọi hàm trần nên this = undefined → lỗi Cannot read properties of undefined ngay khi method chạm vào field của nó. Đây là bug số một khi truyền method làm callback.

How
obj.method()
this = obj
↓
const f = obj.method
f() → this = undefined
↓
Sửa: .bind(obj) hoặc arrow wrapper

Ba cách sửa: obj.method.bind(obj) (cố định this, tạo hàm mới mỗi lần gọi bind), arrow wrapper () => obj.method() (giữ this tại nơi gọi), hoặc khai báo method bằng class field arrow method = () => {...} để this luôn gắn với instance.

When

Bind/arrow khi truyền callback cho DOM listener, setTimeout, then/catch, hoặc khi destructure method ra khỏi object; call/apply khi cần mượn hàm hoặc gọi với this khác (Array.prototype.slice.call(arguments)).

When NOT

Không arrow-field hoá mọi method: mỗi instance mang bản hàm riêng (memory tăng, không share trên prototype). Không dùng arrow làm method khi cần this động (ví dụ method của class cần gọi qua super hoặc qua delegate). Không bind lặp trong render — tạo hàm mới mỗi lần, phá memoization.

const counter = {
  value: 0,
  inc() { this.value++; return this.value; },
};

setTimeout(counter.inc, 10);                  // this = undefined → TypeError
setTimeout(counter.inc.bind(counter), 10);    // OK
setTimeout(() => counter.inc(), 10);         // OK — arrow giữ this ngoài
Use case

React class component trước đây hay khai báo handleClick = () => this.setState(...) đúng vì arrow field giữ this là instance; functional component + hooks bỏ hẳn vấn đề này.

Pitfall / Interview trap

Bẫy hay gặp: truyền this.handleChange vào onChange rồi mất this; hoặc dùng arrow trong object literal khiến this trỏ ra ngoài thay vì vào object. Nhớ thứ tự ưu tiên: new > bind > method call > hàm trần, và arrow luôn "miễn nhiễm" với mọi quy tắc đó.

Nói trong 60 giây
  • this theo call-site, không theo nơi khai báo.
  • Truyền method làm callback → mất object → this undefined.
  • Sửa: bind, arrow wrapper, hoặc arrow class field.
  • Arrow không có this riêng — lấy từ scope ngoài.
  • Ưu tiên: new > bind > method > hàm trần.

Q4 Prototype chain và class trong JS hoạt động ra sao — instanceof kiểm tra gì?

What

Mỗi object có internal slot [[Prototype]] (đọc bằng Object.getPrototypeOf). Truy cập một property không có trên chính object sẽ đi theo prototype chain lên các prototype cha cho tới Object.prototype rồi null. class chỉ là cú pháp đường (sugar) trên prototype: method nằm trên ClassName.prototype, extends nối prototype chain, super() gọi constructor của lớp cha.

Why

Method nằm trên prototype dùng chung một bản cho mọi instance thay vì copy vào từng object — tiết kiệm bộ nhớ đáng kể khi tạo nhiều instance. instanceof không kiểm tra "kiểu tĩnh" mà duyệt prototype chain của object, tìm xem có gặp Constructor.prototype hay không; vì thế d instanceof Animal đúng khi Dog kế thừa Animal.

How
d (instance)
↓
Dog.prototype
↓
Animal.prototype
↓
Object.prototype → null (hết chain)

Lookup dừng ở lần gặp property đầu tiên — nên method ở lớp con "che" (shadow) method cùng tên ở lớp cha. Object.create(proto) tạo object với prototype chỉ định, đúng cơ chế bên dưới của class.

When

Dùng prototype/class khi cần chia sẻ hành vi giữa nhiều instance và muốn kế thừa có kiểm soát. Khi cần ghép nhiều nguồn hành vi mà không có quan hệ "là-một", ưu tiên composition hoặc mixin hơn là đào sâu cây kế thừa.

When NOT

Đừng xây cây kế thừa sâu 4–5 tầng chỉ để tái dùng vài hàm — dễ vỡ khi thay lớp giữa. Đừng nới quá nhiều thứ lên Object.prototype (monkey patching) vì có thể phá code của thư viện khác.

class Animal {
  constructor(public name: string) {}
  speak() { return `${this.name} makes a sound`; }
}

class Dog extends Animal {
  speak() { return `${this.name} barks`; }
}

const d = new Dog("Rex");
d instanceof Dog;                         // true
d instanceof Animal;                      // true — duyệt proto chain
Object.getPrototypeOf(Dog.prototype) === Animal.prototype; // true
Pitfall / Interview trap

instanceof thất bại qua các realm khác nhau: một array tạo trong iframe có prototype khác nên arr instanceof Array = false — dùng Array.isArray. Trong TypeScript, class có cả type và runtime value, còn interface chỉ tồn tại lúc compile nên không dùng được với instanceof.

Nói trong 60 giây
  • Property lookup đi theo prototype chain tới null.
  • class = sugar trên prototype, method share một bản.
  • extends nối prototype, super() gọi constructor cha.
  • instanceof duyệt proto chain tìm Constructor.prototype.
  • Kế thừa sâu dễ vỡ — ưu tiên composition.

Q5 Promise có những trạng thái nào — phân biệt Promise.all, allSettled, race, any và cách bắt lỗi đúng

What

Promise có ba trạng thái: pending → fulfilled hoặc rejected, chuyển đúng một lần và bất biến sau đó. Bốn combinator chính: all trả mảng kết quả nhưng reject ngay khi một cái fail (fail-fast); allSettled luôn fulfilled với mảng {status, value|reason}; race lấy cái settle đầu tiên bất kể thành công hay lỗi; any lấy cái fulfilled đầu tiên, reject bằng AggregateError nếu tất cả fail.

Why

Chọn sai combinator sinh bug khó thấy: dùng all khi một request phụ có thể fail sẽ làm cả màn hình lỗi dù phần lớn data đã về; dùng allSettled khi mọi kết quả đều bắt buộc sẽ khiến code phải tự kiểm tra status từng phần tử. Hiểu rõ semantics giúp viết code vừa đúng vừa ngắn.

How
new Promise / async fn
pending
↓
resolve() → fulfilled → .then()
reject() / throw → rejected → .catch()
↓
.finally() chạy dù thành công hay lỗi

.then nhận giá trị fulfilled; ném lỗi bên trong then rơi thẳng xuống catch gần nhất. catch không re-throw sẽ "nuốt" lỗi và biến chuỗi thành fulfilled.

When

Cần đủ hết dữ liệu để render → all. Cần partial result, chấp nhận vài cái lỗi (dashboard nhiều widget) → allSettled. Timeout hoặc "ai nhanh nhất" → race (kèm một promise reject sau N giây). Gọi nhiều mirror/replica, chỉ cần một cái thành công → any.

When NOT

Không dùng all như một cơ chế cancel: khi một promise reject, các promise còn lại vẫn chạy tiếp, không bị huỷ — muốn huỷ thật phải dùng AbortController. Không dùng any rồi bỏ quên AggregateError để mất hết thông tin lỗi gốc.

// fail-fast: một request lỗi là cả mảng reject
const [user, orders] = await Promise.all([fetchUser(id), fetchOrders(id)]);

// không throw: luôn trả về kèm status từng cái
const settled = await Promise.allSettled([fetchUser(id), fetchReport(id)]);
const ok = settled.filter((r) => r.status === "fulfilled");

// timeout pattern với race
const withTimeout = Promise.race([fetchSlow(), rejectAfter(3000)]);
Pitfall / Interview trap

Bẫy: Promise.all nhận mảng giá trị không phải Promise vẫn OK (coi như đã fulfilled); truyền một Promise không ở trong mảng mà gọi Promise.all(p1, p2) thì sai signature. Và lỗi hay gặp nhất: catch không re-throw làm lỗi biến mất im lặng, hoặc quên return promise trong then khiến chuỗi không chờ.

Nói trong 60 giây
  • Promise: pending → fulfilled | rejected, một lần, bất biến.
  • all fail-fast, allSettled luôn resolve, race ai settle trước, any ai fulfilled trước.
  • throw trong then rơi xuống catch gần nhất.
  • catch không re-throw sẽ nuốt lỗi.
  • all không huỷ các promise còn lại — cần AbortController.

Q6 async/await có những bẫy nào — quên await, xử lý lỗi song song, tuần tự hoá không cần thiết

What

Một async function luôn trả về Promise; await tạm dừng thân hàm (chỉ dùng được trong async) và nhường quyền qua microtask queue. Ba bẫy chuẩn: quên await nên nhận về một Promise thay vì value, và lỗi cũng thoát khỏi try/catch thành unhandled rejection; await tuần tự trong vòng lặp dù các call độc lập; await trong forEach không hề chờ.

Why

Tuần tự hoá không cần thiết làm latency bằng tổng các call thay vì giá trị lớn nhất — với 5 request 200ms là 1000ms thay vì 200ms. Quên await thì bug âm thầm: so sánh Promise với value luôn sai, điều kiện if luôn đúng, và stack trace báo unhandled rejection ở chỗ khác chứ không phải nơi gây lỗi.

How
await tuần tự: t1 + t2 + t3
↓
Promise.all([p1, p2, p3])
↓
Latency = max(t1, t2, t3)

Quy tắc: call độc lập thì khởi động hết rồi await một lần bằng Promise.all; call phụ thuộc (dùng kết quả trước làm input) thì bắt buộc tuần tự. Vòng lặp cần chờ thì dùng for...of với await, hoặc await Promise.all(items.map(fn)) khi thứ tự không quan trọng.

When

Dùng Promise.all khi gộp nhiều call API độc lập (user + settings + notification), hoặc khi nạp nhiều bảng song song. Khi cần lỗi từng phần thì bọc allSettled hoặc try/catch quanh từng call.

When NOT

Không Promise.all khi các call phải giữ thứ tự hoặc gây tác dụng phụ lên cùng tài nguyên (ghi đè cùng record). Không dùng forEach với callback async — nó trả undefined và không chờ gì cả. Không bọc await vào try chỉ để "cho chắc" mà bỏ qua việc hiểu promise nào fail khi nào.

// SAI: tuần tự, latency = t1 + t2
const u = await fetchUser(id);
const o = await fetchOrders(id);

// ĐÚNG: song song, latency = max(t1, t2)
const [user, orders] = await Promise.all([fetchUser(id), fetchOrders(id)]);

// SAI: forEach không chờ await
items.forEach(async (it) => { await save(it); });
// ĐÚNG
await Promise.all(items.map((it) => save(it)));
Pitfall / Interview trap

Trong try/catch, nếu chỉ await một lần mà quên await ở các call khác thì lỗi của call đó thoát ra ngoài và trở thành unhandled rejection. Bẫy thứ hai: return await bên trong try là cần thiết nếu muốn catch bắt lỗi — return promise không await sẽ thoát khỏi try trước khi lỗi xảy ra.

Nói trong 60 giây
  • async luôn trả Promise; await nhường microtask.
  • Quên await → nhận Promise, lỗi thành unhandled rejection.
  • Call độc lập thì Promise.all, latency = max.
  • Call phụ thuộc thì giữ tuần tự bằng for...of.
  • forEach + async không chờ — dùng Promise.all(map).

Q7 Vì sao immutability quan trọng — spread và structuredClone khác gì, và vì sao ưu tiên map/filter/reduce

What

Immutability nghĩa là không sửa object/array sau khi tạo mà sinh ra bản mới. Spread {...obj} và [...arr] là shallow copy — chỉ copy một tầng, object lồng bên trong vẫn chia sẻ cùng reference. structuredClone deep clone theo chuẩn structured clone (hỗ trợ Date, Map, Set, TypedArray, ArrayBuffer) nhưng không clone được function, DOM node hay class instance giữ được prototype.

Why

React quyết định re-render bằng so sánh reference (Object.is). Mutate state tại chỗ làm reference không đổi nên React "tưởng" state cũ và bỏ qua render — bug kinh điển "setState rồi mà UI không đổi". Immutability cũng giúp so sánh nhanh, dễ trace thay đổi và tránh side-effect ngầm giữa các hàm dùng chung một object.

How
state.tags.push(x) → cùng reference
↓
React so sánh Object.is → thấy bằng nhau
↓
Bỏ qua re-render → UI sai
↓
setX({...x, tags: [...x.tags, v]}) → reference mới → render

Nguyên tắc: chỉ copy đúng nhánh bị thay đổi (spread từng tầng trên đường tới field cần sửa), thay vì deep clone cả state mỗi lần cập nhật để giữ hiệu năng.

When

Dùng immutability trong reducer (Redux/Zustand), state của React, cache key theo reference, và mọi API trả về data dùng để so sánh lại về sau. map/filter/reduce trả về mảng mới — đúng tinh thần này; for + push sửa mảng gốc.

When NOT

Không structuredClone object/state lớn trong mỗi lần render — chi phí O(n) và mất hết memoization. Không dùng spread để "deep copy" rồi sửa object lồng (vẫn trỏ chung). Với vài chục phần tử, một vòng for tại chỗ nhanh hơn và không sai — immutability quan trọng ở ranh giới state/boundary, không phải mọi chỗ.

type Filters = { status: string; tags: string[] };

// shallow merge — tags vẫn trỏ về mảng cũ
setFilters((f) => ({ ...f, status: "DONE" }));

// đúng: copy nhánh bị đổi
setFilters((f) => ({ ...f, tags: [...f.tags, "urgent"] }));

// deep clone chỉ khi cần bản độc lập hoàn toàn
const snapshot = structuredClone(state);

// map/filter/reduce trả mảng mới, không mutate
const total = orders.filter((o) => o.status === "PAID").reduce((s, o) => s + o.amount, 0);
Pitfall / Interview trap

sort và reverse mutate mảng gốc dù tên nghe như hàm thuần — phải copy trước: [...arr].sort(). Object lồng trong spread vẫn chung reference (bug aliasing âm thầm). Và khi truyền cùng options object cho nhiều component, một nơi mutate sẽ ảnh hưởng tất cả.

Nói trong 60 giây
  • Immutability = tạo bản mới, không sửa tại chỗ.
  • Spread là shallow — object lồng vẫn share reference.
  • structuredClone deep nhưng không clone function/DOM.
  • React so sánh reference — mutate thì không re-render.
  • map/filter/reduce tạo mảng mới; sort/reverse thì mutate.

Q8 ES modules khác CommonJS thế nào — tree-shaking nhờ đâu và import vòng xử lý ra sao

What

CommonJS dùng require() đồng bộ, evaluate lúc runtime, gán module.exports; export là object thường nên có thể thay đổi sau. ESM dùng import/export tĩnh, được phân tích lúc build, export là live binding (import luôn đọc giá trị hiện tại của biến nguồn), import bị hoist, hỗ trợ top-level await, và mỗi module chỉ evaluate đúng một lần.

Why

Vì import/export của ESM là cấu trúc tĩnh, bundler (Vite, Rollup, webpack) dựng được dependency graph chính xác và biết export nào thực sự được dùng → tree-shaking loại được code chết. CommonJS mang tính động (export gán trong if, require trong hàm) nên rất khó tree-shake. ESM còn được browser hỗ trợ native qua type="module".

How
a.ts: import { b } from "./b"
b.ts: import { a } from "./a"
↓
ESM: hoist binding, tạo live binding trước khi evaluate
↓
Dùng biến trước khi module kia evaluate → TDZ / undefined
↓
Sửa: gọi hàm lúc runtime, hoặc tách module shared

Với import vòng, ESM vẫn tạo được binding nhưng giá trị có thể chưa gán xong tại thời điểm module khác thực thi — thường chỉ an toàn nếu truy cập bên trong function gọi sau đó, chứ không phải ở top-level.

When

Viết library/ứng dụng mới thì dùng ESM; khai báo "type": "module" trong package.json hoặc đặt đuôi .mjs để Node hiểu là ESM. Đánh dấu "sideEffects": false khi code thực sự không có side-effect lúc import để bundler shake mạnh hơn.

When NOT

Không trông cậy vào named import từ package CommonJS — bundler phải đoán shape nên có package chạy, có package vỡ (thường phải dùng default import rồi destructure). Không tạo import vòng rồi hy vọng hoist "chữa" được: nên refactor tách type/constant hoặc hàm dùng chung ra module thứ ba.

// format.ts — named export, bundler phân tích tĩnh → tree-shake được
export function formatPrice(v: number): string { return String(v); }
export function parsePrice(s: string): number { return Number(s); }

// consumer.ts — chỉ formatPrice được kéo vào bundle
import { formatPrice } from "./format";
import type { Order } from "./types"; // bị xoá hoàn toàn khi build

// CommonJS tương đương — khó tree-shake vì export là object động
// module.exports = { formatPrice, parsePrice };
Pitfall / Interview trap

Dùng import type để type không lọt vào bundle. Side-effect import (import "./polyfill") phá tree-shaking và có thể thứ tự chạy khác mong đợi. Khi trộn ESM/CJS trong Node, nhớ ESM không có __dirname/require — phải dùng import.meta.url.

Nói trong 60 giây
  • CJS động, runtime; ESM tĩnh, phân tích lúc build.
  • ESM export là live binding, module eval một lần.
  • Tree-shaking nhờ cấu trúc tĩnh của ESM.
  • import type và sideEffects: false giúp bundle nhỏ.
  • Import vòng: binding hoist nhưng dễ TDZ — nên tách module.

Q9 Khi nào dùng type, khi nào dùng interface — structural typing nghĩa là gì

What

interface mô tả shape của object, hỗ trợ declaration merging (khai báo cùng tên sẽ gộp) và có thể extends nhiều interface. type alias đặt tên cho bất kỳ kiểu nào: union, intersection, tuple, conditional type, mapped type — và không merge. Với shape object thuần, cả hai gần như tương đương; khác biệt nằm ở khả năng mở rộng và một vài ngữ cảnh compiler.

Why

TypeScript dùng structural typing: hai kiểu tương thích nếu cấu trúc khớp nhau, không cần khai báo implements hay quan hệ kế thừa danh nghĩa. Nghĩa là object literal nào có đủ field cần thiết đều gán được vào tham số — linh hoạt nhưng cũng là nguồn bug khi hai kiểu trùng cấu trúc mà ngữ nghĩa khác nhau (ví dụ hai kiểu đều có { id: string }).

How
interfacetype
Mô tả object shapeCóCó
Union / tuple / conditionalKhôngCó
Declaration mergingCó (gộp khai báo)Không (báo lỗi trùng tên)
Mở rộngextends nhiều interfaceintersection &
Class implementsCóCó (nếu là object type)

Thực tế: interface cho API/contract công khai có thể được nơi khác mở rộng; type cho union, DTO dẫn xuất và các kiểu phức tạp không biểu diễn được bằng interface.

When

Dùng interface cho shape object của service/repository, props của component, và mọi contract có thể được thư viện khác augment. Dùng type cho union trạng thái ("idle" | "loading" | "error"), tuple, và các kiểu dẫn xuất bằng utility type.

When NOT

Không dùng interface để biểu diễn union — không làm được, phải dùng type. Không lạm dụng declaration merging: vô tình trùng tên interface ở hai file sẽ gộp âm thầm và che lỗi. Không trộn lẫn hai phong cách trong cùng một file tuỳ tiện — chọn quy ước và giữ nhất quán để review dễ.

// interface: object shape, có thể được merge/extends
interface UserService {
  findById(id: string): Promise<User>;
}

// type: union trạng thái, tuple, kiểu dẫn xuất
type LoadState = "idle" | "loading" | "error";
type Point = [number, number];
type UserWithRole = User & { role: string };

// structural typing: không cần implements, chỉ cần đủ shape
function send(u: { email: string }) { /* ... */ }
send({ email: "a@b.com", name: "An" }); // OK — field thừa vẫn hợp lệ
Pitfall / Interview trap

Structural typing khiến hai kiểu khác ngữ nghĩa nhưng cùng shape hoán đổi cho nhau được — dùng branded type (type UserId = string & { __brand: "UserId" }) khi cần phân biệt. Object literal thừa field sẽ bị báo lỗi khi gán trực tiếp (excess property check) nhưng biến thì không — chi tiết hay bị hỏi.

Nói trong 60 giây
  • interface: object shape, merge được, extends nhiều.
  • type: union, tuple, conditional, kiểu dẫn xuất.
  • TS structural typing: cấu trúc khớp là tương thích.
  • Interface cho contract công khai; type cho union/utility.
  • Tránh merge vô tình — interface trùng tên sẽ gộp.

Q10 Generic và utility type dùng thế nào trong code API thật — Partial, Pick, Omit, Record, ReturnType

What

Generic tham số hoá kiểu, giữ quan hệ vào–ra mà không mất thông tin kiểu. Constraint extends giới hạn tập kiểu hợp lệ, ví dụ <T extends { id: string }> buộc mọi T phải có id. Utility types là mapped/conditional type dựng sẵn: Partial (mọi field thành optional), Pick/Omit (chọn/bỏ field), Record (map key → value), ReturnType (kiểu trả về của hàm).

Why

Generic cộng utility type loại bỏ hai thứ tệ: any và DTO trùng lặp. Một ResponseDto<T> dùng cho mọi entity; Omit<User, "id"> sinh CreateDto không cần id; Pick tạo view list gọn. Khi entity đổi field, mọi DTO dẫn xuất tự cập nhật — type là nguồn sự thật duy nhất.

How
Entity User { id, name, email, createdAt }
↓
Omit<User, "id" | "createdAt">
Pick<User, "id" | "name">
Partial<...>
↓
CreateDto / ListItem / PatchDto — tất cả dẫn xuất, không copy tay

Generic áp cho <T extends BaseEntity> ở tầng service xử lý create/getById; utility type áp cho DTO ở biên API. Kiểm tra bằng typeof kết hợp ReturnType để tránh khai báo kiểu trả về trùng lặp với implementation.

When

Repo/service dùng chung logic cho nhiều entity (BaseService<T>), hook React generic (useApi<T>()), factory function giữ kiểu (createStore<S>()), và mọi nơi cần DTO dẫn xuất từ một entity type duy nhất.

When NOT

Không generic hoá khi chỉ có đúng một kiểu dùng thực tế — thêm T mà không có lợi gì, chỉ khó đọc. Không dùng Record<string, any> như escape hatch: nó tắt kiểm tra kiểu ở đúng nơi cần nhất. Không dùng Partial cho request body bắt buộc field — sẽ chấp nhận payload thiếu dữ liệu.

interface User { id: string; name: string; email: string; createdAt: Date; }

type CreateUserDto = Omit<User, "id" | "createdAt">;
type UserSummary = Pick<User, "id" | "name">;
type UserPatch = Partial<CreateUserDto>;
type UserIndex = Record<string, UserSummary>;

// generic có constraint: T bắt buộc có id
async function createOne<T extends { id: string }>(dto: Omit<T, "id">): Promise<T> {
  return api.post<T>("/users", dto);
}

// ReturnType: lấy kiểu trả về, không khai báo lại
function toSummary(u: User): UserSummary { return { id: u.id, name: u.name }; }
type Summary = ReturnType<typeof toSummary>; // UserSummary
Use case

API paged: type Page<T> = { items: T[]; total: number; cursor?: string } rồi Page<UserSummary>, Page<Order> — một định nghĩa phục vụ mọi endpoint danh sách.

Pitfall / Interview trap

Omit/Pick chỉ hoạt động trên kiểu biết trước field; trên union hoặc generic chưa resolve có thể ra kiểu rộng hơn mong đợi. Partial làm field optional nhưng không làm nested optional — cần DeepPartial tự viết. Và generic quá lồng nhau (T xuất hiện sáu lần) là dấu hiệu abstraction sai.

Nói trong 60 giây
  • Generic giữ quan hệ kiểu vào–ra, tránh any.
  • Constraint extends giới hạn tập kiểu hợp lệ.
  • Omit/Pick/Partial sinh DTO từ một entity gốc.
  • Record cho map key→value; ReturnType suy kiểu trả về.
  • Generic chỉ đáng khi có hơn một kiểu dùng thật.

Q11 any và unknown khác nhau thế nào — narrowing, strict mode và kiểm tra kiểu ở ranh giới API

What

any tắt hoàn toàn kiểm tra kiểu: đọc/ghi/gọi gì cũng được và lỗi chỉ nổ ở runtime. unknown an toàn hơn: nhận mọi giá trị nhưng bắt buộc phải narrow (thu hẹp) trước khi dùng — qua typeof, instanceof, in, Array.isArray, discriminated union, hoặc user-defined type guard. Type chỉ tồn tại lúc compile và bị xoá khi build, nên dữ liệu từ network vẫn cần validate ở runtime.

Why

Vì type bị erase khi compile, TypeScript không bảo vệ bạn khỏi JSON sai shape từ API. Nếu dùng any ở biên, tính an toàn kiểu lan ngược ra toàn codebase và lỗi chỉ hiện khi người dùng gặp. unknown buộc phải kiểm tra ngay tại cửa vào — bug bị chặn tại ranh giới thay vì rải rác trong UI. Bật strict (gồm noImplicitAny, strictNullChecks) để compiler ép bạn làm điều đó.

How
JSON từ API → kiểu unknown
↓
Validate runtime: zod / io-ts / type guard
↓
Nuôi vào typed object → dùng an toàn
↓
Nếu fail → lỗi rõ ràng tại biên

Trong catch (e), JS cho e là unknown — phải kiểm tra e instanceof Error trước khi đọc e.message. Tránh as SomeType để "qua cửa" compiler: đó là ép kiểu không kiểm chứng, chỉ đổi chỗ lỗi runtime.

When

Dùng unknown cho mọi thứ đi vào từ bên ngoài: response API, JSON.parse, message từ worker, tham số của error handler. Dùng type guard khi cùng một kiểm tra dùng lại nhiều nơi để compiler hiểu nhánh if đã narrow kiểu.

When NOT

Không dùng any trong public API, props hay state — một any đủ để mất type của cả chuỗi gọi phía sau. Không dùng as thay validate. Không lạm dụng unknown cho biến nội bộ đã biết kiểu rõ — chỉ gây thêm bước narrow vô ích.

// any tắt kiểm tra; unknown buộc narrow trước khi dùng
function parseUser(raw: unknown): UserSummary {
  if (typeof raw !== "object" || raw === null) throw new Error("invalid payload");
  const o = raw as { id?: unknown; name?: unknown };
  if (typeof o.id !== "string") throw new Error("id required");
  return { id: o.id, name: String(o.name ?? "") };
}

// user-defined type guard — compiler hiểu nhánh đã narrow
function isUserSummary(v: unknown): v is UserSummary {
  return typeof v === "object" && v !== null && "id" in v;
}

// catch (e) → e là unknown
try { parseUser(payload); } catch (e) {
  if (e instanceof Error) console.error(e.message);
}

// tsconfig.json — bật strict để ép noImplicitAny + strictNullChecks
// { "compilerOptions": { "strict": true } }
Use case

Fetch layer: response luôn nhận unknown → qua schema (zod/io-ts) để parse → trả về kiểu đã khẳng định. Nếu schema và type lệch nhau, chính validator báo lỗi thay vì UI vỡ lúc runtime.

Pitfall / Interview trap

Narrowing không xuyên qua callback: biến đã narrow nhưng khi dùng trong closure (ví dụ setTimeout) TypeScript có thể mở rộng lại kiểu — copy ra biến const để giữ narrow. Và as không validate: JSON.parse(s) as User hoàn toàn không kiểm tra gì, đây là lỗi phổ biến trong review.

Nói trong 60 giây
  • any tắt kiểm tra; unknown buộc narrow.
  • Type bị erase khi compile — API cần validate runtime.
  • Narrow qua typeof, instanceof, in, type guard.
  • Bật strict để ép noImplicitAny và strictNullChecks.
  • Đừng dùng as để né validate.
