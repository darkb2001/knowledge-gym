VPC anatomy & thiết kế subnet

AWS1 VPC anatomy: CIDR, subnet, route table, IGW và NAT gateway

What

Amazon VPC là mạng riêng ảo cô lập trong một Region. Bạn tự chia dải IP bằng CIDR (thường /16 private RFC1918, cho phép /16–/28), rồi cắt thành các subnet. Mỗi subnet gắn đúng một Availability Zone — subnet không bao giờ trải qua nhiều AZ. Điều hướng nội/ngoại mạng do route table quyết định.

How

Internet vào VPC qua Internet Gateway (IGW) — subnet nào có route 0.0.0.0/0 → igw-… thì là public subnet. Chiều ra cho private subnet đi qua NAT gateway (đặt trong public subnet, có Elastic IP): nó cho phép kết nối ra ngoài nhưng chặn kết nối vào từ internet.

Internetclient
→0.0.0.0/0
IGWgắn vào VPC
→public subnet
NAT GWegress one-way
→private route
Private subnetkhông route tới IGW
aws ec2 create-vpc --cidr-block 10.0.0.0/16 --query 'Vpc.VpcId'
aws ec2 create-subnet --vpc-id vpc-0abc --cidr-block 10.0.1.0/24 \
  --availability-zone ap-southeast-1a
aws ec2 create-internet-gateway
aws ec2 attach-internet-gateway --vpc-id vpc-0abc --internet-gateway-id igw-0def
aws ec2 create-route --route-table-id rtb-pub \
  --destination-cidr-block 0.0.0.0/0 --gateway-id igw-0def
aws ec2 allocate-address --domain vpc   # Elastic IP cho NAT gateway
aws ec2 create-nat-gateway --subnet-id subnet-pub1a --allocation-id eipalloc-0aaa

Bẫy thi / Pitfall

NAT gateway thuộc một AZ — hỏng AZ là mất egress. Best practice: mỗi AZ một NAT gateway + route table riêng cho private subnet cùng AZ. NAT gateway không gắn được Security Group (chỉ NACL áp dụng).

AWS2 Tình huống: ứng dụng 3 tier — chọn subnet nào cho web, app, database?

What

Một ứng dụng web 3 tier (ALB → app → RDS) cần chia public subnet cho ALB, private subnet cho compute, private DB subnet cho RDS — nhân đôi trên ≥2 AZ để HA. Public subnet là subnet có route tới IGW; private subnet không có route ra IGW trực tiếp.

How

Trải 3 tầng lên 2 AZ, mỗi AZ một bộ subnet. App ở private subnet có thể ra internet (pull image, gọi API ngoài) qua NAT gateway, nhưng internet không vào được app/RDS.

Private subnet10.0.12.0/24 · app

  --destination-cidr-block 0.0.0.0/0 --nat-gateway-id nat-0abc
aws ec2 associate-route-table --route-table-id rtb-priv --subnet-id subnet-priv1a

# RDS nằm trong DB subnet group (không route ra internet)
aws rds create-db-subnet-group --db-subnet-group-name db-subnets \
  --subnet-ids subnet-db1a subnet-db1b --db-subnet-group-description "private db"

Use case

Đề DVA hay hỏi: "app trong private subnet cần cài package lúc khởi động" → thêm NAT gateway (hoặc VPC endpoint nếu chỉ cần AWS service). "RDS không được truy cập từ internet" → private subnet + SG nguồn là app SG.

Bẫy thi / Pitfall

Một subnet chỉ thuộc 1 AZ; muốn 2 AZ phải tạo 2 subnet. Nhiều AZ + cùng route table bị coi là "public" nếu route có IGW. Đừng nhầm "private" với "không có route nào" — private subnet vẫn thường có route đi NAT.

AWS3 Security Group vs Network ACL: stateful/stateless và thứ tự đánh giá

What

Security Group (SG) là firewall ở cấp instance/ENI, stateful: chỉ có rule allow, và return traffic tự động được phép. Network ACL (NACL) là firewall cấp subnet, stateless: có cả allow lẫn deny, đánh giá theo số thứ tự, và return traffic phải được mở tường minh.

How

Gói tin vào VPC đi qua NACL của subnet trước, rồi tới SG của resource. Vì SG stateful nên chỉ cần rule chiều request; NACL stateless nên phải mở cả chiều về (dải ephemeral port 1024–65535).

→app port 8080

# SG: cho phép app nhận traffic từ SG của ALB (reference SG, không dùng CIDR)
aws ec2 authorize-security-group-ingress --group-id sg-app \
  --protocol tcp --port 8080 --source-group sg-alb

# NACL stateless: phải mở CẢ hai chiều cho traffic về qua ephemeral ports
aws ec2 create-network-acl-entry --network-acl-id acl-0abc --ingress \
  --rule-number 100 --protocol tcp --port-range From=1024,To=65535 \
  --cidr-block 0.0.0.0/0 --rule-action allow

Bẫy thi / Pitfall

NACL mặc định cho phép tất cả; nếu tạo rule deny số thấp hơn rule allow thì nó chặn trước. Lỗi kinh điển: app kết nối ra được nhưng response bị nuốt vì NACL không mở ephemeral port chiều về. Debug: mở Flow Logs lọc REJECT.

AWS4 VPC Endpoint: Gateway (S3/DynamoDB) vs Interface (PrivateLink) và vì sao Lambda trong VPC cần chúng

What

Gateway endpoint chỉ hỗ trợ Amazon S3 và DynamoDB: gắn vào route table, miễn phí, không cần IGW/NAT. Interface endpoint dùng AWS PrivateLink: tạo ENI có private IP trong subnet, hỗ trợ hầu hết AWS service (Secrets Manager, SSM, ECR, KMS…), tính phí theo giờ + data xử lý.

How

Khi bạn gắn Lambda vào VPC, hàm chạy trong subnet private và mất internet mặc định. Muốn gọi S3/DynamoDB → dùng gateway endpoint (rẻ, không NAT); muốn gọi Secrets Manager/ECR → dùng interface endpoint hoặc NAT gateway cho egress.

Gateway endpointS3 · DynamoDB · route table · free
Interface endpointPrivateLink · ENI + SG · phần lớn service
NAT gatewayegress ra internet, không dùng cho endpoint
# Gateway endpoint cho S3 — gắn vào route table của private subnet
aws ec2 create-vpc-endpoint --vpc-id vpc-0abc \
  --service-name com.amazonaws.ap-southeast-1.s3 \
  --vpc-endpoint-type Gateway --route-table-ids rtb-priv

# Interface endpoint (PrivateLink) cho Secrets Manager — tạo ENI trong subnet
aws ec2 create-vpc-endpoint --vpc-id vpc-0abc \
  --service-name com.amazonaws.ap-southeast-1.secretsmanager \
  --vpc-endpoint-type Interface --subnet-ids subnet-priv1a

Bẫy thi / Pitfall

Gateway endpoint không có Security Group — kiểm soát bằng route table + endpoint policy. Interface endpoint có SG nên nhớ mở port 443 inbound từ SG của consumer. Đừng chọn "Gateway endpoint cho Secrets Manager" — sai, chỉ S3/DynamoDB mới có gateway endpoint.

Kết nối liên VPC & cân bằng tải

AWS5 Nối nhiều VPC: VPC peering vs Transit Gateway vs VPN/Direct Connect

What

VPC peering nối trực tiếp 1-1 hai VPC (cùng/khác account, cùng/khác Region) qua backbone AWS, không transitive, CIDR không được trùng. Transit Gateway (TGW) là hub-and-spoke: nối nhiều VPC + on-prem thành một mô hình, hỗ trợ transitive. Site-to-Site VPN đi qua internet có mã hoá IPsec; Direct Connect là đường truyền riêng vật lý, độ trễ ổn định.

How

Peering cần tạo ở cả hai VPC và cập nhật route table ở cả hai. Với nhiều VPC, nối full-mesh bằng peering rất tốn công (N VPC cần N×(N−1)/2 peering) → chuyển sang TGW hub-and-spoke.

VPC A10.0.0.0/16
↔1-1, non-transitive
VPC B10.1.0.0/16
→hub
Transit Gatewaynhiều VPC + on-prem
↔IPsec / private
On-premisesVPN hoặc Direct Connect
# VPC peering: tạo ở một bên, accept ở bên kia
aws ec2 create-vpc-peering-connection --vpc-id vpc-a --peer-vpc-id vpc-b
aws ec2 accept-vpc-peering-connection --vpc-peering-connection-id pcx-0abc

# Transit Gateway: gom hub-and-spoke

Bẫy thi / Pitfall

Peering không transitive: A peer B, B peer C nhưng A KHÔNG tới được C qua B. CIDR trùng nhau thì peering/TGW không định tuyến được (dùng private NAT gateway cho VPC trùng CIDR). Direct Connect một mình không mã hoá — thêm VPN cho mã hoá.

AWS6 Application Load Balancer: target group, health check, path/host routing

What

ALB hoạt động ở Layer 7 (HTTP/HTTPS/gRPC/WebSocket), terminate TLS, và định tuyến theo nội dung request. Một listener (vd 443) chứa nhiều rule; mỗi rule gồm condition (path, host, header, method, source IP) và action (forward/redirect/fixed-response). Rule đánh giá theo priority từ thấp tới cao, default rule chạy cuối.

How

Request khớp rule được forward vào một target group — nơi đăng ký target (instance, IP, Lambda). Health check cấu hình theo từng target group; target unhealthy bị loại khỏi vòng xoay. Đây là cách chạy nhiều microservice sau một ALB.

ALB/api/* · host
→forward
tg-apiECS tasks
→health /health
tg-webtarget Lambda
aws elbv2 create-target-group --name tg-app --protocol HTTP --port 8080 \
  --vpc-id vpc-0abc --target-type ip \
  --health-check-path /health --health-check-interval-seconds 15
aws elbv2 create-load-balancer --name alb-app --type application \
  --scheme internet-facing --subnets subnet-pub1a subnet-pub1b --security-groups sg-alb
aws elbv2 create-rule --listener-arn arn:aws:elasticloadbalancing:...:listener/app/... \
  --priority 10 --conditions Field=path-pattern,Values='/api/*' \
  --actions Type=forward,TargetGroupArn=arn:aws:...:targetgroup/tg-app/...

Bẫy thi / Pitfall

ALB không có static IP — DNS name thay đổi IP. Weighted target group không tự failover sang target group khỏe khi một group rỗng. Cross-zone load balancing của ALB bật mặc định; của NLB thì tính phí khi bật.

AWS7 So sánh: ALB vs NLB (Layer 7 vs Layer 4, static IP, extreme performance)

What

ALB là load balancer Layer 7 cho HTTP/HTTPS với định tuyến nâng cao. NLB là Layer 4 (TCP/UDP/TLS), xử lý hàng triệu request/giây với độ trễ cực thấp, giữ nguyên source IP client, và cung cấp static IP / Elastic IP mỗi AZ. CLB (Classic) là thế hệ cũ, tránh dùng cho hệ mới.

How

Chọn theo tầng giao thức: cần route theo path/host, HTTP/2, WAF → ALB. Cần TCP/UDP thuần, IP tĩnh, cực nhanh, PrivateLink → NLB. Muốn cả hai: đặt NLB làm mặt tiền (target type = alb) để có static IP + PrivateLink, còn ALB làm định tuyến nâng cao.

ALB — L7path/host, HTTP/2, gRPC, WAF
NLB — L4triệu req/s, static IP, TCP/UDP
CLB — legacyEC2-Classic, không dùng mới
Global Acceleratoranycast IP toàn cầu
# NLB với static Elastic IP mỗi AZ (ALB không làm được điều này)
aws elbv2 create-load-balancer --name nlb-app --type network \
  --scheme internet-facing \
  --subnet-mappings SubnetId=subnet-pub1a,AllocationId=eipalloc-0aaa \
                    SubnetId=subnet-pub1b,AllocationId=eipalloc-0bbb

Bẫy thi / Pitfall

ALB không thể làm Layer 4; nếu đề yêu cầu "làm việc với TCP thuần hoặc IP tĩnh", đáp án là NLB. Nếu đề cần "static IP cho ALB", câu trả lời là đặt NLB phía trước ALB (NLB target type = application load balancer).

AWS8 Lambda/ECS sau ALB và deploy blue/green bằng weighted target group

What

ALB target group nhận nhiều loại target: instance, IP (ECS/Fargate), hoặc Lambda. Với deploy an toàn, tạo 2 target group (blue = bản cũ, green = bản mới) và dùng weighted forward để chuyển dần traffic. ECS cũng hỗ trợ deployment type blue/green (CodeDeploy) ngoài rolling update.

How

Mỗi target group có trọng số 0–999; đặt green weight nhỏ trước, theo dõi metric, rồi tăng dần tới 100 (canary/blue-green). Rollback chỉ là đổi trọng số về 0 cho green.

AWS9 Tình huống: app ở private subnet không kết nối được RDS/S3 — kiểm gì, theo thứ tự nào?

What

Khi app trong private subnet không reach được RDS (nội VPC) hoặc S3 (ra AWS), nguyên nhân nằm ở một trong bốn lớp: route table, NACL, security group, hoặc endpoint/DNS. Debug theo thứ tự từ ngoài vào trong để loại trừ nhanh.

How

Kiểm route trước (có route tới đích không), rồi NACL (stateless — đủ hai chiều chưa), rồi SG (inbound/outbound đúng nguồn/port chưa), cuối cùng là endpoint + DNS. Đối chiếu triệu chứng để chốt nguyên nhân.

Use case

Công cụ đắc lực: Reachability Analyzer phân tích path giữa source/destination để chỉ đúng lớp chặn, và VPC Flow Logs để xem ACCEPT/REJECT thực tế. Nhớ: SG stateful nên hiếm khi là thủ phạm của return traffic; NACL stateless mới hay chặn chiều về.
