Module 13

Design Patterns

23 Gang of Four patterns + SOLID, anti-patterns, và cách Spring Framework áp dụng sẵn — trọng tâm phỏng vấn Java backend & WMS domain.

Creational Patterns

Q1 Singleton — eager, lazy, Bill Pugh, enum

What

Singleton đảm bảo class chỉ có một instance duy nhất trong JVM và cung cấp điểm truy cập global (getInstance()). Các biến thể: Eager (static final field khởi tạo khi class load), Lazy (double-checked locking với volatile), Bill Pugh (static holder class — JVM lazy init thread-safe), Enum Singleton (Joshua Bloch — chống reflection & serialization break).

Why

Dùng khi tài nguyên đắt hoặc phải unique: connection pool config, logger facade, registry. Tránh tạo nhiều instance gây inconsistency (2 config khác nhau) hoặc lãng phí memory. Trong Spring, bean scope singleton (default) quản lý lifecycle thay vì tự implement GoF Singleton.

How
Client gọi getInstance()
↓
Bill Pugh Holder
Enum INSTANCE
Spring @Scope singleton

Eager: đơn giản, thread-safe, nhưng load sớm. Lazy DCL: cần volatile từ Java 5+. Bill Pugh: inner static class chỉ load khi getInstance() được gọi — không cần synchronized. Enum: public enum Config { INSTANCE; } — best practice nếu không dùng DI container.

When

Config manager, metric registry, in-memory cache coordinator. Trong interview: so sánh 4 cách và giải thích tại sao enum/Bill Pugh tốt hơn lazy DCL thuần.

When NOT

Không dùng Singleton cho stateful service có request context (user session) — vi phạm thread-safety. Không dùng thay DI container trong Spring — test khó (global state), hidden dependency. Không implement thủ công nếu Spring bean đủ — over-engineering.

Use case

Spring: mọi @Service mặc định singleton — một instance InventoryService inject vào nhiều controller; container đảm bảo single instance per context.

Pitfall

Reflection (setAccessible) và deserialization có thể tạo instance thứ 2 nếu không chặn trong readResolve() hoặc dùng enum. Double-checked locking thiếu volatile → broken trên JMM cũ.

// Bill Pugh — khuyến nghị khi không có Spring
public class DbConfig {
  private DbConfig() {}
  private static class Holder {
    static final DbConfig INSTANCE = new DbConfig();
  }
  public static DbConfig getInstance() { return Holder.INSTANCE; }
}

// Enum — chống reflection/serialization
public enum AppRegistry { INSTANCE; }
Nói trong 60 giây
  • Singleton = 1 instance, global access — config, registry.
  • Eager load sớm; Lazy DCL cần volatile; Bill Pugh dùng holder class — JVM thread-safe.
  • Enum singleton là best practice thuần Java.
  • Spring bean scope singleton ≠ GoF — container quản lý, dễ test hơn.
  • Tránh singleton stateful — race condition giữa requests.

Q2 Factory Method vs Abstract Factory

What

Factory Method: subclass quyết định instantiate class con nào (createDocument() → PDF/Word). Abstract Factory: interface factory tạo family related products (GUIFactory → Button + Checkbox cùng theme Win/Mac).

Why

Tách client khỏi concrete class — tuân OCP & DIP. Factory Method khi chỉ 1 product hierarchy. Abstract Factory khi nhiều product phải consistent (cùng DB driver family + connection + statement).

How

Factory Method: abstract creator + factoryMethod() override ở subclass. Abstract Factory: interface với nhiều createX(), concrete factory implement full set.

When

Factory Method: framework hook (Spring BeanFactory tạo bean theo type). Abstract Factory: chọn stack integration (SAP vs Oracle EBS message format + parser + validator cùng bộ).

When NOT

Chỉ 1 implementation — gọi new hoặc DI đủ. Không nhầm Simple Factory (static method) với GoF Factory Method — interview hay hỏi.

Factory Method

  • 1 product type / hierarchy
  • Inheritance — subclass override
  • DocumentCreator.create()

Abstract Factory

  • Family nhiều product liên quan
  • Composition — inject factory
  • UIFactory.createButton() + createCheckbox()
Use case

WMS: LabelPrinterFactory (Factory Method) tạo Zebra vs Honeywell printer. WcsIntegrationFactory (Abstract Factory) tạo cặp MessageEncoder + PlcAdapter + AckHandler cho từng vendor WMS/Muratec.

Pitfall

Thêm product mới vào Abstract Factory → sửa interface tất cả implement — vi phạm OCP; cân nhắc Factory Method + registry thay vì AF cứng.

interface PickTaskFactory {
  PickTask createTask(OrderLine line); // Factory Method style
}
class BatchPickFactory implements PickTaskFactory {
  public PickTask createTask(OrderLine line) { return new BatchPickTask(line); }
}
Nói trong 60 giây
  • Factory Method: 1 sản phẩm, subclass quyết định class con.
  • Abstract Factory: cả họ sản phẩm compatible — button + checkbox cùng theme.
  • Simple Factory không phải GoF pattern — chỉ helper static.
  • Spring BeanFactory là Factory Method ở scale framework.
  • Chọn FM khi 1 hierarchy; AF khi family consistency.

Q3 Builder Pattern

What

Tách construction complex object khỏi representation — build từng bước qua fluent API (builder().sku().qty().build()).

Why

Constructor telescoping (10 params) khó đọc; object nhiều optional field; immutable object cần validate trước khi expose.

How

Inner static Builder, chain methods return this, build() gọi private constructor. Java 16+ record có thể dùng compact constructor; Lombok @Builder generate code.

When

DTO phức tạp, HTTP request builder, test data builder, config object nhiều flag.

When NOT

Object 2–3 field bắt buộc — constructor hoặc record đủ. Không mix Builder với JavaBean setter mutable — mất immutability.

Use case

AllocationRequest.builder().orderId("O1").priority(HIGH).allowPartial(true).build() — WMS allocation gửi sang optimization engine.

Pitfall

Quên validate trong build() → invalid object. Builder không thread-safe nếu share giữa threads — tạo builder per thread.

Shipment s = Shipment.builder()
  .trackingNo("TRK-99")
  .carrier(Carrier.DHL)
  .build();
Nói trong 60 giây
  • Builder = step-by-step construction, fluent API.
  • Giải quyết telescoping constructor và nhiều optional params.
  • build() validate + gọi private ctor → immutable safe.
  • Lombok @Builder phổ biến trong Spring DTO.
  • Đơn giản thì record/ctor — đừng over-use Builder.

Q4 Prototype Pattern

What

Clone object có sẵn thay vì new từ đầu — shallow copy (clone()) hoặc deep copy (serialize/copy constructor).

Why

Tạo object tốn kém (load template từ DB/file) hoặc cần bản sao gần giống với vài field khác — pick wave template, report layout.

How

Implement Cloneable + override clone(), hoặc copy constructor / factory from(other). Deep copy: manual recursive, JSON round-trip, hoặc library.

When

Game entity spawn, document template, sandbox order từ production order snapshot.

When NOT

Object có shared mutable nested refs mà chỉ shallow clone — bug silent aliasing. Prefer immutable + builder thay clone nếu structure đơn giản.

Pitfall

Cloneable marker interface broken design — không bắt buộc public clone(); deep vs shallow hay sai với List bên trong.

public class WaveTemplate implements Cloneable {
  private List<String> zones;
  public WaveTemplate deepCopy() {
    WaveTemplate c = (WaveTemplate) super.clone();
    c.zones = new ArrayList<>(zones);
    return c;
  }
}
Nói trong 60 giây
  • Prototype = clone thay vì new — tiết kiệm init cost.
  • Shallow copy share nested refs; deep copy duplicate tree.
  • Cloneable interface yếu — copy constructor rõ ràng hơn.
  • WMS: duplicate wave template cho shift mới.
  • Immutable objects ít cần prototype.

Structural Patterns

Q5 Adapter Pattern

What

Chuyển interface của class hiện có sang interface client mong đợi — “cắm adapter” giữa incompatible APIs.

Why

Tích hợp legacy/third-party không sửa source gốc; tuân ISP — client chỉ phụ thuộc interface mình cần.

How

Class adapter (extends adaptee + implements target) hoặc Object adapter (compose adaptee — linh hoạt hơn, Java khuyến nghị).

When

Wrap SAP RFC SDK, PLC vendor SDK, payment gateway cũ behind InventoryPort interface nội bộ.

When NOT

Có thể refactor adaptee trực tiếp (owned code) — adapter thêm indirection. Không nhầm với Facade (đơn giản hóa subsystem, không đổi interface).

Use case

LegacyWcsAdapter implements WcsPort — translate REST nội bộ sang TCP binary protocol PLC cũ.

class SapInventoryAdapter implements InventoryPort {
  private final SapRfcClient sap;
  public StockLevel getStock(String sku) {
    return map(sap.callBapi(sku));
  }
}
Nói trong 60 giây
  • Adapter = bridge incompatible interface — integration classic.
  • Object adapter (compose) preferred trong Java.
  • Khác Facade: Adapter đổi interface; Facade đơn giản hóa.
  • WMS tích hợp ERP/PLC qua adapter layer.
  • Owned code nên refactor thay wrap vô hạn.

Q6 Decorator vs Proxy

What

Decorator bọc object để thêm behavior (logging, cache, compress) — cùng interface, stack nhiều lớp. Proxy kiểm soát truy cập — lazy load, security, remote, transaction wrapper.

Why

Tránh subclass explosion (10 combo feature = 10 subclass). Decorator = Open/Closed — thêm behavior runtime. Proxy = indirection + control (Spring AOP, Hibernate lazy loading).

How

Cả hai: implement cùng interface, delegate tới wrapped object. Decorator nhấn enhance before/after call. Proxy nhấn control (có thể không gọi delegate).

When

Decorator: new CachedUserService(new LoggingUserService(delegate)). Proxy: Spring tạo JDK dynamic proxy / CGLIB cho @Transactional, @Cacheable.

When NOT

Cross-cutting toàn app → AOP framework thay manual decorator chain. Không decorator cho logic business core — khó trace.

Decorator

  • Thêm chức năng (stackable)
  • Client biết (thường) có wrap
  • Java I/O streams classic

Proxy

  • Kiểm soát access / lazy / remote
  • Client có thể không biết proxy
  • Spring AOP, RMI stub
Use case

Spring: @Transactional → proxy mở/commit TX trước/sau method. InputStream decorator chain: BufferedInputStream(new FileInputStream(...)).

// JDK Dynamic Proxy — Spring dùng khi interface có sẵn
OrderService proxy = (OrderService) Proxy.newProxyInstance(
  cl, new Class<>[]{OrderService.class},
  (Object target, Method m, Object[] args) -> {
    System.out.println("TX begin");
    try { return m.invoke(delegate, args); }
    finally { System.out.println("TX commit"); }
  });
Nói trong 60 giây
  • Decorator thêm behavior; Proxy kiểm soát truy cập.
  • Cùng structure wrap-delegate — intent khác nhau.
  • Java I/O = decorator; Spring @Transactional = proxy.
  • JDK proxy cần interface; CGLIB subclass cho class concrete.
  • Self-invocation trong class bypass proxy — interview trap.

Q7 Facade Pattern

What

Interface đơn giản che subsystem phức tạp — một entry point (WmsFacade.releaseOrder()) gọi allocation + inventory + WCS + notification.

Why

Giảm coupling client ↔ nhiều service; onboarding dev nhanh; boundary rõ cho module.

When

Application service layer trong DDD, REST controller gọi 1 facade thay 5 repository.

When NOT

Facade trở thành God Object chứa mọi logic — tách use-case service. Không thay thế domain model rich behavior.

Pitfall

Anemic Facade — chỉ pass-through không orchestration — thêm layer vô ích.

Nói trong 60 giây
  • Facade = cửa vào đơn giản cho subsystem phức tạp.
  • Khác Adapter: không đổi interface bên ngoài legacy.
  • Spring @Service orchestration thường là facade.
  • Tránh God Facade — split theo use case.

Q8 Composite Pattern

What

Cây part-whole: component interface chung cho leaf và composite — client xử lý uniform (getWeight() trên cả pallet lẫn carton).

Why

Recursive structure: menu, org chart, BOM (bill of materials), location tree (warehouse → zone → aisle → bin).

How

Component interface; Leaf; Composite chứa List<Component>, delegate operation xuống children.

When

Tính tổng capacity subtree location; render nested pick list; permission tree.

When NOT

Hierarchy cố định 2 level — list đơn giản đủ. Composite + visitor phức tạp khi chỉ cần SQL recursive CTE.

interface LocationNode { int availableSlots(); }
class Zone implements LocationNode {
  private final List<LocationNode> aisles;
  public int availableSlots() {
    return aisles.stream().mapToInt(LocationNode::availableSlots).sum();
  }
}
Nói trong 60 giây
  • Composite = tree uniform — leaf và group cùng interface.
  • WMS location hierarchy, BOM kitting classic.
  • Operation recursive trên root → propagate children.
  • Đừng dùng khi cấu trúc phẳng đơn giản.

Behavioral Patterns

Q9 Strategy Pattern

What

Định nghĩa họ algorithm, encapsulate từng cái, interchange runtime — context delegate tới Strategy interface.

Why

Tránh if/else/switch theo type dài; OCP — thêm strategy mới không sửa context. Spring DI inject strategy bean theo profile/qualifier.

How

Interface AllocationStrategy, implementations FifoStrategy, NearestBinStrategy; context gọi strategy.allocate(order).

When

Sorting (Spring Comparator beans), pricing rules, payment method, shipping cost calculator.

When NOT

Chỉ 2 cố định variant không đổi — enum + method đủ. Không nhầm State — Strategy client chọn algorithm; State transition nội bộ entity.

Strategy

  • Algorithm interchangeable
  • Client/config chọn strategy
  • Không đổi khi entity “tự” chuyển

State

  • Hành vi đổi theo internal state
  • Transition do event nội bộ
  • Order CREATED → ALLOCATED → PICKING
Use case

WMS: @Qualifier("fifo") AllocationStrategy vs fefo inject vào AllocationService — đổi rule theo customer SLA không sửa service.

public class AllocationService {
  private final AllocationStrategy strategy;
  public AllocationService(AllocationStrategy strategy) { this.strategy = strategy; }
  public void allocate(Order o) { strategy.execute(o); }
}
Nói trong 60 giây
  • Strategy = swap algorithm runtime — DI friendly.
  • Thay cho switch/if monster — OCP.
  • Khác State: strategy do client chọn; state tự chuyển theo lifecycle.
  • Spring inject nhiều impl cùng interface.
  • WMS allocation FIFO/FEFO/nearest bin.

Q10 State Pattern — WMS order flow

What

Object đổi behavior khi internal state đổi — mỗi state là class implement interface chung (OrderState.onPickComplete()).

Why

Order lifecycle WMS: CREATED → ALLOCATED → RELEASED → PICKING → PICKED → SHIPPED. Switch/if theo status field scattered → bug illegal transition (pick khi chưa allocate).

How
CREATED
allocate()
ALLOCATED
releaseToWcs()
RELEASED
PICKING → SHIPPED

Context (WmsOrder) giữ reference OrderState current; method delegate current.release(this); state mới set trong transition hợp lệ.

When

State machine rõ ràng, nhiều action phụ thuộc status, cần guard illegal transition — bổ sung Spring State Machine hoặc enum+transition table nếu đơn giản.

When NOT

2–3 status tĩnh — enum status + validation đủ. Không duplicate State pattern lẫn Strategy — nếu chỉ đổi algorithm không đổi lifecycle thì Strategy.

Use case

WMS: PickingState chỉ cho confirmPick(); gọi khi ALLOCATED → throw IllegalStateException — bảo vệ inventory consistency trước khi gửi WCS.

Pitfall

Quên persist state transition atomically — DB status PICKING nhưng in-memory vẫn RELEASED sau crash. Dùng TX + optimistic lock trên status column.

class AllocatedState implements OrderState {
  public void release(WmsOrder ctx) {
    ctx.sendToWcs();
    ctx.setState(new ReleasedState());
  }
  public void confirmPick(WmsOrder ctx) {
    throw new IllegalStateException("Not released yet");
  }
}
Nói trong 60 giây
  • State = behavior thay đổi theo lifecycle nội bộ object.
  • WMS order flow là ví dụ sát phỏng vấn domain.
  • Mỗi state class chặn illegal transition.
  • Khác Strategy: transition do event, không phải user chọn algorithm.
  • Persist status + TX — tránh desync sau crash.

Q11 Observer Pattern

What

One-to-many dependency: subject notify observers khi state đổi — push model (callback) hoặc pull.

Why

Decouple publisher/subscriber — inventory thay đổi → notify dashboard, audit, Kafka without tight coupling.

How

Java legacy Observable/Observer deprecated; modern: Spring ApplicationEventPublisher, @EventListener, reactive streams.

When

Domain events: OrderShippedEvent → email, ERP sync, metrics.

When NOT

Critical synchronous workflow cần guaranteed order — dùng orchestration/Saga thay fire-and-forget observer. Tránh observer leak (quên unsubscribe).

Use case

publishEvent(new BinEmptyEvent(binId)) — listener trigger replenishment task và Andon alert.

@Component
class ReplenListener {
  @EventListener
  void onEmpty(BinEmptyEvent e) { replenService.schedule(e.binId()); }
}
Nói trong 60 giây
  • Observer = publish-subscribe decoupling.
  • Spring ApplicationEvent = Observer trong ecosystem.
  • Async @EventListener — cẩn thận ordering & failure.
  • Critical path dùng Saga không pure observer.

Q12 Template Method Pattern

What

Abstract class định nghĩa skeleton algorithm (processOrder()), subclass override hook steps (validate(), allocate()).

Why

DRY flow chung, customize điểm khác — Hollywood principle: “don’t call us, we’ll call you”.

How

Final template method gọi abstract/protected hooks; Spring JdbcTemplate.query() — callback là hook variaton.

When

Batch job framework, import pipeline (parse → validate → persist), servlet GenericServlet.service().

When NOT

Cần composition thay inheritance — Strategy + pipeline rõ hơn Template Method. Java single inheritance hạn chế.

Use case

JdbcTemplate.execute(ConnectionCallback) — template lo acquire/release connection; callback chỉ SQL logic.

Nói trong 60 giây
  • Template Method = skeleton in base class, hooks in subclass.
  • JdbcTemplate là ví dụ Spring canonical.
  • final template method tránh subclass phá flow.
  • Prefer composition nếu nhiều variation orthogonal.

Q13 Command Pattern

What

Encapsulate request thành object — Command.execute(), hỗ trợ undo, queue, log, retry.

Why

WCS instruction queue: mỗi lệnh AGV là command object persist + replay; audit trail; transactional outbox.

How

Interface Command, concrete MoveAgvCommand, invoker CommandQueue push/pop execute.

When

Undo/redo UI, job scheduler, macro operations, CQRS write side.

When NOT

Simple CRUD one-shot — method call đủ. Command object overhead khi không cần queue/undo.

Use case

WMS release wave: ReleaseWaveCommand serialize vào DB queue; worker retry khi WCS timeout — idempotent by commandId.

record ReleasePickCommand(String taskId) implements WcsCommand {
  public void execute(WcsGateway gw) { gw.releaseTask(taskId); }
}
Nói trong 60 giây
  • Command = request as object — queue, undo, audit.
  • WCS/AGV instruction queue classic domain.
  • Invoker decouple sender/receiver.
  • CQRS command side cùng tinh thần.
  • Đừng wrap mọi service method thành command.

Q14 Chain of Responsibility

What

Chain handlers — mỗi handler xử lý hoặc pass next; client gửi request tới head chain.

Why

Servlet Filter chain, Spring Security filter chain, validation pipeline, logging middleware.

When

Order validation: format → credit check → inventory → compliance — dừng sớm nếu fail.

When NOT

Luôn cần mọi bước chạy — pipeline parallel hoặc single service rõ hơn. Chain quá dài khó debug.

AuthFilter
RateLimit
Controller
Nói trong 60 giây
  • Chain of Responsibility = linked handlers pass-or-process.
  • Servlet/Spring Security filter chain real-world.
  • Early exit khi handler xử lý xong.
  • WMS validation pipeline ví dụ tốt.

Q15 Iterator Pattern

What

Truy cập collection tuần tự không expose internal structure — java.util.Iterator, enhanced for-loop.

Why

Uniform traversal; support multiple iterator types (forward/backward); fail-fast vs concurrent iterator.

When

Custom collection (BinGrid); lazy pagination iterator over DB cursor.

When NOT

Stream API functional pipeline đủ — không reinvent Iterator. remove() during iteration → ConcurrentModificationException.

Pitfall

Modify collection while iterating without iterator.remove() — fail-fast. Dùng removeIf hoặc copy-on-write.

Nói trong 60 giây
  • Iterator = traverse without exposing internals.
  • Built into Java Collections Framework.
  • Fail-fast vs ConcurrentModificationException.
  • Streams often replace manual iterator loops.

Q16 Mediator Pattern (tóm tắt)

What

Object trung gian điều phối communication giữa colleagues — colleagues không reference trực tiếp lẫn nhau.

Why

Giảm mesh coupling N×N — chat room, air traffic control, event bus central.

When

Spring Mediator (CQRS bus), message broker abstraction, UI dialog coordinator.

When NOT

Mediator thành God Object — split bounded context. Simple 2-component talk — direct call OK.

Nói trong 60 giây
  • Mediator = central hub, colleagues decoupled.
  • Event bus / CQRS mediator cùng idea.
  • Tránh God mediator — giữ scope nhỏ.
  • Interview: biết khái niệm, ít code deep hơn Strategy/State.

SOLID, Anti-patterns & Spring

Q17 SOLID liên quan Design Patterns thế nào?

What

SOLID là nguyên tắc thiết kế; Design Patterns là giải pháp cụ thể thường hiện thực hóa các nguyên tắc đó.

Why

Interviewer muốn thấy bạn không học thuộc pattern mà hiểu vì sao pattern tồn tại — map pattern → principle.

Nguyên tắcPattern minh họa
S — Single ResponsibilityMỗi State class một trách nhiệm transition; Command tách request khỏi handler
O — Open/ClosedStrategy/Decorator thêm behavior không sửa context
L — Liskov SubstitutionDecorator/Proxy phải substitute được interface gốc
I — Interface SegregationAdapter expose interface nhỏ; tránh fat factory
D — Dependency InversionFactory Method, Strategy — depend abstraction Spring inject
When NOT

Ép mọi class vào pattern để “đúng SOLID” — YAGNI. SOLID là hướng dẫn, không phải checklist 5 pattern mỗi feature.

Nói trong 60 giây
  • SOLID = why; Patterns = how cụ thể.
  • Strategy/Decorator → OCP; DI → DIP.
  • State/Command → SRP tách concern.
  • LSP: subclass/proxy không phá contract.
  • Đừng pattern cho pattern — YAGNI.

Q18 Anti-patterns thường gặp

What

Anti-pattern = giải pháp tưởng hữu ích nhưng hậu quả xấu lặp lại. Liên quan: God Object, Anemic Domain Model, Golden Hammer (mọi thứ đều Singleton/Factory).

Why

Nhận biết over-engineering trong interview — senior phải biết khi không dùng pattern.

How

God Object: class 3000 dòng làm mọi thứ — refactor SRP + facade/use-case services. Anemic: entity chỉ getter/setter, logic trong service — cân bằng rich domain khi invariant phức tạp (order state). Pattern over-use: 5 pattern cho CRUD đơn giản.

When

Code review, thiết kế mới — hỏi “ có cần pattern này nếu requirement đổi 1 lần/năm không?”

When NOT

Coi Anemic luôn sai — với Spring JPA entity, logic nhẹ trong @Service chấp nhận được; rich domain khi behavior gắn chặt data (state machine trong entity).

Pitfall

Interview trap: “Design Patterns always improve code” — sai nếu complexity > benefit. Prefer clarity over pattern name-dropping.

Nói trong 60 giây
  • God Object = SRP violation extreme.
  • Anemic domain = data bag, logic ở service — trade-off JPA.
  • Golden Hammer = lạm dụng pattern.
  • Senior biết When NOT quan trọng hơn liệt kê 23 pattern.
  • YAGNI + simplest thing that works.

Deep Dive — Phân biệt & chọn pattern đúng

D1 Adapter vs Decorator vs Facade vs Proxy — 4 pattern hay bị nhầm

What

Cả 4 đều là pattern "bọc" (wrap) một object khác, nhưng intent khác hẳn nhau: Adapter đổi interface để khớp với client; Decorator giữ nguyên interface, thêm behavior; Facade tạo interface mới đơn giản hơn cho cả một subsystem; Proxy giữ nguyên interface nhưng kiểm soát truy cập.

Why

Interviewer rất hay hỏi "Decorator vs Proxy khác gì?" vì cấu trúc class gần như giống nhau (đều implement cùng interface và delegate lời gọi). Điểm khác biệt nằm ở mục đích và ai tạo/điều khiển object bị bọc — nắm được điều này là phân biệt được 4 pattern trong một câu trả lời.

How

So sánh theo 4 tiêu chí — interface, intent, ví dụ:

PatternInterfaceIntentVí dụ
AdapterĐổi thành interface client cầnKết nối 2 interface không tương thíchWrap SDK thanh toán cũ → port nội bộ
DecoratorGiữ nguyên (hoặc mở rộng)Thêm behavior, xếp lớp lúc runtimeBufferedReader(FileReader)
FacadeTạo interface mới, đơn giản hơnChe subsystem phức tạp bằng 1 entry pointApplication service placeOrder()
ProxyGiữ nguyên interfaceKiểm soát truy cập (lazy, bảo mật, TX)Spring @Transactional

Decorator

  • Client tự xếp lớp, thứ tự lồng do client quyết định
  • Luôn delegate rồi mới enhance
  • Không đổi vòng đời của object

Proxy

  • Proxy tự quản lý vòng đời service, thường do framework tạo
  • Có thể KHÔNG gọi delegate (chặn hẳn truy cập)
  • Trong suốt (transparent) với client
// Adapter: đổi interface SDK cũ sang port nội bộ
interface PaymentPort { Receipt pay(Money amount); }

class LegacyBankAdapter implements PaymentPort {
  private final LegacyBankSdk sdk;        // interface khác hoàn toàn
  public Receipt pay(Money amount) {
    return map(sdk.charge(amount.cents(), amount.currency()));
  }
}

// Decorator: giữ nguyên interface, thêm logging + retry
class RetryingPayment implements PaymentPort {
  private final PaymentPort delegate;
  RetryingPayment(PaymentPort delegate) { this.delegate = delegate; }
  public Receipt pay(Money amount) {
    int tries = 0;
    while (true) {
      try { return delegate.pay(amount); }
      catch (RetryableException e) { if (++tries > 3) throw e; }
    }
  }
}
When

Adapter khi phải tích hợp hệ thống ngoài không sửa được. Decorator khi cần bật/tắt behavior (cache, log, retry) linh hoạt theo cấu hình. Facade khi muốn một entry point cho workflow nhiều bước. Proxy cho cross-cutting concern (transaction, bảo mật, lazy loading).

When NOT

Code do mình owns nên refactor interface thay vì bọc Adapter chồng chất. Decorator chain quá dài gây khó debug — cross-cutting cho toàn app nên dùng AOP. Facade chỉ pass-through không orchestration thì chỉ thêm một tầng vô ích.

Pitfall / Interview trap

Nhầm Facade với Adapter: Facade định nghĩa interface MỚI (đơn giản hóa subsystem), Adapter làm interface CŨ dùng được mà không đơn giản hóa. Với Decorator vs Proxy: cả hai đều bọc cùng interface, nhưng Decorator để client tự do lồng nhiều lớp, còn Proxy thường do framework tạo và tự quản lý vòng đời. Nhớ: JDK dynamic proxy cần interface; CGLIB sinh subclass cho class cụ thể.

D2 Behavioral patterns: Strategy vs State vs Observer vs Template Method vs Chain of Responsibility

What

Nhóm behavioral quản lý cách object giao tiếp và chia trách nhiệm: Strategy hoán đổi algorithm; State đổi behavior theo trạng thái nội bộ; Observer publish–subscribe một–nhiều; Template Method cố định khung thuật toán, subclass điền các bước; Chain of Responsibility chuyền request qua một chuỗi handler.

Why

Hai câu hỏi kinh điển "Strategy khác State thế nào?" và "Template Method khác Strategy thế nào?" — chúng cùng giải quyết bài toán "thay đổi behavior" nhưng bằng cơ chế khác nhau (composition vs inheritance, và ai là người chọn thay đổi). Trả lời gọn được điểm cộng lớn.

How

Phân biệt theo "ai quyết định thay đổi" và cơ chế:

ObserverSubject phát eventDanh sách listenerApplicationEventPublisher
Template MethodBase class gọi hookInheritance (Hollywood principle)JdbcTemplate, HttpServlet.service()
Chain of ResponsibilityHandler tự quyết dừng/chuyềnChuỗi handler liên kếtServlet Filter, HandlerInterceptor

// Template Method: khung cố định, subclass điền hook
abstract class ImportJob {
  final void run() { extract(); transform(); load(); }  // final: không cho phá khung
  abstract void extract();
  abstract void transform();
  abstract void load();
}

class CsvImportJob extends ImportJob {
  void extract()   { /* đọc CSV */ }
  void transform() { /* chuẩn hóa */ }
  void load()      { /* ghi DB */ }
}

// So với Strategy: cùng "thay behavior" nhưng Template dùng KẾ THỪA,
// Strategy dùng COMPOSITION và hoán đổi được lúc runtime.
When

Strategy khi có nhiều cách tính/so sánh. State khi vòng đời có transition hợp lệ rõ ràng (draft → paid → shipped). Observer khi nhiều bên cùng quan tâm một sự kiện. Template Method khi khung xử lý chung, chỉ vài bước khác. Chain of Responsibility cho pipeline filter/validation.

When NOT

Chỉ 2 nhánh cố định không đổi thì if/else hoặc enum là đủ. Đừng dùng Template Method khi các bước orthogonal (dễ nổ subclass) — chuyển sang Strategy + composition. Không dùng Observer cho luồng cần thứ tự và đảm bảo chặt — dùng orchestration/Saga.

Pitfall / Interview trap

Phân biệt Strategy vs State: mấu chốt là ai chọn — client chọn Strategy (thường qua config/inject, không đổi giữa chừng), còn State tự chuyển khi event nội bộ xảy ra. Phân biệt Template Method vs Strategy: Template dùng kế thừa (ràng buộc compile-time), Strategy dùng composition (đổi runtime). Chain of Responsibility cho handler "không xử lý và chuyền tiếp" — khác Decorator luôn chạy và không được phá luồng.

D3 Anti-patterns & Singleton pitfalls: God Object, Anemic Domain, phá Singleton

What

Anti-pattern là giải pháp trông có vẻ đúng nhưng gây hại lặp đi lặp lại. Ba cái phổ biến: God Object (một class ôm quá nhiều trách nhiệm), Anemic Domain Model (entity chỉ có getter/setter, toàn bộ logic dồn vào service), Singleton abuse (lạm dụng singleton cho global mutable state). Với Singleton còn có bẫy tạo được instance thứ hai qua reflection, serialization và nhiều classloader.

Why

Senior không chỉ biết 23 pattern mà biết khi nào KHÔNG dùng. Nhận diện anti-pattern là kỹ năng review code: chúng làm giảm cohesion, tăng coupling, khiến code khó test và khó thay đổi.

How

Nhận diện dấu hiệu rồi xử lý:

Anti-patternDấu hiệuCách xử lý
God ObjectClass 2000+ dòng, làm 10 việc, được inject khắp nơiTách theo trục thay đổi (SRP), dùng use-case service
Anemic DomainEntity toàn getter/setter; rule nằm hết ở serviceĐẩy invariant vào aggregate khi rule gắn với data
Singleton abuseGlobal mutable state, hidden dependency, khó testDùng DI container; bean stateless/immutable
Golden HammerChỗ nào cũng Factory/Singleton "cho chuẩn"YAGNI — chọn giải pháp đơn giản nhất đủ dùng
 
// CÁC CÁCH PHÁ SINGLETON và cách chống
// 1) Reflection tạo instance thứ hai
Constructor<AppConfig> c = AppConfig.class.getDeclaredConstructor();
c.setAccessible(true);            // phá được private constructor
// 2) Deserialization tạo object mới
// 3) Nhiều ClassLoader (app server) -> nhiều "singleton"

// CHỐNG: dùng enum — an toàn trước reflection, serialization, classloader
public enum AppConfig {
  INSTANCE;
  private final Map<String, String> values = new ConcurrentHashMap<>();
  public String get(String k) { return values.get(k); }
}

// Nếu buộc dùng class: chặn trong constructor + cài readResolve()
private AppConfig() {
  if (instance != null) throw new IllegalStateException("Use getInstance()");
}
When

Dùng pattern khi có trục thay đổi/lặp thật. Tránh singleton thủ công khi đã có Spring bean. Chọn enum singleton khi cần singleton thật sự nằm ngoài DI container.

When NOT

Đừng tuyệt đối hóa "Anemic = sai": với Spring Data JPA, entity làm data holder + service xử lý là hợp lý và phổ biến — chỉ chuyển sang rich domain khi invariant phức tạp. Không tự implement Singleton thay vì để DI container quản lý.

Pitfall / Interview trap

Double-checked locking thiếu volatile có thể khiến thread khác thấy object "chưa khởi tạo xong" do JMM reorder — sai trước Java 5 và vẫn sai nếu bỏ volatile. Reflection phá được Bill Pugh/class singleton nhưng KHÔNG phá được enum (JVM chặn). Lưu ý: @Service của Spring mặc định singleton nhưng KHÔNG phải GoF singleton — container quản lý nên dễ test hơn.
