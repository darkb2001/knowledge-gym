Hibernate / JPA

Lazy/Eager loading, N+1, cache, locking, entity lifecycle, pagination, inheritance mapping — tối ưu ORM trong production.

ORM & Fetch Strategy

Q1 Phân biệt Lazy Loading vs Eager Loading?

What

Lazy Loading trì hoãn query association cho đến lần truy cập đầu tiên — Hibernate tạo proxy (collection wrapper hoặc entity proxy) thay vì SELECT ngay. Eager Loading fetch association cùng lúc với entity cha qua JOIN hoặc query phụ. JPA default: @OneToMany/@ManyToMany → LAZY; @ManyToOne/@OneToOne → EAGER (có thể override bằng fetch = FetchType.LAZY).

Why

Fetch strategy quyết định số query và lượng dữ liệu mỗi request. EAGER mặc định trên @ManyToOne dễ gây over-fetch khi list 500 pick order nhưng không cần customer detail — mỗi row kéo thêm JOIN. LAZY đúng hướng nhưng truy cập ngoài Persistence Context → LazyInitializationException. Trên WMS, API list task thường chỉ cần header; detail screen mới cần lines + location — fetch plan phải khác nhau theo use case.

How
SELECT * FROM pick_order WHERE id=1
↓ LAZY: lines chưa query — proxy rỗng
order.getLines().size()
→ SELECT * FROM pick_line WHERE order_id=1
↓ EAGER: đã JOIN/SELECT lines ngay bước 1

Fix LazyInitializationException: (1) giữ access trong @Transactional, (2) JOIN FETCH / @EntityGraph, (3) trả DTO/projection thay vì entity graph, (4) tránh OSIV che lỗi.

When

LAZY cho mọi association mặc định — đặc biệt collection (@OneToMany). Chỉ EAGER khi 100% mọi code path luôn cần association và cardinality nhỏ (ví dụ entity luôn kèm 1 config row). Production: explicit fetch trong service theo từng API endpoint.

When NOT

Đừng EAGER toàn cục "cho chắc" — list API sẽ cartesian product và chậm. Đừng LAZY rồi truy cập association ở controller/view ngoài transaction. Đừng dựa OSIV (spring.jpa.open-in-view=true) thay fetch plan — che N+1 và giữ DB connection suốt HTTP request. Đừng EAGER 2 collection cùng lúc — MultipleBagFetchException.

LAZY (default @OneToMany, @ManyToMany)EAGER (@ManyToOne default, @OneToOne có thể)
Khi nào queryLần truy cập association đầu tiên (proxy)Ngay khi load entity cha (JOIN hoặc query riêng)
PerformanceTốt nếu không cần associationDễ over-fetch, cartesian product trên list
Rủi roLazyInitializationException ngoài session; N+1 trong loopLoad dư dữ liệu, chậm pagination
WMSList pick task (header only)Hiếm — prefer explicit fetch
 
@Entity
public class PickOrder {
  @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
  private List<PickLine> lines = new ArrayList<>();

  @ManyToOne(fetch = FetchType.LAZY) // override EAGER default
  private StorageLocation location;
}

// ❌ LazyInitializationException — session đã đóng
PickOrder order = orderRepo.findById(1L).get();
order.getLines().size(); // fail nếu ngoài @Transactional

// ✅ Explicit fetch trong service
@Query("SELECT o FROM PickOrder o JOIN FETCH o.lines WHERE o.id = :id")
Optional<PickOrder> findWithLines(@Param("id") Long id);
Use case
Dashboard WMS list 200 open pick order: LAZY + không touch lines → 1 query. Detail screen order #PO-8842: service gọi findWithLines() JOIN FETCH trong @Transactional → 1 query đủ data. Export CSV cần order + customer: DTO projection thay vì EAGER global trên entity.
Pitfall / Interview trap
Interviewer hỏi "EAGER an toàn hơn LAZY?" — SAI: EAGER gây over-fetch và cartesian product trên list. "OSIV fix LazyInitializationException?" — technically đúng nhưng anti-pattern: giữ session + connection suốt request, che N+1. Trả lời đúng: LAZY default + explicit fetch plan theo use case.
Nói trong 60 giây
  • LAZY = proxy, query khi access; EAGER = fetch ngay cùng cha.
  • Default: OneToMany LAZY, ManyToOne EAGER — nên override ManyToOne → LAZY.
  • LazyInitializationException = access ngoài Persistence Context.
  • Fix: @Transactional, JOIN FETCH, EntityGraph, DTO — không OSIV.
  • Production: fetch explicit theo API, không EAGER global.

Q2 N+1 Query — nguyên nhân, phát hiện, giải pháp?

What

N+1 Query là anti-pattern ORM: 1 query load N entity cha (ví dụ 100 pick order), rồi thêm N query riêng khi lazy-load association con (order.lines) trong vòng lặp — tổng 101 round-trip DB thay vì 1–2. Hibernate sinh proxy cho @OneToMany(fetch=LAZY); mỗi lần order.getLines() trigger SELECT mới nếu chưa được fetch trước.

Why

LAZY là default đúng cho performance, nhưng service/controller truy cập collection ngoài ý đồ hoặc thiếu fetch plan → explosion. Trên WMS, list 500 outbound order rồi loop lấy line items có thể biến API 200ms thành 3–5s, làm timeout WCS callback và spike connection pool HikariCP.

How
❌ N+1: 1 + N queries
↓
SELECT * FROM pick_order WHERE status='OPEN'
→ 100 rows
↓ for each order → SELECT * FROM pick_line WHERE order_id=?
×100 queries

Phát hiện: bật spring.jpa.show-sql, Hibernate statistics, p6spy/datasource-proxy, APM trace (Datadog/New Relic), log pattern "cùng SQL lặp với param khác nhau".

When

Dùng JOIN FETCH khi chắc chắn cần association ngay (detail screen, export). @EntityGraph khi muốn khai báo fetch plan trên repository mà không viết JPQL dài. @BatchSize / default_batch_fetch_size khi list lớn, nhiều parent, không cần cartesian product — gom lazy load thành WHERE id IN (...) theo batch 25–50.

When NOT

Không JOIN FETCH mọi association "cho chắc" — cartesian product phình row (order × lines × customer). Không dùng EAGER global. Không JOIN FETCH trực tiếp với Pageable — Hibernate có thể paginate sai. Không batch fetch khi chỉ load 1 entity.

Giải phápCơ chếƯuNhược
JOIN FETCH1 JPQL join, load eager trong query1 query, deterministicCartesian product, khó paginate
@EntityGraphHint fetch plan trên find methodDeclarative, tái sử dụngMultiple bag fetch cùng lúc bị lỗi
@BatchSizeLazy load theo IN-clause batchGiữ LAZY, giảm N+1Vẫn nhiều query hơn JOIN FETCH
DTO / ProjectionQuery chỉ cột cần thiếtNhẹ nhất, không proxyKhông full entity graph
 
// ❌ N+1 — 1 query orders + N query lines
List<PickOrder> orders = orderRepo.findByStatus(OPEN);
for (PickOrder o : orders) {
  o.getLines().size(); // lazy trigger → SELECT ... WHERE order_id=?
}

// ✅ JOIN FETCH — 1 query duy nhất
@Query("SELECT DISTINCT o FROM PickOrder o JOIN FETCH o.lines WHERE o.status = :st")
List<PickOrder> findWithLines(@Param("st") OrderStatus st);

// ✅ EntityGraph — fetch plan trên repository
@EntityGraph(attributePaths = {"lines", "location"})
List<PickOrder> findByStatus(OrderStatus status);

// ✅ Batch fetch — IN (1,2,3...) thay vì từng id
@BatchSize(size = 25)
private List<PickLine> lines;
// yml: hibernate.default_batch_fetch_size=25
Use case
API list pick task WMS trả order + lines: JOIN FETCH hoặc EntityGraph trong @Transactional service. Dashboard chỉ cần header → không fetch lines. Pagination 20/page → 2-query: (1) SELECT id ... LIMIT/OFFSET, (2) JOIN FETCH WHERE id IN (...).
Pitfall / Interview trap
Interviewer hỏi "JOIN FETCH fix N+1?" — trả lời có điều kiện: fix được nhưng có thể duplicate row (DISTINCT), không paginate trực tiếp, và fetch 2 collection cùng lúc → MultipleBagFetchException. OSIV che lỗi bằng cách giữ session mở suốt HTTP request — anti-pattern production.
Nói trong 60 giây
  • N+1 = 1 query cha + N query con do lazy access trong loop.
  • Phát hiện qua SQL log lặp, APM, p6spy.
  • Fix: JOIN FETCH (1 query), EntityGraph (declarative), BatchSize (lazy gom IN).
  • Cẩn thận cartesian product và pagination — dùng 2-query approach.
  • Production: fetch explicit trong service, tránh OSIV.

Cache & Locking

Q3 First-level cache vs Second-level cache?

What

First-level cache (L1) là Persistence Context — identity map trong phạm vi 1 EntityManager/Session: cùng PK = cùng object instance, dirty checking tự phát hiện thay đổi khi flush. Second-level cache (L2) là cache ở SessionFactory scope, chia sẻ giữa nhiều session — lưu entity state đã detach (dehydrated), cần provider (Caffeine, EhCache, Redis) và @Cacheable trên entity.

Why

L1 giảm duplicate SELECT trong cùng transaction (findById(1) 2 lần → 1 query) và đảm bảo consistency trong TX. L2 giảm round-trip DB cho read-heavy data ít đổi — product catalog, warehouse config, SKU master trên WMS có thể đọc hàng nghìn lần/ngày nhưng update vài lần. Không có L2, mỗi HTTP request tạo session mới → miss cache liên tục.

How
Request → Session mới
↓ findById(skuId)
L1 hit?
L2 hit?
→ DB SELECT
↓ put L2 (nếu @Cacheable) + put L1

Lookup order: L1 → L2 → DB. Update entity: L1 dirty check → flush DB → invalidate/update L2 region. Query cache (extension của L2) cache kết quả query — dễ stale, production ít dùng.

When

L1: luôn bật tự động — hiểu để tránh duplicate query và stale trong TX. L2: entity read-heavy, write-rare, dữ liệu nhỏ-vừa (SKU, location type, system config). Cluster multi-node cần distributed L2 (Redis) + TTL/invalidate strategy.

When NOT

Đừng L2 cho inventory/bin status — stale gây double booking AGV. Đừng cache entity có @Version conflict cao. Đừng nhầm L1 tồn tại giữa requests — session đóng = L1 mất. Đừng bật query cache cho dynamic query (filter theo status/date). Đừng L2 mà không test invalidation khi deploy multi-instance.

L1 (Persistence Context)L2 (SessionFactory)
Scope1 Session / TransactionShared toàn application
ConfigTự động — không cầnProvider + @Cacheable + yml
Identity mapCó — cùng ID = cùng instanceDehydrated state, tạo instance mới mỗi session
Dirty checkingCó — auto UPDATE khi flushKhông — chỉ read cache

Use case
WMS: cache L2 cho SkuMaster (10K SKU, đọc mỗi pick scan) và WarehouseConfig (zone mapping, AGV speed limit). Pick transaction vẫn query real-time BinInventory — không cache. Sau admin update SKU weight, L2 READ_WRITE invalidate region → scan tiếp theo lấy data mới.
Pitfall / Interview trap
"L2 thay L1?" — SAI: L1 luôn có trong session; L2 bổ sung cross-session. "Cache @ManyToOne association?" — collection cache phức tạp và dễ stale. Stale L2 trên inventory → AGV pick sai bin — interviewer test awareness về cache invalidation hơn config syntax.
Nói trong 60 giây
  • L1 = Persistence Context, per session, identity map + dirty checking.
  • L2 = SessionFactory scope, shared, cần @Cacheable + provider.
  • Lookup: L1 → L2 → DB; update invalidate L2.
  • L2 cho read-heavy master data; không cache inventory/status.
  • Cluster: distributed cache (Redis) + test invalidation.

Q4 Optimistic Locking vs Pessimistic Locking?

What

Optimistic locking giả định conflict hiếm: đọc entity kèm @Version, khi UPDATE DB check WHERE version = ? — mismatch → OptimisticLockException. Pessimistic locking lock row ngay lúc SELECT (SELECT ... FOR UPDATE) — transaction khác phải chờ hoặc timeout. JPA: @Version vs @Lock(PESSIMISTIC_WRITE).

Why

WMS: 2 AGV/station cùng allocate bin A-01-03 cho SKU khác nhau. Không lock → double booking. Optimistic phù hợp khi conflict thấp (cập nhật master data). Pessimistic bắt buộc khi "giữ chỗ" bin/inventory trong transaction ngắn — đảm bảo chỉ 1 luồng reserve thành công, luồng kia block rõ ràng thay vì fail sau cùng.

How
Tx A: SELECT bin A-01-03 FOR UPDATE
↓ row locked — Tx B chờ
Tx A: UPDATE status='RESERVED', COMMIT
↓ lock release → Tx B đọc, thấy RESERVED → chọn bin khác

Optimistic flow: cả A và B đọc version=5, qty=10 → A commit version=6 → B update WHERE version=5 → 0 rows → retry hoặc báo conflict.

When

Optimistic: profile update, config WMS, inventory adjustment thỉnh thoảng, read-heavy write-rare. Pessimistic: bin reservation, pick task allocation, chuyển tồn giữa location, bất kỳ "check-then-act" trên cùng row mà lost update không chấp nhận được.

When NOT

Đừng pessimistic lock cả bảng location khi chỉ cần 1 bin — lock đúng row. Đừng optimistic cho hot row (counter sequence) — retry storm. Đừng giữ pessimistic lock qua HTTP call/user input — deadlock và timeout WCS. Đừng mix 2 chiến lược trên cùng entity không có lý do.

Optimistic (@Version)Pessimistic (FOR UPDATE)
Cơ chếCheck version lúc flush UPDATEDB row lock lúc SELECT
ConflictException / 0 rows updatedBlock, timeout, deadlock risk
ThroughputCao — không block readerThấp hơn — contention
DB supportMọi RDBMSPostgreSQL, Oracle, InnoDB
WMSMaster data, audit fieldBin hold, inventory reserve
 
// Optimistic — bin inventory, conflict hiếm
@Entity
public class BinInventory {
  @Id private Long id;
  private String binCode;   // A-01-03
  private int qty;
  @Version private Long version;
}

// Pessimistic — reserve bin trước khi gửi lệnh AGV
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT b FROM StorageBin b WHERE b.binCode = :code AND b.status = 'EMPTY'")
Optional<StorageBin> findEmptyBinForUpdate(@Param("code") String code);

@Transactional
public void reserveBin(String binCode, String taskId) {
  StorageBin bin = repo.findEmptyBinForUpdate(binCode).orElseThrow();
  bin.setStatus("RESERVED");
  bin.setTaskId(taskId);
  // COMMIT → release lock; AGV dispatch sau TX
}
Use case
Putaway WMS: pessimistic lock row storage_bin khi WMS assign vị trí, update status RESERVED, commit nhanh (<100ms), rồi async gọi WCS. Cycle count adjustment dùng optimistic + retry 3 lần vì operator hiếm cùng sửa 1 bin.
Pitfall / Interview trap
"Optimistic nhanh hơn nên luôn dùng" — SAI trên hot inventory row: retry loop tốn CPU và vẫn lost update nếu không handle exception. Pessimistic + transaction dài (chờ operator scan) → deadlock. Lock order: luôn lock bin theo bin_code ASC khi update nhiều bin trong 1 TX.
Nói trong 60 giây
  • Optimistic: @Version, check lúc UPDATE, exception khi conflict.
  • Pessimistic: FOR UPDATE lock row ngay, block transaction khác.
  • WMS bin reservation → pessimistic; master data → optimistic.
  • Giữ TX ngắn với pessimistic; retry/backoff với optimistic.
  • Lock đúng granularity (row), sort key tránh deadlock.

Entity Lifecycle & Pagination

Q5 Phân biệt persist(), merge(), save(), saveOrUpdate()?

What

persist() và merge() là JPA EntityManager API; save() là Spring Data abstraction; saveOrUpdate() là Hibernate Session legacy (Hibernate 5 trở xuống). Chúng map entity lifecycle state (transient, managed, detached) sang INSERT/UPDATE — nhưng semantics khác nhau, đặc biệt với detached entity và return value.

Why

Nhầm lẫn gây bug production: gọi persist(detached) → exception; gọi merge() rồi tiếp tục dùng param detached → thay đổi không flush; save() với entity có ID nhưng chưa tồn tại DB → merge thay vì insert. Trên WMS, REST API nhận DTO rồi map sang entity detached rất phổ biến — phải biết save() internally merge và trả managed copy.

How
Transient
persist() / save(isNew)
Managed → INSERT
↓ session close / clear
Detached
merge() / save(hasId)
Managed copy → UPDATE

Spring save(): id == null hoặc isNew() == true → persist; ngược lại → merge. merge() luôn trả managed copy — param gốc vẫn detached. saveOrUpdate() deprecated — dùng save/merge trong Spring Data.

When

persist: entity mới trong cùng transaction. merge: reattach detached entity (DTO → entity từ client, entity từ cache ngoài session). save: default Spring Data repo — đủ cho CRUD thông thường. Override isNew() (Persistable) khi ID assigned trước insert (UUID, sequence).

When NOT

Đừng persist detached — IllegalArgumentException. Đừng merge rồi modify param detached — changes lost. Đừng save entity có ID giả (client gửi id=0) nếu không override isNew. Đừng dùng saveOrUpdate trong code mới. Tránh merge trong loop 1000 entity — dùng batch INSERT hoặc JDBC.

// Spring Data save — id null → persist (INSERT)
PickOrder order = new PickOrder();
orderRepo.save(order);

// Detached từ REST DTO — save() internally merge
PickOrder detached = mapper.toEntity(dto); // id=42, đã tồn tại DB
detached.setStatus("SHIPPED");
PickOrder saved = orderRepo.save(detached); // UPDATE

// merge pitfall — param không thành managed
PickOrder managed = entityManager.merge(detached);
managed.setStatus("SHIPPED");  // ✅ dirty check trên managed
// detached.setStatus(...) — ❌ không flush

// Persistable — UUID assigned trước insert
public class Task implements Persistable<UUID> {
  @Id private UUID id = UUID.randomUUID();
  private transient boolean isNew = true;
  public boolean isNew() { return isNew; }
}
Use case
WCS callback update pick task status: controller nhận JSON → MapStruct → entity detached với id có sẵn → pickTaskRepo.save(entity) merge UPDATE. Tạo pick order mới từ WMS UI: entity id=null → save persist INSERT. Bulk import 5000 SKU: không loop save — dùng saveAll batch hoặc JDBC batch.
Pitfall / Interview trap
"save() = persist()?" — SAI: save() gọi merge khi entity có ID. "merge() modify param được?" — SAI: phải dùng return value. Interviewer cho code: findById → close session → modify → save — hỏi INSERT hay UPDATE? Trả lời UPDATE via merge nếu ID tồn tại.
Nói trong 60 giây
  • persist = INSERT entity mới; merge = reattach detached → UPDATE.
  • save() Spring Data: isNew → persist, else → merge.
  • merge trả managed copy — đừng modify param detached.
  • saveOrUpdate legacy — tránh code mới.
  • DTO → entity detached: save/merge; entity mới: persist/save.

Q6 Pagination — Page vs Slice, ảnh hưởng COUNT(*)?

What

Page<T> trả data + metadata đầy đủ: totalElements, totalPages, number — Spring Data chạy 2 query (SELECT + COUNT). Slice<T> chỉ SELECT LIMIT size+1, dùng row thừa để suy ra hasNext() — không biết tổng số trang. Cả hai dùng Pageable nhưng trade-off khác nhau về UX và performance.

Why

COUNT(*) trên bảng pick_order 5M row (WMS) có thể mất 2–5s dù SELECT 20 row chỉ 10ms — full index scan hoặc seq scan. UI infinite scroll operator không cần "Trang 847/12000" — Slice bỏ COUNT tiết kiệm 50%+ latency. Admin dashboard cần total để hiển thị pager → Page chấp nhận cost COUNT hoặc cache approximate total.

How
Page: SELECT ... LIMIT 20 OFFSET 40
+
SELECT COUNT(*) WHERE status='OPEN'
vs
Slice: SELECT ... LIMIT 21 OFFSET 40
→ 21 rows? hasNext=true, trả 20

Tối ưu thêm: keyset pagination (WHERE id > :cursor) thay OFFSET lớn; cache COUNT với TTL; PostgreSQL approximate count (reltuples); tách COUNT query đơn giản hơn (chỉ index column).

When

Page: admin UI cần pager "3/500", báo cáo cần total chính xác, bảng <100K row hoặc COUNT có index phù hợp. Slice: mobile/tablet operator scroll, API "load more", feed realtime — không cần total. Keyset: bảng hàng triệu row, deep pagination (page >100).

When NOT

Đừng Page trên bảng log/audit hàng chục triệu row mỗi API call — COUNT kill DB. Đừng Slice khi UI bắt buộc hiển thị total pages. Đừng OFFSET pagination page 10000 — O(n) skip rows. Đừng JOIN FETCH + Pageable trực tiếp — Hibernate paginate sai in-memory.

Page<T>Slice<T>
QueriesSELECT + COUNT(*)SELECT LIMIT size+1

Pageable pageable = PageRequest.of(0, 20, Sort.by("createdAt").descending());

// Page — 2 queries
Page<PickOrder> page = orderRepo.findByStatus(OPEN, pageable);
long total = page.getTotalElements();   // COUNT đã chạy
int pages = page.getTotalPages();

// Slice — 1 query, không COUNT
Slice<PickOrder> slice = orderRepo.findSliceByStatus(OPEN, pageable);
boolean hasNext = slice.hasNext();

// Keyset — tránh OFFSET lớn
@Query("SELECT o FROM PickOrder o WHERE o.status = :st"
     + " AND o.createdAt < :cursor ORDER BY o.createdAt DESC")
List<PickOrder> findNextPage(@Param("st") OrderStatus st,
    @Param("cursor") Instant cursor, Pageable limit);
Use case
Operator tablet WMS scroll danh sách pick task OPEN: Slice<PickOrder> 20 item/lần, hasNext → "Tải thêm". Admin search order theo date range (filter còn 30K row): Page hiển thị "1/1500" — COUNT chấp nhận được vì có index (status, created_at). Audit log 10M row export: keyset WHERE id > :lastId LIMIT 1000.
Pitfall / Interview trap
"Page luôn tốt vì có metadata?" — SAI trên bảng lớn: COUNT(*) expensive. "Slice biết được trang cuối?" — KHÔNG. OFFSET page 5000 = DB skip 100K rows — interviewer hỏi fix → keyset/cursor pagination. JOIN FETCH + Pageable → duplicate count, wrong page size.
Nói trong 60 giây
  • Page = SELECT + COUNT; Slice = SELECT LIMIT n+1, no COUNT.
  • Page cho pager UI cần total; Slice cho infinite scroll.
  • COUNT(*) chậm trên bảng lớn — cache hoặc approximate.
  • Deep page: keyset (WHERE id > cursor) thay OFFSET.
  • WMS: Slice cho operator, Page cho admin filter nhỏ.

Inheritance Mapping

Q7 @Inheritance — SINGLE_TABLE, JOINED, TABLE_PER_CLASS?

What

@Inheritance map class hierarchy Java sang relational schema. Ba strategy JPA: SINGLE_TABLE — 1 bảng + discriminator (DTYPE); JOINED — bảng cha + bảng con FK; TABLE_PER_CLASS — mỗi entity class 1 bảng riêng (duplicate columns cha). Polymorphic query SELECT p FROM Payment p sinh SQL khác nhau tùy strategy.

Why

Trade-off giữa normalization, query speed và schema evolution. SINGLE_TABLE nhanh (no JOIN) nhưng sparse NULL khi subclass nhiều field riêng. JOINED chuẩn hóa nhưng mỗi load = JOIN. TABLE_PER_CLASS polymorphic query = UNION all tables — Hibernate không khuyến khích. WMS: Equipment hierarchy (AGV, Conveyor, Shuttle) — chọn strategy ảnh hưởng report query và migration cost.

How
SINGLE_TABLE
equipment (all cols + DTYPE)
JOINED
equipment
+ agv_equipment + conveyor_equipment
TABLE_PER_CLASS
agv_equipment | conveyor_equipment (full cols each)

SINGLE_TABLE: @DiscriminatorColumn hoặc @DiscriminatorValue. JOINED: subclass table PK = FK tới parent. Polymorphic JPQL trên JOINED → LEFT JOIN subtables; TPC → UNION (chậm, phức tạp).

When

SINGLE_TABLE: hierarchy nhỏ (2–4 subclass), ít field riêng, read-heavy polymorphic query. JOINED: subclass nhiều field riêng, cần normalized schema, write/update thường xuyên từng subtype. TABLE_PER_CLASS: gần như không — chỉ legacy codebase.

When NOT

Đừng SINGLE_TABLE khi subclass có 20+ column riêng — bảng sparse, index kém. Đừng JOINED khi polymorphic list 10K row/req — JOIN cost cao. Đừng TPC cho project mới. Đừng deep inheritance (>2 level) — prefer composition (@Embedded, separate entity + FK) thay inheritance mapping.

@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "task_type")
public abstract class WarehouseTask {
  @Id @GeneratedValue private Long id;
  private String status;
  private String zoneCode;
}

@Entity
@DiscriminatorValue("PICK")
public class PickTask extends WarehouseTask {
  private String pickLocation;
}

@Entity
@DiscriminatorValue("PUTAWAY")
public class PutawayTask extends WarehouseTask {
  private String targetBin;
}

// Polymorphic query — SINGLE_TABLE: 1 SELECT, no JOIN
List<WarehouseTask> tasks = em.createQuery(
  "SELECT t FROM WarehouseTask t WHERE t.zoneCode = :z", WarehouseTask.class)
  .setParameter("z", "A").getResultList();
Use case
WMS task queue: 3 subtype (Pick, Putaway, Transfer) với 2–3 field riêng mỗi loại → SINGLE_TABLE đủ, polymorphic list API nhanh. Equipment master với AGV (20 field), Conveyor (15 field), Shuttle (18 field) khác biệt lớn → JOINED normalized. Refactor legacy TPC → migrate sang JOINED hoặc flatten thành entity riêng + type enum.
Pitfall / Interview trap
"JOINED luôn best practice vì normalized?" — SAI cho hierarchy nhỏ read-heavy: JOIN overhead > NULL cost. SINGLE_TABLE constraint: không enforce NOT NULL trên subclass column ở DB level. Interviewer hỏi polymorphic query TPC — trả lời UNION all tables, performance kém. Prefer composition over inheritance khi không cần polymorphic JPQL.
Nói trong 60 giây
  • SINGLE_TABLE: 1 bảng + DTYPE — nhanh, nhiều NULL.
  • JOINED: parent + child table — normalized, JOIN mỗi query.
  • TABLE_PER_CLASS: 1 bảng/class — polymorphic = UNION, tránh.
  • Hierarchy nhỏ → SINGLE; nhiều field riêng → JOINED.
  • Cân nhắc composition thay deep inheritance.

Deep Dive — Persistence Context & Dirty Checking

D1 Persistence Context và cơ chế Dirty Checking hoạt động thế nào?

What

Persistence Context là lớp cache "transactional write-behind" của JPA/Hibernate: mọi entity managed nằm trong đó như một identity map — cùng primary key luôn trả về cùng một object instance. Dirty Checking là cơ chế tự phát hiện entity đã đổi: khi load, Hibernate giữ một snapshot toàn bộ giá trị property; tới lúc flush() nó so state hiện tại với snapshot (mặc định quét mọi entity × mọi property) và sinh UPDATE cho entity "dirty".

Why

Hiểu cơ chế này để: (1) tránh duplicate query — findById() hai lần trong cùng transaction chỉ chạy 1 SELECT; (2) tránh bối rối "tôi đổi object mà sao DB chưa đổi" (vì write-behind chỉ đẩy SQL khi flush); (3) kiểm soát hiệu năng — chi phí dirty check là tổng số property của mọi managed entity (n × p), nên giữ Persistence Context quá lớn sẽ tốn CPU và gấp đôi bộ nhớ (do phải lưu snapshot bên cạnh entity).

How
em.find(Task, 1L)
→ lưu snapshot vào L1
↓ task.setStatus("DONE") — chưa có SQL nào chạy
flush() / commit
dirty check → sinh UPDATE
↓ ActionQueue gom SQL theo thứ tự INSERT → UPDATE → DELETE
SQL gửi DB trong cùng transaction

Thời điểm flush phụ thuộc FlushMode (xem bảng). Mặc định AUTO: Hibernate flush trước khi chạy JPQL/HQL và trước commit. Muốn giải phóng bộ nhớ giữa chừng (batch lớn) thì flush() rồi clear().

When

Dùng hiểu biết này ở mọi service @Transactional. Gọi em.flush() khi cần ID tự sinh ngay, khi muốn validate constraint DB sớm, hoặc khi phải clear() giải phóng Persistence Context trong vòng lặp xử lý khối lượng lớn. Dùng bytecode enhancement (hibernate.enhancer.enableDirtyTracking=true) khi entity nhiều property và Persistence Context lớn.

When NOT

Đừng giữ hàng trăm nghìn entity managed trong một Persistence Context — dirty check và snapshot làm tăng CPU/bộ nhớ. Đừng modify entity rồi kỳ vọng DB thấy ngay khi chưa flush/commit. Đừng dựa vào auto-flush cho câu native SQL khi dùng Hibernate Session thuần (chỉ JPA đảm bảo flush trước mọi query). Đừng để entity bị đổi ngoài ý muốn rồi flush — mọi thay đổi managed sẽ thành UPDATE.

FlushModeFlush khi nàoGhi chú

COMMITChỉ trước khi commitQuery trong TX có thể thấy dữ liệu cũ
ALWAYSTrước mọi query, kể cả nativeAn toàn nhưng nhiều lần flush, chậm hơn

@Entity
public class Task {
  @Id @GeneratedValue private Long id;
  private String status;
}

@Transactional
public void complete(Long id) {
  Task t = em.find(Task.class, id); // snapshot được lưu vào L1
  t.setStatus("DONE");              // chỉ đổi field — CHƯA có SQL
  em.flush();                         // dirty check → UPDATE task SET status=?
}

// AUTO flush: chạy query JPQL sẽ kích hoạt flush trước
em.persist(new Task());
em.createQuery("select t from Task t", Task.class)
  .getResultList(); // INSERT chạy trước SELECT
Use case
Service hoàn tất task: load task, đổi status, đổi thêm vài field audit — chỉ cần gọi setter, Hibernate tự sinh một UPDATE gộp. Trong job import 50K dòng: persist() theo lô, cứ 50 bản ghi gọi flush() + clear() để Persistence Context không phình to.
Pitfall / Interview trap
Mặc định Hibernate update tất cả cột (dynamic-update off) chứ không chỉ cột đổi — bật @DynamicUpdate nếu chỉ muốn cập nhật cột thay đổi. "Đổi object là DB đổi ngay?" — SAI, phải tới flush trong transaction. "Native query cũng auto-flush?" — chỉ đúng khi bootstrap qua JPA (Hibernate 5.2+), Session thuần không flush trước native SQL.

Deep Dive — JDBC Batching & Bulk Operations

D2 JDBC Batching trong Hibernate — cấu hình và bẫy với IDENTITY?

What

JDBC batching gom nhiều câu INSERT/UPDATE/DELETE cùng hình dạng thành một lượt gửi tới DB, giảm hẳn số network round-trip. Hibernate tắt batch mặc định; bật bằng hibernate.jdbc.batch_size (khuyến nghị 10–50). Vì mỗi JDBC batch chỉ phục vụ một bảng, cần thêm hibernate.order_inserts / hibernate.order_updates để gom statement cùng bảng lại với nhau.

Why

Không batch, mỗi INSERT là một round-trip; insert 5000 bản ghi thành 5000 vòng mạng. Batching biến chúng thành vài trăm lượt — throughput tăng rõ rệt. Cái bẫy lớn: chiến lược IDENTITY vô hiệu hoá batch insert, vì Hibernate phải chạy INSERT ngay tại thời điểm persist() để lấy ID tự tăng do DB cấp — không còn statement nào nằm chờ để gom batch. Trên MySQL (không có SEQUENCE) bạn thường mắc đúng bẫy này.

How
persist(x) ×1000
↓ batch_size=50: gom theo bảng (order_inserts)
JDBC addBatch() ×50
executeBatch() — 1 round-trip
↓ IDENTITY: không gom được → mỗi persist 1 INSERT riêng
1000 round-trips

Chiến lược ID hoạt động với batch: SEQUENCE, TABLE, hoặc generator gán ID trước insert (UUID, custom NoOp + @SQLInsert). Với MySQL có thể bật rewriteBatchedStatements=true để driver viết lại batch INSERT thành multi-values.

When

Dùng batching cho bulk insert/update, import dữ liệu, ETL, job đồng bộ. Đặt batch_size ~ bằng số bản ghi giữa hai lần flush()+clear(). Dùng StatelessSession khi cần insert khối lượng cực lớn mà không cần persistence context.

When NOT

Đừng kỳ vọng batch khi ID generator là IDENTITY (MySQL) — phải đổi chiến lược ID hoặc dùng kỹ thuật gán ID trước. Đừng đặt batch_size quá lớn (hàng nghìn) — tốn bộ nhớ driver và transaction dài. Đừng trộn nhiều bảng trong một batch (mỗi batch một bảng). Đừng quên flush()+clear() khi batch lớn, nếu không L1 cache phình to.

Cấu hìnhÝ nghĩaLưu ý
hibernate.jdbc.batch_sizeSố statement gom mỗi batch0/âm = tắt; khuyến nghị 10–50
hibernate.order_insertsSắp INSERT theo bảngTăng khả năng gom batch (có chi phí sort)
hibernate.order_updatesSắp UPDATE theo entity + PKGiảm deadlock ở hệ concurrent cao
hibernate.batch_versioned_dataBatch cả entity có @VersionCho phép batch với optimistic locking
rewriteBatchedStatementsMySQL driver viết lại thành multi-valuesChỉ MySQL, hiệu quả rõ khi insert
 
// application.properties
// spring.jpa.properties.hibernate.jdbc.batch_size=50
// spring.jpa.properties.hibernate.order_inserts=true
// spring.jpa.properties.hibernate.order_updates=true

@Transactional
public void importItems(List<Item> items) {
  int i = 0;
  for (Item it : items) {
    em.persist(it);
    if ((++i % 50) == 0) { // khớp batch_size
      em.flush();
      em.clear();          // giải phóng L1 cache
    }
  }
}
Use case
Job nạp 200K dòng master data: dùng SEQUENCE + batch_size=50 + order_inserts=true, cứ 50 dòng flush/clear; trên MySQL bật rewriteBatchedStatements=true. Kết quả: thời gian import giảm mạnh so với insert từng dòng.
Pitfall / Interview trap
"Đặt batch_size là Hibernate tự batch?" — SAI nếu dùng IDENTITY. saveAll() không đồng nghĩa batch; nó chỉ gọi save() lần lượt. Interviewer thường hỏi vì sao batch bật mà log vẫn ra từng INSERT → trả lời do ID generator hoặc do trộn nhiều bảng / thiếu order_inserts. Nhớ: order_updates giảm deadlock nhưng có chi phí sắp xếp, nên benchmark.

Deep Dive — Hibernate Statistics & Đo lường N+1

D3 Đo hiệu năng ORM bằng Hibernate Statistics — phát hiện N+1 khách quan?

What

Hibernate Statistics (org.hibernate.stat.Statistics) là bộ đếm metrics của một SessionFactory/EntityManagerFactory: số câu query đã thực thi, số PreparedStatement, số lần load/fetch entity, số lần open/close session, flush, và hiệu quả cache L2 (hit/miss/put). Không bật mặc định; bật bằng hibernate.generate_statistics=true rồi lấy qua sessionFactory.getStatistics().

Why

N+1 rất khó "đo bằng cảm giác". Statistics cho con số dứt khoát: ví dụ 1 request mà getQueryExecutionCount() tăng 101 trong khi chỉ load 100 entity cha → có N+1. Nó cũng cho biết cache L2 có thực sự hữu ích (hit ratio) hay đang làm chậm vì invalidate liên tục. Dùng để chứng minh cải thiện trước/sau khi thêm EntityGraph/@BatchSize, và làm "hàng rào hồi quy" trong test (assert số query không vượt ngưỡng).

How
generate_statistics=true
↓ chạy request / load test
getQueryExecutionCount()
getEntityFetchCount()
getSecondLevelCacheStatistics()
↓ query ≫ entity cha → nghi N+1; cache miss cao → L2 vô ích
N+1 / cache kém hiệu quả

Bổ trợ: SessionFactory.getStatistics().logSummary(); datasource-proxy / p6spy để xem SQL thật; hibernate.session.events.log để log số query mỗi session.

When

Bật ở môi trường dev/staging và trong load test, integration test khi cần khẳng định số query. Kết hợp default_batch_fetch_size / @BatchSize để giảm N+1 mà vẫn giữ LAZY. Giữ Statistics nhẹ ở production nếu chỉ cần đếm tổng (clear định kỳ) — nhưng cẩn thận chi phí thu thập.

When NOT

Đừng coi Statistics là APM thay thế — nó đo trong tiến trình, không thay trace phân tán. Đừng bật rồi để counter phình vô hạn ở production (cần clear()). Đừng đọc getEntityLoadCount() mà nhầm với getEntityFetchCount(). Đừng tối ưu "theo cảm giác" khi đã có số liệu — luôn đo trước/sau.

Integration test API list đơn hàng: chạy request, đọc getQueryExecutionCount(), assert nhỏ hơn ngưỡng (ví dụ <= 3). Khi dev vô tình touch association trong loop, test đỏ ngay thay vì để lên production. Load test staging dùng hit ratio L2 để quyết định giữ hay bỏ cache entity.
Pitfall / Interview trap
"Bật show-sql là đủ để thấy N+1?" — show-sql chỉ in SQL, không đếm; Statistics cho con số tổng hợp. Đừng nhầm getEntityLoadCount() (số entity nạp) với getEntityFetchCount() (số lần fetch association). Ở production, counter tích luỹ vô hạn gây nhiễu — cần clear() định kỳ hoặc tắt. Statistics hữu ích nhưng không thay thế APM cho hệ phân tán.

Đào sâu và đính chính phỏng vấn

Stale L1/L2 sau native SQL hoặc writer ngoài Hibernate: refresh không phải thần dược

What

L1 giữ managed entity trong Persistence Context nên có thể stale sau bulk/native SQL hoặc writer bên ngoài. L2 cũng không tự biết mọi thay đổi ngoài Hibernate; cần invalidation rõ ràng và hiểu snapshot isolation khi refresh hoặc mở lại context.

How / Trade-offs / Pitfalls
  • find theo ID đã managed thường trả cùng object L1 chứ không SELECT lại. entityManager.refresh reload một entity và ghi đè state chưa flush; clear detach toàn bộ, detach chỉ một entity. Không clear mù khi còn thay đổi chưa flush; nếu định flush trước thì phải kiểm tra có ghi đè concurrent update không. @Version kiểm soát conflicting writes, không tự làm reads fresh.
  • Bulk JPQL/native SQL bỏ qua đồng bộ state managed entity. flush/clear đúng boundary hoặc clearAutomatically/flushAutomatically khi phù hợp; kiểm thử bằng hai transaction độc lập. Native SQL qua Hibernate có cơ chế query-space/cache synchronization theo API/version; không nói mọi native update đều tự evict đúng toàn bộ L2.
  • Writer bên ngoài Hibernate: evict entity/collection/query regions bị ảnh hưởng hoặc tích hợp CDC/invalidation. L2 eviction không xóa object đang nằm trong L1 của session khác. TTL giới hạn thời gian tồn tại nhưng không bảo đảm strict consistency; query cache khác entity cache. READ_WRITE cache strategy không biến external writers thành transaction participants.
  • Dưới PostgreSQL REPEATABLE READ, clear rồi SELECT hay refresh vẫn tuân snapshot của transaction, không bảo đảm thấy commit mới bên ngoài; cần kết thúc transaction và mở transaction mới nếu cần snapshot mới. Dữ liệu balance/inventory quan trọng phải kiểm tra và ghi atomically ở DB, không dựa stale cache.
Evidence → bounded resource / transaction boundary → failure test → verify recovery
// Sau bulk update tại boundary đã thiết kế:
entityManager.clear(); // không bỏ thay đổi chưa xử lý
// Refresh một entity khi chấp nhận overwrite local changes:
entityManager.refresh(entity);
// Evict L2 theo entity key (không tác động L1 session khác):
entityManagerFactory.getCache().evict(Product.class, productId);
