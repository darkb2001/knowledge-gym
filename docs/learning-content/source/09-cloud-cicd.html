Cloud (GCP / AWS)

Q1 Deploy & auto-scale Java trên K8s / GKE / EKS / Cloud Run

What

Deploy Java Spring Boot lên K8s/GKE/EKS/Cloud Run/ECS Fargate: multi-stage Dockerfile JRE slim, Deployment + Service + HPA auto-scale theo CPU/RPS.

Why

Cloud-native Java = container 12-factor, không SSH server. HPA scale pod horizontal thay vertical. Chọn platform theo ops maturity vs serverless simplicity.

How

Dockerfile: temurin JDK build → JRE alpine runtime, non-root user, MaxRAMPercentage 75%. K8s: requests/limits, readiness/liveness actuator, HPA min 3 max 20 CPU 70%.

Docker Image
PlatformĐặc điểmAuto-scalePhù hợp
GKE (GCP)Managed K8s, Workload Identity, Cloud SQL proxyHPA + Cluster Autoscaler + VPAEnterprise, multi-service
EKS (AWS)Managed K8s, IRSA, ALB IngressHPA + Karpenter / CAAWS-native workloads
Cloud RunServerless container, scale-to-zeroRequest-based auto-scaleAPI nhẹ, traffic biến động
ECS FargateServerless container AWSService auto-scalingĐơn giản hơn K8s trên AWS
 
# Multi-stage Dockerfile cho Spring Boot
FROM eclipse-temurin:21-jdk-alpine AS build
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN ./mvnw package -DskipTests

FROM eclipse-temurin:21-jre-alpine
RUN addgroup -S app && adduser -S app -G app
USER app
COPY --from=build /app/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-XX:+UseContainerSupport", "-XX:MaxRAMPercentage=75.0", "-jar", "app.jar"]

When

GKE/EKS: enterprise multi-service, full control. Cloud Run: API traffic biến động, scale-to-zero OK cold start 1-3s.

When NOT

Không Cloud Run long-running batch 30min — timeout limit. Không fat JRE image 500MB khi jlink slim đủ. Không HPA không set requests — scale sai.

Use case

Order service Black Friday: HPA 3→18 pods CPU 70%; Cloud Run dev API scale zero tiết kiệm cost.

Pitfall / Interview trap

Cold start Cloud Run; missing resource requests HPA blind.

Nói trong 60 giây
  • Multi-stage Docker JDK build JRE run.
  • K8s Deployment + HPA CPU target.
  • GKE/EKS full control; Cloud Run serverless.
  • Actuator health probes readiness/liveness.
  • Non-root user + MaxRAMPercentage container.

Q2 Multi-AZ, VPC, Private Subnets, IAM Least Privilege

What

Multi-AZ VPC: public subnet (LB/NAT) + private subnet (app/DB). IAM least privilege: service account per app, Security Group minimal, K8s NetworkPolicy deny-all default.

Why

Security compliance + HA. DB không expose internet. Compromised pod không lateral move nếu NetworkPolicy strict.

How

App pods 3 AZ spread. RDS Multi-AZ private subnet. SG: app inbound 8080 from LB only; DB 5432 from app SG. GKE Workload Identity bind K8s SA → GCP SA scoped role.

CI/CD Pipeline

Q3 Thiết kế pipeline GitLab CI/CD hoàn chỉnh

What

Pipeline GitLab CI/CD: validate→test→SonarQube→build image→Trivy scan→deploy staging→E2E→manual prod deploy.

Why

Shift-left quality + automated deploy giảm human error. Quality gate block bad code trước production.

How

Stages parallel where safe (needs:). Maven cache .m2. JUnit artifact report. Sonar qualitygate.wait=true. Docker push CI_REGISTRY. Trivy HIGH/CRITICAL exit 1. kubectl rollout status staging. E2E profile verify. deploy-prod when:manual main only.

Lint
# .gitlab-ci.yml
stages: [validate, test, quality, build, scan, deploy-staging, e2e, deploy-prod]

variables:
  MAVEN_OPTS: "-Dmaven.repo.local=$CI_PROJECT_DIR/.m2/repository"
  DOCKER_IMAGE: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA

cache:
  paths: [.m2/repository/]

lint:
  stage: validate
  script:
    - ./mvnw checkstyle:check spotless:check

unit-test:
  stage: test
  script:
    - ./mvnw test -DfailIfNoTests=false
  artifacts:
    reports:
      junit: target/surefire-reports/TEST-*.xml
    paths: [target/site/jacoco/]

sonarqube:
  stage: quality
  script:
    - ./mvnw sonar:sonar -Dsonar.qualitygate.wait=true
  allow_failure: false

build-image:
  stage: build
  script:
    - docker build -t $DOCKER_IMAGE .
    - docker push $DOCKER_IMAGE

security-scan:
  stage: scan
  script:
    - trivy image --severity HIGH,CRITICAL --exit-code 1 $DOCKER_IMAGE

deploy-staging:
  stage: deploy-staging
  script:
    - kubectl set image deployment/order-service app=$DOCKER_IMAGE -n staging
    - kubectl rollout status deployment/order-service -n staging

e2e-test:
  stage: e2e
  script:
    - ./mvnw verify -Pe2e -Dstaging.url=$STAGING_URL

deploy-prod:
  stage: deploy-prod
  when: manual
  only: [main]
  script:
    - kubectl set image deployment/order-service app=$DOCKER_IMAGE -n production
When

Team ≥3 dev, release weekly+. GitLab self-hosted hoặc SaaS.

When NOT

Không skip test stage prod deploy. Không manual deploy without audit trail. Không secrets in .gitlab-ci.yml plain text — CI variables masked.

Use case

PR merge main: auto staging deploy + E2E pass → engineer click manual prod promote.

Pitfall / Interview trap

Flaky E2E block pipeline; Docker DinD permission CI runner.

Nói trong 60 giây
  • Stages: lint, test, Sonar, build, scan, staging, E2E, prod.
  • Trivy block CVE HIGH image.
  • Sonar quality gate mandatory.
  • Prod deploy manual approval main.
  • Cache Maven + parallel needs keyword.

Q4 Debug pipeline khi build hoặc deploy fail

What

Debug CI/CD fail theo stage: unit test surefire report, Sonar quality gate, Docker build, Trivy CVE, K8s deploy events, E2E staging health.

Why

DevOps interview + daily unblock pipeline. Fail fast identify stage root cause không guess.

How

Unit: mvn test local + read TEST-*.xml. Sonar dashboard blocker issues. Docker: build --no-cache local. Deploy: kubectl describe pod events ImagePullBackOff. CI_DEBUG_TRACE=true verbose. gitlab-runner exec docker reproduce.

  • CI_DEBUG_TRACE verbose GitLab.
  • gitlab-runner exec docker local.

Q5 Blue/Green Deployment & Canary Release

What

Blue/Green: 2 env identical, switch traffic 100% instant, rollback switch back. Canary: gradual 5→25→50→100% new version monitor metrics auto rollback.

Why

Zero-downtime deploy + limit blast radius bad release. Canary catch error rate spike trước full rollout.

How

Blue/Green: 2 Deployment + Service selector flip hoặc Ingress weight. Canary: Argo Rollouts/Flagger steps setWeight + pause + analysis error-rate template.

Blue/Green

  • 2 environment identical: Blue (live), Green (new)
  • Deploy Green → test → switch traffic 100%
  • Rollback = switch back to Blue
  • Instant switch, cần 2× resource
  • K8s: 2 Deployment + Service selector switch

Canary

  • Deploy new version cho % nhỏ traffic (5→25→50→100%)
  • Monitor error rate, latency
  • Auto rollback nếu metrics degrade
  • Tiết kiệm resource hơn Blue/Green
  • K8s: Argo Rollouts, Flagger, Istio
LB / Ingress
↓
v1.0 (95%)
v1.1 Canary (5%)
↓ metrics OK → increase
v1.1 (100%)
# Argo Rollouts Canary example
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: order-service
spec:
  strategy:
    canary:
      steps:
        - setWeight: 5
        - pause: { duration: 5m }
        - setWeight: 25
        - pause: { duration: 5m }
        - setWeight: 50
        - pause: { duration: 5m }
        - setWeight: 100
      analysis:
        templates:
          - templateName: error-rate
        startingStep: 1
When

Blue/Green: critical instant rollback need, budget 2× resource. Canary: gradual confidence, metric-driven, save resource.

When NOT

Không canary without metrics observability — blind rollout. Không blue/green DB schema breaking incompatible both versions.

Use case

Payment service canary 5% 5min error rate OK → 25% → 100%; spike → auto rollback v1.

Pitfall / Interview trap

Session sticky break on switch; DB migration backward compatible required.

Nói trong 60 giây
  • Blue/Green: 2 env switch 100% instant.
  • Canary: gradual % + metric analysis.
  • Argo Rollouts setWeight pause steps.
  • Auto rollback error rate degrade.
  • Schema change must both versions compatible.

Testing Pyramid

Q6 Unit Test / Integration Test / E2E Test

What

Testing pyramid: nhiều Unit (fast mock), vừa Integration (real DB Testcontainers), ít E2E (full flow Playwright).

Why

E2E chậm đắt flaky — không scale 1000 tests. Unit catch logic bug ms; Integration catch SQL/schema; E2E catch wiring.

How

Unit: JUnit5 + Mockito @ExtendWith. Integration: @SpringBootTest + Testcontainers PostgreSQL @DynamicPropertySource. E2E: REST Assured/Playwright staging.

E2E (ít, chậm, đắt)
TầngScopeToolSpeedVí dụ
Unit1 class/method, mock dependenciesJUnit 5, Mockito, AssertJmsTest OrderService.calculateTotal()
IntegrationMulti-component, real DB/HTTPSpring Boot Test, TestcontainerssecondsTest OrderController → DB
E2EFull user flow, real envPlaywright, REST Assured, CucumberminutesUser đặt hàng → thanh toán → confirm
 
// Unit test — mock repository
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
  @Mock OrderRepository orderRepo;
  @InjectMocks OrderService orderService;

  @Test
  void shouldCalculateTotal() {
    var order = new Order(List.of(new Line("SKU1", 2, new BigDecimal("100"))));
    assertThat(orderService.calculateTotal(order)).isEqualByComparingTo("200");
  }
}

// Integration test — real Spring context + Testcontainers
@SpringBootTest
@Testcontainers
class OrderIntegrationTest {
  @Container
  static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16");

  @Autowired TestRestTemplate rest;

  @Test
  void createOrder_endToEnd() {
    var response = rest.postForEntity("/api/orders", request, OrderResponse.class);
    assertThat(response.getStatusCode()).isEqualTo(HttpStatus.CREATED);
  }
}
When

Unit mọi business logic. Integration repository/controller+DB. E2E critical user journey checkout.

When NOT

Không E2E cho mọi edge case — unit cover. Không mock everything integration — false confidence H2 vs PostgreSQL.

Use case

OrderService unit mock repo; OrderIntegrationIT Testcontainers JSONB query; E2E staging create order flow.

Pitfall / Interview trap

Ice cream cone anti-pattern — nhiều E2E ít unit.

Nói trong 60 giây
  • Pyramid: nhiều unit, vừa integration, ít E2E.
  • Unit Mockito fast isolated.
  • Integration Testcontainers real PostgreSQL.
  • E2E critical path staging only.
  • H2 không thay PostgreSQL production dialect.

Q7 Xử lý Flaky Tests

What

Flaky test pass/fail không deterministic cùng code — timing, shared state, order dependency, external API, Date/random.

Why

Flaky erode CI trust → team ignore red pipeline → real bug miss. Waste engineer hours rerun.

How

Fix root: Awaitility thay Thread.sleep. @DirtiesContext/@Transactional rollback isolation. Inject Clock.fixed(). WireMock external. @Tag flaky quarantine + JIRA ticket. Track flaky rate metric.

Nguyên nhânVí dụFix
Timing / asyncThread.sleep(100) không đủAwaitility, CountDownLatch, @Timeout
Shared stateStatic counter, DB không cleanup@DirtiesContext, @Transactional rollback, @BeforeEach reset
Order dependencyTest A tạo data cho Test BIsolate: mỗi test tự setup data
External dependencyCall real API, network timeoutMock/WireMock, Testcontainers
Date/timenew Date() → fail midnightClock.fixed(), inject Clock bean
RandomUUID.random in assertionSeed random, mock RandomGenerator
 
// ❌ Flaky — hardcoded sleep
Thread.sleep(500);
assertThat(result.isReady()).isTrue();

// ✅ Stable — Awaitility
await().atMost(Duration.ofSeconds(5))
    .pollInterval(Duration.ofMillis(100))
    .until(() -> result.isReady());

// Quarantine flaky tests — tag và chạy riêng
@Tag("flaky")
@Disabled("Flaky — ticket JIRA-1234")
@Test
void flakyTest() { ... }
When

CI intermittent red; test pass local fail CI.

When NOT

Không @Disabled flaky indefinitely — fix or delete. Không retry 3x Maven surefire hide flake — fix root.

Use case

Async test sleep 100ms flake → Awaitility atMost 5s poll 100ms stable.

Pitfall / Interview trap

Test order dependency JUnit5; static mutable state leak.

Nói trong 60 giây
  • Flaky = nondeterministic pass/fail.
  • Cause: timing, shared state, external.
  • Fix: Awaitility, Clock inject, isolate data.
  • Quarantine @Tag flaky + ticket.
  • Flaky test = bug in test or code.

Q9 Contract Testing với Pact

What

Pact contract testing: Consumer define expected API → pact JSON → Provider verify implementation match — không deploy full stack.

Why

Microservices breaking API change detect CI trước prod. Consumer-driven: provider biết client expect gì.

How

Consumer @Pact test mock server verify client. Publish pact broker. Provider @ProviderVerification verify against pact file. CI fail provider nếu response schema change.

Consumer Test
// Consumer side — Order Service calls Payment Service
@ExtendWith(PactConsumerTestExt.class)
@PactTestFor(providerName = "payment-service")
class PaymentClientPactTest {

  @Pact(consumer = "order-service")
  public static RequestResponsePact createPaymentPact(PactDslWithProvider builder) {
    return builder
        .given("payment method exists")
        .uponReceiving("a request to charge")
        .path("/api/payments/charge")
        .method("POST")
        .body(new PactDslJsonBody()
            .decimalType("amount", 100.00)
            .stringType("currency", "VND"))
        .willRespondWith()
        .status(200)
        .body(new PactDslJsonBody()
            .stringType("transactionId", "txn-123")
            .stringValue("status", "SUCCESS"))
        .toPact();
  }

  @Test
  void testCharge(MockServer mockServer) {
    var client = new PaymentClient(mockServer.getUrl());
    var result = client.charge(new ChargeRequest(new BigDecimal("100"), "VND"));
    assertThat(result.getStatus()).isEqualTo("SUCCESS");
  }
}
When

≥2 teams own consumer/provider services. REST API stable contract.

When NOT

Không pact thay E2E business flow — complementary. Không pact internal private method — API boundary only.

Use case

Order service expect Payment charge response transactionId — Payment rename field → provider verification fail CI.

Pitfall / Interview trap

Pact broker versioning; provider states given clause setup.

Nói trong 60 giây
  • Consumer-driven contract Pact JSON.
  • Consumer test generate pact file.
  • Provider verification CI gate.
  • Breaking change fail before deploy.
  • Complement not replace E2E.

Q10 Performance Testing — JMeter & Gatling

What

Performance test JMeter (GUI XML) vs Gatling (Scala/Java DSL code-as-test). Measure RPS, p50/p95/p99 latency, error rate under load.

Why

Functional test pass không đảm bảo scale. Baseline before/after optimization. SLA p99<500ms validate.

How

Gatling: rampUsers + constantUsersPerSec scenario. Assertions p99<500ms error<1%. JMeter thread group ramp. Monitor JVM GC CPU during test. Staging env representative data volume.

ToolLanguageStrengthWeakness
JMeterGUI + XMLDễ bắt đầu, nhiều protocolGUI-heavy, khó version control
GatlingScala/Java DSLCode-as-test, reports đẹp, high perfLearning curve Scala DSL
 
// Gatling Java DSL
public class OrderLoadSimulation extends Simulation {

  HttpProtocolBuilder httpProtocol = http
      .baseUrl("https://api.staging.example.com")
      .acceptHeader("application/json");

  ScenarioBuilder scn = scenario("Create Order")
      .exec(http("Create Order")
          .post("/api/orders")
          .body(StringBody("""{"sku":"ABC","qty":1}"""))
          .check(status().is(201)))
      .pause(1);

  {
    setUp(
      scn.injectOpen(
        rampUsers(100).during(Duration.ofMinutes(5)),  // ramp up
        constantUsersPerSec(50).during(Duration.ofMinutes(10)) // steady
      )
    ).protocols(httpProtocol)
     .assertions(
       global().responseTime().percentile3().lt(500),  // p99 < 500ms
       global().successfulRequests().percent().gt(99.0)     // error < 1%
     );
  }
}
When

Pre-release major feature, capacity planning, regression after perf fix.

When NOT

Không load test prod without approval — impact users. Không single-user test call performance test.

Use case

Gatling 100 user ramp 5min steady 50 RPS — p99 420ms pass gate deploy prod.

Pitfall / Interview trap

Staging smaller DB false positive pass; not warm JVM before measure.

Nói trong 60 giây
  • JMeter GUI vs Gatling code DSL.
  • Metrics: RPS, p99 latency, error rate.
  • Gatling ramp + steady state injection.
  • Assert SLA threshold CI gate.
  • Staging representative data volume.

Q11 Mutation Testing (PIT) — Mutation Score

What

Mutation testing PIT: inject code mutants (a+b→a-b) → test kill mutant = good test; survived = weak assertion. Mutation score = KILLED/(KILLED+SURVIVED).

Why

80% line coverage có thể assert yếu — mutant survived. Measure test quality not just coverage.

How

pitest-maven plugin targetClasses service.* mutationThreshold 80. Run mutationCoverage. HTML report survived mutants → add test case kill.

Original Code
TermMeaning
Mutant KILLEDTest fail khi code bị mutate → test tốt
Mutant SURVIVEDTest vẫn pass dù code sai → test yếu, cần thêm assertion
Mutation ScoreKILLED / (KILLED + SURVIVED) × 100%. Target ≥ 80%
Timeout / No CoverageMutant không chạy được → excluded from score

  <version>1.15.3</version>

      <param>com.example.service.*</param>
    </targetClasses>
    <targetTests>
      <param>com.example.service.*Test</param>
    </targetTests>

    <outputFormats>HTML</outputFormats>
  </configuration>
</plugin>

<!-- Run: mvn org.pitest:pitest-maven:mutationCoverage -->
When

Critical domain payment/inventory logic. Improve test suite quality audit.

When NOT

Không PIT mọi PR — slow minutes. Không chase 100% mutation score diminishing return.

Use case

if qty>0 mutant qty>=0 survived — add test qty=0 edge kill mutant.

Pitfall / Interview trap

D1 Build once, deploy many — artifact promotion & image digest pinning

What

Build once, deploy many: container image được build & đóng gói một lần ở CI, rồi promote nguyên bản (cùng digest sha256) qua dev → staging → prod. Không rebuild lại cho từng môi trường.

Why

Rebuild ở mỗi env sinh ra artifact khác nhau (base image mới hơn, dependency trôi version) → lỗi kinh điển "chạy được ở staging, chết ở prod". 12-factor tách bạch build / release / run; digest bất biến cho phép rollback chính xác và audit đầy đủ.

How

CI build một lần, push registry, lấy digest bất biến. CD deploy bằng image@sha256:… thay vì tag mutable (:latest). Promote = deploy cùng digest sang env kế tiếp. Bật BuildKit cache mount và xếp layer hợp lý (COPY pom.xml trước src) để tái dùng layer cache, build nhanh hơn nhiều.

↓ promote cùng artifact, KHÔNG rebuild

rollback = deploy lại digest của bản trước
When

Microservices nhiều môi trường, yêu cầu audit/compliance, release & rollback thường xuyên, nhiều team cùng deploy chung registry.

When NOT

Không dùng tag mutable (:latest, :prod) trong production — không truy vết được. Không pin digest khi cần dev hot-reload liên tục. Prototype một môi trường duy nhất thì promote ít giá trị.

D2 Zero-downtime DB migration — Expand / Contract (backward-compatible)

What

Thay đổi schema theo 3 pha Expand (mở rộng) → Migrate (di trú) → Contract (thu hẹp), mỗi pha là một migration riêng deploy cùng app version. Mục tiêu: schema luôn tương thích ngược để bản app cũ và mới chạy song song được.

Why

Rolling deploy chạy 2 version app đồng thời (pod cũ + pod mới). Nếu đổi cột "một phát" (rename/drop/NOT NULL) thì version cũ gãy ngay → 500 errors, downtime. Expand/contract (Martin Fowler: Parallel Change) tách thay đổi phá vỡ thành các bước an toàn.

How

Expand: thêm cột mới NULL, chưa ràng buộc. Migrate: code mới dual-write (ghi cả cũ lẫn mới), đọc mới + fallback cũ; backfill dữ liệu theo lô. Contract: khi 100% traffic đã dùng schema mới, mới xoá cột/đường cũ. Flyway/Liquibase quản lý versioned migration, mỗi bước idempotent.

1. Expand — thêm cột nullable + backfill theo lô
↓ deploy app version mới (dual-write, đọc mới fallback cũ)
2. Migrate — chuyển hết consumer sang cột mới
↓ khi 100% traffic đã dùng schema mới
3. Contract — xoá cột / đường code cũ
When

Mọi thay đổi schema phá vỡ (rename/drop/đổi kiểu/thêm NOT NULL) trên hệ thống deploy zero-downtime, DB lớn, nhiều replica đọc.

When NOT

Không cần 3 pha cho thay đổi additive thuần (thêm bảng/cột nullable mới). Không drop cột cũ khi vẫn còn instance bản cũ đang chạy — phải chờ rollout xong. Không chạy UPDATE backfill toàn bảng trong 1 transaction — sẽ giữ lock lâu.

PhaThay đổi DBThay đổi AppRủi ro nếu làm sai

-- Expand: them cot NULL duoc, KHONG dung NOT NULL DEFAULT (co the lock/rewrite bang)
ALTER TABLE orders ADD COLUMN customer_ref UUID NULL;
-- Migrate: backfill theo lo (batch) de khong giu lock/CPU qua lau
UPDATE orders SET customer_ref = legacy_customer_id WHERE customer_ref IS NULL;
-- Contract (chi sau khi 100% code moi da deploy):
-- ALTER TABLE orders DROP COLUMN legacy_customer_id;
public class OrderWriter {
  // Migrate: ghi CA cot cu lan moi (dual write), doc uu tien cot moi + fallback cu
  public void save(Order o) {
    o.setLegacyCustomerId(o.getCustomerRef()); // dual write
    repository.save(o);
  }
  public String readCustomerRef(Order o) {
    return o.getCustomerRef() != null ? o.getCustomerRef() : o.getLegacyCustomerId();
  }
}
Use case

Đổi tên cột customer_id → customer_ref kiểu UUID trên bảng orders 50M dòng mà không downtime: thêm cột mới, dual-write, backfill đêm, rồi drop cột cũ ở release sau.

Pitfall / Interview trap

RENAME/DROP COLUMN một phát trong cùng release = downtime. Và migration phá vỡ đi trước code (backward) chứ không phải sau. Luôn có kế hoạch rollback: giữ cột cũ tới khi chắc chắn.

D3 Secrets & supply-chain — OIDC keyless + SBOM / vulnerability scan

What

Pipeline lấy credential tạm thời qua OIDC (workflow → cloud STS) thay vì lưu secret dài hạn trong CI. Kèm bước SBOM (liệt kê thành phần), scan CVE và ký artifact để chặn supply-chain attack.

Why

Secret dài hạn nằm trong CI = blast radius lớn nếu leak, lại phải rotate thủ công. OIDC đổi lấy token ngắn hạn chỉ sống trong 1 job, tự hết hạn, không nhân bản credential. SBOM + scan cho biết đang dùng thành phần nào, CVE nào; chữ ký đảm bảo artifact không bị sửa.

How

permissions: id-token: write để workflow xin JWT; cloud tin OIDC provider của GitHub/GitLab kèm claim repo/branch → AssumeRole. Sau build: syft xuất SBOM (CycloneDX/SPDX), trivy fail khi có HIGH/CRITICAL, cosign ký image; deploy từ chối image chưa ký.

Workflow job
OIDC provider (GitHub)
↓ JWT mang claim repo/branch — KHÔNG có secret dài hạn
Cloud STS AssumeRole
Token tạm thời (hết hạn cuối job)
↓ build → SBOM → scan → ký → deploy
When

Deploy lên cloud (AWS/GCP/Azure/Vault) từ CI, môi trường có compliance (SLSA, SOC2), cần chứng minh artifact toàn vẹn.

When NOT

Không phải cứ nhiều secret là an toàn — OIDC cần trust policy chặt (đừng để * cho mọi repo). Không dùng pull_request_target cẩu thả rồi cấp id-token (workflow từ fork có thể lợi dụng). Với hệ thống không hỗ trợ OIDC thì vẫn cần vault + rotate định kỳ.
