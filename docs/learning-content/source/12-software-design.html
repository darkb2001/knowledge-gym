Software Design Documents & UML

SRS, SDD, HLD/LLD, Interface Design, FDS, TDS — kèm UML diagrams và PlantUML examples cho hệ thống WCS/WMS warehouse automation.

Tài liệu thiết kế phần mềm

Q1 SRS — Software Requirements Specification

What

SRS (Software Requirements Specification) mô tả WHAT hệ thống phải làm — functional, non-functional, constraints, assumptions — không HOW implement.

Why

Contract giữa stakeholder và dev team; base test case acceptance criteria UAT. Enterprise WCS project cần SRS signed trước design.

How

Sections: Functional (allocate bin, release pick), Non-functional (p99<200ms, 99.9% uptime), Constraints (integrate SAP EDI), Assumptions (PLC latency<50ms). Traceability matrix req ID → test case.

PhầnNội dungVí dụ WMS
Functional RequirementsChức năng hệ thống phải thực hiệnAllocate bin, release pick task, confirm putaway
Non-functional RequirementsPerformance, availability, securityAPI response < 200ms, uptime 99.9%, RBAC
ConstraintsGiới hạn kỹ thuật / nghiệp vụPhải tích hợp SAP ERP qua EDI
AssumptionsGiả định khi viết SRSNetwork latency PLC < 50ms
When

Enterprise fixed bid, compliance audit, multi-vendor integration WMS customer.

When NOT

Không SRS chi tiết HOW code class — thuộc LLD/TDS. Không Agile spike thay SRS contract project — dùng epic+AC thay thế.

Use case

WMS WCS SRS: FR-012 allocate bin <500ms, NFR-003 uptime 99.9%, constraint SAP IDoc.

Pitfall / Interview trap

SRS vs User Story khi nào; ambiguous requirement không measurable.

Nói trong 60 giây
  • SRS = WHAT not HOW.
  • Functional + non-functional + constraints.
  • Base acceptance test UAT.
  • Enterprise contract WCS customer.
  • Agile user story khi team nhỏ thay đổi nhanh.

Q2 SDD — HLD vs LLD

What

HLD high-level architecture component data flow tech stack vs LLD class sequence ERD API detail algorithm.

Why

Separation audience: architect/PM vs developer/QA. SRS→HLD→LLD→Code traceability.

How

HLD: component diagram WMS↔WCS↔PLC deployment topology. LLD: class diagram, sequence allocate bin, Flyway schema, error handling state machine.

HLD (High-Level Design)

  • Audience: Architect, Tech Lead, PM
  • Component diagram, data flow
  • Technology stack selection
  • Integration points (WMS ↔ WCS ↔ PLC)
  • Deployment topology

LLD (Low-Level Design)

  • Audience: Developer, QA
  • Class diagram, sequence diagram
  • Database schema (ERD)
  • API contract chi tiết
  • Algorithm, error handling
SRS (Requirements)
↓
HLD (Architecture)
↓
LLD (Implementation Detail)
↓
Code + Unit Test
When

HLD sprint 0 architecture review. LLD per feature sprint before coding.

When NOT

Không LLD trước HLD approved — rework. Không HLD quá chi tiết class level — blur boundary.

Use case

HLD choose MQTT vs OPC-UA; LLD PlcGateway interface sequence diagram.

Pitfall / Interview trap

HLD/LLD outdated living doc; who maintains.

Nói trong 60 giây
  • HLD architecture component data flow.
  • LLD class sequence ERD API.
  • Flow SRS → HLD → LLD → Code.
  • HLD audience architect PM.
  • LLD audience developer QA implement.

Q4 FDS & TDS

What

FDS functional design business view Input→Process→Output rules vs TDS technical class algorithm DB schema message format performance target.

Why

Bridge BA business language và dev technical. FDS sign-off business TDS sign-off tech lead.

How

FDS: putaway flow ASN receive assign bin confirm business validation. TDS: PutawayService class slotting algorithm index strategy Kafka payload JSON load test 500 TPS.

FDS (Functional Design Specification)

  • Bridge giữa BA và Developer
  • Mô tả chức năng từ góc nhìn business
  • Input → Process → Output
  • Business rules, validation logic
  • Ví dụ: Putaway flow — nhận ASN, assign bin, confirm

TDS (Technical Design Specification)

  • Chi tiết kỹ thuật triển khai
  • Class design, algorithm
  • DB schema, index strategy
  • Message format (Kafka, MQTT payload)
  • Performance target, load test plan
When

FDS UAT scenario BA review. TDS implementation sprint dev reference.

When NOT

Không TDS without FDS approved scope creep. Không FDS code pseudo quá chi tiết — blur LLD.

Use case

FDS putaway rule hazmat SKU special zone; TDS Redis lock bin implementation.

Pitfall / Interview trap

FDS/TDS duplicate content maintain sync.

Nói trong 60 giây
  • FDS business Input Process Output.
  • TDS technical class DB algorithm.
  • Bridge BA and developer.
  • FDS business sign-off first.
  • TDS performance load test plan.

Deep Dive — Thiết kế thực chiến: SOLID, Coupling & Hexagonal

D1 SOLID thực chiến — nhận diện vi phạm và cách sửa

What

SOLID là 5 nguyên tắc hướng đối tượng: SRP (một lý do để thay đổi), OCP (mở để mở rộng, đóng để sửa), LSP (subtype thay được supertype), ISP (không ép client phụ thuộc method nó không dùng), DIP (phụ thuộc abstraction). Đây là guideline, không phải luật cứng — mục tiêu cuối là giảm coupling, tăng cohesion.

Why

Interviewer senior không hỏi "kể tên 5 nguyên tắc" mà hỏi "cho ví dụ vi phạm và cách sửa". SOLID giúp code dễ test, dễ thay đổi; vi phạm nó chính là nguồn gốc của "software rot" (mục nát phần mềm).

How

Với mỗi nguyên tắc, nhận diện code smell rồi refactor:

Nguyên tắcDấu hiệu vi phạm (smell)Cách sửa
SRP1 class vừa tính toán, vừa gửi email, vừa format reportTách theo trục thay đổi, không theo "tầng"
OCPThêm loại mới phải sửa switch/if-else dàiĐa hình + Strategy/Factory
LSPSubclass throw exception "not supported" cho method của chaSubtype phải tôn trọng contract (pre/post-condition)
ISPInterface "fat" 20 method, client chỉ dùng 2Tách interface nhỏ theo nhu cầu client
DIPService new trực tiếp concrete repositoryInject interface qua constructor
 
// VI PHẠM OCP + DIP: thêm kênh mới phải sửa if-else, new trực tiếp
class Notifier {
  void send(String type, String msg) {
    if (type.equals("email")) new SmtpEmailSender().send(msg);
    else if (type.equals("sms")) new TwilioSender().send(msg);
  }
}

// SỬA: abstraction + inject (OCP + DIP)
interface MessageSender { void send(String msg); }
class Notifier {
  private final MessageSender sender;     // phụ thuộc abstraction
  Notifier(MessageSender sender) { this.sender = sender; }
  void send(String msg) { sender.send(msg); }   // thêm kênh = thêm impl, không sửa class này
}
When

Áp dụng khi biết trước trục thay đổi: nhiều implementation, nhiều kênh, nhiều tenant. Dùng khi review code hoặc trước khi thêm một feature lặp lại lần thứ 3.

When NOT

SRP/ISP cực đoan sinh "class 3 dòng + 200 interface" — over-engineering. DIP không có nghĩa mọi class phải có interface — chỉ ở biên (boundary) nơi implementation thực sự có thể đổi. Đừng tách interface cho class chưa từng có >1 implementation.

Pitfall / Interview trap

Nhầm SRP với "class chỉ được làm 1 việc nhỏ". SRP thực ra là "một lý do để thay đổi" — một class có thể có nhiều method nếu chúng cùng phục vụ một actor/trục thay đổi. Interviewer hay hỏi: "class 10 method có vi phạm SRP không?" — câu trả lời: tùy, hãy xét lý do thay đổi chứ không đếm method.

D2 Coupling vs Cohesion — Layering vs Hexagonal (Ports & Adapters)

What

Cohesion = mức độ các phần trong một module thuộc về nhau (cao là tốt). Coupling = mức độ phụ thuộc giữa các module (thấp là tốt). Layered architecture xếp tầng UI → Service → Domain → Persistence (dependency hướng xuống). Hexagonal (Ports & Adapters) đặt domain ở giữa, mọi thứ bên ngoài (DB, HTTP, queue) giao tiếp chỉ qua port — interface do domain định nghĩa.

Why

Layering dễ hiểu nhưng khi service phụ thuộc trực tiếp Repository/JPA thì domain coupling chặt với hạ tầng — khó test, khó đổi DB. Hexagonal đảo chiều phụ thuộc (DIP): adapter phụ thuộc vào port của domain, không ngược lại. Kết quả: test domain thuần bằng in-memory adapter, đổi công nghệ không đụng business logic.

How

Chuyển từ layered sang hexagonal theo 2 bước: (1) đảo chiều dependency, (2) định nghĩa port nằm trong domain.

Layered (3-tier)

  • Dependency hướng xuống theo tầng
  • Domain thường biết DB/SQL
  • Test tích hợp phải dựng DB
  • Nhanh gọn cho CRUD đơn giản

Hexagonal (Ports & Adapters)

  • Domain ở giữa, adapter ở ngoài
  • Adapter phụ thuộc port của domain
  • Test domain bằng in-memory adapter
  • Linh hoạt hơn, đổi lại nhiều code hơn

// Port do DOMAIN định nghĩa (nằm trong domain package)
interface OrderRepository {
  Optional<Order> findById(OrderId id);
  void save(Order order);
}

// Application service chỉ biết port, không biết JPA/Hibernate
class PlaceOrderService {
  private final OrderRepository repo;     // abstraction, không phải JpaRepository
  PlaceOrderService(OrderRepository repo) { this.repo = repo; }
  void place(Order order) { repo.save(order); }
}

// Adapter (hạ tầng) hiện thực port — nơi DUY NHẤT chạm JPA
class JpaOrderRepository implements OrderRepository {
  private final EntityManager em;
  public Optional<Order> findById(OrderId id) { return Optional.ofNullable(em.find(Order.class, id.value())); }
  public void save(Order order) { em.persist(order); }
}
When

Domain logic phức tạp, nhiều loại I/O (HTTP, queue, batch), cần test nhanh không phụ thuộc DB, hoặc chuẩn bị tách service/microservice.

When NOT

CRUD/backoffice đơn giản — hexagonal thêm port/adapter/mapper chỉ tăng boilerplate. Không biến mọi repository thành interface nếu chưa từng có >1 implementation hoặc test double (YAGNI).

Pitfall / Interview trap

Hexagonal KHÔNG phải "chia 6 package". Nó là dependency rule: domain không được compile-time phụ thuộc hạ tầng. Nếu domain import jakarta.persistence.Entity hay javax.sql.DataSource là đã rò rỉ (leak). Cũng đừng nhầm Hexagonal = Onion = Clean: cùng dependency rule, nhưng Ports & Adapters chỉ có 2 tầng inside/outside và bắt buộc định nghĩa port.

D3 DDD-lite: Aggregate, Bounded Context + ADR & trade-off analysis

What

DDD-lite = dùng chọn lọc building block của Domain-Driven Design mà không áp full strategic DDD. Aggregate là một cụm entity/value object đảm bảo invariant trong một transaction; chỉ Aggregate Root được truy cập từ ngoài. Bounded Context là biên ngôn ngữ: cùng từ "Order" nhưng mang nghĩa khác ở từng context. ADR (Architecture Decision Record) là bản ghi ngắn một quyết định kiến trúc kèm bối cảnh và hệ quả.

Why

Aggregate định hình transaction boundary: boundary sai → lock quá rộng (giảm throughput) hoặc mất nhất quán. Bounded Context giải thích khi nào nên tách service. ADR + trade-off analysis giúp team không tranh luận lại mãi và giữ được lý do quyết định khi người cũ rời đi.

When

Domain nghiệp vụ phức tạp, nhiều team dùng ngôn ngữ khác nhau, invariant gắn chặt với dữ liệu (giỏ hàng, đơn hàng, ví tiền), hoặc cần cơ sở để chia service.

When NOT

CRUD đọc-ghi đơn giản → Anemic model + Active Record chấp nhận được (đừng ép DDD). Đừng làm aggregate to "cho đủ" — aggregate lớn tăng lock contention và load thừa. Bounded Context ≠ microservice: 1 service có thể chứa nhiều context, và 1 context có thể gồm nhiều service.

ADR — bản ghi quyết định

  • 1 file markdown / 1 quyết định
  • Trạng thái: proposed / accepted / superseded
  • Cấu trúc: Bối cảnh · Quyết định · Hệ quả
  • Lưu trong repo (docs/adr/) để review cùng code

Trade-off analysis

  • Nêu 2–3 phương án thay vì 1
  • Tiêu chí: latency, cost, complexity, team skill
  • Chọn + ghi rõ điều đánh đổi
  • Ghi điều kiện khiến quyết định nên xem lại
Pitfall / Interview trap

Anemic Domain Model: entity chỉ getter/setter, logic dồn vào service — với JPA đôi khi chấp nhận được, nhưng nếu invariant phức tạp thì logic ở ngoài dễ bị vi phạm. Ngược lại nhồi quá nhiều vào entity lớn cũng tạo God Object. Interviewer hay hỏi: "Vì sao OrderLine không nên có repository riêng?" — vì nó không phải aggregate root; truy cập trực tiếp sẽ phá vỡ invariant của Order.
