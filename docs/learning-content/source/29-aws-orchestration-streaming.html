Step Functions: điều phối workflow

AWS1 Step Functions: Standard vs Express khác nhau thế nào và có những state type nào?

What

State machine là một workflow định nghĩa bằng JSON (Amazon States Language); mỗi bước là một state. Có hai loại workflow:

  • Standard — chạy dài tới 1 năm, exactly-once execution, lịch sử đầy đủ từng bước (audit tốt), tối đa 2.000 execution khởi động/giây và 4.000 state transition/giây. Phù hợp quy trình nghiệp vụ dài (duyệt đơn, ETL, human approval).
  • Express — chỉ tối đa 5 phút, mô hình at-least-once; throughput rất cao (tới 100.000 execution/giây), rẻ hơn nhiều cho khối lượng lớn. Log đẩy sang CloudWatch Logs chứ không giữ history như Standard; không hỗ trợ .sync.

Các state type chính: Task (gọi một việc), Choice (rẽ nhánh điều kiện), Parallel (nhiều nhánh song song), Map (lặp qua mảng), Pass (truyền/biến đổi dữ liệu), Wait (chờ), Succeed, Fail.

How

Event khởi động workflow → engine chạy tuần tự qua các state theo Next/StartAt, mang theo JSON input và tích luỹ kết quả qua từng bước.

When

Chọn Standard khi cần chạy lâu, audit từng bước, hoặc cần .sync/waitForTaskToken. Chọn Express khi là luồng xử lý sự kiện khối lượng lớn, thời gian ngắn (ví dụ pipeline biến đổi mỗi event vài giây). Đừng chọn Standard cho luồng hàng nghìn event/giây vì chi phí và throughput.

Pitfall
Dễ nhầm Express không có lịch sử execution đầy đủ như Standard và không hỗ trợ các integration đồng bộ .sync. Nếu đề cần "chờ job ECS/Glue hoàn thành rồi mới đi tiếp" thì đó là Standard.

AWS2 Tình huống: quy trình duyệt chi phí cần người bấm duyệt — Retry/Catch và waitForTaskToken dùng thế nào?

What

Ứng dụng cần một bước chờ con người duyệt (có thể vài giờ), đồng thời phải chịu lỗi tạm thời khi gọi API. Step Functions cho hai cơ chế:

  • Retry — khai báo ErrorEquals, IntervalSeconds, MaxAttempts, BackoffRate, MaxDelaySeconds, JitterStrategy (full/exponential) để thử lại với backoff.
  • Catch — khi hết retry vẫn lỗi thì chuyển sang state khác (Next), ghi lỗi vào ResultPath.
  • TimeoutSeconds / HeartbeatSeconds — giới hạn tổng thời lượng task và nhịp tim; vượt sẽ ném States.Timeout / States.HeartbeatTimeout. Mã lỗi phổ biến: States.ALL, States.TaskFailed, States.Timeout.
  • waitForTaskToken — pattern callback: task phát ra một task token cho hệ thống ngoài (SQS/SNS/email), workflow tạm dừng cho tới khi bên ngoài gọi SendTaskSuccess/SendTaskFailure. Đây chính là mảnh ghép cho human approval.

When

Dùng waitForTaskToken khi cần chờ sự kiện ngoài không xác định thời điểm (duyệt thủ công, callback từ hệ thống bên thứ ba). Luôn đặt TimeoutSeconds để tránh treo vô hạn; dùng HeartbeatSeconds cho job dài để phát hiện worker "chết".

Pitfall
Dễ nhầm Retry và Catch gắn ở cấp state, không phải toàn workflow. Task token chỉ dùng được với Standard workflow, và phải có timeout — thiếu timeout là lỗi cấu hình kinh điển.

AWS3 Map, Parallel và Distributed Map khác nhau ra sao?

What

Ba state mở rộng song song trong Step Functions: Parallel (nhánh cố định chạy đồng thời rồi gộp), Map Inline (lặp mảng trong payload, tối đa ~40 concurrent) và Distributed Map (dataset lớn đọc từ S3, tới 10.000 concurrent).

  • Parallel — nhiều nhánh cố định chạy đồng thời, mỗi nhánh là một state machine con; chờ tất cả nhánh xong mới đi tiếp.
  • Map (Inline) — lặp qua một mảng trong payload, chạy song song với MaxConcurrency. Giới hạn ~40 concurrent cho Inline và payload vào/ra bị chặn bởi kích thước state (256 KB).
  • Distributed Map — xử lý dataset lớn (đọc object S3, hàng triệu item), concurrency tới 10.000, chạy như các child execution độc lập. Có ToleratedFailurePercentage/ToleratedFailureCount và ItemReader từ S3 (JSON/CSV/Parquet).

Chọn Parallel khi số nhánh cố định và khác nhau. Chọn Inline Map khi danh sách item nằm trong input và không quá lớn. Chọn Distributed Map khi phải quét hàng triệu object/file — đây là lựa chọn cho batch processing quy mô lớn.

Pitfall
Dễ nhầm Map không đảm bảo thứ tự hoàn thành theo thứ tự mảng. Distributed Map cần quyền s3:GetObject trên bucket chứa dataset. Vai trò của state machine phải có quyền gọi mọi service trong ItemProcessor.

AWS4 Tình huống: nối Lambda, DynamoDB, SNS mà không muốn tự code glue — tích hợp SDK service thế nào?

What

Step Functions có optimized service integrations — gọi thẳng API của service thay vì tự bọc Lambda. Ví dụ arn:aws:states:::lambda:invoke, arn:aws:states:::dynamodb:putItem, arn:aws:states:::sns:publish, arn:aws:states:::sqs:sendMessage. Có ba pattern tích hợp:

  • Request Response — gọi rồi nhận kết quả ngay.
  • Run a Job (.sync) — chờ job dài hoàn thành (ECS, Glue, Batch) — chỉ Standard.
  • Wait for Callback (.waitForTaskToken) — chờ token như card AWS2.
How

Mỗi bước Task gọi một service; kết quả trả về được đặt vào $.Payload/$.Record… và có thể cắt gọn bằng ResultSelector, bỏ qua bằng ResultPath: null.

Pitfall
Dễ nhầm IAM role của state machine phải được cấp quyền tương ứng (ví dụ dynamodb:PutItem). Nếu thiếu quyền, execution fail với States.TaskFailed — lỗi rất hay bị bỏ sót khi test bằng console.

Kinesis Data Streams

AWS5 Tình huống: 10.000 thiết bị gửi telemetry, cần đúng thứ tự theo từng thiết bị — thiết kế stream thế nào?

What

Kinesis Data Streams là một append-only log chia thành các shard. Mỗi shard là đơn vị song song: ghi vào 1 MB/s hoặc 1.000 record/s, đọc ra 2 MB/s hoặc 2.000 record/s. Partition key được băm (MD5) để chọn shard; thứ tự chỉ được đảm bảo trong cùng một shard. Retention mặc định 24 giờ, cấu hình được từ 24 giờ đến 365 ngày. Resharding = split (tăng shard) hoặc merge (giảm shard); chế độ on-demand tự co giãn.

How

Dùng deviceId làm partition key → mọi event của cùng thiết bị rơi vào cùng shard → consumer đọc tuần tự theo thiết bị. Nhiều shard để tăng throughput tổng.

10k devicespartition-key = deviceId
→hash → shard
Shard 1..N1 MB/s in · 2 MB/s out
→ordered read
Consumerđọc theo shard
Code 
aws kinesis put-record \
  --stream-name telemetry \
  --partition-key device-1234 \
  --data '{"deviceId":"device-1234","temp":42.5}' \
  --cli-binary-format raw-in-base64-out

# tăng số shard khi lưu lượng vượt ngưỡng (resharding)
aws kinesis update-shard-count \
  --stream-name telemetry \
  --target-shard-count 8 \
  --scaling-type UNIFORM_SCALING
When

Chọn Kinesis Data Streams khi cần nhiều consumer đọc cùng dữ liệu, replay theo vị trí, giữ thứ tự theo key, hoặc lưu trữ dạng log có thời hạn dài (tới 365 ngày).

Pitfall
Dễ nhầm Partition key lệch (hot shard) gây ProvisionedThroughputExceededException. Dùng PutRecords để gửi lô (tối đa 500 record/5 MB) và có cơ chế retry cho record lỗi. Record đơn tối đa 1 MB.

AWS6 Tình huống: nhiều ứng dụng cùng đọc một stream bị chậm — KCL, enhanced fan-out và Lambda giải quyết thế nào?

What

Với shared throughput, băng thông đọc 2 MB/s của mỗi shard bị chia đều cho các consumer (giới hạn ~5 lần đọc/shard). Ba cách mở rộng:

  • Enhanced fan-out (EFO) — mỗi consumer được cấp riêng 2 MB/s per shard với độ trễ ~70 ms, không dùng chung băng thông; hỗ trợ tới 20 consumer/stream (nhiều hơn nếu bật On-demand Advantage).
  • KCL (Kinesis Client Library) — thư viện quản lý lease shard, checkpoint (thường vào DynamoDB), cân bằng tải giữa các worker.
  • Lambda event source mapping — Lambda tự đọc stream: BatchSize, ParallelizationFactor (1–10), tumbling window, retry + On-Failure destination.
How
Shard2 MB/s shared
→EFO: 2 MB/s riêng/consumer
Lambda consumerParallelizationFactor
→checkpoint
DynamoDB leaseKCL checkpoint table
Code 
# đăng ký consumer dùng enhanced fan-out
aws kinesis register-stream-consumer \
  --stream-arn arn:aws:kinesis:ap-southeast-1:123456789012:stream/telemetry \
  --consumer-name analytics-efo

# Lambda đọc stream, xử lý song song trong mỗi shard
aws lambda create-event-source-mapping \
  --function-name process-stream \
  --event-source-arn arn:aws:kinesis:ap-southeast-1:123456789012:stream/telemetry \
  --batch-size 100 --parallelization-factor 4 \
  --starting-position LATEST
When

Bật EFO khi có nhiều consumer đọc cùng stream và cần độ trễ thấp. Dùng KCL khi chạy consumer trên EC2/ECS và cần tự quản lý checkpoint. Dùng Lambda ESM khi muốn serverless, ít vận hành.

Pitfall
Dễ nhầm Lambda scale theo số shard × ParallelizationFactor. Một record lỗi có thể chặn cả shard tới khi cạn retry — cấu hình MaximumRetryAttempts + On-Failure destination và theo dõi metric IteratorAge để phát hiện tụt hậu.

Firehose, MSK & chọn service

AWS7 Kinesis Data Firehose: buffer, transform và các sink hoạt động thế nào?

What

Firehose là dịch vụ nạp dữ liệu streaming tới storage/analytics theo kiểu gần thời gian thực. Nó không phải nơi lưu trữ và không replay được (khác Kinesis Data Streams). Dữ liệu được gom theo buffer:

  • Buffer size 1–128 MB (mặc định 5 MB) và buffer interval 60–900 giây (mặc định 300 giây) — điều kiện nào đến trước thì flush trước.
  • Transform bằng Lambda (payload tối đa 6 MB, timeout tối đa 5 phút) để lọc/biến đổi record.
  • Sink: S3, Redshift (qua S3), OpenSearch, Splunk, HTTP endpoint, third-party. Có thể chuyển đổi định dạng sang Parquet/ORC và dynamic partitioning.

When

Pitfall
Dễ nhầm Firehose không replay và ghi vào S3 theo buffer chứ không tức thời. Khi transform thất bại, record lỗi có thể được đẩy sang bucket S3 backup — nên bật để không mất dữ liệu.

AWS8 Kinesis Data Streams vs SQS vs MSK — chọn cái nào?

What

Ba dịch vụ đều "chở" dữ liệu nhưng khác bản chất: SQS là queue (message bị xoá sau khi xử lý xong), Kinesis Data Streams là log (nhiều consumer đọc, replay theo vị trí, giữ theo thời hạn), MSK là Apache Kafka do AWS quản lý (hệ sinh thái Kafka, partition/topic, giữ dữ liệu dài).

When

Đề nói "decouple, retry, DLQ, mỗi message xử lý một lần" → SQS. Đề nói "aggregate nhiều consumer đọc cùng dữ liệu, replay, analytics real-time" → Kinesis Data Streams. Đề nói "đã dùng Kafka, cần hệ sinh thái Kafka/Connect/Flink, giữ dữ liệu lâu, di trú từ on-prem" → MSK.

Pitfall
Dễ nhầm SQS xoá message sau khi xử lý nên không có khái niệm replay; Kinesis giữ dữ liệu và cho phép nhiều consumer, nhưng một shard bị giới hạn 1 MB/s ghi. Đừng chọn Kinesis chỉ vì "cần throughput cao" nếu không cần replay hay nhiều consumer.

AWS9 Tình huống: clickstream 5 triệu event/phút cần real-time + lưu S3 — và "exactly-once" thật ra đảm bảo tới đâu?

What

Bài toán kinh điển: thu lượng lớn event, vừa phân tích gần thời gian thực vừa lưu trữ dài hạn. Kiến trúc thường dùng: Kinesis Data Streams (on-demand) làm xương sống → nhiều consumer (Lambda/EFO) cho analytics → Firehose đổ vào S3. Về tính đúng đắn: Kinesis là at-least-once, nghĩa là record có thể bị giao lại; "exactly-once" thực sự chỉ tồn tại trong phạm vi hẹp.

How
Clickstream5M events/phút
→partition key = sessionId
Data Streamson-demand, EFO
→fan-out
Analyticsidempotent sink
→buffer
Firehose→ S3 (Parquet)
Code 
# gửi lô record (tối đa 500 record / 5 MB mỗi lần gọi)
aws kinesis put-records \
  --stream-name clickstream \
  --records file://records.json

# consumer idempotent: chỉ cộng 1 lần cho mỗi event đã xử lý
aws dynamodb update-item --table-name sessions \
  --key '{"sid":{"S":"s-1"}}' \
  --update-expression "SET hits = hits + :one" \
  --condition-expression "attribute_not_exists(processed)" \
  --expression-attribute-values '{":one":{"N":"1"}}'
When

Thiết kế chuẩn: partition key phân tán đều (tránh hot shard), bật EFO khi nhiều consumer, dùng Firehose để nén/chuyển Parquet trước khi vào S3, và luôn làm idempotent ở tầng ghi cuối.

Pitfall
Dễ nhầm "Exactly-once" end-to-end gần như không có sẵn: SQS FIFO chỉ dedup trong 5 phút, Step Functions Standard cho exactly-once ở mức orchestration, còn Kinesis/Lambda là at-least-once. Cách duy nhất chắc chắn không xử lý trùng là ghi kết quả bằng conditional write idempotent. Theo dõi IteratorAge và WriteProvisionedThroughputExceeded để phát hiện nghẽn.
