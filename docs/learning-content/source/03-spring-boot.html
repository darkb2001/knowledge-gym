Q1 Giải thích Dependency Injection (DI) và Inversion of Control (IoC)?

What

IoC (Inversion of Control): Đảo ngược quyền kiểm soát — thay vì class tự new dependency, Spring Container (ApplicationContext) quản lý vòng đời object và wiring. DI (Dependency Injection): Cơ chế cụ thể của IoC — container inject dependency vào object qua constructor, setter, hoặc field annotation.

Why

Loose coupling qua interface — swap implementation (mock, stub, prod) không sửa consumer. Testability: unit test inject mock thay vì cần DB thật. Single Responsibility: class chỉ lo business logic, không lo khởi tạo dependency graph. Spring quản lý singleton scope, lazy init, lifecycle hooks tập trung.

❌ Không DI (new thủ công)

  • Tight coupling — phụ thuộc concrete class
  • Khó test — không mock được dependency
  • Thay implementation phải sửa mọi nơi new
  • Quản lý lifecycle thủ công (connection pool, cleanup)

✅ Có DI (Spring Container)

  • Loose coupling qua interface
  • Unit test inject mock dễ dàng
  • Swap bean qua config, @Profile, @Primary
  • Container quản lý scope, lifecycle, AOP proxy
How

Container bootstrap: component-scan (@SpringBootApplication) → đọc @Configuration + @Bean methods → đăng ký BeanDefinition → resolve dependency graph (topological sort, phát hiện circular dep) → instantiate từng bean → inject dependency → chạy lifecycle hooks → bean ready trong singleton pool.

When

Mọi Spring Boot app enterprise — service inject repository, controller inject service. Dùng interface cho dependency cross-cutting (payment, notification, storage). @Profile để inject bean khác nhau theo môi trường (dev mock vs prod real).

When NOT

Đừng inject mọi thứ — value object, DTO, utility pure static không cần bean. POJO domain entity không nên là Spring bean (tránh coupling domain với framework). Tránh Service Locator anti-pattern (context.getBean()) — dùng constructor injection thay thế.

Nói trong 60 giây
  • IoC: container kiểm soát object lifecycle, không tự new.
  • DI: cách inject — constructor (khuyến nghị), setter, field.
  • Lợi ích: loose coupling, testable, swap implementation dễ.
  • Phỏng vấn: IoC là nguyên tắc, DI là implementation cụ thể.

Q2 Constructor Injection vs Field Injection vs Setter Injection?

What

Spring hỗ trợ 3 cách inject dependency: Constructor (param constructor), Setter (method setXxx()), Field (@Autowired trực tiếp trên field). Cả ba đều do container thực hiện sau khi instantiate bean — khác nhau ở thời điểm và cách gán dependency.

Why

Constructor injection được Spring team khuyến nghị từ 4.3+: immutable (final fields), required dependency bắt buộc tại creation time, dễ unit test không cần reflection. Field injection ngắn code nhưng ẩn dependency, vi phạm encapsulation, khó mock trong test. Setter phù hợp optional dependency có thể thay đổi runtime.

LoạiƯu điểmNhược điểmKhi dùng
ConstructorImmutable, testable, deps rõ ràng, circular dep fail sớmNhiều param → constructor dàiDefault cho mọi required dependency
SetterOptional dep, re-configure runtimeObject có thể half-initializedOptional plugin, legacy integration
FieldCode ngắn nhấtAnti-pattern: khó test, ẩn dep, cần reflectionTránh — chỉ legacy code
How

Constructor: Spring 4.3+ auto-detect single constructor — không cần @Autowired. Nhiều constructor → annotate constructor cần dùng. Lombok @RequiredArgsConstructor generate constructor cho final fields. Setter: @Autowired trên setter method. Field: @Autowired trên field — container inject qua reflection (package-private OK).

@Service
public class OrderService {
  private final OrderRepository repo;
  private final PaymentClient payment;

  // ✅ Constructor — 1 constructor → @Autowired optional
  public OrderService(OrderRepository repo, PaymentClient payment) {
    this.repo = repo;
    this.payment = payment;
  }
}

// Lombok equivalent:
@Service @RequiredArgsConstructor
public class OrderService {
  private final OrderRepository repo;
  private final PaymentClient payment;
}

// ❌ Field injection — tránh
@Autowired private OrderRepository repo;
When

Constructor cho tất cả required dependency (repository, client, config). Setter cho optional dependency (cache provider có thể null). @RequiredArgsConstructor + final fields khi team dùng Lombok — giữ immutability.

When NOT

Đừng field inject trong code mới — SonarQube rule S3305. Constructor >6 params = smell — tách bean hoặc facade. Đừng setter inject required dependency — object có thể dùng trước khi setter gọi. Circular dependency qua constructor → Spring fail startup (đúng — buộc refactor).

Use case
OrderService cần OrderRepository + PaymentClient (required) → constructor injection. AuditExporter optional, chỉ prod bật → setter injection hoặc Optional<AuditExporter> trong constructor. Unit test: new OrderService(mockRepo, mockPayment) không cần @SpringBootTest.
Pitfall
Field injection khiến dependency invisible trong constructor signature. Test phải dùng ReflectionTestUtils.setField() thay vì constructor. Circular dep: constructor A→B→A fail ngay; field/setter có thể "pass" qua early reference — che design flaw.
Nói trong 60 giây
  • 3 loại: constructor (best), setter (optional), field (anti-pattern).
  • Constructor: final fields, testable, Spring khuyến nghị từ 4.3+.
  • Lombok @RequiredArgsConstructor cho final fields — ngắn gọn.
  • Phỏng vấn trap: field injection "tiện" nhưng SonarQube cấm.

Q3 Vòng đời Spring Bean (Bean Lifecycle)?

What

Bean Lifecycle là chuỗi phase từ khi Spring Container nhận bean definition đến khi bean bị destroy. Mỗi bean đi qua: instantiate → populate (DI) → aware callbacks → BeanPostProcessor → init → ready → destroy. Hiểu lifecycle giúp biết khi nào chạy warmup, khi nào AOP proxy được tạo.

Why

Lifecycle hooks cho phép init resource (connection, cache warmup) sau khi DI hoàn tất nhưng trước khi bean serve request. BeanPostProcessor là extension point mạnh — @Transactional, @Cacheable, @Async đều tạo proxy tại đây. @PreDestroy đảm bảo graceful shutdown (flush buffer, close connection).

How

Chi tiết từng phase:

  1. Instantiation: Container gọi constructor (hoặc @Bean factory method). Object tồn tại nhưng dependency chưa inject — đừng dùng dependency trong constructor logic.
  2. Populate (DI): Inject constructor args, setter, @Value, @Autowired fields. Circular dependency constructor-based → fail startup (design smell).
  3. Aware interfaces: BeanNameAware.setBeanName(), BeanFactoryAware, ApplicationContextAware — bean biết context metadata.
  4. BeanPostProcessor before init: Custom preprocessing trước init hooks (@PostConstruct).
  5. Init: @PostConstruct (JSR-250, khuyến nghị), InitializingBean.afterPropertiesSet(), hoặc custom init-method XML — warmup cache, validate config sau khi DI xong.
  6. BeanPostProcessor after init: Quan trọng phỏng vấn — Spring tạo AOP proxy (CGLIB/JDK) cho @Transactional, @Cacheable, @Async. Caller inject proxy, không phải raw bean.
  7. Ready: Bean trong singleton pool, phục vụ request. Prototype scope: mỗi getBean() tạo instance mới.
  8. Destroy: Context shutdown (K8s SIGTERM) → @PreDestroy, DisposableBean.destroy() — close connection, flush queue. Prototype: destroy không tự động.
@Component
public class CacheWarmup {
  private final ProductRepository repo;

  public CacheWarmup(ProductRepository repo) { this.repo = repo; }

  @PostConstruct
  public void init() {
    loadTopProductsIntoCache(); // repo đã inject — an toàn gọi DB
  }

  @PreDestroy
  public void cleanup() { flushPendingWrites(); }
}

// Custom BeanPostProcessor — wrap bean trước khi return
public Object postProcessAfterInitialization(Object bean, String name) {
  return createProxyIfNeeded(bean); // AOP, @Transactional proxy
}
When

@PostConstruct cho startup logic cần dependency đã inject (load config từ DB, warm cache). @PreDestroy cho cleanup trước shutdown (K8s SIGTERM). BeanPostProcessor khi cần custom proxy/wrapping toàn bộ bean type.

When NOT

Đừng heavy I/O trong constructor — dependency chưa inject xong. Đừng @PostConstruct cho logic nên lazy (first request). Tránh InitializingBean interface — couple với Spring API; dùng @PostConstruct. Prototype scope bean: @PreDestroy không gọi tự động — phải manage manually.

Use case
WMS startup: CacheWarmup @PostConstruct load top 1000 SKU vào Redis trước traffic. MqttClient @PreDestroy disconnect broker khi pod terminate. @Transactional trên OrderService → Spring tạo CGLIB proxy ở BeanPostProcessor — caller luôn qua proxy.
Pitfall
Gọi dependency trong constructor → NullPointerException. @PostConstruct throw exception → bean fail, app không start. Nhầm thứ tự: BeanPostProcessor chạy trước @PostConstruct (before) và sau (after — proxy wrap). Prototype bean không có full destroy lifecycle.
Nói trong 60 giây
  • 8 bước: instantiate → DI → Aware → BPP before → @PostConstruct → BPP after (proxy) → ready → destroy.
  • @PostConstruct: init sau DI — warmup cache, validate config.
  • AOP proxy (@Transactional) tạo ở postProcessAfterInitialization — caller qua proxy.
  • Trap: logic trong constructor — dependency chưa sẵn sàng; prototype không auto @PreDestroy.

Q4 Phân biệt @Component, @Service, @Repository?

What

@Component, @Service, @Repository đều là stereotype annotations — meta-annotated với @Component. Spring component-scan đăng ký cả ba như bean bình thường. Khác nhau về ngữ nghĩa layer (DDD/clean architecture) và một số behavior đặc biệt của @Repository.

Why

Phân layer giúp team đọc code nhanh — biết class thuộc persistence hay business logic. @Repository kích hoạt PersistenceExceptionTranslationPostProcessor — translate SQLException/vendor-specific exception → Spring DataAccessException hierarchy, giúp catch exception portable giữa các DB.

AnnotationLayerBehavior đặc biệtVí dụ
@ComponentGenericKhông thêm behaviorEmailValidator, IdGenerator, Mapper helper
@ServiceBusiness / Use caseSemantic only — @Transactional thường ở đâyOrderService, InventoryService
@RepositoryPersistenceException translation SQLException → DataAccessExceptionOrderRepository, JpaOrderRepository
@ControllerPresentationView resolution (MVC)AdminDashboardController
@RestControllerREST API= @Controller + @ResponseBodyOrderApiController
How

@SpringBootApplication kích hoạt component scan package gốc trở xung. Class có stereotype → BeanDefinition registered → instantiate khi context refresh. @Repository trigger exception translation AOP advisor trên persistence layer.

@Repository
public interface OrderRepository extends JpaRepository<Order, Long> {}

@Service
public class OrderService {
  private final OrderRepository repo;
  @Transactional
  public Order placeOrder(Order order) { return repo.save(order); }
}

@Component
public class SkuValidator {
  public boolean isValid(String sku) { return sku.matches("^[A-Z0-9]{6,12}$"); }
}
When

@Repository cho mọi data access (JPA repo, JDBC template wrapper). @Service cho business logic, transaction boundary. @Component cho utility/helper không thuộc layer cụ thể. Package-by-feature: mỗi feature folder có controller/service/repository riêng.

When NOT

Đừng @Service cho pure utility không có business logic — dùng @Component. Đừng @Repository cho HTTP client — đó là infrastructure adapter, không phải persistence. Entity class (@Entity) không annotate @Component — JPA quản lý lifecycle riêng. Không cần phân biệt quá cứng nếu team nhỏ — nhưng interview expect biết semantic.

Use case
WMS module order/: OrderController (REST) → OrderService (@Transactional business rules) → OrderRepository (JPA + exception translation). SkuValidator (@Component) dùng chung bởi service và import job — không thuộc layer cụ thể.
Pitfall
Nghĩ @Service/@Repository khác behavior ngoài exception translation — thực tế gần như giống @Component. Business logic trong @Repository (complex query + calculation) — vi phạm SRP. @Component scan miss nếu class ngoài base package — cần @ComponentScan explicit.
Nói trong 60 giây
  • Cả ba đều là @Component stereotype — scan và register bean.
  • @Repository: translate SQLException → DataAccessException.
  • @Service: business layer; @Component: generic helper.
  • Thêm @Controller/@RestController cho presentation layer.

Q5 Phân biệt @Controller vs @RestController?

What

@Controller đánh dấu presentation layer — xử lý HTTP request, trả về view name hoặc redirect. @RestController = @Controller + @ResponseBody trên class level — mọi handler method auto serialize return value thành JSON/XML qua HttpMessageConverter (Jackson).

Why

Tách SSR web (render HTML template) vs REST API (trả JSON). @RestController giảm boilerplate — không cần @ResponseBody từng method. Content negotiation: Accept header + registered converters quyết định format response. Separation giúp API versioning và frontend decoupling (SPA/mobile).

@Controller

  • Return view name → ViewResolver render HTML
  • JSON cần @ResponseBody từng method
  • SSR: Thymeleaf, JSP, FreeMarker
  • Form submit, redirect, Model attribute

@RestController

  • Mọi method auto @ResponseBody
  • Jackson serialize object → JSON
  • REST API cho SPA, mobile, microservice
  • Return DTO/ResponseEntity trực tiếp
Aspect@Controller@RestController
Return typeString (view name), ModelAndViewDTO, List, ResponseEntity<T>

How

DispatcherServlet route request → HandlerMapping tìm @RequestMapping/@GetMapping → invoke method → nếu @ResponseBody: HttpMessageConverter write body; nếu @Controller thuần: ViewResolver resolve template. @RestController meta-annotation apply @ResponseBody lên class.

// REST API — @RestController
@RestController

public class OrderApiController {
  @GetMapping("/{id}")
  public OrderDto get(@PathVariable Long id) {
    return orderService.findById(id); // auto JSON
  }
}

// SSR — @Controller
@Controller
public class AdminController {
  @GetMapping("/dashboard")
  public String dashboard(Model model) {
    model.addAttribute("stats", statsService.today());
    return "admin/dashboard"; // → templates/admin/dashboard.html
  }
}
When

@RestController cho backend API phục vụ React/Vue/mobile/microservice. @Controller cho admin panel SSR, legacy JSP/Thymeleaf. ResponseEntity khi cần custom status code/header. @RestControllerAdvice cho global JSON error response.

When NOT

Đừng business logic trong controller — chỉ validate input, map DTO, gọi service. Đừng @RestController nếu app pure SSR không có API. Tránh expose JPA entity trực tiếp — lazy load exception + over-posting. Đừng mix SSR và API trong cùng controller class — tách rõ.

Use case
WMS: OrderApiController (@RestController) serve JSON cho handheld scanner app. AdminDashboardController (@Controller + Thymeleaf) render báo cáo HTML cho warehouse manager. Cùng OrderService backend — hai presentation adapter khác nhau.
Pitfall
Return entity từ @RestController → LazyInitializationException khi Jackson serialize association ngoài session. Thiếu @Valid trên @RequestBody → invalid input vào service. @Controller return object không phải String → Spring coi là view name → 404 confusing.
Nói trong 60 giây
  • @Controller: MVC, return view name, SSR HTML.
  • @RestController = @Controller + @ResponseBody — auto JSON.
  • Controller mỏng: validate, map DTO, delegate service.
  • Trap: return entity → lazy load leak khi serialize JSON.

Q6 Circular Dependency — Spring xử lý thế nào?

What

Circular Dependency xảy ra khi bean A cần B, B cần A (hoặc chuỗi A→B→C→A). Spring không thể instantiate cả hai nếu dùng constructor injection — không có bean nào hoàn chỉnh để inject trước. Spring Boot 2.6+ mặc định spring.main.allow-circular-references=false — fail fast thay vì workaround im lặng.

Why

Circular dependency là design smell — hai class phụ thuộc lẫn nhau vi phạm SRP và khó test. Spring 3-level singleton cache cho phép field/setter injection "pass" bằng early reference — nhưng che giấu vấn đề thiết kế. Fail fast buộc developer refactor thay vì patch.

Cache levelChứa gìVai trò
singletonObjectsBean hoàn chỉnh, fully initializedPool bean ready sử dụng
earlySingletonObjectsEarly reference (chưa init xong)Cho phép inject bean đang khởi tạo
singletonFactoriesObjectFactory tạo early refCallback khi cần expose sớm
How

Constructor circular: Spring detect cycle trong dependency graph → throw BeanCurrentlyInCreationException. Field/setter: tạo A (chưa inject) → đăng early ref vào factory → tạo B → inject early A vào B → hoàn thiện A → hoàn thiện B. @Lazy trên một dependency: inject proxy, resolve thật khi first call.

// ❌ Constructor circular — FAIL startup
@Service public class ServiceA {
  public ServiceA(ServiceB b) {} // cần B hoàn chỉnh
}
@Service public class ServiceB {
  public ServiceB(ServiceA a) {} // cần A hoàn chỉnh → deadlock
}

// ✅ Refactor: tách logic chung
@Service public class SharedHelper { ... }
@Service public class ServiceA {
  public ServiceA(SharedHelper helper) {}
}
@Service public class ServiceB {
  public ServiceB(SharedHelper helper) {}
}

// Workaround tạm: @Lazy
public ServiceA(@Lazy ServiceB b) {}
When

Gặp circular dep → refactor trước tiên. @Lazy khi không thể refactor ngay (legacy). Event-driven decouple: A publish event, B listen — không direct dependency. ApplicationContext.getBean() self-injection cho @Transactional self-call (khác circular dep nhưng related).

When NOT

Đừng bật allow-circular-references=true để "fix" — che design flaw. Đừng dùng field injection workaround trong code mới. @Lazy everywhere = lazy loading surprise + khó debug. Prototype scope circular phức tạp hơn singleton — tránh.

Use case
OrderService cần NotificationService, NotificationService cần OrderService (query order detail) → refactor: tách OrderQueryService bean thứ 3, cả hai inject query service. Hoặc NotificationService listen OrderPlacedEvent thay vì inject OrderService.
Pitfall
Field injection "fix" circular dep nhưng object có thể half-init khi method gọi. @Lazy proxy → first call mới resolve — unexpected NPE nếu B chưa ready. 3+ bean cycle (A→B→C→A) khó detect hơn — graph tool hoặc startup log. Spring Boot 2.6+ fail nếu chưa migrate — check release notes.
Nói trong 60 giây
  • A→B→A: constructor injection fail; field/setter có thể early ref.
  • 3-level cache: singletonObjects, earlySingletonObjects, factories.
  • Boot 2.6+ cấm circular ref mặc định — fail fast.
  • Fix đúng: refactor, tách bean 3, event-driven — không patch @Lazy.

Q7 Spring Boot Auto-configuration hoạt động thế nào?

What

Auto-configuration là cơ chế Spring Boot tự động cấu hình bean dựa trên classpath và properties — không cần viết XML/Java config thủ công. @SpringBootApplication meta-include @EnableAutoConfiguration, load danh sách auto-config classes và filter bằng @Conditional annotations.

Why

Convention over configuration — thêm starter dependency (spring-boot-starter-data-jpa) → DataSource, EntityManagerFactory, TransactionManager auto wired. Giảm boilerplate từ hàng trăm dòng XML xuống vài dòng properties. @ConditionalOnMissingBean cho phép override — user define bean riêng thì auto-config skip.

When

When NOT

Đừng exclude auto-config tùy tiện — hiểu trước bean nào bị ảnh hưởng. Đừng duplicate @Bean mà không biết auto-config đã có — conflict hoặc unexpected override. Tránh @EnableAutoConfiguration(exclude = ...) quá rộng trong microservice nhỏ — mất lợi ích convention.

Use case
Thêm spring-boot-starter-data-redis → RedisConnectionFactory, RedisTemplate auto config nếu spring.data.redis.host set. Multi-datasource: define 2 @Bean DataSource → auto-config skip, full control. Actuator auto-config expose /health khi starter-actuator on classpath.
Pitfall

Nói trong 60 giây
  • @EnableAutoConfiguration load classes từ AutoConfiguration.imports.
  • @ConditionalOnClass/MissingBean/Property filter config.
  • Starter = dependency + auto-config — convention over config.
  • Override: define @Bean riêng → MissingBean skip default.

Q9 AOP — Aspect, Join Point, Advice, Pointcut?

What

AOP (Aspect-Oriented Programming) tách cross-cutting concern (logging, security, transaction) khỏi business code. Spring AOP dùng runtime proxy (JDK dynamic proxy hoặc CGLIB). Aspect = module chứa advice; Join Point = điểm có thể inject (method execution); Pointcut = expression chọn join points; Advice = code chạy tại join point.

Why

DRY: logging mọi service method không copy-paste. Separation of concerns: business code không biết transaction/logging wrapper. @Transactional, @Cacheable, @Async đều implement qua AOP proxy — hiểu AOP = hiểu tại sao self-invocation fail.

Khái niệmÝ nghĩaVí dụ
AspectModule cross-cutting logic@Aspect class PerformanceAspect
Join PointĐiểm execution có thể adviseMethod call OrderService.placeOrder()
PointcutExpression chọn join pointsexecution(* com.wms..*Service.*(..))
AdviceCode tại join point@Before, @After, @Around, @AfterThrowing
WeavingGắn aspect vào targetSpring: runtime proxy (not compile-time)
How

@EnableAspectJAutoProxy (auto trong Boot) → BeanPostProcessor wrap bean matching pointcut → proxy delegate tới target. @Around: control trước/sau, gọi pjp.proceed() cho target method. Pointcut expression: @annotation(Timed), execution(* *(..)), within(@Service *).

@Aspect @Component
public class PerformanceAspect {
  @Around("@annotation(Timed)")
  public Object measure(ProceedingJoinPoint pjp) throws Throwable {
    long start = System.nanoTime();
    try { return pjp.proceed(); }
    finally {
      log.info("{} took {}ms", pjp.getSignature(), (System.nanoTime()-start)/1e6);
    }
  }

  @AfterThrowing(pointcut = "within(@Service *)", throwing = "ex")
  public void logServiceError(Exception ex) { alertService.notify(ex); }
}

// @Transactional cũng là AOP — TransactionInterceptor @Around service method
When

Logging/audit cross-cutting. Performance monitoring (@Timed). Security @PreAuthorize. Custom retry/circuit breaker aspect. Hiểu AOP để debug @Transactional/@Cacheable/@Async không hoạt động.

When NOT

Đừng AOP cho core business logic — khó đọc, debug stack phức tạp. Spring AOP chỉ method execution trên Spring bean — không advise constructor, field access, private method (non-proxy). Tránh pointcut quá rộng (execution(* *(..))) — performance overhead.

Use case
@Transactional trên OrderService.placeOrder(): proxy begin TX → method → commit. PerformanceAspect @Around @Timed methods — log slow query >500ms. AuditAspect @AfterReturning trên @Service — ghi who/when/what không sửa business code.
Pitfall
Self-invocation this.txMethod() bypass proxy — TX không chạy. Final class/method → CGLIB không extend được. Pointcut typo → aspect im lặng không match. @Order aspect conflicts — thứ tự advice matters (@Order annotation).
Nói trong 60 giây
  • Aspect = cross-cutting module; Pointcut chọn method; Advice = code chạy.
  • Spring AOP = runtime proxy, chỉ public method trên bean.
  • @Transactional/@Cacheable/@Async đều là AOP.
  • Trap: this.method() bypass proxy — self-invocation fail.

Q10 Phân biệt @Configuration vs @Component?

What

@Configuration đánh dấu class Java-based config — chứa @Bean methods định nghĩa bean manually. @Component là generic stereotype — class được scan và instantiate trực tiếp. Khác biệt quan trọng: @Configuration full mode CGLIB-enhance @Bean methods — gọi lẫn nhau vẫn trả singleton.

Why

@Configuration cho third-party class không annotate được (@Bean RestTemplate, DataSource). Full mode đảm bảo orderClient() gọi restTemplate() trong cùng class → cùng singleton instance. @Component class gọi method nội bộ = plain Java call → mỗi lần object mới nếu @Bean trên @Component (anti-pattern).

@Configuration@Component
Mục đíchJava config, define @BeanGeneric bean — business/utility class
@Bean method inter-callCGLIB proxy → singleton sharedPlain call → new instance mỗi lần
proxyBeanMethodstrue (full, default) / false (lite)N/A — không enhance
Typical useDataSource, RestTemplate, SecurityFilterChainService, Validator, Helper
How

@Configuration full mode: Spring tạo CGLIB subclass — mỗi @Bean method intercepted, lần đầu tạo bean và cache, lần sau return cached. Lite mode (proxyBeanMethods=false): không CGLIB — @Bean methods độc lập, inject qua param thay vì gọi method nội bộ. Boot 2.2+ default lite cho @SpringBootApplication internal config.

@Configuration // proxyBeanMethods=true — full mode
public class AppConfig {
  @Bean
  public RestTemplate restTemplate() { return new RestTemplate(); }

  @Bean
  public OrderClient orderClient() {
    return new OrderClient(restTemplate()); // ✅ qua proxy → cùng singleton
  }
}

@Configuration(proxyBeanMethods = false) // lite — @Bean inject param thay vì gọi method
public class LiteConfig {
  @Bean public OrderClient orderClient(RestTemplate rt) {
    return new OrderClient(rt); // inject — không gọi restTemplate()
  }
}
When

@Configuration cho mọi @Bean definition (third-party, multi-bean setup). Full mode khi @Bean methods gọi lẫn nhau. Lite mode (proxyBeanMethods=false) khi @Bean độc lập — startup nhanh hơn, ít CGLIB. @Component cho class logic, không define @Bean (trừ anti-pattern).

When NOT

Đừng @Bean trên @Component class — mất singleton guarantee khi inter-call. Đừng @Configuration cho business service — không phải config class. Lite mode + gọi @Bean method nội bộ → duplicate bean instances bug.

Use case
SecurityConfig @Configuration define SecurityFilterChain + AuthenticationManager beans. RedisConfig @Bean RedisConnectionFactory + RedisTemplate — OrderClient inject RestTemplate qua constructor param (lite mode safe).
Pitfall
@Component + @Bean method gọi nhau → 2 RestTemplate instances — subtle bug. Full mode CGLIB yêu cầu class non-final. Nhầm @Configuration với @ConfigurationProperties — khác hoàn toàn (properties binding).
Nói trong 60 giây
  • @Configuration: Java config, @Bean methods, CGLIB proxy full mode.
  • @Component: generic bean — không enhance @Bean inter-call.
  • Full mode: gọi @Bean method trong class → cùng singleton.
  • Lite (proxyBeanMethods=false): inject param, startup nhanh hơn.

Q11 @Bean vs @Autowired — @Qualifier vs @Primary?

What

@Bean: đăng ký object vào container — bạn tạo và cấu hình instance (thường trong @Configuration). @Autowired: Spring inject bean có sẵn vào constructor/field/setter. Khi nhiều bean cùng type: @Primary chọn default, @Qualifier("name") chọn cụ thể.

Why

@Bean cho class bạn không control (RestTemplate, ObjectMapper custom config). @Autowired cho dependency consumption. @Primary tránh ambiguity khi có default impl. @Qualifier khi cần inject non-default bean cùng lúc (Stripe + PayPal gateway).

AnnotationVai tròDùng ở đâu
@BeanDefine/produce bean@Configuration method
@AutowiredConsume/inject beanConstructor, field, setter
@PrimaryDefault khi ambiguous@Bean hoặc @Component class
@Qualifier("x")Chọn bean by nameInject point hoặc @Bean method
How

@Bean method return object → Spring register với bean name = method name. @Autowired resolve by type; nhiều match → @Primary wins, hoặc bắt buộc @Qualifier. @Qualifier on @Bean method set explicit name. Constructor injection: Spring 4.3+ single constructor không cần @Autowired.

@Configuration
public class PaymentConfig {
  @Bean @Primary
  public PaymentGateway stripeGateway() {
    return new StripeGateway(apiKey);
  }

  @Bean @Qualifier("paypal")
  public PaymentGateway paypalGateway() {
    return new PaypalGateway(clientId);
  }
}

@Service
public class CheckoutService {
  private final PaymentGateway defaultGateway;  // @Primary → Stripe
  private final PaymentGateway paypal;

  public CheckoutService(
      PaymentGateway defaultGateway,
      @Qualifier("paypal") PaymentGateway paypal) {
    this.defaultGateway = defaultGateway;
    this.paypal = paypal;
  }
}
When

@Bean: third-party lib, custom ObjectMapper, DataSource, RestTemplate builder. @Primary: default impl trong multi-impl setup. @Qualifier: inject specific bean by name — A/B payment, primary/secondary cache.

When NOT

Đừng @Bean cho class đã @Component scan được — duplicate bean. Nhiều @Primary cùng type → startup error. @Qualifier typo → NoUniqueBeanDefinitionException hoặc NoSuchBeanDefinitionException. Tránh @Autowired field — dùng constructor.

Use case
PaymentConfig: @Primary StripeGateway cho checkout mặc định, @Qualifier("paypal") cho market EU. NotificationService inject @Primary EmailSender; AdminService inject @Qualifier("smtpBulk") cho campaign email.
Pitfall
2+ bean cùng type không @Primary không @Qualifier → NoUniqueBeanDefinitionException. @Bean method name = bean name — rename method = break @Qualifier reference. @Autowired optional dependency: dùng Optional<T> hoặc @Autowired(required=false).
Nói trong 60 giây
  • @Bean: tạo bean; @Autowired: inject bean có sẵn.
  • @Primary: default khi nhiều impl cùng type.
  • @Qualifier: chọn bean cụ thể by name.
  • Trap: 2 bean cùng type thiếu Primary/Qualifier → fail startup.

Đặt @Transactional ở service layer public methods (use case boundary). Dùng REQUIRES_NEW trên bean khác (AuditService) cho audit/outbox — commit độc lập outer TX. readOnly = true trên query service (OrderQueryService). Chỉ định rollbackFor = Exception.class khi cần rollback checked exception. Self-invocation: inject proxy bean thay gọi this.

When NOT

Đừng @Transactional trên controller (quá sớm, giữ connection lâu). Đừng gọi this.txMethod() — inject self proxy hoặc tách bean. Method private/final không bị intercept. Đừng expect rollback khi catch exception mà không rethrow. Bean new thủ công không có proxy.

Use case

Pitfall
Self-invocation là trap #1 phỏng vấn. Default rollback chỉ RuntimeException — checked exception commit TX trừ khi khai báo rollbackFor. private method @Transactional im lặng không hoạt động. Long TX (gọi HTTP trong @Transactional) giữ DB connection → pool exhaustion.
Nói trong 60 giây
  • @Transactional = AOP proxy: begin → method → commit/rollback.
  • Đặt trên Service public method — không Controller/Repository/private.
  • readOnly=true query; REQUIRES_NEW audit trên bean riêng.
  • Fail: self-invocation (this.), private/final, swallowed exception.
  • Default rollback RuntimeException only — dùng rollbackFor nếu cần.

Q14 @Async + @EnableAsync?

What

@EnableAsync bật xử lý bất đồng bộ qua Spring AOP proxy. @Async trên method khiến caller trả về ngay (thường void hoặc Future/CompletableFuture) trong khi method thực thi trên thread pool riêng — tách khỏi request thread của Tomcat.

Why

Giải phóng HTTP thread khi task I/O-bound dài: gửi email, generate PDF, gọi API bên thứ ba. Tăng throughput không cần tăng max threads servlet. CompletableFuture cho phép compose nhiều async task. Cơ chế proxy giống @Transactional — hiểu proxy = tránh bug “async không chạy”.

Return typeHành vi callerGhi chú
voidFire-and-forget, không biết kết quảException → AsyncUncaughtExceptionHandler
Future<T>future.get() block chờLegacy, vẫn dùng được
CompletableFuture<T>Chain thenApply, non-blocking composeKhuyến nghị cho flow phức tạp
How

Thêm @EnableAsync trên @Configuration. Khai báo Executor bean (ThreadPoolTaskExecutor) — set core/max pool, queue, thread prefix để debug. Gắn @Async("taskExecutor") nếu nhiều pool. Method phải public, gọi qua proxy từ bean khác — không this.async().

@Configuration
@EnableAsync
public class AsyncConfig {
  @Bean("taskExecutor")
  public Executor taskExecutor() {
    ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
    ex.setCorePoolSize(4); ex.setMaxPoolSize(16);
    ex.setQueueCapacity(500); ex.setThreadNamePrefix("async-");
    ex.setRejectedExecutionHandler(new CallerRunsPolicy());
    ex.initialize(); return ex;
  }
}

@Service
public class ReportService {
  @Async("taskExecutor")
  public CompletableFuture<Report> generate(Long id) {
    Report r = heavyPdfBuild(id);
    return CompletableFuture.completedFuture(r);
  }
}
When

Side-effect không cần kết quả ngay trong response: notification, audit enrich, cache warm. CPU/IO work song song với CompletableFuture.allOf. Tách pool riêng cho email vs report để tránh starvation. Kết hợp @Async @EventListener cho event handler không block publisher.

When NOT

Đừng @Async cho logic cần kết quả đồng bộ trong cùng request (race, mất error handling). Đừng dùng default SimpleAsyncTaskExecutor (tạo thread mới mỗi lần) ở prod. Đừng @Async method có @Transactional cần join TX caller — TX không propagate sang thread khác. CPU-bound nặng trên pool nhỏ → dùng @Scheduled hoặc message queue.

Use case
POST /orders trả 201 ngay; @Async gửi confirmation email + push webhook. Report dashboard: controller gọi 3 @Async service, CompletableFuture.allOf gom kết quả trước khi render — Tomcat thread chỉ chờ compose, không build PDF.
Pitfall
Self-invocation (this.generate()) chạy sync — inject self hoặc tách bean. Exception trong void @Async bị nuốt nếu không cấu hình handler. Queue đầy + CallerRunsPolicy chạy trên caller thread → vô tình block HTTP. Mất SecurityContext/MDC — cần TaskDecorator copy context sang async thread.
Nói trong 60 giây
  • @EnableAsync + @Async = AOP proxy, method chạy trên thread pool.

What

Why

Tách side-effect khỏi core flow: placeOrder chỉ save + publish; email, analytics, cache invalidation ở listener. Loose coupling — thêm listener không sửa OrderService. AFTER_COMMIT đảm bảo listener chỉ chạy khi DB đã commit — tránh “ghost notification” khi TX rollback.

Define immutable event record/class. Inject ApplicationEventPublisher vào service, publish sau business logic. Listener method nhận event type — Spring route theo parameter type. AFTER_COMMIT listener đăng ký “pending” trong TX, fire thật khi commit. Order listener với @Order nếu cần thứ tự.

Use case

Pitfall

  • @TransactionalEventListener AFTER_COMMIT = side-effect sau DB commit.

Q17 @ControllerAdvice / @RestControllerAdvice — global exception?

What

@ControllerAdvice (hoặc @RestControllerAdvice = @ControllerAdvice + @ResponseBody) định nghĩa global exception handler cho mọi @Controller/@RestController. Method @ExceptionHandler map exception type → HTTP status + response body thống nhất — không cần try-catch lặp ở từng endpoint.

Why

API contract nhất quán: client luôn nhận JSON {code, message, details} thay vì stack trace HTML 500. Tách cross-cutting concern khỏi business controller. @ResponseStatus hoặc ResponseEntity kiểm soát status code. Có thể @ExceptionHandler trên controller riêng nhưng Advice áp toàn app.

How

Tạo class @RestControllerAdvice. Mỗi @ExceptionHandler method nhận exception (+ HttpServletRequest tùy chọn). Trả ErrorResponse DTO. Xử lý MethodArgumentNotValidException cho @Valid. ExceptionHandler có priority: handler cụ thể trước Exception.class catch-all. Log server-side, trả message an toàn client.

@RestControllerAdvice
public class GlobalExceptionHandler {

  @ExceptionHandler(ResourceNotFoundException.class)
  @ResponseStatus(HttpStatus.NOT_FOUND)
  public ErrorResponse handleNotFound(ResourceNotFoundException ex) {
    return new ErrorResponse("NOT_FOUND", ex.getMessage());
  }

  @ExceptionHandler(MethodArgumentNotValidException.class)
  @ResponseStatus(HttpStatus.BAD_REQUEST)
  public ErrorResponse handleValidation(MethodArgumentNotValidException ex) {
    List<String> errors = ex.getBindingResult().getFieldErrors().stream()
        .map(f -> f.getField() + ": " + f.getDefaultMessage()).toList();
    return new ErrorResponse("VALIDATION_ERROR", errors);
  }

  @ExceptionHandler(Exception.class)
  public ResponseEntity<ErrorResponse> handleUnexpected(Exception ex) {
    log.error("Unhandled", ex);
    return ResponseEntity.status(500)
        .body(new ErrorResponse("INTERNAL_ERROR", "Unexpected error"));
  }
}
When

Mọi REST API production: map business exception → 4xx, infrastructure → 5xx. Centralize validation error format. Problem Details (RFC 7807) với ResponseEntity nếu team chuẩn hóa. basePackages khi admin API vs public API error shape khác nhau.

When NOT

Đừng expose stack trace hoặc SQL message ra client prod. Đừng @ExceptionHandler(Exception) quá rộng nuốt lỗi cần fail fast. Non-web layer (@Service) không bị Advice — exception propagate lên controller. GraphQL/Servlet filter error cần handler riêng ngoài @ControllerAdvice.

Use case
WMS REST: SkuNotFoundException → 404 + code SKU_NOT_FOUND; InsufficientStockException → 409 CONFLICT; @Valid fail → 400 field list. Mobile app parse code cố định, không phụ thuộc message tiếng Anh thay đổi.
Pitfall
Quên handle MethodArgumentNotValidException → 500 thay vì 400. Handler Exception.class che lỗi programming bug mà không log đủ context. @ControllerAdvice không catch exception từ @ControllerAdvice khác theo thứ tự không mong muốn. Trả ex.getMessage() có thể leak internal path/constraint name.
Nói trong 60 giây
  • @RestControllerAdvice = global handler cho mọi controller.
  • @ExceptionHandler map exception → status + ErrorResponse JSON.
  • Handle validation, business 4xx, catch-all 500 không leak stack.
  • Chỉ web layer; service throw, advice translate.

What

Why

Declarative validation tách khỏi if-else trong controller. Fail fast tại boundary với HTTP 400 chuẩn. Nested object cần @Valid trên field collection. Thêm spring-boot-starter-validation. Annotate DTO fields. Controller: @Valid @RequestBody → MethodArgumentNotValidException nếu fail. Nested: @NotEmpty List<@Valid OrderLine>. Business rule phức tạp (stock đủ không) → domain service, không chỉ annotation.

Use case

  • JSR-380 annotations trên DTO; @Valid trigger tại controller.
  • @Validated (Spring) = groups + validate @Service method params.

What

Why

Giảm load DB cho read-heavy data (product catalog, config). Latency ổn định — Redis in-memory vs query phức tạp. TTL tránh stale vô hạn. SpEL key linh hoạt (#sku, composite key). unless skip cache null result tránh cache poison.

What

Why

ApproachƯuNhược
Derived query findByXAndYĐơn giản, ít codeExplosion khi nhiều filter combo

How

Repository extends JpaSpecificationExecutor<Order>. Static factory methods trả Specification — null-safe: filter null → spec luôn true (cb.conjunction()). Service build spec chain từ request DTO. findAll(spec, Pageable) cho pagination. Join fetch trong spec cẩn thận — distinct + count query.

public interface OrderRepository extends
    JpaRepository<Order, Long>, JpaSpecificationExecutor<Order> {}

public class OrderSpecs {
  public static Specification<Order> hasStatus(OrderStatus status) {
    return (root, query, cb) ->
        status == null ? cb.conjunction() : cb.equal(root.get("status"), status);
  }
  public static Specification<Order> createdAfter(Instant from) {
    return (root, query, cb) ->
        from == null ? cb.conjunction() : cb.greaterThan(root.get("createdAt"), from);
  }
  public static Specification<Order> customerId(Long id) {
    return (root, query, cb) ->
        id == null ? cb.conjunction() : cb.equal(root.get("customerId"), id);
  }
}

Specification<Order> spec = OrderSpecs.hasStatus(filter.status())
    .and(OrderSpecs.createdAfter(filter.from()))

List<Order> findRecentByStatus(@Param("status") String status);

// Bulk update — @Modifying + @Transactional
@Modifying(clearAutomatically = true)
@Query("UPDATE Inventory i SET i.qty = i.qty - :qty WHERE i.sku = :sku AND i.qty >= :qty")
int decrementStock(@Param("sku") String sku, @Param("qty") int qty);
When

JPQL: fetch graph, filter entity relationship, portable app multi-DB. Native: report SQL phức tạp, pagination tối ưu với index cụ thể. @Modifying: bulk status update, soft delete batch, optimistic lock version increment — return 0 rows = conflict/stale.

When NOT

CRUD đơn giản → derived query. Native everywhere → mất portability, khó test H2 vs PostgreSQL. @Modifying không có @Transactional → TransactionRequiredException hoặc silent fail. JPQL UPDATE entity với relationship cascade phức tạp — load entity an toàn hơn. Dynamic WHERE nhiều → Specification thay vì concat @Query string.

Use case
WMS: JPQL JOIN FETCH order + lines cho pick list screen một query. Native report “orders last 7 days by status” dùng PostgreSQL INTERVAL. decrementStock @Modifying atomic — return 0 nếu không đủ qty, service throw InsufficientStockException không race condition load-modify-save.
Pitfall
Quên @Modifying trên UPDATE → exception hoặc hành vi lạ. Bulk update không refresh persistence context — entity cached trong session stale (dùng clearAutomatically). Native column name snake_case vs entity camelCase mismatch. JOIN FETCH nhiều bag collection → MultipleBagFetchException — fetch từng collection hoặc DTO query.
Nói trong 60 giây
  • @Query JPQL = entity name portable; native = SQL DB-specific.
  • JOIN FETCH fix N+1; native cho tune phức tạp.
  • @Modifying + @Transactional cho UPDATE/DELETE bulk.
  • Return rows affected; clearAutomatically tránh stale cache.

Deep Dive — Spring Proxy & AOP runtime

D1 Spring AOP tạo proxy thế nào — CGLIB vs JDK Dynamic Proxy, và vì sao final/private/self-invocation phá advice?

What

Spring AOP không sửa bytecode của class bạn — nó tạo một object proxy bọc quanh bean gốc rồi inject proxy thay cho bean. Có hai công nghệ:

  • JDK dynamic proxy (java.lang.reflect.Proxy + InvocationHandler): chỉ dùng được khi target implements ít nhất một interface; proxy cũng implements đúng interface đó.
  • CGLIB (repackaged trong spring-core): sinh bytecode tạo subclass của class target, override method để chèn advice chain.

Spring Framework: target có interface → JDK proxy; không có → CGLIB. Spring Boot mặc định spring.aop.proxy-target-class=true nên thực tế hầu hết bean dùng CGLIB, kể cả khi có interface.

Why

Mọi cross-cutting concern — @Transactional, @Cacheable, @Async, custom @Aspect — chỉ hoạt động khi lời gọi đi qua proxy. Hiểu cơ chế proxy là hiểu vì sao advice “im lặng không chạy”, và vì sao chọn JDK vs CGLIB lại ảnh hưởng tới class bị final, method private, hay lời gọi nội bộ.

How

Luồng gọi chuẩn: caller giữ tham chiếu tới proxy, proxy chạy Interceptor chain (các advice), rồi mới gọi method thật trên target. Bất kỳ lời gọi nào phát sinh từ bên trong target (qua this) đều không đi qua proxy.

Deep Dive — Transaction rollback rules

D2 @Transactional rollback: mặc định khi nào rollback, checked exception có rollback không, rollbackFor/noRollbackFor và readOnly khác gì?

What

Rollback rule quyết định transaction có rollback hay không dựa trên loại exception ném ra khỏi method. Mặc định của Spring: rollback trên RuntimeException và Error, nhưng KHÔNG rollback trên checked exception (business exception). Cấu hình qua rollbackFor / noRollbackFor (theo type) hoặc rollbackForClassName / noRollbackForClassName (theo pattern tên class).

Why

Đây là nguồn bug dữ liệu “âm thầm”: method ném checked exception, tưởng là thất bại nhưng Spring vẫn commit phần đã ghi trước đó → dữ liệu nửa vời. Ngược lại, hiểu sai khiến lập trình viên dùng rollbackFor = Exception.class tràn lan, vô tình rollback cả những lỗi nghiệp vụ chỉ nên bỏ qua.

How

TransactionInterceptor bọc method: mở TX → gọi target → khi có exception ném ra tới proxy, nó đối chiếu với các RollbackRuleAttribute đã đăng ký để quyết định rollback hay commit.

When

Dùng noRollbackFor khi muốn transaction vẫn commit dù một exception nào đó được ném ra và được xử lý ở tầng trên (ví dụ ghi log “best-effort”). readOnly = true dùng cho query service: là hint để Hibernate bỏ dirty-check/flush, tối ưu read.

When NOT

Không đặt readOnly = true lên method có ghi — có provider/DB ném lỗi hoặc tệ hơn là âm thầm bỏ qua ý định ghi. Không dùng rollbackFor = Exception.class như “công tắc rollback mọi thứ” — nó biến cả lỗi nghiệp vụ bình thường thành rollback. Không try/catch rồi “ăn” exception bên trong method TX: nuốt exception khiến TX không thấy lỗi và vẫn commit.

@Service
public class PaymentService {

  // BUG: checked exception -> KHONG rollback -> van COMMIT

  public void payWrong() throws PaymentException {
    repo.save(tx);
    if (fail) throw new PaymentException();  // checked -> commit (!)
  }

  // FIX: rollbackFor cho checked exception
  @Transactional(rollbackFor = PaymentException.class)
  public void payOk() throws PaymentException { /** ... **/ }

  // ngoai le: mot so unchecked van muon commit
  @Transactional(noRollbackFor = DuplicateKeyException.class)
  public void upsert() { /** ... **/ }

Use case

Trong luồng thanh toán: charge() (REQUIRED) ghi payment, gọi auditService.log() đánh dấu REQUIRES_NEW để audit luôn được ghi dù payment rollback. Nếu charge() ném checked exception mà quên rollbackFor, payment đã ghi vẫn commit mà client lại nhận báo lỗi — sai lệch nghiêm trọng.

Pitfall / Interview trap

UnexpectedRollbackException: inner method dùng propagation REQUIRED (join TX ngoài) gặp lỗi, Spring đánh dấu rollback-only lên TX vật lý; nhưng nếu exception bị inner try/catch nuốt mất, outer method thấy “không có lỗi” nên gọi commit → lúc này Spring buộc phải rollback và ném UnexpectedRollbackException. Đây là cái bẫy kinh điển: “tôi bắt exception rồi mà sao transaction vẫn fail?”.

Deep Dive — Virtual Threads (Boot 3.2+ / Java 21)

D3 Virtual Threads trong Spring Boot 3.2+ (Java 21): bật thế nào, lợi ích gì và khi nào KHÔNG nên bật?

What

Virtual thread (Project Loom, Java 21) là thread do JVM quản lý, rẻ hơn nhiều so với platform thread (OS thread). Spring Boot 3.2+ hỗ trợ bật bằng một property: spring.threads.virtual.enabled=true (cần Java 21+). Khi bật: Tomcat/Jetty dùng virtual thread cho request processing; applicationTaskExecutor trở thành SimpleAsyncTaskExecutor dùng virtual thread (nên @Async cũng chạy trên virtual thread); taskScheduler trở thành SimpleAsyncTaskScheduler dùng virtual thread.

Why

Với workload I/O-bound (gọi HTTP service, JDBC, đọc file), platform thread bị block suốt lúc chờ I/O, nên muốn xử lý nhiều request đồng thời phải tăng thread pool — tốn RAM và context switch. Virtual thread cho phép mỗi request một thread rẻ, hàng triệu virtual thread có thể tồn tại; JVM “unmount” virtual thread khỏi carrier thread khi nó block, giải phóng carrier để phục vụ việc khác.

How

Virtual thread chạy trên một pool carrier thread (ForkJoinPool) có kích thước xấp xỉ số CPU. Khi gặp thao tác blocking “biết nhường”, scheduler unmount virtual thread khỏi carrier. Lợi ích chỉ hiện rõ với code thật sự blocking và có thể unmount được.

Bean scopes: prototype trong singleton và ObjectProvider

What

Prototype được tạo mỗi lần container resolve bean, không phải mỗi lần gọi method. Inject trực tiếp prototype vào singleton chỉ resolve một lần; dùng ObjectProvider.getObject() trong từng thao tác để lấy instance mới và tự quản lý cleanup.

Scope và lifecycle

singleton mặc định là một instance mỗi bean definition trong ApplicationContext, không phải một object toàn JVM. prototype tạo mới mỗi lần lookup; request/session gắn vòng đời web scope. Container inject và gọi initialization callback cho prototype nhưng không tự gọi destruction callback lúc context đóng.

Bẫy injection

Singleton ReportService nhận Worker prototype qua constructor: Worker được tạo lúc singleton khởi tạo rồi bị giữ dùng lại. Nếu Worker chứa mutable buffer, request đồng thời có thể tranh chấp. Scope prototype không tự làm object thread-safe.

ObjectProvider

Inject ObjectProvider<Worker>, gọi getObject một lần ở đầu use case, giữ instance đó cho toàn bộ thao tác. Gọi nhiều lần trong cùng use case tạo nhiều worker khác nhau. Scoped proxy hay @Lookup là lựa chọn khác nhưng phải hiểu target resolution; ObjectProvider biểu lộ rõ nơi cần object mới.

Cleanup và kiểm thử

Worker giữ resource phải có close rõ ràng và caller gọi try/finally; @PreDestroy của prototype không tự chạy. Test hai lời gọi nhận hai Worker khác nhau; constructor injection trực tiếp thì cùng Worker. Với stateless service hãy dùng singleton đơn giản, đừng prototype mọi bean.

Singleton service → ObjectProvider.getObject mỗi use case → prototype mới → init → run → caller close
@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
class Worker implements AutoCloseable {
  public void run() { /* buffer riêng */ }
  public void close() { /* giải phóng resource */ }
}
@Service
class ReportService {
  private final ObjectProvider<Worker> workers;
  ReportService(ObjectProvider<Worker> workers) { this.workers = workers; }
  void execute() { try (Worker w = workers.getObject()) { w.run(); } }
}

AOP audit an toàn: allowlist log và phân biệt attempt với committed event

What

Audit aspect chỉ nên ghi trường allowlist như actor ID, operation, resource ID, trace ID và kết quả; không dump arguments, JWT hay response. Method return thành công chưa chứng minh transaction đã commit, nên audit nghiệp vụ cần gắn đúng transaction boundary.

Giữ kiến thức proxy hiện có

JDK proxy intercept qua interface, CGLIB dùng subclass; self-invocation bỏ qua cả hai. Điểm cần làm sâu là log có kiểm soát, không phải thêm aspect ghi toàn object. Method final trên target vẫn có thể được gọi qua JDK interface proxy; giới hạn override final chủ yếu thuộc CGLIB, còn private không phải interface method.

Schema allowlist

Ghi timestamp, actor nội bộ/pseudonym, operation enum, resource ID được kiểm soát, outcome và trace ID. Không ghi Authorization, Cookie, password, OTP, số thẻ, toàn request DTO hay exception message chứa dữ liệu. Giới hạn chiều dài và loại CR/LF để chống log injection; log backend phải có access control và retention.

Commit khác return

@AfterReturning chỉ biết method trả bình thường. Thứ tự transaction advice có thể khiến commit xảy ra sau advice audit. Audit attempt độc lập có thể dùng REQUIRES_NEW và phải ghi ATTEMPT/FAILED thật; business event thành công nên được ghi outbox trong cùng REQUIRED transaction với business data. Không đặt outbox độc lập REQUIRES_NEW vì sẽ phát ghost event nếu business rollback.

Độ bền và lỗi

AFTER_COMMIT listener in-process không bảo đảm delivery sau crash. Relay outbox cần retry/idempotency. Audit bắt buộc vì compliance phải xác định fail-closed/fail-open với nghiệp vụ, không nuốt lỗi tùy tiện. Ví dụ này là thiết kế minh họa, không phải tuyên bố hệ thống đã đạt chứng nhận.
