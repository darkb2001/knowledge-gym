Chọn compute nào?

AWS1 Lambda vs Fargate vs ECS-EC2 vs EKS: chọn compute nào cho workload?

What

AWS có bốn cách chạy code chính trên compute: Lambda (serverless function, scale tới 0), Fargate (container serverless — không quản EC2), ECS trên EC2 (tự quản cluster instance) và EKS (Kubernetes managed control plane). Chọn sai nền tảng là nguyên nhân phổ biến nhất khiến chi phí hoặc độ phức tạp vận hành tăng vọt. Câu hỏi DVA hay cho một đoạn mô tả workload rồi hỏi nên dùng gì.

How

Bốn lựa chọn, xếp theo mức bạn phải quản hạ tầng từ ít tới nhiều:

Lambdaevent, ≤15 phút, scale 0
→cần container
Fargatecontainer, không EC2
→cần GPU / giá tốt
ECS on EC2tự quản node
→cần K8s
EKSKubernetes API
# Serverless: scale tới 0, trả tiền theo request
aws lambda create-function --function-name img-thumb \
  --runtime python3.12 --handler app.handler \
  --role arn:aws:iam::111122223333:role/lambda-exec \
  --zip-file fileb://function.zip --timeout 60 --memory-size 1024

# Container dài hạn: Fargate, desired-count cố định
aws ecs create-service --cluster prod --service-name orders-api \
  --task-definition orders-api:12 --desired-count 3 --launch-type FARGATE

Quản serverKhôngKhôngCó (node)Có / node group

When

Chọn Lambda khi workload hướng sự kiện, chạy ngắn, chịu được cold start. Chọn Fargate khi cần container nhưng không muốn vá OS. Chọn ECS on EC2 khi cần GPU, instance spot giá rẻ hoặc kiểm soát kernel. Chọn EKS khi đội đã dùng Kubernetes và cần portability đa cloud.

When NOT

Đừng ép Lambda cho job chạy hơn 15 phút hoặc cần giữ kết nối dài (WebSocket stateful) — phải dùng ECS/EKS. Đừng dựng EKS chỉ để chạy một container đơn giản: gánh nặng vận hành Kubernetes không đáng. Đừng chọn Fargate nếu cần GPU (Fargate không có GPU).

Bẫy thi / Pitfall

Đề hay gài "container image, không muốn quản EC2, chạy 24/7" — đáp án là ECS Fargate, không phải Lambda (vì Lambda không chạy thường trú) và không phải ECS-EC2 (vì phải quản node).

AWS2 Giải phẫu ECS: cluster, task definition, service và task placement

What

ECS gồm bốn khái niệm dễ lẫn: cluster (nhóm logic các tài nguyên chạy task), task definition (bản thiết kế JSON — giống docker-compose, mô tả image, CPU/RAM, port, log, role), task (một lần chạy cụ thể của task definition) và service (bộ điều khiển giữ đúng desired count task, tự thay task chết, gắn load balancer).

How

Luồng từ định nghĩa tới chạy thật:

Clusterprod / staging
→register
Task definitionimage, cpu, port, role
→desired-count
Servicegiữ N task khoẻ
→run

How

Task placement strategy (chỉ với EC2 launch type): binpack (dồn task vào ít instance nhất — tiết kiệm), spread (rải đều theo AZ/instance — chịu lỗi tốt), random. Với Fargate, AWS tự lo placement nên không cần strategy.

Khái niệmLà gìVòng đời

When

Dùng task definition + service cho ứng dụng web chạy thường trú. Chỉ dùng run-task độc lập (không service) cho job một lần như migration, batch ngắn.

When NOT

Đừng nhồi nhiều container không liên quan vào một task definition kiểu "một máy chủ ảo" — mỗi task nên là một đơn vị deploy; tách để scale độc lập. Đừng dùng taskRoleArn cho permission kéo image: đó là việc của executionRoleArn.

Bẫy thi / Pitfall

execution role = cho ECS agent kéo image ECR + ghi log CloudWatch. task role = cho code trong container gọi S3/DynamoDB/SQS. Đề rất hay đổi chỗ hai role này.

ECS, Fargate và ECR

AWS3 Fargate vs EC2 launch type và capacity provider: khác nhau ra sao?

What

Launch type quyết định ai chạy container của bạn. EC2 launch type: bạn tự tạo và quản một ASG gồm EC2, mỗi instance cài ECS container agent. Fargate launch type: AWS cấp một máy ảo vi mô cho mỗi task, bạn không thấy và không vá được OS. Capacity provider là lớp trừu tượng gộp cả hai, cho phép service chọn FARGATE, FARGATE_SPOT hoặc ASG và đặt weight/base.

How

Cùng một task definition, chỉ khác launch type và cách cấp năng lực:

FARGATEper-task, không quản node
FARGATE_SPOTrẻ, có thể bị thu hồi
ASG providertự điều chỉnh node EC2
Managed scalingscaling theo số task
# Trộn Fargate + Fargate Spot: 2 task nền tối thiểu, phần còn lại 4 phần spot
aws ecs put-cluster-capacity-providers --cluster prod \
  --capacity-providers FARGATE FARGATE_SPOT \
  --default-capacity-provider-strategy \
    capacityProvider=FARGATE,weight=1,base=2 \
    capacityProvider=FARGATE_SPOT,weight=4
Tiêu chíFargateEC2 launch type
Quản OS / vá lỗiAWS loBạn lo (AMI, agent)
Đơn vị tính tiềnvCPU + GB theo giâyEC2 instance chạy 24/7
GPUKhôngCó
Tối ưu chi phí ở tải lớnKém hơnTốt hơn (spot/reserved)
Kiểm soát hostKhôngToàn quyền
When

Chọn Fargate cho phần lớn microservice mới: đơn giản, đúng mức sử dụng. Chọn EC2 launch type khi tải lớn ổn định (đặt reserved/spot cho rẻ), cần GPU/instance đặc thù, hoặc cần custom AMI đã hardened.

When NOT

Đừng chạy Fargate cho batch tải cao liên tục rồi kêu tốn tiền — EC2 reserved thường rẻ hơn nhiều ở mức tải ổn định. Đừng bật FARGATE_SPOT cho workload không chịu được gián đoạn: task spot có thể bị dừng với tín hiệu trước 2 phút.

Bẫy thi / Pitfall

Task Fargate bắt buộc networkMode: awsvpc và mỗi task nhận ENI riêng với IP trong subnet — đừng tìm cách gán nhiều task chung một IP. Ngoài ra Fargate không hỗ trợ host port mapping cố định.

AWS4 ECR và vòng đời image: scan, lifecycle policy, tag bất biến

What

Amazon ECR là registry container private, gắn chặt IAM và ECS/EKS. Ứng dụng developer quan tâm bốn thứ: đẩy/kéo image qua docker, image scanning (phát hiện CVE), lifecycle policy (tự xoá image cũ để giảm phí lưu trữ) và tag immutability (chặn ghi đè một tag, bảo đảm deploy tái lập được).

When

Bật scan on push cho mọi repo (basic scan miễn phí, enhanced scan dùng Inspector sâu hơn). Đặt lifecycle policy khi repo nhận hàng trăm build mỗi ngày. Bật tag immutability cho repo prod để một tag luôn trỏ về đúng một image.

When NOT

Đừng dùng tag latest làm tham chiếu deploy prod — image thay đổi âm thầm, rollback không tái lập được. Đừng xoá bằng tay hàng loạt: hãy để lifecycle policy tự động.

Bẫy thi / Pitfall

Deploy nên ghim theo image digest (repo@sha256:…) thay vì tag. Digest là bất biến; tag có thể bị trỏ lại. Repository policy khác account phải cấp cả quyền ecr:GetAuthorizationToken.

AWS5 Tình huống: task chạy nhưng ALB báo unhealthy, deploy xong cứ rollback — sửa thế nào?

What

Một ứng dụng deploy bản mới lên ECS service sau ALB; task ở trạng thái RUNNING nhưng target bị đánh unhealthy, rồi deployment tự rollback. Ở đây cần nắm ba thứ: target group health check, health check grace period và deployment circuit breaker.

How

ALB kiểm tra sức khoẻ qua target group; service ECS chỉ đưa task nhận traffic khi pass:

ALBlistener :443
→route theo path
Target grouphealth GET /healthz
↔đăng ký/rút target
ECS servicegrace period + breaker
→task IP
Task/healthz phải 200
aws ecs create-service --cluster prod --service-name orders-api \
  --task-definition orders-api:12 --desired-count 3 --launch-type FARGATE \
  --load-balancers targetGroupArn=arn:aws:elasticloadbalancing:ap-southeast-1:111122223333:targetgroup/orders-tg/abc123,containerName=api,containerPort=8080 \
  --health-check-grace-period-seconds 60 \
  --deployment-configuration \
    maximumPercent=200,minimumHealthyPercent=100,deploymentCircuitBreaker={enable=true,rollback=true}
How

Ba nguyên nhân thường gặp: (1) đường dẫn health check sai hoặc trả mã khác 200, (2) task khởi động chậm hơn grace period nên bị đánh unhealthy trước khi kịp sẵn sàng, (3) containerPort trong phần load-balancers không khớp cổng app thật. Bật deployment circuit breaker để ECS tự rollback thay vì treo deployment.

When

Luôn cấu hình health check trỏ tới một endpoint nhẹ, đã kiểm tra cả dependency. Đặt minimumHealthyPercent=100 cho prod để không mất năng lực khi deploy (đổi lại cần chỗ cho 200% task).

When NOT

Đừng để health check đụng vào dependency nặng (DB query) — một DB chậm có thể khiến toàn bộ task bị rút khỏi ALB. Đừng tắt circuit breaker ở prod: deploy lỗi sẽ treo vô hạn và bạn phải can thiệp tay.

Bẫy thi / Pitfall

deregistration_delay (mặc định 300 giây) làm lâu khi rút task; health check grace period phải lớn hơn thời gian app khởi động. Đừng lẫn hai thông số này.

EKS và EC2 cho developer

AWS6 EKS cho developer: kubectl, node group và IRSA

What

Amazon EKS là Kubernetes managed: AWS chạy control plane (API server, etcd) và bạn chỉ lo worker node. Developer cần biết: trỏ kubectl vào cluster, chọn cách chạy pod (managed node group, self-managed node hay Fargate profile) và cấp quyền IAM cho pod qua IRSA (IAM Roles for Service Accounts).

How

Luồng làm việc và ánh xạ quyền:

EKS control planeAPI + etcd, AWS lo
↔aws eks update-kubeconfig
kubectlapply / get pods
→schedule
Node groupEC2 worker
→annotate SA
IRSArole cho ServiceAccount
# Trỏ kubectl vào cluster (cần quyền describe cluster)
aws eks update-kubeconfig --name prod --region ap-southeast-1
kubectl get nodes
kubectl apply -f orders-deployment.yaml

# Liên kết OIDC provider (một lần) để dùng IRSA
eksctl utils associate-iam-oidc-provider --cluster prod --approve
apiVersion: v1
kind: ServiceAccount
metadata:
  name: orders-sa
  namespace: default
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::111122223333:role/orders-irsa
How

IRSA hoạt động nhờ OIDC provider của cluster: pod gắn ServiceAccount có annotation sẽ được STS cấp credential tạm thời — không cần nhúng access key vào image. Đây là cách cấp quyền chuẩn, thay cho việc gán role cho cả node (khiến mọi pod trên node dùng chung quyền).

When

Dùng managed node group cho hầu hết workload (AWS lo AMI/vá). Dùng Fargate profile khi muốn chạy pod không cần quản node. Dùng IRSA cho mọi pod cần gọi dịch vụ AWS.

When NOT

Đừng cấp quyền S3 rộng cho node role rồi cho mọi pod dùng chung — vi phạm least privilege và khó audit. Đừng chạy EKS nếu đội chưa có kinh nghiệm Kubernetes: chi phí vận hành và bề mặt lỗi lớn hơn ECS.

Bẫy thi / Pitfall

IRSA gắn ở mức ServiceAccount, không phải Deployment. Kiểm tra lại: nếu pod gọi S3 bị AccessDenied, thường do thiếu OIDC provider hoặc quên annotation trên đúng ServiceAccount.

AWS7 EC2 cho developer: instance family, spot vs on-demand vs reserved, user data và SSM

What

Dù hướng serverless, developer vẫn gặp EC2. Cần nắm: instance family (nhóm chữ cái), cách mua (on-demand / reserved / spot), user data để bootstrap lúc khởi động và SSM Session Manager để vào máy không cần SSH.

How

Các family phổ biến, chạm chữ cái để đoán:

t / mgeneral purpose (t3, m7i)
ccompute-optimized (CI, game)
r / xmemory (cache, DB)
i / dstorage NVMe
p / gGPU (ML, render)
# Boot máy có user data chạy 1 lần lúc launch (cloud-init)
aws ec2 run-instances --image-id ami-0abcd1234 \
  --instance-type t3.micro --key-name dev \
  --user-data file://bootstrap.sh

# Vào máy KHÔNG cần SSH, không mở port 22, không bastion
aws ssm start-session --target i-0abcd1234efgh5678
Kiểu muaGiảm giáRủi ro / cam kết
On-Demand0%Không, linh hoạt nhất
Reserved / Savings Planstới ~72%Cam kết 1–3 năm
Spottới ~90%Có thể bị thu hồi, báo trước 2 phút
When

Dùng Spot cho batch, CI runner, worker chịu gián đoạn. Dùng Reserved/Savings Plans cho nền tải ổn định chạy 24/7. Dùng SSM Session Manager thay SSH: cần IAM + agent, không cần mở cổng, có log phiên lên CloudWatch/CloudTrail.

When NOT

Đừng mở port 22 ra Internet hay dựng bastion host khi chỉ cần vào máy để debug — SSM an toàn và rẻ hơn. Đừng đặt state quan trọng trên instance spot; hãy coi nó luôn có thể biến mất. Đừng nhét bí mật vào user data (nó lộ trong metadata/console).

Bẫy thi / Pitfall

User data chạy một lần ở lần boot đầu (mặc định); không phải script cấu hình chạy lại. Log của nó nằm ở /var/log/cloud-init-output.log. Đặt secret ở user data là lỗi bảo mật kinh điển.

Beanstalk và lab chọn compute

AWS8 Elastic Beanstalk deployment policies: all-at-once tới traffic splitting

What

Elastic Beanstalk là PaaS: bạn đẩy code, nó lo EC2/ALB/ASG. Khi triển khai phiên bản mới, phải chọn deployment policy đánh đổi giữa tốc độ, chi phí và rủi ro downtime. Có năm chính sách: all-at-once, rolling, rolling with additional batch, immutable và traffic splitting.

How

Mức an toàn tăng dần, chi phí cũng tăng dần:

Rủi ro giảm dần → an toàn tăng
All-at-oncenhanh nhất, có downtime
Rollingtừng batch, giảm năng lực
Rolling + batchgiữ đủ năng lực
ImmutableASG mới, rollback nhanh
Traffic splittingcanary % lên bản mới
# .ebextensions/deploy.config
option_settings:
  aws:elasticbeanstalk:command:
    DeploymentPolicy: RollingWithAdditionalBatch
    BatchSizeType: Percentage
    BatchSize: 25
    Timeout: 600
PolicyDowntimeNăng lực trong deployRollback
All-at-onceCó0Phải deploy lại
RollingKhôngGiảm theo batchDeploy lại
Rolling + additional batchKhôngĐủ (thêm batch)Deploy lại
ImmutableKhôngĐủNhanh, bỏ ASG mới
Traffic splittingKhôngĐủNhanh theo %
When

Dùng all-at-once cho dev/test cần nhanh. Dùng rolling with additional batch hoặc immutable cho prod cần zero-downtime. Dùng traffic splitting (canary) khi muốn đưa một phần nhỏ traffic lên bản mới để quan sát rồi mới all-in.

When NOT

Đừng dùng all-at-once cho prod (downtime toàn bộ). Đừng lẫn rolling với blue/green: rolling thay dần trên cùng môi trường, còn blue/green là đổi hai môi trường và swap CNAME — không phải một deployment policy của Beanstalk.

Bẫy thi / Pitfall

Deployment policy áp ở cấp môi trường (aws:elasticbeanstalk:command). Đừng tìm nó trong Dockerfile hay buildspec — đó không phải chỗ cấu hình.

AWS9 Lab tình huống: chọn compute cho ba workload cụ thể

What

Bài tổng hợp: ba mô tả workload, chọn nền tảng compute phù hợp và giải thích. Đây là dạng câu hỏi tình huống đặc trưng của DVA-C02 — mấu chốt là khớp ràng buộc (thời gian chạy, hướng sự kiện, nhu cầu vận hành) với dịch vụ.

How

Bảng ánh xạ nhanh ràng buộc → lựa chọn:

Workload Aresize ảnh khi upload S3
Workload BAPI container 24/7
Workload Cnhiều microservice K8s
Workload Dbatch số lớn cuối ngày
# A) S3 upload sinh event -> Lambda (không giữ server)
aws s3api put-bucket-notification-configuration \
  --bucket uploads --notification-configuration file://notif.json

# B) API container chạy thường trú -> ECS Fargate sau ALB
sam build
sam deploy --guided

# D) Batch lớn chạy cuối ngày trên spot -> AWS Batch / ECS run-task
WorkloadChọnVì sao
A. resize ảnh khi có file mớiLambdaHướng sự kiện, ngắn, scale tới 0
B. API container chạy 24/7ECS FargateContainer lâu dài, không quản node
C. Bộ microservice chuẩn K8sEKSCần hệ sinh thái và portability K8s
D. Batch lớn, chịu gián đoạnSpot / AWS BatchTối ưu chi phí, job dài quá 15 phút
When

Dùng khung này khi đề cho một đoạn văn mô tả hệ thống. Luôn tự hỏi bốn câu: chạy bao lâu, hướng sự kiện hay liên tục, ai quản hạ tầng, có cần K8s/GPU không.

When NOT

Đừng chọn Lambda nếu workload vượt 15 phút hoặc cần streaming dài; khi đó chuyển sang Fargate/ECS. Đừng chọn EKS chỉ vì "nghe hiện đại" nếu đội không vận hành được Kubernetes — ECS đơn giản hơn cho phần lớn bài toán.

Bẫy thi / Pitfall

Đọc kỹ từ khoá: "spiky, unpredictable traffic" thiên về Lambda/Serverless; "long-running server process" thiên về container; "many services, portable across clouds" thiên về EKS; "cost-sensitive, interruptible" thiên về spot.
