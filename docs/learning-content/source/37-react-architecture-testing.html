Kiến trúc React, Tích hợp API & Testing

Đưa React lên mức production: routing, code splitting, lớp gọi API và refresh token, CORS, accessibility, chiến lược test và tối ưu Web Vitals.

Routing, layout & phân quyền ở FE

Q1 Routing trong SPA — cấu trúc route, nested route và layout khác gì nhau?

What

Routing là tầng ánh xạ URL thành cây component. React Router khai báo route lồng nhau: route cha render <Outlet /> làm chỗ chèn route con. Next.js App Router suy ra route từ cấu trúc thư mục app/: page.tsx tạo route, layout.tsx bọc chung, loading.tsx và error.tsx xử lý trạng thái. Cả hai dùng History API nên đổi URL không reload toàn trang.

Why

Nested route + layout cho phép chia sẻ UI (sidebar, topbar, tab) mà layout không remount khi điều hướng giữa các route con — state filter, vị trí scroll, kết nối socket giữ nguyên. Nếu để route phẳng hết, mỗi trang tự render lại khung, mất state và tốn re-render. URL là state có thể share, bookmark, back/forward — điều mà state cục bộ không làm được.

How
URL thay đổi (pushState)
↓
Router khớp route tree
Layout cha (giữ nguyên)
↓
Page con render trong Outlet

Router so khớp segment với route tree, mount phần layout còn thiếu rồi render page con vào Outlet. Route động dùng param (/orders/:orderId) hoặc catch-all (*). Next.js làm tương tự nhưng dựa trên thư mục: layout không đổi khi điều hướng trong cùng nhánh, nên chỉ segment mới được stream/render.

When

App nhiều màn hình có khung chung (dashboard, admin, tab trong chi tiết), cần deep link, breadcrumb, back/forward, hoặc cần giữ state của khung khi chuyển tab con.

When NOT

App một màn hình hoặc chỉ có modal/step — state cục bộ đủ, dựng router chỉ thêm phức tạp. Cũng đừng lạm dụng nested route quá sâu cho những thứ không phải điều hướng thật (tab nhỏ, wizard trong modal) vì URL sẽ khó đọc và dễ lệch state.

// React Router v6 — nested route + layout cha
const router = createBrowserRouter([
  {
    path: '/',
    element: <AppLayout />,           // layout cha render <Outlet />
    children: [
      { index: true, element: <Dashboard /> },
      { path: 'orders', element: <Orders />,
        children: [{ path: ':orderId', element: <OrderDetail /> }] },
      { path: '*', element: <NotFound /> },
    ],
  },
]);

function AppLayout() {
  return (
    <div className="shell">
      <Sidebar />
      <main><Outlet /></main>   // route con render ở đây
    </div>
  );
}
Use case

Trang chi tiết đơn hàng: layout khung (sidebar + header) giữ nguyên khi chuyển giữa tab "Lines / Timeline / Documents"; tab là route con nên copy link gửi đồng nghiệp vẫn mở đúng tab.

Pitfall / Interview trap

Đặt layout bên trong từng page thay vì ở route cha → remount toàn bộ, mất state và giật khi điều hướng. Với danh sách dùng cùng component nhưng khác URL, thiếu key ổn định khiến React reuse sai state giữa hai trang. Next.js: layout.tsx mặc định là Server Component — không đặt logic cần useState ở đó mà không có "use client".

Nói trong 60 giây
  • Routing = map URL → cây component; React Router dùng Outlet, Next dùng thư mục app/.
  • Nested route + layout cha để không remount khung, giữ state và scroll.
  • Layout phải nằm ở route cha, không nằm trong page.
  • Route động qua param, không đủ thì catch-all '*'.
  • URL là state share được — deep link, back/forward.

Q2 Protected route ở FE có phải là ranh giới bảo mật không?

What

Protected route là guard phía client: trước khi render, kiểm tra user đã đăng nhập và có role/permission cần thiết; nếu không thì chuyển hướng về trang login hoặc 403. Nó chỉ là UX gate — quyết định hiện hay ẩn UI — không phải ranh giới bảo mật. Ranh giới thật nằm ở backend: mỗi request phải được xác thực và phân quyền độc lập, không tin bất cứ gì client gửi lên.

Why

Người dùng luôn có thể gọi API trực tiếp bằng curl/Postman, sửa JS trong DevTools, hoặc sửa state để guard trả về true. Nếu backend không kiểm tra quyền, dữ liệu vẫn bị trả về → broken access control (OWASP A01). FE guard có giá trị thật nhưng nằm ở chỗ khác: tránh cho user vào một trang trắng rồi nhận 403, giảm request vô nghĩa, và ẩn nút mà user không có quyền bấm.

How
Điều hướng tới /admin
↓
Guard FE: còn token? đủ role?
↓ không / có
Redirect /login
Render trang + gọi API
↓
Backend xác thực + kiểm tra quyền theo resource

Guard chỉ chặn ở tầng render. Song song, backend phải kiểm tra trên từng endpoint: token hợp lệ, role đủ, và quan trọng nhất là quyền trên đúng resource (order này có thuộc user/tenant này không) để chặn IDOR khi user đổi orderId trên URL.

When

Dùng để điều hướng UX: chưa đăng nhập thì về login kèm redirect về trang cũ; role không đủ thì ẩn menu/nút và hiện trang "không có quyền"; permission đọc từ server trả về (claim trong access token hoặc endpoint /me) chỉ để trang trí UI.

When NOT

Không dùng FE guard để bảo vệ dữ liệu nhạy cảm, không coi "ẩn nút" là đã phân quyền. Cũng đừng decode JWT ở FE rồi tin payload để ra quyết định business (payload đọc được và có thể bị sửa trước khi decode nếu ta tự parse) — chữ ký chỉ backend verify. Với dữ liệu cần bảo mật, luôn hỏi: "endpoint này có tự kiểm tra quyền chưa?".

// Guard chỉ chặn render — KHÔNG phải bảo mật
function RequireAuth({ children, roles }: { children: ReactNode; roles?: string[] }) {
  const { user, loading } = useAuth();
  const location = useLocation();

  if (loading) return <Spinner />;
  if (!user) return <Navigate to="/login" state={{ from: location }} replace />;
  if (roles && !roles.some((r) => user.roles.includes(r))) {
    return <Navigate to="/403" replace />;
  }
  return <>{children}</>;
}
Use case

Route /admin/reports chỉ cho role MANAGER: guard ẩn khỏi menu và redirect nếu truy cập tay, đồng thời endpoint GET /api/reports trả 403 nếu token thiếu role — hai lớp độc lập, lớp sau mới là thật.

Pitfall / Interview trap

Trả lời "FE ẩn nút nên user không gọi được API" là mất điểm. Bẫy tiếp theo: chỉ kiểm tra "đã đăng nhập" mà không kiểm tra quyền trên resource → IDOR (đổi orderId thấy đơn của user khác). Cũng cẩn thận backend tin header X-Role hoặc role do client gửi.

Nói trong 60 giây
  • Protected route = UX gate, không phải bảo mật.
  • Client luôn có thể gọi API trực tiếp — backend phải tự kiểm tra.
  • Guard tốt cho UX: redirect, ẩn menu, tránh trang trắng.
  • Phải kiểm quyền trên đúng resource để chặn IDOR.
  • Không tin payload/route do client gửi để ra quyết định.

Q3 Code splitting, lazy + Suspense, dynamic import — đo bundle và khi nào nên tách chunk?

What

Code splitting chia bundle thành nhiều chunk tải theo nhu cầu bằng dynamic import(). React bọc nó qua React.lazy(() => import('./Heavy')) rồi đặt trong <Suspense fallback={...}>; Next.js tự tách chunk theo route và có next/dynamic cho component. Mục tiêu là giảm lượng JavaScript của lần tải đầu để first paint và khả năng tương tác đến sớm hơn.

Why

Bundle lớn đồng nghĩa parse + compile + execute JS nặng trên main thread, làm LCP muộn và INP cao — đặc biệt trên máy yếu/mạng 3G. Tách route và component nặng ra khỏi chunk đầu giúp trang chính nhẹ. Nhưng tách quá nhỏ cũng hại: nhiều request sinh waterfall, mỗi lần chuyển màn hình có thêm một round-trip, dễ thấy nhấp nháy khi Suspense fallback hiện lên.

How
Đo bundle (build output / visualizer)
↓
Tìm chunk lớn & ít dùng lúc đầu
Route nặng, editor, chart, map
↓ dynamic import()
Chunk riêng, tải khi cần

Cách đo: xem output của vite build (danh sách chunk + kích thước gzip), next build in cột "First Load JS" theo route, và phân tích thành phần bằng rollup-plugin-visualizer hoặc source map explorer. Ngưỡng thực dụng: tách theo route trước; một dependency chiếm hơn ~30–50 kB gzip và không cần ngay ở màn hình đầu thì đáng lazy.

When

Route/màn hình chỉ vào sau khi user đăng nhập hoặc bấm menu; component nặng nhiều phụ thuộc (rich text editor, biểu đồ, bản đồ, pdf viewer); modal/panel ít mở; thư viện chỉ dùng ở một trang. Ở Next.js, dùng next/dynamic với ssr: false cho component chỉ chạy được trên browser.

When NOT

Không lazy component nằm above the fold hoặc render ngay khi vào app — sẽ chậm hơn và nháy fallback. Không tách vụn từng component nhỏ: mỗi chunk là một request, waterfall làm chậm hơn là nhanh hơn. Cũng đừng lazy chỉ để "cho đẹp số liệu build" khi route đó vốn là đường vào chính.

import { lazy, Suspense } from 'react';

// dynamic import: chunk riêng, chỉ tải khi route này được render
const ReportEditor = lazy(() => import('./ReportEditor'));

export function ReportPage() {
  return (
    <Suspense fallback={<Skeleton rows={6} />}>
      <ReportEditor />
    </Suspense>
  );
}

// Vite: tách vendor, tránh chunk quá lớn
// build.rollupOptions.output.manualChunks = { react: ['react', 'react-dom'] }
Use case

Dashboard nội bộ: trang chính nhẹ, chỉ khi user mở tab "Analytics" mới tải thư viện biểu đồ. First Load JS của route chính giảm mạnh, tab analytics chấp nhận tải thêm một chunk khi bấm.

Pitfall / Interview trap

Bẫy hay gặp: prefetch sai — React Router/Next prefetch mọi route khiến user tải hết dù không vào, phản tác dụng. Nữa là dynamic import bên trong component dùng ngay ở lần render đầu → mỗi render tạo promise mới nếu viết sai chỗ, cần khai báo ở module scope. Và nhớ: Suspense chỉ bắt lazy/transition, không tự chặn lỗi runtime — lỗi thì cần error boundary.

Nói trong 60 giây
  • Code splitting = dynamic import() tạo chunk tải theo nhu cầu.
  • React.lazy + Suspense; Next tách route tự động, next/dynamic cho component.
  • Đo bằng build output, First Load JS, visualizer — không đoán.
  • Tách theo route và component nặng; tránh tách vụn gây waterfall.
  • Không lazy thứ above the fold; Suspense không thay error boundary.

Tích hợp API, auth & CORS

Q4 Lớp gọi API ở FE nên tổ chức thế nào? Xử lý 401, refresh token, retry, timeout, huỷ request ra sao?

What

Tách một HTTP client dùng chung (một axios instance hoặc wrapper quanh fetch) thay vì gọi rải rác khắp component. Client đó gắn interceptor để: thêm header Authorization, khi gặp 401 thì gọi refresh token một lần rồi retry request cũ, chuẩn hoá lỗi về một shape thống nhất, đặt timeout, và nhận AbortSignal để huỷ request khi không còn cần.

Why

Gom vào một chỗ giúp đổi baseURL/header/format lỗi mà không sửa hàng trăm call site, và tránh "refresh storm" — nhiều request 401 cùng lúc đều gọi refresh làm token hỏng/đăng xuất oan. Timeout + abort ngăn request treo vô hạn và race condition khi user đổi filter liên tục (kết quả cũ về sau ghi đè kết quả mới). Retry đúng chỗ giúp chịu lỗi mạng mà không gây tác dụng phụ.

How
Request qua client chung
↓ interceptor gắn token + timeout
Server trả 401
Refresh single-flight
↓ refresh OK
Retry request 1 lần → trả data
↓ refresh fail
Logout + về trang login

Refresh phải single-flight: giữ một promise refresh đang chạy, mọi request 401 khác chờ chung promise đó thay vì gọi song song. Chỉ retry một lần, và chỉ retry an toàn với request idempotent (GET/HEAD) hoặc request đã có idempotency key; retry mù với POST có thể tạo đơn trùng.

When

App có auth và nhiều endpoint; cần xử lý token hết hạn êm (user không bị đá ra giữa chừng); cần phân biệt lỗi mạng, lỗi 4xx nghiệp vụ và lỗi 5xx để hiện toast/retry phù hợp; cần huỷ request khi unmount hoặc khi filter đổi.

When NOT

Đừng retry vô hạn hoặc retry cả 4xx (401 sau refresh, 403, 422 — retry vô nghĩa, chỉ tốn request). Không bọc mọi lỗi thành toast chung chung — mất khả năng xử lý theo ngữ cảnh. Không nhồi logic business vào interceptor; nó chỉ nên lo cross-cutting (auth, log, lỗi, timeout).

let refreshPromise: Promise<void> | null = null;

// gọi qua client chung, không fetch rải rác trong component
async function apiFetch<T>(url: string, init: RequestInit = {}): Promise<T> {
  const res = await fetch(url, {
    ...init,
    credentials: 'include',                    // gửi cookie httpOnly
    headers: { ...init.headers, 'Content-Type': 'application/json' },
    signal: init.signal ?? AbortSignal.timeout(10_000),
  });

  if (res.status === 401) {
    // single-flight: nhiều 401 cùng chờ một refresh
    refreshPromise ??= refreshToken().finally(() => { refreshPromise = null; });
    await refreshPromise;
    return apiFetch<T>(url, init);              // retry đúng 1 lần
  }
  if (!res.ok) throw new ApiError(res.status, await res.json());
  return res.json() as Promise<T>;
}

// huỷ khi filter đổi / component unmount
const ac = new AbortController();
apiFetch(`/api/orders?q=${q}`, { signal: ac.signal });
return () => ac.abort();
Use case

Màn hình danh sách có ô search debounce: mỗi lần gõ, request cũ bị abort() nên kết quả cũ không ghi đè kết quả mới; khi access token hết hạn, một refresh duy nhất chạy và toàn bộ request đang chờ tự retry.

Pitfall / Interview trap

Bẫy kinh điển: refresh loop vô hạn khi chính endpoint refresh cũng trả 401 — phải loại trừ URL refresh khỏi interceptor. Thứ hai: retry POST không idempotent gây tạo bản ghi trùng. Thứ ba: quên AbortController → setState sau unmount và race kết quả. Cuối cùng: timeout quá ngắn cắt cả request upload chậm.

Nói trong 60 giây
  • Một HTTP client chung + interceptor, không fetch rải rác.
  • 401 → refresh single-flight → retry đúng một lần.
  • Loại trừ endpoint refresh khỏi interceptor, tránh loop.
  • Timeout mặc định + AbortSignal để huỷ và tránh race.
  • Chỉ retry idempotent, không retry 4xx.

Q5 Access token nên lưu ở đâu: memory, localStorage hay cookie httpOnly?

What

Có ba lựa chọn chính. Memory (biến module/React state): an toàn nhất trước XSS kéo dài nhưng mất khi reload. localStorage/sessionStorage: tiện và tồn tại qua reload, nhưng JavaScript đọc được nên một XSS là token bị lấy trọn. Cookie httpOnly (kèm Secure, SameSite): JS không đọc được, chặn đánh cắp token qua XSS, nhưng phải xử lý CSRF.

Why

Đây là bài toán cân bằng XSS và CSRF. Cookie httpOnly giấu token khỏi JavaScript nên XSS không exfiltrate được, đổi lại browser tự gửi cookie nên cần chống CSRF (cùng SameSite + CSRF token). localStorage kháng CSRF tự nhiên vì JS phải chủ động gắn header, nhưng đúng cái JS đó là thứ XSS chiếm quyền. Không có lựa chọn "miễn nhiễm cả hai", nên phải chọn theo mô hình đe dọa.

How
Login thành công
↓
Access token ngắn hạn → memory
Refresh token → cookie httpOnly
↓ refresh khi hết hạn
/auth/refresh (cookie tự gửi) → token mới vào memory

Pattern phổ biến: access token thời gian ngắn giữ trong memory, refresh token dài hạn đặt trong cookie httpOnly; Secure; SameSite=Strict (hoặc Lax nếu cần điều hướng từ site khác). Reload trang thì gọi /auth/refresh để lấy access token mới, nên user không phải đăng nhập lại mà token vẫn ngắn hạn.

When

Dùng cookie httpOnly khi có thể kiểm soát CSRF (SameSite + CSRF token, hoặc API cùng origin qua BFF). Dùng memory khi không muốn dính CSRF và chấp nhận reload sẽ refresh lại. localStorage chỉ nên là lựa chọn đánh đổi có ý thức, ví dụ công cụ nội bộ, ít rủi ro XSS và cần đơn giản.

When NOT

Không lưu refresh token dài hạn trong localStorage — đó là món hời lớn nhất cho kẻ tấn công XSS. Không đặt SameSite=None mà thiếu Secure và thiếu chống CSRF; browser cũng sẽ chặn SameSite=None không kèm Secure. Không giả định cookie tự chống CSRF khi đã hạ SameSite xuống None.

// Gửi cookie httpOnly: credentials phải bật, origin phải cụ thể
await fetch('/api/orders', {
  method: 'GET',
  credentials: 'include',          // cookie httpOnly tự đính kèm
  headers: {
    'X-CSRF-Token': readCsrfCookie(),  // chống CSRF, đọc từ cookie KHÔNG httpOnly
  },
});

// Set-Cookie phía server (minh hoạ thuộc tính cần có)
// refresh=...; HttpOnly; Secure; SameSite=Strict; Path=/auth; Max-Age=604800
// csrf=...;    Secure; SameSite=Strict; Path=/    (JS đọc được để gắn header)
Use case

SPA gọi API khác origin qua BFF cùng origin: refresh token nằm cookie httpOnly; SameSite=Strict ở domain BFF, SPA chỉ cầm access token trong memory — XSS không lấy được refresh token nên không duy trì được phiên.

Pitfall / Interview trap

Trả lời "dùng localStorage vì tiện" mà không nêu rủi ro XSS là thiếu chiều sâu. Bẫy nữa: CORS với Access-Control-Allow-Origin: * không dùng được cùng credentials: 'include' — browser từ chối, phải nêu origin cụ thể kèm Allow-Credentials: true. Và nhớ: httpOnly chặn đọc cookie nhưng KHÔNG chặn được CSRF — đó là lý do phải có SameSite và CSRF token.

Nói trong 60 giây
  • Memory an toàn trước XSS nhưng mất khi reload.
  • localStorage tiện nhưng XSS đọc được token.
  • Cookie httpOnly giấu token khỏi JS, đổi lại phải chống CSRF.
  • Pattern tốt: access token ngắn hạn ở memory, refresh token ở cookie httpOnly SameSite=Strict.
  • Không SameSite=None thiếu Secure; ACAO * không đi cùng credentials.

Q6 Lỗi CORS có phải lỗi backend không? Preflight và khi nào dùng proxy/BFF?

What

CORS là cơ chế của browser thực thi Same-Origin Policy, không phải backend tự chặn request. Khi FE và API khác origin (khác scheme/host/port), browser gửi preflight OPTIONS trước với các method/header không "đơn giản", và chỉ cho JavaScript đọc response nếu server trả về header khớp: Access-Control-Allow-Origin, cùng Allow-Methods, Allow-Headers, và Allow-Credentials khi cần cookie.

Why

Hiểu sai điều này khiến ta đi sửa logic backend trong khi request đã tới và server trả 200 — chỉ có browser chặn JS đọc kết quả và báo lỗi CORS trong console. Nắm đúng bản chất giúp chọn đúng cách sửa: cấu hình response header cho đúng origin, hoặc né hẳn cross-origin bằng proxy/BFF để mọi thứ same-origin.

How
FE (origin A) gọi API (origin B)
↓ method/header không đơn giản
Preflight OPTIONS
Server trả ACAO + Allow-Methods/Headers
↓ browser xác nhận hợp lệ
Request thật gửi đi
↓ nếu thiếu header
Browser chặn JS đọc response (không phải server lỗi)

Preflight chỉ xảy ra với request cần nó: method khác GET/HEAD/POST "đơn giản", hoặc có header tuỳ biến như Authorization hay Content-Type: application/json. Khi dùng cookie (credentials), server bắt buộc trả origin cụ thể và Access-Control-Allow-Credentials: true — không được dùng *.

When

Dùng proxy/BFF khi muốn FE và API same-origin: dev thì proxy của Vite/Next rewrite /api sang backend; production thì BFF đứng cùng domain FE, giữ cookie httpOnly mà không cần SameSite=None, đồng thời che API key và gom endpoint. Cấu hình CORS trực tiếp khi các origin đã biết và ổn định, không cần giấu token hay che API.

When NOT

Không "mở CORS cho hết" bằng * nếu có credentials — vừa bị browser chặn vừa nới rộng bề mặt tấn công. Không dùng CORS như cơ chế xác thực: nó chỉ là chính sách đọc kết quả của browser, không bảo vệ API khỏi client khác (curl, server-to-server). Cũng đừng quên preflight bị cache — cấu hình sai có thể nằm lại trong cache trình duyệt một lúc.

OPTIONS /api/orders HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, authorization

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com   <-- origin cụ thể, KHÔNG dùng *
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 600
Use case

Dev local FE ở localhost:5173 gọi backend localhost:8080: cấu hình proxy trong Vite (server.proxy['/api']) để browser thấy same-origin, không phải động vào CORS của backend và cookie hoạt động như production.

Pitfall / Interview trap

Bẫy: Access-Control-Allow-Origin: * kèm Allow-Credentials: true bị browser từ chối dù server "có set header" — phải echo đúng origin. Bẫy nữa: thiếu Allow-Headers cho Authorization khiến preflight fail trong khi endpoint GET trực tiếp vẫn chạy. Nhớ phân biệt: lỗi CORS hiện ở console browser, server không hề nhận được request thật; còn lỗi 500 từ API mới là lỗi backend.

Nói trong 60 giây
  • CORS là chính sách browser, không phải backend chặn.
  • Request vẫn tới server — browser chặn JS đọc response.
  • Preflight OPTIONS cho method/header không đơn giản.
  • Credentials thì ACAO phải là origin cụ thể, không '*'.
  • Tránh cross-origin bằng proxy dev hoặc BFF same-origin.

Chất lượng — a11y, testing, build & performance

Q7 Accessibility và responsive: semantic HTML, focus management, aria-live, keyboard, breakpoint?

What

Accessibility (a11y) nghĩa là UI dùng được bằng keyboard và screen reader: dùng đúng semantic HTML (button, nav, label, table) thay vì div gắn handler; quản lý focus khi mở/đóng modal và khi đổi route; dùng aria-live cho thông báo động và role="alert" cho lỗi. Responsive là mobile-first với breakpoint hợp lý, tap target đủ lớn, không khoá cứng chiều rộng.

Why

Semantic HTML cho sẵn hành vi miễn phí: button đã focus được, kích hoạt bằng Enter/Space, có role đúng; label gắn với input giúp screen reader đọc tên trường. Tự dựng lại bằng div thường thiếu những thứ này và phải bù bằng ARIA — dễ sai hơn. Focus management quyết định người dùng keyboard có lạc trong modal hay không. Với nhiều thị trường, a11y còn là yêu cầu pháp lý, và responsive kém làm hỏng luồng mua/thao tác trên mobile.

How
Semantic HTML trước (button, label, nav)
↓ chỉ bù ARIA khi thiếu ngữ nghĩa
Keyboard: Tab/Enter/Space/Escape
Focus trap trong modal
↓
aria-live thông báo, focus trả về trigger

Modal: khi mở thì chuyển focus vào phần tử đầu trong modal và giữ focus trong đó, khi đóng thì trả focus về nút đã mở. Đổi route trong SPA nên đưa focus tới heading của trang mới hoặc thông báo bằng vùng aria-live, vì screen reader không tự biết nội dung đã thay. Responsive: mobile-first, breakpoint theo nội dung thay vì thiết bị, dùng min-width và đảm bảo tap target tối thiểu khoảng 44px.

When

Bắt buộc cho form (label + thông báo lỗi liên kết input), modal/drawer, menu và dropdown, bảng dữ liệu có sort/pagination, và mọi SPA vì điều hướng không reload nên screen reader cần được báo. Responsive cho mọi màn hình có bảng, toolbar, hoặc danh sách dài trên mobile.

When NOT

Không dùng aria-* để bù cho HTML sai (div giả button) — đó là anti-pattern; aria-hidden="true" lên phần tử vẫn focus được làm keyboard mắc kẹt. Không lạm dụng aria-live="assertive" cho mọi cập nhật vì nó cắt ngang screen reader liên tục. Không dựng breakpoint theo từng model thiết bị; cũng đừng ẩn nội dung chỉ bằng CSS mà vẫn focus được.

// Modal: semantic + focus management + thông báo động
export function ConfirmDialog({ open, onClose, message }: DialogProps) {
  const ref = useRef<HTMLDivElement>(null);

  useEffect(() => {
    if (!open) return;
    const prev = document.activeElement as HTMLElement;
    ref.current?.focus();                       // đưa focus vào modal
    return () => prev?.focus();                 // trả focus về trigger
  }, [open]);

  if (!open) return null;

  return (
    <div
      role="dialog"
      aria-modal="true"
      aria-labelledby="dlg-title"
      tabIndex={-1}
      ref={ref}
      onKeyDown={(e) => e.key === 'Escape' && onClose()}
    >
      <h2 id="dlg-title">Xác nhận</h2>
      <p>{message}</p>
      <button onClick={onClose}>Huỷ</button>
      <button onClick={confirm}>Đồng ý</button>
    </div>
  );
}

// Vùng thông báo: polite cho cập nhật, assertive cho lỗi
// <div aria-live="polite" role="status">{toast}</div>
Use case

Bảng dữ liệu: nút sort là button có aria-sort, phân trang keyboard truy cập được; khi kết quả tải xong, một vùng aria-live="polite" thông báo "Tìm thấy 42 kết quả" để người dùng screen reader biết bảng đã cập nhật.

Pitfall / Interview trap

Bẫy: div với onClick không nhận keyboard và screen reader không đọc là nút — dùng button. Bẫy nữa: focus không trả về sau khi đóng modal khiến keyboard bắt đầu lại từ đầu trang. Và aria-live đặt trên phần tử bị unmount/mount lại liên tục sẽ không announce — vùng live phải cố định trong DOM và chỉ đổi nội dung.

Nói trong 60 giây
  • Semantic HTML trước, chỉ bù ARIA khi thiếu ngữ nghĩa.
  • Keyboard: Tab/Enter/Space/Escape, focus trap trong modal.
  • Đóng modal thì trả focus về trigger; đổi route báo bằng aria-live.
  • aria-live polite cho cập nhật, assertive chỉ cho lỗi.
  • Responsive mobile-first, tap target đủ lớn, breakpoint theo nội dung.

Q8 Testing pyramid cho FE: unit, component, MSW, e2e — test cái gì và tránh bẫy gì?

What

Kim tự tháp FE: nhiều unit test (Vitest) cho hàm thuần — format tiền, validate, reducer, parse; tầng giữa là component test với React Testing Library, render component rồi assert theo hành vi người dùng (getByRole, userEvent) thay vì theo implementation; mock network bằng MSW ở tầng HTTP; và ít e2e (Playwright) chạy luồng thật xuyên màn hình.

Why

Test theo implementation (state nội bộ, tên prop, class CSS) sẽ vỡ ngay khi refactor dù hành vi không đổi — test thành gánh nặng. RTL khuyến khích truy vấn như người dùng nên test bền và phản ánh đúng kỳ vọng. MSW giữ handler giống server thật (đúng method, path, status), nên component không bị dính chi tiết của axios/fetch và tái dùng được giữa component test và e2e. E2E chậm và giòn nên chỉ dành cho luồng sống còn.

How
Nhiều: unit test (Vitest) — logic thuần
↓
Vừa: component test (RTL) + MSW mock HTTP
↓
Ít: e2e (Playwright) — luồng critical

Luồng điển hình: render component, MSW trả response giả cho request nó gọi, chờ trạng thái hiển thị (findBy*), rồi assert bằng role/text. Ưu tiên truy vấn theo accessibility (role, label, text) vì vừa test hành vi vừa kiểm tra a11y. E2E để riêng cho login, checkout, hoặc luồng nhiều màn hình cần backend thật.

When

Unit: mọi logic có nhánh và dễ sai (tính tiền, phân trang, sắp xếp). Component test: form, danh sách có loading/empty/error, tương tác có state. MSW: mọi component có data fetching. E2E: luồng critical xuyên màn hình, smoke test sau deploy.

When NOT

Không dùng snapshot khổng lồ cho cả cây component — giòn, ai cũng bấm update, không ai đọc. Không assert class CSS hay cấu trúc DOM nội bộ. Không chạy e2e cho từng case nhỏ (chậm, flaky) và không mock module bằng vi.mock cho axios khi MSW đã mô phỏng đúng HTTP — mock module khiến test không còn kiểm tra được tầng tích hợp thật.

// Component test: hành vi, không phải implementation
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { setupServer } from 'msw/node';
import { http, HttpResponse } from 'msw';

const server = setupServer(
  http.get('/api/orders', () =>
    HttpResponse.json([{ id: '1', code: 'SO-1' }])
  )
);

beforeAll(() => server.listen());
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

it('hiển thị đơn hàng sau khi tải xong', async () => {
  render(<OrderList />);
  expect(screen.getByRole('status')).toHaveTextContent(/đang tải/i);
  expect(await screen.findByText('SO-1')).toBeInTheDocument();
});

it('lọc theo từ khoá', async () => {
  render(<OrderList />);
  await userEvent.type(screen.getByLabelText(/tìm kiếm/i), 'SO');
  expect(await screen.findAllByRole('row')).toHaveLength(1);
});
Use case

Form tạo đơn: unit test validate rule, component test cho luồng submit với MSW trả 422 để kiểm tra map lỗi ra đúng trường, và một e2e Playwright cho luồng login → tạo đơn → thấy trong danh sách.

Pitfall / Interview trap

Bẫy: test gọi getByTestId tràn lan — testId không phản ánh trải nghiệm người dùng, dùng khi thật sự không có cách truy vấn theo role/label. Bẫy nữa: await waitFor bao quanh mọi thứ gây test chậm và che lỗi; dùng findBy* cho bất đồng bộ. Cuối cùng: MSW handler sai method/path khiến test "xanh" nhưng production lỗi vì không ai gọi endpoint thật.

Nói trong 60 giây
  • Vitest cho logic thuần; RTL cho component; MSW mock HTTP; Playwright cho e2e.
  • Test hành vi theo role/label, không test implementation.
  • MSW giữ handler giống server, tái dùng được nhiều tầng.
  • E2E ít, chỉ luồng critical vì chậm và giòn.
  • Tránh snapshot lớn và assert class CSS.

Q9 Build và môi trường: Vite/Next build, biến NEXT_PUBLIC_*, build-time vs runtime config, cache/CDN, deploy SPA?

What

Vite build (esbuild/rollup) tạo output static; Next build tạo cả client bundle và server bundle. Biến có tiền tố VITE_ (Vite) hoặc NEXT_PUBLIC_ (Next) bị inline vào bundle lúc build — không phải secret runtime. Cấu hình đổi theo môi trường mà không rebuild phải lấy từ server (endpoint config, hoặc window.__ENV nhúng trong HTML). SPA deploy cần fallback route để mọi đường dẫn sâu trả về index.html.

Why

Nhầm build-time với runtime khiến mỗi lần đổi URL API phải build lại và deploy lại, hoặc tệ hơn là nhét secret vào biến client rồi thấy nó nằm trần trong bundle. Không có fallback route thì F5 trên /orders/42 trả 404 vì server tìm file tĩnh không thấy. Và cache sai (index.html bị cache lâu, asset hash bị no-cache) làm user kẹt ở bản cũ hoặc tải lại mọi thứ mỗi lần.

How
Source + env (VITE_ / NEXT_PUBLIC_)
↓ build — biến public được inline vào bundle
Assets hash tên file
index.html tham chiếu chunk
↓ deploy
CDN: asset immutable, index.html no-cache

Quy tắc cache: file có hash trong tên (chunk, ảnh) đặt Cache-Control: public, max-age=31536000, immutable; index.html để no-cache hoặc max-age ngắn để lấy được bản mới. Deploy SPA cấu hình rewrite mọi path về index.html (trừ /assets và API). Config runtime: gọi /config.json khi app khởi động hoặc SSR đọc env và truyền xuống.

When

Dùng biến build-time cho giá trị cố định theo build (tên app, sentry DSN public, bật/tắt feature ở tầng build). Dùng config runtime khi cùng một artifact phải chạy nhiều môi trường (staging/prod) hoặc khi giá trị chỉ biết sau khi deploy, ví dụ URL API đổi theo khách hàng.

When NOT

Không đặt API secret, private key, hay token trong NEXT_PUBLIC_*/VITE_* — chúng nằm trong bundle cho bất kỳ ai tải. Không cache index.html dài hạn. Không xử lý fallback trong app (catch-all route) để chữa lỗi 404 của server — phải cấu hình ở tầng host/CDN, vì request chưa tới được app.

// vercel.json — SPA fallback: mọi path trả index.html
{
  "rewrites": [{ "source": "/((?!assets/).*)", "destination": "/index.html" }],
  "headers": [
    {
      "source": "/assets/(.*)",
      "headers": [{ "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }]
    },
    {
      "source": "/index.html",
      "headers": [{ "key": "Cache-Control", "value": "no-cache" }]
    }
  ]
}
# Biến public được inline lúc build — không phải secret
VITE_API_URL=https://api.example.com npm run build   # Vite
NEXT_PUBLIC_APP_VERSION=1.4.0 next build               # Next.js

# Runtime config: đổi được không cần rebuild
curl -s https://app.example.com/config.json
Use case

Cùng một Docker image FE deploy cho nhiều khách: URL API và tenant đọc từ /config.json khi app khởi động, nên đổi cấu hình chỉ cần sửa file config trên CDN, không build lại image.

Pitfall / Interview trap

Bẫy: tin rằng NEXT_PUBLIC_* là biến môi trường runtime — đổi env rồi restart container mà app vẫn trỏ URL cũ vì giá trị đã inline từ lúc build. Bẫy nữa: deploy SPA lên object storage không bật static website/rewrite → deep link 404 dù app chạy tốt trên máy local. Cuối cùng: cache index.html quá lâu khiến user không nhận bản mới và lỗi "chunk not found" sau deploy.

Nói trong 60 giây
  • VITE_/NEXT_PUBLIC_ inline lúc build — không phải secret, không đổi được lúc runtime.
  • Config runtime qua /config.json hoặc SSR để khỏi rebuild.
  • Asset có hash: cache immutable; index.html: no-cache.
  • SPA deploy cần fallback route về index.html, cấu hình ở host/CDN.
  • Không nhét secret vào biến client.

Q10 Performance FE thực chiến: memo hoá, virtual list, lazy image, đo bằng Lighthouse/Web Vitals?

What

Tối ưu theo số đo chứ không theo cảm giác: dùng React.memo, useMemo, useCallback khi profiler cho thấy re-render đắt; virtualize danh sách dài bằng thư viện như react-window hoặc TanStack Virtual để chỉ render phần đang thấy; lazy-load ảnh và đặt width/height để tránh layout shift; và đo bằng Lighthouse, Web Vitals (LCP, INP, CLS) cùng dữ liệu field thật (RUM).

Why

Memo hoá bừa tốn bộ nhớ và thời gian so sánh props, dễ sinh bug giá trị stale vì dependency sai — nó không miễn phí. Ngược lại, render vài nghìn dòng DOM làm scroll giật và INP tệ; virtual list cắt số node xuống mức hằng số. LCP/INP/CLS là chỉ số người dùng cảm nhận được, khớp với SEO và trải nghiệm, nên là đích của tối ưu thay vì những con số trang trí.

How
Đo: Lighthouse + Web Vitals + RUM
↓ tìm bottleneck thật
Profiler: component re-render
Network: bundle, ảnh, waterfall
↓ sửa đúng chỗ
Split chunk, virtual list, lazy image, memo có chọn lọc
↓
Đo lại & so sánh trên cùng điều kiện

Trình tự thực dụng: React DevTools Profiler tìm component render lại nhiều nhất với props đổi không cần thiết; Network/coverage tìm bundle và ảnh lớn; Lighthouse trên profile mobile (CPU throttle) để biết LCP/INP/CLS. Sau mỗi thay đổi, đo lại trên cùng điều kiện — nếu không cải thiện số metric thì bỏ thay đổi đó.

When

Virtual list khi bảng/danh sách vượt khoảng vài trăm dòng hoặc hàng nghìn item. Lazy image (loading="lazy", srcset/sizes, định dạng hiện đại) cho ảnh ngoài viewport. Memo cho component render đắt hoặc list item nhận callback ổn định. Tối ưu LCP khi LCP trên 2.5s, INP khi trên 200ms.

When NOT

Không useMemo/useCallback cho tính toán rẻ hoặc cho mọi hàm — thêm chi phí và dễ sai dependency. Không React.memo cho component vốn không re-render hoặc props luôn đổi mới mỗi render (memo vô hiệu). Không virtualize danh sách ngắn vì nó phá Ctrl+F, in, và SEO nội dung; không lazy-load ảnh LCP ở đầu trang vì làm chậm chỉ số chính.

// Virtual list: chỉ render phần đang thấy
import { useVirtualizer } from '@tanstack/react-virtual';

export function OrderTable({ rows }: { rows: Order[] }) {
  const parentRef = useRef<HTMLDivElement>(null);
  const v = useVirtualizer({
    count: rows.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 44,
    overscan: 8,
  });

  return (
    <div ref={parentRef} style={{ height: 600, overflow: 'auto' }}>
      <div style={{ height: v.getTotalSize() }}>
        {v.getVirtualItems().map((item) => (
          <Row key={item.key} style={v.measureElement(item)} data={rows[item.index]} />
        ))}
      </div>
    </div>
  );
}

// Memo có chọn lọc + callback ổn định cho list item
const Row = memo(function Row({ data, onSelect }: RowProps) { /* ... */ });
// <img loading="lazy" width={640} height={360} src={url} alt={name} />
Use case

Màn hình audit log 50.000 dòng: virtual list giữ DOM ở mức vài chục node nên scroll mượt; ảnh thumbnail dùng loading="lazy" và có width/height nên CLS gần như không đổi khi cuộn.

Pitfall / Interview trap

Bẫy: useCallback nhưng vẫn truyền object/array literal mới mỗi render xuống con đã memo → memo vô hiệu. Bẫy nữa: đo LCP trên máy dev nhanh rồi kết luận sai — phải throttle CPU/network theo mobile.
