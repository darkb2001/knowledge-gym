Auth, RBAC & OAuth2

Authentication vs Authorization, RBAC/ABAC, JWT, Spring Security Filter Chain, OAuth 2.0/OIDC, service-to-service auth — deep dive phỏng vấn Backend.

Authentication & Authorization

Q1 Authentication vs Authorization?

What

Authentication (AuthN) trả lời "Bạn là ai?" — xác minh danh tính qua password, MFA, certificate, JWT signature. Authorization (AuthZ) trả lời "Bạn được làm gì?" — kiểm tra role, permission, policy trên resource cụ thể. AuthN luôn trước AuthZ: phải biết identity trước khi quyết định quyền.

Why

Tách AuthN/AuthZ giúp scale và audit: Identity Provider (Keycloak, Auth0) lo login; Resource Server lo policy. Vi phạm thứ tự → privilege escalation (authorize trước khi verify token) hoặc confused deputy (service tin header client gửi mà không verify).

How
HTTP Request
↓ Security Filter Chain
AuthN Filter
Verify JWT / Session / mTLS cert
↓ SecurityContext.setAuthentication()
AuthZ Filter / @PreAuthorize
Controller → Service

Spring: AuthenticationManager + JwtAuthenticationProvider (AuthN); AuthorizationManager + @PreAuthorize("hasAuthority('order:write')") (AuthZ).

When

Mọi protected API. AuthN tại gateway hoặc resource server. AuthZ tại service boundary — kiểm tra permission trên từng endpoint và row-level (ownerId == principal).

When NOT

Đừng nhầm "có JWT" = "được phép" — JWT chỉ là AuthN nếu chưa check scope/role. Đừng skip AuthN cho "internal API" — zero trust yêu cầu mọi hop đều verify. Public static assets không cần AuthZ nhưng vẫn có thể cần rate limit.

Authentication

  • "Who are you?"
  • Login, MFA, cert verify
  • Output: Principal + credentials
  • 401 Unauthorized nếu fail

Authorization

  • "What can you do?"
  • RBAC, ABAC, scopes
  • Output: allow/deny decision
  • 403 Forbidden nếu fail
Use case

WMS operator login → AuthN trả JWT với sub=operator42. Gọi POST /pick-tasks → AuthZ check hasRole('PICKER') + warehouse scope match. Admin gọi cùng endpoint với role ADMIN → pass.

Pitfall

401 vs 403: 401 = chưa authenticate; 403 = đã authenticate nhưng thiếu quyền. Trap: return 404 thay 403 để "hide" resource — OK cho security-by-obscurity nhưng document rõ policy.

Nói trong 60 giây
  • AuthN = who; AuthZ = what — luôn AuthN trước.
  • 401 unauthorized vs 403 forbidden.
  • Spring: AuthenticationManager vs @PreAuthorize.
  • JWT verify ≠ authorization — cần check scope/role.
  • Zero trust: internal call vẫn authenticate.

Q2 RBAC vs ABAC — roles, permissions, resource scopes?

What

RBAC (Role-Based Access Control): user được gán roles (ADMIN, PICKER); role map tới permissions (order:read, bin:write). ABAC (Attribute-Based Access Control): policy đánh giá attributes — subject (role, dept), resource (warehouseId, ownerId), action, environment (time, IP). Resource scope giới hạn role theo tenant/warehouse/region.

Why

RBAC đơn giản, dễ audit — phù hợp 80% enterprise. ABAC linh hoạt khi rule phức tạp: "PICKER chỉ sửa task trong warehouse được assign, giờ ca 6–22h". Scope tránh admin global vô tình thấy data tenant khác (multi-tenant WMS).

How
User + JWT claims
↓ RBAC: roles → permissions
hasAuthority('pick:write')
↓ ABAC / scope: match resource attrs
warehouseId ∈ user.scopes → ALLOW

Spring RBAC: @PreAuthorize("hasRole('ADMIN')"). Fine-grained: hasAuthority('order:cancel'). ABAC: custom PermissionEvaluator hoặc OPA/Rego sidecar. Scope trong JWT: "wh": ["WH-01","WH-02"].

When

RBAC: CRUD theo job function (operator, supervisor). ABAC: dynamic policy (credit limit, data residency). Scope: multi-tenant SaaS, multi-warehouse WMS.

When NOT

Đừng RBAC với 200 roles — role explosion. Đừng ABAC cho 3 rule đơn giản — over-engineering. Đừng tin client gửi X-Warehouse-Id — lấy scope từ verified token/server-side membership.

RBACABAC
ModelUser → Role → PermissionPolicy(subject, resource, action, env)
FlexibilityThấp — thêm rule = thêm roleCao — policy engine
AuditDễ — "user có role X"Phức tạp — trace policy eval
Spring@PreAuthorize, GrantedAuthorityMethodSecurityExpressionRoot custom
 
@PreAuthorize("hasAuthority('pick:confirm') and @warehouseGuard.canAccess(#taskId)")
public void confirmPick(Long taskId) { ... }

// warehouseGuard — ABAC-style scope check
public boolean canAccess(Long taskId) {
  String wh = taskRepo.findWarehouseId(taskId);
  return currentUser().getScopes().contains(wh);
}
Use case

RBAC: role SUPERVISOR có report:export. ABAC + scope: PICKER chỉ confirm task thuộc warehouse trong JWT claim wh, không thấy task warehouse khác dù biết ID.

Pitfall

Privilege escalation: user tự đổi role trong JWT nếu server không verify signature/issuer. Horizontal escalation: đổi taskId URL — phải check resource scope server-side.

Nói trong 60 giây
  • RBAC = role → permission; ABAC = policy trên attributes.
  • Resource scope = giới hạn warehouse/tenant.
  • Role explosion → chuyển permission-based RBAC.
  • Luôn verify scope server-side, không tin client header.
  • Spring: @PreAuthorize + custom PermissionEvaluator.

Session vs JWT

Q3 Session/Cookie Stateful vs JWT Stateless?

What

Stateful (Session): server lưu session (memory/Redis) với session ID trong HttpOnly cookie. Stateless (JWT): server không lưu session — client gửi signed JWT mỗi request; server verify signature + claims.

Why

Session: revoke instant (delete session), CSRF cần token nếu cookie-based. JWT: scale horizontal không cần shared session store; phù hợp microservices và mobile. Trade-off: JWT revoke khó hơn (blacklist/TTL ngắn).

How
Session flow
JWT flow
Session: Login → Set-Cookie JSESSIONID → Redis lookup mỗi request
JWT: Login → access_token → Authorization: Bearer → verify local (JWKS)
Revoke: del session key
Revoke: blacklist jti / wait exp
When

Session: server-rendered web (Thymeleaf), same-site app, cần logout instant. JWT: SPA/mobile API, microservices, cross-domain API. Hybrid: HttpOnly cookie chứa JWT (BFF pattern) — tránh XSS localStorage.

When NOT

Đừng JWT trong localStorage nếu có XSS risk. Đừng session in-memory khi scale >1 pod không sticky. Đừng JWT access token TTL 7 ngày không refresh — stolen token window quá lớn.

Session + CookieJWT Stateless
Server stateCó (Redis)Không (verify only)
RevokeInstantBlacklist / short TTL + refresh
CSRFRisk nếu cookie authÍt (Bearer header)
ScaleShared session storeDễ horizontal
Use case

WMS admin portal (SSR): session Redis + SameSite cookie. Mobile picker app: JWT access 15 phút + refresh rotation. API gateway validate JWT, forward claims downstream.

Pitfall

Sticky session che lỗi thiếu shared store. JWT "stateless" nhưng blacklist = state lại. Cookie JWT vẫn cần CSRF protection.

Nói trong 60 giây
  • Session = server state + cookie ID; JWT = self-contained signed token.
  • Session revoke dễ; JWT scale dễ.
  • Hybrid: HttpOnly cookie JWT qua BFF.
  • Tránh localStorage JWT — XSS steal.
  • Short access TTL + refresh rotation.

Q4 JWT structure, refresh rotation, blacklist/revocation?

What

JWT = header.payload.signature. Header: alg (RS256, ES256), typ JWT. Payload: claims — sub, iss, aud, exp, iat, jti, custom roles/scopes. Signature: HMAC(secret) hoặc RSA/ECDSA — verify integrity, không encrypt (payload Base64URL readable).

Why

Access token ngắn (5–15 phút) giảm stolen window. Refresh token dài hơn, opaque, rotate mỗi lần dùng — detect reuse (token theft). Blacklist jti cho logout/revoke trước expiry.

How
Login
↓ issue access (15m) + refresh (7d, opaque)
API call với access JWT
↓ 401 exp → POST /token refresh + refresh_token
Server: invalidate old refresh, issue new pair
Reuse old refresh → revoke all sessions
↓ Logout: blacklist jti (Redis TTL = exp)
Verify: signature + iss + aud + exp + !blacklist(jti)
When

Refresh rotation: production SPA/mobile. Blacklist: logout, compromise, admin revoke user. Validate aud (audience): token chỉ dùng cho API này — chống confused deputy.

When NOT

Đừng lưu password/PII trong payload. Đừng HS256 shared secret leak trong frontend. Đừng skip aud/iss validation. Đừng refresh token trong JS accessible storage.

// Verify JWT — Spring Security OAuth2 Resource Server
spring.security.oauth2.resourceserver.jwt:
  issuer-uri: https://auth.example.com/realms/wms
  audiences: wms-api   # bắt buộc aud claim

// Blacklist on logout
public void logout(String jti, Instant exp) {
  redis.setex("jwt:bl:" + jti, ttl(exp), "1");
}
Use case

Operator logout → server thêm jti vào Redis blacklist TTL = thời gian còn lại của token. Refresh reuse detection: attacker dùng stolen refresh → legitimate user refresh fail → force re-login all devices.

Pitfall

Missing audience validation: token của app A dùng gọi API B. Alg none attack: reject alg=none. Clock skew: cho phép ±60s leeway trên exp.

Nói trong 60 giây
  • JWT = header.payload.signature — payload không mã hóa.
  • Access ngắn; refresh opaque + rotate.
  • Reuse refresh → revoke family.
  • Blacklist jti cho logout; validate aud/iss/exp.
  • RS256 + JWKS preferred over HS256 in microservices.

Spring Security

Q5 Spring Security Filter Chain & SecurityContext — end-to-end?

What

FilterChain: chuỗi servlet filters xử lý security trước DispatcherServlet. SecurityContext: ThreadLocal chứa Authentication (principal, authorities) cho request hiện tại — truy cập qua SecurityContextHolder.

Why

Centralize security — controller không parse JWT thủ công. Filter order quan trọng: CORS → CSRF → Logout → JWT Bearer → Authorization. Hiểu flow = debug 401/403 và async/thread pool mất context.

How
HTTP Request
↓ DelegatingFilterProxy ("springSecurityFilterChain")
SecurityContextPersistenceFilter
BearerTokenAuthenticationFilter
↓ JwtDecoder.validate → JwtAuthenticationToken
SecurityContextHolder.setAuthentication()
↓ FilterSecurityInterceptor / AuthorizationFilter
@PreAuthorize / requestMatchers.hasRole
Controller method
↓ finally: SecurityContextPersistenceFilter clear context
When

Mọi Spring Boot REST API protected. Custom filter khi cần API key header song song JWT. @EnableMethodSecurity cho method-level AuthZ.

When NOT

Đừng parse JWT trong controller rồi vẫn dùng Filter — duplicate logic. Đừng assume SecurityContext trong @Async — propagate với DelegatingSecurityContextRunnable. Public endpoints phải permitAll() explicit.

@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
  return http
    .csrf(csrf -> csrf.disable())
    .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
    .authorizeHttpRequests(auth -> auth
      .requestMatchers("/actuator/health").permitAll()
      .requestMatchers(HttpMethod.POST, "/api/orders/**").hasAuthority("order:write")
      .anyRequest().authenticated())
    .oauth2ResourceServer(oauth -> oauth.jwt(Customizer.withDefaults()))
    .build();
}
Use case

Request GET /api/inventory + Bearer JWT → BearerTokenAuthenticationFilter decode → authorities inventory:read → FilterSecurityInterceptor allow → Controller gọi SecurityContextHolder.getContext().getAuthentication().getName() lấy operatorId.

Pitfall

Filter order sai → JWT chưa set context mà Authorization chạy. Multiple SecurityFilterChain beans — match @Order và securityMatcher. Actuator expose không auth.

Nói trong 60 giây
  • Filter chain chạy trước DispatcherServlet.
  • SecurityContext = ThreadLocal Authentication.
  • BearerTokenFilter → setAuthentication → authorize.
  • STATELESS = không HttpSession.
  • @Async cần propagate SecurityContext.

OAuth 2.0 & OIDC

Q6 OAuth 2.0 — Authorization Code + PKCE, Client Credentials, khi NOT Implicit/ROPC?

What

Authorization Code: user login tại Auth Server → redirect code → client đổi code lấy token (server-side, có client_secret). PKCE: public client (SPA/mobile) thêm code_verifier/challenge — chống intercept code. Client Credentials: machine-to-machine, không user — client_id + secret → access token.

Why

Auth Code giữ secret/token khỏi browser URL. PKCE thay thế secret cho public client. Client Credentials cho batch/cron/service account. Implicit/ROPC deprecated vì leak token và trust password qua client.

How
User
SPA/Mobile
Auth Server
Resource API
Auth Code + PKCE: generate verifier → redirect + challenge → login → code → POST token + verifier → access_token
Service A
Auth Server
Client Credentials: POST /token grant_type=client_credentials → access_token (no refresh usually)
When

Auth Code + PKCE: SPA React, mobile native. Auth Code (confidential): server-side web app. Client Credentials: inventory-sync job, service mesh egress, internal API caller.

When NOT

Implicit flow: token trong URL fragment — deprecated, dùng Auth Code + PKCE. ROPC (Resource Owner Password): app thu thập password — chỉ legacy migration, không app mới. Client Credentials khi cần user context — dùng Auth Code thay vì.

Auth Code✅Confidential (backend)✅ Recommended

  provider: keycloak
  client-id: inventory-sync
  client-secret: ${INV_SECRET}
  authorization-grant-type: client_credentials

Use case

WMS dashboard (SPA): PKCE login Keycloak. Nightly ERP sync job: Client Credentials scope erp:pull, không refresh token user.

Pitfall

Redirect URI mismatch open redirect. PKCE optional = insecure public client. Client secret trong mobile binary — extract được, bắt buộc PKCE + no secret.

Nói trong 60 giây
  • Auth Code + PKCE cho SPA/mobile — không Implicit.
  • Client Credentials cho S2S — không user context.
  • ROPC deprecated — không thu password ở client.
  • Confidential client giữ secret server-side only.
  • Token endpoint luôn HTTPS.

Q7 OIDC vs OAuth — ID token vs access token?

What

OAuth 2.0 = authorization framework — access token để gọi Resource Server API. OIDC (OpenID Connect) = identity layer trên OAuth — thêm ID Token (JWT) chứa identity claims (sub, email, name) cho Client App, không gửi tới API.

Why

Access token = permission delegate ("access API on my behalf"). ID token = proof of authentication event cho client UI (hiển thị tên, session). Dùng ID token gọi API = sai — thiếu audience/intended use; API cần access token với scope.

How
Auth Code flow + scope openid
↓ token response
ID Token (JWT) → Client parse identity
Access Token → Resource Server API
Refresh Token → secure storage
↓ OIDC discovery /.well-known/openid-configuration
Validate ID token: iss, aud, nonce, exp
When

OIDC khi cần SSO + user profile (Keycloak, Auth0, Azure AD). OAuth thuần khi chỉ delegate API access (GitHub API scope) không cần standard identity claims.

When NOT

Đừng gửi ID token tới backend API thay access token. Đừng tin ID token từ client không verify signature/nonce. Access token opaque — introspect thay decode nếu không phải JWT.

TokenAudienceMục đích
ID TokenClient App (aud = client_id)Identity — sub, email, auth_time
Access TokenResource Server (aud = api)Authorization — scopes, gọi API
Refresh TokenAuth Server onlyLấy access token mới
Use case

SPA login OIDC: ID token hiển thị "Xin chào, operator42"; access token gọi /api/pick-tasks với scope pick:read. Backend chỉ validate access token.

Pitfall

Nhầm OAuth = login protocol — OAuth là delegation; OIDC mới standardize login. Missing nonce validation → replay ID token.

Nói trong 60 giây
  • OAuth = access resource; OIDC = who is user.
  • ID token cho client; access token cho API.
  • Validate ID token: iss, aud, nonce, exp.
  • scope openid bật OIDC layer.
  • Không dùng ID token làm API bearer.

Service-to-Service Authentication

Q8 S2S auth — mTLS, JWT pass-through, Client Credentials, Gateway token exchange, service mesh?

What

Các pattern xác thực call giữa microservices: mTLS (cert mỗi service), JWT pass-through (forward user token), OAuth Client Credentials (service lấy token riêng), Gateway token exchange (RFC 8693 — đổi user token → downstream token), Service mesh identity (Istio SPIFFE/SPIRE — cert tự động mỗi pod).

Why

Zero trust: internal network không đáng tin. Mỗi pattern trade-off giữa user context propagation, ops complexity, và blast radius khi token leak.

How
Client JWT
Gateway
Svc A
Svc B
Pass-through: Gateway validate → forward Authorization header → B validates same JWT
Token exchange: Gateway/subject_token → Auth Server → audience-restricted token for B
Client Credentials: A ignores user JWT → A gets own token scoped for B
mTLS / Mesh: Envoy sidecar present client cert — identity = SPIFFE ID
When

JWT pass-through: cần user audit trail end-to-end, ít service hop.
Client Credentials: background job, không user context, B chỉ tin service A.
Token exchange: downstream cần token audience/scope khác, không tin gateway header.
mTLS / mesh: infra-level identity, encrypt transit, policy L4/L7 (Istio AuthorizationPolicy).
Kết hợp: mesh mTLS + JWT user context = defense in depth.

When NOT

Pass-through user JWT tới mọi service — token quá rộng, confused deputy. Client Credentials khi B cần biết user nào thực hiện — mất attribution. mTLS alone không thay AuthZ — cert chỉ prove service identity. Tin X-User-Id header không signed.

PatternUser contextComplexityBest for
JWT pass-through✅ FullThấp2–3 services, same IdP
Client Credentials❌ Service onlyThấpBatch, internal sync
Token exchange✅ MappedTrung bìnhMulti-audience, zero trust
mTLS / mesh❌ TransportCao (ops)K8s, regulated, encrypt all hops
Use case

OrderService → InventoryService: pass-through user JWT để audit "operator42 reserved bin". Nightly sync OrderService → ERP: Client Credentials. Bank-grade: Istio mTLS + token exchange per downstream API audience.

Pitfall

Confused deputy: Service A nhận user token, gọi B với token đó — B phải validate aud= B, không chỉ signature. Gateway set X-User-Id không verify → spoof.

Nói trong 60 giây
  • Pass-through giữ user context; Client Credentials cho machine.
  • Token exchange đổi audience — RFC 8693.
  • mTLS/mesh = transport identity, không thay JWT AuthZ.
  • Zero trust: mTLS + scoped token.
  • Không tin unsigned internal headers.

Q9 API Key vs OAuth vs mTLS cho internal APIs?

What

API Key: static secret trong header (X-API-Key) identify caller. OAuth: dynamic token với scope, expiry, rotation (Client Credentials / token exchange). mTLS: client certificate xác thực TLS layer — không phải HTTP header.

Why

API Key đơn giản cho partner ít, low-risk internal webhook. OAuth chuẩn hóa lifecycle, scope, audit. mTLS mạnh nhất về transport identity — key không traverse application layer.

How

API Key

  • Static, long-lived
  • Header/query
  • Rotate manual
  • No standard scope

OAuth CC

  • Short-lived JWT
  • Bearer token
  • Auto refresh/issue
  • Scope-based AuthZ

mTLS

  • Cert per service
  • TLS handshake
  • Auto rotate (mesh)
  • Network + app policy
When

API Key: dev sandbox, single partner webhook, cron nội bộ isolated VLAN (vẫn nên rotate). OAuth: production microservices, multi-tenant, cần scope/revoke. mTLS: service mesh, PCI/HIPAA, east-west traffic encrypt + identity.

When NOT

API Key trong browser/mobile — leak dễ. OAuth cho script 1 lần — overkill dùng Key. mTLS cho public internet client — không issue cert cho user. Chỉ API Key không HTTPS — sniff plaintext.

Use case

PLC webhook nội bộ VLAN: API Key + IP allowlist. Microservice inventory: OAuth Client Credentials. K8s cluster east-west: Istio STRICT mTLS + AuthorizationPolicy.

Pitfall

API Key trong git repo. Shared key mọi service — không audit được caller. mTLS terminate tại gateway rồi plain HTTP internal — mất protection hop cuối.

Nói trong 60 giây
  • API Key = simple static — rotate khó.
  • OAuth = scoped, expiring tokens.
  • mTLS = cert identity at TLS layer.
  • Production internal → OAuth or mTLS.
  • Defense in depth: mTLS + OAuth.

Spring Microservice Calls

Q10 Securing microservice calls — WebClient + OAuth2 client?

What

Spring Security OAuth2 Client tự lấy và cache access token (Client Credentials hoặc on-behalf-of). ServletOAuth2AuthorizedClientExchangeFilterFunction / reactive equivalent attach Bearer token vào WebClient outbound calls. @RegisteredOAuth2AuthorizedClient inject authorized client vào controller/service method.

Why

Tránh hardcode token, tự refresh trước expiry, centralize client registration trong YAML. Pass-through user token: dùng OAuth2AuthorizedClientManager với authorization_code context hoặc forward SecurityContext JWT.

How
OrderService
↓ WebClient + OAuth2AuthorizedClientManager
Token endpoint (client_credentials)
↓ cache token → Authorization: Bearer
InventoryService API
When

Client Credentials cho S2S không user. Custom filter để forward incoming JWT khi cần user context. @RegisteredOAuth2AuthorizedClient("inventory-api") trong method cần explicit client.

When NOT

Đừng new WebClient mỗi request không share filter — mất cache token. Đừng log full access token. Blocking RestTemplate without OAuth2 support — prefer WebClient + oauth2 client starter.

@Configuration
class WebClientConfig {
  @Bean
  WebClient inventoryClient(
      OAuth2AuthorizedClientManager manager) {
    ServletOAuth2AuthorizedClientExchangeFilterFunction oauth2 =
        new ServletOAuth2AuthorizedClientExchangeFilterFunction(manager);
    oauth2.setDefaultClientRegistrationId("inventory-api");
    return WebClient.builder()
        .baseUrl("https://inventory.internal")
        .apply(oauth2.oauth2Configuration())
        .build();
  }
}

// Pass-through user JWT (alternative)
WebClient.builder()
  .filter((req, next) -> {
    Authentication auth = SecurityContextHolder.getContext().getAuthentication();
    if (auth instanceof JwtAuthenticationToken jwt) {
      return next.exchange(
        ClientRequest.from(req).header("Authorization", "Bearer " + jwt.getToken().getTokenValue()).build());
    }
    return next.exchange(req);
  }).build();
Use case

OrderService gọi InventoryService: WebClient với client_credentials registration inventory-api, scope inventory:reserve. Token cache trong AuthorizedClientService — auto refresh.

Pitfall

Quên @EnableWebSecurity + oauth2 client config → 401 loop. Blocking call trong reactive chain — block() trên WebClient cẩn thận thread. Client secret trong config map không Vault.

Nói trong 60 giây
  • WebClient + OAuth2AuthorizedClientExchangeFilterFunction.
  • Client Credentials auto cache/refresh token.
  • Pass-through: copy JWT từ SecurityContext.
  • @RegisteredOAuth2AuthorizedClient inject client.
  • Không hardcode Bearer token.

Common Pitfalls

Q11 Pitfalls — JWT localStorage XSS, missing aud, confused deputy, privilege escalation?

What

Bốn lỗi security phổ biến: (1) JWT trong localStorage → XSS steal token; (2) không validate aud (audience) → token reuse cross-service; (3) confused deputy — service A dùng user token gọi B, B không check audience; (4) privilege escalation — user sửa claims/role hoặc IDOR bypass AuthZ.

Why

Interviewers test thực chiến — biết flow OAuth chưa đủ nếu mắc các lỗi implementation. OWASP API Security Top 10: BOLA (Broken Object Level Authorization) = privilege escalation phổ biến nhất.

How
XSS → document.cookie/localStorage → steal JWT
↓ Mitigate: HttpOnly cookie + CSP + sanitize input
Token aud=api-a used on api-b
↓ Mitigate: resource server validate aud claim
Svc A forwards any Bearer to Svc B
↓ Mitigate: token exchange OR B validates aud + scope
GET /orders/999 as user owning order 1

Deep Dive — OAuth 2.0 Authorization Code + PKCE

Q12 Authorization Code + PKCE — luồng đầy đủ, code_verifier/challenge, khi nào bắt buộc?

What

Authorization Code: client redirect user tới Authorization Endpoint; user login + consent; server redirect code ngắn hạn về redirect_uri; client đổi code ở Token Endpoint lấy access/refresh token. PKCE (RFC 7636) thêm code_verifier (chuỗi ngẫu nhiên 43–128 ký tự) và code_challenge = BASE64URL(SHA256(code_verifier)) gửi kèm authorization request; khi đổi token client gửi lại verifier để server đối chiếu.

Why

Authorization code đi qua front channel (redirect browser hoặc custom URI scheme) nên có thể bị app độc hại intercept. PKCE bind code với phiên của client gốc — kẻ chỉ có code mà không có verifier thì không đổi được token. RFC 9700: public client MUST dùng PKCE, authorization server MUST hỗ trợ; confidential client RECOMMENDED dùng để defense-in-depth. Method plain lộ verifier nên phải dùng S256.

How
Client: tạo code_verifier → tính code_challenge
↓ GET /authorize?response_type=code&code_challenge=...&code_challenge_method=S256&state=...
Auth Server: user login + consent, bind challenge vào code
↓ 302 redirect_uri?code=...&state=...
Client: POST /token grant_type=authorization_code&code=...&code_verifier=...
↓ server verify S256(verifier) == challenge
Trả access_token (ngắn hạn) + refresh_token (xoay vòng)
Tham sốGửi ở đâuGiá trị
code_verifierToken request43–128 ký tự ngẫu nhiên, entropy ≥ 256-bit
code_challengeAuthorization requestBASE64URL(SHA256(verifier)), bỏ padding
code_challenge_methodAuthorization requestS256 (bắt buộc dùng, không dùng plain)
stateCả haiChống CSRF — đối chiếu khi redirect về

    .encodeToString(randomBytes(32));            // 43 ký tự

When

When NOT

Client Credentials (machine-to-machine) không có code để bind nên không dùng PKCE. Không dùng Implicit (response_type=token) hay ROPC — RFC 9700/OAuth 2.1 đã bỏ các flow này. Không nhúng client_secret vào public client (extractable).

Use case

SPA dashboard login qua Keycloak/OIDC: sinh verifier trong storage phiên, redirect authorize, callback đổi code + verifier lấy access token — kẻ cài app trùng custom scheme cũng không đổi được code.

Pitfall / Interview trap

redirect_uri phải khớp chính xác (không wildcard mở → open redirect). Server hỗ trợ PKCE nhưng không enforce → kẻ tấn công strip code_challenge tạo downgrade. Không fallback từ S256 sang plain khi S256 lỗi.

Deep Dive — JWKS & Xoay khoá ký JWT

Q13 JWKS, kid và xoay khoá ký JWT không downtime — resource server verify thế nào?

What

JWKS (JSON Web Key Set, RFC 7517) là tài liệu JSON công bố public key(s) của authorization server, thường ở /.well-known/jwks.json. Mỗi JWT có header kid (key id) chỉ định key nào dùng để verify chữ ký. Resource server không giữ private key — chỉ tải public key qua JWKS và chọn đúng key theo kid.

Why

Xoay khoá định kỳ thu hẹp cửa sổ nếu private key bị lộ (kẻ có private key ký được token giả mạo). Nhưng xoay sai cách gây "sóng 401": key mới ký trước khi mọi verifier biết, hoặc gỡ key cũ khi token cũ còn hạn. JWKS cho phép nhiều key cùng tồn tại nên rotation diễn ra êm.

How
1. Sinh cặp khoá mới (kid mới)
↓ 2. Công bố public key mới vào JWKS (chờ ≥ 1 cache TTL)
3. Chuyển signing sang khoá mới — token cũ vẫn verify bằng khoá cũ
↓ 4. Chờ overlap = token TTL + JWKS cache TTL + clock skew
5. Gỡ public key cũ khỏi JWKS
Bước verifierHành vi đúng
Cache JWKSBounded theo Cache-Control, thường 5–15 phút — không vô hạn
Chọn keyTheo kid trong header — không thử lần lượt mọi key
Gặp kid lạRefetch JWKS một lần, rate-limited (cooldown) rồi mới từ chối
AlgorithmWhitelist RS256/ES256; từ chối alg=none, confusion RS→HS

When

Mọi hệ dùng asymmetric signing (RS256/ES256) với OIDC provider (Keycloak, Auth0, Entra ID, Cognito). Emergency rotation khi nghi private key lộ: gỡ key compromised ngay, chấp nhận buộc mọi phiên re-authenticate.

When NOT

HS256 dùng chung secret không phù hợp JWKS — mọi verifier giữ secret đều ký được token. Không hardcode một public key đơn lẻ (không xoay được). Không đặt max-age JWKS quá dài — kéo dài overlap và làm chậm phản ứng khi gỡ key.

Use case

Inventory API validate JWT từ Keycloak: cache JWKS 10 phút; khi Keycloak xoay khoá, token mới mang kid lạ → refetch một lần, verify thành công — không cần restart service, không có 401 hàng loạt.

Pitfall / Interview trap

Algorithm confusion: verifier nhận HS256 rồi dùng public key RSA làm HMAC secret → kẻ tấn công tự ký token giả. kid phải duy nhất trên toàn bộ lịch sử key. Refetch không rate-limit → bị tấn công làm ngập JWKS endpoint.

Deep Dive — Cookie bảo mật & CSRF

Q14 HttpOnly / Secure / SameSite — đặt cờ cookie thế nào và lưu token ở đâu cho an toàn?

What

Cờ cookie bảo mật: HttpOnly — JavaScript không đọc được (chống XSS đánh cắp); Secure — chỉ gửi qua HTTPS; SameSite=Strict|Lax|None — giới hạn gửi cookie trong request cross-site (chống CSRF); prefix __Host- — bắt buộc Secure, Path=/, không Domain. Nơi lưu token: HttpOnly cookie vs localStorage vs in-memory/BFF.

Why

JWT trong localStorage bị mọi XSS đọc được → token bị đánh cắp. Chuyển sang HttpOnly cookie chặn XSS đọc token nhưng mở lại nguy cơ CSRF (browser tự gửi cookie). Lựa chọn storage là trade-off giữa XSS và CSRF; SameSite + CSRF token giải quyết lớp CSRF.

How

HttpOnly cookie (BFF)

  • JS không đọc — chống XSS steal
  • Cần chống CSRF (SameSite + token)
  • Logout/revoke tập trung

localStorage

  • XSS đọc được token
  • Không tự gửi — ít CSRF
  • Không revoke được phía server

In-memory (SPA)

  • Mất khi refresh tab
  • Vẫn dính XSS nếu script chạy
  • Ghép refresh cookie HttpOnly

When NOT

Không đặt SameSite=None mà thiếu Secure (bị browser từ chối). Không lưu token dài hạn trong localStorage khi có bề mặt XSS. Bearer token trong header thuần (không cookie) thì CSRF ít liên quan — không cần CSRF token nhưng vẫn phải chống XSS.

Use case

Admin console server-rendered: session Redis qua cookie __Host-session HttpOnly + SameSite=Lax; mỗi form POST kèm CSRF token; logout xoá session server-side là revoke tức thời.

Pitfall / Interview trap

SameSite=Lax mặc định vẫn gửi cookie ở top-level navigation GET → không đủ chặn mọi CSRF; cần CSRF token cho thao tác thay đổi trạng thái. Secure không bảo vệ khỏi XSS đọc giá trị cookie nếu thiếu HttpOnly. Đừng "fix" XSS bằng cách đổi sang sessionStorage — vẫn JS-readable.

Bổ sung chiều sâu phỏng vấn

Filter vs HandlerInterceptor: JWT nằm ở đâu trong request chain?

What

Servlet Filter chạy quanh servlet chain trước Spring MVC; HandlerInterceptor chạy quanh handler đã được MVC chọn. Xác thực JWT nên ở Spring Security filter chain, không dựa vào MVC interceptor như hàng rào bảo mật duy nhất.

Boundary và thứ tự

Container filters → DelegatingFilterProxy → FilterChainProxy → SecurityFilterChain phù hợp → DispatcherServlet → HandlerMapping → interceptor.preHandle → controller → postHandle/afterCompletion. Chỉ SecurityFilterChain đầu tiên match request được dùng; filter order phải dựa vào authentication/authorization flow, không đoán theo tên class.

JWT

Ưu tiên OAuth2 Resource Server với BearerTokenAuthenticationFilter/JwtDecoder; validate signature, thuật toán cho phép, expiry, issuer và audience theo policy. Authentication phải được dựng trước AuthorizationFilter. Invalid/missing credential xử lý 401 khi tài nguyên cần auth; đã auth nhưng thiếu quyền thường là 403. Không chỉ decode Base64 rồi tin claim.

Dùng đúng công cụ

Filter phù hợp CORS, correlation ID, wrapper request/response và security. Interceptor biết HandlerMethod và annotation, phù hợp timing hoặc context MVC; không bao phủ mọi servlet/static/dispatch theo cùng cách nên không dùng thay security. Method security bổ sung kiểm tra quyền ở service boundary.

Async/error và cleanup

OncePerRequestFilter có semantics theo dispatch/thread và hook cho async/error, không phải bảo đảm duy nhất một lần toàn vòng đời request. Kiểm tra registration để custom filter không chạy hai lần qua container và security. ThreadLocal/MDC phải clear finally; async handoff không tự mang security/context. Kiểm thử preflight CORS, expired token, public route, async/error route và endpoint ngoài MVC.

HTTP → Servlet Filter / Spring Security JWT → authorization → DispatcherServlet → MVC interceptor → controller
// Resource Server cấu hình chuẩn; issuer/audience phải được cấu hình và kiểm thử.
http.authorizeHttpRequests(a -> a
    .requestMatchers("/public/**").permitAll()
    .anyRequest().authenticated())
