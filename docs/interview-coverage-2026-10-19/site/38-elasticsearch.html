Module 38

Elasticsearch cho Backend Developer

Search engine ở góc nhìn backend: mapping, analyzer, query DSL, relevance, phân trang sâu, tích hợp Spring, đồng bộ dữ liệu và vận hành cluster.

Nền tảng Indexing & Analysis

Q1 Inverted index là gì, vì sao ES tìm text nhanh hơn LIKE của SQL?

What

Inverted index (chỉ mục nghịch đảo) ánh xạ mỗi term đã phân tích sang danh sách document chứa nó (posting list). Thay vì lưu document rồi quét nội dung mỗi lần query, ES tra thẳng posting list của term, nên tìm text nhanh hơn nhiều so với LIKE '%kw%' phải full scan từng row.

Why

LIKE '%kw%' có wildcard ở đầu nên không dùng được B-tree index → engine phải đọc mọi row và so chuỗi con, chi phí O(n) theo số row và tăng tuyến tính. Inverted index tra theo term (đã chuẩn hóa) nên gần như không phụ thuộc số document, lại ghép được nhiều term bằng boolean và có sẵn relevance score mà SQL không có.

How
Document gốc (text)
Analyzer: tokenizer + filter
↓ phân tích thành các term đã chuẩn hóa (lowercase, bỏ dấu, bỏ stopword)
Inverted index: term → posting list (doc id, vị trí)
↓ query được phân tích cùng analyzer
Tra posting list, giao/ hợp các tập doc, chấm BM25
Rank & trả kết quả

Chi phí nằm ở phía ghi: mỗi document mới phải analyze, cập nhật posting list, tạo segment (immutable) và merge segment về sau. Đây là write amplification — ghi vào ES luôn đắt hơn ghi một row SQL, còn đọc full-text thì rẻ hơn nhiều.

When

Full-text search sản phẩm (tên + mô tả), tìm log theo message, search-as-you-type, autocomplete, và các màn hình vừa filter vừa sort trên tập dữ liệu lớn mà SQL LIKE chậm.

When NOT

Không dùng ES thay lookup theo khoá chính của OLTP (một SELECT theo PK đã nhanh sẵn). Không dùng khi cần join, FK, transaction nhiều bảng. Cũng đừng kỳ vọng match chuỗi con giữa từ (%abc%) vì inverted index tách theo token — muốn vậy phải dùng wildcard, regexp hoặc n-gram tốn kém.

{
  "document": { "title": "Ao thun nam cotton" },
  "inverted_index": {
    "ao":     [1, 7, 12],
    "thun":   [1, 7],
    "nam":    [1, 3, 9],
    "cotton": [1, 12]
  },
  "query": { "match": { "title": "ao" } },
  "tra_cuu": "terminverted_index['ao'] → [1, 7, 12]"
}
Use case

Ô tìm kiếm sản phẩm: người dùng gõ "ao thun" và cần match cả "Áo Thun", "áo polo" theo từ, sắp xếp theo relevance — thứ mà một câu LIKE '%ao thun%' không làm nổi khi bảng lên hàng triệu row.

Pitfall / Interview trap

Câu "ES nhanh hơn SQL mọi query" là SAI: ES nhanh hơn cho full-text/scan-filter theo term, nhưng ghi và update đắt hơn, gần như không hỗ trợ transaction. Bẫy nữa: inverted index không index chuỗi con giữa từ. Và ES là near real-time — document vừa ghi chưa refresh thì chưa tìm thấy ngay.

Nói trong 60 giây
  • Inverted index = term → posting list, tra theo token.
  • SQL LIKE '%kw%' full scan vì wildcard đầu khoá.
  • Đọc rẻ, ghi đắt: analyze + segment + merge.
  • Có boolean + relevance scoring, SQL không có.
  • Không phải chỗ thay OLTP lookup theo PK.

Q2 Mapping & dynamic mapping: text vs keyword, vì sao khai mapping tường minh?

What

Mapping là schema của index: khai báo từng field và kiểu dữ liệu (text, keyword, long, date, boolean, object, nested, geo_point...). Dynamic mapping là cơ chế ES tự suy kiểu khi gặp field mới ở document đầu tiên; muốn kiểm soát chặt thì khai mapping tường minh và đặt dynamic: strict để từ chối document chứa field lạ.

Why

Kiểu đoán sai thì query, sort và aggregation đều sai: số điện thoại hay mã bưu chính bị đoán thành long (mất số 0 đầu), chuỗi ngày thành text (không range được), và mỗi field lạ thêm vào lại làm nở mapping (mapping explosion — thường vì dữ liệu kiểu key động). Khai tường minh giữ schema ổn định, còn text vs keyword quyết định field đó có được phân tích để full-text hay chỉ dùng filter/sort/aggregate.

How
Index document lần đầu
↓ field đã có trong mapping?
Có → dùng kiểu đã khai
Chưa có → dynamic mapping suy kiểu
↓ kiểm soát bằng dynamic
true: tự thêm field
false: bỏ qua field lạ
strict: reject document
KiểuPhân tích?Dùng cho
textCó (analyzer cắt thành token)Full-text search: tên, mô tả, nội dung
keywordKhông (nguyên giá trị)Filter, sort, aggregation: status, category, id, tag
When

Mọi index production nên khai mapping tường minh trong template hoặc file cấu hình. Field vừa cần search vừa cần sort/agg thì khai text kèm sub-field keyword (multi-field) để phục vụ cả hai.

When NOT

Dynamic mapping tiện cho prototype hoặc index log ngắn hạn bạn sẽ xoá, nhưng không dùng dynamic: true cho index nhận payload đa dạng từ client. Cũng đừng để sẵn dynamic rồi sau đó mới thêm field — mapping đã chốt kiểu thì không sửa tại chỗ được, phải tạo index mới.

PUT /products
{
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "id":        { "type": "keyword" },
      "name":      { "type": "text",
                     "fields": { "raw": { "type": "keyword" } } },
      "category":  { "type": "keyword" },
      "price":     { "type": "scaled_float", "scaling_factor": 100 },
      "createdAt": { "type": "date" },
      "active":    { "type": "boolean" }
    }
  }
}
Use case

Field name dùng text để search từ, nhưng sort theo tên chữ cái hoặc aggregation theo tên dùng name.raw (keyword). Filter category bằng term trên category (keyword) thay vì trên text.

Pitfall / Interview trap

Sort/aggregate trên field text sẽ lỗi hoặc buộc bật fielddata — rất tốn heap, hay bị hỏi. Keyword mặc định bị cắt bởi ignore_above (256) với chuỗi dài. Và đặt dynamic: strict rồi quên thêm field mới sẽ làm toàn bộ bulk index fail.

Nói trong 60 giây
  • Mapping = schema, khai tường minh là best practice.
  • text: phân tích, cho full-text search.
  • keyword: nguyên giá trị, cho filter/sort/agg.
  • Multi-field text + keyword khi cần cả hai.
  • dynamic: strict chặn field lạ và mapping explosion.

Q3 Analysis pipeline: analyzer, tokenizer, filter và custom analyzer cho tiếng Việt?

What

Analysis pipeline là chuỗi xử lý biến text thành các term: char filter (tuỳ chọn) rồi tokenizer (cắt thành token) rồi token filter (lowercase, asciifolding, stop, synonym...). Pipeline chạy ở cả index time (dựng inverted index) và search time (phân tích query), nên hai phía phải cùng analyzer mới match đúng.

Why

Với tiếng Việt, analyzer mặc định không đủ: cùng một từ có nhiều cách bỏ dấu ("hoà" vs "hòa"), người dùng gõ không dấu ("ao thun") trong khi dữ liệu có dấu. Nếu index and query không được chuẩn hoá giống nhau, tìm "hoa" sẽ trượt "hoà". Cần lowercase + asciifolding để đồng nhất, và cân nhắc tokenize theo từ tiếng Việt (word segmentation) hoặc n-gram cho autocomplete.

How
Raw text
↓ char filter: html_strip, thay ký tự
Tokenizer: standard / whitespace / ngram
↓ token filter: lowercase → asciifolding → stop → synonym
Terms (tokens) → đưa vào inverted index

Với field keyword không chạy analyzer mà chạy normalizer — chỉ gồm filter, không tokenize, thường để lowercase cho mã/tag so khớp không phân biệt hoa thường.

When

Khi nội dung là tiếng Việt, cần match có dấu lẫn không dấu, cần autocomplete, hoặc khi cần synonym ("laptop" ~ "máy tính xách tay"). Chỉ định rõ analyzer trong mapping của field text.

When NOT

Không để analyzer (index time) khác search_analyzer (query time) một cách vô ý — đây là bug kinh điển khiến filter đúng mà tìm không ra. Không dùng asciifolding cho mã sản phẩm có phân biệt dấu. Và nhớ: keyword không đi qua analyzer, muốn chuẩn hoá phải dùng normalizer.

PUT /products
{
  "settings": {
    "analysis": {
      "analyzer": {
        "vi_folded": {
          "type": "custom",
          "tokenizer": "standard",
          "filter": ["lowercase", "asciifolding"]
        }
      },
      "normalizer": {
        "lower_norm": { "type": "custom", "filter": ["lowercase"] }
      }
    }
  }
}
Use case

Field name dùng analyzer vi_folded: người dùng gõ "ao thun" vẫn match document "Áo Thun Nam". Field sku là keyword dùng normalizer lower_norm để filter "abc-01" khớp "ABC-01".

Pitfall / Interview trap

Đổi analyzer của một field đã có dữ liệu KHÔNG re-index dữ liệu cũ — phải reindex (dùng _reindex). Tokenize từ ghép tiếng Việt chuẩn thường cần plugin (ví dụ ICU), đừng hứa hão là standard analyzer làm được. Bẫy nữa: gọi _analyze với analyzer search time để tự kiểm tra token trước khi tin kết quả query.

Nói trong 60 giây
  • Pipeline: char filter → tokenizer → token filter.
  • Chạy ở cả index time và search time, phải khớp nhau.
  • Tiếng Việt: lowercase + asciifolding để match không dấu.
  • keyword dùng normalizer, không dùng analyzer.
  • Đổi analyzer phải reindex — không tự áp cho dữ liệu cũ.

Query, Scoring & Phân trang

Q4 Query DSL cơ bản: match vs term vs range, bool với must/should/filter/must_not?

What

Query DSL gồm nhóm leaf query và compound query. Ba leaf hay dùng: match (phân tích query text rồi tìm theo token, có tính điểm), term (khớp chính xác, không phân tích), range (so sánh khoảng). bool ghép chúng bằng must, should, filter, must_not.

Why

Nhầm match với term là lỗi phổ biến nhất khi mới dùng ES: term trên field text hiếm khi match vì giá trị đã bị analyzer cắt thành nhiều token, còn match trên field keyword cũng không đúng kỳ vọng. Hiểu rõ cái nào tính điểm, cái nào chỉ lọc, là nền để viết query đúng và nhanh.

How
bool query
↓ phân nhánh theo vai trò
must (bắt buộc, có điểm)
should (tuỳ chọn, cộng điểm)
↓
filter (bắt buộc, 0 điểm)
must_not (loại trừ)
Leaf queryPhân tích?ĐiểmDùng cho
matchCóCóFull-text trên field text
termKhôngKhôngKhớp chính xác field keyword, số, boolean
rangeKhôngKhôngNgày, giá, số trong khoảng
When

Dùng match cho tìm text (tên, mô tả), term cho field cấu trúc (status, category, id), range cho ngày/giá, và bool để kết hợp tất cả trong một truy vấn có xếp hạng.

When NOT

Không dùng term để tìm trong field text (trừ khi hiểu rõ token). Không dùng match cho field keyword nếu bạn chỉ muốn khớp chính xác. Không đặt điều kiện lọc cấu trúc trong must — điều đó tốn tính điểm vô ích và làm lệch thứ tự kết quả.

POST /products/_search
{
  "query": {
    "bool": {
      "must":     [ { "match": { "name": "ao thun nam" } } ],
      "filter":   [ { "term":  { "category": "shirt" } },
                    { "range": { "price": { "gte": 100000, "lte": 500000 } } } ],
      "must_not": [ { "term":  { "status": "archived" } } ],
      "should":   [ { "term":  { "brand.keyword": "demo-brand" } } ],
      "minimum_should_match": 1
    }
  }
}
Use case

Màn hình danh sách sản phẩm: search theo tên (must), lọc category + khoảng giá (filter), loại sản phẩm đã ẩn (must_not), ưu tiên thương hiệu được chọn (should). Một bool gói gọn cả nhu cầu.

Pitfall / Interview trap

match mặc định ghép các token bằng OR, nên "áo thun" có thể khớp cả document chỉ chứa "áo" — dùng operator: "and" hoặc minimum_should_match khi cần AND. term chỉ khớp đúng MỘT token, không phải một chuỗi. Và should trong ngữ cảnh có must/filter chỉ cộng điểm chứ không bắt buộc trừ khi set minimum_should_match.

Nói trong 60 giây
  • match phân tích + tính điểm, cho text.
  • term không phân tích, cho keyword/number.
  • range cho khoảng ngày/số.
  • bool = must + should + filter + must_not.
  • match mặc định OR — cần AND thì set operator.

Q5 Filter context vs query context: vì sao filter nhanh hơn?

What

Query context tính _score (thường BM25) cho từng document và xếp hạng; filter context chỉ trả về đúng/sai, không tính điểm, và kết quả được cache ở tầng node. Điều kiện lọc cấu trúc như status, category hay khoảng thời gian nên đặt trong filter; chỉ phần text cần xếp hạng mới đặt trong must/should.

Why

Bỏ được bước tính điểm đồng nghĩa bỏ công tính toán cho mỗi document khớp. Quan trọng hơn, kết quả boolean của filter được cache (node query cache) nên một điều kiện lặp lại nhiều lần, ví dụ status = active, chỉ tính một lần rồi tái dùng — nhanh hơn hẳn và không tốn CPU scoring. Đặt filter đúng chỗ còn tránh việc điều kiện lọc "lẫn" vào điểm số, làm thứ tự kết quả sai lệch.

How
Query đến
↓ tách hai nhánh
must/should → tính BM25 cho mỗi doc
filter → match / không match (cache)
↓ giao hai tập kết quả
Sắp xếp theo _score (chỉ với phần query context)

Có thể bọc một leaf query vào constant_score để biến nó thành filter. Dùng track_scores: false khi sort theo field và không cần điểm.

When

Mọi truy vấn có cả phần tìm kiếm lẫn phần lọc: lọc status/type/category/thời gian trong filter, tìm text trong must. Rất hay dùng cho màn hình có bộ lọc (facet) bên cạnh ô search, và cho phân quyền/tách theo tenant.

When NOT

Không đưa vào filter những điều kiện bạn muốn cộng điểm (ví dụ ưu tiên thương hiệu, ưu tiên hàng mới) — filter không ảnh hưởng thứ tự. Và filter cache không hữu ích với điều kiện cardinality cao, giá trị khác nhau mỗi lần (như id người dùng) vì cache sẽ bị đẩy ra liên tục.

POST /products/_search
{
  "query": {
    "bool": {
      "must":   [ { "match": { "name": "ao thun" } } ],
      "filter": [
        { "term":  { "status": "active" } },
        { "range": { "createdAt": { "gte": "now-30d/d" } } }
      ]
    }
  },
  "track_scores": false
}
Use case

Dashboard tìm đơn: người dùng search theo mã/tên khách (must), đồng thời lọc theo trạng thái đơn và khoảng ngày (filter). Phần lọc chạy trên cache, phần search mới tính điểm để xếp hạng liên quan.

Pitfall / Interview trap

Đưa match của một điều kiện lọc thuần vào must vừa tốn CPU vừa làm loãng điểm số, khiến relevance bị lệch. Ngược lại, đặt vào filter một điều kiện mà bạn cần nó cộng điểm thì kết quả sẽ không như ý. Nhớ nêu điểm chính khi được hỏi: filter = no scoring + cache.

Nói trong 60 giây
  • Query context: có _score, dùng để xếp hạng.
  • Filter context: chỉ đúng/sai, 0 điểm, có cache.
  • Filter nhanh hơn vì bỏ scoring + tái dùng cache.
  • Điều kiện cấu trúc → filter; phần text cần xếp hạng → must.
  • track_scores=false khi sort theo field.

Q6 Phân trang: from/size, giới hạn max_result_window, search_after và PIT khi export?

What

from/size là phân trang cổ điển nhưng phải thu thập và sắp xếp from + size document trên mỗi shard nên càng lật sâu càng tốn, và bị chặn bởi index.max_result_window (mặc định 10000). search_after lật theo con trỏ sort key (thường kèm PIT) cho pagination sâu; scroll phù hợp export/batch một lần.

Why

Với from/size, mỗi shard phải giữ và sort from + size document rồi coordinator merge lại — from càng lớn thì bộ nhớ và CPU càng tăng, nên ES đặt trần max_result_window. search_after không cần đếm từ đầu: nó dùng giá trị sort của document cuối làm con trỏ, chi phí gần như không đổi dù lật tới trang rất sâu. PIT (point-in-time) giữ một "khung nhìn" nhất quán để các trang không bị nhảy khi index đang thay đổi.

How
Trang sâu (from/size) → chặn ở max_result_window
↓ thay bằng con trỏ
Mở PIT → query với search_after + sort key duy nhất
↓ lấy sort value cuối trang làm điểm bắt đầu trang sau
Lặp tới hết → đóng PIT

Export toàn bộ dữ liệu: mở PIT, lặp search_after với size vừa phải, dùng _shard_doc hoặc một tiebreaker duy nhất làm khoá sort. Scroll cũng làm được nhưng tốn context trên cluster và không thấy document mới.

When

Phân trang UI vài trang đầu: from/size là đủ và đơn giản. Infinite scroll hoặc "xem thêm" sâu: search_after + PIT. Export báo cáo, đổ dữ liệu sang hệ khác, batch: PIT + search_after (hoặc scroll).

When NOT

Đừng tăng max_result_window để "chữa" deep pagination — nó chỉ đẩy vấn đề về bộ nhớ đi xa hơn. search_after không cho nhảy tới trang bất kỳ (chỉ tiến tuần tự) và cần sort key duy nhất; sort theo score mà không có tiebreaker sẽ lặp/thiếu bản ghi. Không dùng scroll cho UI realtime.

POST /products/_search
{
  "size": 20,
  "query": { "match": { "name": "ao thun" } },
  "sort": [
    { "price": "asc" },
    { "id": "asc" }
  ],
  "search_after": [300000, "prod-500"],
  "track_total_hits": false
}
Use case

Màn hình "tải thêm" sản phẩm: giữ PIT, gửi search_after là mảng sort value của bản ghi cuối cùng. Job export cuối ngày cũng dùng cùng cơ chế với size lớn dần thay vì từng lô from tăng dần.

Pitfall / Interview trap

Bẫy kinh điển: sort chỉ theo _score rồi search_after → bản ghi trùng hoặc mất. Phải thêm tiebreaker duy nhất (_id hoặc field unique). Chú ý PIT tiêu tốn tài nguyên nên phải close/hết hạn; và track_total_hits: false giúp bỏ chi phí đếm tổng khi không cần hiển thị tổng số.

Nói trong 60 giây
  • from/size tốn dần theo độ sâu, trần 10000.
  • search_after = con trỏ sort, chi phí gần như hằng số.
  • PIT giữ khung nhìn nhất quán giữa các trang.
  • Sort cần tiebreaker duy nhất khi dùng search_after.
  • Scroll/PIT cho export, không cho UI realtime.

Q7 Relevance: BM25, boost, multi_match, function_score và explain API?

What

Relevance là mức độ liên quan quyết định thứ tự kết quả. ES mặc định chấm bằng BM25 (dựa trên tần suất term, độ hiếm IDF và độ dài trường), có thể điều chỉnh bằng boost, multi_match và function_score, và gỡ rối bằng explain API để xem chi tiết điểm số từng document.

Why

BM25 khác TF-IDF ở chỗ làm bão hoà tần suất (term xuất hiện 100 lần không đắt hơn nhiều lần 10) và chuẩn hoá theo độ dài trường, nên document ngắn gọn thường được ưu tiên hợp lý. Hiểu cơ chế giúp chọn đúng cách kết hợp nhiều field và biết khi nào nên vứt bỏ điểm để sort theo field (giá, ngày) — vừa nhanh vừa ổn định.

How
Query text
↓ match/ multi_match trên nhiều field, có boost (name^3)
Điểm BM25 cho từng field → kết hợp theo best/most/cross fields
↓ function_score chỉnh điểm (recency, popularity)
Sắp theo _score → trả kết quả

multi_match mặc định best_fields (lấy điểm field cao nhất); most_fields cộng điểm nhiều field; cross_fields coi nhiều field như một. function_score thêm hàm như gauss theo ngày để ưu tiên hàng mới.

When

Ranking thương mại điện tử (tên quan trọng hơn mô tả), ưu tiên sản phẩm mới/bán chạy bằng function_score, tinh chỉnh trọng số theo kết quả thực tế. Dùng explain: true khi kết quả bất ngờ để xem vì sao một document được điểm cao.

When NOT

Không dùng _score khi người dùng muốn sort theo giá/thời gian — vừa tốn CPU vừa vô nghĩa, hãy sort theo field (và track_scores: false). Không nhồi quá nhiều function lồng nhau tới mức không debug nổi. Đừng coi _score là con số tuyệt đối so sánh giữa các truy vấn khác nhau.

{
  "query": {
    "function_score": {
      "query": {
        "multi_match": {
          "query": "ao thun",
          "fields": ["name^3", "description"]
        }
      },
      "functions": [
        { "gauss": { "createdAt": {
            "origin": "now", "scale": "30d", "decay": 0.5 } } }
      ],
      "score_mode": "sum",
      "boost_mode": "multiply"
    }
  },
  "explain": true
}
Use case

Sàn thương mại: match tên sản phẩm với trọng số cao, rồi function_score cộng thêm điểm cho sản phẩm mới trong 30 ngày. Khi kết quả đứng đầu bất thường, bật explain để đọc phần đóng góp điểm của từng field.

Pitfall / Interview trap

IDF được tính theo shard, nên điểm có thể khác nhau giữa các lần chia shard — đừng dựa vào con số tuyệt đối. Nhầm best_fields với most_fields là bẫy hay gặp trong phỏng vấn. Và nhớ: khi sort theo field, việc tính _score là lãng phí — tắt đi.

Nói trong 60 giây
  • Mặc định BM25: tf bão hoà, idf, chuẩn hoá độ dài.
  • boost field, multi_match (best/most/cross).
  • function_score cho recency/popularity.
  • explain API để xem cách tính điểm.
  • Sort theo field thì bỏ _score.

Q8 Tích hợp Spring: Spring Data Elasticsearch, mapping entity, khoá version khi update, xử lý khi cluster down?

What

Spring Data Elasticsearch cung cấp hai mức: ElasticsearchRepository cho CRUD đơn giản và ElasticsearchOperations/ElasticsearchClient cho query DSL linh hoạt. Entity gắn @Document, @Id, @Field; cập nhật đồng thời dùng @Version (dựa trên _seq_no/_primary_term) để chặn lost update; khi cluster down phải degrade chứ không làm sập app.

Why

Repository tiện cho CRUD nhưng nhanh chóng bí khi cần bool, aggregation hay function_score — lúc đó cần operations/client. Về concurrency: hai request cùng đọc rồi ghi một document sẽ ghi đè nhau, nên ES dùng optimistic concurrency qua cặp _seq_no + _primary_term. Về lỗi: ES là hệ phụ trợ, nếu search chết mà app vẫn bán hàng được thì phải degrade (trả kết quả rỗng có báo, dùng fallback DB), không để exception ES làm hỏng luồng chính.

How
Service
ElasticsearchRepository / Operations
↓ ghi kèm version (_seq_no, _primary_term)
Cluster OK → ACK
Cluster down / conflict → xử lý
↓
Conflict → retry; Down → fallback / xếp hàng retry

Cấu hình client bean theo phiên bản (RestClient/ElasticsearchClient + JSON mapper). Khi ghi cần set SeqNoPrimaryTerm để ES bác bỏ update cũ, và bắt exception lỗi kết nối để fallback.

When

Microservice search hoặc read-model: API tra cứu đọc từ ES, index được nuôi từ luồng sự kiện. Dùng @Version cho document có cập nhật đồng thời (tồn kho hiển thị, trạng thái đơn). Dùng repository cho CRUD, chuyển sang operations khi query ĐSL phức tạp.

When NOT

Không dùng ES làm primary datastore cần transaction nhiều bước (đặt hàng + trừ kho + ghi sổ) — không có ACID như DB quan hệ. Không bỏ qua version khi update read-modify-write, sẽ lost update âm thầm. Và đừng để lỗi ES ném thẳng ra tầng API làm sập luồng nghiệp vụ chính.

@Document(indexName = "products")
public class Product {
  @Id private String id;
  @Field(type = FieldType.Text, analyzer = "vi_folded")
  private String name;
  @Field(type = FieldType.Keyword) private String category;
  @Version private Long version; // map _seq_no + _primary_term
}

public void update(Product p) {
  try {
    repo.save(p);                    // upsert idempotent
  } catch (DataAccessResourceFailureException ex) {
    log.warn("ES down, fallback");
    retryQueue.enqueue(p.getId());   // không chặn luồng chính
  }
}
Use case

API tra cứu sản phẩm: repository cho get/save, operations cho query bool + aggregation. Khi ES tạm down, endpoint search trả về thông báo "tạm thời không khả dụng" và luồng đặt hàng vẫn chạy bình thường.

Pitfall / Interview trap

@Version của Spring Data ES khác @Version JPA — nó dựa trên _seq_no/_primary_term, không phải cột số trong DB, dễ bị hỏi. Bẫy nữa: test ghi xong đọc ngay có thể không thấy vì chưa refresh (dùng refresh(true) trong test). Và nhớ phân biệt save() (index toàn bộ document, ghi đè) với update() theo script (chỉ sửa field).

Nói trong 60 giây
  • Repository cho CRUD, operations/client cho query phức tạp.
  • @Document/@Id/@Field map entity.
  • @Version = optimistic concurrency theo _seq_no.
  • Cluster down → degrade/fallback, không sập app.
  • ES không phải primary datastore giao dịch.

Q9 Đồng bộ DB → ES: dual write vs outbox/CDC, reindex alias swap, thứ tự sự kiện?

What

Đồng bộ DB sang ES có hai hướng: dual write (code ghi cả DB lẫn ES) và outbox/CDC (ghi DB rồi phát sự kiện qua bảng outbox hoặc transaction log để relay sang ES). DB là source of truth, ES chỉ là read model; reindex không downtime bằng cách dựng index mới rồi atomic swap qua alias.

Why

Dual write dễ mất nhất quán: DB commit xong nhưng ghi ES thất bại (mạng, cluster down) thì hai bên lệch nhau, mà không có transaction chung để rollback — đây là lý do phải ưu tiên outbox/CDC. Outbox ghi sự kiện cùng transaction với thay đổi DB, rồi một tiến trình relay đẩy sang ES, đảm bảo at-least-once; phía tiêu thụ phải idempotent. Reindex qua alias cho phép đổi mapping/analyzer mà người dùng không thấy gián đoạn, và cần quản lý thứ tự sự kiện để update cũ không ghi đè update mới.

How
App
DB (source of truth) + outbox (cùng TX)
↓ relay poll bảng outbox hoặc đọc transaction log (CDC)
Đẩy sang ES qua alias "products"
↓ reindex: dựng products_v2 → verify → atomic swap alias
products_v2 phục vụ, xoá products_v1

Chống lệch thứ tự: gắn external version (hoặc timestamp) cho mỗi lần ghi để ES từ chối document có version cũ hơn; relay xử lý trùng bằng upsert idempotent.

When

Read model cho search, dashboard tổng hợp, hoặc bất cứ khi nào cần truy vấn full-text/filter linh hoạt trên dữ liệu gốc nằm trong DB quan hệ. Cần reindex khi đổi mapping, đổi analyzer, hoặc muốn rebuild để dọn phân mảnh.

When NOT

Không dùng dual write khi có tải ghi cao hoặc nhiều hệ đích — sẽ nhanh chóng lệch và khó gỡ. Không reindex thẳng vào index đang phục vụ. Và app phải query qua alias, nếu hard-code tên index thật thì swap vô nghĩa. Đừng coi ES là nguồn sự thật để xử lý nghiệp vụ.

@Transactional
public void updateProduct(Product p) {
  productRepo.save(p);                                // DB source of truth
  outboxRepo.save(new OutboxEvent(          // cùng transaction
      "product", p.getId(), "UPDATE", toJson(p)));
}

@Scheduled(fixedDelay = 1000)
public void relay() {                              // at-least-once
  for (OutboxEvent e : outboxRepo.findUnpublished(100)) {
    ops.save(toDoc(e));                             // upsert idempotent
    outboxRepo.markPublished(e.getId());
  }
}
Use case

Đổi mapping thêm sub-field keyword cho sort: dựng products_v2, chạy _reindex từ v1, kiểm tra số lượng và chất lượng, rồi swap alias products sang v2 — không downtime.

Pitfall / Interview trap

Bẫy hay hỏi: relay có thể gửi trùng (at-least-once) và có thể đảo thứ tự — nếu không dùng external version, một update cũ về sau sẽ ghi đè update mới. Nhớ nêu ba thứ: idempotent upsert, quản lý version/thứ tự, và swap qua alias (không query vào index thật).

Nói trong 60 giây
  • Dual write dễ lệch — ưu tiên outbox/CDC.
  • Outbox ghi cùng TX DB, relay at-least-once.
  • Consumer idempotent + external version chống out-of-order.
  • Reindex sang index mới rồi swap alias atomically.
  • App query qua alias, DB là source of truth.

Q10 Vận hành: shard/replica, refresh_interval, mapping explosion, disk watermark, cluster health và khi nào KHÔNG nên dùng ES?

What

Vận hành ES: shard là đơn vị lưu trữ và chạy song song, replica là bản sao cho failover và tăng read; refresh_interval (mặc định 1s) quyết định độ trễ thấy document mới; disk watermark theo phần trăm dung lượng có thể chuyển index sang read-only; cluster health green/yellow/red phản ánh tình trạng shard. ES không phù hợp làm datastore giao dịch chính.

Why

Hiểu các khái niệm này để tránh lỗi vận hành: quá nhiều shard nhỏ làm tăng overhead và chậm cluster (_oversharding_); yellow nghĩa là primary đủ nhưng chưa đủ replica (chưa mất dữ liệu nhưng mất khả năng chịu lỗi); red là có primary shard chưa được gán (dữ liệu có thể đang thiếu, cần khôi phục); đầy đĩa vượt watermark làm index chuyển read-only đúng lúc cần ghi nhất. Đây là phần phân biệt người đã vận hành thật với người mới học lý thuyết.

How
Trạng tháiÝ nghĩaHệ quả
greenTất cả primary và replica đã ở trạng thái activeBình thường, đủ dự phòng
yellowPrimary active, thiếu/ chưa gán đủ replicaĐọc/ghi vẫn được, mất khả năng failover
redCó primary shard chưa được gánCó index không truy vấn được, cần khôi phục

refresh_interval ngắn (1s) = gần realtime nhưng tạo nhiều segment nhỏ; tăng lên 30s cho lúc bulk index giúp giảm tải rồi trả lại. Shard nên đủ lớn (vài chục GB) chứ không vô số shard bé xíu.

When

Dùng ES cho search, log/observability, analytics log-scale. Chọn số shard theo dung lượng dự kiến và tăng replica nếu cần HA + đọc song song. Tuning refresh_interval và dùng _bulk khi nạp dữ liệu lớn.

When NOT

KHÔNG dùng ES làm nguồn sự thật cho dữ liệu giao dịch: không transaction nhiều document, không ACID, không join/FK, ghi chỉ near real-time, và mất shard có thể mất dữ liệu nếu không dự phòng. Dữ liệu tài chính, số dư, tồn kho thật phải nằm trong DB quan hệ; ES chỉ phản chiếu để tìm kiếm.

curl -s 'localhost:9200/_cat/indices?v&h=index,health,docs.count,store.size,pri,rep'

# Tăng refresh_interval khi bulk index, trả về 1s sau đó

# Xem watermark và index đang bị read-only

Use case

Cluster bật yellow thường vì đang chạy 1 node (replica chưa gán được) — với môi trường dev chấp nhận, nhưng production cần đủ node để green. Job nạp dữ liệu lớn tạm đặt refresh_interval: 30s, sau đó trả lại 1s.

Pitfall / Interview trap

Đừng nhầm yellow = mất dữ liệu (nó chỉ thiếu replica); red mới là có primary chưa gán. Bẫy khác: mapping explosion do dynamic mapping sinh vô số field từ key động làm tràn cluster state — phải kiểm soát mapping, đặt dynamic: strict hoặc dùng flattened. Và tuyệt đối không dùng ES thay DB giao dịch rồi không có chiến lược khôi phục/backup.

Nói trong 60 giây
  • Shard = đơn vị chạy song song; replica = HA + read.
  • refresh_interval 1s gần realtime, tăng khi bulk.
  • green/yellow/red: yellow thiếu replica, red mất primary.
  • Watermark đầy đĩa → index read-only.
  • Không dùng ES làm datastore giao dịch chính.

DB → ES/Redis: giới hạn consistency, version và chống stale resurrection

What

Outbox/CDC khép lỗ hổng mất event sau DB commit nhưng không tạo atomic transaction xuyên DB, Elasticsearch và Redis. Read model vẫn có lag; consumer phải idempotent, xử lý version/tombstone và có quy trình rebuild, reconciliation.

Một nguồn sự thật

Business row và outbox cùng local transaction REQUIRED; relay at-least-once sau commit. Không ghi outbox bằng REQUIRES_NEW độc lập. CDC có thể đọc transaction log thay polling nhưng vẫn phải vận hành offset, retention, schema và bootstrap; exactly-once end-to-end không tự xuất hiện.

ES

Dùng aggregate version tăng đơn điệu, document ID ổn định; xử lý event out-of-order và delete tombstone. Wall-clock timestamp đơn thuần có clock skew/tie nên không là version đáng tin nếu không có tie-break. External version strategy phải phù hợp API được dùng và test duplicate/retry. Reindex cần snapshot + catch-up offset hoặc cơ chế replay, không chỉ copy index rồi swap alias và bỏ concurrent writes.

Redis

Cache-aside DB commit rồi DEL cache vẫn có race: reader đọc DB cũ trước commit và SET cache sau invalidation, hồi sinh stale value. TTL chỉ giới hạn thời gian stale, không chứng minh strong consistency. Dùng generation/version và atomic compare-and-set phù hợp, CDC invalidation có quan sát lag, hoặc bypass cache cho read-your-writes quan trọng. Delayed double delete chỉ giảm xác suất race, không bảo đảm tuyệt đối.

Read-your-writes và phục hồi

Response write trả dữ liệu/version DB; client có thể đọc DB cho thao tác kế tiếp hoặc chờ read-model đạt version với timeout. Nếu event tới ES thành công nhưng Redis fail, retry từng sink theo checkpoint/idempotency; không đánh dấu toàn event hoàn tất quá sớm. Theo dõi oldest outbox age, consumer lag, DLQ, mismatch count và tombstone retention.

Khi không phù hợp

Không đọc search/cache làm căn cứ final debit hoặc kiểm invariant số dư. Eventual consistency cần UX pending và SLA lag, không chỉ nói “sẽ đồng bộ”. Ví dụ ở đây là thiết kế, không phải số đo production hay lời hứa zero-loss khi mọi storage mất dữ liệu.
