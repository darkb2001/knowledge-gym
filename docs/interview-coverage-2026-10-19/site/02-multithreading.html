Process vs Thread, synchronization, thread pools, concurrent utilities, và Virtual Threads Java 21 — chủ đề phân biệt mid vs senior.

Q1 Phân biệt Process vs Thread?

What

Process là một instance chương trình đang chạy với không gian địa chỉ riêng (code segment, data, heap, stack, file descriptors). OS cấp PID và cô lập bộ nhớ — process A không đọc trực tiếp bộ nhớ process B. Thread là đơn vị thực thi nhỏ nhất bên trong process: nhiều thread chia sẻ heap, metaspace, static fields nhưng mỗi thread có stack riêng (local variables, call frames).

Why

CPU multi-core cần song song hóa. Tạo process mới cho mỗi task quá đắt (fork/exec, TLB flush, JVM startup ~giây). Thread cho phép chia sẻ dữ liệu in-memory nhanh — nhưng đổi lại phải đồng bộ hóa (race, deadlock). Hiểu ranh giới process/thread giúp chọn scale strategy và debug production (OOM heap vs thread stack overflow).

When

Chọn process (pod/container riêng) khi cần fault isolation, deploy độc lập, scale theo CPU/memory boundary. Chọn thread trong cùng JVM khi task I/O-bound, cần chia sẻ cache/in-memory state, latency thấp giữa các task (request handling, async job).

When NOT

Đừng spawn process mới cho mỗi HTTP request — overhead khổng lồ. Đừng tạo unbounded platform threads (10k thread = 10GB stack) — dùng pool hoặc virtual threads. Đừng assume "thread crash = app vẫn chạy" — uncaught handler mặc định có thể kill JVM; shared heap corruption ảnh hưởng toàn process.

Pitfall
Nhầm "multi-threaded" với "multi-process" — Java luôn multi-threaded trong 1 JVM. Runtime.getRuntime().exec() spawn process con, không phải thread. ThreadLocal leak khi dùng thread pool (object không GC vì thread sống lâu).
Nói trong 60 giây

  • Java = 1 JVM process, nhiều threads; scale ngang = nhiều pod.
  • Platform thread ~1MB stack; virtual thread cho I/O-bound hàng nghìn concurrent.

Q2 Phân biệt Runnable vs Callable?

What

Runnable là functional interface (void run()) đóng gói task không trả về kết quả — fire-and-forget. Callable<V> là task có return type (V call() throws Exception) — tích hợp với Future<V> để lấy kết quả hoặc exception sau khi hoàn thành.

Why

Thread pool cần abstraction tách "cái gì chạy" khỏi "thread nào chạy". Runnable đủ cho logging, cache invalidation, event publish. Callable cần khi caller phải biết kết quả (query DB, gọi API) hoặc propagate checked exception — execute() nuốt exception nếu không có handler.

Runnable

  • void run() — không return
  • Checked exception phải wrap (RuntimeException)
  • Thread.start(r) hoặc executor.execute(r)
  • Lambda: () -> { ... }

Callable<V>

  • V call() throws Exception
  • Checked exception propagate qua Future
  • executor.submit(callable) → Future<V>
  • Nền tảng CompletableFuture.supplyAsync()

How

ExecutorService.execute(runnable) trả void — không biết khi nào xong. submit(callable) trả Future — get() block chờ, get(timeout) tránh treo vô hạn. Callable lambda: () -> service.fetch(). Runnable có thể wrap Callable qua Executors.callable(runnable, result).

ExecutorService pool = Executors.newFixedThreadPool(4);

// Runnable — fire-and-forget, không cần kết quả
pool.execute(() -> auditLog.info("order created"));

// Callable — cần kết quả + checked exception
Future<BigDecimal> future = pool.submit(() -> {
  Connection conn = dataSource.getConnection(); // throws SQLException
  return pricingService.calculate(conn, orderId);
});

try {
  BigDecimal price = future.get(5, TimeUnit.SECONDS);
} catch (ExecutionException e) {
  Throwable cause = e.getCause(); // SQLException gốc
} catch (TimeoutException e) {
  future.cancel(true);
}
When

Dùng Runnable cho side-effect không cần return: ghi log, gửi metric, invalidate cache, fire event. Dùng Callable khi caller cần kết quả, compose nhiều task (invokeAll), hoặc handle checked exception qua Future chain.

When NOT

Đừng dùng Callable cho mọi task chỉ để "an toàn exception" — overhead Future không cần thiết. Đừng execute() rồi expect kết quả qua shared variable (race). Đừng block future.get() trên request thread nếu có thể dùng CompletableFuture async pipeline.

Use case — Parallel inventory check
Submit 3 Callable (warehouse A, B, C) qua invokeAll, tổng hợp stock. Runnable cho fire-and-forget: publish Kafka event sau khi pick confirmed — caller không cần đợi ack.
Pitfall
execute(runnable) exception chỉ log qua UncaughtExceptionHandler — dễ miss trong production. Callable exception wrap trong ExecutionException — phải getCause() mới thấy lỗi gốc. submit(runnable) trả Future<?> null — dùng khi cần cancel, không phải lấy result.
Nói trong 60 giây
  • Runnable = void, fire-and-forget; Callable = có return + throws Exception.
  • execute() vs submit() — submit trả Future để get result/cancel.
  • Callable exception → ExecutionException.getCause().
  • CompletableFuture.supplyAsync dùng Callable-style lambda.

Q3 Phân biệt wait(), sleep() và join()?

What

wait() (Object) đưa thread vào wait-set của monitor, nhả lock, chờ notify()/notifyAll(). sleep(ms) (Thread) tạm dừng thread theo thời gian cố định, giữ lock nếu đang trong synchronized. join() (Thread) block caller cho đến khi target thread terminate — không liên quan monitor lock.

Why

Producer-Consumer cần condition wait có điều kiện (queue empty/full) — wait/notify là primitive coordination. sleep chỉ delay đơn thuần, không signal thread khác. join đồng bộ lifecycle: main thread chờ worker hoàn thành trước khi shutdown hoặc aggregate kết quả.

How

wait() bắt buộc trong synchronized(obj) trên cùng monitor — nếu không → IllegalMonitorStateException. Pattern: while (condition) obj.wait() (không dùng if — spurious wakeup). Producer: synchronized { queue.add(); notifyAll(); }. join() tương đương while (thread.isAlive()) thread.join() — prefer join(timeout) tránh treo vô hạn.

// wait/notify — bounded buffer
synchronized (lock) {
  while (queue.isEmpty()) {
    lock.wait(); // nhả lock, vào wait-set
  }
  Task task = queue.poll();
}
synchronized (lock) {
  queue.offer(task);
  lock.notifyAll(); // đánh thức consumer đang wait
}

Thread.sleep(1000); // delay thuần — KHÔNG release lock

worker.start();
worker.join(30, TimeUnit.SECONDS); // chờ worker, có timeout
When

wait/notify khi tự implement lock/condition (legacy code, interview). Production prefer BlockingQueue, ReentrantLock.newCondition(), CountDownLatch. sleep cho retry backoff, test/demo. join khi cần đợi thread spawn hoàn thành trước bước tiếp (shutdown hook, parallel batch nhỏ).

When NOT

Đừng sleep thay wait trong Producer-Consumer — busy-wait hoặc miss signal. Đừng wait ngoài synchronized — crash ngay. Đừng notify thay notifyAll khi nhiều condition trên cùng monitor (lost signal). Đừng join trên request thread production — block throughput; dùng Future/CompletableFuture.

Use case — PLC polling loop
Worker thread poll sensor: sleep(100) giữa mỗi lần đọc (rate limit). Shutdown: main gọi worker.join(5s) trước khi close connection. Event-driven buffer dùng BlockingQueue.take() thay wait/notify thủ công.
Pitfall
sleep trong synchronized block giữ lock → các thread khác BLOCKED toàn bộ thời gian sleep. wait với if thay while → spurious wakeup consume item không tồn tại. join self (thread.join() trên chính nó) → deadlock vĩnh viễn.
Nói trong 60 giây
  • wait = nhả lock, chờ notify; sleep = giữ lock, chờ timer; join = chờ thread chết.
  • wait phải trong synchronized + while loop (spurious wakeup).
  • sleep không phải coordination — không đánh thức thread khác.
  • Production: BlockingQueue/Latch thay wait/notify thủ công.

Q4 Race Condition là gì? Cách phòng chống?

What

Race Condition (data race / logical race) xảy ra khi ≥2 thread truy cập shared mutable state mà ít nhất 1 thread ghi, và kết quả phụ thuộc thứ tự thực thi không xác định (non-deterministic). Pattern phổ biến: check-then-act (if balance >= amount then deduct) và read-modify-write (count++ = 3 bytecode ops).

Why

JVM không đảm bảo atomicity cho compound operations. count++ thực tế: READ → ADD 1 → WRITE — 2 thread interleave → lost update (1000 threads increment → kết quả < 1000). CPU cache per-core làm visibility cũng sai nếu không có happens-before. Bug race hiếm reproduce → "works on my machine", fail production under load.

How

Phát hiện: code review shared mutable field + multi-thread access. Fix theo scope: single counter → AtomicInteger; multi-field invariant → synchronized block; high contention map → ConcurrentHashMap.compute(). Test: stress test nhiều thread, Thread.sleep(0) tăng interleave, ThreadSanitizer (native) hoặc JCStress (Java).

// ❌ Race: check-then-act không atomic
if (inventory.get(sku) >= qty) {   // T1,T2 cùng pass check
  inventory.put(sku, inventory.get(sku) - qty); // oversell!
}

// ✅ synchronized — bảo vệ cả check + act
synchronized (inventory) {
  int current = inventory.get(sku);
  if (current >= qty) inventory.put(sku, current - qty);
}

// ✅ AtomicInteger — counter đơn giản
private final AtomicInteger hits = new AtomicInteger();
hits.incrementAndGet();

// ✅ ConcurrentHashMap.compute — atomic per-key
inventory.compute(sku, (k, v) -> v >= qty ? v - qty : v);
When

Luôn audit khi có shared mutable state + thread pool / async. Ưu tiên immutability và concurrent collections trước lock thô. Dùng DB optimistic lock (@Version) cho inventory/order — JVM sync không đủ khi multi-instance.

When NOT

Đừng synchronized mọi method "cho chắc" — deadlock + performance hit. Đừng dùng volatile cho i++ — chỉ visibility, không atomicity. Đừng assume ConcurrentHashMap thread-safe cho compound ops cross-key (transfer A→B vẫn race). Đừng fix race bằng Thread.sleep — timing-dependent, không deterministic.

Use case — Pick task counter
Metric totalPicks dùng AtomicLong — nhiều worker thread increment song song. Inventory deduct dùng DB UPDATE ... WHERE qty >= ? (optimistic) hoặc SELECT FOR UPDATE — không chỉ synchronized in-memory khi có 2 pod.
Pitfall
"Collections.synchronizedMap" thread-safe cho single op nhưng if (!map.containsKey(k)) map.put(k,v) vẫn race — cần sync bên ngoài hoặc putIfAbsent. volatile không fix compound ops. Race bug intermittent — log thiếu, cần metric anomaly detection (count mismatch).
Nói trong 60 giây
  • Race = shared mutable + concurrent access → kết quả non-deterministic.
  • count++ là 3 bước — volatile không đủ, cần sync/Atomic.
  • Fix hierarchy: immutable → confinement → concurrent util → lock.
  • Multi-instance: JVM sync không đủ — cần DB lock hoặc distributed lock.

Q5 So sánh volatile vs synchronized?

What

volatile là keyword JMM (Java Memory Model) đảm bảo visibility — mọi thread đọc biến volatile thấy giá trị mới nhất sau write, nhờ flush/invalidate CPU cache và cấm reorder quanh volatile access. synchronized là monitor lock (intrinsic lock) trên object — đảm bảo cả visibility lẫn atomicity cho toàn bộ critical section (compound operations).

Why

Multi-core CPU cache biến shared variable thành bản copy per-core → thread A ghi running=false nhưng thread B vẫn thấy true (stale read). Compiler/CPU có thể reorder instruction nếu không có happens-before. counter++ là 3 bước (read → increment → write) — volatile không làm compound operation atomic.

volatile

  • Visibility: ✅ write happens-before read
  • Atomicity: ❌ chỉ single read/write
  • Blocking: ❌ non-blocking
  • Overhead: thấp — không acquire lock

synchronized

  • Visibility: ✅ unlock → lock tiếp theo
  • Atomicity: ✅ cả critical section
  • Blocking: ✅ mutual exclusion
  • Overhead: cao hơn — contention, context switch
How

JMM happens-before rules: (1) volatile write → volatile read cùng biến; (2) unlock monitor M → lock M tiếp theo. synchronized có thể dùng trên method (this) hoặc block (synchronized(obj)). Reentrant — cùng thread lock lại được.

// ✅ volatile — shutdown flag, publish-once reference
private volatile boolean running = true;
private volatile Config config; // immutable swap reference

// ❌ volatile KHÔNG atomic cho compound op
private volatile int counter = 0;
void bad() { counter++; } // vẫn race!

// ✅ synchronized — check-then-act, read-modify-write
private int balance;
synchronized void transfer(int amount) {
  if (balance >= amount) balance -= amount; // atomic + visible
}

// ✅ hoặc AtomicInteger khi chỉ cần counter
private final AtomicInteger hits = new AtomicInteger();
When

Dùng volatile cho status flag (shutdown, initialized), double-checked locking (kết hợp immutable object), publish reference một lần. Dùng synchronized cho invariant nhiều biến, check-then-act, read-modify-write, bảo vệ collection không thread-safe.

When NOT

Đừng dùng volatile cho i++, lazy init mutable object, hoặc logic nhiều bước phụ thuộc nhau. Đừng synchronized cho mọi biến đơn — overhead không cần thiết; prefer Atomic* hoặc concurrent collections. Không thay synchronized bằng volatile “cho nhanh” khi cần atomicity.

Use case — WCS task dispatcher
Worker thread poll task: volatile boolean running để main thread signal shutdown ngay lập tức. Cập nhật inventory (qty -= pickedQty + validate) cần synchronized hoặc DB optimistic lock — volatile không đủ.
Pitfall
“volatile đảm bảo thread-safe” — SAI. Chỉ visibility, không atomicity. Interview trap: volatile int x; x++ vẫn lost update. Nói rõ: visibility ≠ atomicity.
Nói trong 60 giây
  • volatile = visibility only; synchronized = visibility + atomicity + mutual exclusion.
  • volatile cho flag/reference publish; synchronized cho compound ops (check-then-act).
  • counter++ cần synchronized, AtomicInteger, hoặc Lock — volatile không đủ.
  • Happens-before: volatile write→read; unlock→lock trên cùng monitor.

Q6 So sánh synchronized vs ReentrantLock?

What

Cả synchronized (intrinsic/monitor lock) và ReentrantLock (java.util.concurrent) đều cung cấp mutual exclusion + visibility + atomicity cho critical section. ReentrantLock là explicit lock API — bạn tự lock()/unlock(), hỗ trợ thêm fairness, tryLock, interruptible lock, và nhiều Condition.

Why

synchronized đơn giản, JVM optimize (biased locking, lock coarsening). Nhưng không fair queue, không tryLock timeout, chỉ 1 wait-set (wait/notify). ReentrantLock cho control chi tiết khi cần tránh deadlock (tryLock + backoff), fair scheduling, hoặc nhiều condition variables — đặc biệt quan trọng với Virtual Threads (tránh pinning).

How

ReentrantLock pattern bắt buộc: acquire trong try, release trong finally. Fair lock queue theo thứ tự request — giảm starvation nhưng throughput thấp hơn. tryLock(timeout) trả false thay vì block vô hạn — dùng cho deadlock avoidance.

private final ReentrantLock lock = new ReentrantLock(true); // fair
private final Condition notEmpty = lock.newCondition();

// Producer-Consumer với 2 Condition
void consume() throws InterruptedException {
  lock.lock();
  try {
    while (queue.isEmpty()) notEmpty.await();
    queue.poll();
  } finally { lock.unlock(); }
}

// tryLock — tránh deadlock: không acquire được thì backoff
ReentrantLock lock1 = ..., lock2 = ...;
if (lock1.tryLock(200, TimeUnit.MILLISECONDS)) {
  try {
    if (lock2.tryLock(200, TimeUnit.MILLISECONDS)) {
      try { /* transfer funds */ }
      finally { lock2.unlock(); }
    }
  } finally { lock1.unlock(); }
}
When

Default: synchronized — code ngắn, ít bug (auto unlock). Chọn ReentrantLock khi cần fair queue, tryLock/timeout, lockInterruptibly, nhiều Condition (custom bounded buffer), hoặc code chạy trên Virtual Threads (tránh pinning synchronized).

When NOT

Đừng ReentrantLock cho mọi method — boilerplate, quên unlock = bug nghiêm trọng. Đừng fair lock khi throughput quan trọng hơn latency công bằng. Đừng tryLock mà không có retry/backoff strategy. Không dùng Lock thay concurrent collection khi built-in đã đủ (ConcurrentHashMap).

Use case — PLC command sequencer
Fair ReentrantLock cho conveyor segment access — AGV chờ theo FIFO, tránh starvation. tryLock(500ms) khi 2 zone cần lock cross — timeout → log alert thay vì deadlock silent.
Pitfall
Quên unlock() trong finally → lock leak, toàn bộ threads BLOCKED. Fair lock ≠ deadlock-free — vẫn cần lock ordering. Virtual Thread + synchronized = pinning risk — monitor bằng -Djdk.tracePinnedThreads=full.
Nói trong 60 giây
  • Cả hai đều visibility + atomicity; khác ở API và tính năng nâng cao.
  • synchronized = simple, auto unlock; ReentrantLock = fair, tryLock, Conditions.
  • tryLock + timeout là công cụ phòng deadlock thực tế.
  • Virtual Threads: prefer ReentrantLock over synchronized (pinning).

Q7 Deadlock — 4 điều kiện, phòng tránh, điều tra production?

What

Deadlock là trạng thái vĩnh viễn: ≥2 thread mỗi thread giữ ít nhất 1 resource (lock) và chờ resource do thread khác giữ — không ai tiến được. Wait-for graph (đồ thị chờ): node = thread, cạnh T1→T2 nghĩa là T1 chờ lock mà T2 đang giữ. Cycle trong graph = deadlock.

Why

Xảy ra khi thiết kế lock không có thứ tự cố định — Thread A lock account1 rồi account2, Thread B lock account2 rồi account1. Trong WCS/PLC: 2 crane cùng claim zone theo thứ tự ngược nhau → cả hai đứng im.

How — 4 điều kiện Coffman

Đủ cả 4 mới deadlock (phá 1 điều kiện = phòng được):

  1. Mutual exclusion: resource exclusive (lock).
  2. Hold and wait: giữ lock A, chờ lock B.
  3. No preemption: không cưỡng chế lấy lock.
  4. Circular wait: chuỗi vòng T1→T2→…→T1.

"Found Java-level deadlock"
// ❌ Deadlock — lock order ngược nhau
synchronized (lock1) {
  Thread.sleep(50);
  synchronized (lock2) { transfer(); }
}
// Thread B: synchronized(lock2) { synchronized(lock1) { ... } }

// ✅ Fix 1: lock ordering — luôn lock id nhỏ trước
Object first  = System.identityHashCode(a) < System.identityHashCode(b) ? a : b;
Object second = first == a ? b : a;
synchronized (first) {
  synchronized (second) { transfer(); }
}

// ✅ Fix 2: tryLock + timeout + backoff
if (lock1.tryLock(200, TimeUnit.MS) && lock2.tryLock(200, TimeUnit.MS)) {
  try { transfer(); } finally { lock2.unlock(); lock1.unlock(); }
}
When — Detect production

When NOT

Q9 CompletableFuture — async pipeline?

What

CompletableFuture<T> là implementation của Future hỗ trợ composition — nối chuỗi async operations bằng callback (thenApply, thenCompose, thenCombine) thay vì block thread gọi get(). Mỗi stage trả về CF mới; exception propagate qua chain hoặc xử lý bằng exceptionally/handle.

Why

Microservice thường cần gọi song song 3–5 API rồi merge kết quả. Future.get() block thread, khó timeout từng bước, khó fallback khi 1 dependency fail. CF cho phép pipeline declarative, kết hợp allOf/anyOf, và tách executor cho CPU vs I/O.

MethodVai tròAnalogy

How

supplyAsync(task, executor) submit task; callback chạy trên cùng executor (hoặc caller thread nếu stage đã complete). thenCompose dùng khi bước tiếp cũng async (gọi API khác). Luôn truyền custom Executor cho I/O — đừng để blocking call trong ForkJoinPool.commonPool().

private static final Executor IO_POOL = Executors.newFixedThreadPool(32);

CompletableFuture<OrderDetail> detail = CompletableFuture
    .supplyAsync(() -> userClient.findById(id), IO_POOL)
    .thenCompose(user -> orderClient.getSummary(user.getId()))
    .thenCombine(inventoryClient.getStock(skuId), (summary, stock) ->
        new OrderDetail(summary, stock))
    .orTimeout(3, TimeUnit.SECONDS)
    .exceptionally(ex -> OrderDetail.fallback());

CompletableFuture<Void> all = CompletableFuture.allOf(f1, f2, f3);
CompletableFuture<Object> first = CompletableFuture.anyOf(f1, f2);
When

Parallel fetch nhiều dependency (user + order + inventory), orchestration trong service layer, fan-out/fan-in trước khi trả response. Kết hợp với Virtual Threads hoặc dedicated I/O pool cho blocking HTTP/JDBC.

When NOT

Đừng dùng CF cho CPU-bound batch lớn trên common pool — starve parallelStream(). Đừng lồng quá sâu callback hell khi team quen reactive (WebFlux) hoặc structured concurrency (Java 21+). Không dùng join() trong request thread servlet blocking nếu đã có VT/reactive stack.

Use case — WCS order enrichment
Song song gọi inventory, routing, pricing API; allOf + timeout 2s; nếu pricing fail → exceptionally trả giá mặc định, vẫn ship order. Trace ID propagate qua thenApplyAsync(..., IO_POOL).
Pitfall
supplyAsync() không executor → common pool. Blocking I/O trong common pool làm chậm toàn JVM. get() sau exceptionally vẫn có thể throw nếu handler trả null không đúng contract. Quên timeout → cascade latency khi downstream chết.
Nói trong 60 giây
  • CF = Future + compose: thenApply (map), thenCompose (flatMap), thenCombine (zip).
  • allOf chờ hết, anyOf lấy cái xong trước; handle/exceptionally xử lý lỗi trong pipeline.
  • Luôn custom Executor cho I/O — common pool chỉ cho CPU ngắn.
  • orTimeout + exceptionally tránh hang khi microservice downstream fail.

Q10 CountDownLatch vs CyclicBarrier vs Semaphore vs Phaser?

What

Bốn utility trong java.util.concurrent điều phối thread không dùng lock truyền thống: CountDownLatch (1-shot countdown), CyclicBarrier (N thread rendezvous, reset được), Semaphore (permit pool), Phaser (barrier đa phase, dynamic parties). Khác nhau ở ai chờ ai, có reuse không, và có giới hạn concurrent không.

Why

Startup coordination (chờ cache warm), parallel batch phases, rate limiting resource đắt (DB connection, S3 upload), pipeline nhiều bước — cần primitive đúng semantics thay vì tự spin/wait hoặc over-use synchronized.

ClassCơ chếReuse?Use case thực tế
CountDownLatchĐếm N → 0; threads await❌ One-shotChờ N worker/cache shard ready trước khi nhận traffic
CyclicBarrierN threads chờ nhau tại barrier; optional barrier action✅ ResetParallel ETL: load → transform → export, lặp mỗi batch
Semaphoreacquire/release permit✅Max 10 concurrent export; fair queue tránh starvation
PhaserDynamic parties, multi-phase✅Simulation: thread join/leave giữa phase; fork/join style
How

Latch: 1 thread (hoặc nhiều) await cho đến khi N lần countDown(). CyclicBarrier: đúng N thread await() mới release tất cả — thread cuối có thể chạy barrier action. Semaphore: acquire() lấy permit, release() trả lại — không bắt buộc cùng thread. Phaser: register()/arriveAndAwaitAdvance() linh hoạt hơn barrier cố định.

// CountDownLatch — main chờ 3 shard cache
CountDownLatch ready = new CountDownLatch(3);
for (int i = 0; i < 3; i++)
  pool.execute(() -> { warmCache(); ready.countDown(); });
if (!ready.await(30, TimeUnit.SECONDS)) throw new TimeoutException();

// CyclicBarrier — 4 workers, phase action merge partial result
CyclicBarrier barrier = new CyclicBarrier(4, () -> mergePartialResults());

// Semaphore — max 5 DB writes
Semaphore dbSlots = new Semaphore(5, true); // fair
dbSlots.acquire();
try { db.write(data); } finally { dbSlots.release(); }
When

Latch cho one-time gate (startup, test fixture). CyclicBarrier cho lặp N-phase đồng bộ. Semaphore cho throttling concurrent access. Phaser khi số participant thay đổi giữa các phase.

When NOT

Đừng dùng Latch khi cần chạy lại — reset không được. CyclicBarrier không phù hợp “1 thread chờ N worker xong rồi tiếp” (dùng Latch). Semaphore không thay mutex cho invariant phức tạp — chỉ limit concurrency. Phaser overkill cho simple “chờ 3 API”.

Use case — Nightly warehouse report
4 zone workers xử lý song song; CyclicBarrier sau mỗi zone batch → barrier action aggregate KPI. Semaphore(3) giới hạn concurrent JDBC connection tới reporting DB.
Pitfall
Quên countDown() → Latch await vô hạn. CyclicBarrier broken: 1 thread die → tất cả BrokenBarrierException. Semaphore acquire không release trong finally → permit leak, deadlock dần. await() without timeout trong production = hang khó debug.
Nói trong 60 giây
  • Latch = one-shot countdown; CyclicBarrier = N thread rendezvous, reuse.
  • Semaphore = permit pool — rate limit, không phải mutual exclusion đầy đủ.
  • Phaser = barrier linh hoạt, dynamic parties, multi-phase.
  • Chọn theo: ai chờ ai, có lặp không, có giới hạn concurrent không.

Q11 ThreadLocal — cơ chế, use case, memory leak?

What

ThreadLocal<T> cung cấp biến per-thread — mỗi thread có bản copy riêng, đọc/ghi không cần synchronize với thread khác. JVM lưu trong Thread.threadLocals (internal map): key là ThreadLocal (weak ref), value là object user set (strong ref).

Why

Request-scoped context (traceId, tenantId, UserPrincipal) phải đi xuyên call stack mà không truyền parameter mọi method. SimpleDateFormat không thread-safe — mỗi thread 1 instance qua ThreadLocal. JDBC connection per thread trong pattern cũ (hiện prefer pool + try-with-resources).

ThreadLocal

  • Isolation per thread
  • Không lock khi access cùng thread
  • Static holder + set/get/remove wrapper
  • Phải remove() khi xong

Alternatives

  • RequestContextHolder (Spring)
  • Explicit parameter passing
  • ScopedValue (Java 21+, structured)
  • MDC trong logging (SLF4J)
How

set(value) ghi vào map của thread hiện tại. get() lazy-init nếu dùng ThreadLocal.withInitial(). remove() xóa entry — bắt buộc trong thread pool vì thread được reuse; value cũ (User, byte[], Connection) bị strong ref giữ → memory leak + data bleed sang request sau.

public final class RequestContext {
  private static final ThreadLocal<Context> CTX =
      ThreadLocal.withInitial(Context::new);

  public static void setTraceId(String id) { CTX.get().setTraceId(id); }
  public static String getTraceId() { return CTX.get().getTraceId(); }
  public static void clear() { CTX.remove(); } // BẮT BUỘC
}

// Servlet filter / Spring interceptor
try {
  RequestContext.setTraceId(traceId);
  MDC.put("traceId", traceId);
  chain.doFilter(request, response);
} finally {
  RequestContext.clear();
  MDC.clear();
}
When

Per-request metadata trong servlet + thread pool, non-thread-safe helper (DateFormat cũ), tenant routing implicit. Kết hợp filter/interceptor set ở entry, clear ở finally.

When NOT

Đừng ThreadLocal cho data cần share giữa threads. Virtual Threads + millions TL entries = overhead — cân nhắc ScopedValue. Không lưu object lớn (session, cache) — leak risk cao. Async handoff (@Async, CF) không tự propagate TL — phải copy explicit hoặc dùng Reactor context.

Use case — Multi-tenant WCS API
Filter set tenantId vào ThreadLocal; repository layer đọc để chọn schema. finally { remove() } sau mỗi request — tránh tenant A data lọt sang request tenant B trên cùng Tomcat worker thread.
Pitfall
Thread pool reuse → quên remove() = OOM + wrong tenant data. ThreadLocal key weak nhưng value strong — GC không thu value nếu thread sống. Child thread không inherit parent TL (trừ InheritableThreadLocal, dễ leak hơn). Heap dump: tìm ThreadLocalMap entries bất thường.
Nói trong 60 giây
  • ThreadLocal = biến riêng mỗi thread; không cần sync trong cùng thread.
  • Use case: traceId, tenantId, non-thread-safe formatter.
  • Thread pool: luôn remove() trong finally — leak + data bleed.
  • Async không propagate tự động; Java 21 có ScopedValue thay thế dần.

Q12 ConcurrentHashMap — CAS, compute(), merge()?

What

ConcurrentHashMap là thread-safe Map tối ưu concurrent read/write. Java 8+ bỏ segment lock: mỗi bucket dùng CAS cho insert đầu danh sách, synchronized lock node đầu khi cần update chain. Read hầu hết lock-free; write lock scope = 1 bucket.

Why

Collections.synchronizedMap lock toàn map — read cũng block. get + put riêng lẻ vẫn race (lost update). CHM cung cấp atomic compound ops: compute, merge, computeIfAbsent — 1 atomic step trên bucket, tránh check-then-act bug.

APISemanticsKhi dùng
computeIfAbsentLazy init nếu key absentCache load-from-DB
computeRead-modify-write atomicCounter object phức tạp
mergeInsert default hoặc apply remappingAggregate số (sum, max)
putIfAbsentSet nếu chưa cóDeduplication đơn giản
How

CAS thử set head node mới; fail (contention) → sync on bin head. compute* gọi remapping function trong lock bucket — function phải nhanh, không gọi lock khác (deadlock). Iterator weakly consistent — reflect state tại thời điểm iterate, không throw CME.

ConcurrentHashMap<String, LongAdder> metrics = new ConcurrentHashMap<>();

// merge — atomic increment counter per SKU
metrics.merge(skuId, 1L, Long::sum);

// computeIfAbsent — cache; mapping fn chỉ chạy 1 lần per key (per bucket lock)
Product p = cache.computeIfAbsent(id, k -> productRepo.findById(k));

// compute — update nested state atomically
cache.compute(userId, (k, profile) -> {
  if (profile == null) return new Profile();
  profile.touchLastSeen();
  return profile;
});
When

Shared cache in-memory, metrics aggregation, session store nhỏ, concurrent config map. Prefer merge/LongAdder cho counter thay get-put. computeIfAbsent cho lazy load expensive object.

When NOT

Đừng CHM làm distributed cache thay Redis — không share cross JVM. Mapping function chậm/blocking I/O trong computeIfAbsent — block bucket, giảm throughput. Không iterate + modify structural cùng lúc nếu logic phức tạp — dùng snapshot hoặc forEach. Null key/value không allowed.

Use case — Pick-path heatmap cache
ConcurrentHashMap<String, LongAdder> đếm pick frequency per aisle. Worker threads merge(aisle, 1L, Long::sum) lock-free hot path. Admin dashboard forEach snapshot — không cần external lock.
Pitfall
computeIfAbsent với DB call: nhiều thread cùng key vẫn chỉ 1 load (OK), nhưng function chậm block bucket neighbors nếu hash collision. “CHM thread-safe nên mọi compound op OK” — SAI nếu dùng get()+put() thay compute/merge. Size() là approximate under heavy write.
Nói trong 60 giây
  • Java 8+ CHM: CAS + lock per bucket head — read nhanh, write fine-grained.
  • Dùng compute/merge/computeIfAbsent — tránh get-then-put race.
  • Mapping function phải nhanh; không I/O blocking trong compute.
  • Iterator weakly consistent; null key/value không hỗ trợ.

Q13 CopyOnWriteArrayList — copy-on-write pattern?

What

CopyOnWriteArrayList (COW) implement copy-on-write: mỗi mutating op (add, set, remove) tạo bản copy mới của internal array, ghi xong rồi swap reference (volatile). Read/iterate dùng snapshot hiện tại — không lock, không ConcurrentModificationException.

Why

Listener/subscriber list: read (fire event) xảy ra hàng nghìn lần/giây, write (register/unregister) hiếm. Lock-based list làm reader chờ writer. COW đảo trade-off: write O(n) copy nhưng read lock-free, iterator snapshot-safe.

CopyOnWriteArrayList

  • Read/iterate: lock-free, rất nhanh
  • Write: copy full array O(n)
  • Iterator = snapshot cố định
  • Memory spike khi write list lớn

Collections.synchronizedList

  • Read cũng cần lock
  • Write O(1) amortized
  • Iterator cần external sync
  • Phù hợp read/write cân bằng
How

Write path: lock → copy array → mutate copy → publish reference. Read path: đọc volatile array ref, iterate trực tiếp. Element vừa add có thể chưa visible tới iterator đang chạy (snapshot cũ) — acceptable cho listener pattern.

CopyOnWriteArrayList<PickListener> listeners =
    new CopyOnWriteArrayList<>();

public void register(PickListener l) { listeners.add(l); }       // rare
public void unregister(PickListener l) { listeners.remove(l); } // rare

void onPickCompleted(PickEvent e) {
  for (PickListener l : listeners) {  // snapshot, no lock
    try { l.onPick(e); } catch (Exception ex) { log.warn("listener failed", ex); }
  }
}
When

Event listeners, config whitelist/blacklist, feature flag subscribers — read-heavy, write-rare, list size nhỏ/trung bình (< vài nghìn). Cần iterate trong lúc có thể có concurrent add/remove.

When NOT

List thay đổi liên tục (realtime order lines, buffer producer-consumer). List lớn + write thường xuyên → copy O(n) + GC pressure. Cần strong consistency “thấy ngay element vừa add trong loop hiện tại” — COW không đảm bảo.

Use case — PLC event bus
50 listeners đăng ký alarm handler; PLC fire 500 event/s — COW iterate lock-free. Admin thêm listener lúc runtime: add copy 1 lần, không block event loop.
Pitfall
Dùng COW cho list 100k item + add liên tục → CPU/GC spike. Iterator không reflect add mid-loop — design phải chấp nhận eventual visibility. removeIf cũng full copy — không “cheap” như ArrayList.
Nói trong 60 giây
  • COW = copy-on-write: write copy array, read lock-free snapshot.
  • Ideal: listener list, config — read nhiều, write hiếm.
  • Iterator snapshot-safe, không ConcurrentModificationException.
  • Tránh list lớn + write thường xuyên — O(n) mỗi mutation.

Q14 BlockingQueue — Producer-Consumer pattern?

What

BlockingQueue là queue thread-safe với blocking semantics: producer put block khi đầy (bounded), consumer take block khi rỗng. Decouple producer/consumer tốc độ khác nhau — buffer giữa hai bên, optional backpressure khi bounded.

Why

Order ingestion nhanh hơn pick worker xử lý → cần buffer tránh drop hoặc spin. Bounded queue ép producer chậm lại (backpressure) thay vì OOM với unbounded LinkedBlockingQueue. ThreadPoolExecutor dùng BlockingQueue làm work queue.

Producer: put(e) block, offer(e, timeout) timeout fallback. Consumer: take() block, poll(timeout) cho graceful shutdown. drainTo(collection) batch consumer. Poison pill pattern: gửi sentinel task để worker thoát loop.

BlockingQueue<PickTask> queue = new ArrayBlockingQueue<>(1000);

// Producer — backpressure khi queue đầy
if (!queue.offer(task, 500, TimeUnit.MS))
  throw new BackpressureException("pick queue saturated");

// Consumer pool
while (running) {
  PickTask task = queue.poll(1, TimeUnit.SECONDS);
  if (task == POISON) break;
  if (task != null) process(task);
}
When

Classic producer-consumer, worker pool handoff, rate smoothing giữa API layer và batch processor. Bounded ArrayBlockingQueue khi memory predictable quan trọng. Priority/Delay queue khi ordering/time matter.

When NOT

Đừng default LinkedBlockingQueue() unbounded trong production — burst traffic → OOM. Không dùng BlockingQueue cho request-reply sync (dùng CompletableFuture). Single-thread app không cần blocking — overhead không xứng. DelayQueue unbounded + producer nhanh = heap growth.

Use case — Order dispatch buffer
REST API enqueue pick task vào ArrayBlockingQueue(2000); 16 worker take() gửi tới WMS. Queue 90% full → metric alert, API trả 503 (backpressure) thay vì silently queue vô hạn.
Pitfall
put() vô hạn block producer khi consumer chết — cần timeout + monitoring queue size. Quên poison pill → worker hang on shutdown. PriorityBlockingQueue unbounded — low priority job có thể starve nếu high priority flood liên tục.
Nói trong 60 giây
  • BlockingQueue = producer-consumer với put/take blocking.
  • Bounded (ArrayBlockingQueue) = backpressure; unbounded = OOM risk.
  • offer/poll with timeout cho graceful degradation và shutdown.
  • ThreadPoolExecutor work queue thường là BlockingQueue implementation.

What

Why

Servlet/blocking style: 10k concurrent HTTP calls cần 10k platform threads → memory + context switch không scale. VT cho phép code blocking quen thuộc (HttpClient.send, JDBC) với chi phí per-request ~KB, không cần rewrite full reactive.

Deep Dive — Java Memory Model & happens-before

D1 Java Memory Model và quan hệ happens-before là gì? Vì sao hiểu nó quan trọng?

What

Java Memory Model (JMM, JLS §17) quy định visibility và ordering của thao tác bộ nhớ giữa các thread. Trái tim của nó là quan hệ happens-before (hb): nếu A hb B thì mọi ghi của A đều visible với B và A phải xảy ra trước B về mặt logic. JMM mô tả một tập cạnh hb; cặp thao tác không có cạnh hb nào (data race) có kết quả không xác định.

Why

CPU có cache riêng và compiler/JIT được phép reorder (đổi thứ tự) lệnh miễn là giữ đúng ngữ nghĩa trong một thread. Không có hbmắc, thread B có thể thấy giá trị stale hoặc thấy một trạng thái nửa vời. Hiểu hb cho phép bạn chứng minh code đa luồng đúng mà không phải bọc mọi thứ trong lock nặng — và giải thích được vì sao volatile, Thread.start/join, lock hay final lại tạo ra đảm bảo visibility.

How

Các cạnh happens-before cốt lõi (JLS §17.4.5): program order (trong cùng thread, lệnh trước hb lệnh sau); monitor lock (unlock hb lock kế tiếp cùng monitor); volatile (ghi volatile hb lần đọc volatile sau giá trị đó); Thread.start() hb mọi hành động trong thread mới; mọi hành động hb Thread.join() trả về; và transitivity (A hb B, B hb C ⇒ A hb C). Quy tắc final field (§17.5) đảm bảo object được publish đúng thì thread khác thấy giá trị final mà không cần đồng bộ.

1write value = 42 (ordinary)
→
2write ready = true (volatile)
⇄ hb
3read ready == true (volatile)
→
4read value — thấy 42

Vì (2) hb (3) và (1) program-order trước (2), transitivity cho (1) hb (3): đọc được ready thì chắc chắn thấy value. Đây là kỹ thuật piggybacking trên một volatile flag.

When
  • Publish một object/state bất biến qua một trường volatile thay vì khóa toàn bộ cấu trúc.
  • Dựa vào Thread.start()/join() để truyền kết quả giữa các thread (đã có hb sẵn).
  • Future.get(), CountDownLatch.await(), AtomicXxx cũng tạo hb — dùng làm điểm đồng bộ đúng nghĩa.
When NOT
  • volatile không cho atomicity: count++ vẫn race (đọc–sửa–ghi 3 bước) → dùng AtomicInteger hoặc lock.
  • volatile trên reference không bảo vệ các field mutable bên trong — cần object immutable hoặc đồng bộ.
  • Đừng dựa vào thứ tự thực thi thực tế ("nó chạy đúng trên máy tôi") thay cho một cạnh hb thật.
class Config {
    private int value;              // ordinary (non-volatile)
    private volatile boolean ready; // publication flag

    void init() {
        value = 42;      // (1) ordinary write
        ready = true;    // (2) volatile write — publishes value
    }

    int read() {
        while (!ready) { /* spin */ } // (3) volatile read, hb with (2)
        return value;                 // (4) guaranteed to see 42
    }
}
Use case

Cấu hình chỉ đọc sau khi khởi tạo, cache lazy, cờ dừng (stop flag) — publish qua volatile hoặc final. Thread.join() đủ để đảm bảo thấy kết quả của thread đã kết thúc, không cần thêm lock.

Pitfall

Khẩu quyết "volatile là thread-safe" là sai. Nguy hiểm hơn: unsafe publication khi để this escape khỏi constructor (đăng ký listener, start thread trong constructor) khiến thread khác thấy object chưa khởi tạo xong. long/double không volatile có thể bị đọc torn (§17.7).

Nguồn: JLS §17 — Threads and Locks; JLS §17.5 — Final Field Semantics.

Deep Dive — AbstractQueuedSynchronizer (AQS)

D2 AbstractQueuedSynchronizer là gì và vì sao ReentrantLock/Semaphore/CountDownLatch đều dựa trên nó?

What

AbstractQueuedSynchronizer (AQS) là framework nền tảng của java.util.concurrent cho các synchronizer: ReentrantLock, ReentrantReadWriteLock, Semaphore, CountDownLatch, FutureTask. Nó gồm hai phần: (1) một biến int state volatile cập nhật bằng CAS; (2) một wait queue FIFO (biến thể của CLH lock queue) chứa các thread đang chờ.

Why

Mọi synchronizer đều cần cùng một cơ chế "thử chiếm — nếu fail thì xếp hàng & block — khi nhả thì đánh thức thread kế". AQS đóng gói phần cơ chế đó và để subclass chỉ định nghĩa ý nghĩa của state. Nhờ vậy không phải viết lại logic queue/park trong từng class, và đảm bảo hiệu quả (enqueue lock-free bằng CAS lên tail, không dùng lock để bảo vệ queue).

How

Subclass override các phương thức tryAcquire/tryRelease (chế độ exclusive) hoặc tryAcquireShared/tryReleaseShared (shared). Ý nghĩa state do subclass quyết định; AQS dùng LockSupport.park/unpark để block/đánh thức qua Node trong queue.

// Mutex không reentrant tối giản — mô phỏng ví dụ trong javadoc AQS
final class Mutex implements Lock {
    private static final class Sync extends AbstractQueuedSynchronizer {
        protected boolean tryAcquire(int acquires) {
            if (compareAndSetState(0, 1)) {          // CAS 0 -> 1
                setExclusiveOwnerThread(Thread.currentThread());
                return true;
            }
            return false;
        }
        protected boolean tryRelease(int releases) {
            if (getState() == 0) throw new IllegalMonitorStateException();
            setExclusiveOwnerThread(null);
            setState(0);                             // mở khoá
            return true;
        }
        protected boolean isHeldExclusively() { return getState() == 1; }
    }
    private final Sync sync = new Sync();
    public void lock()   { sync.acquire(1); }
    public void unlock() { sync.release(1); }
}
Use case

Chọn ReentrantLock khi cần timeout/interruptible/fair; Semaphore để giới hạn số request đồng thời; CountDownLatch làm "cổng xuất phát" cho benchmark hoặc chờ N service sẵn sàng.

Pitfall

lock() phải luôn có unlock() trong finally, nếu không thread khác treo vĩnh viễn. Reentrancy là do subclass tự đếm trên state — viết sai sẽ tự khoá mình (self-deadlock). Fair mode (new ReentrantLock(true)) chậm hơn non-fair đáng kể.

Deep Dive — Thread-per-task vs Virtual Threads vs Reactive

D3 Khi nào dùng Virtual Threads (JDK 21), khi nào dùng Reactive (WebFlux)?

What

Ba mô hình phục vụ tải I/O-bound: thread-per-task (mỗi request một platform thread, blocking — Servlet truyền thống); reactive/asynchronous (WebFlux/Reactor: một event loop nhỏ, non-blocking, trả về Mono/Flux); và Virtual Threads (JDK 21, JEP 444): vẫn viết code blocking theo kiểu thread-per-task, nhưng thread là ảo, nhẹ, do JVM mount/unmount trên một pool carrier nhỏ.

Why

Platform thread tốn ~1 MB stack và do OS quản lý → thực tế chỉ chịu được vài nghìn thread. Reactive giữ số thread ~ số CPU nên scale tốt, nhưng code bị "colored", khó debug, và bất kỳ lời gọi blocking nào cũng có thể nghẽn event loop. Virtual Threads cho hàng trăm nghìn thread với style blocking quen thuộc, giữ nguyên JDBC/try-catch/thread dump — nên đôi khi bỏ được cả một chuyển đổi sang reactive đắt đỏ.

How

Tạo virtual thread bằng Executors.newVirtualThreadPerTaskExecutor() (không pool — mỗi task một VT mới, rất rẻ). Carrier pool mặc định là một ForkJoinPool kích thước ≈ số CPU; khi VT block trên I/O, nó unmount khỏi carrier để carrier chạy VT khác. Reactive dùng Netty event loop (số thread ≈ CPU) và bắt buộc non-blocking end-to-end; nếu phải gọi code blocking thì đẩy sang publishOn(Schedulers.boundedElastic()).

Batch DB hữu hạn: sizing CPU, Hikari và backpressure bằng số cụ thể

What

Pool xử lý batch DB phải giới hạn cả worker lẫn số task đang chờ; concurrency bị chặn bởi ngân sách connection và sức chịu tải DB, không chỉ số CPU. Chia chunk hữu hạn và đo throughput, p95, lock wait trước khi tăng song song.

Ví dụ giả định, không phải benchmark

Ví dụ thiết kế: 4 vCPU, Hikari maximumPoolSize=12; dành khoảng 8 connection cho API, 4 cho batch theo ngân sách vận hành. Pool batch cố định 4 worker, queue 8 chunk, mỗi chunk tối đa 200 bản ghi. Đây là số khởi điểm để load test, không phải công thức tối ưu. Chung một Hikari pool không cưỡng chế được phần dự trữ: muốn bảo đảm API có quota cần admission control chung hoặc datasource tách với tổng connection không vượt ngân sách DB.

CPU và DB là hai trần khác nhau

CPU-bound transform bắt đầu gần số core khả dụng; JDBC blocking có thể dùng nhiều hơn nhưng phải cap bằng connection và năng lực DB. Mỗi task một transaction/connection; không giữ connection khi gọi API ngoài. Nếu 3 replica cùng Hikari 12 thì phải tính tổng 36 connection cộng job/admin, không tune từng pod cô lập.

Backpressure ở producer

Chỉ page/keyset một chunk sau khi còn permit; không đọc triệu row vào List trước. AbortPolicy phải được bắt ở job admission để trả 429/503 hoặc retry có giới hạn, không mất task. CallerRunsPolicy chỉ phù hợp producer chuyên dụng, tránh request/event-loop thread và tránh producer giữ transaction khi chờ worker. Đừng tạo Future cho toàn bộ dataset.

Chunk và transaction

200 là ví dụ; row rộng/lock lâu thì giảm, không đồng nhất với JDBC batch_size. Một chunk một transaction giúp retry/checkpoint có giới hạn; flush/clear persistence context sau chunk, dùng idempotency hoặc unique key để retry không ghi trùng. Nếu input đổi trong lúc quét cần snapshot/high-water mark và quy tắc checkpoint rõ.

Kiểm chứng

Theo dõi active/idle/pending Hikari, queue depth, rejected count, CPU, rows/s, p95 và DB lock/WAL/I/O. Tăng worker từng bước; throughput không tăng mà wait tăng thì dừng. Đóng executor sau job; timeout/cancel không bảo đảm JDBC query đã dừng, cần query timeout và transaction timeout riêng.
