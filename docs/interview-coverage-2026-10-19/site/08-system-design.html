Q1 Thiết kế URL Shortener Service

What

URL Shortener nhận URL dài, sinh short code unique (vd go/abc12X), redirect HTTP 301/302 tới URL gốc, ghi analytics click async. Read-heavy (~100:1), scale hàng trăm triệu URL/tháng, redirect p99 <50ms.

Why

Bài toán kinh điển phỏng vấn system design: đo khả năng capacity estimation, ID generation, caching read path, analytics không block redirect. Pattern áp dụng cho mọi read-heavy lookup service.

How

Write path: validate URL → generate ID (Snowflake/counter) → Base62 encode → persist PostgreSQL + warm Redis. Read path: Redis cache-aside → miss thì DB → populate cache. Analytics: Kafka async. Custom alias: unique index, 409 nếu trùng.

// Base62 encoding — 0-9, a-z, A-Z
public class Base62Encoder {
  private static final String ALPHABET =
      "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";

  public static String encode(long id) {
    StringBuilder sb = new StringBuilder();
    while (id > 0) {
      sb.append(ALPHABET.charAt((int) (id % 62)));
      id /= 62;
    }
    return sb.reverse().toString();
  }
}

@Service
public class UrlShortenerService {
  public String createShortUrl(String longUrl) {
    long id = snowflake.nextId();
    String code = Base62Encoder.encode(id);
    urlRepo.save(new UrlMapping(code, longUrl));
    redis.set("url:" + code, longUrl, Duration.ofDays(30));
    return baseUrl + "/" + code;
  }

  public String resolve(String code) {
    String cached = redis.get("url:" + code);
    if (cached != null) return cached;
    return urlRepo.findByCode(code)
        .map(u -> { redis.set("url:" + code, u.getLongUrl()); return u.getLongUrl(); })
        .orElseThrow(() -> new NotFoundException(code));
  }
}

Prototype bit.ly nội bộ, marketing link tracking, deep link mobile app. Dùng 301 nếu SEO permanent; 302 nếu cần track mọi click.

When NOT

Không hash MD5 7 ký tự không check collision — risk trùng. Không sync analytics trong redirect path — latency spike. Không lưu URL không validate (open redirect XSS). Không dùng auto-increment sequential expose business volume.

Use case

Campaign email 10M link: 95% redirect hit Redis, 5% miss DB; Kafka ghi click geo/device không block user.

Pitfall / Interview trap

301 vs 302 trade-off; hash collision retry; TTL cache vs custom alias permanent; estimate storage 100M URL × 500B ≈ 50GB.

Nói trong 60 giây
  • URL shortener = read-heavy lookup + async analytics.
  • ID: Snowflake + Base62 hoặc counter an toàn.
  • Redis cache redirect hot path; PostgreSQL source of truth.
  • 301 SEO vs 302 track click.
  • Analytics qua Kafka, không block redirect.

Q2 Thiết kế Payment System

What

Payment System xử lý authorize/capture/refund với ACID ledger, idempotency key chống double-charge, double-entry bookkeeping (debit = credit), audit trail bất biến.

Why

Tiền không tha lỗi: retry network, duplicate webhook, race condition order status → double charge mất trust + pháp lý. Ledger bất biến là compliance bắt buộc fintech.

How

Idempotency-Key unique index → return cached result nếu retry. State machine order PENDING→AUTHORIZED→CAPTURED. SELECT FOR UPDATE lock order. Double-entry journal trong cùng TX. Outbox publish PaymentCaptured event. Reconciliation batch vs gateway settlement.

@Transactional
public PaymentResult capturePayment(CaptureRequest req) {
  // 1. Idempotency check
  Optional<Payment> existing = paymentRepo.findByIdempotencyKey(req.getKey());
  if (existing.isPresent()) return existing.get().toResult();

  // 2. Lock order — chỉ CAPTURE nếu AUTHORIZED
  Order order = orderRepo.findByIdForUpdate(req.getOrderId())
      .orElseThrow(() -> new OrderNotFoundException());
  if (order.getStatus() != OrderStatus.AUTHORIZED)
    throw new InvalidStateException(order.getStatus());

  // 3. Double-entry ledger
  ledgerService.post(JournalEntry.builder()
      .debit(Account.CUSTOMER_WALLET, req.getAmount())
      .credit(Account.MERCHANT_RECEIVABLE, req.getAmount())
      .reference(req.getOrderId())
      .build());

  Payment payment = paymentRepo.save(new Payment(req));
  order.transitionTo(OrderStatus.CAPTURED);
  outboxPublisher.publish(new PaymentCapturedEvent(payment));
  return payment.toResult();
}
When

E-commerce checkout, subscription billing, wallet transfer nội bộ. Mọi endpoint mutate balance.

When NOT

Không float/double cho tiền — dùng BigDecimal/cents long. Không DELETE ledger — chỉ reversal entry. Không capture không idempotency khi client retry. Không 2PC cross payment gateway + DB — dùng saga/outbox.

Use case

User double-click Pay: cùng Idempotency-Key → server trả paymentId cũ, không charge 2 lần.

Pitfall / Interview trap

Optimistic lock order status; reconciliation phát hiện gateway captured nhưng ledger miss.

Nói trong 60 giây
  • Payment = ACID + idempotency + double-entry ledger.
  • Idempotency-Key chống retry double-charge.
  • State machine + FOR UPDATE lock order.
  • BigDecimal/cents, không float.
  • Reconciliation hàng ngày vs gateway.

Q3 Thiết kế Order Management System (OMS)

What

OMS quản lý vòng đời đơn hàng CREATED→PAID→ALLOCATED→PICKING→SHIPPED, tích hợp inventory lock, payment, WMS fulfillment qua state machine + saga.

Why

Order cross nhiều bounded context — không global TX. State machine enforce valid transition, prevent skip PAID→SHIPPED. Inventory lock tránh oversell peak sale.

How

Enum OrderStatus + transition map. Saga orchestration: reserve stock → charge → create shipment; compensate ngược nếu fail. Optimistic UPDATE qty WHERE qty>=n hoặc pessimistic FOR UPDATE bin WMS. Outbox OrderCreated event.

public enum OrderStatus {
  CREATED, PENDING_PAYMENT, PAID, ALLOCATED, PICKING, SHIPPED, DELIVERED, CANCELLED;

  private static final Map<OrderStatus, Set<OrderStatus>> TRANSITIONS = Map.of(
      CREATED, Set.of(PENDING_PAYMENT, CANCELLED),
      PENDING_PAYMENT, Set.of(PAID, CANCELLED),
      PAID, Set.of(ALLOCATED, CANCELLED),
      ALLOCATED, Set.of(PICKING, CANCELLED),
      PICKING, Set.of(SHIPPED),
      SHIPPED, Set.of(DELIVERED)
  );

  public boolean canTransitionTo(OrderStatus next) {
    return TRANSITIONS.getOrDefault(this, Set.of()).contains(next);
  }
}

@Transactional
public void allocateInventory(Long orderId) {
  Order order = orderRepo.findByIdForUpdate(orderId).orElseThrow();
  if (!order.getStatus().canTransitionTo(OrderStatus.ALLOCATED))
    throw new InvalidTransitionException();

  for (OrderLine line : order.getLines()) {
    int updated = inventoryRepo.decrementIfAvailable(line.getSku(), line.getQty());
    if (updated == 0) throw new InsufficientStockException(line.getSku());
  }
  order.setStatus(OrderStatus.ALLOCATED);
}
When

E-commerce, B2B wholesale, WMS wave release. Flow ≥3 bước, eventual consistency chấp nhận được vài giây.

When NOT

Không cho transition tùy ý (PAID→SHIPPED skip ALLOCATED). Không lock inventory vô thời hạn — timeout release. Không sync call chain 5 service không timeout/CB.

Use case

Flash sale 10K order/phút: optimistic inventory decrement; fail → cancel order + notify user.

Pitfall / Interview trap

Saga compensate idempotent; invalid transition exception; inventory insufficient mid-saga.

Nói trong 60 giây
  • OMS = state machine + inventory lock + saga.
  • Transition map strict — không skip bước.
  • Optimistic stock decrement hoặc FOR UPDATE bin.
  • Outbox event cùng TX DB.
  • Compensate khi payment/inventory fail.

Caching & High Availability

Q5 Redis Caching — Cache-Aside, Write-Through, Write-Behind

What

Ba pattern Redis caching: Cache-Aside (app quản lý), Write-Through (write DB+cache đồng thời), Write-Behind (write cache trước, flush DB async), plus Read-Through.

Why

Read-heavy service (catalog, user profile) giảm DB load 80-95%. Chọn pattern sai → stale data hoặc mất write khi cache crash.

How

Cache-Aside: read miss → DB → set cache; write → DB → invalidate cache. Write-Through: cache layer write cả hai. Write-Behind: accept write cache, queue persist — fastest write, risk loss.

Cache-Aside (Lazy Loading)

  • App tự quản lý cache
  • Read: check cache → miss → DB → set cache
  • Write: update DB → invalidate/delete cache
  • Phổ biến nhất, linh hoạt

Write-Through

  • Write đồng thời DB + cache
  • Cache luôn fresh sau write
  • Write latency cao hơn
  • Phù hợp read-heavy, consistency quan trọng

Write-Behind (Write-Back)

  • Write cache trước, flush DB async
  • Write cực nhanh
  • Risk mất data nếu cache crash
  • Analytics, metrics, non-critical

Read-Through

  • Cache layer tự load từ DB khi miss
  • App chỉ talk to cache
  • Logic tập trung ở cache provider
  • Redis không native — cần wrapper/lib

  • Write-Through: cache luôn fresh sau write.
  • Write-Behind: nhanh nhưng risk mất data.
  • Invalidate on update, không quên.
  • Chọn pattern theo consistency requirement.

Q6 Cache Penetration, Breakdown, Avalanche

What

Ba failure mode cache: Penetration (key không tồn tại → DB flood), Breakdown (hot key expire → thundering herd), Avalanche (nhiều key expire cùng lúc).

Why

Cache không magic — miss storm có thể sụp DB dù có Redis. Production incident thường gặp khi launch hot product.

How

Penetration: cache null TTL ngắn + Bloom filter. Breakdown: single-flight mutex lock + logical TTL/async refresh. Avalanche: TTL jitter ±random, stagger refresh, multi-level cache.

Vấn đềMô tảGiải pháp
Cache Penetration Query key không tồn tại → miss liên tục → DB overload Cache null với TTL ngắn; Bloom Filter trước DB; validate input
Cache Breakdown Hot key expire → hàng nghìn request cùng hit DB Mutex lock (single flight); never expire + async refresh; logical TTL
Cache Avalanche Nhiều key expire cùng lúc → DB spike TTL jitter (base ± random); stagger refresh; multi-level cache 
// Single-flight lock chống Cache Breakdown
public Product getHotProduct(String id) {
  String key = "product:" + id;
  Product cached = redis.get(key, Product.class);
  if (cached != null) return cached;

  String lockKey = "lock:" + key;
  if (redis.setIfAbsent(lockKey, "1", Duration.ofSeconds(5))) {
    try {
      Product product = productRepo.findById(id).orElse(null);
      if (product == null) {
        redis.set(key, "NULL", Duration.ofSeconds(60)); // anti-penetration
      } else {
        int jitter = ThreadLocalRandom.current().nextInt(60);
        redis.set(key, product, Duration.ofMinutes(10).plusSeconds(jitter));
      }
      return product;
    } finally { redis.delete(lockKey); }
  }
  Thread.sleep(50); // wait for other thread
  return getHotProduct(id);
}
When

Mọi production Redis cache layer. Đặc biệt hot SKU, celebrity profile, config flag.

When NOT

Không cache null với TTL dài — attacker enumerate ID. Không single-flight lock vô hạn — deadlock. Không Bloom filter quá nhỏ — false negative vẫn hit DB.

Use case

Product ID không tồn tại bị scan: Bloom filter reject 99%; cache NULL 60s cho remainder.

Pitfall / Interview trap

Thread.sleep retry trong single-flight — dùng spin/retry limit.

Nói trong 60 giây
  • Penetration: null cache + Bloom filter.
  • Breakdown: mutex single-flight rebuild hot key.
  • Avalanche: TTL jitter tránh expire đồng loạt.
  • Hot key: never expire + async refresh.
  • Monitor cache hit rate + DB spike correlation.

Q7 High Availability & Failover

What

High Availability (HA) = hệ thống tiếp tục phục vụ khi component fail. Failover = chuyển traffic sang standby tự động (VIP/DNS promotion, K8s reschedule).

Why

SLA 99.9% = 8.7h downtime/năm max. Single point of failure (1 DB, 1 AZ, 1 Redis node) vi phạm enterprise contract.

How

App: multi-instance + LB + pod anti-affinity cross AZ. DB: primary-replica sync/async, Patroni/RDS Multi-AZ auto failover RPO<1min. Redis: Sentinel/Cluster 3+ nodes. Region: active-active hoặc active-passive DR.

Production customer-facing, payment, WCS không thể dừng line. RTO/RPO defined trong SLA.

Không HA cho dev/staging — cost. Không sync replica cross-region mọi write nếu latency critical — async replica chấp nhận lag. Không failover manual-only khi SEV1 — cần automation.

Use case

RDS Multi-AZ: primary AZ-a fail → auto promote replica AZ-b trong ~60-120s.

Pitfall / Interview trap

Split-brain nếu quorum sai; test failover bằng chaos engineering.

  • HA = no single point of failure mọi layer.
  • App multi-pod cross AZ; DB Multi-AZ; Redis Cluster.
  • Failover auto: VIP/DNS/K8s reschedule.
  • Define RPO/RTO; chaos test thực tế.
  • Design for failure: timeout+retry+CB mọi external call.

Q8 Traffic Spikes — Rate Limiting (Token Bucket / Leaky Bucket)

What

Rate limiting kiểm soát request rate: Token Bucket (cho phép burst, refill theo rate) vs Leaky Bucket (output rate cố định, smooth traffic).

Why

Traffic spike (sale, DDoS) bảo vệ downstream DB và fair quota per user/API key. Không rate limit → cascade overload.

How

Token Bucket: bucket refill tokens/sec, mỗi request consume 1. Distributed: Redis Lua script atomic decrement. Leaky Bucket: queue request, process fixed rate. K8s + HPA scale trước khi hit hard limit.

Token Bucket

  • Bucket chứa tokens, refill theo rate
  • Mỗi request consume 1 token
  • Cho phép burst (dùng token tích lũy)
  • Phổ biến: API Gateway, Guava RateLimiter

Leaky Bucket

  • Request vào bucket, xử lý đều đặn (leak)
  • Output rate cố định
  • Bucket full → reject/queue
  • Smooth traffic, không burst
TechniqueUse case
Rate limitingPer-user/API key quota (100 req/min)
Request throttlingQueue excess requests, process gradually
Load sheddingDrop low-priority requests khi overload
Auto-scalingHPA scale out trước khi rate limit hit
 
// Redis-based Token Bucket (distributed rate limit)
public boolean allowRequest(String userId, int maxTokens, int refillRate) {
  String key = "rate:" + userId;
  String lua = """
    local tokens = tonumber(redis.call('get', KEYS[1]) or ARGV[1])
    local last = tonumber(redis.call('get', KEYS[2]) or ARGV[3])
    local now = tonumber(ARGV[3])
    local elapsed = now - last
    tokens = math.min(tonumber(ARGV[1]), tokens + elapsed * tonumber(ARGV[2]))
    if tokens >= 1 then
      redis.call('set', KEYS[1], tokens - 1)
      redis.call('set', KEYS[2], now)
      return 1
    end
    return 0
    """;
  return redis.eval(lua, List.of(key, key+":ts"),
      List.of(String.valueOf(maxTokens), String.valueOf(refillRate),
              String.valueOf(System.currentTimeMillis()))) == 1;
}
  • Bucket chứa tokens, refill theo rate
  • Mỗi request consume 1 token
  • Cho phép burst (dùng token tích lũy)
  • Phổ biến: API Gateway, Guava RateLimiter
  • Request vào bucket, xử lý đều đặn (leak)
  • Output rate cố định
  • Bucket full → reject/queue
  • Smooth traffic, không burst
When

Public API per-key quota, login brute-force protection, third-party API budget. Burst-friendly: Token Bucket.

When NOT

Không rate limit internal service-to-service tin cậy — dùng bulkhead. Không leaky bucket khi cần burst hợp lệ (batch upload). Không 429 không Retry-After header — client retry storm.

Use case

Free tier 100 req/min: Token Bucket cho burst 20 request đầu giây, sau đó steady 100/min.

Pitfall / Interview trap

Distributed rate limit clock skew; per-IP vs per-user key choice.

Nói trong 60 giây
  • Token Bucket: burst OK, refill steady rate.
  • Leaky Bucket: output smooth, no burst.
  • Distributed: Redis + Lua atomic.
  • 429 + Retry-After; HPA scale proactive.
  • Per API key / user / IP tùy use case.

Health Check & Graceful Shutdown

Q9 Liveness Probe vs Readiness Probe

What

K8s Liveness probe: process còn sống? Fail → restart pod. Readiness: sẵn sàng nhận traffic? Fail → remove khỏi Service/LB, không restart. Startup: chờ app boot xong trước liveness.

Why

Rolling deploy: pod mới chưa ready không nhận traffic. Liveness sai → restart loop kill pod healthy. Readiness check dependency → flapping remove/add LB.

How

Spring Boot 3: /actuator/health/liveness, /readiness. Liveness chỉ JVM/process. Readiness include db, redis optional. K8s yaml: initialDelaySeconds, periodSeconds, failureThreshold.

@Configuration

  public CircuitBreaker paymentCircuitBreaker() {

        .failureRateThreshold(50)
        .waitDurationInOpenState(Duration.ofSeconds(30))

  @Bean

    return () -> {

      if (state == CircuitBreaker.State.OPEN)

      return Health.up().withDetail("payment-cb", state.name()).build();
    };
  }
}

Q18 Capacity estimation (back-of-envelope): QPS, storage, latency?

What

Capacity estimation là ước lượng nhanh bằng giấy nháp (back-of-envelope): từ vài giả định (DAU, requests/user/ngày, kích thước payload, thời gian lưu, replication factor) suy ra QPS trung bình & đỉnh, storage, bandwidth, memory cache và latency budget.

Why

Đây là bước đầu tiên của mọi buổi system design: nó quyết định số shard, số replica, kích thước cache, số instance. Bỏ qua dễ dẫn tới over-provision (tốn tiền) hoặc under-provision (sập khi peak).

B5: chia latency budget p99 cho số hop (client → LB → service → DB). Dùng lũy thừa 10/2 để tính nhẩm nhanh.

Q19 Consistent Hashing & Sharding / Rebalancing?

What

Chia dữ liệu ra N node (shard). Cách ngây thơ hash(key) % N khiến gần toàn bộ key phải remap mỗi khi N thay đổi. Consistent hashing hash cả key lẫn node lên một vòng tròn; key thuộc node kế tiếp theo chiều kim đồng hồ, nên chỉ khoảng K/N key phải di chuyển khi thêm/bớt node. Virtual nodes khắc phục phân bố lệch.

Why

Khi scale hoặc có node chết, ta cần thêm/bớt node mà không "cache miss toàn tập" hay shuffle lại toàn bộ dữ liệu. Đây là nền tảng của Redis Cluster, Cassandra, DynamoDB, và phân vùng của Kafka.

How

Vòng hash + tìm successor bằng binary search (TreeMap). Mỗi node vật lý đặt nhiều vnode (Cassandra mặc định 256 vnodes/node) để chia đều cung tròn. Replication factor nhân bản sang N-1 successor kế tiếp. Khi thêm node, chỉ chuyển phân đoạn bị ảnh hưởng. Chống hot partition bằng key salting, key splitting hoặc tăng số vnode.

Modulo hash

  • hash(key) % N, đơn giản
  • Đổi N remap gần như 100% key
  • Không có khái niệm vnode
  • Chỉ hợp khi N cố định

Consistent hashing

  • Key & node cùng lên vòng tròn
  • Chỉ ~K/N key đổi vị trí
  • Virtual nodes giảm lệch tải
  • Chuẩn cho cache/DB phân tán

When NOT

Q20 Quorum (R + W > N) & PACELC?

What

Với N replica: một ghi cần W replica xác nhận, một đọc cần R replica trả lời. Nếu R + W > N thì tập đọc và tập ghi luôn giao nhau ⇒ đọc thấy được ghi mới nhất. Nếu R + W ≤ N ⇒ eventual consistency. PACELC mở rộng CAP: khi có Partition chọn Availability hay Consistency, Else chọn Latency hay Consistency.

Why

Cho phép chỉnh nhất quán theo từng thao tác thay vì chọn cứng: ghi nhanh (W nhỏ) hay đọc nhanh (R nhỏ); hiểu tradeoff latency vs consistency ngay cả khi mạng bình thường — điều CAP không nói tới.

How

Chọn N/W/R theo nhu cầu. Quorum phổ biến: W = R = floor(N/2)+1. Muốn đọc/ghi nhanh có thể W=1, R=N (đọc phải hỏi mọi replica). Với eventual cần read repair, hinted handoff, anti-entropy (Merkle tree). Raft và Kafka dùng majority cho bầu leader/commit. Kafka: acks=all + min.insync.replicas=2 đảm bảo durability.

CAP

  • Chỉ nói khi có partition
  • Chọn Consistency hay Availability
  • Bỏ qua lúc mạng bình thường
  • CP (HBase) vs AP (Cassandra)

PACELC

  • If Partition: A hay C
  • Else: Latency hay Consistency
  • Ví dụ: PA/EL chỉnh per-operation

When

Khi cần tune nhất quán theo use case: ví dụ ghi số dư dùng quorum mạnh, hiển thị lượt xem dùng eventual read cho nhanh. Khi đọc/ghi phải đảm bảo thấy dữ liệu đã ghi.

When NOT

Không dùng quorum khi latency cực nhạy và chấp nhận eventual. Không tăng R,W vô ích khi độ sẵn sàng quan trọng hơn (partition xảy ra sẽ mất quorum). Không áp quorum cho hệ single-node.

Use case

Giỏ hàng cần đọc-thấy-ghi của chính user: ghi QUORUM (W=2), đọc QUORUM (R=2) trên N=3; feed xem số like dùng R=1 cho nhanh.

Pitfall / Interview trap

Nhầm "R+W>N thì luôn nhất quán tuyệt đối" (chỉ đúng cho single key, không đúng cho multi-key/transaction). Quên read repair khi để eventual. Không phân biệt N (số replica) với số node.

Nguồn: Abadi - PACELC (IEEE Computer, 2012); Apache Cassandra - Dynamo architecture; Apache Kafka documentation

  • N replica, W ghi, R đọc.

  • Ngược lại → eventual.

Redis Hash vs ZSET và rate limit sliding window atomic

What

Hash lưu các field của một object còn ZSET lưu member duy nhất kèm score để truy vấn theo thứ tự. Rate limit sliding window có thể dùng timestamp làm score và request ID làm member, nhưng prune/count/add/expire phải atomic để tránh vượt hạn mức.

Chọn cấu trúc

Hash: profile/session metadata, HSET/HGET/HINCRBY theo field, tránh HGETALL trên object lớn. TTL của key là baseline portable; field expiration phụ thuộc Redis version và client. ZSET: leaderboard, delayed queue, sliding window; ZADD thường O(log N), range trả thêm chi phí theo số phần tử. Không dùng Hash nếu cần query top/range theo score.

Thuật toán và ví dụ giả định

Ví dụ giới hạn 100 request trong 60 giây mỗi user: key rl:{userId}; loại score cũ hơn cutoff theo định nghĩa cửa sổ, ZCARD, nếu dưới 100 thì ZADD timestamp/requestId và PEXPIRE. Chạy trong Lua script hoặc server-side function để một thao tác atomic. Nếu dùng millisecond làm cả member, hai request cùng ms đè nhau khiến đếm thiếu; member phải unique.

Clock, TTL và cluster

Dùng clock thống nhất/server TIME theo triển khai, xác định biên cửa sổ chính xác và test. TTL ít nhất đủ cleanup sau window; reject có thể trả retry-after tính theo oldest member. Redis Cluster: script nhiều key cần cùng hash slot; giới hạn global qua nhiều slot/region không còn một atomic counter chung.

Trade-off vận hành

Sliding log chính xác theo các request được admit nhưng memory tăng theo số user và số entry/window, cần cap và TTL. Fixed window INCR rẻ hơn nhưng burst ở ranh giới; token bucket phù hợp burst allowance. Redis down: fail-open hay fail-closed phải do nghiệp vụ quyết định. Replica lag/failover có thể làm mất state gần nhất, đừng hứa giới hạn tuyệt đối hay dùng rate limiter thay sổ cái tiền.

request → atomic prune → count → admit/add hoặc reject → TTL cleanup
-- Lua minh họa: KEYS[1], ARGV = nowMs, windowMs, limit, uniqueRequestId
local now = tonumber(ARGV[1])
local win = tonumber(ARGV[2])
redis.call("ZREMRANGEBYSCORE", KEYS[1], "-inf", now-win)
local n = redis.call("ZCARD", KEYS[1])
if n >= tonumber(ARGV[3]) then return 0 end
redis.call("ZADD", KEYS[1], now, ARGV[4])
redis.call("PEXPIRE", KEYS[1], win)
return 1
-- Cửa sổ (now-window, now]; uniqueRequestId phải unique mỗi attempt.
