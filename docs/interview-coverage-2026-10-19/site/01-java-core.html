Java Core & Memory Internals

JVM, String Pool, Collections, Generics, Records, Exception Handling — nền tảng bắt buộc trong mọi vòng phỏng vấn Java.

Nền tảng JVM & Bộ nhớ

Q1 Phân biệt JDK, JRE và JVM?

What

JVM (Java Virtual Machine) là engine thực thi bytecode (.class) — quản lý Heap, Stack, Metaspace, GC, JIT compilation. JRE (Java Runtime Environment) = JVM + thư viện runtime (java.lang, java.util, I/O, networking…) — đủ để chạy app đã compile. JDK (Java Development Kit) = JRE + công cụ phát triển: javac, javadoc, jdb, jconsole, jlink, jar. Quan hệ lồng nhau: JDK ⊃ JRE ⊃ JVM.

Why

Phân biệt 3 khái niệm giúp trả lời câu hỏi phỏng vấn kinh điển: "Cài JDK hay JRE trên server?" — production container thường chỉ cần JRE (hoặc JRE slim), nhưng Docker image phổ biến dùng JDK vì tiện debug và jlink custom runtime. Hiểu JVM tách biệt khỏi ngôn ngữ Java — Kotlin, Scala, Groovy cũng compile ra bytecode chạy trên cùng JVM.

How

Luồng phát triển: viết .java → javac (JDK) compile → .class bytecode → JVM load class qua ClassLoader, verify bytecode, interpret hoặc JIT compile sang native code → thực thi. JRE cung cấp bootstrap classloader load rt modules (Java 9+ module system). Từ Java 11, Oracle phân phối JDK và có thể tạo custom runtime bằng jlink chỉ gồm modules cần thiết.

When

Dùng JDK trên máy dev, CI/CD build pipeline. Dùng JRE/JDK slim trên production pod nếu không cần compile tại runtime. Chọn JVM vendor theo SLA: HotSpot (default), GraalVM (native image, polyglot), Amazon Corretto, Eclipse Temurin — cùng spec JVM nhưng support/patch khác nhau.

When NOT

Đừng nhầm "Java chạy trên OS" — luôn qua JVM (trừ GraalVM Native Image compile ahead-of-time). Đừng cài JRE-only trên dev machine — thiếu javac. Đừng assume JRE tách rời JDK trên mọi bản phân phối Java 11+ — nhiều vendor chỉ ship JDK. Không nhầm JVM với JRE: JVM là phần thực thi, JRE bao gồm cả libraries.

Q2 String Pool là gì? Vì sao String immutable?

What

String Pool (String Table) là vùng trong Heap (Java 7+ chuyển từ PermGen) lưu các literal string unique — khi gặp "hello" lần hai, JVM reuse cùng object thay vì allocate mới. String.intern() đưa string vào pool hoặc trả reference đã có. String immutable: sau khi tạo, nội dung char[] không đổi — mọi "thay đổi" (concat, replace) tạo object mới.

Why

Pool tiết kiệm memory khi app dùng nhiều literal trùng (status code, SQL fragment, config key). Immutability bảo vệ security (class name, file path không bị mutate sau validation), thread-safety miễn phí, và cho phép cache hashCode — HashMap key hiệu quả. Compiler cũng tối ưu string concat constant-time vào pool lúc compile.

How

Literal "hello" → compile vào constant pool của class → runtime intern vào String Table. new String("hello") tạo object heap riêng (char[] copy hoặc share tùy version) — == với literal là false. intern() lookup String Table: có thì trả ref, không thì add và trả ref pool. Java 7+: pool trong Heap → không còn PermGen OOM riêng cho string.

When

Dùng literal/intern khi so sánh reference (==) an toàn và biết giá trị finite (enum-like strings). Immutable string làm Map key, cache key, constant. Dùng StringBuilder cho nối chuỗi trong loop.

When NOT

Đừng intern() mọi user input — String Table không GC được (Java 7+ vẫn có rủi ro memory leak với unique string vô hạn). Đừng dùng == so sánh nội dung string từ input/network — luôn equals(). Đừng concat string bằng + trong hot loop. Không mutate char[] reflection — phá immutability contract.

Use case

HTTP status mapping: Map<String, Handler> keyed by "GET", "POST" — literal pool tiết kiệm memory across millions requests. Config constant private static final String TOPIC = "order.created" — immutable, thread-safe broadcast.

Pitfall / Interview trap

"String Pool ở PermGen?" — Java 6 trở về trước; Java 7+ trong Heap. "String mutable qua reflection?" — Có thể nhưng phá contract. String s = "a" + "b" compile-time fold thành "ab" — 1 object pool. Runtime concat tạo StringBuilder tạm.

String a = "hello";      // String Pool
String b = "hello";      // reuse
String c = new String("hello"); // heap object mới

System.out.println(a == b);        // true
System.out.println(a == c);        // false
System.out.println(a.equals(c));   // true
String d = c.intern();
System.out.println(a == d);        // true
Nói trong 60 giây
  • String Pool intern literal — tiết kiệm memory, so sánh == được giữa literal.
  • Immutable: security, thread-safe, hashCode cache cho HashMap key.
  • new String() tạo object riêng; intern() đưa vào pool.
  • Java 7+: pool trong Heap, không PermGen.
  • Loop concat → StringBuilder; so sánh nội dung → equals().

Q3 So sánh == và .equals() — hợp đồng equals/hashCode

What

== so sánh reference (2 biến trỏ cùng object trên heap) hoặc giá trị primitive. .equals() so sánh nội dung theo logic nghiệp vụ — override được. equals/hashCode contract (Object spec): nếu a.equals(b) thì a.hashCode() == b.hashCode(); reflexive, symmetric, transitive, consistent; equals(null) → false.

Why

HashMap/HashSet dùng hashCode chọn bucket, equals so khớp trong bucket — vi phạm contract khiến "equal" object không tìm thấy trong Map. String Pool dùng == hợp lệ cho literal; user input bắt buộc equals. Record (Java 16+) auto-generate equals/hashCode từ components.

How

Override equals: check this == o, null, class type (instanceof hoặc getClass()), so sánh từng field quyết định identity. hashCode: cùng fields với equals — dùng Objects.hash(...). Integer cache -128..127: Integer a=127; b=127; a==b true; 128 false — autobox tạo object mới.

When

equals cho mọi so sánh object content (String, DTO, entity business key). Override cả equals + hashCode khi object làm Map/Set key. == cho primitive, null check, hoặc singleton/literal đã biết intern.

When NOT

Đừng dùng == so String từ user/DB. Đừng override equals mà quên hashCode — bug HashMap khó debug. Đừng dùng instanceof equals với subclass nếu cần symmetry strict — cân nhắc getClass(). Không include mutable field trong equals/hashCode nếu object làm key.

Employee keyed by id trong Map<Employee, Team> — equals/hashCode chỉ trên id, bỏ qua name (có thể đổi). Order dedup Set: equals theo orderNumber + warehouseId.

Pitfall / Interview trap

Lombok @EqualsAndHashCode thiếu callSuper trên inheritance → bug. BigDecimal: new BigDecimal("1.0") vs "1.00" equals false (scale khác) — dùng compareTo cho số. Default Object.equals là ==.

public class Employee {
  private final String id;

  @Override
  public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Employee e)) return false;
    return Objects.equals(id, e.id);
  }

  @Override
  public int hashCode() { return Objects.hash(id); }
}
Nói trong 60 giây
  • == = reference/primitive; equals = nội dung, override được.
  • Contract: equal objects → cùng hashCode — bắt buộc cho HashMap.
  • String user input: equals, không ==.
  • Override cả hai; dùng Objects.equals/hash cho null-safe.
  • Record auto equals/hashCode từ components.

Q4 String vs StringBuilder vs StringBuffer

What

String immutable — mỗi concat tạo object mới. StringBuilder mutable char buffer, không synchronized — single-thread. StringBuffer giống Builder nhưng mọi method synchronized — thread-safe, chậm hơn. Java 9+ compiler tối ưu string concat trong method thành StringBuilder tự động, nhưng loop vẫn O(n²) nếu dùng +=.

Why

Immutable String an toàn share giữa threads nhưng tốn allocation khi build chuỗi lớn. StringBuilder amortized O(n) nhờ buffer resize. StringBuffer legacy (pre-concurrent util) — ngày nay hiếm cần vì thường build string per-thread rồi publish immutable result.

How

StringBuilder internal char[] (hoặc byte[] compact strings Java 9+). append fill buffer, double capacity khi đầy. toString() copy ra String immutable. StringBuffer lock mỗi append → contention multi-thread. Alternative hiện đại: String.join, String.formatted, stream Collectors.joining.

When

String cho constant, template nhỏ, key. StringBuilder loop/build SQL/log message trong single thread. StringBuffer chỉ khi thực sự share builder giữa threads (rất hiếm — prefer local Builder).

When NOT

Đừng StringBuffer "cho an toàn" khi mỗi thread có builder riêng. Đừng += trong loop lớn. Không dùng StringBuilder làm Map key (mutable). Tránh sync StringBuffer trong hot path — bottleneck.

Export CSV 100k rows: StringBuilder per chunk, append line, flush to writer. JSON manual build (trước Jackson): Builder trong loop. Multi-thread report: mỗi worker Builder riêng → merge String cuối.

Pitfall / Interview trap

String s = "a" + "b" compile-time constant — 1 pool object, không Builder. String s = x + y runtime — Builder. "StringBuffer thread-safe nên tốt hơn" — sai nếu không share; Builder + immutable publish nhanh hơn.

String result = sb.toString();
Nói trong 60 giây
  • String immutable; Builder/Buffer mutable cho nối chuỗi.
  • Builder single-thread nhanh; Buffer synchronized — legacy.
  • Loop += String → O(n²); dùng StringBuilder O(n).
  • Constant concat compile-time fold — không cần Builder.
  • Hiện đại: String.join, formatted, Collectors.joining.

Q5 Java Memory Model (JMM) — Stack, Heap, Metaspace

What

Java Memory Model (JMM) là specification mô tả cách các thread trong JVM tương tác với bộ nhớ: khi nào một thread thấy thay đổi do thread khác ghi, và thứ tự thực thi nào được đảm bảo. Song song đó, JVM chia bộ nhớ runtime thành các vùng: Stack (mỗi thread một stack riêng), Heap (shared — chứa object/array), Metaspace (class metadata, thay PermGen từ Java 8), cộng thêm PC Register và Native Method Stack. Stack lưu stack frames (local variables, operand stack, reference trỏ tới object trên heap); heap là nơi new cấp phát; Metaspace lưu bytecode, constant pool, method metadata của class đã load.

Why

CPU và compiler tối ưu hóa mạnh (instruction reordering, store buffer, cache per core) khiến code tuân thủ Java syntax vẫn có thể cho kết quả khác nhau giữa các thread nếu không có quy tắc chung. JMM giải quyết bằng quan hệ happens-before: nếu action A happens-before B thì mọi thay đổi memory do A gây ra phải visible với B. Phân vùng Stack/Heap/Metaspace giúp GC chỉ quét heap, thread crash không làm hỏng heap của thread khác, và class metadata tách khỏi object heap để tránh PermGen overflow kiểu Java 7. Hiểu JMM là nền tảng trả lời câu hỏi double-checked locking, visibility của volatile, và tại sao synchronized không chỉ là mutex.

How

Luồng thực thi: mỗi method call đẩy frame lên Stack; local variable chứa primitive hoặc reference; object thực sự nằm trên Heap. GC bắt đầu từ GC Roots (static fields, local ref trên stack, JNI handles, synchronized monitor) rồi mark-reachability. JMM định nghĩa happens-before qua: unlock monitor happens-before lock cùng monitor; write volatile happens-before read volatile đó; thread start happens-before mọi action trong thread con; thread join happens-before code sau join(); write final field (sau constructor) happens-before đọc final sau khi object fully constructed.

volatile đảm bảo visibility (mọi read thấy write mới nhất) và cấm reorder một số instruction quanh volatile access — nhưng không atomic cho i++. synchronized vừa mutual exclusion vừa flush cache / establish happens-before khi release lock.

When

Dùng kiến thức JMM khi thiết kế code đa luồng: shared mutable state cần synchronized, volatile, Atomic*, hoặc immutable objects. Metaspace tuning khi deploy nhiều class (Spring, dynamic proxy, Groovy) — flag -XX:MaxMetaspaceSize. Phân biệt Stack vs Heap khi debug StackOverflowError (đệ quy sâu, stack frame lớn) vs OutOfMemoryError: Java heap space (object leak, heap nhỏ).

When NOT

Đừng giả định “code viết trước chạy trước” trên multi-core — đó là lỗi phỏng vấn kinh điển. Không dùng volatile thay cho lock khi cần atomic read-modify-write phức tạp. Không nhầm JMM với physical memory layout: JMM là abstract model; actual heap có thể compact, object di chuyển khi GC. Không cố “tối ưu” bằng cách bỏ synchronized mà không hiểu visibility — race condition khó reproduce hơn deadlock.

  • Primitive + reference (không chứa object)

Use case

Web server xử lý request: mỗi request chạy trên thread pool — stack frame của handler chứa local OrderDto dto (reference), object OrderDto nằm heap; static Map<String, Cache> là GC root. Dùng volatile boolean shutdown để worker thread thấy flag dừng service ngay lập tức mà không cần lock toàn bộ pipeline.

Pitfall / Interview trap

Interviewer hỏi: “volatile có thread-safe không?” — Trả lời: visibility yes, atomicity no (count++ vẫn race). Bẫy khác: “String nằm ở đâu?” — literal trong String Pool (heap, Java 7+), object new String() cũng heap. “happens-before và execution order khác nhau” — reorder được phép miễn không phá happens-before edge.

public class VisibilityDemo {
  private volatile boolean ready = false;
  private int value = 0;

  void writer() {
    value = 42;       // plain write
    ready = true;     // volatile write → reader thấy value=42
  }

  void reader() {
    while (!ready) { }  // volatile read
    System.out.println(value); // guaranteed 42
  }
}
Nói trong 60 giây
  • JMM = quy tắc visibility & ordering giữa threads trên multi-core, không phải diagram bộ nhớ vật lý.
  • Stack per-thread (frames, locals); Heap shared (objects); Metaspace (class metadata, thay PermGen).
  • happens-before: synchronized, volatile, thread start/join, final fields — đảm bảo thread khác thấy write.
  • volatile = visibility, không atomic; synchronized = lock + happens-before.
  • GC Roots: static, stack refs, JNI — điểm bắt đầu mark object còn sống.

Q6 Garbage Collection — Young Gen, Old Gen, G1GC, ZGC

What

Garbage Collection (GC) tự động thu hồi object trên Heap không còn reachable từ GC Roots. Generational hypothesis: hầu hết object chết sớm → heap chia Young Generation (Eden + 2 Survivor S0/S1) và Old Generation (Tenured). Minor GC (Young GC) dọn Eden/Survivor — thường nhanh, stop-the-world ngắn. Major/Full GC dọn Old Gen — pause dài hơn, đôi khi compact heap. Mỗi object sống sót qua Minor GC tăng age; vượt -XX:MaxTenuringThreshold (mặc định 15) thì promote lên Old Gen. Collectors phổ biến: Serial, Parallel (throughput), G1 (region-based, pause target), ZGC/Shenandoah (ultra-low latency, concurrent).

Why

Manual memory management dễ leak và dangling pointer; GC trade-off pause time vs throughput. Young Gen tách riêng vì Minor GC copy-only (Mark-Copy) trên vùng nhỏ — hiệu quả khi mortality cao. Old Gen dùng Mark-Sweep hoặc Mark-Compact tùy collector. Ứng dụng latency-sensitive (trading, gaming, realtime API) cần collector giới hạn pause; batch ETL ưu tiên throughput với Parallel GC. G1 chia heap thành regions (~1–32MB) để thu gom từng phần thay vì cả heap — phù hợp heap multi-GB. ZGC dùng colored pointers + load barriers để concurrent compaction — pause sub-millisecond dù heap TB.

How

Vòng đời object: new trong Eden → Eden đầy → Minor GC: mark live objects, copy sang Survivor (from-space → to-space), swap S0/S1, age++. Object long-lived sau nhiều Minor GC → promote Old Gen. Old Gen đầy → Full GC (G1: Mixed GC thu gom một phần Old regions có nhiều garbage nhất). G1 chọn collection set theo -XX:MaxGCPauseMillis target. ZGC chạy concurrent mark, relocate, remap — hầu hết công việc ngoài STW pause ngắn.

Minor vs Full: Minor chỉ Young; Full thu gom Old (và thường cả Young). Triệu chứng: log [GC (Allocation Failure) = Minor; [Full GC = toàn heap — nếu Full GC liên tục → heap nhỏ, leak, hoặc promotion quá nhanh.

When

G1GC (default Java 9+): heap 4GB– vài chục GB, cần pause ổn định ~100–200ms, microservices đa số case. Flag: -XX:+UseG1GC, -XX:MaxGCPauseMillis=200, set -Xms=-Xmx tránh resize. ZGC (Java 15+ production, Java 21 generational ZGC): heap lớn, SLA pause <10ms, financial/realtime — chấp nhận overhead CPU hơn G1. Parallel GC: offline batch, không care pause. Monitor: jstat -gcutil, GC logs (-Xlog:gc*), Micrometer, async-profiler.

When NOT

Đừng chọn ZGC cho heap nhỏ (<4GB) app đơn giản — overhead không xứng. Đừng tăng -Xmx vô hạn thay vì fix memory leak — chỉ trì hoãn Full GC. Tránh allocate object không cần trong hot path (boxing, String concat trong loop) vì tăng Minor GC frequency. Không nhầm “object trong Old Gen = leak” — long-lived cache hợp lệ cũng promote. Không tune GC khi chưa có metrics — đo trước, đo sau.

E-commerce API (G1): heap 8GB, -Xms8g -Xmx8g -XX:+UseG1GC -XX:MaxGCPauseMillis=150 — P99 latency ổn khi Minor GC vài chục ms. Pitfall / Interview trap

“Minor GC có dọn Old Gen không?” — Không, chỉ Young (trừ một số edge promotion). “G1 eliminater Full GC?” — Không hoàn toàn; evacuation failure vẫn trigger Full GC. “Object age reset khi nào?” — Khi Survivor không đủ chỗ, object có thể promote sớm dù age thấp. Nói ZGC cần Java 11+ (experimental) vs 15+ production-ready — thể hiện biết timeline.

Q7 HashMap hoạt động như thế nào?

What

HashMap là implementation của Map dựa trên hash table: lưu các cặp key-value trong mảng buckets (mặc định capacity 16). Mỗi key qua hashCode() rồi spread bit bằng hash(key) (XOR high bits — Java 8+) để giảm collision khi capacity là power of 2. Index bucket: (n - 1) & hash với n = table length. Entry nội bộ là Node<K,V> (Java 8+) chứa hash, key, value, next pointer. Average case get/put O(1); worst case O(log n) khi bucket treeified hoặc O(n) nếu hash xấu và chưa treeify.

Why

Hash table trade-off memory vs speed lookup — O(1) average là lý do HashMap là default map trong Java. Load factor 0.75 cân bằng: factor cao → ít memory nhưng collision nhiều; thấp → ít collision nhưng lãng phí bucket. Treeify (Java 8) giải quyết collision attack / hash xấu: linked list dài O(n) → Red-Black Tree O(log n) khi cùng bucket ≥ 8 nodes và table size ≥ 64. Resizing (rehash) khi size > threshold (capacity × loadFactor) — double capacity và redistribute entries — costly nên khởi tạo capacity hợp lý nếu biết trước size.

How

put(key, value): tính hash → index → nếu bucket null, tạo Node mới; nếu có entry, so sánh hash rồi equals() key — trùng thì replace value; không trùng append linked list (hoặc insert tree). Nếu list length ≥ TREEIFY_THRESHOLD (8) và table ≥ MIN_TREEIFY_CAPACITY (64) → convert sang TreeNode (Red-Black Tree). get(key): cùng hash/index, traverse list hoặc tree, so sánh equals. resize: capacity × 2, rehash mọi entry — Java 8 tối ưu: chỉ recalc index bằng bit (e.hash & oldCap) thay vì mod lại.

equals/hashCode contract: nếu a.equals(b) thì a.hashCode() == b.hashCode() — vi phạm → get trả null dù key “bằng” nhau. Key mutable (object thay đổi sau put) → mất entry. Fail-fast iterator: throw ConcurrentModificationException nếu structurally modify khi iterate (không phải thread-safe).

When

Single-thread hoặc chỉ read sau build (immutable map). Cache in-memory, index lookup, deduplication. Khởi tạo new HashMap<>(expectedSize) khi biết trước ~N entries để tránh resize nhiều lần (capacity = N / 0.75 + 1). Dùng immutable key (String, Integer, record) và override equals/hashCode đúng cho custom key.

When NOT

Không dùng HashMap khi nhiều thread write/read đồng thời — race corrupt internal table. Không dùng mutable object làm key. Không dùng khi cần sorted order — dùng TreeMap. Không wrap HashMap bằng Collections.synchronizedMap rồi iterate — vẫn phải sync manually; prefer ConcurrentHashMap. Tránh hash collision cố ý (DoS) trên Java 7 — Java 8+ đã treeify mitigate.

Use case

What

HashSet là implementation của Set — collection không trùng lặp, không đảm bảo thứ tự (LinkedHashSet giữ insertion order; TreeSet sorted). Q8 HashMap vs ConcurrentHashMap

What

HashMap không thread-safe — concurrent read/write có thể corrupt table, infinite loop (Java 7), hoặc lost update. ConcurrentHashMap (CHM) cho phép nhiều thread get/put đồng thời với throughput cao hơn Hashtable hay Collections.synchronizedMap vì lock granularity nhỏ. Java 7 CHM: chia table thành 16 Segments, mỗi segment là HashMap mini với ReentrantLock riêng — lock theo segment, không lock cả map. Java 8+ CHM: bỏ Segment, dùng cùng cấu trúc Node như HashMap nhưng concurrent control bằng CAS (lock-free insert vào bucket empty) + synchronized lock first node của bucket khi collision/tree update. Size/count dùng LongAdder / counter cells để giảm contention.

Why

Hashtable synchronize mọi public method → serial hóa toàn bộ access — bottleneck trên multi-core. synchronizedMap(HashMap) cũng lock toàn map. CHM target concurrency level: Java 7 segment count (default 16) giới hạn parallel writes; Java 8 lock per-bucket (finer) + CAS cho empty bucket insert → scale tốt hơn read-heavy workload. CHM cấm null key/value vì null ambiguous trong concurrent context (get trả null = không có hay value null?). Iterator weakly consistent — reflect state tại thời điểm tạo iterator, không throw CME, có thể miss entry add sau nhưng không corrupt.

How

Java 7 put: hash → segment index → lock segment → put như HashMap trong segment → unlock. Java 8 put: nếu bucket null → CAS insert Node; nếu đang resize → help transfer; nếu bucket có node → synchronized lock head node → insert list/tree hoặc update value. size() approximate (đủ cho monitoring). Atomic compound ops: putIfAbsent, replace, compute, merge — lock bucket tương ứng. ConcurrentHashMap.newKeySet() cho concurrent Set.

When

Shared cache, session store, rate limiter counters, in-memory registry nhiều thread read/write. Read-heavy web app: CHM scale tốt vì get thường không lock (volatile read Node array). Dùng computeIfAbsent atomic lazy init per key — tránh double-create race. Chọn initial capacity / concurrencyLevel (Java 7) hoặc size hint (Java 8) nếu biết trước load.

When NOT

Single-thread → HashMap đơn giản hơn, cho phép null. Cần strict snapshot iteration consistent → copy-on-write (ConcurrentHashMap iterator weakly consistent) hoặc lock toàn map khi iterate. Strong consistency cross-key transaction → dùng DB/lock service, không phải CHM. Đừng dùng CHM thay Redis cho distributed cache — CHM chỉ in-process JVM.

Q9 ArrayList vs LinkedList

What

ArrayList wrap dynamic array (Object[]), resize ×1.5 khi đầy. LinkedList doubly-linked nodes — mỗi node chứa prev/next pointer + element. Cả hai implement List; LinkedList thêm Deque (addFirst, pollLast). Big-O không phản ánh hết thực tế do CPU cache và constant factor.

Why

ArrayList contiguous memory → cache-friendly, random access O(1) thực sự nhanh. LinkedList insert đầu O(1) lý thuyết nhưng mỗi node rải rác heap → pointer chasing chậm hơn ArrayList shift nhỏ. Benchmark thực tế: ArrayList thường thắng LinkedList hầu hết scenario trừ deque-heavy edge case.

How

Default: ArrayList — index access, iterate, append cuối. LinkedList khi cần Deque operations hai đầu liên tục và list nhỏ/vừa. ArrayDeque thường tốt hơn LinkedList cho queue/stack.

When NOT

Đừng chọn LinkedList vì "insert O(1)" khi cần get by index. Không LinkedList cho list lớn + random access. ArrayList không phù hợp insert đầu liên tục trên list rất lớn — cân nhắc Deque hoặc linked structure chuyên dụng.

What

Q12 Overloading vs Overriding

What

Overloading (compile-time polymorphism): cùng tên method, khác parameter list (type/số/thứ tự) trong cùng class (hoặc inherited + new overload). Overriding (runtime polymorphism): subclass cung cấp implementation mới cho method instance đã có ở parent — cùng signature, compatible return, access không hẹp hơn.

Why

Overloading API tiện (println int/String/Object). Overriding hỗ trợ Liskov substitution — code gọi qua reference parent chạy behavior child. JVM dynamic dispatch qua vtable — virtual method call. @Override annotation bắt lỗi typo signature lúc compile.

How

Overload: compiler chọn method best match lúc compile (static binding). Override: runtime chọn method thực tế của object (dynamic dispatch). static method "hide" không override. private/final không override. Covariant return: child trả subtype được (Java 5+).

When

Overload cho convenience method (process(Order), process(Order, Options)). Override khi polymorphism — template method pattern, strategy qua inheritance, equals/hashCode/toString.

When NOT

Đừng overload chỉ khác return type — compile error. Override không được thu hẹp access (public → private). Không override static — đó là hide, gọi qua reference type quyết định. Tránh override không @Override — dễ tạo overload nhầm.

Q13 Pass-by-value trong Java

What

Java chỉ pass-by-value — mọi method call copy giá trị argument vào parameter. Primitive: copy bit pattern. Object: copy reference value (pointer) — hai reference trỏ cùng object heap. Không có pass-by-reference như C++ int&.

Why

Hiểu đúng giải thích vì sao swap(int a, int b) không hoạt động, nhưng mutate object qua reference thì có. Phỏng vấn hay hỏi "Java pass by reference?" — trả lời value of reference. Ảnh hưởng design API: không thể reseat caller variable, cần return object mới hoặc wrapper holder.

How

Method nhận copy ref → gọi method trên object (mutate state) → caller thấy thay đổi. Gán parameter = object khác → chỉ đổi local copy ref, caller không đổi. Immutable object (String): "modify" tạo object mới — caller giữ ref cũ. Arrays là object — pass copy ref, mutate element visible.

When

Mutate object khi cần side effect (append StringBuilder, fill array). Return new object khi cần thay reference (functional style). Optional/wrapper cho "out parameter" pattern thay pass-by-ref.

When NOT

Đừng expect reassign parameter thay đổi caller variable. Đừng nói "Java pass object by reference" — gây hiểu nhầm. Không dùng single-element array hack trừ legacy — prefer return value.

Use case

void fillBuffer(StringBuilder sb, data) — append visible caller. String s = transform(s) — immutable phải return. int[] results shared mutate OK; reassign results = new int[] không affect caller.

Pitfall / Interview trap

swap(Object a, Object b) { Object t=a; a=b; b=t; } — vô hiệu. C++ programmer nhầm. Integer i=1; modify(i) không đổi i vì Integer immutable — phải return hoặc AtomicInteger.

}

Nói trong 60 giây
  • Java luôn pass-by-value — kể cả object.
  • Object = copy reference; mutate object → caller thấy.
  • Reassign parameter → không đổi caller variable.
  • Immutable (String) phải return object mới.
  • Không pass-by-reference như C++.

Q14 Generics — PECS & Type Erasure

What

Generics (Java 5+) thêm type parameter compile-time safety — List<String> không nhận Integer. PECS: Producer Extends (? extends T — đọc T), Consumer Super (? super T — ghi T). Type Erasure: compiler xóa type parameter lúc runtime — bytecode dùng raw type + cast; không có List<String>.class.

Why

Tránh ClassCastException runtime từ raw collection. Wildcard linh hoạt API (copy List bất kỳ subtype). Erasure giữ backward compatibility với pre-Java 5 bytecode — trade-off mất reified generics (khác C#).

How

extends upper bound: đọc T, không add (trừ null) — covariant read. super lower bound: add T, đọc Object — contravariant write. Erasure: T → Object, T extends Number → Number. Bridge methods generate cho override generic. Reifiable types: primitive, non-generic class, array, wildcard with extends super Object.

When

PECS cho utility copy, compare, consume/produce API. Bounded type parameter <T extends Comparable<T>> cho sort. Generic method khi type infer từ argument.

When NOT

Đừng raw type trừ legacy interop. Không new T() / T[] trực tiếp — dùng Class<T> reflect hoặc factory. Không instanceof parameterized type. Tránh wildcard phức tạp khi method generic đơn giản hơn.

What

When

Transform/filter/aggregate in-memory collection. Parallel cho dataset lớn, operation pure CPU (map math). Optional thay null return. Stream cho business logic read; không side effect trong map nếu parallel.

When NOT

Đừng parallelStream với I/O blocking — starve common pool. Không mutate external state trong forEach parallel — race. Stream one-shot — không reuse sau terminal. Simple loop có thể rõ hơn stream phức tạp. Không stream cho very small collection (overhead).

Deep Dive — Autoboxing & Integer Cache

D1 Autoboxing và bộ đệm Integer cache — vì sao == trên wrapper gây bug?

What

Autoboxing (Java 5+) là cơ chế compiler tự chuyển giữa primitive và wrapper: Integer x = 5; biên dịch thành Integer.valueOf(5), còn int y = x; thành x.intValue() (unboxing). Điểm mấu chốt: Integer.valueOf có bộ đệm (cache) cho giá trị −128..127 — JLS §5.1.7 bắt buộc hai lần boxing cùng một giá trị nhỏ phải trả về cùng một instance. Ngoài khoảng này, mỗi lần boxing thường tạo object mới.

Why

Vì sao có cache? Các giá trị nhỏ xuất hiện liên tục (chỉ số vòng lặp, status code, ký tự ASCII) nên dùng lại instance giúp tiết kiệm bộ nhớ và thời gian cấp phát. Nhưng cache tạo ra hành vi không đối xứng: toán tử == so sánh reference (identity), còn .equals() so sánh giá trị. Với wrapper, == chỉ đúng khi hai biến trỏ cùng một instance — đúng trong khoảng cache, sai ngoài khoảng. Đây là bẫy phỏng vấn kinh điển vì code chạy đúng lúc test với số nhỏ nhưng nổ ở production với số lớn.

How

Integer.valueOf(int) kiểm tra i >= IntegerCache.low (−128) và i <= IntegerCache.high (127 mặc định): trong khoảng trả phần tử trong cache, ngoài khoảng gọi new Integer(i). Ngưỡng trên chỉnh được qua -XX:AutoBoxCacheMax=size hoặc system property java.lang.Integer.IntegerCache.high. Các wrapper khác cũng có cache: Long/Short/Byte cố định −128..127, Character 0..127, Boolean chỉ hai hằng TRUE/FALSE. Lưu ý new Integer(127) (deprecated) luôn tạo object mới nên == sẽ cho false.

Deep Dive — fail-fast vs fail-safe Iterator

D2 fail-fast vs fail-safe iterator — vì sao có ConcurrentModificationException?

What

fail-fast là iterator của các collection trong java.util (ArrayList, HashMap, TreeSet): nếu collection bị sửa cấu trúc (thêm/xóa) trong lúc đang duyệt — trừ khi qua chính iterator — thì lần gọi next() kế tiếp ném ConcurrentModificationException (CME). fail-safe (chính xác hơn là weakly consistent) là iterator của java.util.concurrent (ConcurrentHashMap, CopyOnWriteArrayList, ConcurrentLinkedQueue): duyệt trên snapshot hoặc view chịu được thay đổi đồng thời, KHÔNG ném CME.

Why

fail-fast phát hiện bug “sửa collection trong lúc duyệt” càng sớm càng tốt — nhưng Oracle nói rõ nó chỉ là best-effort, không đảm bảo, và không được dùng để kiểm soát tính đúng đắn. Weakly consistent cho phép nhiều thread đọc/ghi mà không cần khóa, đổi lại iterator không hứa phản ánh mọi thay đổi mới nhất (có thể thấy hoặc không). Hiểu hai cơ chế này để chọn collection đúng: fail-fast cho single-thread (bắt bug sớm), weakly consistent khi thực sự concurrent.

How

ArrayList.Itr giữ một biến expectedModCount; mỗi lần next()/remove() gọi checkForComodification() và so với modCount hiện tại của list — lệch thì ném CME. Vì modCount tăng khi add/remove trực tiếp trên list, vòng for-each vừa duyệt vừa list.remove() sẽ nổ. Cách đúng là dùng Iterator.remove() (có cập nhật lại expectedModCount) hoặc list.removeIf(...). CopyOnWriteArrayList giữ tham chiếu tới một array bất biến; mỗi thao tác ghi tạo array mới, nên iterator đang chạy vẫn thấy array cũ (snapshot) — không CME nhưng có thể bỏ sót phần tử vừa thêm.

When

Dùng fail-fast iterator trong code single-thread để bắt bug sớm. Khi vừa duyệt vừa xóa, dùng Iterator.remove() hoặc removeIf. Dùng CopyOnWriteArrayList cho danh sách đọc nhiều ghi ít (listener, cấu hình), ConcurrentHashMap cho map chia sẻ giữa nhiều thread, ConcurrentLinkedQueue/BlockingQueue cho hàng đợi.

When NOT

Đừng bắt ConcurrentModificationException rồi nuốt — đó là dấu hiệu bug chứ không phải lỗi cần phục hồi. Đừng dựa vào CME như cơ chế đồng bộ (nó best-effort). Đừng dùng CopyOnWriteArrayList cho workload ghi nhiều — mỗi lần ghi copy toàn bộ array O(n) và tốn GC. Đừng dùng ArrayList rồi add/remove trực tiếp trong for-each.

List<String> list = new ArrayList<>(List.of("A", "B", "C"));

for (String s : list) {
    if (s.equals("B")) list.remove(s);   // ConcurrentModificationException
}

// Đúng: dùng iterator.remove() — cập nhật expectedModCount
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    if (it.next().equals("B")) it.remove();
}
list.removeIf(s -> s.equals("C"));              // OK

// Weakly consistent — không ném CME
ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();
map.put("a", 1);
for (var e : map.entrySet()) map.put("b", 2); // an toàn
Use case

Cache in-memory chia sẻ giữa nhiều request: dùng ConcurrentHashMap và duyệt entrySet() đồng thời. Danh sách listener/observer đăng ký một lần, gọi nhiều lần: CopyOnWriteArrayList để vòng lặp gọi listener không bao giờ văng CME.

Pitfall / Interview trap

CME có thể ném ngay cả trong single-thread nếu sửa collection trực tiếp khi duyệt — không phải chỉ do đa luồng. CME là “best-effort”: không đảm bảo luôn phát hiện. list.subList(...) là view nên sửa list gốc cũng làm nó ném. Weakly consistent không ném CME nhưng có thể bỏ sót phần tử vừa thêm — đừng giả định iterator phản ánh trạng thái mới nhất.

Deep Dive — Immutable Class & Defensive Copy

D3 Viết immutable class đúng cách — defensive copy và safe publication?

What

Immutable object là object có trạng thái không đổi sau khi khởi tạo. Immutable class đạt được điều đó bằng: mọi field là private final, không có setter, và nếu field trỏ tới mutable object (Date, List, array) thì phải defensive copy cả lúc nhận vào (constructor) và lúc trả ra (getter). Ví dụ chuẩn trong JDK: String, các wrapper, java.time.*, và record (Java 16) cho value trong suốt.

Why

Immutable object thread-safe miễn phí: không cần đồng bộ vì không ai đổi được trạng thái. Đặc biệt JLS §17.5 cho final-field freeze — field final gán xong trong constructor được đảm bảo visible với mọi thread đọc reference, ngay cả khi publish không an toàn (miễn this không escape khỏi constructor). Ngoài ra immutable object an toàn khi làm key HashMap/phần tử HashSet (hashCode ổn định) và có thể cache/ chia sẻ thoải mái.

How

Công thức: (1) khai báo public final class (hoặc constructor private + factory) để cấm subclass phá vỡ; (2) mọi field private final; (3) copy phòng vệ lúc vào — gán this.start = new Date(start.getTime()) thay vì gán thẳng reference; (4) copy phòng vệ lúc ra — getter trả bản sao, không trả reference gốc; (5) với collection, dùng List.copyOf/Map.copyOf/Set.copyOf (Java 10+) để tạo bản bất biến; (6) không để this escape (đăng ký listener, truyền this ra ngoài) trong constructor.

❌ Trông immutable nhưng không

  • final List nhưng getter trả list gốc → caller add() được
  • Field Date lưu thẳng reference → caller setTime() đổi được
  • this escape trong constructor → mất final-field guarantee
  • Class không final, subclass thêm setter

✅ Immutable đúng nghĩa

  • List.copyOf(input) → không sửa được
  • Copy Date cả vào lẫn ra
  • Class final, field private final
  • An toàn chia sẻ giữa thread, làm cache key
When

Dùng cho value object/DTO (Money, Range, Period), config bất biến chia sẻ giữa nhiều thread, cache key, tham số bất biến của service. record (Java 16) tự sinh constructor/accessor/equals/hashCode/toString và field là final — dùng khi data là “shallow immutable” (các component cũng nên immutable).

When NOT

Đừng gọi là immutable nếu còn lộ reference mutable ra ngoài. Đừng copy phòng vệ trong hot path một cách mù quáng nếu chi phí đáng kể — khi collection đã build xong và không ai mutate, có thể dùng Collections.unmodifiableList (view rẻ) thay vì copy. final chỉ chặn gán lại reference, KHÔNG làm object bên trong bất biến — final List vẫn add() được.

public final class Period {                 // final class
    private final Date start;              // field final
    private final Date end;

    public Period(Date start, Date end) {
        this.start = new Date(start.getTime()); // defensive copy IN
        this.end   = new Date(end.getTime());
    }
    public Date start() { return new Date(start.getTime()); } // copy OUT
}

// Java 10+: immutable copy rẻ hơn và gọn hơn
public final class Team {
    private final List<String> members;
    public Team(List<String> m) { this.members = List.copyOf(m); }
    public List<String> members() { return members; }   // an toàn — copy bất biến
}
Use case

Config đọc một lần lúc khởi động rồi chia sẻ read-only giữa mọi request thread — không cần khóa. Cache key là record gồm các field bất biến, tránh bug “key đổi hash sau khi put”. DTO trả về từ API dùng record để tự có equals/hashCode/toString đúng.

Pitfall / Interview trap

Getter trả thẳng Date/List là lỗi immutability kinh điển — người nhận sửa được object bên trong. final List chỉ cố định reference: list.add() vẫn chạy. Để this escape trong constructor (gọi method override, đăng ký listener) khiến thread khác thấy field chưa gán — final-field guarantee bị vô hiệu. Sửa field final bằng reflection cũng phá guarantee.

Bổ sung chiều sâu phỏng vấn

OOM dù máy còn RAM: G1/ZGC và runbook production

What

RAM trống của host không bảo đảm JVM còn bộ nhớ: heap bị giới hạn bởi Xmx, native memory và cgroup có ngân sách riêng. Phải phân biệt Java OOME với kernel OOMKilled trước khi chọn cách xử lý.

Phân loại trước khi sửa

Ghi nguyên thông báo: Java heap space, GC overhead limit exceeded, Metaspace, Direct buffer memory hoặc unable to create native thread. Exit 137 chỉ cho biết SIGKILL, chưa đủ kết luận OOM; đối chiếu container state, kernel log và memory.events của cgroup. OOMKilled có thể không sinh heap dump vì JVM bị kill từ ngoài.

Vì sao còn RAM vẫn chết

Xmx là trần heap riêng, không tự tăng theo RAM host. Tổng RSS còn gồm metaspace, code cache, stack mỗi thread, direct buffer, thư viện native và overhead GC. Limit container có thể thấp hơn RAM host; nhiều container chia sẻ host. Heap còn khoảng trống nhưng không đáp ứng allocation cụ thể cũng cần kiểm tra GC log và loại allocation.

G1 và ZGC

G1 có humongous object từ nửa region trở lên: cần chuỗi region liên tiếp; fragmentation và evacuation failure có thể dẫn đến Full GC hay allocation failure. ZGC cần headroom để concurrent relocation và tốc độ GC đuổi kịp allocation; low pause không đồng nghĩa không bao giờ OOM. Không đổi collector để chữa reference leak.

Runbook an toàn

1. Lưu timestamp, version, traffic, limit/RSS/heap và GC log. 2. Kiểm tra GC.heap_info, Thread.print; NMT chỉ có ích nếu bật NativeMemoryTracking trước đó. 3. So histogram/dominator retained size và đường tới GC roots. 4. Giảm tải/giới hạn queue/cache hoặc scale có kiểm soát. 5. Reproduce với tải đại diện và so live set sau GC. Histogram/heap dump có thể gây pause và I/O lớn: cần quyền vận hành, dung lượng và redaction; dump có thể chứa token/PII, không upload công khai.

Phỏng vấn và giới hạn

Cache Map tăng mãi: tìm GC root giữ entry và đặt eviction, không chỉ tăng Xmx. RSS tăng nhưng heap ổn: kiểm tra thread/direct/native. Chỉ nâng heap sau khi dành ngân sách native dưới cgroup limit. Không force Full GC trên production như bước đầu.
