Module 07

Microservices & Distributed Architecture

Service Discovery, CQRS, Saga, Circuit Breaker, Kafka, Distributed Tracing — kiến thức cốt lõi cho hệ thống phân tán quy mô lớn.

Cơ trúc & Mô hình giao tiếp

Q1 Microservices vs Monolith?

What

Monolith — single deployable unit 1 DB ACID vs Microservices — independent deploy, DB per service, scale per bottleneck, network complexity.

Why

Trade-off phỏng vấn Architect: team scale, domain boundary vs operational cost tracing saga.

How

Monolith: simple debug TX ACID, scale whole app. Microservices: bounded context, polyglot, independent release, cần gateway/discovery/tracing/saga.

Monolith

  • Deploy đơn giản, debug dễ
  • Transaction ACID trong 1 DB
  • Scale toàn bộ app cùng lúc
  • Phù hợp startup/MVP
  • Deploy đơn giản, debug dễ
  • Transaction ACID trong 1 DB
  • Scale toàn bộ app cùng lúc
  • Phù hợp startup/MVP
  • Deploy độc lập từng service
  • Tech stack linh hoạt
  • Scale theo bottleneck service
  • Phức tạp: network, tracing, ops
When

Microservices: team lớn, domain rõ, scale khác nhau Order vs Notification. Monolith: MVP startup monolith-first.

When NOT

Không tách microservices sớm 2 dev — distributed monolith pain. Không monolith forever 50 team same codebase. Không tách without bounded context map.

Use case

WMS: tách Order/Inventory/WCS khi team scale; MVP OMS monolith trước.

Pitfall / Interview trap

Distributed monolith shared DB; premature microservices.

Nói trong 60 giây
  • Monolith simple deploy 1 DB ACID.
  • Microservices independent deploy scale.
  • Monolith-first MVP startup.
  • Tách khi team domain scale.
  • Cost: network tracing ops.

Q2 Service Discovery & API Gateway?

What

Service Discovery (Eureka/Consul) — register/lookup instance dynamic. API Gateway — single entry routing SSL rate limit auth aggregation.

Why

Hardcode IP không scale K8s pod ephemeral. Gateway centralize cross-cutting thay mỗi service implement auth/rate limit.

How

Service register heartbeat → client lb://service-name (Spring Cloud). Gateway routes Path predicate → Filter rate limit → downstream.

Service A
# Spring Cloud Gateway route
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service
          predicates:
            - Path=/api/orders/**
          filters:
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 100
When

K8s/Eureka dynamic instances ≥3 services. Gateway public API edge.

When NOT

Không service discovery 1 instance dev — overkill. Không gateway business logic fat — belongs domain service. Không skip health check registered dead instance.

Use case

Spring Cloud Gateway lb://order-service /api/orders/** rate limit Redis.

Pitfall / Interview trap

Eureka self-preservation false positive; gateway SPOF HA pair.

Nói trong 60 giây
  • Discovery register lookup dynamic IP.
  • Eureka Consul K8s DNS.
  • Gateway routing SSL rate limit.
  • lb://service-name not hardcode.
  • Centralize cross-cutting edge.

Q3 Sync vs Async communication?

What

Sync REST/gRPC caller chờ response immediate vs Async Kafka/RabbitMQ fire-and-forget event-driven eventual.

Why

Sync tight coupling cascade failure. Async loose buffer retry DLQ — phù hợp notify side effect.

How

Sync Feign @GetMapping getStock immediate. Async kafkaTemplate.send OrderCreated fire. Choose sync query need result now; async side effect tolerate delay.

Sync (REST/gRPC)Async (Kafka/RabbitMQ)
CouplingTight — caller chờ responseLoose — fire-and-forget / event-driven
LatencyImmediateEventual
FailureCascade nếu downstream downBuffer, retry, DLQ
Use caseQuery cần kết quả ngayOrder placed → notify, inventory update
 
// Sync — OpenFeign
@FeignClient(name = "inventory-service")
public interface InventoryClient {
  @GetMapping("/stock/{sku}")
  StockResponse getStock(@PathVariable String sku);
}

// Async — Kafka
kafkaTemplate.send("order-events", order.getId(), new OrderCreatedEvent(order));
When

Sync: checkout get stock price user waiting. Async: order placed → notify email inventory update ERP.

When NOT

Không sync chain 5 service no timeout/CB — cascade. Không async khi user cần immediate confirm payment success UI.

Use case

Checkout sync inventory check; OrderCreated Kafka async reserve stock notify WCS.

Pitfall / Interview trap

Sync cascade timeout; async ordering partition key.

Nói trong 60 giây
  • Sync REST gRPC immediate tight.
  • Async Kafka loose eventual.
  • Sync query user waiting.
  • Async side effect notify.
  • Combine both hybrid flow.

Q4 Database per Service?

What

Database per Service — mỗi microservice sở hữu schema riêng, không share table cross-service direct access.

Why

Loose coupling schema evolve independent; tránh shared DB = distributed monolith mất lợi ích tách.

How

Order service PostgreSQL orders schema; Inventory service own DB. Cross-service: API call, event projection, CQRS read model — không JOIN cross DB.

  • Ưu: Loose coupling, schema evolve độc lập, polyglot persistence
  • Nhược: Không JOIN cross-service, distributed transaction phức tạp
  • Cross-service query: API composition, CQRS read model, event projection
When

True microservices bounded context. Polyglot persistence per access pattern.

When NOT

Không 2 services cùng read/write 1 table — anti-pattern. Không JOIN cross service DB — API composition thay. Không DB per service khi chưa tách domain — premature.

Use case

Order DB + Inventory DB; OrderCreated event sync stock view.

Pitfall / Interview trap

Shared database distributed monolith; cross-service query pain.

Nói trong 60 giây
  • Each service owns DB schema.
  • No shared table cross service.
  • Cross query via API event.
  • Polyglot per pattern.
  • Shared DB anti-pattern.

What

API Gateway generic edge all clients vs BFF Backend-for-Frontend per client type (mobile/web) aggregate/transform API cho UI.

Why

Mobile cần payload nhỏ khác web; BFF tránh over-fetching generic API; Gateway handle infra concerns.

How

Mobile App → Mobile BFF aggregate 3 calls → Gateway → microservices. Gateway: auth rate limit routing. BFF: shape response UI-specific.

Mobile App

  • Generic — mọi client

  • Transform response shape

BFF: multiple client types different UX needs. Gateway: always public edge.

When NOT

Không BFF per developer — per client type. Không business logic Gateway — domain service. Không duplicate BFF logic — share domain API.

Use case

Web BFF aggregate order+lines+tracking 1 call; Gateway SSL JWT rate limit.

Pitfall / Interview trap

BFF too fat becomes monolith; gateway vs BFF responsibility blur.

Nói trong 60 giây

Q6 CAP trong microservices?

What

CAP trong microservices context: khi partition chọn CP (consistent unavailable) vs AP (available stale) per service business impact.

Why

Không one-size — payment CP, catalog AP. Design each bounded context trade-off.

How

Order/Payment: CP PostgreSQL strong consistency. Product catalog: AP cache stale OK sync later. Inventory: CP or saga compensation.

  • Order/Payment service: CP — không chấp nhận inconsistent balance
  • Product catalog: AP — hiển thị stale price tạm OK, sync sau
  • Inventory reservation: CP hoặc saga với compensation
When

Architecture review assign CAP profile per service. Partition assume always possible datacenter.

When NOT

Không AP payment balance. Không ignore partition rare — design assume P. Không CAP thay business risk analysis.

Use case

Catalog AP Redis cache 30s stale; Payment CP no stale balance.

Pitfall / Interview trap

CAP-C vs ACID-C confusion; all AP wrong.

Nói trong 60 giây
  • Partition choose C or A per service.
  • Payment CP catalog AP.
  • Assume partition possible.
  • Business impact drives choice.
  • Not all services same CAP.

Q7 Eventual Consistency patterns?

What

Eventual consistency patterns: event-driven sync, read repair, compensating transaction, UI processing hint.

Why

Microservices không global TX — user và dev phải chấp nhận delay vài giây với mitigation UX.

How

Event chain OrderCreated→ReserveStock→Charge. Read repair detect stale trigger sync. Compensate fail step. UI 'Đang xử lý' not fake instant.

Write (strong)
  • Event-driven sync: OrderCreated → InventoryReserved → PaymentCharged
  • Read repair: Phát hiện stale read → trigger sync
  • Compensating transaction: Rollback logic khi step fail
  • UI hint: "Đơn hàng đang xử lý" thay vì giả vờ instant
When

Cross-service flow saga outbox. Read replica dashboard. Cross-region replication.

When NOT

Không eventual checkout payment confirmation without clear UX. Không read repair production without monitoring stale detection.

Use case

Order placed UI spinner 3s until PaymentCharged event update status.

Pitfall / Interview trap

User expect instant; missing compensate stuck state.

Nói trong 60 giây
  • Event-driven sync chain.
  • Compensating fail step undo.
  • UI hint processing not instant.
  • Read repair stale detect.
  • Accept seconds delay cross svc.

Q8 Idempotency trong distributed systems?

What

Idempotency — cùng request/event xử lý nhiều lần = kết quả như 1 lần. Network retry duplicate message inevitable.

Why

Kafka at-least-once, HTTP retry, duplicate webhook — double charge double reserve without idempotency.

How

Idempotency-Key header unique index return cached. processed_events table event_id dedup. Natural idempotency SET balance=100 not +=10.

@KafkaListener(topics = "payment-events")
public void handle(PaymentEvent event) {
  if (processedRepo.existsByEventId(event.getId())) {
    return; // already processed — skip
  }
  paymentService.charge(event);
  processedRepo.save(new ProcessedEvent(event.getId()));
}
When

Mọi payment/charge endpoint. Kafka consumer mutate state. Outbox relay duplicate.

When NOT

Không idempotency key TTL quá ngắn retry window. Không check-then-act race — unique constraint DB. Không skip idempotent consumer khi at-least-once.

Use case

Payment Idempotency-Key duplicate POST return same paymentId no double charge.

Pitfall / Interview trap

Check-then-insert race; idempotency vs concurrency.

Nói trong 60 giây
  • Retry causes duplicate delivery.
  • Idempotency-Key unique index.
  • processed event_id dedup table.
  • Natural idempotent SET not +=.
  • Consumer must idempotent at-least-once.

Q9 CQRS (Command Query Responsibility Segregation)?

What

CQRS — tách Write model (commands business logic) và Read model (denormalized optimized queries).

Why

Read/write ratio cao, query pattern khác write schema — scale read independent projection.

How

Command → Write DB → domain event → Read DB projection denormalized. Query hits Read DB direct not Write.

Command
When

Dashboard realtime task status WMS OMS. High read scale search list different write aggregate.

When NOT

Không CQRS simple CRUD 10 field — over-engineer. Không skip eventual lag read model — not strong consistent instant. Không 2 model without sync strategy.

Use case

Write create pick task; Read dashboard denormalized task+order+customer view.

Pitfall / Interview trap

CQRS complexity; projection lag UX.

Nói trong 60 giây
  • Separate write command read query.
  • Write DB event projection read DB.
  • Scale read independent.
  • WMS dashboard read model.
  • Not for simple CRUD.

Q10 Event Sourcing?

What

Event Sourcing — lưu immutable event stream thay current state; rebuild state replay fold events.

Why

Full audit trail temporal query debug replay — inventory mọi movement event không chỉ qty hiện tại.

How

InventoryReceived +10, InventoryPicked -3 → currentQty fold sum. Event store append-only; snapshot periodic performance.

// Events thay vì UPDATE inventory SET qty=5
InventoryReceived(sku="A", qty=10, at=...)
InventoryPicked(sku="A", qty=3, at=...)
// Current qty = fold(events) = 10 - 3 = 7

public int currentQty(String sku) {
  return eventStore.load(sku).stream()
    .mapToInt(InventoryEvent::delta).sum();
}
  • Ưu: Full audit trail, temporal queries, debug replay
  • Nhược: Complexity, eventual read model, schema evolution events
When

Audit compliance critical financial inventory. Temporal 'qty at time T' query.

When NOT

Không event sourcing mọi CRUD — complexity schema evolution. Không DELETE event — contradict immutable. Không skip read model projection — query slow replay all.

Use case

WMS inventory event log every pick putaway rebuild qty audit dispute.

Pitfall / Interview trap

Event schema migration; snapshot strategy; not true undo DELETE.

Nói trong 60 giây
  • Store events not just state.
  • Rebuild fold replay events.
  • Full audit trail temporal.
  • Snapshot periodic performance.
  • Complexity schema evolution.

Q11 Bulkhead Pattern?

What

Bulkhead — cô lập resource pool (thread/semaphore/connection) — failure một dependency không sink toàn system.

Why

Payment slow không chiếm hết Tomcat threads Inventory cần — vách ngăn tàu metaphor.

How

Resilience4j @Bulkhead separate thread pool per dependency. Semaphore max 5 parallel WCS calls. Separate Hikari pool per DB.

IsolationCơ chếVí dụ
Thread poolPool riêng per dependencyPayment pool 10 threads, Inventory pool 20
SemaphoreGiới hạn concurrent callsMax 5 parallel calls tới legacy WCS

public PaymentResult charge(PaymentRequest req) { ... }
When

Multiple external dependencies varying SLA. Legacy WCS slow protect main API pool.

When NOT

Không bulkhead thay circuit breaker — complementary. Không pool quá nhỏ starve legit traffic. Không shared pool all deps — defeats purpose.

Use case

Payment bulkhead 10 threads; Inventory 30 threads — payment timeout không block inventory.

Pitfall / Interview trap

Bulkhead + CB + Timeout together; thread pool sizing.

Nói trong 60 giây
  • Isolate resource pools per dep.
  • Thread pool semaphore bulkhead.
  • Failure contained not cascade.
  • Resilience4j @Bulkhead.
  • Complement CB timeout retry.

Q12 Service Mesh (Istio, Linkerd)?

What

Service Mesh (Istio/Linkerd) — sidecar proxy (Envoy) handle mTLS, traffic canary, retry, timeout, observability service-to-service.

Why

Language-agnostic infra layer — không mỗi Java service copy retry mTLS logic.

Service A

  • Observability: Metrics, tracing, access log

When NOT

Operational complexity; sidecar resource cost; debug harder.

  • Sidecar proxy Envoy per pod.
  • mTLS traffic canary retry.
  • Istio Linkerd control plane.
  • >20 services zero-trust.
  • Small team Gateway Resilience4j enough.

Q13 Circuit Breaker (Resilience4j) — CLOSED / OPEN / HALF-OPEN?

What

Circuit Breaker là cơ chế bảo vệ caller khỏi cascade failure: khi dependency (Inventory, Payment, legacy WCS) liên tục timeout hoặc trả lỗi, breaker ngắt mạch — từ chối gọi ngay (fail-fast) thay vì giữ thread chờ. Resilience4j quản lý 3 trạng thái: CLOSED (bình thường, đo failure rate trên sliding window), OPEN (reject mọi call, trả fallback hoặc exception), HALF-OPEN (cho phép số call thử nghiệm giới hạn để kiểm tra dependency đã hồi phục chưa).

Why

Microservices sync (Feign/gRPC) tạo chuỗi phụ thuộc: Order → Inventory → WMS. Một service chậm làm cạn thread pool toàn bộ caller — retry storm càng làm downstream sụp nhanh hơn. Circuit breaker cắt vòng lặp sớm, giữ capacity cho request khác và cho phép dependency thở (recovery time). Kết hợp Bulkhead + Timeout: breaker là lớp phòng thủ cuối sau khi retry đã thất bại.

CLOSED
calls pass → đo failure%
↓ failure rate > threshold (vd: 50% / 10 calls) HOẶC slow call rate cao
OPEN
reject all → fallback / CallNotPermittedException
↓ waitDurationInOpenState (vd: 30s) hết hạn
HALF-OPEN
permittedNumberOfCallsInHalfOpenState (vd: 3 probe calls)
↓ probe success → CLOSED  |  probe fail → OPEN (reset timer)
How

Resilience4j dùng CircuitBreakerRegistry + sliding window đếm failure/slow call. Cấu hình qua application.yml: failureRateThreshold, waitDurationInOpenState, minimumNumberOfCalls, permittedNumberOfCallsInHalfOpenState. Annotation @CircuitBreaker bọc method; khi OPEN, gọi fallbackMethod. Metrics export qua Micrometer: resilience4j.circuitbreaker.state, calls — alert khi state=OPEN kéo dài.

StateHành viCaller nhậnChuyển state khi
CLOSEDForward mọi requestResponse bình thường hoặc lỗi thậtFailure rate vượt ngưỡng → OPEN
OPENFail-fast, không gọi downstreamFallback / cached / degraded modeTimer hết → HALF-OPEN
HALF-OPENProbe N call thửSuccess → real response; fail → fallbackĐủ probe OK → CLOSED; fail → OPEN
When

Gọi dependency không kiểm soát được SLA: third-party payment, legacy WCS TCP, catalog service quá tải peak sale. Đặc biệt khi caller có thread pool hữu hạn (Tomcat 200 threads) và downstream latency spike 5s → 30s. Fallback hợp lệ: cache stock cũ, default "unknown availability", queue async thay vì block.

When NOT

Không bọc operation bắt buộc strong consistency mà fallback gây sai nghiệp vụ (charge payment với số dư cache cũ). Không dùng breaker thay Retry/Timeout — thiếu timeout thì OPEN muộn, thread vẫn chết. Tránh breaker trên internal DB call cùng JVM — dùng connection pool + query timeout. Không set minimumNumberOfCalls=1 trên traffic thấp → flapping OPEN/CLOSED liên tục.

// application.yml — Resilience4j Circuit Breaker
resilience4j.circuitbreaker:
  instances:
    inventory:
      slidingWindowSize: 20
      failureRateThreshold: 50
      waitDurationInOpenState: 30s
      permittedNumberOfCallsInHalfOpenState: 3
      slowCallDurationThreshold: 2s
      slowCallRateThreshold: 80

@CircuitBreaker(name = "inventory", fallbackMethod = "fallbackStock")
@Retry(name = "inventory")       // retry TRƯỚC khi breaker đếm failure
@TimeLimiter(name = "inventory")   // timeout 3s
public CompletableFuture<StockResponse> getStockAsync(String sku) {
  return CompletableFuture.supplyAsync(() -> inventoryClient.getStock(sku));
}

public StockResponse fallbackStock(String sku, Throwable t) {
  return stockCache.get(sku)                      // stale-while-degrade
      .orElse(StockResponse.unknown(sku));
}
Use case — WMS OMS gọi WCS legacy
Peak wave release: 500 pick task/giây gọi WCS reservation API. WCS restart → latency 10s. Circuit breaker OPEN sau 30s, Order service trả "task queued" thay vì treo 200 Tomcat threads; sau HALF-OPEN probe OK, traffic restore tự động.
Pitfall / Interview trap
"Retry + Circuit Breaker cùng lúc có conflict không?" — Retry chạy trong CLOSED; mỗi retry fail đều đếm vào window. Pitfall: fallback không idempotent (double-reserve stock). Trap: HALF-OPEN chỉ 1 probe call nhưng traffic burst → probe success nhưng call tiếp theo fail ngay → flapping. Fix: permittedNumberOfCallsInHalfOpenState ≥ 3 + alert on OPEN duration.
Nói trong 60 giây
  • Circuit Breaker = cầu dao tự ngắt khi dependency lỗi liên tục — tránh cascade failure.
  • 3 state Resilience4j: CLOSED bình thường → OPEN fail-fast + fallback → HALF-OPEN probe thử → success thì CLOSED.
  • Cấu hình: failure rate threshold, wait duration OPEN, số probe HALF-OPEN.
  • Kết hợp Timeout + Retry + Bulkhead; fallback phải an toàn nghiệp vụ (cache, degraded).
  • Không dùng cho payment bắt buộc real-time balance; monitor metric state=OPEN.

Q14 Saga Pattern — Choreography vs Orchestration + Compensating?

What

Saga là chuỗi local transactions phân tán — mỗi service commit DB riêng, không có 2PC/XA cross-DB. Khi một bước fail, saga chạy compensating transactions (hành động nghiệp vụ undo: release stock, refund, cancel shipment) theo thứ tự ngược. Hai style: Choreography (services tự phản ứng event, không coordinator trung tâm) và Orchestration (Saga Orchestrator gọi từng participant theo state machine).

Why

Database-per-service loại bỏ distributed ACID. Order + Inventory + Payment không thể BEGIN GLOBAL TX. Saga chấp nhận eventual consistency nhưng đảm bảo business invariant: không vừa charge tiền vừa không reserve stock. Compensating ≠ rollback SQL — là logic nghiệp vụ (refund có thể mất phí, email đã gửi không "unsend").

Choreography

  • Order publish OrderCreated → Inventory listen, publish StockReserved → Payment listen
  • Loose coupling, không single point of failure
  • Compensate: Payment publish PaymentFailed → Inventory tự ReleaseStock
  • Khó trace/debug khi ≥5 services; implicit flow trong event graph

Orchestration

  • State machine rõ: PENDING → RESERVED → PAID → CONFIRMED | COMPENSATING
  • Fail path explicit: onPaymentFail → compensateInventory → compensateOrder

How

Choreography: mỗi service subscribe event, thực hiện local TX + publish event tiếp; dùng Outbox đảm bảo publish atomic với DB write. Orchestration: orchestrator lưu saga instance state, gọi participant API, timeout → trigger compensate. Cả hai cần: saga ID correlation, idempotent compensate handler, timeout per step, dead-letter cho compensate fail (manual intervention).

When

Long-running business flow cross-service: place order, booking travel, WMS wave release (allocate → pick → ship). Flow có ≥3 bước và chấp nhận vài giây eventual consistency. Orchestration khi flow phức tạp, cần visibility SLA, audit compliance. Choreography khi team độc lập, event-driven culture mạnh, flow đơn giản linear.

When NOT

Không dùng saga khi cần strong consistency ngay lập tức (chuyển tiền real-time giữa 2 ledger — cân nhắc 2PC hoặc single service). Không compensate được (physical action: hàng đã lên xe). Tránh choreography cho flow có branch/parallel phức tạp — debug nightmare. Không quên: compensate cũng có thể fail → cần retry + alerting, không assume auto-heal.

// Orchestration-style Saga Orchestrator (simplified)
@Service
public class OrderSagaOrchestrator {
  public void execute(CreateOrderCommand cmd) {
    String sagaId = cmd.getSagaId();
    try {
      orderService.createPending(cmd);                    // step 1
      inventoryClient.reserve(sagaId, cmd.getLines());    // step 2
      paymentClient.charge(sagaId, cmd.getTotal());       // step 3 — FAIL here
      orderService.confirm(cmd.getOrderId());
    } catch (PaymentException ex) {
      compensate(sagaId, cmd);  // reverse order: release → cancel
    }
  }

  private void compensate(String sagaId, CreateOrderCommand cmd) {
    inventoryClient.release(sagaId);   // idempotent: IF reserved THEN release
    orderService.cancel(cmd.getOrderId());
    sagaLog.markCompensated(sagaId);
  }
}
Use case — OMS outbound wave
WMS release wave: Allocate bins → Lock inventory → Dispatch WCS tasks → Confirm ERP. Payment step fail (credit hold expired) → compensate: cancel WCS tasks, release bin locks, revert allocation. Orchestrator giữ snapshot trạng thái từng step cho operator dashboard.
Pitfall / Interview trap
"Saga = eventual consistency, vậy user thấy gì?" — UI hiển thị PENDING/COMPENSATING, không fake CONFIRMED. Trap: compensate không idempotent → retry release stock 2 lần → oversell. Trap: choreography cyclic event (A→B→A) — thiếu saga timeout. "Saga vs 2PC?" — Saga availability cao hơn, trade-off temporary inconsistency window.
Nói trong 60 giây
  • Saga = chuỗi local TX phân tán, không 2PC; fail thì compensate ngược thứ tự.
  • Choreography: event-driven, decentralized; Orchestration: coordinator + state machine.
  • Compensating ≠ SQL rollback — release stock, refund, cancel shipment; phải idempotent.
  • Happy path: Create → Reserve → Pay → Confirm; fail path: Pay fail → Release → Cancel.
  • Dùng khi database-per-service; không dùng khi cần instant strong consistency.

Q16 Transactional Outbox Pattern — giải quyết Dual-Write?

What

Transactional Outbox giải bài toán dual-write: service cần vừa ghi DB vừa publish message (Kafka) nhưng hai thao tác không nằm cùng transaction — crash giữa chừng gây mất event hoặc duplicate. Naive approach: save(order); kafka.send(event); — nếu crash sau save trước send → downstream không biết order mới (inventory không reserve). Ngược lại send trước save fail → ghost event. Trong saga/event-driven, mất event = stuck saga; duplicate event = double charge nếu consumer không idempotent. Outbox biến "2 writes" thành "1 atomic DB TX + 1 at-least-once relay".

Q23 Phân rã service: Business Capability vs Bounded Context (DDD)?

What

Decompose by business capability — mỗi service ứng với một năng lực tạo giá trị của doanh nghiệp (Order Management, Inventory Management). Decompose by subdomain (DDD) — mỗi service là một bounded context, phân loại core / supporting / generic subdomain.

Why

Ranh giới sai sinh ra distributed monolith: service gọi nhau chatty, dùng chung DB, đổi một field vỡ cả chuỗi. Ranh giới đúng cho team autonomous (two-pizza, 6-10 người), deploy độc lập, mỗi thay đổi chỉ chạm một service (Common Closure Principle).

How

Bước 1: liệt kê business capability từ cơ cấu tổ chức + domain model cấp cao. Bước 2: vẽ các bounded context (DDD) và gắn nhãn core (tự làm, tạo khác biệt) / supporting / generic (mua hoặc SaaS). Bước 3: map 1 context = 1 service + DB riêng, giao tiếp qua API/event chứ không share bảng. Áp SRP (một lý do để thay đổi) và CCP (thứ thay đổi cùng nhau thì đóng gói cùng nhau).

  • Xuất phát từ org structure và domain model
  • Khớp trực tiếp với team autonomous

Bounded Context (DDD subdomain)

  • Góc nhìn: ngôn ngữ và domain model nhất quán
  • Chia core / supporting / generic subdomain
  • Đặt tên theo ubiquitous language
  • Sát code hơn, cho biên module rõ ràng

Q24 Retry sao cho không tạo "retry storm" (Exponential Backoff + Jitter)?

What

Retry chỉ cho lỗi tạm thời, kèm exponential backoff (delay tăng gấp đôi mỗi lần) + jitter (thêm ngẫu nhiên) + số lần thử tối đa + retry budget. Retry storm / thundering herd xảy ra khi mọi client retry đồng bộ cùng thời điểm.

Why

Khi sự cố do quá tải, backoff thường không giúp đúng như kỳ vọng vì tương quan: mọi call lỗi backoff về cùng một mốc rồi retry cùng lúc, gây quá tải lần nữa. Jitter rải các lần retry ra theo thời gian (AWS Builders' Library).

How

delay = min(cap, base × 2attempt) rồi cộng jitter. Chỉ retry thao tác idempotent (GET/PUT/DELETE, POST có idempotency key). Giới hạn retry budget (ví dụ không quá 10% tổng request). Ghép với timeout và circuit breaker; không retry lỗi 4xx không thể phục hồi.

Bổ sung chiều sâu phỏng vấn

Ví dụ thiết kế ngân hàng: tách monolith và saga không giả mạo kinh nghiệm

What

Ví dụ giả định: tách Notification khỏi banking monolith trước, giữ debit/credit và double-entry ledger trong một transaction có invariant rõ. Saga phù hợp workflow liên dịch vụ có trạng thái pending và compensation, không thay atomic ledger posting bằng hai API độc lập.

Phạm vi và cách trình bày

Đây là bài tập thiết kế minh họa, không phải dự án cá nhân đã triển khai. Khi phỏng vấn, nói “Tôi đề xuất với giả định…”; chỉ nêu kinh nghiệm thực nếu thực sự có. Liệt kê constraint: audit, idempotency, reconciliation, latency, giới hạn mất dữ liệu và quyền sở hữu ledger.

Strangler từng bước

Đo baseline và vẽ bounded context; bắt đầu Notification hoặc Reporting read model có coupling thấp. Giữ contract ổn định qua facade/anti-corruption layer, phát event bằng outbox, shadow compare trước cutover, rollback routing được. Tránh cùng lúc tách service, đổi DB và đổi domain rule. Mỗi dữ liệu chỉ có một writer authority trong giai đoạn chuyển.

Ledger boundary

Chuyển khoản nội bộ cùng ledger: một local transaction ghi bút toán debit và credit cân bằng, unique transfer/idempotency key, kiểm soát số dư bằng locking hoặc constraint phù hợp. Timeout response không có nghĩa transfer thất bại: tra trạng thái theo idempotency key trước retry. Không dùng saga “trừ tài khoản A rồi cộng B” nếu yêu cầu atomic ngay trong một ledger.

Saga ngoài boundary

Chuyển liên ngân hàng giả định: CreateTransfer(PENDING) → reserve funds → submit external rail → settlement confirmation → post/finalize theo policy ledger. Timeout external rail là UNKNOWN, không tự refund khi có thể đã settle. Query/reconcile hoặc xử lý manual; compensation là release reservation/reversal posting có audit, không xóa bút toán lịch sử. State machine cần durable state, idempotent command, bounded retry, timeout và operator queue.

Đánh giá trade-off

XA/2PC có thể dùng khi resource manager và yêu cầu cho phép, nhưng khóa lâu/coordinator failure có chi phí. Saga cho availability và long-running workflow nhưng có cửa sổ bất nhất và compensation failure. Không khẳng định mọi banking flow dùng saga hoặc microservices luôn tốt hơn modular monolith. Test duplicate, out-of-order, crash sau commit, timeout không rõ kết quả và reconciliation.
